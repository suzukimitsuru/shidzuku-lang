## 1. フェーズ計画

### Phase 0 — 言語仕様(2026-11-07 に閉じた)

- 第0章 ビジョン(本書と対の `00-vision.md`)✅ 初稿
- 第1章 システムコンテキスト(システムの宣言、外部の人と外部システム、動作環境の位置づけ)✅ 初稿
- 第2章 コンポーネントの定義(コンポーネントの宣言構文、三層記述の形式)✅ 初稿
- 第3章 制約の体系(検証可能な意図の一覧と検証時期: コンパイル時/実行時)✅ 初稿
- 第4章 通信モデル(コンポーネント間の接続、フローの記述)✅ 初稿
- 第5章 記述の表記(ソースの符号化、言語の語彙と記述者の名前、識別子の規則)✅ 初稿
- 第6章 データと型(データ宣言 `record`・`choice`・`id`、基本型10、数値と量と単位、時間の3層と暦)✅ 初稿
- 章の順序は C4 モデルの4段(Context / Container / Component / Code)に対応する(ADR 0015)。Container は言語の記述対象外。
  第4章(通信)・第5章(表記)・第6章(データと型)は段に属さず段を跨ぐため、段の順の後ろに置く
- **検証方法**: 既存の小さなシステム(例: Web API+DB の小規模サービス、パイプライン処理)を Shidzuku で「記述してみる」思考実験。書けない事があれば仕様に戻す。
- **閉じ方**: [ADR 0033(試作を先に置く進め方)](decisions/0033-試作を先に置く進め方.md) により、2026-11-07 に閉じた。成果物は初稿の仕様書(第0〜6章)と採用済みの ADR である。
  「動く最小の成果物」では締められなかった。未決の課題(U10・U11・U12・U14・U20・U26 ほか)は、Phase 1 の試作の中で仮に決めて確かめる(第4節「仮置き」)

### Phase 1 — 最小の言語実装(現在地)

- パーサ+検証器+トランスパイラ+動作環境の最小構成を、三つの試作で順に作る(ADR 0033 の決定3(三つの試作))。試作の順と仮置きは第4節に置く
  - **細い縦の試作** — 思考実験 02(センサー収集パイプライン)の SensorIntake と Normalizer を `flow` 一本で繋ぎ、1プロセスで動かす
  - **再起動と版の入れ替えの試作** — 落ちた Normalizer を動作環境が再起動し、Normalizer の新しい版を流れを止めずに入れ替える
  - **混在の試作** — 1つのコンポーネントを TypeScript の出力に差し替えても同じ流れが動く。題材を第1段から第3段へ増やす
- トランスパイル先は TypeScript と Rust の2言語とする(課題 U5、ADR 0012 採用)。動作環境は Rust の1実装とし、コンポーネントのみをトランスパイル先の言語で書く
- 実装の順序は Rust が先。ただし接合面(コンポーネントと動作環境の境界)の凍結は TypeScript が通ってから
- 成果物: 三つの試作が `examples/` で動く。三層記述を持つコンポーネントを 2〜3 個接続したプログラムが動き、そのうち 1 コンポーネントを別言語の出力に差し替えても同じフローが動く(混在の適合試験)
- 仕様書は、試作で動いた事を書き戻す場所とする。ADR を起こすのは、二つ以上の候補を比べて選ぶ時だけとする(ADR 0033 の決定4(書き戻し))
- 既存の言語(Rust・TypeScript)への lint である shidzuku-lint は、細い縦の試作の検証器ができてから着手し、検証器と規則の一覧を共有する。Phase 2 以降も継続して改良する(ADR 0026・0033)

### Phase 2 — 最小の分散動作環境

- コンポーネント=配置単位を実際に複数プロセス/ノードへ配置する実行系
- Raft による合意(自作せず既存ライブラリ利用を第一候補とする)
- ログ規約からの自動出力
- 再起動と版の入れ替えは、Phase 1 の試作で1プロセスの中で先に確かめてあるものを、ノードを跨いで行う
- 成果物: 小さな分散システム(例: KV ストア)が「静かに」動き、ノード障害時に伝播しない事を確認
- 最小の動作環境として ESP32 の器を作る(ADR 0029(最小の動作環境))。PC 1台と ESP32 1台で思考実験 02(センサー収集パイプライン)の上流(SensorIntake・Normalizer)を動かし、ノードを跨いだ `pressure` と障害の非伝播を実機で見る。
  動作環境は意味の核(`no_std` の1クレート)と器(PC・ESP32)に分け、意味の核は最小の言語実装(Phase 1)の動作環境の着手時から `no_std` で作る
  ボードは ADR 0030(ESP32 ボードの選定)で決めた。一体の書き込みには ESP32-C6-DevKitC-1 を4枚(開発2・セキュアブートの確かめ1・予備1)、WASM でのロードには ESP32-S3-DevKitC-1 を使う

### Phase 3 — 可視化

- コードからの構造図・フロー図・障害境界図の抽出
- 図の段は C4 の4段(ADR 0015)とし、図の形式そのものは Shidzuku の三層記述とコンポーネントに即して設計する
- システムの入れ子(ADR 0018)により、Context 図はルートから1段掘るごとに1枚出る。最上段が C4 の System Landscape 図に当たる

## 3. 決定の記録(ADR 一覧)

ADR の番号・題名・領域は [docs/numbering.md](numbering.md) に、状態・対応課題・決めた事は、担当する領域の README の「ADR」に置く。
課題と ADR の関係図は [docs/roadmap.html](roadmap.html) 第2節 2-1(検討の領域)に、領域ごとに置く。

- 状態「採用」は現在の仕様の裏付けであり、第0〜6章はこれに依拠して書かれている。
- 状態「提案」は判断待ちを表す。2026-09-26 の ADR 0023 の採用で判断待ちは一度無くなり、**同日に思考実験 23 から 0024・0025 を起案した**(第7節 7.8)。**2026-09-28 に2本とも採用した**(第7節 7.13)。同日に U26 の ADR 0027 を起票した(提案)。
- ADR 0009・0010・0013・0017・0019・0020 は基本型を共に改訂する。2026-08-29 に全て採用され第6章として仕様書に入ったが、**2026-09-03 に 0010・0017 を破棄し、数値型の変換規則(0019 決定2・7)を凍結した**。**2026-09-16 に ADR 0021 を採用して数値型が確定し、凍結は解けた**(0019 決定2・決定7 は 0021 が置き換えた)。基本型10のうち非数値の部分(論理・テキスト・バイト列・時点・日付・時刻・時間帯・暦)は一連の変更の影響を受けていない。
- 検証番号は `E<出自>-<連番>` である(ADR 0016)。出自はその検査を定めた ADR の番号であり、`0000` は仕様書本体を表す。
  ADR と思考実験は旧番号(E1・E17 等)のまま残るため、読み替え表を第3章 3.3 に置いた。
- ADR 間の改訂関係: 0008 が 0004・0005 を、0010 と 0013 が 0009 を、0013 が 0005 を、0015 が 0007・0014 を、0017 が 0010 を、0019 が 0009・0010・0017・0014 を、0020 が 0019 をそれぞれ改訂する。
  0021 は破棄した 0010・0017 の後継であり、0019 の決定2・決定7 の凍結を解いた(決定7 は 0021 が置き換え、決定2 の `整数` は `intN(s)`・`uintN(s)` に置き換わった。2026-09-16 採用)。
  0022 は 0021 の決定4(`unitless` とのスカラー倍)・決定11(添字と長さの型)を改訂する。改訂される側の 0021 は採用済みのため単独で判断でき、2026-09-17 に起案と同日に採用した。
  0025 は 0006 に分割・統合・束ね方のシグナルを足す(骨格は変えない)。依拠する 0024 と同時に、2026-09-28 に採用した。
  0028 は 0009 の宣言の語 `data` を `record`・`choice`・`id` に分ける。0009 の他の決定は変えない。起案と同日の 2026-09-29 に採用した。
- ADR 0014 は表記の基準であり、ADR 0009・0010・0013・0017・0019・0020 の日本語の語彙は採用時に対応表で英字へ読み替える(各 ADR の本文は履歴として残す)。
- ADR 0017 は起案時 0016 を名乗っていたが、採用済みの ADR 0016(検証番号の採番規則)と衝突したため 0017 に振り直した(2026-08-29)。
  検証番号も `E<出自>-<連番>` 形式へ改めてある(E0017-1・W0017-1・W0017-2)。**ADR 0017 自体は 2026-09-03 に破棄した。**
- ADR 0015 は 0014 の語彙表から `measure` を外して `unit` に戻し、ユニットの綴りを `component` に改める。旧称の読み替えは 0015 の決定4の対応表による。
- ADR 0014 は 2026-08-29 に採用し、第5章「記述の表記」を新設して反映した。基本型の語彙は同日のステップ2 の採用で第5章 5.3 に入った(8区分)。
- ADR 0018 は 0015 の決定2(1プログラム = 1システム)・決定7(E0015-2・E0015-3)・机上検証の発見1(外部システムの判定基準)を改訂する。改訂される側の 0015 が先に採用されているため、0018 は単独で採否を判断できた。
  2026-09-25 に、混在した `contains` の中で呼び合えない穴を塞ぐ改訂を経て採用した(第7節 7.1)。
- ADR 0019 は 0009 の基本型の一覧を確定し、0010 の量の体系に `量 時間` を加え、0017 の E0017-1 を整数へ広げ、0014 の基本型の語彙表を差し替える。**0010・0017 は 2026-09-03 に破棄され、0019 の該当決定(決定2・7)は 2026-09-16 に ADR 0021 が置き換えて凍結が解けた**(第7節 7.1)。
- ADR 0020 は 0019 の決定5(言語が持つ暦は算術暦だけ)を改訂し、記述者が紀年法を宣言できるようにする。0019 の他の決定は1つも取り消さない。
- ADR 0002 は課題 U1〜U18 の外にあるが、命名の経緯を残すため ADR とした。
- 採否の順序と、同時に採否を判断するステップは第4節に置く。ステップ1(ADR 0014・0015)は採用済み、ステップ2 は 0009・0019・0020 と、数値型を引き取った 0021 が採用済みである。
  0010・0017 は破棄され、数値型は思考実験 14〜18 を経て ADR 0021 として起案し直し、2026-09-16 に採用した(第7節 7.1)。
  ステップ5 の 0012 は 2026-09-17 に、ステップ3 の 0006 は 2026-09-18 に、ステップ4 の 0018 は 2026-09-25 に採用した(第7節 7.1)。
  ステップ4 の新規 ADR として起案した 0023 も同日に採用し(2026-09-26)、全てのステップが一度空になった。
  同日に起案した 0024・0025 はステップ3 に入れ、2026-09-28 に同時に採用した(第4節 4.1)。
  0022(単位の種別)は 0021 を改訂する型の ADR としてステップ2 に入れ、2026-09-17 に起案と同日に採用した。

### 試作の順

各試作は動く物で締め、`examples/` に置く。前の試作が動くまで次へ進まない(ADR 0033 の決定3(三つの試作))。

| 試作                       | 題材と範囲                                                                                                                                                | 締めの確かめ                                                                                                                 | 確かめる要件                         |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 細い縦の試作               | [思考実験 02(センサー収集パイプライン)](experiments/02-センサー収集パイプライン.md) の SensorIntake と Normalizer を `flow` 一本で繋ぎ、1プロセスで動かす | 記述から生成した Rust が動き、試験の口から流した計測値が正規化されて受け口に届く。`pressure` を書かない記述を検証器が拒む    | データフロー言語として動く事         |
| 再起動と版の入れ替えの試作 | 同じ題材。Normalizer が落ちたら動作環境が再起動する。Normalizer の新しい版を、流れを止めずに入れ替える。1プロセスのまま                                   | 故意の障害の後も流れが止まらず、`durable` の流れは失われない。版を入れ替えても受け口に届く値が途切れない                     | 動作環境が再起動と版の更新を行う事   |
| 混在の試作                 | 1つのコンポーネントを TypeScript の出力に差し替える。題材を下の「題材の段」の第1段から第3段へ増やす                                                       | 差し替えても同じ試験が通る。通った時に接合面を凍結する(ADR 0012(動作環境の言語とトランスパイル先の言語)の決定10(凍結の時期)) | 一本の記述から二つの言語へ落とせる事 |

- 細い縦の試作のパーサは `system`・`component`・`intent`・`constraint`・`flow` を読み、body は読まない。検証器は省略の禁止のうち、`intent` と、接続の `pressure`・配達保証の必須だけを見る。
  データの型は、計測値の `record` 一つを読むのに要る分だけ作る
- 動作環境は Rust で作り、意味の核を標準ライブラリに依らない1つのクレートにする事は、細い縦の試作から守る(ADR 0029(最小の動作環境)の決定1(意味の核を1つのクレートにする))
- shidzuku-lint は、細い縦の試作の検証器ができてから着手する(ADR 0026(shidzuku-lint の作成)の決定2(時期)の範囲の中)
- 道のりの図は [docs/roadmap.html](roadmap.html) 第3節に置く

## 9. 進め方の原則

- 課題(U1〜)の決定は `docs/decisions/` に ADR として残す(自分の言語の思想「意図を残す」を、開発プロセス自身にも適用する)。
  ADR を起こすのは、二つ以上の候補を比べて選ぶ時である。試作で一つに決まった事は仕様書に書き戻し、担当する領域の経緯に一行残す(ADR 0033 の決定4(書き戻し))
- 各フェーズは「動く最小の成果物」で締める。仕様だけが先行して空転しない
- 未決の課題は試作の中で仮に決め、動かして確かめてから決める。仮置きは第4節の表にだけ置く(ADR 0033 の決定2(仮に決めて確かめる))
- 仕様に迷ったら、まず試作で動かして確かめる。思考実験(既存システムを書いてみる)に戻るのは、候補を比べる時と、まだ作れない段を考える時に限る(ADR 0033 の決定5(思考実験の範囲))
- 文書の運営の規則を増やさない。足したくなったら、試作を妨げた事を理由として ADR に書く(ADR 0033 の決定6(運営の規則を増やさない))
- 略号や番号だけで物を指さない。名前で書き、番号には名前を併記する(検索に掛けるため。`CLAUDE.md` の制約、第7節 7.18)
- 検査を足す時は、既存の言語に移せるかを併せて考える。移せる物は shidzuku-lint の規則にし、lint にする中で見つけた穴は仕様に戻す(ADR 0026)
- 検討は領域の木に分け、検討の作業は持っている領域のファイルだけを書き換える。番号と領域は main の上で予約してから枝を切り、ADR の採用と仕様書への反映は一度に一つずつ行う([docs/areas/README.md](areas/README.md))

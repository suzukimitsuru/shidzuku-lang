# Shidzuku 計画書

- 状態: Draft
- 日付: 2026-08-18
- 進め方: GitHub リポジトリ(`shidzuku-lang`)+ Claude Code で検討・実装を進める

## 1. フェーズ計画

### Phase 0 — 言語仕様(現在地)

- 第0章 ビジョン(本書と対の `00-vision.md`)✅ 初稿
- 第1章 システムコンテキスト(システムの宣言、外部の人と外部システム、動作環境の位置づけ)✅ 初稿
- 第2章 コンポーネントの定義(コンポーネントの宣言構文、三層記述の形式)✅ 初稿
- 第3章 制約の体系(検証可能な意図の一覧と検証時期: コンパイル時/実行時)✅ 初稿
- 第4章 通信モデル(コンポーネント間の接続、フローの記述)✅ 初稿
- 第5章 記述の表記(ソースの符号化、言語の語彙と記述者の名前、識別子の規則)✅ 初稿
- 第6章 データと型(データ宣言 `record`・`choice`・`id`、基本型10、数値と量と単位、時間の3層と暦)✅ 初稿
- 章の順序は C4 モデルの4段(Context / Container / Component / Code)に対応する(ADR 0015)。Container は言語の記述対象外。
  第4章(通信)・第5章(表記)・第6章(データと型)は段に属さず段を跨ぐため、段の順の後ろに置く
- **検証方法**: 既存の小さなシステム(例: Web API+DB の小規模サービス、パイプライン処理)を Shidzuku で「記述してみる」思考実験。書けない事があれば仕様に戻す。

### Phase 1 — 最小の言語実装

- パーサ+検証器+トランスパイラの最小構成
- トランスパイル先は TypeScript と Rust の2言語とする(課題 U5、ADR 0012 採用)。動作環境は Rust の1実装とし、コンポーネントのみをトランスパイル先の言語で書く
- 実装の順序は Rust が先。ただし接合面(コンポーネントと動作環境の境界)の凍結は TypeScript が通ってから
- 成果物: 三層記述を持つコンポーネントを 2〜3 個接続したプログラムが動く。さらに、そのうち 1 コンポーネントを別言語の出力に差し替えても同じフローが動く(混在の適合試験)
- 既存の言語(Rust・TypeScript)への lint である shidzuku-lint も並行して着手し、検証器と規則の一覧を共有する。Phase 2 以降も継続して改良する(ADR 0026)
- 移行の条件(M1〜M5)と、移行までに残る判断は第4節 4.5 に置く

### Phase 2 — 最小の分散動作環境

- コンポーネント=配置単位を実際に複数プロセス/ノードへ配置する実行系
- Raft による合意(自作せず既存ライブラリ利用を第一候補とする)
- ログ規約からの自動出力
- 成果物: 小さな分散システム(例: KV ストア)が「静かに」動き、ノード障害時に伝播しない事を確認
- 最小の動作環境として ESP32 の器を作る(ADR 0029(最小の動作環境))。PC 1台と ESP32 1台で思考実験 02(センサー収集パイプライン)の上流(SensorIntake・Normalizer)を動かし、ノードを跨いだ `pressure` と障害の非伝播を実機で見る。
  動作環境は意味の核(`no_std` の1クレート)と器(PC・ESP32)に分け、意味の核は最小の言語実装(Phase 1)の動作環境の着手時から `no_std` で作る
  ボードは ADR 0030(ESP32 ボードの選定)で決めた。一体の書き込みには ESP32-C6-DevKitC-1 を4枚(開発2・セキュアブートの確かめ1・予備1)、WASM でのロードには ESP32-S3-DevKitC-1 を使う

### Phase 3 — 可視化

- コードからの構造図・フロー図・障害境界図の抽出
- 図の段は C4 の4段(ADR 0015)とし、図の形式そのものは Shidzuku の三層記述とコンポーネントに即して設計する
- システムの入れ子(ADR 0018)により、Context 図はルートから1段掘るごとに1枚出る。最上段が C4 の System Landscape 図に当たる

## 4. ADR の検討順

ADR は互いを改訂する。改訂される側を先に採ると、採用した直後に改訂が入って仕様書を二度書き直す事になる。
改訂する側を先に採ると、依拠先が提案のままで決定が宙に浮く。したがって順序が要る。

順序を決める規則は三つである。

- **R1** 改訂の関係にある ADR は同じ**ステップ**に入れ、同時に採否を判断する(片方だけ採らない)
- **R2** ステップの順序は依拠の向きに従う。**名前 → 型 → 指針 → 接合面**の順である
- **R3** 第2節の「決定フェーズ」より前倒ししない。前倒しは、判断の材料が揃う前に決める事を意味する

課題と ADR とステップの関係図は [docs/roadmap.html](roadmap.html) 第3節に置く。

ステップは 2026-08-28 の採用(ADR 0005・0013・0015)と 2026-08-29 の採用(ADR 0014)、2026-09-17 の採用(ADR 0012)、2026-09-18 の採用(ADR 0006)、2026-09-25 の採用(ADR 0018)を反映してある。
採用済みの ADR はステップから外れ、全てのステップが一度空になった。2026-09-26 に起案した 0024・0025 はステップ3 に入れ、2026-09-28 に採用した。**残るのはステップ4 の新規 ADR(U10〜U14・U20・U26)である。U26 は ADR 0027 として起票した。** ステップの番号は動かさない(採用の記録と対応が付かなくなるため)。

ステップ1 を先頭に置いたのは、これが他の全 ADR の**名前**を決めるからである。
ユニット → コンポーネントの改名(0015)と、日本語の語彙の英字への読み替え(0014)は、
0006・0009・0010・0012・0017・0019・0020 の本文すべてに掛かる。名前を後から変えると、仕様書を二度書き直す事になる。
2026-08-29 に 0014 を採用してステップ1 は空になり、以後の ADR は英字の語彙の上で書ける。

ステップ5 を最後に置くのは、接合面 H1〜H8 が他の決定の**写し**だからである。
H2・H3 は ask の応答待ち(U10)を、H5 は durable な受領と順序(U11)を、H8 は終了の理由(U13)を、H6 はログ規約(U4)を写している。
これらが未決のまま凍結すると、Phase 1 の途中で接合面を書き直す事になる。
なお 0012 の**採否**はステップ2 の後であれば判断できる(出力先の言語に何を要求するか——整数の幅と十進固定小数点——は 0021 が決めた)。
ADR 0021 の採用により、要求は「8〜256 ビットの整数」と「`dec` のための多倍長整数」になり、`float32`・`float64` の側は IEEE 754 を持つ言語ならそのまま通る。
凍結の時期は 0012 の決定10(TypeScript のコンポーネントが同じ H1〜H8 で通ってから)に従う。
**0012 は 2026-09-17 に採用した**(第7節 7.1)。採用したのは接合面の形と分担であり、H1〜H8 の凍結ではない。
したがって上の「写し」の関係は採用後も生きており、ステップ4 の決定が H1〜H8 を改訂し得る。

### 4.5 Phase 1 へ移るまでの計画(2026-09-26、2026-09-28 見直し・決定)

ADR 0023 の採用と[思考実験 22](experiments/22-失敗の棚卸し.md)で、判断待ちの ADR は一度無くなった。
同日に[思考実験 23](experiments/23-結合の釣り合い.md)から ADR 0024・0025 を起案し(7.8)、[思考実験 24](experiments/24-Hikeの取り組み.md)が U10 と Phase 1 への入力を出した(7.9)。
2026-09-27 の[思考実験 25](experiments/25-系の失敗の書き分け.md)(7.10)と、2026-09-28 の[思考実験 26](experiments/26-shidzuku-lint.md)・[ADR 0026](decisions/0026-shidzuku-lintの作成.md)(7.11・7.12)を受けて、2026-09-28 に全体を見直した。
同日、suzukimitsuru が移行の条件・U14 の位置・ADR 0024・0025 の採用を決め、成果物の題材と body の記法について候補を求めた(7.13)。
残る判断を「Phase 1 の前に決める物」「Phase 1 の中で決める物」「Phase 2 以降へ送る物」に分け、移行の条件を定める。
各章の未定事項(第1章 1.8・第3章 3.5・第4章 4.6・第5章 5.8・第6章 6.6)は、全てこのどれかに振り分けた。

#### 移行の条件(2026-09-28 確定)

Phase 1 へ移るのは、次の五つが揃った時とする。

- **M1** Phase 1 の前に決める課題(U10〜U14・U20・U26)が、ADR として採用されている
- **M2** U21 は、採用されているか、Phase 1 の期中へ送る判断が記録されている
- **M3** 接合面の写し元が決まっている——H2・H3(U10)、H5(U11)、H8(U13)。
  H1(U16)と H6(U4)は Phase 1 以降でよい(ADR 0012 決定10: 凍結は TypeScript が通ってから)
- **M4** 成果物の題材を最新の仕様だけで書き下ろし、書けない所が無い(移行点検の思考実験)
- **M5** 判断待ちの ADR が無い。ステップ3 の 0024・0025 は 2026-09-28 に採用した。同日に起票した 0027(U26)を含む。2026-10-08 に起案した 0031(U13)は同日に採用した。
  どちらも Phase 1 の実装には影響しない(7.8)が、提案を残したまま段を移ると、仕様書と ADR のどちらに依拠するかが曖昧になる

M4 は Phase 0 の検証方法(第1節)をそのまま移行の試験に使う。書けない所が出たら、該当する課題へ戻す。
M5 は 0024・0025 の起案を受けて足した。U14 の起案より前に採否を決めるとしていた——0025 の決定3(強く結ぶ物を同じ `contains` に束ねる)と、
思考実験 23 が U14 に渡した K-a(データ宣言は届く範囲に属する)が、同じ物差しに立つためである。2026-09-28 の採用で、この分は満たされた。
以後に起案する ADR(U13・U10・U11・U12・U20・U14・U26)も、採否を移行の前に決める。

**M1 と M2 の中身は、2026-09-28 の決定に合わせて動かした。** U14 を Phase 1 の前に決める事にしたため M2 から M1 へ移し、
新設した U26(body の記法)を M1 に加えた。条件の数と記号は変えていない。
条件の記号を M(移行)としたのは、ADR 0012 のバックエンドの責務 G1〜G7 と取り違えないためである。

**shidzuku-lint の着手も、この条件に従う。** ADR 0026 決定2 は shidzuku-lint を Phase 1 の言語実装と並行して着手し、Phase 0 の間は作らないとした(道具だけを先行させない)。
したがって M1〜M5 は、shidzuku-lang の実装と shidzuku-lint の実装の両方の着手条件になる。
移せる11件と既にある10件の多くは採用済みの検査に依るが、先に作っても、検証器と規則の一覧を共有する(決定2)相手がまだ無い。

- **U20 を U12 と同じ行に加える。** U20 は「層の役割が言う外部とは何か」を問い、U12 は「コンポーネントが外部にどう依存するか」を問う。

- **U14 を Phase 1 の前に置く**(2026-09-28、suzukimitsuru の決定)。U14 の思考実験(思考実験 15・23 の続き)は、U13・U10・U11・U12・U20 と並行して進める(同日の決定)。決定フェーズは Phase 0〜1 だが、パーサが読む単位(ファイルとプログラムの関係)と名前の解決が決まらないと、

- **ask の閉路の扱いを U10・U11 の行に移す。** 第3章 3.5 は依存の循環を Phase 1 の検証器設計で決めるとしていたが、
  思考実験 24 の論点4 は、閉路を検証器で見つける重さを U10 の再入の決定と組にして決めるとした。再入を許さない実行モデルでは、ask の閉路はそのままデッドロックになるためである。

- **U13 の軸(c)は、記述の中の接続に限る**(2026-09-27、suzukimitsuru の判断)。7.10 の F-4 は「全ての接続がどれかのフローに現れる」事を求めるが、
  外部システムは今はフローの端点に書けない(第1章 1.8・第4章 4.6。U12 の未定事項)。そのまま決めると、外部との接続がこの要求を満たせない。
  U13 の ADR では要求の範囲を記述の中の接続(兄弟と親の兄弟)に限り、外部との接続を含めるかは U12 がフローの端点を決める時に広げる。
  U12 と組にして決める案は採らない——U13 と U12 を束ねると、U13 が U10・U11 を越えて U12 を待つ事になり、4.3 の順序が崩れる。
- **U13・U10・U11・U12・U20・U14・U26 の ADR は、既存の言語に移せるかを併せて書く**(ADR 0026 決定6)。いずれも検査(E・W)を足す見込みが高い——
  U13 は `on failure` の型と軸(c)、U10・U11 は ask の閉路、U12・U20 は外部依存と W0018-1、U14 は名前の解決と E0014-3 の範囲、U26 は body の中の暗黙の変換や網羅の分岐である。
  各検査が思考実験 26 の4つの判定のどれに当たるかを一行添え、「そのまま移せる」「既にある」なら shidzuku-lint の規則の候補に足す。
  U12 には、思考実験 26 の論点5(外への要求の期限は `external` より先に lint の側で形を持つ)が既に入力として入っている。
- **U26(body の記法)を新設し、U14 の次に置く**(2026-09-28)。全ての思考実験は body を `{ ... }` のまま書いてきた。
  Phase 1 の成果物は三層記述のコンポーネントが動く事であり、body が書けなければ移行点検(M4)もトランスパイラも成り立たない。
  U13(数値と解析の失敗を body でどう受けるか)と U10(待つ所の印)に依るため ADR はその後に置くが、候補の書き比べは今から並行して始めてよい。
  見直し前に「構文規則(文法)を書く時期」として問うたのは、宣言の層も含めた形式文法をいつ文書にするかであり、記法そのものの選択(U26)とは別である。
- **pressure block の上限は U10・U11 の行に入れる。** 第4章 4.6 が「実装を待たずに決める」とした唯一の語彙であり、キューの意味(U11)と同じ所で決まる。

## 9. 進め方の原則

- 課題(U1〜)の決定は `docs/decisions/` に ADR として残す(自分の言語の思想「意図を残す」を、開発プロセス自身にも適用する)
- 各フェーズは「動く最小の成果物」で締める。仕様だけが先行して空転しない
- 仕様に迷ったら言語仕様(Phase 0)の思考実験(既存システムを書いてみる)に戻る
- 略号や番号だけで物を指さない。名前で書き、番号には名前を併記する(検索に掛けるため。`CLAUDE.md` の制約、第7節 7.18)
- 検査を足す時は、既存の言語に移せるかを併せて考える。移せる物は shidzuku-lint の規則にし、lint にする中で見つけた穴は仕様に戻す(ADR 0026)
- 検討は領域の木に分け、検討の作業は持っている領域のファイルだけを書き換える。番号と領域は main の上で予約してから枝を切り、ADR の採用と仕様書への反映は一度に一つずつ行う([docs/areas/README.md](areas/README.md))

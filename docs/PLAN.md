# Shidzuku 計画書

- 状態: Draft
- 日付: 2026-08-18
- 進め方: GitHub リポジトリ(`shidzuku-lang`)+ Claude Code で検討・実装を進める

## 1. フェーズ計画

### Phase 0 — 言語仕様(現在地)

- 第0章 ビジョン(本書と対の `00-vision.md`)✅ 初稿
- 第1章 システムコンテキスト(システムの宣言、外部の人と外部システム、動作環境の位置づけ)✅ 初稿
- 第2章 コンポーネントの定義(コンポーネントの宣言構文、三層記述の形式)✅ 初稿
- 第3章 制約の体系(検証可能な意図の一覧と検証時期: コンパイル時/実行時)✅ 初稿
- 第4章 通信モデル(コンポーネント間の接続、フローの記述)✅ 初稿
- 第5章 記述の表記(ソースの符号化、言語の語彙と書き手の名前、識別子の規則)✅ 初稿
- 第6章 データと型(data 宣言、基本型10、数値と量と単位、時間の3層と暦)✅ 初稿
- 章の順序は C4 モデルの4段(Context / Container / Component / Code)に対応する(ADR 0015)。Container は言語の記述対象外。
  第4章(通信)・第5章(表記)・第6章(データと型)は段に属さず段を跨ぐため、段の順の後ろに置く
- **検証方法**: 既存の小さなシステム(例: Web API+DB の小規模サービス、パイプライン処理)を Shidzuku で「記述してみる」思考実験。書けない事があれば仕様に戻す。

### Phase 1 — 最小の言語実装

- パーサ+検証器+トランスパイラの最小構成
- トランスパイル先は TypeScript と Rust の2言語とする(課題 U5、ADR 0012 提案)。動作環境は Rust の1実装とし、コンポーネントのみをトランスパイル先の言語で書く
- 実装の順序は Rust が先。ただし接合面(コンポーネントと動作環境の境界)の凍結は TypeScript が通ってから
- 成果物: 三層記述を持つコンポーネントを 2〜3 個接続したプログラムが動く。さらに、そのうち 1 コンポーネントを別言語の出力に差し替えても同じフローが動く(混在の適合試験)

### Phase 2 — 最小の分散動作環境

- コンポーネント=配置単位を実際に複数プロセス/ノードへ配置する実行系
- Raft による合意(自作せず既存ライブラリ利用を第一候補とする)
- ログ規約からの自動出力
- 成果物: 小さな分散システム(例: KV ストア)が「静かに」動き、ノード障害時に伝播しない事を確認

### Phase 3 — 可視化

- コードからの構造図・フロー図・障害境界図の抽出
- 図の段は C4 の4段(ADR 0015)とし、図の形式そのものは Shidzuku の三層記述とコンポーネントに即して設計する
- システムの入れ子(ADR 0018 提案)により、Context 図はルートから1段掘るごとに1枚出る。最上段が C4 の System Landscape 図に当たる

U1(ADR 0003)・U2(ADR 0004)は採用され、意図テンプレートと通信モデルは確定した。
全体制約「省略の禁止」(ADR 0008)も採用され、ADR 0004 の既定規定と ADR 0005 の省略規定を正式に改訂した。
U3(ADR 0005・0013)・U18(ADR 0015)も採用され、内部階層(強度と役割)とシステムコンテキストが確定した。U7(ADR 0006)は提案の判断待ち。
U17(ADR 0014)も採用され、記述の表記——言語の語彙は ASCII、書き手の名前は UTF-8——が確定した(2026-08-29)。
第1〜5章は初稿を執筆済み。未採用の提案 ADR に依拠する部分は、その採否により改訂される。
思考実験 04 で「配置・複製の記述を言語仕様に含めるか(章を立てるか、実行系の設定に置くか)」という Phase 0 の骨格論点が出ていたが、ADR 0015 が「含めない。動作環境(Container)の設定として Phase 2 で決める」と答えた(採用)。
U4・U6 への先行入力(捨てた事実のログ、durable な flow・合意対象・設計単位:配置単位の 1:N)は各 ADR・思考実験に記録済み。
見落とし課題の点検(2026-08-20)で U9〜U14 を追加した。U9(データ型)は思考実験 05 で検証し ADR 0009 を提案済み。U10〜U14 は思考実験→ADR のループで順次検討する。
U5 は ADR 0012 で、動作環境の言語(Rust の1実装)とトランスパイル先の言語(TypeScript + Rust)をまとめて決めた。
主要言語11種を比較した上で、接合の距離がゼロの言語と最大の言語を取っている。移植層はコンポーネントと動作環境の接合面(8つの呼び出し)であり、互換性の単位は言語中立の「コンポーネント記述子」である(ADR 0012 の本文では「ユニット記述子」)。
併せて、版の混在(別言語・別バージョンの同時稼働)の扱いを U16「コンポーネントのバージョンと移行」として登録した(起案時は U15 としていたが、U15 は数値の型と単位が先に取得しているため振り直した)。
ADR 0009 が保留した単位付き数値(思考実験 05 の論点5)を U15 として引き上げ、思考実験 06 で検証し ADR 0010 を提案した。
U15 は U9(基本型「数値」の置き換え)・U12(単位の付け外しは型の外へ出る操作)・U13(桁溢れの位置づけ)・U5(多倍長整数を持つ出力先が要る)へ入力を残している。
思考実験 07 で ADR 0010 の反証を探し、書けない数(循環小数・無理数)と書けない計算(平方根・累乗)を洗い出した。
この形式は「単位付き・静的位取りの十進固定小数点数」であり、既存の体系(PL/I の `FIXED DECIMAL(p,q)`・Ada の十進固定小数点型・SQL の厳密数値型)との対応と、二進浮動小数点(IEEE 754)との違いを ADR 0010 に対比表として置いた。
併せて ADR の様式(ADR 0007)に従い「結果(利点と欠点)」を ADR 0010 に加えた。要点は「実行時の驚きを、記述の重さとして前払いする」であり、分散した複数ノードで同じ計算が同じ結果になる事(Raft の前提)を利点の中心に置いた。
指数部は「桁の窓の位置」を解くが「窓の幅」は解かないため、静的指数(型に書く)を採用し、動的指数(十進浮動小数点)は棄却して ADR 0010 を改訂した(2026-08-25)。
ADR 0013 は、U9 の基本型から「文字列」を外して「テキスト」「バイト列」に置き換え、併せて U3 の内部階層に**役割**(境界・解析・領域・整形)の宣言を足す。
層をコンポーネントの属性にする案は、情報隠蔽の単位・障害境界・配置単位が層で割れるため却下し、既存の `layers` の拡張とした(思考実験 01・03 で机上検証)。
ADR 0009・0010・0013 は基本型を共に改訂するため揃えて判断する予定だったが、**0013 のみが先に採用された**(2026-08-28)。
このため層(役割・照合器・E0013-1〜E0013-4)は仕様書に入り、基本型(テキスト・バイト列)は入っていない。ねじれの内容と解消の条件は ADR 0013 の「採用の記録」に書いた。
コード例の表記(英字のキーワードと日本語の識別子・型名の混在)は思考実験 01 以来の慣行であり決定が無かったため、U17 として登録し ADR 0014 を提案した(2026-08-26)。
線引きは「言語が定める語彙は ASCII、書き手が定める名前は UTF-8 を許容」であり、ADR 0013 が保留していた表記の統一(決定8)に基準を与える。
C4 モデルの命名を仕様に取り込む決定を U18 として登録し、ADR 0015 を提案した(2026-08-26。2026-08-28 に採用)。
四段は Context=システム(新設の第1章)・Container=動作環境(言語の記述対象外)・Component=コンポーネント(旧ユニット)・Code=body と内部階層である。
これに伴い章立てを段の順に振り直し、度量衡の単位の綴りを `measure` から `unit` に戻した(ADR 0014 の回避策が不要になったため)。
ADR 0015 は ADR 0007 の C4 対応表と ADR 0014 の語彙表を改訂し、U12(外部世界との境界)の一部——外部の人と外部システムを宣言する場所——に答えている。
改名は仕様書と索引(本書・README・roadmap)に限り、ADR と思考実験は決定の履歴として旧称のまま残す(ADR 0014 の先例)。
第三層の `body` を段の名前に合わせて `code` に改める案も検討し、据え置いた(ADR 0015 決定5・論点5)。
本仕様書で「コード」は intent を含む記述全体を指しており(第0章 0.1・0.7)、第三層だけを `code` と名付けると
「意図はコードではない」と読めて理念に当たる事、`layers` が constraint の語彙であるため `code` ブロックが Code 段と
一致しない事が理由である。
判断待ちの提案 ADR が8本(0005・0006・0009・0010・0012・0013・0014・0015)に達したため、
どれをどの順に、どれと束にして採否を判断するかを第4節にまとめた(2026-08-28)。
根拠は ADR 間の改訂の関係であり、改訂の関係にある ADR は片方だけ採らない。
同日に 0005・0013・0015 を採用したため、判断待ちは 0006・0009・0010・0012・0014 の5本になり、後述の 0017 を加えて6本である。
第4節の束と段は、この採用後の状態に更新してある。
ADR 0010 の十進固定小数点は、桁と丸め方の宣言を全ての数値に課すため記述が重い。ADR 0017(提案)は、この重さを厳密さが要る値だけに絞る(2026-08-28)。
数値型を1つに絞る事をやめ、`実数`(IEEE 754 binary64)と `十進数`(ADR 0010 の型)の2つとし、**主に使うのは `実数`** とした。
0010 の決定は1つも取り消さず、名前を `十進数` に改めてそのまま残す。量と単位の検査(E0010-1・E0010-2・E0010-5)は両方の型に載る。
既定は置かない(型名は必ず書く。省略の禁止・ADR 0008)。「主に使う」は指針であって省略時の補完ではない。
分散ノードでの結果の一致(Raft の前提・ADR 0001)は、strict IEEE(binary64 のみ・最近接偶数固定・FMA と再結合の禁止)・超越関数の正しい丸め・合算順序の固定で保つ。
NaN・±∞・-0 は値として持たず、生む演算は失敗とする(U13 への入力)。外部の double をそのまま受けられるため、U12 の境界も軽くなる。
本 ADR は起案時 0016 を名乗っていたが、同日に採用された ADR 0016(検証番号の採番規則)と番号が衝突していたため 0017 に振り直した(2026-08-29)。
併せて、本文が使っていた E21・W5・W6 と ADR 0010 由来の E12〜E16・W3・W4 を ADR 0016 の `E<出自>-<連番>` 形式へ改めた。
ADR 0014 を採用し(2026-08-29)、識別子と語彙の規則を置く第5章「記述の表記」を新設した。表記は段に属さないため、段を跨ぐ第4章(通信)の後ろに置いた。
併せて ADR 0015 が持ち込んだ日本語の語彙(`担当`)と、ADR を持たないまま第3章に入っていた公開面の形(`の流れ`・`の受け口`)を、
それぞれ `by`・`flow out`・`flow in` として決定7の表に足した。基本型の語彙は反映先の章が無いため、段2(束 B)の採否を待つ。
同日、ADR 0015 が残した「1プログラム = 1システム」の制限を外す ADR 0018 を提案した。
C4 の System Landscape に当たる**システムの入れ子**を許し、`contains` の対象にシステムを加える。ルートはちょうど1つとする。
束 B(基本型)の検討で、**確定しているのは数値だけである**事が分かった。ADR 0009 は基本型を本文1行で挙げているにすぎず、
思考実験 05 が検証したのは構成子(直積・直和・識別子型・列)であって基本型ではない。文字列は ADR 0013 が、数値は ADR 0010・0017 が
それぞれ思考実験を伴って作り直したが、**真偽・時刻・期間・時間量は一度も検証されておらず、整数は一覧にすら無い**。
これを U22「基本型の体系(数値以外)」として登録し、思考実験 09 で検証して ADR 0019 を提案した(2026-08-29)。
基本型を `論理・整数・実数・十進数・テキスト・バイト列・時点・日付・時刻・時間帯` の10 に確定し、`期間`(直積で書ける)と `時間量`(`量 時間` の値)を外す。
`日付` は紀元前10000年から西暦9999年までを表す(年は天文学的年番号の符号付き整数。紀元の欄を分けると比較と減算が分岐する)。
**暦は `日付` の型の欄とする**——ADR 0010 が数値に単位の欄を課したのと同じ形であり、`1582-10-04` がユリウス暦かグレゴリオ暦かが型から読める。
暦の換算は日番号の付け替えであり、単位換算と違って**常に厳密で往復も一致する**。言語が持つのは算術暦(グレゴリオ暦・ユリウス暦)だけとし、元号・イスラム暦は版が変わる表を要するため持たない。
**`時間帯` を基本型に置く。** ログ行の `2026-08-29T14:30:00+09:00` は「いつ起きたか」と「どこの時計で読んだか」が混ざった外部表現であり、
`時点` と `時間帯` を分けて持てば他の時間帯への読み替えは欄の差し替えになる——**変換ではなく読み替えであり、`時点` は動かない**。
tzdata の版依存は境界・整形の役割の内側に閉じ込められ、複製された状態機械は割れない(ADR 0001 の前提が保たれる)。
**日時は基本型に置かず直積で書く**(暦の読みは `日付`+`時刻`、時間帯付きは `時点`+`時間帯`)。暦の値に `量 時間` を足す演算は持たない(「02:30 の3時間後」は時間帯が無ければ決まらないため、時間軸の加算は `時点` の上で行う)。
`実数` は 53 ビットしか持たないためナノ秒の時点(19 桁)を表せず、`十進数(19.0)` は 8 バイトで足りる値に 16 バイトを払う。
**ADR 0017 が数値型を軽くした副作用として 19 桁の値の置き場所が消えていた**事が、整数を置く直接の理由である。
論理型は置くが、置き場所を body に限る(公開面と `data` には名前の付いた直和を書く)。8実験の公開面に真偽は一度も現れなかった。
`instant` は体系によって意味が正反対である(Java は壁時計、Rust は単調時計)ため、Shidzuku の `時点` を壁時計の一点と定め、
`時点 - 時点` を持たず、期限は `量 時間` でのみ宣言できるものとした。うるう秒は持たない(表の版に依存すると Raft の前提が壊れる)。
ADR 0013 が文字列を廃した結果、締め日・誕生日を書く場所が消えていたため `日付` を新設した。時間帯の扱いは U12 へ送る。

### 2026-08-29 の採用と起案

ADR 0014 を採用し、ADR 0018 を提案した。

- **第5章「記述の表記」を新設した**。ADR 0014 の決定1・4・5・6(符号化と識別子の規則)は、それまで置き場が無かった。
  表記は段に属さない規則であり、段を跨ぐ第4章(通信)と同じ立場として段の順の後ろに置いた。ADR 0015 決定6 の章の表に1行足す形になる。
- **語彙を英字へ移した**。`なし` → `none`、`照合器` → `collator`、`ロケール`/`強度` → `locale`/`strength`、
  役割の4種 → `boundary`/`parse`/`domain`/`format`、`期限` → `deadline`。書き手の名前(`受注`・`名前順`・`センサー機器群`)は1つも変わっていない。
- **語彙の棚卸しが足りていなかった**。ADR 0014 の決定7 は基本型・数値・層・共通の四表しか持たず、
  `担当`(ADR 0015)と `の流れ`・`の受け口`(第3章 3.2)を数え落としていた。採用の記録で3語を足した。
- **反映できなかった事**: 基本型(decimal・text・bytes …)と数値の語彙は、依拠する ADR 0009・0010・0017 が未採用で
  データ型の章が無いため入れられない。ADR 0013 の基本型と同じねじれである(第2節)。
- **ADR 0018(提案)**: システムの入れ子。ADR 0015 の「他の Shidzuku システムは external として外に置く」は、
  自分たちが設計し Shidzuku で書いている系を記述の外へ追い出しており、設計意図の喪失(第0章 0.2)を言語が強制していた。
  併せて **ADR 0015 が置いた外部システムの判定基準(独立に設計され、独立に壊れるか)を廃した**。
  `external` に書いた物が外部システムであり、それ以外の規則を持たない。Shidzuku で書いた系かどうかも関係しない。
  机上検証(思考実験 01 と 08 を一つのプログラムに並べる)で、判定基準は書き手の判断を後から正当化する役にしか
  立っていない事が分かったためである。思考実験 08 の論点5(判定基準が割れる)は、解決したのではなく**問い自体が消えた**。
  外部が段を上がっても外部である事(E0018-5)も、この検証で見つかった。
  論点3(外部を呼ぶコンポーネントを書けない)は、相手が記述の中にあるときだけ塞がり、半分は U12 に残る。
  名前空間は動かさず、U14 に残した。
- **ADR 0019(提案)**: 基本型の体系。束 B の検討で、**確定しているのは数値だけである**事が分かった。
  ADR 0009 は基本型を本文1行で挙げているにすぎず、思考実験 05 が検証したのは構成子であって基本型ではない。
  真偽・時刻・期間・時間量は一度も検証されておらず、整数は一覧にすら無い。これを U22 として登録し、思考実験 09 で検証した。
  基本型を10(`論理・整数・実数・十進数・テキスト・バイト列・時点・日付・時刻・時間帯`)に確定し、`期間` と `時間量` を外す。
  `日付` は紀元前まで表し(天文学的年番号)、**暦は型の欄**とする(単位と同じ形。換算は常に厳密で往復も一致する)。言語が持つのは算術暦の2つだけ。
  **`時間帯` を置き、ログの日時は `時点` と `時間帯` の直積で書く。** 他の時間帯への「変換」は欄の差し替えであり `時点` は動かない。
  日時は基本型に置かず直積で書き、暦の値への `量 時間` の加算は持たない。
  **整数を置く直接の理由は ADR 0017 の副作用**である——主に使う型を `実数`(53 ビット)にした結果、
  ナノ秒の時点(19 桁)と 64 ビットの識別子の置き場所が消えていた。
  論理型は body に限り(公開面には名前の付いた直和)、`時点` は壁時計と定めて `時点 - 時点` を持たない。
  0010・0017 の決定は1つも取り消さない。
- **反証試験(思考実験 10)**: ADR 0019 は棚卸し(思考実験 09)から導いた決定であり、系を書いた裏付けを持たなかった。
  時間軸(`時点`)・暦(`日付`・`時刻`)・時間帯が全部出る系——多地域シフト勤怠——を書き下ろし、9つの論点を得た。
  打刻を `時点` で受ける形が境界の設計をそのまま決めた事、夏時間の曖昧さが公開面の直和に出た事、
  暦の値(締め期間)を鍵にした事で締めの冪等が成り立った事は、決定が効いた側である。
  一方で **`時刻` に長さを足せずシフトの終了時刻が書けない・曜日が無い・`整数` の単位換算の規則が無い・
  `隔たり` が 584 年で桁溢れする**という穴が出た。同日 ADR 0019 を改訂して埋めた——
  `時計を進める(時刻, 量 時間) -> (時刻, 整数 日)`(繰り上がりを返すため時間軸の加算と混ざらない)、
  `曜日(日付)`(日番号 mod 7 であり暦に依らない)、整数の単位換算(粗い単位へは丸めの宣言、細かい単位へは桁溢れの失敗)、
  `隔たり` の結果の単位と丸めの宣言、W0019-3 の書き分け(業務規則が決めた暦の値は対象外)である。
  地帯名の解決失敗(U12)と、body 内の判断を intent に書く場所(U1)は欠点として記録し、送った。
- **暦の拡張(思考実験 11 → ADR 0020 提案)**: ADR 0019 は「元号は版が変わる表だから言語が持たない」としたが、
  **退けた対象を取り違えていた**。退けるべきは「言語が表を持つ事」であり、「書き手がソースに表を宣言する事」は
  ADR 0010 が量と単位で既に採っている形である(インチの定義を言語は知らないが、インチは書ける)。
  暦は「表がどこから来るか」で3つに割れる——**算術暦**(言語が持つ)・**紀年法**(書き手が宣言)・**表暦**(持たない)。
  紀年法は年の呼び方だけが違う暦であり、月日を変えないため**改元日の一覧だけ**で宣言できる。和暦・仏暦・民国紀元・皇紀が同じ仕組みで書ける。
  内部表現は日番号のままで、比較・日数差・曜日・`日を足す` を一つも失わない。
  代わりに**換算が全域でなくなる**(表の外は `暦の外` として直和で受ける)。厳密さは保つ。
  `紀元 明治 : 1873-01-01 から 6 年` は、明治5年以前が天保暦であるという断絶を宣言がそのまま表す。
  **イスラム暦は依然として書けない**——タブラー暦法は算術だが紀年法ではなく閏年の配置に流派が複数あり、
  ウンム・アルクラー暦と観測ベースは版を持つ表である。太陰太陽暦も同じ理由で書けない。
- **新設した課題**: U22(基本型の体系。数値以外)。

### 2026-08-29(2)の採用と検証ループ — 束 B

ADR 0009・0010・0017・0019・0020 を採用した。**2026-08-28 から続いていた「層は仕様書に入ったが基本型は入っていない」ねじれは、これで解消した。**

- **第6章「データと型」を新設した**。データは段に属さず段を跨ぐため、第4章(通信)・第5章(表記)と同じ立場として段の順の後ろに置いた。
  内容は `data` 宣言と構成子(6.1)・基本型10(6.2)・数値3種と量と単位(6.3)・時間の3層と暦(6.4)・型が告げる事(6.5)・未定事項(6.6)である。
- **他の章への反映**: 第3章 3.3(E0009-1・E0010-1〜5・E0019-1〜6・E0020-1〜3 と対応する警告。E0008-1 の対象に型の欄を追加)、
  第4章 4.2(`deadline` の欄が `量 時間` を持つ数値になった)、第5章 5.3(型の語彙を8区分)、第2章 2.1(公開面の型の参照先)。
- **ADR 0013 の基本型(テキスト・バイト列)も同時に入った**。反映先の章が無いために保留されていたものである。
- **検証ループ(思考実験 12)**: 思考実験 01〜11 の全データを、仕様書(第6章)だけを読んで書き直した。
  **11 実験の全データが書けた**。真偽は一度も要らず、`期間`・`時間量` を外した事でも困らなかった。数値型の使い分けは 6.3 の3列がそのまま当たった。
  一方で5つの論点が出た。
- **仕様書の修正で閉じた事**: E0019-1 の対象を**型の入れ子**(`list<論理>`・直和の区分の引数)へ広げた(論点3)。
  不在の区分名は「何が無いのかを言う」という指針を 6.1 に足した(論点5)。
- **新設した課題**: U23(数値型を跨ぐスカラー倍)。`十進数(7.2) 円 × 整数 単位なし` が E0019-3 で落ちる。
  単位の側は既に答えを持つ(スカラー倍は単位を変えない)が、型の側が決まっていない。
  `整数` → `十進数` は原理的に丸めが起きないため危険は少ないが、「暗黙の変換を置かない」の例外になるため決定が要る。
- **U14 に足した論点**: 直和の区分名の可視範囲(`理由`・`なし` が複数の `data` に現れる)と、
  `量`・`単位`・`暦` の宣言の置き場所(トップレベルだが `contains` に現れない)。**U14 の論点は第5節に展開した。**
- **U23 の検証(思考実験 13)**: 「数える値にも `個` のような単位を持たせる」案を書き下ろした。
  **単位の軸と数値型の軸は直交しており、この案は U23 を解かない**——次元は通るようになるが、`整数` を `十進数` の式に混ぜる事は依然として書けない。
  加えて、割合・税率は本当に無次元(ISO 80000-1 の「次元が 1 の量」)であるためスカラー倍の規則はどのみち要り、
  列の長さ(E0019-4)で原則が破れ、助数詞の数だけ量の宣言が増え、採用済みの決定(個数は `単位なし`)と衝突する。
  ただし**数える単位が落とす誤りは本物**であり(ケースと個の換算忘れ、件数と行数の取り違え)、
  第6章 6.3 の指針を「換算比を持つなら数える単位にも付けてよい」へ緩める事は有効である(指針の明確化で足りる)。
  U23 そのものは型の軸で解く。実験は `倍する(<値>, <整数>)` という**名前のある操作**を推している——例外を作らずに済むためである。
- **新設した課題**: U24(序数と基数の区別)。`版`・`ページ番号`・`列の添字`・`連番` は数えた値だが足し算に意味が無い。
  ADR 0010 が量と単位で「距離 + 重さ」を落としたのと同じ問題が、数える値の中に残っている。

## 4. ADR の検討順

ADR は互いを改訂する。改訂される側を先に採ると、採用した直後に改訂が入って仕様書を二度書き直す事になる。
改訂する側を先に採ると、依拠先が提案のままで決定が宙に浮く。したがって順序が要る。

順序を決める規則は三つである。

- **R1** 改訂の関係にある ADR は同じ**束**に入れ、同時に採否を判断する(片方だけ採らない)
- **R2** 束の順序は依拠の向きに従う。**名前 → 型 → 指針 → 接合面**の順である
- **R3** 第2節の「決定フェーズ」より前倒ししない。前倒しは、判断の材料が揃う前に決める事を意味する

課題と ADR と束の関係図は [docs/roadmap.html](roadmap.html) 第3節に置く。

束は 2026-08-28 の採用(ADR 0005・0013・0015)と 2026-08-29 の採用(ADR 0014)を反映してある。
**採用済みの ADR は束から外れ、残りだけが判断待ちである。** 段の番号は動かさない(採用の記録と対応が付かなくなるため)。

## 5. U14(プログラムの宣言)の論点

U14 は「束ねる器」の課題だが、中身は8つの独立した問いに分かれる。思考実験 12・13 と ADR 0018 の採用で材料が揃ったため、ここに展開する。
**決めるのは Phase 0〜1 であり、本節は決定ではなく論点の一覧である。**

### 5.1 何が未定なのか — トップレベルの宣言の一覧

現在トップレベルに書ける宣言は6種ある。

| 宣言          | 定めた所       | `contains` に現れるか |
| ------------- | -------------- | --------------------- |
| `system`      | ADR 0015・0018 | **現れる**            |
| `component`   | 第2章 2.1      | **現れる**            |
| `flow`        | 第4章 4.2      | 現れない              |
| `data`        | 第6章 6.1      | 現れない              |
| `量` / `単位` | 第6章 6.3      | 現れない              |
| `暦`(紀年法)  | 第6章 6.4      | 現れない              |

**`contains` に現れないものは、どのシステムのものかが書かれていない。** ADR 0018 でシステムの入れ子を許した結果、
「内側のシステム A だけが使う `data` を、兄弟の B が参照できるのか」に答えが無い。これが U14 の中心である。

### 5.2 論点1 — `data` はシステムに属するか、プログラムに属するか

| 案                                  | 利点                                  | 欠点                                                      |
| ----------------------------------- | ------------------------------------- | --------------------------------------------------------- |
| プログラム全体に属する(現在)        | 共有語彙が1か所。参照に宣言が要らない | 情報隠蔽の単位(システム)を型が跨ぐ。名前の衝突が増える    |
| システムに属し、`expose` で外へ出す | 隠蔽の単位が型にも及ぶ                | 「型を使うため」の宣言が増える。ADR 0009 が退けた形に近い |
| システムに属し、親からは常に見える  | 入れ子の向きと一致する                | 兄弟からは見えないため、兄弟間で流れるデータが書けない    |

ADR 0009 は「共有語彙を参照するためだけに `depends` が発生すると、依存の意味(通信相手)が濁る」として
`data` をトップレベルに置いた。**この判断は「型の参照は依存ではない」という立場である。** そこは動かないとして、
**可視範囲**をどう決めるかが残っている。

### 5.3 論点2 — 直和の区分名はどこに属するか

思考実験 12 で見つかった。`なし`・`失敗`・`理由` が複数の `data` に現れる。

``` plaintext
data 照会結果 = 見つかった(値) | なし          # 実験 04
data 検索結果 = 見つかった(list<…>) | 検索不可  # 実験 08
```

| 案                                   | `照会結果.なし` と `別の型.なし` | 書く時                       |
| ------------------------------------ | -------------------------------- | ---------------------------- |
| 区分名は `data` の中に閉じる         | 別物                             | 修飾が要る場面がある         |
| 区分名はトップレベルに出る           | 同じ物                           | 全 `data` の区分名が衝突     |
| 中に閉じるが、文脈から推論して省ける | 別物                             | 素直に書ける。推論規則が要る |

名前的型付け(第6章 6.1)からは1番目が自然だが、**書く時の冗長さ**が残る。
さらに深い問い: **区分は型か、値か、構築子か。** `見つかった(値)` は構築子で `なし` は値なのか、どちらも区分という一つの物なのか。
パターン照合の記法も未定であり、この問いと同じ所で決まる。

### 5.4 論点3 — `量`・`単位`・`暦` の可視範囲

思考実験 12 の論点4。これらは**型の一部**である(`実数 メートル`・`日付 和暦`)。

- 型が公開面に現れる以上、**接続の両端から見えなければならない**。したがって `data` と同じ扱いになるはずである。
- しかし名前的型付けを素直に当てると、**2つのシステムが別々に宣言した `量 長さ` は別の型になる**。
  メートルはメートルであるという物理の現実と、名前で区別するという型の規則が衝突する。
- 案: 量・単位・暦はプログラムに1つとする(名前の一意性を強制する)。あるいは data と同じ規則に従わせ、
  重複宣言を E とする。

### 5.5 論点4 — 名前空間の分け方

第5章 5.5 は「同一の名前空間」の範囲を U14 に送っている。E0014-3(混同可能な識別子の共存)の範囲も同じである。

| 案                            | `注文` という `component` と `注文` という `data` |
| ----------------------------- | ------------------------------------------------- |
| 1プログラム = 1名前空間(現在) | 共存できない                                      |
| 宣言の種類ごとに分ける        | 共存できる                                        |
| システムごとに分ける          | 別のシステムなら共存できる                        |

種類ごとに分ける案は書きやすいが、**同じ名前が2つの意味を持つ**事を許す。第0章 0.5 の「名前で語る」との整合が論点になる。

### 5.6 論点5 — 修飾名を持つか

名前空間を分けるなら、外から指す記法が要る(`受注管理.注文`)。持たないなら、名前空間は分けられない。

- ADR 0008(省略の禁止)からは、**参照する物は書く**のが筋である。
- しかし ADR 0009 は「型の参照のために宣言が増える事」を退けている。
- **修飾名は宣言ではなく参照の形**であるため、0009 の判断とは衝突しない可能性が高い。ここは整理が要る。

### 5.7 論点6 — W0003-1(intent のコピペ検出)の範囲

W0003-1 は「他のコンポーネント・フローと intent 本文が完全一致」を警告する。**どの範囲で総当たりするかが未定**である。

- プログラム全体で比べると、入れ子が深い系では遠いコンポーネントどうしの偶然の一致まで警告する。**静かさ(第0章 0.5)に反する。**
- 同じシステムの中だけに限ると、コピペしたコンポーネントを別のシステムへ移すと警告が消える。
- 名前空間の設計が決まれば、範囲もそれに従うのが素直である。

### 5.8 論点7 — ファイルとの関係

- 1ファイルに複数の宣言を書けるか。ファイルの境界は名前空間の境界か。
- 取り込みの語彙(`import` に当たるもの)を持つか。持つなら ADR 0008 の「書く」に沿うが、宣言が増える。
- **ファイルは道具の都合であり、言語の意味に持ち込まない**という立場も採れる(名前空間はファイルと無関係)。

### 5.9 論点8 — 外部システムの語彙(U12 との境界)

`external 翻訳サービス` の公開面に現れる型は、どこで宣言するのか。

- 外部の型も `data` で書くのか、外部専用の語彙を持つのか。
- 外部の型は**版が外から変わる**(U16)。内側の型と同じ名前空間に置くと、版の混在が名前の衝突として現れる。

### 5.10 決める順序の案

論点は独立ではない。次の順に決めると、後の決定が前の決定を書き直さない。

| 順  | 論点                       | 理由                                                     |
| --- | -------------------------- | -------------------------------------------------------- |
| 1   | 論点1(`data` の可視範囲)   | 他の全ての論点の前提になる                               |
| 2   | 論点4・5(名前空間と修飾名) | 論点1 が決まれば形が決まる                               |
| 3   | 論点2(区分名)              | 名前空間の中の話であり、パターン照合の記法と同時に決まる |
| 4   | 論点3(量・単位・暦)        | `data` の規則に従わせるかどうかの判断で済む              |
| 5   | 論点6・7・8                | 上が決まれば従属的に決まる                               |

**先に思考実験が要るのは論点1 と論点2 である。** 入れ子を持つ系(思考実験 08 と 01 を並べた ADR 0018 の机上検証)に
`data` を持ち込み、共有語彙がどこに現れるかを書き下ろすのが素直である。

## 6. 決定の方向と、その上で残る問題(2026-08-29)

U23 と U14 の論点1・2・4・5 について方向が示された。**方向はまだ ADR になっていない。** 起案の前に潰す必要のある問題をここに置く。

### 6.1 U23 — 「`単位なし` の値とのスカラー倍は単位も型も変えない」

#### 問題1: 9つの組み合わせのうち4つで、宣言のない丸めが起きる

規則を字義どおり全組み合わせに当てると次になる。

| 単位を持つ側 | `単位なし` 側 | 結果(規則どおり) | 起きる事                                             |
| ------------ | ------------- | ---------------- | ---------------------------------------------------- |
| `整数`       | `整数`        | `整数`           | 安全(既存の規則)                                     |
| `整数`       | `十進数`      | `整数`           | **小数を掛けて整数を返す。宣言のない丸めが起きる**   |
| `整数`       | `実数`        | `整数`           | **同上。加えて近似が厳密に化ける**                   |
| `実数`       | `整数`        | `実数`           | 2^53 を超える整数は丸まる(W0019-1 と同じ性質)        |
| `実数`       | `実数`        | `実数`           | 安全(既存の規則)                                     |
| `実数`       | `十進数`      | `実数`           | **`十進数` → `実数` の丸めが暗黙に起きる**           |
| `十進数`     | `整数`        | `十進数`         | 安全。`整数` → `十進数` は原理的に丸めが起きない     |
| `十進数`     | `十進数`      | `十進数`         | 安全。ただし**桁は和になる**(型は同じでも桁は変わる) |
| `十進数`     | `実数`        | `十進数`         | **近似が厳密に化ける。丸めが宣言されない**           |

太字の4つは、ADR 0010 の「誤差の出る場所を3つに限る」と ADR 0017 の総括「型の名前と実際の性質を一致させる」に反する。
**とくに `十進数 円 × 実数 単位なし` は、金額が静かに近似になる経路である。** ADR 0017 が「主に使う型は `実数`」と決めたため、
`単位なし` の値が `実数` で書かれる事は起きやすい。W0017-1(通貨の量に `実数` を使っている)はこの経路を検出しない。

→ **スカラーに使える型を絞る必要がある。** `整数 単位なし` だけに限れば、上の表の危険な4つは全て消える
(`整数` → 他の型への変換は原理的に丸めが起きないか、起きる場合は W0019-1 が既に警告する)。

#### 問題2: 「型も変えない」の「型」が桁を含むかどうかが決まっていない

`十進数(7.2) 円 × 十進数(1.4) 単位なし` の結果を、ADR 0010 の乗算規則は `十進数(8.6) 円` とする(整数部・小数部とも和)。
「型も変えない」を字義どおり取ると `十進数(7.2) 円` になり、**小数部が 2 に切り詰められる = 宣言のない丸めが起きる**。

→ 「型の**種類**は変えないが、桁は ADR 0010 の規則で決まる」と書き分ける必要がある。

#### 問題3: `整数` をスカラーにすると中間の桁が大きくなる

`整数` は桁を持たない型であるため、乗算では最大値(19 桁)と見なすほかない。

| 式                            | 結果の桁       | 記憶域            |
| ----------------------------- | -------------- | ----------------- |
| `十進数(7.2) × 整数 単位なし` | `十進数(26.2)` | 28 桁 = 16 バイト |
| `十進数(9.2) × 整数 単位なし` | `十進数(28.2)` | 30 桁 = 16 バイト |

ADR 0010 は「中間の桁は自動で広がる」「所要記憶域は実行前に見積もれる」としているため**規則には反しない**が、
**`整数` を桁の無い型にした代償が乗算の中間桁に出る**事は記録しておく。値が名前を得る所で `収める` すれば元の桁に戻る。

#### 問題4: 除算の側が決まっていない

ADR 0010 は「`単位なし` の値との**乗除算**(スカラー倍)は単位を変えない」と書いており、除算を含む。
しかし `十進数` の除算は `割る(<被除数>, <除数>, <結果の桁>, 丸め <方式>)` であり、除数に `整数 単位なし` を書けるかが決まっていない。
乗算だけ決めると、`金額 ÷ 人数` が書けないまま残る。

#### 問題5: 可換性 — 規則の書き方が非対称になる

乗算は可換である。`整数 単位なし × 十進数 円` と `十進数 円 × 整数 単位なし` は同じ結果でなければならない。
規則を「左の型と単位を保つ」と書くと非可換になる。**「単位を持つ側の型と単位を保つ」**と書く必要がある。

#### 問題6: 両辺とも `単位なし` で型が違う場合の規則が無い

`整数 単位なし × 実数 単位なし` には「単位を持つ側」が無い。この場合に規則が適用できない。
E0019-3(コンパイル時エラー)のままとするのか、どちらかへ寄せるのかを決める必要がある。

#### 問題7: E0019-3 の文面を書き直す事になる

現在の E0019-3 は「3つの数値型が明示の変換なしに混ざる」である。スカラー倍を許すと例外が1つできるため、
「混ざる」の定義を書き直す必要がある。**第6章 6.3 の「3つの数値型は暗黙に混ざらない」も、例外を持つ規則になる。**

#### 問題8: 序数(U24)に掛け算が書けるようになる

`版 整数 単位なし × 3` が書けるようになる。序数と基数の区別(U24)が未解決のまま、書ける範囲だけが広がる。

### 6.2 U14 論点1 — 「`data` はシステムに属し、`expose` で外から見える」

#### 問題1: `expose` が2つの意味を持つ

第3章 3.2 の `expose` は公開面(ask の受け口・flow の出入り)の宣言であり、形は3種に限られている。
型の可視性を `expose` で書くと**4つ目の形**になり、同じ語が「通信の口」と「型の可視性」を指す。
第0章 0.5 の「名前で語る」からは、別の語を立てるか、`expose` の意味を明示的に広げるかの判断が要る。

#### 問題2: 参照する側が何を書くのかが決まっていない — ここが最大の未決事項

システム A の `data 注文` をシステム B が使うとき、B は何を書くのか。

| 案                         | 起きる事                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------- |
| B の `depends` に A を書く | 通信していなくても依存が生まれる。**ADR 0009 が退けた「依存の意味が濁る」が再発する** |
| 何も書かない               | `expose` された型はどのシステムからでも参照できる。**可視性の宣言が実質的に働かない** |
| 参照の宣言を別に持つ       | 宣言が1種増える。ADR 0008(省略の禁止)とは整合するが、ADR 0009 の判断とは緊張する      |

**この3案のどれを採るかで、論点1 の決定の意味が変わる。**

#### 問題3: 兄弟間を流れるデータの帰属に基準が無い

`flow A -> B : flow 注文` の `注文` は、A に置いても B に置いても共通の親に置いても書ける。
判断基準が無いと、同じ系が3通りに書ける。ADR 0006(粒度の指針)と同じ形の指針が要る。

#### 問題4: 言語が持つ型と量の居場所

`量 時間` は言語が最初から持つ(第6章 6.3)。基本型10 も同じである。
`data` がシステムに属するなら、**言語が持つものは名前空間の外にある**という規則を明示する必要がある。

#### 問題5: システムを跨ぐ型の循環

A の `data X` が B の `data Y` を欄に持ち、B の `Y` が A の `X` を持つ形。
`contains` の循環は E0018-1 で禁じているが、**型の参照の循環は別**である。木構造のような再帰は正当であるため単純には禁じられない。

#### 問題6: 外部システム(`external`)の型の置き場所が無くなる

`external 翻訳サービス` は記述の外にあり、`system` 宣言を持たない。
`data` がシステムに属すると決めると、**外部システムの公開面に現れる型を置く場所が消える**。U12 の主題だが、論点1 の決定がこの問題を鋭くする。

### 6.3 U14 論点4・5 — 「名前空間で分ける。ユニークな名前空間にする」

#### 問題1: Java のユニーク性は言語ではなく慣習が支えている

Java のパッケージ名が衝突しないのは、逆ドメイン名という**慣習**による。言語は同じパッケージ名を持つ2つの成果物を防げない
(split package の問題は実在する)。「ユニークな名前空間だから衝突しない」を前提にすると、
**誰がユニーク性を保証するのかが書かれていない前提**になり、ADR 0008(省略の禁止)の精神に反する。

#### 問題2: 逆ドメイン名は組織の名前を記述に持ち込む

`com.example.受注管理.注文` の形になる。組織が変われば(買収・分社)全ての型名が変わる。
ADR 0015 の改名(ユニット → コンポーネント)と同じ痛みが、書き手の名前の全体に及ぶ。

#### 問題3: 階層が二重になる — そして、その必要が無い

論点1 で「`data` はシステムに属する」と決めた。ならば**名前空間はシステムの入れ子の経路**にするのが素直である。
Java 風の名前空間を別に導入すると、システムの入れ子と名前空間という**2つの階層が並立**する。

そして**ユニーク性は既に保証されている**。ADR 0018 は「ルートシステムはちょうど1つ」と定めている(E0018-2)。
したがって `ルート.内側システム.注文` という経路は**プログラム内で一意に決まる**。

→ **逆ドメイン名は要らない。** 名前空間 = システムの入れ子の経路とすれば、論点1 との整合も取れ、階層も1つで済む。

#### 問題4: 修飾名が長くなる

入れ子が深いと `受注基盤.受注管理.受付.注文` のようになる。毎回書く事になる。
短縮の記法(`import` に当たるもの)を持つかどうかは、**「省略の禁止は宣言の欄の話であり、参照の記法は別」**という整理が済んでから決まる(論点5)。

#### 問題5: E0014-3(混同可能な識別子)の範囲

名前空間で分けると、E0014-3 の範囲も名前空間ごとになる。
すると**別の名前空間にある `ＩＤ` と `ID` は共存できる**。修飾名では区別できるが、読み手の目には見分けが付かない。
混同の検査を名前空間を跨いで行うかどうかを決める必要がある。

### 6.4 U14 論点2 — 「一般的な区分名は言語の組み込みとする」

#### 問題1: 第6章 6.1 の指針と正面から衝突する

第6章 6.1 には、思考実験 12 の論点5 を受けて次の指針を置いたばかりである。

> **不在の区分名は、何が無いのかを言う。** `欠損`(計測が取れなかった)・`暦の外`(その暦では呼べない)・`訳なし`(訳文が無い)のように、
> 不在の理由が名前に出る。言語が単一の `なし` を持たないのは、不在の意味が文脈ごとに違うためである。

`なし` を組み込みにすると、**この指針を取り下げる事になる**。取り下げるかどうかを先に決める必要がある。

#### 問題2: `理由` は組み込みにできない

`失敗(理由)` の `理由` は系ごとに中身が違う(在庫不足・与信超過・変換失敗・訳なし)。
共通の中身が無いため、組み込みにすると**テキストで持つほかなくなる**。
テキストを制御フローの条件に使う事は E0013-1 でコンパイル時エラーとなりコンパイルできない(ADR 0013)。
→ `理由` は書き手が直和で宣言するものであり、組み込みにできない。

#### 問題3: `失敗` は U13 が使う名前を先に取ってしまう

U13(失敗の体系)は「ドメインの失敗(在庫不足)と系の失敗(期限超過・障害)の区別と語彙」を決める課題であり、**未着手**である。
`失敗` を今組み込みにすると、U13 が使える名前を1つ先に消費する。**U13 の後に決めるのが素直**である。

#### 問題4: 「一般的かどうか」の判定基準が無い

言語は既にいくつかの区分を持っている——`桁溢れ`(ADR 0010)・`逆行`・`存在しない`・`二度ある`(ADR 0019)・`暦の外`(ADR 0020)。
しかしこれらは**特定の操作の結果**として定義されており、汎用の区分ではない。

`なし`・`失敗`・`理由` は汎用の区分であり、性質が違う。**どこで線を引くかの基準が無いと語彙が際限なく増える。**
ADR 0009 が「継承・型引数は必要にならなかったため持たない」とした判断と同じ形の基準が要る。

#### 問題5: 組み込みの区分は型か、区分か

`照会結果` の `なし` と `検索結果` の `なし` が**同じ値**なら、型を跨いで受け渡せる事になり、名前的型付け(第6章 6.1)が緩む。
**別の値**なら、組み込みにする意味は「名前の予約」だけになる。どちらであるかを決める必要がある。

## 7. 2026-09-03 の撤回と再検討

第6節の4つの方向のうち、書き手の判断で3つを撤回し、白紙から再検討する。1つ(U14 論点2)は撤回のまま確定した。
**本節は第6節を置き換えるものではなく、その後に続く経過として記録する**(第6節の各問題は、再検討の出発点として有効なまま残す)。

### 7.1 U23・数値型全体 — ADR 0010・0017 を破棄し、思考実験 14 から再検討する

第6節 6.1 の指摘(9組中4組で宣言のない丸めが起きる)を受け、書き手は**スカラー倍の規則だけでなく数値型の設計そのもの**を
問い直す事にした。ADR 0010(数値の型と単位)・ADR 0017(数値型の体系)を破棄し(両 ADR の「破棄の記録」参照)、
ADR 0019 の決定2(整数)・決定7(3つの数値型の変換規則)を凍結した(ADR 0019「決定2・決定7 の凍結」参照)。

思考実験 14(数値型の再検討)で、金融機関(COBOL の圧縮10進数・Java の `BigDecimal`・C# の `decimal`)と
科学技術計算(Fortran の `KIND`・単精度が主役の領域・区間演算)それぞれの他言語の実例を、
「型をいくつ持つか」「変換をどこまで暗黙に許すか」の2軸で比較した。要点は次の3つである。

- **型を分けるという Shidzuku の根本方針自体は、Swift・Ada・Haskell という強い先行例に支持されている。** 疑う根拠は出ていない。
- **C# の `decimal` が、整数 → 十進数 だけを暗黙にする非対称な橋の先例になっている。** 思考実験 13 の推奨(スカラーを `整数` に限る)を裏付ける。
- **数値の塔(Scheme・Julia)は「暗黙変換が無い」のではなく「暗黙変換の規則を型ごとに1つ書く」という第三の道である。** Haskell の型クラスは塔に見えて実際は Shidzuku と同じくらい明示的であり、「塔=自動」という連想は誤りだと分かった。

論点は7つ(思考実験 14 第10節)に整理してある。**まだどれも決定していない。** 次に必要なのはこの7論点についての書き手との相談であり、
決まり次第、新しい ADR(暫定 ADR 0021)を起案する。

### 7.2 U14 論点1 — 可視性のキーワードを `expose` から切り離す

型の可視性を `expose` で宣言する案は撤回した。**`expose` は公開面(ask の受け口・flow の出入り)の語であり、
型の可視性という別の概念に同じ語を使うと、読み手が「通信の口」と「見えるかどうか」を読み分けねばならなくなる**(第6節 6.2 問題1 の指摘のとおり)。

代わりのキーワードを、他言語の先行例と ADR 0014 の語彙の作法(言語が定める語彙は ASCII、既存の動詞形と調子を合わせる——`depends`・`contains`・`by`)に照らして提案する。

| 候補              | 先行例                                            | 長所                                                                | 短所                                                       |
| ----------------- | ------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------- |
| **`share`**(推奨) | 意味は独自だが `depends`・`contains` と同じ動詞調 | `expose` と語根が違い読み間違えない。「共有する」という意味が直接的 | 前例のある業界標準語ではない                               |
| `export`          | JavaScript・Elm・OCaml のモジュール公開           | 業界で最も広く通じる語                                              | `expose` と語根(ex-)が近く、綴りも似て見間違えやすい       |
| `public`          | Java・C#・Kotlin 等の可視性修飾子                 | 最も馴染みがある                                                    | 修飾子であり宣言の動詞ではない。名詞的すぎて文の形が崩れる |

**`share <data 名>` を推奨する。** 理由は2つ——`expose` と語根を共有せず取り違えの余地が無い事、
そして思考実験 15(名前空間の再検討)が示す「木構造に沿った可視性」(Rust の `pub`)や「輸出の明示」(Common Lisp の `:export`)と役割は同じでも、
**具体的な段階の数(公開/兄弟まで/親までのような区分)は名前空間の再検討(7.3)と一緒に決まる**ため、キーワードだけを先に確定し、引数の形は保留する。

```plaintext
share 注文                    # 案。段階を持たない場合
share 注文 to 受注管理        # 案。段階を持たせる場合(思考実験15 論点2 に依存)
```

**最終的な文法は、7.3 の名前空間の決定と合わせて確定する。**

### 7.3 U14 論点4・5 — 名前空間を白紙から再検討する

「Java のようにユニークな名前空間にすれば衝突が無くなる」という案(逆ドメイン名)は撤回した。第6節 6.3 で指摘した4つの問題
(慣習が一意性を支えるにすぎない・組織名を記述に持ち込む・階層が二重になる・修飾名が長くなる)を踏まえ、思考実験 15(名前空間の再検討)で
Java・Go(フラット+慣習)、Rust・OCaml(木構造そのものが名前空間)、Common Lisp(プログラム内限定)、Unison(内容ハッシュ)を比較した。

結論として、**Shidzuku にはすでに2つの前提がある**事が分かった——`contains` の木構造(ADR 0018)と、ルートシステムはちょうど1つという保証(E0018-2)。
この2つは、**Rust の module tree(木構造そのものが可視性を決める)** と **Common Lisp のプログラム内限定(グローバルな一意性を要求しない)** の組み合わせに最も近い。

> **逆ドメイン名は要らないはずである。** システムの入れ子の経路(`ルートシステム.内側システム.データ名`)が、すでに一意な名前空間になっている。

ただし、これは思考実験の示唆であり、**まだ決定ではない。** 論点は5つ(思考実験 15 第8節)に整理してあり、書き手との相談を経て ADR 0018 の改訂として確定する。
可視性の段階の数(論点2)は、7.2 の `share` の引数の形を最終決定する材料になる。

### 7.4 U14 論点2 — 一般的な区分名を組み込みにする案は撤回のまま確定

「`なし`・`失敗`・`理由` のような一般的な区分名を言語の組み込みにする」案は、**文脈ごとに意味が違うため**撤回した。
第6節 6.4 で指摘したとおり、この撤回は第6章 6.1 の既存の指針(「不在の区分名は、何が無いのかを言う」)とちょうど一致する——
`欠損`・`暦の外`・`訳なし` のように、書き手がその都度、何が無いのかを名前にする。**追加の ADR 作業は不要であり、この論点は撤回のまま閉じる。**

# Shizuku 計画書

- 状態: Draft
- 日付: 2026-08-18
- 進め方: GitHub リポジトリ(`shizuku-lang`)+ Claude Code で検討・実装を進める

## 1. フェーズ計画

### Phase 0 — 言語仕様(現在地)
- 第0章 ビジョン(本書と対の `00-vision.md`)✅ 初稿
- 第1章 基本単位の定義(単位の宣言構文、三層記述の形式)
- 第2章 制約の体系(検証可能な意図の一覧と検証時期: コンパイル時/実行時)
- 第3章 通信モデル(単位間の接続、フローの記述)
- **検証方法**: 既存の小さなシステム(例: Web API+DB の小規模サービス、パイプライン処理)を Shizuku で「記述してみる」思考実験。書けない事があれば仕様に戻す。

### Phase 1 — 最小の言語実装
- パーサ+検証器+トランスパイラの最小構成
- トランスパイル先は 1 言語に絞る(課題 U5)
- 成果物: 三層記述を持つ単位を 2〜3 個接続したプログラムが動く

### Phase 2 — 最小の分散動作環境
- 単位=配置単位を実際に複数プロセス/ノードへ配置する実行系
- Raft による合意(自作せず既存ライブラリ利用を第一候補とする)
- ログ規約からの自動出力
- 成果物: 小さな分散システム(例: KV ストア)が「静かに」動き、ノード障害時に伝播しない事を確認

### Phase 3 — 可視化
- コードからの構造図・フロー図・障害境界図の抽出
- 図の形式は既存の枠組みに縛られず、Shizuku の三層記述と基本単位に即して最初から設計する

## 2. 未解決の課題

| # | 課題 | 論点 | 決定フェーズ |
|---|---|---|---|
| U1 | 検証不能な意図の記述形式 | 自由文か、テンプレート(項目: 理由/捨てた選択肢/変更想定)か。強制の程度(空欄をエラーにするか) | Phase 0 |
| U2 | 単位間の通信モデル | 非同期メッセージのみか、同期呼び出しも許すか。バックプレッシャの扱い | Phase 0 |
| U3 | 内部階層の制約宣言 | 階層の種類は固定(例: 境界層は純粋/中核層は自由)か、自由定義か | Phase 0 |
| U4 | ログ規約の内容 | 何を自動出力するか(入出力/状態遷移/障害)。粒度と抑制の仕組み(静かさとの両立) | Phase 2 |
| U5 | トランスパイル先の言語 | TypeScript(エコシステムの広さ)/ Go(分散・並行)/ Erlang(実行系が思想に近い)等の比較 | Phase 1 前 |
| U6 | Raft の適用範囲 | 何を合意対象にするか(配置情報のみか、アプリ状態も含むか) | Phase 2 |
| U7 | 単位の粒度の指針 | 深いモジュールを単位にする際、大きすぎ/小さすぎの判定基準 | Phase 0〜継続 |
| U8 | 図と実装の一致の範囲 | どこまでを抽出可能にするか(意図の記述も図に載せるか) | Phase 3 |

## 3. リポジトリ構成(案)

```
shizuku-lang/
├── README.md
├── docs/
│   ├── spec/
│   │   ├── 00-vision.md
│   │   ├── 01-unit.md
│   │   ├── 02-constraints.md
│   │   └── 03-communication.md
│   ├── decisions/        # ADR: U1〜U8 の決定を記録
│   └── experiments/      # 思考実験(既存システムの Shizuku 記述)
├── compiler/             # Phase 1
├── runtime/              # Phase 2
└── examples/
```

## 4. 進め方の原則

- 課題 U1〜U8 の決定は `docs/decisions/` に ADR として残す(自分の言語の思想「意図を残す」を、開発プロセス自身にも適用する)
- 各フェーズは「動く最小の成果物」で締める。仕様だけが先行して空転しない
- 仕様に迷ったら Phase 0 の思考実験(既存システムを書いてみる)に戻る

# Shidzuku 計画書

- 状態: Draft
- 日付: 2026-08-18
- 進め方: GitHub リポジトリ(`shidzuku-lang`)+ Claude Code で検討・実装を進める

## 1. フェーズ計画

### Phase 0 — 言語仕様(現在地)

- 第0章 ビジョン(本書と対の `00-vision.md`)✅ 初稿
- 第1章 基本ユニットの定義(ユニットの宣言構文、三層記述の形式)✅ 初稿
- 第2章 制約の体系(検証可能な意図の一覧と検証時期: コンパイル時/実行時)✅ 初稿
- 第3章 通信モデル(ユニット間の接続、フローの記述)✅ 初稿
- **検証方法**: 既存の小さなシステム(例: Web API+DB の小規模サービス、パイプライン処理)を Shidzuku で「記述してみる」思考実験。書けない事があれば仕様に戻す。

### Phase 1 — 最小の言語実装

- パーサ+検証器+トランスパイラの最小構成
- トランスパイル先は TypeScript と Rust の2言語とする(課題 U5、ADR 0012 提案)。動作環境は Rust の1実装とし、ユニットのみをトランスパイル先の言語で書く
- 実装の順序は Rust が先。ただし接合面(ユニットと動作環境の境界)の凍結は TypeScript が通ってから
- 成果物: 三層記述を持つユニットを 2〜3 個接続したプログラムが動く。さらに、そのうち 1 ユニットを別言語の出力に差し替えても同じフローが動く(混在の適合試験)

### Phase 2 — 最小の分散動作環境

- ユニット=配置単位を実際に複数プロセス/ノードへ配置する実行系
- Raft による合意(自作せず既存ライブラリ利用を第一候補とする)
- ログ規約からの自動出力
- 成果物: 小さな分散システム(例: KV ストア)が「静かに」動き、ノード障害時に伝播しない事を確認

### Phase 3 — 可視化

- コードからの構造図・フロー図・障害境界図の抽出
- 図の形式は既存の枠組みに縛られず、Shidzuku の三層記述と基本ユニットに即して最初から設計する

U1(ADR 0003)・U2(ADR 0004)は採用され、意図テンプレートと通信モデルは確定した。
全体制約「省略の禁止」(ADR 0008)も採用され、ADR 0004 の既定規定と ADR 0005 の省略規定を正式に改訂した。
U3(ADR 0005)・U7(ADR 0006)は提案の判断待ち。
第1〜3章は初稿を執筆済み。未採用の提案 ADR に依拠する部分は、その採否により改訂される。
思考実験 04 で「配置・複製の記述を言語仕様に含めるか(第4章を立てるか、実行系の設定に置くか)」という Phase 0 の骨格論点が出た(判断待ち)。
U4・U6 への先行入力(捨てた事実のログ、durable な flow・合意対象・設計単位:配置単位の 1:N)は各 ADR・思考実験に記録済み。
見落とし課題の点検(2026-08-20)で U9〜U14 を追加した。U9(データ型)は思考実験 05 で検証し ADR 0009 を提案済み。U10〜U14 は思考実験→ADR のループで順次検討する。
U5 は ADR 0012 で、動作環境の言語(Rust の1実装)とトランスパイル先の言語(TypeScript + Rust)をまとめて決めた。
主要言語11種を比較した上で、接合の距離がゼロの言語と最大の言語を取っている。移植層はユニットと動作環境の接合面(8つの呼び出し)であり、互換性の単位は言語中立の「ユニット記述子」である。
併せて、版の混在(別言語・別バージョンの同時稼働)の扱いを U16「ユニットのバージョンと移行」として登録した(起案時は U15 としていたが、U15 は数値の型と単位が先に取得しているため振り直した)。
ADR 0009 が保留した単位付き数値(思考実験 05 の論点5)を U15 として引き上げ、思考実験 06 で検証し ADR 0010 を提案した。
U15 は U9(基本型「数値」の置き換え)・U12(単位の付け外しは型の外へ出る操作)・U13(桁溢れの位置づけ)・U5(多倍長整数を持つ出力先が要る)へ入力を残している。
思考実験 07 で ADR 0010 の反証を探し、書けない数(循環小数・無理数)と書けない計算(平方根・累乗)を洗い出した。
指数部は「桁の窓の位置」を解くが「窓の幅」は解かないため、静的指数(型に書く)を採用し、動的指数(十進浮動小数点)は棄却して ADR 0010 を改訂した(2026-08-25)。
ADR 0013(提案)は、U9 の基本型から「文字列」を外して「テキスト」「バイト列」に置き換え、併せて U3 の内部階層に**役割**(境界・解析・領域・整形)の宣言を足す。
層をユニットの属性にする案は、情報隠蔽の単位・障害境界・配置単位が層で割れるため却下し、既存の `layers` の拡張とした(思考実験 01・03 で机上検証)。
ADR 0009・0010・0013 は基本型を共に改訂するため、揃えて採否を判断する。

## 5. 進め方の原則

- 課題(U1〜)の決定は `docs/decisions/` に ADR として残す(自分の言語の思想「意図を残す」を、開発プロセス自身にも適用する)
- 各フェーズは「動く最小の成果物」で締める。仕様だけが先行して空転しない
- 仕様に迷ったら Phase 0 の思考実験(既存システムを書いてみる)に戻る

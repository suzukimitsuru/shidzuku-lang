# 0013: 文字列型の廃止、text 型の導入、および層モデル

- 日付: 2026-08-24
- 状態: 提案
- 関連課題: U9(データ型の記述)・U3(内部階層の制約宣言)。関連: U12(外部世界との境界)・U13(失敗の体系)・U7(粒度)

## 背景(なぜ決める必要があるか)

ADR 0009(提案)は基本型として「文字列」を置いた。しかし汎用の文字列型は、日時・識別子・区分コード・通貨・電話番号など、本来は専用型で表すべきデータを保持してしまう。
Fowler と Beck は *Refactoring* でこれを primitive obsession(基本型への執着)として挙げ、電話番号は文字の集まり以上のものであり、こうした概念を文字列で表すのはあまりに一般的なため "stringly typed" と呼ばれる、と述べている。

雫は設計意図と制約をコードの上に書かせる言語である(第0章 0.1)。文字列型のメンバーは、その項目が何であるかを一切語らない。これは「設計と実装が一体である」という原則に真っ向から反する。

そこで「外部システムとの入出力およびメッセージ以外に、文字列は必要か」を問うた。必要なのは次の3つの場合だけである。

1. 自然言語そのものが値である場合(商品説明、備考、コメント)
2. テキスト処理自体がドメインである場合(エディタ、コンパイラ)
3. 表示・整形の最終段

1 は「文字列型で代用している」のではなく、本当にテキストが値である。したがって 1 を表す型は必要であり、これは認める。

思考実験 05(既存4実験の全データの書き下ろし)がこれを裏付けている。**4実験の公開面を流れる全データに、文字列型は一度も現れなかった**。
現れ得たのは `受注不可(理由)` の理由だけであり、これは区分(直和)で書くのが適切だった。識別子は識別子型が、時刻・期間は時間の型が、数量は数値が受けている。

同時に、この決定は層の問題を必ず伴う。「解析はどこで行うのか」「表示のための組み立てはどこに置くのか」を決めない限り、テキストへの操作の可否を語れないためである。
雫には既に内部階層の仕組みがある(ADR 0005、第1章 1.4、第2章 2.2 の `layers`)。本 ADR は**既存の内部階層を拡張する形で層モデルを定める**。新しい層の概念を別に立てる事はしない。

## 検討した選択肢

### 論点1: 文字列型をどうするか

- **残して lint で検出する**: 導入は容易。ただし検出は強制ではない。
- **廃してテキスト型を置く**: 汎用文字列を言語から除き、値としての自然言語だけを認める。
- **テキストも持たない**: 全てのテキストを外部表現として境界の外に出す。商品説明・コメントが書けない。

### 論点2: ロケールの置き場所

- **型パラメータ**(`テキスト(ja-JP)`): 型で言語を固定する。
- **値の属性**: 値が (ロケール, 正規化形, 内容) を持つ。
- **持たない**: 従来の文字列と同じ。照合と正規化の問題がそのまま残る。

### 論点3: テキストの同一性

- **等値比較とハッシュを与える**: 従来通り。キーとして使える。
- **どちらも与えない**: 識別子としての使用を型が拒む。
- **等値のみ与える**: 正準形が一意でない以上、`=` の意味が定まらない。

### 論点4: 層の粒度 — 本 ADR の中心

- **ユニットの属性にする**: ユニットごとに境界・解析・領域・整形のいずれかを宣言し、ユニット間の依存を一方向に固定する。
- **内部階層の性質にする**: 既存の `layers` に役割を足し、ユニットの内側で層を宣言する。
- **宣言しない**: テキストへの操作の可否を型だけで決める。解析の置き場所が記述に現れない。

### 論点5: 照合器(整列・曖昧一致)の置き場所

- **整形の層に限定する**: 領域から追い出す。
- **全面禁止**: 名寄せ・曖昧検索が書けない。
- **全ての役割で使え、宣言を強制する**: 使う事自体を制約層に明示させる。

## 決定

### 1. 基本型「文字列」を廃し、「テキスト」を置く

ADR 0009 の基本型から文字列を除き、値としての自然言語を表す**テキスト**を置く。名称を分ける事で、汎用の文字列との違いを明示する。

- 型名は他の基本型(数値・真偽・時刻)と表記を揃え、**テキスト**とする。本 ADR の題名の `text` はこの型を指す。
- テキストは不透明な値であり、演算をほとんど持たない。
- 識別子・日時・パス・URL・通貨・電話番号・区分コード・版はすべて専用型(識別子型・時間の型・直和・ADR 0010 の数値)で表す。
- 併せて**バイト列**を基本型として置く。外部表現(JSON・画像・添付)の運搬に必要であり、これも不透明な値である。中身の解釈は受け手の解析の役割を持つ層が行う(思考実験 03 の画像がこれにあたる)。

基本型の一覧は次の通りとなる(ADR 0010 が数値を改訂した上で)。

| 基本型             | 内容                                |
| ------------------ | ----------------------------------- |
| テキスト           | 値としての自然言語(本 ADR)          |
| バイト列           | 不透明な媒体・外部表現(本 ADR)      |
| 数値(i.f) 単位     | 十進固定小数点と単位(ADR 0010)      |
| 真偽               | 真/偽                               |
| 時刻・期間・時間量 | 時間の3種(期限宣言と共通。ADR 0009) |

### 2. ロケールと正規化形は型ではなく値の属性とする

テキストは型パラメータを持たない。値が **(ロケール, 正規化形, 内容)** の三つ組である。

- ロケールは実行時に外部から入る(Content-Language ヘッダ、DB の言語列、利用者設定)。境界と解析の層がこれを値に載せる。
- 型に言語を固定する案(`テキスト(ja-JP)`)は却下する。多言語のデータを扱うコードが書けなくなる。
- 特定のロケールだけを受け付けたい箇所の絞り込みは、値に対する不変条件の語彙を要する。**この語彙は現在の仕様に無い**(制約層の語彙は depends / expose / idempotent / state / layers で閉じている)。本 ADR はこれを決めず、「将来の変更想定」に送る。

### 3. テキストに素の等値比較とハッシュを与えない

テキストは `=` を持たず、ハッシュも持たない。したがって対応表・集合のキーにできず、識別子として使えない。

一般規則として、**ハッシュ可能なのは正準形が一意に定まる型だけ**と定める。識別子型・直和の区分・時刻・数値はこれを満たす。テキストは正規化形とロケールに依存するため満たさない。
テキストを名指しで禁じる規則ではなく、型の性質からの帰結である。

これは ADR 0009 の識別子型と対になる。**同一性が要る所には識別子型があり、テキストはそこへ立ち入らない。**

### 4. テキストへの構造的操作は、役割を宣言した層に閉じる

| 禁じる操作                   | 理由                                                      |
| ---------------------------- | --------------------------------------------------------- |
| 部分取得・分割・パターン照合 | 桁位置から意味を取り出す手法が復活するため。最も重要      |
| ハッシュ・キー利用           | 識別子としての使用を封じる(決定3)                         |
| 制御フローの条件に使う       | 区分コードの代用を封じる                                  |
| 連結                         | 組み立ては型付きの穴を持つテンプレートに限る              |
| 長さ・添字                   | 桁数による判定を封じる                                    |
| 空テキストへの意味づけ       | 「空 = 未設定」の代用を封じる。不在は直和で書く(ADR 0009) |

ただし禁止は**一律ではない**。解析と整形はまさにこれらの操作を仕事とする。どの層で許されるかを決めるのが次の決定である。

### 5. 層は内部階層の性質として宣言する — ユニットの属性にはしない

**層をユニットの属性とする案は却下する。** 層は既存の内部階層(ADR 0005)に**役割**という第二の宣言を足す形で表す。

```plaintext
constraint {
  layers {
    <階層名> { <制約強度> <役割> }
    ...
  }
}
```

- **制約強度**は ADR 0005 の 2 種(pure / io)を変えない。IO と決定性を決める。
- **役割**は本 ADR が定める 4 種(境界 / 解析 / 領域 / 整形)。テキストと外部表現に対する権能を決める。
- 階層の**名前は自由**(ADR 0005 を維持)。役割の宣言は必須であり、欠落は E9(必須宣言の欠落)とする。
- 2 つの軸は直交する。強度は「何をしてよいか(IO)」を、役割は「何を扱ってよいか(外部表現とテキスト)」を語る。

| 役割 | 責務                                                                   |
| ---- | ---------------------------------------------------------------------- |
| 境界 | 外部システムとのバイト列の授受。テキストも領域の型も現れない           |
| 解析 | バイト列またはテキストから領域の型を作る。部分取得が許される唯一の役割 |
| 領域 | 業務。テキストは不透明な値として通過するだけ                           |
| 整形 | 領域の型とテキストから、表示と出力用のバイト列を組み立てる             |

**データの向きは 境界 → 解析 → 領域 → 整形 → 境界 の一方向**である。逆流(領域でバイト列を作る、整形の結果を領域へ戻す)は E20 とする。
入りと出りを別の役割にはしない。向きはデータの流れから決まり、受付のユニットは必ず両方向を持つため、入出を宣言に足しても同じ役割の層が2つに割れるだけで読みは良くならない。

**ユニットの属性にしない理由**は、雫の基本ユニットが「設計単位 = 処理単位 = 障害境界 = 配置単位」だからである(第0章 0.3)。

- 思考実験 01 の OrderIntake は「HTTP と JSON の知識をこのユニットに閉じ込める」事を why としている。層をユニットの属性にすると、この 1 ユニットは受信・解析・領域・整形の 4 ユニットに割れ、隠していた知識が 4 つに散る。捨てたはずの選択肢(各ユニットが自分のプロトコルを持つ)に戻ってしまう。
- 割れた 4 ユニットは 4 つの障害境界・4 つの配置単位になる。`on failure` は 4 件必要になり、フローは伸び、障害点が増える。静けさ(第0章 0.5)に反する。
- 割れた層の間の公開面は素通しの委譲になる。これは ADR 0006 が「統合を検討せよ」と定めた統合シグナルそのものである。
- 既存の 3 実験がいずれも反例になる。OrderStore(domain / driver)・Aggregator(domain / driver)・Converter(planning / codec)は、外の形式を扱う階層と業務の階層を**1 ユニットの内側に**持っている。

役割を内部階層に置けば、これらはユニットを割らずに書ける(「机上検証」を参照)。

### 6. 役割と機能の対応表

○ = 可、× = 不可。

| 機能                                                       | 境界 | 解析 | 領域 | 整形             |
| ---------------------------------------------------------- | ---- | ---- | ---- | ---------------- |
| バイト列の入出力(外部システムとの授受)                     | ○    | ×    | ×    | ×                |
| バイト列・テキストからの解析(部分取得・分割・パターン照合) | ×    | ○    | ×    | ×                |
| 領域の型への変換                                           | ×    | ○    | ×    | ×                |
| テキストの生成                                             | ×    | ○    | ×    | ○                |
| テキストの保持・受け渡し                                   | ×    | ○    | ○    | ○                |
| 素の等値比較・ハッシュ・キー利用                           | ×    | ×    | ×    | ×                |
| 照合器による比較・整列・検索                               | ×    | ○    | ○    | ○                |
| 照合キーの永続化・受け渡し                                 | ×    | ×    | ×    | ×                |
| テキストの内容による分岐                                   | ×    | ○    | ×    | ×                |
| 連結                                                       | ×    | ×    | ×    | テンプレートのみ |
| 長さ・添字                                                 | ×    | ○    | ×    | 表示幅のみ       |
| 出力用のバイト列化                                         | ×    | ×    | ×    | ○                |

境界に照合器が無いのは、その層にまだテキストが存在しないためである。

### 7. 役割と制約強度の対応

役割は強度を選べる範囲を狭める。

| 役割 | pure | io  | 理由                                                                                                                |
| ---- | ---- | --- | ------------------------------------------------------------------------------------------------------------------- |
| 境界 | ×    | ○   | 外部との授受そのものが IO である                                                                                    |
| 解析 | ○    | ×   | 解析の途中で外部を引くと、変換規則が記述から読めなくなる。対応表は境界が取り、値として注入する(ADR 0005 の注入規則) |
| 領域 | ○    | ○   | 純粋な計算の層と、状態を持つ層の双方がある(思考実験 04 の KV 表)                                                    |
| 整形 | ○    | ×   | 組み立ては決定的である。出力は境界が行う                                                                            |

矛盾する組合せ(io の解析層など)は E18 とする。

### 8. 照合器は constraint に宣言し、境界を除く全ての役割で使える

顧客名での整列や絞り込みは業務ロジックそのものであり、特定の層に押し込められない。したがって照合器は領域でも使える。ただし**使う事を制約層に明示させる**。

```plaintext
unit 商品索引 {
  intent {
    why      "人が入力した語から商品の候補を絞り込む知識(照合の強度と語の揺れ)をこのユニットに閉じ込める。"
    rejected option "呼び手が名前の完全一致で引く"
             reason "全角半角・異体字・正規化の差で一致せず、一致しない事が呼び手に見えないため。"
    change   "対象ロケールと照合の強度の追加を想定。公開面(候補の列)は変えない。"
  }
  constraint {
    depends  なし
    expose   検索(語: テキスト) -> 列<商品コード>
    state    索引 recoverable(商品原簿の再生)
    照合器   名前順(ロケール ja-JP, 強度 二次)      # 使わなければ `照合器 なし`
    layers {
      照合 { pure 領域 }
      表   { io   領域 }
    }
  }
  body { ... }
}
```

- 制約の語彙に `照合器` を追加する。**宣言は必須**であり、使わないユニットは `照合器 なし` と書く(省略の禁止・ADR 0008、E9)。
- 戻り値が単一の値ではなく**列**である事が重要である。従来 `対応表<文字列, 商品>` が単一の値を返していたのは、全角半角・異体字・正規化の差を無視していたからであり、日本語で破綻するのはここである。曖昧さを型に出せば、その破綻が設計時に見える。
- 表記(`照合器` のような日本語の語彙と、depends / expose のような英字の語彙の混在)は ADR 0010 の `量`・`単位` と同じ扱いとし、統一は第1章への反映時に一括で決める。

### 9. 照合キーの永続化と受け渡しを禁じる

照合器を領域に開いた事で「照合器で等値を判定 → 実質のキー引き」という抜け道が生じる。これを、**照合結果の永続化・受け渡し・ハッシュだけを禁じる**事で塞ぐ。

照合キーは照合器のロケールと強度に加えて Unicode の版に依存する。CLDR のテーラリングは版ごとに変わるため、ある版で作った索引は次の版で一致しなくなる。照合器の結果は「その場限りの判定」であり、保存できる同一性ではない。

```plaintext
列.並べる(名前順)                    # 可: その場の順序
列.絞る(名前順, 語)                  # 可: その場の一致
対応表<テキスト, 商品>               # 誤り: テキストはハッシュを持たない(E17)
state 索引 ... 名前順.キー(名前)     # 誤り: 照合キーは永続化できない(E19)
```

照合器はロケールと版を引数に取る関数であって、テキストに正準形を与えるものではない。したがって照合器を開いてもテキストがハッシュ可能になる事はなく、決定3の規則に追加は要らない。

### 10. テキストのリテラルは解析と整形の層にのみ書ける

テキストの値はロケールを伴う(決定2)。ソースに書かれたリテラルには実行時のロケールが無いため、生成にはロケールの明示を要求する。

```plaintext
テキスト("在庫がありません", ロケール ja-JP)   # 整形の層でのみ
```

- 領域の層でテキストを生成する事はできない。定型の文言は表示の語彙であり、整形の層のカタログに置く。data の既定値としても書けない(既定を持たないのが省略の禁止の立場である)。
- テキスト以外のリテラル(`"A-1024"` のような書かれた値)は「文字列の代入」ではなく、**宣言された型に向けた解析**として解釈する。文字列型は一度も現れない。

```plaintext
表["A-1024"]      # 可: 商品コード(識別子型)へ解決される
表[商品.名前]     # 誤り: テキストはハッシュを持たない(E17)
```

識別子型に書式を宣言してコンパイル時に検査する案は魅力的だが、書式の語彙は現在の仕様に無い。決定2のロケールの絞り込みと同じく、値の不変条件の語彙としてまとめて決める(「将来の変更想定」)。

### 11. 検証の追加

第2章 2.3 の一覧に次を加える。いずれもコンパイル時のエラーである。

| #   | 検査                                                                           |
| --- | ------------------------------------------------------------------------------ |
| E17 | 正準形を持たない型(テキスト)の素の等値比較・ハッシュ・キー利用                 |
| E18 | 役割に許されない操作(領域での部分取得・連結、境界での照合)と、役割と強度の矛盾 |
| E19 | 照合キーの永続化・受け渡し(state・data・公開面への出現)                        |
| E20 | 役割の向きに逆らう受け渡し(領域でのバイト列化、整形から領域への戻し)           |

E9(必須宣言の欠落)の対象に、内部階層の**役割**と制約の**照合器**を加える。

## 机上検証 — 既存の思考実験を新しい層モデルで写す

**OrderIntake(思考実験 01)** — 層をユニットの属性にすれば 4 ユニットに割れるが、内部階層なら 1 ユニットのままである。

```plaintext
constraint {
  depends  Inventory, OrderStore
  expose   受注(注文) -> 受注番号 | 受注不可
  照合器   なし
  layers {
    受信   { io   境界 }      # HTTP のバイト列の授受
    復号   { pure 解析 }      # JSON のバイト列 -> 注文
    受付   { io   領域 }      # 引当と保存の依頼、結果の判断。ask は他ユニットへの通信なので io
    符号化 { pure 整形 }      # 受注番号・受注不可 -> JSON
  }
}
```

why(HTTP と JSON の知識をこのユニットに閉じ込める)はそのまま保たれ、障害境界も配置単位も 1 つのままである。

**OrderStore(思考実験 01)** — 元は domain(pure)/ driver(io)の 2 層だった。役割を書くと 4 層になる。

```plaintext
layers {
  domain { pure 領域 }      # 注文の組み立て
  文     { pure 整形 }      # 注文 -> SQL 文(テンプレート)
  行     { pure 解析 }      # 結果行 -> 注文
  driver { io   境界 }      # 接続とバイト列の授受
}
```

宣言は 2 行から 4 行に増える。ただし増えた 2 層は元から body の中にあった区別であり、名前が付いただけである。ユニットは割れていない。

**Converter(思考実験 03)** — planning(pure)/ codec(io)は `planning { pure 領域 }` と `codec { io 境界 }` になる。画像はバイト列として公開面を流れ、変換パラメータの決定は領域に残る。

**思考実験 05 の全データ** — 文字列は現れず、書き換えを要したのは `受注不可(理由)` だけである。理由は直和の区分にする(表示の文言は整形の層のカタログが持つ)。

## 根拠 — 先行例と規格

### 先行例: Ada の limited type

最も近い先行例は Ada の limited type である。Ada 83 の時点から、limited 型には等値・不等値の演算子が定義されず、代入も禁じられている。目的にはシャローコピーの防止と、オブジェクトの一意な同一性の保護が含まれる。

特に Ada 参照マニュアル 7.5 の `File_Name` の例が近い。パッケージの外から得たファイル名は一種の合言葉として働き、内部が数値である事は知られず、加算や比較といった操作もできない。
これは「不透明にして識別子以外に使わせない」例であり、本 ADR の決定3とは適用の向きが逆だが、機構としては同一である。

### 根拠: Unicode

「テキストの等値をロケールなしに定義できない」のは言語設計者の恣意ではなく、Unicode 側の結論である。

- UCA(UTS #10)は入力をまず NFD に正規化する事を要求し、正準等価な入力に対して同一の結果を出す事を求める。
- ICU の解説によれば、既定の UCA の順序で正しく並ぶ言語はオランダ語やポルトガル語などごく一部であり、それ以外はロケールを与えないと適切な照合にならない。

決定8・決定9はこの帰結である。

### 調査で見つからなかったもの

「テキストの識別子化を防ぐ目的で等値比較を外した」言語そのものは見つからなかった。本決定は Ada の機構と Unicode の根拠を組み合わせた新しい適用である。

## 捨てたもの・理由

### 型について

- **文字列を残し lint で検出する**: 設計と実装が一体であるという原則に反する。検出は強制ではなく、破っても動く。
- **テキストに言語のパラメータを持たせる(`テキスト(ja-JP)`)**: 多言語のデータを扱うコードが書けなくなる。ロケールは外から入る実行時の事実である。
- **newtype による包み込みだけで対処する**: 包んだ値から元の文字列を取り出せる限り、抜け道が残る。
- **型名を英字の `text` のまま置く**: 数値・真偽・時刻・識別子型が日本語の表記であるため、基本型の表記が割れる。ADR 0010 の `量`・`単位` と同じ扱いに揃える。
- **テキストも持たない**: 商品説明・コメントが書けない。背景の 1 は代用ではなく本物のテキストである。

### 層について

- **層をユニットの属性にする**(元案): 決定5の通り。情報隠蔽の単位が割れ、障害境界と配置単位が増え、素通しのユニットを量産する。ADR 0006 の統合シグナルに正面から当たり、思考実験 01〜03 の全ユニットが反例になる。
- **「層」を内部階層とは別の概念として二重に持つ**: 同じ語が 2 つの粒度を指す事になり、`layers` の宣言と層モデルのどちらを読めばよいか分からなくなる。既存の仕組みを拡張する方が、宣言も検証も 1 か所で済む。
- **役割を「外 / 内」の 2 種に減らす**: 解析と整形が同じ役割になり、一方向性(整形の出力は計算へ戻らない)が宣言から読めなくなる。「テキスト → バイト列 → 再解析」の抜け道が層の宣言の内側に隠れる。
- **役割に入り / 出りの別を持たせる**: 受付のユニットは必ず両方向を持つため、同じ役割の層が 2 つに割れるだけで読みは良くならない。向きはデータの流れから決まる。
- **役割を宣言しない(型だけで決める)**: 解析の置き場所が記述に現れず、部分取得がどこでも起き得る。省略の禁止(ADR 0008)にも反する。

### 照合について

- **照合器を整形の層に限定する**: 名前での整列・検索は業務ロジックそのものであり、領域から追い出せない。
- **照合器を全面禁止する**: 全文検索・名寄せの需要を満たせない。
- **照合キーを識別子型として永続化できる事にする**: Unicode の版を跨いで一致しなくなる。保存できる同一性ではない。

## 将来の変更想定

- **値の不変条件の語彙**(ロケールの絞り込み、識別子型の書式、数値の範囲)は現在の仕様に無い。決定2・決定10 が要求しており、ADR 0010 の桁の検査と併せて別途決める。U9 の続きとして扱う。
- **テンプレートの構文**(型付きの穴の記法)は Phase 1 で定める。整形の層で連結の代わりに使う唯一の手段である。
- **照合器の強度の語彙**(一次〜四次)は ICU に倣うが、語の選定は未定。
- **全文検索の索引ユニットの形**。照合器と索引を明示する仕組みとして別途設計する。
- **解析の失敗の扱い**は U13(失敗の体系)に送る。解析はバイト列を領域の型に変える箇所であり、失敗が集まる場所になる。
- **境界の役割と U12(外部世界との境界)の関係**。本 ADR は境界の層に「バイト列の授受」という権能だけを与えた。外部依存の宣言そのものは U12 で決める。
- **テキストが主役の系での検証**(全文検索・多言語カタログ)を思考実験 07 として行う。本 ADR は既存 4 実験の裏返し(文字列が現れなかった事)までしか裏付けを持たない。
- **採用時の反映先**:
  - ADR 0009 の基本型から「文字列」を除き、「テキスト」「バイト列」を加える。
  - 第1章 1.4(内部階層)に役割の宣言を追加し、第1章のデータの宣言にテキスト・バイト列を反映する。
  - 第2章 2.2 の制約の語彙に `照合器` を追加し、2.3 に E17〜E20 を追加、E9 の対象に役割と照合器を加える。
  - 思考実験 01〜05 の `layers` の記述に役割を補う。

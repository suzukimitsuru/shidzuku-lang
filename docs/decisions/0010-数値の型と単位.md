# 0010: 数値の型と単位

- 日付: 2026-08-23(改訂: 2026-08-25)
- 状態: 提案
- 関連課題: U15(関連: U9・U12・U13)
- 改訂: 思考実験 07(限界の洗い出し)を受け、静的指数の追加・動的指数の棄却・演算語彙の補完を反映した
- 改訂: ADR 0017(数値型の体系)により、本 ADR が定める型は数値型の唯一ではなくなった。本文の `数値` は `十進数` と読み替える(2026-08-28)

## 背景(なぜ決める必要があるか)

ADR 0009(提案)は基本型として「数値」を置いたが、その中身——表現・精度・演算の規則——は未定である。
浮動小数点を既定にすると、`0.1 + 0.2 ≠ 0.3` という誤差が公開面を流れるデータに入り込む。これは第0章 0.5 が排したい「運用の驚き」そのものであり、金額を扱う系では設計の欠陥になる。
また ADR 0009 は単位付き数値(℃/℉ 等)を「複雑さが大きい。必要が出たら検討する」として保留していた(思考実験 05 の論点5)。

思考実験 06 で、金額計算・計測の正規化・国際出荷の3系を数値として書き下ろし、入力を集めた。

- 誤差が生じ得るのは除算・単位換算・桁を狭める受け渡しの3箇所だけであり、そこに丸めの宣言を要求すれば残りは厳密になる。
- 消費税の端数処理は事業者の選択であり、言語が既定を置く方が誤りである。
- 単位を型に載せると、距離と重さの加算がコンパイル時に落ち、℉→℃ の変換忘れも落ちる。
- ℃↔℉ と通貨は比では書けず、比例変換だけを言語が持てば足りる。

思考実験 07 で逆向きに反証を探し、書けない数と書けない計算を洗い出した。

- 循環小数(1/3)と無理数(√2・π)は位取り記数法の限界であり、二進でも指数部を足しても書けない。
- 桁の窓の**位置**が原点から遠い値(電子の質量、アボガドロ定数)は、有効6桁のために 16〜32 バイトを費やす。
- 平方根・累乗など、四則以外にも丸めが要る演算がある。厳密な累乗は桁が爆発する(`(1.004167)^360` の厳密解は小数部 2160 桁・約 898 バイト)。
- 指数部を値ごとに持たせる(十進浮動小数点)と、加算の厳密さ・結合則・丸め箇所の静的な既知性を全て失う。

## 検討した選択肢

- **二進浮動小数点(IEEE 754)**: 実行環境の支援が厚く速いが、十進の値が正確に表せず、加算の順序で結果が変わる。
- **BCD(2進化10進)**: COBOL の系譜。1桁を4ビットで持つため約 17% が無駄になり、演算のたびに桁補正がいる。
- **十進固定小数点(小数桁倍した整数)**: 桁を宣言し、内部は整数演算のみ。誤差の出る箇所が除算・換算に限定される。
- **有理数(分数)**: 除算も厳密だが、分母が計算のたびに膨らみ、値の大きさが実行時まで決まらない。組込みでは使えない。
- **単位を持たない(数値は数値)**: 単純だが、距離と重さの加算が検出できない。
- **単位を型に載せる**: 次元の検査がコンパイル時に効く。組立単位の代数をどこまで持つかが複雑さの分かれ目。
- **静的指数(型に書く指数)**: 桁の窓の位置だけを動かす。厳密さを保ったまま、極端な位置の値を少ない桁で表せる。
- **動的指数(値が持つ指数 = 十進浮動小数点)**: 1つの値の中の動的範囲は広がるが、加算が厳密でなくなり結合則も失われる。

## 決定

### 数値型は十進固定小数点とし、桁の宣言を必須とする

```plaintext
数値(<整数部の桁数>.<小数部の桁数>) <単位 | 単位なし>
数値(<整数部の桁数>.<小数部の桁数> 指数 <e>) <単位 | 単位なし>   # 桁の窓を 10^e ずらす
```

- `数値(7.2) 円` は `-9999999.99` から `9999999.99` までを 0.01 刻みで表す。
- 桁を書かない `数値` は存在しない(省略の禁止・ADR 0008 の型への適用。E9)。値の範囲と刻みは型を読めば分かる。
- 符号は常に持つ。2の補数の整数表現では符号にコストがないため、符号の有無を選択にしない(選択が減れば宣言も減る)。
- リテラルの桁は書かれた通りとする(`123.45` は `数値(3.2)`、`1000` は `数値(4.0)`)。
- **単位を持つ事は必須ではない**。`<単位 | 単位なし>` は選択であり、単位を持たない数値も正規の値である(個数・回数・割合・税率など)。
  必須なのは**単位の欄を書く事**であって、単位を持つ事ではない(下記「単位の欄は省略できない」)。

(改訂済 2026-08-28)ADR 0017 により、数値型は複数になった。本 ADR が定めるのは厳密さが要る側の型であり、名前は `十進数` に改まった。
主に使う型は二進浮動小数点(IEEE 754 binary64)の `実数` である。**本 ADR の規則は1つも取り消されておらず**、全て `十進数` の上でそのまま生きる。

### この形式の名前

新しい形式ではない。既存の体系での呼び名を対応させておく。

| 体系     | 対応する呼称                                  | Shidzuku との違い                                               |
| -------- | --------------------------------------------- | --------------------------------------------------------------- |
| 分類     | **厳密数値型**(exact numeric)                 | SQL 標準の「厳密」対「近似」の区分でいう厳密側だけを持つ        |
| 表現形式 | **位取り整数**(scaled integer)                | 十進の位取りを持つ2進整数。同じ                                 |
| 宣言様式 | **精度と位取り**(precision and scale)         | 同じ                                                            |
| PL/I     | `FIXED DECIMAL(p,q)`(p = 精度、q = 位取り)    | ほぼ同型。単位と静的指数がない                                  |
| COBOL    | `PIC S9(7)V99 USAGE COMP`(暗黙小数点+2進格納) | 同型。`COMP-3`(パック10進)は BCD であり別物                     |
| Ada      | 十進固定小数点型(`delta 0.01 digits 15`)      | 同型。`delta` が 10 のべきに限られる点まで一致                  |
| SQL      | `DECIMAL(p,s)` / `NUMERIC(p,s)`               | 同型。Oracle の `NUMBER(p,s)` は `s` に負を許し、静的指数に相当 |
| Java     | `BigDecimal`(unscaled × 10^-scale)            | 表現は同型だが scale が値ごと(動的)。Shidzuku は型に固定        |
| 信号処理 | Q 形式(Qm.n)                                  | 位取りが二進。Shidzuku は十進                                   |
| 数学     | 十進分数の環 `ℤ[1/10]` の有限部分集合         | 表せる値の集合そのもの                                          |
| 単位     | units of measure(F# の `[<Measure>]`)         | 同型。次元型の系譜(Kennedy, *Dimension Types*, 1994)            |

まとめると、Shidzuku の数値は**単位付き・静的位取りの十進固定小数点数**である。

### 桁の窓の位置は静的指数で動かす

桁の宣言は値の取れる**窓**を決める。窓の**幅**は桁数が、**位置**は指数が担う。

```plaintext
数値(1.5 指数 -31) キログラム    # 6 桁のマンティサ、刻み 10^-36、上限 9.99999e-31
数値(1.5 指数 23) 単位なし       # 6 桁のマンティサ、刻み 10^18、上限 9.99999e23
```

- 値は `m × 10^(e - 小数部桁)` である(`e` を書かない場合は `e = 0`)。指数は**型情報のみ**であり、実行時の値は整数のまま、記憶域は総桁数だけで決まる。
- 指数を書かない事は省略ではない。書かれた桁がそのまま窓の位置を意味する(リテラル `123.45` の小数点位置と同じ)。
- **厳密さを一つも失わない**。加算は両辺の窓の下端(`指数 - 小数部桁`)の細かい方へ揃え、上端の大きい方に桁上がりを1つ足す。乗算は桁も指数も和。いずれも結果の桁は静的に決まり、値は厳密である。
- 窓が大きく離れた値どうしの加算は桁が膨らむ(`指数 23` と `指数 -31` の和は 61 桁 = 26 バイト)。**そのコストはコンパイル時に見える**。黙って片方が消える事はない。
- 有効6桁の物理定数は、指数なしでは 16〜32 バイト(`数値(0.36)`・`数値(24.0)`)を要するが、指数ありでは 4 バイトで済む(思考実験 07)。

**単位の 10 のべき換算は、静的指数の付け替えである。** `ナノメートル` は「`メートル` に指数 -9 を付けた単位」に他ならない。指数を持つ事で、換算は桁を増やさずに書ける。

```plaintext
数値(4.2) メートル  ->  数値(6.0 指数 1) ミリメートル   # 6 桁のまま、刻みは 10 mm
```

指数が無い場合は `数値(7.0) ミリメートル` へ広げるほかなく、元の型が表せない値(9999.999 m)まで受け入れる型になっていた。指数があれば**値の集合が完全に一致する**。

量を持つ値は単位が位置を担うため指数を書く必要は少ない。指数が要るのは、位置を掛ける先が無い**単位なしの値**(確率・比率・無次元の定数)である。

### 内部表現は「小数桁倍した符号付き2進整数」とする

- 値は整数 `m` と宣言された小数部桁 `s` の組で保持し、実数値は `m × 10^-s` である。演算は全て整数演算になる。
- BCD は採らない。10 進1桁に4ビットを要して約 17% が無駄になり、加減算のたびに桁補正がいる。2進整数なら環境の整数命令がそのまま使える。
- 総桁数 `d`(整数部+小数部)を格納するのに必要なビット数は `⌈d × log₂10⌉ + 1`(符号1ビットを含む)である。実装は下表の下限以上のバイト数を選ぶ。

| 割当バイト | ビット | 表せる総桁数 `d` |
| ---------- | ------ | ---------------- |
| 1          | 8      | 2 まで           |
| 2          | 16     | 4 まで           |
| 4          | 32     | 9 まで           |
| 8          | 64     | 18 まで          |
| 16         | 128    | 38 まで          |
| 32         | 256    | 76 まで          |
| 多倍長     | —      | 77 以上          |

- **動作環境の扱いやすい単位へ切り上げてよい**。8 桁の値を 8 バイト境界に揃える、全て 8 バイトに揃える、といった判断は実装の自由である。
- ただし**桁の意味はバイト数に依存しない**。4 バイトに格納された `数値(3.0)` に 1000 を入れる事はできない。余ったビットで桁溢れを救わないため、記述の意味は環境を跨いで同じになる。
- 小数部の桁は表現の大きさに影響しない(スケールは型情報であり、実行時の値には現れない)。総桁数だけがバイト数を決める。
- 単位も型情報のみであり、実行時の表現には現れない。単位の検査に実行時コストはない。

### 演算の規則 — 誤差の出る場所を3つに限る

| 演算               | 結果の桁                                  | 誤差    |
| ------------------ | ----------------------------------------- | ------- |
| `a + b` / `a - b`  | 整数部 = 大きい方 + 1、小数部 = 大きい方  | なし    |
| `a × b`            | 整数部 = 和、小数部 = 和                  | なし    |
| `分ける(a, b)`     | 商・余りとも `a` と同じ桁                 | なし    |
| `割る(a, b, …)`    | 宣言した桁                                | 丸め1回 |
| `換算(a, 単位, …)` | 宣言した桁(10 のべきの換算は自動で無損失) | 丸め1回 |
| `丸める(a, 桁, …)` | 宣言した桁                                | 丸め1回 |
| `累乗(a, n, …)`    | 宣言した桁                                | 丸め1回 |
| `平方根(a, …)`     | 宣言した桁                                | 丸め1回 |

- **除算の演算子は持たない**。除算は必ず `割る(<被除数>, <除数>, <結果の桁>, 丸め <方式>)` と書き、結果の桁と丸め方を明示する。
  記号 `÷` を置くと丸めが暗黙に起き、省略の禁止(ADR 0008)が演算の中だけ破れる。
- **`分ける(a, b)` は商と余りを同時に返す**。`a = 商 × b + 余り` が厳密に成り立ち、商は零方向へ切り捨てる(余りの符号は `a` に従う)。金額の按分で1円が消えない事が型で保証される。
- **桁の検査は値が名前を得る所でのみ行う**。data のフィールド・公開面・状態への受け渡しで検査し、式の中間の桁は自動で広がる(思考実験 06 の 3.2-1)。中間桁も静的に決まるため、所要メモリは実行前に見積もれる。
- **四則以外の丸めが要る演算も同じ形に揃える**。`累乗(底, 回数, 数値(桁), 丸め <方式>)`・`平方根(値, 数値(桁), 丸め <方式>)` は結果の桁と丸め方を宣言する。
  厳密な累乗は桁が爆発するため(`(1.004167)^360` の厳密解は小数部 2160 桁)、累乗は各段で丸める演算としてのみ持つ。
  三角関数・対数は同じ形で追加できるが、必要が確認されるまで語彙に入れない。
- **列の合算は桁の上界が定まらない**。要素数の上限が型に無いため、`合算(列)` の結果は必ず `収める` で受ける(下記の直和)。桁が静的に決まらない演算はこれだけである。
- 小数部を狭める受け渡しは `丸める(値, 数値(桁), 丸め <方式>)` を書く。必ず成功する。
- 整数部を狭める受け渡しは `収める(値, 数値(桁))` を書き、結果は直和 `数値(桁) | 桁溢れ` になる。呼び手が桁溢れを扱うため、実行時に黙って値が壊れる事はない。

### 丸めの語彙 — 既定は持たない

| 方式     | 意味                         |
| -------- | ---------------------------- |
| 切り捨て | 零へ向かう(絶対値が減る)     |
| 切り上げ | 零から離れる(絶対値が増える) |
| 床       | 負へ向かう                   |
| 天井     | 正へ向かう                   |
| 四捨五入 | 半数は零から離れる方へ       |
| 銀行丸め | 半数は偶数側へ               |

消費税の端数処理が事業者の選択であるように、丸め方は設計判断である。既定を置かず、丸めが起きる場所では必ず選ぶ。

### 量(次元)と単位を分けて宣言する

```plaintext
量   長さ 基準 メートル
単位 センチメートル : 長さ = メートル × 1/100
単位 インチ         : 長さ = メートル × 127/5000       # 0.0254 m(1959年の国際定義。正確)

量   体積 = 長さ × 長さ × 長さ 基準 立方メートル       # 組立の量
量   通貨 基準 なし                                     # 換算比を持たない量
単位 円   : 通貨
単位 ドル : 通貨
```

- **量**は加減算・比較の可否を決める。異なる量の加減算・比較はコンパイル時エラー(E12)。距離と重さは足せない。
- **単位**は量に属し、基準単位に対する比で定義する。**比は必ず有理数(整数の分子/分母)で書く**。浮動小数点は換算比に現れない。
- **換算比を持たない量**(`基準 なし`)を認める。通貨(比が時価)と温度(℃↔℉ はオフセットを伴い比で書けない)がこれにあたる。
  同じ量でも単位が違えば加減算も換算もできず(E13)、変換はユニットの body の仕事になる。思考実験 02 の Normalizer の why(機種ごとの単位系の癖を吸収する)がそのまま変換の置き場所になる。
- **組立の量は宣言されたものだけが存在する**。`長さ × 長さ` の結果を受ける量が宣言されていなければエラー(E16)。無名の量は作らない。
- 単位を付ける対象は物理量と貨幣に限り、個数・回数・割合・税率は `単位なし` とする(思考実験 06 の 3.2-3)。`単位なし` の値との乗除算(スカラー倍)は単位を変えない。
- **単位の欄は省略できない。単位を持たない事は `単位なし` と明示する。**
  これは省略の禁止(ADR 0008)を型に適用したものであり、**単位を持つ事を必須にするものではない**。
  必須なのは「単位を持つか持たないか」という選択を書く事であって、単位そのものではない。書かれなかった欄を既定で補う事はしない。
  適用範囲は data のフィールドと公開面の引数・応答である(body 内の式とリテラルには課さない。単位を書かないリテラルは単位なしとして扱う)。

### 桁単位(10 のべき)の換算は無損失に行う

単位 A の1つが単位 B の `10^k` にあたるとき、桁 `(i.f)` の A の値は、桁 `(i+k . f-k)`(`f-k < 0` なら小数部0)の B の値として正確に表せる。

- 受け側の桁がこれを満たせば、丸めの宣言は要らない。`換算(生値, メートル)` は `数値(7.0) ミリメートル` を `数値(4.3) メートル` にする。
- 満たさなければ丸めの宣言を要求する(E14)。
- **同じ量で比が 10 のべきの単位どうしの加減算は、細かい方の単位へ自動で揃える**。`1.5 メートル + 12.3 センチメートル` は `数値(4.1) センチメートル` になる。桁のずらしに過ぎず、固定小数点の内部表現と噛み合う。
- 比が 10 のべきでない単位どうしの加減算は、先に `換算` を書く(E14)。共通の細かい刻み(1/5000 m 等)へ持ち上げれば厳密に足せるが、その刻みには名前がなく、無名の単位を作らないため採らない。

### 換算誤差を小さくする規則

換算誤差は消せない。**隠さず・累積させず・上限を設計者が決める**の3点で扱う。

1. **比は既約の有理数で保持し、浮動小数点を経由しない**。1 インチ = 0.0254 m、1 ポンド = 0.45359237 kg はいずれも定義値であり、`127/5000`・`45359237/100000000` と正確に書ける。
2. **連鎖換算をしない**。任意の単位対の比は基準単位経由の比の積を**先に約分**し、1回だけ適用する。cm → インチ は `(1/100) ÷ (127/5000) = 50/127` であり、cm → m → インチ と2回丸める事はしない。丸めは常に1回である。
3. **掛けてから割る**。分子を掛けて桁を広げてから分母で割る。先に割ると情報が落ちる。
4. **結果の桁を宣言させる**。丸め誤差の上限は結果の最小刻みで決まる(四捨五入なら刻みの半分以下)。桁を書く事は、誤差の上限を設計に書く事である。
5. **換算先の分解能を換算元より細かく取る**。`数値(2.1) センチメートル`(刻み 0.1 cm)を `数値(2.2) インチ`(刻み 0.0254 cm 相当)へ換算すれば、丸め誤差(0.005 インチ = 0.0127 cm)は元の値が持つ分解能より小さい。逆に粗くする換算は警告(W3)とする。
6. **換算は境界で1回だけ**。保持は1つの単位(基準単位を推奨)で行い、表示・外部連携の直前で換算する。往復の換算は一致を保証しない(12.3 cm → 4.84 インチ → 12.2936 cm)。これは型では表せないため指針とする。
7. **比較は換算しない**。同じ量の異なる単位の比較は、基準単位の共通の分母へ交差乗算して整数として比べる。新しい値を作らないため無名の単位も生まれず、丸めが介在しないので厳密である。

仕様が規定するのは**結果**である。「正確な有理数値を、宣言された桁で、宣言された方式で1回丸めた値と一致する事」だけを定め、算法は実装の自由とする(結果桁+1桁まで計算して丸める等の最適化を妨げない)。

### 書けない数は「書けない」と認める

十進固定小数点で表せない数がある。これは実装の不足ではなく位取り記数法の性質であり、隠さずに認める(思考実験 07)。

- **循環小数**(1/3・1/7): 既約分数の分母が `2^a × 5^b` でなければ有限桁にならない。二進でも、指数部を足しても書けない。
- **無理数・超越数**(√2・π・e): 有限の位取り表現に載らない。

いずれも丸めの宣言を伴う演算(`割る`・`平方根`・`累乗`)としてのみ扱える。丸めた値は元に戻らない(`割る(1, 3, 数値(1.3), 丸め 四捨五入) × 3` は `0.999`)。「分けて足すと元に戻る」事が要る場面は、除算ではなく `分ける`(商と余り)で書く。

**繰り返しの中の丸めは累積する。** 丸めの宣言が示すのは1回の誤差の上限であり、反復回数を掛けた上限は型に現れない。0.4 円を `数値(9.0) 円` へ 1000 回足し込めば 400 円が消える。
型で防ぐ手段は無いため指針を置く: **合算する状態は、足し込む値の刻みより細かい桁で持つ**。刻みが粗い加算は警告(W4)とする。

**0 除算は失敗であり、NaN を返さない。** NaN は黙って伝播するため「運用で驚きがない」の反対である。扱いは桁溢れと揃え、U13(失敗の体系)で定める。

### 二進浮動小数点(IEEE 754)との違い

最も広く使われている数値形式との対比を、採否の根拠として残す(binary64 = 倍精度と比べる)。

| 観点             | Shidzuku の数値            | IEEE 754 binary64                          |
| ---------------- | -------------------------- | ------------------------------------------ |
| 基数             | 10                         | 2                                          |
| 小数点の位置     | 型に固定(静的)             | 値ごとに動く(動的)                         |
| 表せる値の集合   | `ℤ[1/10]` の有限部分       | `ℤ[1/2]` の有限部分                        |
| `0.1`            | 厳密                       | 表せない(実体は 0.1000000000000000055511…) |
| 有効桁           | 宣言した桁(上限なし)       | 53 ビット ≒ 十進 15.95 桁                  |
| 範囲             | 宣言した桁                 | ±1.7976931348623157e308、最小非正規 5e-324 |
| 誤差の性質       | 絶対誤差が一定(刻みが一定) | 相対誤差が一定(有効桁が一定)               |
| 丸めが起きる場所 | 宣言した所だけ             | ほぼ全ての演算                             |
| 丸め方の指定     | 演算ごとに記述する         | 実行時のモード(5種)を大域に設定            |
| 加算の結合則     | 成立                       | 不成立                                     |
| 桁溢れ           | コンパイル時に検出         | 実行時に ±∞ へ                             |
| アンダーフロー   | 宣言した刻みで丸め(見える) | 非正規化数を経て 0 へ                      |
| 0 除算           | 失敗(U13)                  | ±∞ を返す(既定で例外は無視される)          |
| NaN              | 無い                       | 有る。`NaN ≠ NaN` で全順序にならない       |
| ±0               | 無い                       | 有る。`0.0 == -0.0` だが `1/0.0 ≠ 1/-0.0`  |
| 記憶域           | 桁数から静的に決まる       | 4 / 8 / 16 バイト固定                      |
| 演算装置         | 整数演算                   | 浮動小数点演算器(FPU)                      |
| 単位・次元       | 型に載る                   | 無い                                       |
| 想定用途         | 金額・在庫・計測           | 科学技術計算                               |

**包含関係は一方向である。** 二進小数(`2^-k = 5^k/10^k`)は全て有限十進になるため、桁さえ足りれば 754 の値は Shidzuku で厳密に表せる。逆は成り立たない(`0.1` は二進で循環する)。ただし 754 の値を厳密に受けるには最大 751 有効桁を要するため、境界では丸めの宣言を伴う受け取りになる(思考実験 07)。

十進を選ぶ理由は、**人が十進で決めた量を扱うため**である。金額・税率・単価・計測値の刻みは十進で定義されており、二進はその値を最初から持てない。

```plaintext
round(2.675, 2)        -> 2.67    # 2.675 の実体は 2.674999999999999822…
0.1 を 10 回足す       -> 0.9999999999999999
0.1 円を 1000 回足す   -> 99.9999999999986
(0.1 + 0.2) + 0.3      -> 0.6000000000000001
0.1 + (0.2 + 0.3)      -> 0.6                # 足す順序で答えが変わる
```

754 も「不正確だった」事を検出する仕組み(inexact 例外)を持つ。しかし既定では無視され、誤差は黙って先へ流れる。**Shidzuku はその検出をコンパイル時の宣言要求へ前倒しした**——これが両者の設計思想の差である。

### 単位の付け外しは名前のある1操作に閉じ込める

- 比で書けない変換(℉→℃、体積から容積重量)は body の中で計算するほかない。そのため `単位を外す(値)` と `単位を付ける(値, 単位)` を持つ。
- この2操作は body 内でのみ書ける。data 宣言・公開面には現れない。ユニットを跨ぐ値には必ず単位が付く。
- 型の外へ出る操作であり、外部世界から値が入る所と同じ性質を持つ。扱いは U12(外部世界との境界)と揃える。

### 検証の追加(第2章 2.3)

| #   | 検査                                                                                      |
| --- | ----------------------------------------------------------------------------------------- |
| E12 | 異なる量の加減算・比較(距離 + 重さ)                                                       |
| E13 | 換算比を持たない量(`基準 なし`)の、単位を跨ぐ演算・換算(円 + ドル、摂氏 → 華氏)           |

## 結果(利点と欠点)

この決定を採ると何が良くなり、何が痛むか。ADR の様式(Michael Nygard、ADR 0007)の「結果」にあたる。

### 利点

#### 正確さと再現性

| 得られる事         | 中身                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- |
| 十進の値が厳密     | 金額・税率・単価・計測の刻みは十進で定義されている。二進はその値を最初から持てない |
| 加減乗が厳密       | 誤差が出るのは除算・10 のべきでない換算・桁の縮小の3箇所だけ                       |
| 加算に結合則が成立 | 合計は足す順序に依存しない。同じ明細は必ず同じ合計になる                           |
| 丸めが記述の一部   | 実行時の丸めモードではないため、同じ記述はどの環境でも同じ結果を出す               |
| 特殊値が無い       | NaN・±∞・±0・非正規化数を持たない。比較は全順序、等価は素直                        |

**分散環境で結果が一致する。** これは Shidzuku にとって単なる正確さ以上の意味を持つ。ユニットは配置単位であり(第0章 0.3)、合意には Raft を用いる(ADR 0001)。
状態機械の複製は「同じ入力から同じ状態へ遷移する」事を前提とするが、浮動小数点は演算装置・最適化・演算順序で結果が食い違い得る。整数演算と宣言された丸めは、その前提を言語の側で満たす。

#### 静的に決まる事

- **桁溢れがコンパイル時に落ちる**。実行時に黙って値が壊れる事がない(桁を狭める所は直和で受ける)。
- **所要記憶域が実行前に決まる**。中間結果の桁も静的なため、組込み・リアルタイムでも見積もれる。
- **型を読めば値の範囲と刻みが分かる**。既定の表という外部知識が要らない(省略の禁止)。
- **誤差の上限が型から読める**。丸め先の桁が、そのまま誤差の上限である。

#### 単位

- 次元の取り違え(距離 + 重さ)がコンパイル時に落ちる。
- 単位系の変換忘れ(m と インチ、℃ と ℉)が型で落ちる。変換の必要は型が示し、変換の中身はユニットが隠す。
- 単位は型情報のみであり、**実行時コストはゼロ**。
- 量ごとに自然な刻みで書ける(単位が桁の窓の位置を担う)。

#### 静的指数

- 極端な位置の値が少ない桁で書ける(有効6桁の物理定数が 16〜32 バイトから 4 バイトへ)。
- 10 のべきの換算が桁を増やさず、**値の集合が完全に一致**する。
- 厳密さ・結合則・静的検査を一つも失わない(動的指数との決定的な差)。

#### 実装の容易さ

- 整数演算のみで済む。演算装置(FPU)の無い環境でも動き、環境差が出ない。
- トランスパイル先への要件は「多倍長整数を持つ事」だけである(U5・ADR 0012)。
- BCD より稠密(1桁 3.32 ビット対 4 ビットで約 17% の節約)で、演算のたびの桁補正も要らない。

### 欠点

#### 記述が重くなる

- すべての数値に桁を書く。`数値(7.2) 円` は `number` より重い。
- 除算・換算・累乗・平方根のたびに結果の桁と丸め方を書く。式が長くなる。
- 量ごとに `量`・`単位` の宣言が要る。組立の量も宣言が要り、無名の量は作れない。
- 桁を狭める受け渡しが直和(`| 桁溢れ`)になり、呼び手に分岐が増える。

#### 設計時に決める負担

- **桁の見積りが設計判断になる**。狭すぎれば桁溢れ、広すぎれば記憶域の無駄。
- 桁と単位は公開面の一部であり、後から広げる事は公開面の変更(W2 の対象)になる。値域の見積りを先送りできない。

#### 表現と計算の限界

- 循環小数(1/3)・無理数(√2・π)は書けない。丸めるほかない(「書けない数は『書けない』と認める」)。
- **1つの値の中の動的範囲は固定**である。桁が大きく離れる計算(尤度の積、条件数の悪い反復解法)は書けない。
- 繰り返しの中の丸めは累積し、その上限は型に現れない(警告 W4 と指針で補う)。
- 厳密な累乗は桁が爆発するため、各段で丸める必要がある。
- 三角関数・対数はまだ語彙に無い。追加はできるが、いずれも丸めを伴う。

#### 性能と記憶域

| 痛み                         | 中身                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| 演算装置を使えない           | 浮動小数点が速い環境では不利。19 桁を超えると多倍長整数の演算になる                  |
| 2 のべきの境目と噛み合わない | 19・39・77 桁の境目でバイト数が倍になる(ナノ秒の時刻は 8 バイトに入るのに 16 バイト) |
| 乗算で中間桁が膨らむ         | `数値(9.2) × 数値(9.2)` は 22 桁。両辺 8 バイトの積が 16 バイトになる                |
| 換算で中間桁が膨らむ         | 10 のべきでない換算は分子を掛けるため(kg → ポンドの分子は 9 桁)                      |

#### 境界と抜け道

- `単位を外す` / `単位を付ける` は型の抜け道である。1操作に閉じ込めているが無くせない。
- 外部世界(IEEE 754 の double、外部形式の数値)との境界では必ず丸めが要る。754 の値を厳密に受けるには最大 751 有効桁を要する。
- 表示・外部連携のたびに換算が要り、往復は一致を保証しない。

#### 生態系

- 既存の数値ライブラリ(統計・線形代数・信号処理)がそのまま使えない。
- 学習の負担がある。桁・指数・単位・丸めの4つを常に意識する事になる。

### 総括 — 何と引き換えに何を得るか

**実行時の驚きを、記述の重さとして前払いする。**

浮動小数点は「書くのは軽く、間違いは後から静かに出る」。この数値型は「書くのは重く、間違いはコンパイル時に出る」。
どちらが割に合うかは、扱う量の性質で決まる。

| 前払いが割に合う                 | 割に合わない                     |
| -------------------------------- | -------------------------------- |
| 金額・在庫・数量(1 の狂いが事故) | 統計・機械学習(誤差が前提)       |
| 計測・制御(単位の取り違えが事故) | 信号処理・数値解析(反復と条件数) |
| 分散した複数ノードでの同じ計算   | 描画・物理シミュレーション       |

Shidzuku の想定用途(業務システム・計測・分散制御)は左側にある。右側が必要になった場合は、数値型を曲げるのではなく、**名前が近似である事を告げる別の型**を設ける(「将来の変更想定」)。

## 捨てたもの・理由

- **二進浮動小数点を既定の数値型にする案**(対比表は「二進浮動小数点(IEEE 754)との違い」): 十進の値が正確に表せず(`0.1 + 0.2 ≠ 0.3`)、加算の順序で結果が変わる。公開面を流れるデータに誤差が入り、第0章 0.5 の「運用で驚きがない」に反する。物理シミュレーション等での必要が確認されたら、別の型として追加を検討する(既定にはしない)。
  → (改訂済 2026-08-28)ADR 0017 が `実数` として追加し、主に使う型とした。ただし**既定にはしていない**(型名は必ず書く)。棄却したのは「書き手が選ばないまま近似の型を使わされる事」であり、その判断は生きている。
- **BCD**: 1桁4ビットで約 17% が無駄になり、加減算のたびに桁補正がいる。2進整数で表現しても十進の桁の意味は型が保つため、BCD の利点(10 進の桁がそのまま並ぶ)は表示の都合に過ぎない。
- **有理数(分数)を数値型にする案**: 除算も厳密になるが、分母が計算のたびに膨らみ、値の所要メモリが実行時まで決まらない。組込み環境で使えず、「静か」でもない。有理数は換算比の宣言にのみ使う。
- **除算演算子 `÷` を置く案**: 丸めが暗黙に起き、省略の禁止が演算の中だけ破れる。書く量は増えるが、誤差の出る場所が読んで分かる方を採る。
- **単位を持たない案**: 距離と重さの加算が検出できない。思考実験 06 で、単位の検査が落とした誤りは型の複雑さに見合った。
- **単位の完全な代数(無名の組立単位を自動生成する)**: `長さ × 質量 ÷ 時間²` のような無名の量が式の途中に現れ、公開面の語彙に名前のない型が漏れる。宣言された組立の量だけを持つ方が、名前で語る情報隠蔽の思想と揃う。
- **オフセット付き変換(℃↔℉、暦)を言語が持つ案**: 加算の意味が単位ごとに変わり(20℃ + 20℃ は 40℃ ではない)、加算可能性の規則が単位ごとに分岐する。複雑さが跳ね上がるうえ、変換は Normalizer 型のユニットが隠すべき知識であり、置き場所は既に仕様の中にある。
- **単位の付け外しを持たない案(抜け道を作らない)**: ℉→℃ も容積重量も書けなくなる。抜け道は無くせないため、名前のある1操作へ閉じ込め、レビューと可視化(U8)の対象にする方を採る。
- **符号の有無を選択にする案(COBOL の `S` 相当)**: 2の補数では符号にコストがない。選択を減らせば、書くべき宣言も減る。
- **動的指数(値ごとに指数を持つ十進浮動小数点。IEEE 754 の decimal32/64/128)**: 得るものは「1つの値の中の動的範囲」だけで、失うものは ADR 0010 が守ろうとしている性質のほぼ全部である。
  加算が厳密でなくなり(`1e16 + 1 = 1e16` と小さい方が黙って吸収される)、結合則も失われる(`(1e16 + 1) - 1e16` は 0、`1e16 + (1 - 1e16)` は 1)。
  丸めが全ての演算で値に依存して起きるため、「丸めは宣言した所だけで起きる」が崩れ、桁溢れの検出も実行時に落ちる。同じバイト数で桁数も減る(8 バイトで 18 桁 → 16 桁)。
  そして**1つの量の中で必要な窓の幅は実際には広くない**(金額 13 桁、製造の長さ 8 桁、確率 7 桁)。量と単位が問題を分割しているため、桁が大きく離れた値どうしの加算はそもそも起きにくい。
  指数部が解くべきなのは窓の**位置**であり、それは静的指数で厳密さを失わずに解ける(思考実験 07)。
- **暗黙の桁の拡張・縮小**: 拡張は無損失なので自動で行うが、縮小は必ず書かせる。黙って桁が落ちる事は「運用の驚き」そのものである。

## 将来の変更想定

- **値域の宣言**(`数値(7.0) 範囲 0..99999`)。乗算の桁の上界が実務では広すぎる問題(思考実験 06 の 3.2-1)への別解。桁の検査を名前を得る所に限る規則で当面は足りるため、Phase 1 の実装で必要が確認されたら検討する。
- **桁溢れの扱い**。`収める` の直和で受けるか、値域の宣言によりコンパイル時に閉じるか。U13(失敗の体系)と揃えて決める。
- **単位の別名・表示形式**(外部表現での `cm`・`℃` の綴り)。外部世界との境界の話であり、U12 で扱う。
- **時刻・期間・時間量との統合**。時間量は本来「量 時間」の値であり、単位(秒・ミリ秒)を持つ。基本型として別に置くか、量の体系へ寄せるかは U14(プログラムの宣言)で整理する。
- **近似の型の追加**。反復解法・確率の積・信号処理は、丸めを1回に閉じ込める形では書けない(思考実験 07 の 3.3-5)。
  必要が確認された場合に限り、**名前が近似である事を告げる別の型**として設ける。公開面に現れたときに、読み手が厳密でないと分かる事が条件である。数値型の既定にはしない。
  → ADR 0017 で `実数`(IEEE 754 binary64)として設けた。条件(名前が近似を告げる・既定にしない)は満たしている。
- **三角関数・対数**。`平方根`・`累乗` と同じ形(結果の桁と丸め方の宣言)で追加できる。必要が確認されてから語彙に入れる。
- **19 桁・39 桁・77 桁の境目**。桁を意味の単位とした代償として、値が 8 バイトに収まってもバイト数が倍になる箇所がある(ナノ秒の Unix 時刻など)。
  実装の裁量で詰める案は、桁の意味がバイト数に依存しなくなるため採らない。既知のコストとして記録する(思考実験 07 の 1.7)。
- 採用時の反映先: ADR 0009 の基本型「数値」の記述を本 ADR に揃え、第1章のデータの宣言に `量`・`単位` を加え、第2章 2.3 に E12〜E16・W3 を追加する。

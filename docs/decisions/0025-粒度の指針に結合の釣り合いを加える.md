# 0025: 粒度の指針に結合の釣り合いを加える

- 日付: 2026-09-26
- 状態: 提案
- 関連課題: U7(Phase 0〜継続)。関連 U14(プログラムの宣言)
- 改訂: ADR 0006(採用)の決定に、シグナルを足す。決定の骨格(1コンポーネント = 隠す設計判断が1つ、機械検証はしない)は変えない
- 依拠: ADR 0024(提案)の決定3(結合バランスを物差しとして取り込む)

## 背景(なぜ決める必要があるか)

ADR 0006 は粒度の指針を「1コンポーネント = 隠す設計判断が1つ」とし、intent の why で判定する。
この基準は APoSD の深いモジュールと Parnas の情報隠蔽から来ており、**一つのコンポーネントの中**を見ている。
大きすぎのシグナルは why が1文で書けない事、小さすぎのシグナルは why が隠す知識を挙げられない事である。

思考実験 22 で既存の記述を結合バランスの三軸(強度・距離・変動性)で読み直したところ、次の事が分かった。

- **書き手は分割を、変わる理由の違いで説明していた。** 思考実験 01〜04・08 の `rejected` の理由のうち12件が変動性の論証だった
  (「変更の理由が異なり」4件、「変更が全ユニットに波及する」8件)。
  思考実験 02 の Normalizer と Aggregator の分割は、ADR 0006 では「why が2文になった」と説明されるが、
  書き手が `rejected` に書いた理屈は「機種追加の度に集約を触る事になる」だった。
- **コンポーネントの間の最短距離は既に遠い。** 1コンポーネントは1プロセスであり(ADR 0012)、兄弟であっても通信はプロセスの境界を越える。
  強く結び合う二つを分けておく費用は、単一プロセスの言語よりも高い。
- **システムの入れ子には束ねる基準が無い。** ADR 0018 は深さに上限を置かず、深すぎる木を粒度の問題とした(第1章 1.5)。
  しかし、どのコンポーネントを同じ内側のシステムに入れるかについては、粒度の指針も何も言っていない。

ADR 0006 の二つのシグナルは、どちらも一つのコンポーネントの why だけを見る。
**二つのコンポーネントの間を見るシグナル**が無いため、上の三つを拾えない。

## 検討した選択肢

- **G1: ADR 0006 のまま置く**: 変動性と結合の判断は `rejected` の理由に書かれており、それで足りるとする。
- **G2: 二つのコンポーネントの間を見るシグナルを足す**: why に加えて `change` と公開面の型を比べる。機械検証はしない。
- **G3: 基準を結合の釣り合いに置き換える**: 「隠す判断が1つ」をやめ、強度・距離・変動性で粒度を決める。
- **G4: 釣り合いを機械で検査する**: 共有する `data` の数や `change` の一致を数え、警告にする。

## 決定

**G2 を採る。** ADR 0006 の基準と二つのシグナルは変えず、次の三つを足す。いずれも機械検証しない。

### 決定1 — 分割のシグナル: 変わる理由が二つある

why が1文で書けても、`change` が**変わる理由の違う**変化を二つ挙げるなら、分割を検討する。

- 思考実験 02 の Normalizer と Aggregator を一つにまとめた場合、`change` は「対応機種の追加」と「ウィンドウ幅の可変化」を並べる事になる。
  前者は機器の事情で、後者は集計の要求で変わる。
- これは ADR 0006 の大きすぎのシグナル(why が2文になる)を、`change` の側から補うものである。
  why は「何を隠すか」を問うため、書き方次第で1文にまとまる。変わる理由は、まとめにくい。

### 決定2 — 統合のシグナル: 同じ物を共有し、同じ理由で変わる

二つのコンポーネントが次の両方に当たるなら、統合を検討する。

- 公開面の型(`data`)を**ほとんど共有**している(モデル結合が強い)。
- `change` が**同じ変化**を挙げている(一方が変わる時は他方も変わる)。

兄弟であってもプロセスの境界を越えるため(背景)、強く結び合い同時に変わる二つを分けておく理由が無い。
ADR 0006 の小さすぎのシグナル(隠す知識を挙げられない)に当たらなくても、この組合せなら統合を検討する。

### 決定3 — 束ね方の指針: 強く結ぶ物を同じ `contains` に置く

コンポーネントを内側のシステムに束ねる時(ADR 0018)、**強く結び合う物を同じ `contains` に置き**、
システムの境界を越える結合は弱く(契約に近く)する。

- 思考実験 21 の `引当番号` は注文管理の内側(Inventory と OrderStore)に留まり、外へは `受注番号` だけが出た。この形が指針に当たる。
- 思考実験 20 の `注文` は、ルートの `expose` から注文管理の内側の OrderStore まで同じ型で届いている。
  指針に照らすと、システムの境界で型を分ける(外向きの型と内側の型)事を検討する対象になる。
- 何を `external` に置くかには、この指針を及ぼさない。そこは指針も持たないと ADR 0018 決定10 が定めている。
  本決定が扱うのは、`contains` の中をどう束ねるかだけである。

### 機械検証はしない

三つとも ADR 0006 と同じく、エラーにも警告にもしない。

- 決定1・決定2 は `change` の内容を比べる。自然言語の内容に踏み込む検証であり、ADR 0003 の決定により言語の仕事にしない。
- 決定2 の「ほとんど共有」、決定3 の「強く結ぶ」には数の閾値を置かない。ADR 0006 が定量基準を捨てた理由と同じである。
- 型の届く範囲(思考実験 22 の 3.2)は構文から計算できるが、それを使うかどうかは U14 と U8 で決める(ADR 0024 決定3)。

## 捨てたもの・理由

- **G1(ADR 0006 のまま置く)**: 書き手は既に変動性で分割を判断しているのに、指針にはそれが無い。
  指針が実際の判断と違う物差しを示すと、レビューで指針を引く意味が薄れる。束ね方(決定3)の空白も残る。
- **G3(基準を置き換える)**: 「隠す判断が1つ」は思考実験 01〜04・08 で機能しており、反例が出ていない(ADR 0006 採用の記録)。
  結合の釣り合いはコンポーネントの間の関係であり、一つのコンポーネントの中の基準の代わりにはならない。二つは補い合う。
- **G4(機械で検査する)**: 本決定の「機械検証はしない」の理由による。
  共有する `data` の数だけを数えると、変わらない型(`受注番号` のような識別子)を多く共有する健全な組まで拾う。

## 将来の変更想定

- U7 は「Phase 0〜継続」の課題である。本 ADR の三つのシグナルも、思考実験と Phase 1 の記述のたびに反例を探す。
  特に決定2 は、既存の思考実験に当てはまる例が無い(統合側の例は思考実験 03 の JobQueue だけで、それは ADR 0006 の小さすぎのシグナルで判定できた)。
  **採否の判断では、決定2 の裏付けが机上の読み直しにしか無い事を考慮する。** Phase 1 の成果物(三層記述のコンポーネント 2〜3 個)を記述した時に当てはまる例が出るかを見る。
- U14 で `data` の帰属を型の届く範囲で決める(思考実験 22 の K-a)なら、決定3 の「システムの境界で型を分ける」は、書き手の指針から構文の帰結に変わる。
  その時は決定3 を U14 の決定に合わせて書き直す。
- ADR 0006 の将来の変更想定にある「body の中の業務判断を intent がどこまで拾うか」(思考実験 10 の論点8)は、
  業務判断が `change` 欄に書かれた事例である。決定1 が `change` を見るため、この論点とも関わる。

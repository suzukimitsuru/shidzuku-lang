# 0016: 検証番号の採番規則

- 日付: 2026-08-28
- 状態: 採用
- 関連課題: U19(検証番号の採番規則。本 ADR で決める)

## 背景(なぜ決める必要があるか)

検証(エラー・警告)の番号は、これまで各 ADR が独立に、通し番号として採番していた。
ADR 0005・0013・0015 の採用(2026-08-28)の反映作業で、この方式が破綻している事が分かった。

| ADR      | 状態 | 採番した番号     |
| -------- | ---- | ---------------- |
| ADR 0009 | 提案 | E11              |
| ADR 0010 | 提案 | E12〜E16・W3・W4 |
| ADR 0013 | 採用 | E17〜E20         |
| ADR 0014 | 提案 | E21〜E23         |
| ADR 0015 | 採用 | E11〜E13         |

- **E11 が二重に使われている**(ADR 0009 と ADR 0015)。E12・E13 も同様である。
- ADR 0013 は E17 から始めた。E14〜E16 を ADR 0010 のために空けたためであり、
  **未採用の決定のために番号を予約する**という不自然な事が起きている。
- 実際に採用されたのは 0013 と 0015 だけなので、仕様書の番号は E1〜E13・E17〜E20 となり、**穴が空いた**。

原因は一つである。**通し番号は「採用された順序」を表してしまう**。
採否の順序は判断の都合で変わるため、番号が判断待ちの ADR の状態に依存する。

そして番号にそこまでの意味は要らない。**検証番号は検査を識別するためのものであり、順序を表す必要はない**。

## 検討した選択肢

- **N1: 仕様書で一元採番する**。仕様書を唯一の採番元とし、ADR は採用時に振り直す。
- **N2: ADR 番号 + その ADR の中での連番**(`E0013-1`)。採番の権限を出自ごとに分ける。
- **N3: 分類ごとの名前空間**(意図系 `EI-1`、通信系 `EC-1` 等)。読んだだけで種類が分かる。

## 決定

### 1. 識別子は `E<出自>-<連番>` とする

エラーは `E`、警告は `W` を頭に置き、**出自**と**連番**をハイフンで繋ぐ。

``` plaintext
E0013-1     # ADR 0013 が定めた 1 番目のエラー
E0015-3     # ADR 0015 が定めた 3 番目のエラー
W0003-2     # ADR 0003 が定めた 2 番目の警告
E0000-1     # ADR を持たない、仕様書本体が定めた 1 番目のエラー
```

- **出自**は決定を記録した ADR の番号(4桁)である。ADR 番号は不変であり、採否の順序に依存しない。
- **連番**はその出自の中での出現順であり、1 から始まる。**エラーと警告で別に数える**。
- ADR を書く側は、自分の ADR の中で 1・2・3 と振ればよい。**他の ADR を見に行く必要がない**。
  採番の競合は原理的に起きない。

### 2. 出自 `0000` は仕様書本体を表す

ADR を持たず、仕様書が直接定めた検査は出自を `0000` とする。`0000` は ADR の番号として使わない予約値である。

現在これに当たるのは4件である。いずれも第0章のビジョンと、第3章の制約の語彙から直接出ている。

| 識別子  | 検査                                   | 出どころ  |
| ------- | -------------------------------------- | --------- |
| E0000-1 | 三層記述の欠落                         | 第0章 0.5 |
| E0000-2 | depends 宣言外のコンポーネントへの通信 | 第3章 3.2 |
| E0000-3 | expose 宣言外の受け口・出口の使用      | 第3章 3.2 |
| E0000-4 | 状態の宣言と障害時の記述の矛盾         | 第3章 3.2 |

### 3. 一度与えた番号は変えない

- 検査の文言を直しても番号は変えない。検査を廃止した場合は**欠番**とし、再利用しない(ADR 0011 が欠番であるのと同じ扱い)。
- 出自が動く事はない。ADR は上書きせず「破棄」として履歴を残す様式であり(ADR 0007)、番号の出自も同じく動かない。

### 4. 適用範囲は仕様書と索引に限る

- 書き換える: `docs/spec/` の全章、`docs/PLAN.md`、`README.md`、`docs/roadmap.html`。
- 書き換えない: `docs/decisions/`(本 ADR より前の全 ADR)と `docs/experiments/`。
  **ADR と思考実験は決定の履歴であり、書かれた時点の番号で読めなければならない**(ADR 0014・0015 決定8 の先例)。
- 旧番号からの読み替え表は第3章 3.3 に置く。

### 5. 提案中の ADR は本文の番号を変えない

ADR 0009(E11)・ADR 0010(E12〜E16・W3・W4)・ADR 0014(E21〜E23)は提案のままであり、本文を書き換えない。
**その ADR の中での連番として読み替える**。

| ADR      | 本文の番号 | 採用時の識別子   |
| -------- | ---------- | ---------------- |
| ADR 0009 | E11        | E0009-1          |
| ADR 0010 | E12〜E16   | E0010-1〜E0010-5 |
| ADR 0010 | W3・W4     | W0010-1・W0010-2 |
| ADR 0014 | E21〜E23   | E0014-1〜E0014-3 |

これで**衝突は消える**。ADR 0009 の E11 は E0009-1、ADR 0015 の E11 は E0015-1 であり、別の識別子になる。
E14〜E16 の予約も不要になり、ADR 0013 が E17 から始めた理由もなくなる(E0013-1 から数え直す)。

## 捨てたもの・理由

- **N1(仕様書で一元採番する)**: これは今の方式に「採番元は仕様書である」と後付けするだけであり、
  **番号が採用の順序に依存する事は変わらない**。判断待ちの ADR が増えるほど不安定になり、
  ADR を書く時点では番号を書けない(採用まで決まらない)。今回の衝突そのものを再生産する。
- **N3(分類ごとの名前空間)**: 読んだだけで種類が分かる利点はあるが、分類の境界が判断を要する。
  E0013-2(役割に許されない操作)は「型の検査」か「層の検査」か——検査が増えるたびに分類の議論が起き、
  境界の変更が番号の変更になる。**出自は一意に決まり、議論の余地がない**。
- **ADR 番号だけを識別子にする**(`E0013`): 1つの ADR が複数の検査を定める(ADR 0013 は4件)。区別できない。
- **番号を持たず名前で識別する**(`必須宣言の欠落`): 文言の変更が識別子の変更になる。
  多言語のコンパイラ出力でも識別子は不変であってほしい。
- **旧番号を残して別名を与える**: 同じ検査に2つの呼び名ができ、どちらで書くかの判断が毎回発生する。
  読み替え表を1か所(第3章 3.3)に置き、仕様書は新番号だけで書く。

## 結果(利点と欠点)

### 利点

- **採番の競合が原理的に起きない**。出自が違えば連番が衝突しても別の識別子になる。
  提案中の ADR がいくつ並んでも、採用の順序が変わっても、番号は動かない。
- **番号から決定を辿れる**。`E0013-3` を見れば ADR 0013 を読めばよいと分かる。
  これは「意図を残す」という Shidzuku の思想そのものであり、検証番号にも同じ原則を適用した事になる。
- **ADR を書く側の負担が減る**。他の ADR の採番状況を調べる必要がない。
- **穴と予約が要らなくなる**。E14〜E16 のような「未採用の決定のための空き」が消える。

### 欠点

- **番号が長い**。`E9` が `E0008-1` になる。コンパイラの出力と会話の両方で字数が増える。
  検査の識別子は目で追う物であり、短さより一意性を取った。
- **`0000` という ADR の無い出自が残る**。4件の検査が「決定の記録を持たない」事が可視化されたとも言える(「将来の変更想定」)。
- **既存文書に旧番号が残る**。ADR と思考実験は書き換えないため、読み手は読み替え表を一度は見る。
  ADR 0014・0015 と同じ負債であり、Phase 1 の検証器実装で新番号に一本化する。

## 将来の変更想定

- **出自 `0000` の4件に ADR を起こすか**。三層記述の欠落・depends / expose の違反・状態の矛盾は、
  仕様書が直接定めており決定の記録が無い。ADR を起こす場合、決定3(番号を変えない)との整合をどう取るか。
  第一候補は「番号は `0000` のまま据え置き、根拠の ADR を出自の欄に併記する」である。
- **コンパイラの出力形式**(Phase 1)。`E0013-3` をそのまま出すか、短縮形を持たせるか。
  短縮形は語彙の一意性を崩すため、現時点では導入しない立場を取る(ADR 0015 が `component` の短縮形を退けたのと同じ)。
- **実行時の検査の扱い**。現在の番号はコンパイル時の検査に付いている。実行時の逸脱(冪等性の重複検出、
  バックプレッシャの期限超過)にも識別子を与えるかは、ログ規約(U4、Phase 2)と併せて決める。

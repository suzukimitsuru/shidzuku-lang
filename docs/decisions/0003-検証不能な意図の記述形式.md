# 0003: 検証不能な意図の記述形式

- 日付: 2026-08-19
- 状態: 採用
- 関連課題: U1

## 背景(なぜ決める必要があるか)

ユニットの三層記述の第一層「意図(Intent)」は、機械は検証できないが言語が記述を強制する(第0章 0.4)。
その記述形式が未定である。論点は次の三つ。

- 自由文か、テンプレートか
- 強制の程度(空欄をエラーにするか。「特になし」等の無意味な文をどう扱うか)
- テンプレートにする場合、項目をどこまで絞るか

## 検討した選択肢

記述形式について。

- **自由文**: 自由度は高いが、何を書くべきかの指針がなく、空疎な文がそのまま通る。
- **テンプレート(全項目必須)**: 問いが指針になる。項目が多いと形骸化する。
- **テンプレート+任意項目**: 任意項目は事実上書かれず、必須項目だけのテンプレートと変わらない。

項目の候補について。

- 理由・棄却・変化(第0章 0.4 の三つの問いと一致)
- 追加候補: 参考資料(任意項目として採用)、トレードオフ、記述者・日付(→「捨てたもの・理由」参照)

強制の程度について。

- 空欄チェックのみ
- 空欄+無意味語の拒否(拒否語リスト)+最小文字数(無意味な文の機械検出)
- 構造の強制(棄却は「選択肢と理由の組」として書かせる)
- 意味的検証(LLM 等による内容の評価)
- 検出した違反の扱い(コンパイル不能のエラーとするか、警告に留めるか)と、段階の数(2段階か、クリティカル/エラー/警告の3段階か)

## 決定

### 強制の目的

強制の目的は**「無自覚な省略の防止」**であり、「悪意の防止」ではない。
テンプレートの問いを書き手に突き付け、書かずには通れなくする事が言語の仕事である。
意図的にすり抜ける事は可能だが、それは無自覚な省略ではなく意図的な行為であり、痕跡がコードに残り、警告(W1・W2)と可視化(U8)で露出する。

この定義から、自然言語の内容に踏み込む機械検証(拒否語リスト・最小文字数・意味的検証)は行わない(「捨てたもの・理由」参照)。

### 項目 — 必須3項目+任意1項目

| 項目           | 問い                                                           | 形式                          |
| -------------- | -------------------------------------------------------------- | ----------------------------- |
| 理由(why)      | なぜこの境界で切るか。このユニットは何の知識を隠すか           | 文                            |
| 棄却(rejected) | 検討して捨てた選択肢は何か。なぜ捨てたか                       | (選択肢, 理由)の組を 1 件以上 |
| 変化(change)   | 将来どんな変化を想定するか。このユニットはそれをどう吸収するか | 文                            |
| 参考資料(refs) | 意図の理解を助ける外部資料はどこにあるか                       | 参照(URL 等)の列挙。任意      |

必須3項目は第0章 0.4 の三つの問い「なぜこの分割か」「何を捨てたか」「将来どう変わると想定するか」に 1:1 で対応する。

「参考資料」は意図の理解を助ける補足であり、無くても意図の記述は成立するため任意とする。
ただし参考資料への参照で必須3項目の本文を置き換える事はできない。

「理由」の問いを「何の知識を隠すか」と立てるのは Parnas の情報隠蔽基準による。
「なぜ作ったか」と問うと動機の説明(「必要だったから」)で埋まるが、「何を隠すか」と問うと設計判断そのものを書かざるを得ない。

「棄却」の対象は、**このユニットの境界を決めた判断の全て**である。
ユニットの分割方法への棄却(例:「注文と在庫を一緒に管理する」)も、ユニットが隠す実装方式への棄却(例:「各ユニットが直接 SQL を書く」)も、どちらも有効とする。
境界は「どう分けるか」と「何を隠すか」の両方で決まるため、対象を一方に限定しない。
(思考実験 01 で両スコープの棄却が自然に書かれ、テンプレートがどちらを求めるか不明という指摘を受けて明記した)

### 強制の程度 — エラーと警告の2段階

深刻度で2段階に分ける。エラーは深刻な違反(意図の記述が欠けている)であり、コンパイル不能とする。
警告は軽微な違反や誤検出があり得る検出であり、コンパイルは止めずに報告する。
誤検出があり得る検査までコンパイルを止めると、通すためだけの無意味な修正を誘発するためである。

**エラー(コンパイル不能)**:

- E1 必須項目の欠落・空欄(任意項目「参考資料」も、書いた場合に空ならエラー)
- E2 棄却の構造: (選択肢, 理由)の組が 1 件以上あること

**警告(コンパイルは通る)**:

- W1 他のユニットと intent 本文が完全一致している(コピペ検出)
- W2 ユニットの公開面・制約(第二層)が変更されたのに intent が未変更である(陳腐化の検出)

`rejected none "<選択肢がなかった理由>"` と明示した場合のみ E2 を免れる。
これは意図的に書かれ、理由も明示されているため、現段階ではエラーにも警告にもしない。
今後、棄却の記録が必須と判断した場合はエラーに変更する。

**検証しない(できない)**:

- 内容の意味的な正しさ・誠実さは機械検証しない。これは意図層の定義(検証不能)そのものである。
  担保はレビューと、可視化(U8: 意図を図に載せる)による露出に委ねる

### 構文の素描(仮)

ユニットの宣言構文(第1章)が未定のため、形式の雰囲気を示す仮の構文。

```plaintext
unit OrderStore {
  intent {
    why      "注文の永続化方式(現在は RDB)の知識をこのユニットに閉じ込める。"
    rejected option "各ユニットが直接 SQL を書く"
             reason "スキーマ変更が全ユニットに波及するため。"
    change   "注文履歴の増加でイベントソーシングへ移行する可能性。移行してもこのユニットの公開面は変えない。"
    refs     "docs/decisions/0012-注文の永続化方式.md"
  }
  ...
}
```

## 捨てたもの・理由

- **自由文**: 書くべき事の指針がなく、空疎な文の検出がテンプレート以上に難しい。
- **追加の必須項目(トレードオフ、記述者・日付)**: トレードオフは「棄却」の理由の中に現れる。
  記述者・日付は版管理システムが持つ情報であり、言語が二重に持たない。必須項目を増やすほど 1 項目あたりの質が下がり形骸化する。
  なお参考資料は、意図の理解を助けるため任意項目として採用した。
- **検出できる違反をすべてエラーに統一する案**: 警告の見逃しは防げるが、誤検出があり得る検査(コピペ・陳腐化)までコンパイルを止めると、通すためだけの無意味な修正を誘発する。深刻な違反のみエラーとし、軽微な物は警告として残す。
- **クリティカル/エラー/警告の3段階**: 現時点の検査は4種であり、深刻(記述の欠落)/軽微(内容への疑い)の2段階で割り切れる。検査の種類が増えて2段階で足りなくなったら導入を再検討する(「将来の変更想定」参照)。
- **拒否語リスト・最小文字数**: 「特になし」等の無意味な文の機械検出として検討したが、拒否語も文字数下限も自然言語(日本語/英語)に依存し、言語仕様が特定の自然言語を仮定する事になるため不採用。
  この結果「特になし」と書けば機械検査は通るが、それは無自覚な省略ではなく意図的な行為であり、強制の目的の外にある。W1・W2 と可視化で露出させる。
- **意味的検証(LLM 等)のコンパイラ組み込み**: 非決定的で、ビルドの再現性を壊す。導入するなら lint・レビュー支援の層に置く。
- **項目の任意化**: 「いずれも省略できない」(第0章 0.4)に反する。

## 将来の変更想定

- intent を必須とするユニットの水準は、粒度の指針(U7)だけでは判断できない。細かいユニットが必要な場合もあるため、階層(例: MVC)の定義や、汎用/専用の区分といった軸の導入を検討する(内部階層の制約宣言 U3 とも関連)。
- W2(陳腐化の検出)の具体化。何をもって「公開面・制約の変更」とみなすかを、Phase 1 の検証器の設計で定める。
- 段階の見直し。検査の種類が増えて深刻/軽微の2段階で足りなくなったら、クリティカル/エラー/警告の3段階への拡張を検討する。
  併せて、警告の見逃しを防ぐ仕組み(ビルド出力の末尾に警告件数を常に要約する等)を実装時に検討する。
- `rejected none` の扱いの再検討。棄却の記録が必須と判断した場合はエラーに変更する。
- Phase 0 の思考実験(既存システムの Shidzuku 記述)で本テンプレートを実際に使い、「書けない」「書く意味がない」場面が出たら項目を見直す。

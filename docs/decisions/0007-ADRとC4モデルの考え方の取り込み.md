# 0007: ADR と C4 モデルの考え方の取り込み

- 日付: 2026-08-19
- 状態: 採用
- 関連課題: U8(図と実装の一致の範囲。Phase 3 決定の先行検討)、U1(意図の記述形式との関係)

## 背景(なぜ決める必要があるか)

Shidzuku の外に、近い問題を解いてきた二つの先行知見がある。

- **ADR**(Architecture Decision Record / アーキテクチャ決定記録): 決定を背景・検討した選択肢・理由とともに1決定=1文書で記録し、
  上書きせず「破棄(superseded)」として履歴を残す様式。本プロジェクト自身が開発プロセスに採用している。
- **C4 モデル**(Simon Brown): ソフトウェア構造を Context / Container / Component / Code の4段階のズームレベルで描く図法。
  ツール Structurizr は「1つのモデルから複数のビューを投影する」「図をコードとして版管理する(diagrams as code)」を実践している。

Shidzuku の意図層(intent)は ADR の縮図であり、可視化の方針(第0章 0.6「図はコードからの抽出」)は C4/Structurizr の「モデル→ビューの投影」と同型である。
車輪の再発明を避けるため、言語本体・開発ツールのどこに何を取り込み、何を取り込まないかを決めておく。

### 対応関係の確認

意図テンプレート(ADR 0003)と ADR の項目はほぼ 1:1 に対応する。

| ADR の項目               | Shidzuku の intent       |
| ------------------------ | ------------------------ |
| 背景(なぜ決める必要が)   | why(何の知識を隠すか)    |
| 検討した選択肢・捨てた物 | rejected(選択肢, 理由)   |
| 将来の変更想定           | change                   |
| 参照                     | refs                     |
| 状態(提案/採用/破棄)     | **対応なし**(決定で扱う) |

C4 のズームレベルと Shidzuku の構造も対応が取れる。

| C4 レベル | Shidzuku での対応                                      |
| --------- | ------------------------------------------------------ |
| Context   | システムと外部の境界(adapter 型ユニットと外部アクター) |
| Container | ユニット(=配置単位。C4 の Container 定義と一致)        |
| Component | ユニットの内部階層(第1章 1.4)                          |
| Code      | body(実装)                                             |

## 検討した選択肢

ADR の取り込みについて。

- **A1: 決定の履歴(提案/採用/破棄)を言語に第一級で持たせる**: intent の改訂を superseded の連鎖として言語が管理する。
- **A2: 言語は「現在の意図」のみ、履歴は開発ツールが Git から抽出する**: 言語仕様は変えず、ツール層で ADR 相当の決定ログを提供する。
- **A3: 取り込まない**: intent と ADR は別物として関係を定義しない。

C4 の取り込みについて。

- **C1: C4 をそのまま採用する**: Phase 3 の図は C4 の4図とする。
- **C2: 原則のみ取り込み、図は独自設計+C4 互換エクスポート**: ズームレベル・投影・diagrams as code の3原則を設計原則とし、
  図自体は Shidzuku の三層記述と基本ユニットに即して独自設計(PLAN Phase 3 の方針)。Structurizr DSL / Mermaid C4 への変換出力を互換レイヤとして検討する。
- **C3: 参照しない**: 独自設計を白紙から行う。

## 決定

### ADR — A2: 言語は「現在の意図」、履歴と決定ログはツールの仕事

- **言語本体は変えない**。intent は「現在の設計意図」のスナップショットであり、決定の履歴(いつ・何から変わったか)は版管理システムが持つ。
  これは ADR 0003 の決定(記述者・日付など版管理が持つ情報を言語が二重に持たない)の一貫した適用である。
- **開発ツールが ADR 相当を提供する**。Git 履歴と W2(陳腐化検出)の情報から、ユニット・フローごとの「意図の変遷ログ」
  (いつ why/rejected/change が変わったか=決定の履歴)を抽出・表示する。これは Phase 3 の可視化(U8「意図を図に載せるか」)の一部として設計する。
- **refs でプロジェクト ADR と相互接続する**。ユニット境界を超える決定(プロトコル選定・トランスパイル先など)はコードでなく docs/decisions/ の ADR に置き、
  intent の refs で参照する(思考実験 01 で使用済みの型)。ツールは refs のリンク切れを警告する(W3 候補。検証器設計時に採否を決める)。
- **スコープの整理**: ユニットの intent は「ユニット境界の決定」、フローの intent は「接続の決定」、ADR 文書は「システム横断の決定」。
  プログラム全体レベルの intent 宣言は、思考実験 01〜04 で必要が現れていないため今は導入しない(「将来の変更想定」参照)。

### C4 — C2: 3原則を取り込み、図は独自設計+互換エクスポート

C4 から取り込むのは図法ではなく**原則**である。

1. **ズームレベル**: 抽出する図は単一の抽象度でなく、文脈(システムと外部)→ ユニットフロー(ユニットと接続)→ ユニット内部(階層)→ コード、の4段で見せる。
   読者(運用者・設計者・実装者)によって必要な高度が違うという C4 の知見をそのまま使う。
2. **図はモデルの投影**: 1つのモデルから複数のビューを描き、図を手で描かない(Structurizr の原則)。
   Shidzuku はさらに進めて「コードそのものがモデル」であり、図は常にコードからの抽出とする(第0章 0.6 の再確認)。
3. **diagrams as code**: 図の定義と出力は版管理に乗るテキストとして扱う。

図そのものは C4 を採用しない。理由は、Shidzuku の図には C4 に無い要素——障害境界(どこで壊れてよいか)、接続の属性(pressure・配達保証)、
意図の表示(U8)——が第一級で必要であり、C4 の「箱と線」の一般図に還元すると言語の核が図から消えるためである。

ただし既存エコシステムへの漸進的導入(第0章 0.7 の戦略)として、**Structurizr DSL / Mermaid C4 形式へのエクスポート**を Phase 3 で検討する。
対応関係(ユニット→Container、内部階層→Component)は上表の通り自然に定まるため、変換は機械的にできる見込みである。

## 捨てたもの・理由

- **A1(履歴の言語内第一級化)**: ADR 0003「版管理が持つ情報を言語が二重に持たない」と矛盾する。
  intent の過去版は Git に完全に残っており、言語が持ち直すと二重管理になる。
- **A3・C3(取り込まない)**: 決定の記録様式・ズームレベルという検証済みの知見を再発明する事になる。
  特に「読者によって必要な抽象度が違う」という C4 の知見は、ユニットフラット1枚の図では大きな系で破綻する事を先回りして教えている。
- **C1(C4 をそのまま採用)**: 障害境界・接続の属性・意図という Shidzuku 固有の要素が C4 の語彙に無い。
  また PLAN Phase 3 の方針(既存の枠組みに縛られず三層記述と基本ユニットに即して設計する)と矛盾する。
- **プログラム全体レベルの intent の即時導入**: 思考実験で必要が現れていない。仕様は思考実験駆動で育てる(進め方の原則)。

## 将来の変更想定

- Phase 3(可視化)の抽出器を設計する際、本 ADR のズームレベル4段と「意図の変遷ログ」を U8 の決定として具体化する。
- プログラム全体レベルの intent(システム横断の決定をコード内に置く形)は、思考実験で「refs では足りない」場面が出たら再検討する。
- W3(refs のリンク切れ警告)の採否は Phase 1 の検証器設計で決める。
- Structurizr / Mermaid C4 エクスポートの採否は Phase 3 で、その時点のエコシステムの普及度を見て決める。
- 開発ツールと既存 ADR ツール(Log4brains 等)の連携(docs/decisions/ の公開サイト化)は、必要になったら検討する。

# 0032: 実行モデルと順序保証 — 待つ所で次を受ける逐次とし、重ならない仕事の組を宣言する

- 用語: FIFO(First In, First Out、先に入った物が先に出る)。本 ADR の「仕事」は、コンポーネントが一つの起点(受け口に届いた一件・時計・期限切れ)から始めて終えるまでの処理を指す。

- 表記: body の記法(U26)は決まっていない。body は擬似的に書き、待つ所を `待つ` と書く(思考実験 32 と同じ)

## 背景(なぜ決める必要があるか)

### 1. コンポーネントの中の動き方が決まっていない

コンポーネントの間は、共有メモリを持たず `ask` と `flow` だけで通信すると決めた(ADR 0004)。だがコンポーネントの**中**が何本で動くか、`ask` の応答を待つ間に次の要求を受けるかは決まっていない。

- 接合面の三つの呼び出し——要求を送る(接合面の2つ目)・要求を受ける(3つ目)・流れを受ける(5つ目)——の写し元が無い。
  計画書 第4節 4.5 の移行の条件 M3(接合面の写し元)は、これを本 ADR に待たせている。
- 内側の並行を許すなら、全ての `state` に並行時の扱いの欄が要る(思考実験 24 の論点1(状態の欄))。許さないなら、その理由を宣言の数で示す必要がある。

### 2. 順序を誰も約束していない

思考実験 02(センサー収集パイプライン)の `SensorIntake -> Normalizer : flow 計測値` は、計測値が送った順に届く事を前提に読める。今の仕様はそれを言っていない。
durable の再送(第4章 4.4(配達保証))で順序が乱れるかも言っていない。受け手が順序を前提に書けるかどうかが、ここで決まる。

### 3. `pressure block` の上限の書き方

第4章 4.6(未定事項)は、`block` の上限を「実装を待たずに決める」唯一の語彙として残した。動作環境が待ち行列を作る時に上限が要る事は、ADR 0012 の机上検証2 で確認済みである。

### 4. `ask` の閉路

第3章 3.5(未定事項)は、`ask` の閉路の扱いを実行モデルの再入の決定と組にして Phase 1 の前に決めるとした。再入を許さなければ閉路は必ず期限切れになり、許せば状態が待つ所を跨いで書き換わる。

### 5. 問いは一つに集まる

思考実験 32 は、上の問いを九つに分けて書き下ろし、**全てが「待つ所で何をするか」の一つに集まる**事を示した(思考実験 32 の第7節(所見))。
閉路の成否、出る順の入れ替わり、`ask` の応答と `flow` の到着の扱い、溜まる物の上限が、そこから決まる。
計画書 第4節 4.3 が U10 と U11 を同時に決めるとした判断に従い、一本の ADR で決める。

## 検討した選択肢

### 論点1: コンポーネントの中は逐次か並行か

| 案                     | 中の動き                                                                   | 先行例                                                 | 分かった事(思考実験 32)                                                                    |
| ---------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 待たせる逐次           | 仕事を一件ずつ処理する。待つ間も次の仕事を取り出さない                     | Erlang の `gen_server:call` の呼び手側、Orleans の既定 | 読みが書きの詰まりに巻き込まれる。期限が待ち行列の長さで破られる。`ask` の閉路は必ず止まる |
| 待つ所で次を受ける逐次 | 仕事を一件ずつ計算するが、待つ所で止まっている間は次の仕事を取り出してよい | JavaScript のイベントループ、Orleans の再入可能な型    | 状態と待つ所の両方を持つ仕事どうしで追い越しが起きる。TypeScript では何もしなくてもこの形  |
| 内側の並行             | 複数の仕事を同時に計算する。状態は共有され、同期は言語か記述者が担う       | Hike の `threadable`・`concurrent`、Java のスレッド    | TypeScript に写せない。全ての `state` に欄が増える                                         |

### 論点2: 待つ所で次を受けるか、それを選ぶ単位

思考実験 32 の第10節(論点3 の数え上げ)は、思考実験 01・02・04 の 14 の受け口と 1 つの時計の仕事に当てた。**害が出たのは 3 か所**であった。

| 形                                        | 増える物                   | 3 か所の害を防げるか                                 | 擦れる所                                                                |
| ----------------------------------------- | -------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- |
| 待たせる逐次に固定                        | 無し                       | 防げる                                               | 論点1 の表の通り、読みと期限が巻き込まれる                              |
| 待つ所で次を受ける逐次に固定              | 無し                       | 防げない。記述者が待つ所の後で読み直す               | KVCore の整合性の規則が body に沈む。Persister の害は読み直しで防げない |
| 受け口ごとに全て書く                      | 14 語                      | KVCore・Persister は防げる。時計の仕事は書く所が無い | 11 か所で「次を受けてよい」を書き写す                                   |
| コンポーネントごとに1行書く               | 11 行                      | KVCore の取得まで待たせる                            | 論点1 の問題が KVCore に残る                                            |
| 待つ所のある受け口だけに書く              | 10 語と時計の分            | 防げる                                               | 待つ所の有無は body を読むまで分からない                                |
| 重ならない仕事の組を宣言する(`exclusive`) | 3 行(と、書かない所の扱い) | 防げる。時計の仕事と受け口の組も書ける               | 書かない所の扱いが、省略の禁止(ADR 0008)との論点になる                  |

- **害は受け口ではなく、仕事の組に出る。** KVCore は `格納` と `格納`、Persister は `書込記録` と `書込記録`、Aggregator は時計の締めと受け口であった。
- **状態の宣言からは害を推せない。** Persister の害は `state` に無いログのファイル(`io` の層の向こう)から出た。

### 論点3: 待つ所の印と、送り出しと待ちの分離

- 再入の害は待つ所にだけ出るため、待つ所が body に現れていれば、害の起き得る所が読める(思考実験 24 の論点3(待つ所の印))。
- 互いに依存しない `ask` を先に送り、後で並べて待つ形(思考実験 24 の論点2(送り出しと待ちの分離))は、**待ちの並行**であり計算の並行ではない。論点1 のどの案でも書ける。

### 論点4: `ask` の閉路

| 実行モデル             | 閉路で起きる事                                                          |
| ---------------------- | ----------------------------------------------------------------------- |
| 待たせる逐次           | 毎回期限切れになる。`on failure` が毎回走り、記述の上では誤りが見えない |
| 待つ所で次を受ける逐次 | 動く。ただし状態は待つ所を跨いで変わり得る                              |
| 内側の並行             | 動く。状態の扱いは `state` の欄に依る                                   |

- 閉路はコンパイル時に見つけられる。ADR 0031 の決定6(記述の中の接続は全てどれかの `flow` 宣言に現れる)により、`ask` の接続の一覧が漏れなく取れる。
- 動くとしても、閉路は双方向の強い結合である(ADR 0024 の物差し)。

### 論点5: 順序

| 問い                             | 思考実験 32 で分かった事                                                                       |
| -------------------------------- | ---------------------------------------------------------------------------------------------- |
| 一本の `flow` の中               | 接続ごとの待ち行列が一本なら、送り手1つ・受け手1つの中は FIFO が自然に成り立つ。Zenoh とも合う |
| durable の再送                   | 受領の無い最も古い物から元の順で再送すれば、重複はあり得るが追い越しは無い                     |
| 接続を跨ぐ順序                   | 送り手が違えば、届く順に意味は無い。時間の順はデータの `時点` で並べる                         |
| `ask` の応答と `flow` の到着の間 | 別の接続であり順は無い。「応答を先に届ける」約束は、Zenoh への写しで通り道を束ねる事になる     |
| 待つ所で次を受けた時の、出る順   | 入る順が FIFO でも、出る順は入れ替わる。全体の順は待たせた所でだけ保たれる                     |

### 論点6: 上限

| 溜まる所                    | 分かった事                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| `pressure block` の待ち行列 | 上限が要る。数は列の長さであり、`uint64(0) 要素` で書ける(E0019-4(列の長さ・添字の型))     |
| `pressure drop` の待ち行列  | 上限が要る。どこからあふれるかが決まらないと「あふれた分を捨てる」が意味を持たない         |
| `pressure latest`           | 意味から 1 である。選択の無い所に宣言を強いるのは重さである(ADR 0023 が捨てた案と同じ理由) |
| `ask` の受け口の待ち行列    | 期限は寿命を縛るが件数を縛らない。受け口は複数の呼び手が共有するため、接続の欄には書けない |
| 待つ所で止まっている仕事    | 再入すると、局所の値を抱えた仕事が溜まる。Orleans も一つの活性化に入れる要求の数を縛る     |

## 決定

### 決定1 — コンポーネントの中は逐次とする。内側の並行は採らない(論点1)

一つのコンポーネントの中で、**同時に計算している仕事は常に一つ**である。

- `state` に並行時の扱いの欄を足さない。状態を同時に触る仕事は無いため、ロックの語彙も要らない。
- 理由は二つある。内側の並行は TypeScript に写せず、同じ記述子の Rust 出力と TypeScript 出力を置き換える混在の適合試験(ADR 0012 の決定9(互換性の単位))が成り立たない。
  また、第0章 0.9 の Erlang/OTP の系譜(プロセスの中は逐次)と揃う。
- 一件の計算が重く処理量が足りない時は、コンポーネントを複製する。複製は最小の分散動作環境(Phase 2)の課題(Raft の適用範囲(U6))であり、言語の中には置かない。

### 決定2 — 待つ所で次の仕事を受ける。待つ所の範囲を三つに定める(論点2)

仕事が待つ所で止まっている間、コンポーネントは次の仕事を取り出して始めてよい(再入)。これを基本の動き方とし、待たせたい所は決定3(重ならない仕事の組)で宣言する。

待つ所は、次の三つに限る。

| 待つ所                    | 例                                                                          |
| ------------------------- | --------------------------------------------------------------------------- |
| `ask` の応答を待つ        | OrderIntake が `引当` の応答を待つ                                          |
| `pressure block` の受付   | KVCore が `書込記録` を流し、動作環境が受け付けるまで待つ                   |
| `io` の層の外部への入出力 | OrderStore のデータベース、Persister のログのファイル、Alerter の外への通知 |

- `pure` の層の計算は待つ所にならない。待つ所の無い仕事は、始めてから終えるまで他の仕事と重ならない。
- 三つ目は、思考実験 32 の第10節が見つけた範囲である。Persister の害は外部への入出力で止まっている間に出た。外部への入出力の書き方そのものは外部世界との境界(U12)に依る。
- TypeScript では `await` の付く所が、Rust では `.await` の付く所が、ちょうど待つ所に当たる。

### 決定3 — 重ならない仕事の組を `exclusive` で宣言する(論点2)

コンポーネントの `constraint` に、重なってはならない仕事の組を書く。

```plaintext
exclusive <仕事>, <仕事>, ...      # 名指した仕事どうしは重ならない(同じ仕事どうしを含む)
exclusive none                     # 重ならない組を持たない(明示)
```

- `exclusive` は必須の宣言とする。重ならない組を持たないコンポーネントも `exclusive none` と書く(決めた事1(`exclusive none` を書かせるか))。

- 名指した仕事のどれかが始まってから終えるまで(待つ所で止まっている間を含む)、同じ組の仕事は始めない。待たされた仕事は、**取り出した順に**始める。
- `exclusive 格納` のように一つだけ名指せば、その仕事どうしが重ならない。
- 一つの仕事は複数の組に入ってよい。全ての仕事を一つの組に入れれば、そのコンポーネントは待たせる逐次になる。**論点1 の待たせる逐次は、この宣言の一つの場合として書ける。**
- 仕事は名前で指す。受け口(`ask` の受け口と `flow` の受け口)はその `expose` の名前、時計の仕事はその名前(決定4)、期限切れの仕事は `on expiry <接続>` と書く。
- 害を見つけるのは記述者である。言語は `state` と待つ所から害を推して宣言を省かせない(Persister の害は `state` に現れなかった)。

```plaintext
component KVCore {
  constraint {
    depends    Persister
    expose     取得(キー) -> 値 | なし bound 256 要素
    expose     格納(キー, 値) -> 完了 | 失敗 bound 64 要素
    expose     書込記録(キー, 値, 版) flow out
    state      KV表 recoverable(Persister.再生)
    exclusive  格納                       # 格納どうしは重ならない。取得は格納の待つ所で受けてよい
  }
}
```

### 決定4 — 仕事の起点は三つとし、時計で始まる仕事に名前を付けて宣言する

仕事の起点は、**受け口に届いた一件・時計・期限切れ**の三つに限る。

| 起点     | 宣言する所                                       | 名指し方           |
| -------- | ------------------------------------------------ | ------------------ |
| 受け口   | `expose`(`ask` の受け口と `flow in`)             | `expose` の名前    |
| 時計     | `constraint` の `timer`(決めた事2(時計の仕事))   | `timer` の名前     |
| 期限切れ | `flow` 宣言の `on expiry`(ADR 0031 の決定9)      | `on expiry <接続>` |

```plaintext
timer <名前> every <時間>          # 時計で始まる仕事。<時間> は 量 時間 を持つ数値
```

- 置き場は `constraint` とする(決めた事2(時計の仕事))。語(`timer`・`every`)は仮であり、識別子と言語語彙の表記(ADR 0014)に従って採用時に決める。

- 思考実験 02 の Aggregator の締めは、これまで起点が宣言されていなかった。経過時間計はコードに出さない(ADR 0012 の決定2(責務の分担))ため、body が自分で眠って起きる形も書けない。
  時計の仕事を起こすのは動作環境とする(決定12(接合面への写し))。
- 同じ時計の仕事は、前の一件が終わるまで次を起こさない。起こせなかった回は重ねずに飛ばし、飛ばした事をログ規約(U4)の対象とする。
- 時計の仕事は公開面ではない。他のコンポーネントからは呼べない。

### 決定5 — 待つ所を body に印として現す。送り出しと待ちを分けてよい(論点3)

- body の中の待つ所(決定2 の三つ)は、印として読める形で書く。記法は body の記法(U26、ADR 0027)で決める。
- 互いに依存しない `ask` は、先に送り出し、後で並べて待ってよい(待ちの並行)。計算の並行ではないため、決定1 を破らない。
- 印の書き方と、送り出しと待ちの分け方の構文は ADR 0027 の物差し「待つ所の印」に渡す。本 ADR は要求だけを置く。

### 決定6 — 上限を `bound` で書く。`latest` には書かせない(論点6)

`flow` の接続の `pressure` に、待ち行列の上限を書く。

```plaintext
SensorIntake -> Normalizer : flow 計測値 pressure block(deadline 1 秒, bound 64 要素) (transient)
Normalizer   -> Aggregator : flow 正規化済み計測値 pressure drop(bound 256 要素) (transient)
Aggregator   -> Alerter    : flow 集約値 pressure latest (transient)
```

- `bound` は `uint64(0) 要素` の数であり、1 以上とする。新しい量は足さない。
- `bound` が数えるのは、その接続で受け手がまだ終えていない物である——受け口の待ち行列に並んでいる物と、取り出して仕事を始めたが終えていない物の和である。
  durable では、受領を返していない物を数え、この件数一つで記憶と永続の記憶域の両方を縛る(決めた事4(durable の `bound`))。
- `block` は `bound` に達した所から、送り手を `deadline` まで待たせる。`drop` は `bound` に達した後に来た物を捨てる。どちらも残った物の順は変えない。
- `latest` の上限は意味から 1 であり、`bound` を書かせない。
- `block` と `drop` の `bound` の欠落は、E0008-1(必須宣言の欠落)の対象に加える。
- 上限が書かれていれば、ESP32 の最小の動作環境で、配置の設定の時に記憶が足りるかを照らせる(ADR 0029 の決定3(能力と配置の設定))。

### 決定7 — `ask` の受け口に上限を書く(論点6)

`ask` の受け口の `expose` に、その受け口が抱えてよい要求の数を、受け口ごとに書く(決めた事3(`ask` の受け口の上限))。

```plaintext
expose <名前>(<引数>) -> <応答> | <失敗> bound <数> 要素
```

- 数えるのは、その受け口に入ってまだ応答を返していない要求である——待ち行列に並んでいる物、待つ所で止まっている物、`exclusive` で待たされている物の和である。
  **受け口の待ち行列と、待つ所で止まっている仕事の上限を一つにまとめる**(思考実験 32 の第5節 5.3(同時に抱える仕事の上限))。
- 上限を超えた要求は動作環境が拒み、呼び手には接続の失敗として届く。ADR 0031 の決定2(接続の失敗はフローが翻訳する)がそのまま引き受け、新しい失敗の種類を足さない。
  ログのために添える種類(ADR 0031 の決定11(接合面への写し))に「受け口の上限」を足す。
- `flow` の受け口の仕事は、決定6 の接続の `bound` が縛る。時計の仕事は決定4 により一件である。したがって、**コンポーネントが同時に抱える仕事の数は、宣言の和で上から抑えられる。**
- `ask` の受け口の `bound` の欠落は、E0008-1(必須宣言の欠落)の対象に加える。

### 決定8 — 一本の `flow` の接続の中は FIFO とする(論点5)

- 送り手1つ・受け手1つの `flow` の接続の中で、受け口に入る順は送った順である。受け手は、取り出す順をこの順に保つ。
- `latest`・`drop` は途中を捨てるが、残った物の順を入れ替えない。
- これは**入る順**の約束である。受け手が再入すれば、仕事の**出る順**(下流へ流す順)は入れ替わり得る(決定10(言わない順序))。
  入った順のまま出したい所は、決定3(重ならない仕事の組)で待たせる。
- ファンアウトの各接続は、従来通り互いに独立である(第4章 4.3(バックプレッシャ))。

### 決定9 — durable の再送は、受領の無い最も古い物から元の順で行う(論点5)

- 受け手が落ちて再起動した時、動作環境は受領の返っていない最も古い物から、元の順で再送する。再送用の別の通り道を作らない。
- これにより、durable の接続では「**重複はあり得るが、追い越しは無い**」と言える。重複は受け口の `idempotent` が受ける(E0004-1(durable と idempotent))。
- 第4章 4.4(配達保証)の durable の意味に、この一文を足す。実現手段(永続化・再送・Raft の適用)は従来通り Raft の適用範囲(U6)で定めるが、どの手段もこの約束を守らなければならない。

### 決定10 — 言わない順序を明記する(論点5)

次の順序を、言語は保証しない。新しい語は足さず、仕様書に「保証しない事」として書く。

| 保証しない順序                       | 頼りたい時に書く物                                                  |
| ------------------------------------ | ------------------------------------------------------------------- |
| 送り手が違う接続を跨ぐ順             | データの `時点` や鍵で並べる                                        |
| `ask` の応答と `flow` の到着の間の順 | 鍵で引いて、待ちが無ければその旨を body で受ける(ADR 0031 の決定10) |
| 一つのコンポーネントの受け口を跨ぐ順 | 同上。どの受け口から次を取り出すかは、動作環境が決める              |
| 再入した仕事の出る順                 | `exclusive` で待たせる(決定3)                                       |

- **`correlate` の並びは送った時間の順であり、届く順ではない。** ADR 0023 の `correlate 受注番号 : 受注 -> 受注の状態` は、`受注の状態` が `受注` の応答より先に届く事を排除しない。
  採用時に第4章 4.2 の `correlate` の節に読み方として足す。ADR 0023 の本文は書き換えない。
- 「応答を先に届ける」約束は置かない(捨てたもの・理由)。

### 決定11 — `ask` の閉路を検証器で見つける(論点4)

- `flow` 宣言の `ask` の接続だけで、コンポーネントの間の有向グラフを作る(呼び手から受け手へ)。`flow` の接続の辺は数えない(応答を待たないため)。
  ADR 0031 の決定6(記述の中の接続は全てどれかの `flow` 宣言に現れる)により、辺は漏れなく取れる。
- 重さは二段に分ける(決めた事5(`ask` の閉路の重さ))。
- 閉路があれば警告とする(W0032-1)。決定2 により閉路は動き得るが、双方向の強い結合であり、ADR 0024 の物差しで警告に値する。
- body の記法(U26)が決まり、どの仕事がどの `ask` を待つかが読めるようになったら、さらに細かく見る。
  閉路をたどって、待つ所で止まっている仕事と**同じ `exclusive` の組の仕事**が呼ばれる道があれば、その閉路は必ず期限切れになるためエラーとする(E0032-3)。
- `flow` の循環(フィードバック)は、従来通り Phase 1 の検証器設計で決める(第3章 3.5)。

### 決定12 — 接合面への写し(ADR 0012 の決定3 を改訂する)

ADR 0012 の接合面の呼び出しのうち、本 ADR が写し元になる物の中身を定める。接合面の凍結(ADR 0012 の決定10)は従来通り TypeScript が通ってからである。

| 呼び出し                                 | 本 ADR で定める中身                                                                                       |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 結合(接合面の1つ目)                      | 記述子に、`ask` の受け口ごとの `bound`、`flow` の接続ごとの `bound`、時計の仕事の名前と間隔を載せる       |
| 要求を受ける / 応答を返す(接合面の3つ目) | 前の要求に応答する前に、次の要求を渡してよい。渡すのは受け口の `bound` までで、超えた要求は動作環境が拒む |
| 流す(接合面の4つ目)                      | `block` は `bound` まで溜め、超えたら `deadline` まで待たせる。`drop` は `bound` を超えた物を捨てる       |
| 流れを受ける / 受領を返す(接合面の5つ目) | 接続の中は送った順に渡す。durable の再送は、受領の無い最も古い物から元の順に渡す                          |
| 時計の仕事を起こす(**10個目を足す**)     | 動作環境が、記述子に載った間隔で時計の仕事を名前で起こす。前の一件が終わっていなければ起こさない          |

- **`exclusive` は生成コードがコンポーネントの中で守る。** 動作環境は知らない。動作環境が見るのは宛先・型の指紋・期限・要求の識別子だけである(ADR 0012 の決定4(接合面を流れる物))。
- 呼び出しの番号の振り直しと表の書き換えは、採用時に ADR 0012 に改訂の記録として足す(ADR 0031 が9つ目を足したのと同じ扱い)。

### 決定13 — 出力先への写し

## suzukimitsuru が決めた事(2026-11-06)

起案の時に「suzukimitsuru に決めてもらう事」として置いた五つである。2026-11-06、suzukimitsuru の判断により、五つとも推奨の通りに決めた。
候補の表と理由は、決めた時の材料として残す。決めた事は本文の決定3・4・6・7・11・14 に書き入れた。

### 決めた事1: `exclusive` を書かない時に `exclusive none` を書かせるか

| 候補                            | 増える物                                                     | 合う所                                                   | 擦れる所                                         |
| ------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- | ------------------------------------------------ |
| 必須(`state none` と同じ)       | 害の無いコンポーネントに1行ずつ(思考実験 01・02・04 で 8 行) | 省略の禁止(ADR 0008)に沿う。重なってよいと考えた事が残る | 害の無い所が多い(14 の受け口のうち 11)           |
| 該当時のみ(`idempotent` と同じ) | 無し                                                         | 害の起きる3か所だけに書く                                | 書かなければ重なってよい事になり、既定値に見える |

**決定: 必須(推奨の通り)。** 害は `state` から推せず(Persister)、言語は代わりに見つけられない。書き手が「重なってよい」と判断した事を残すのが、`state none`・`expose none` と同じ省略の禁止の趣旨である。
`idempotent` が該当時のみで済むのは、必要な所(durable の受け口)を言語が E0004-1(durable と idempotent)で名指せるためであり、`exclusive` にはその手掛かりが無い。

### 決めた事2: 時計で始まる仕事の語と置き場

| 候補                                              | 合う所                                                 | 擦れる所                                                                                   |
| ------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `constraint` に `timer <名前> every <時間>`       | 公開面ではない事が読める。`exclusive` から名前で指せる | 語が二つ増える                                                                             |
| `expose` に並べる                                 | 仕事の起点が一か所に揃う                               | 他から呼べない物が公開面に載る。E0000-3(expose 宣言外の受け口・出口の使用)の読み方が変わる |
| 外部世界との境界(U12)に送る(時計を外の入力と見る) | 外部の時刻(driver からの注入)と同じ所で決まる          | 記述の中で閉じる仕事を外に出す。U10 の決定が U12 を待つ                                    |

**決定: `constraint` に `timer`(推奨の通り)。** 時計の仕事は他のコンポーネントから呼べず、外部の何かでもない。語(`timer`・`every`)は仮であり、語の選び方は識別子と言語語彙の表記(ADR 0014)に従って採用時に決める。

### 決めた事3: `ask` の受け口の上限の置き場

| 候補                      | 合う所                                                         | 擦れる所                                                            |
| ------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------- |
| `expose` の欄(受け口ごと) | 受け口は呼び手に共有されるため、受け口の側が上限を持つのが合う | `ask` の受け口の全てに語が一つ増える                                |
| コンポーネント全体に一つ  | 記憶の見積もりと直に結ぶ                                       | 重い受け口が軽い受け口の枠を食う。KVCore の取得が格納に巻き込まれる |
| 置かない(期限だけで縛る)  | 増える物が無い                                                 | 件数が縛られない(毎秒 1000 件・期限 500 ミリ秒で 500 件)            |

**決定: `expose` の欄(推奨の通り)。** コンポーネント全体に一つでは、論点1 で避けた「読みが書きに巻き込まれる」形が上限の取り合いとして戻ってくる。

### 決めた事4: durable の `bound` が何を縛るか

| 候補                                       | 合う所                               | 擦れる所                                                   |
| ------------------------------------------ | ------------------------------------ | ---------------------------------------------------------- |
| 件数一つで、記憶と永続の記憶域の両方を縛る | 語が増えない。transient と同じ読み方 | 永続の記憶域の大きさは件数だけでは決まらない(一件の大きさ) |
| 永続の記憶域の上限を別に書かせる           | 記憶域の見積もりが記述に現れる       | 接続の欄が重くなる。配置の都合が記述に入る                 |

**決定: 件数一つ(推奨の通り)。** 記憶域の大きさは、件数と型から見積もり、配置の設定(ADR 0029 の決定3(能力と配置の設定))で照らす。記述子に記憶の見積もりを載せるかは、コンポーネントのバージョンと移行(U16)へ送る。

### 決めた事5: `ask` の閉路の重さ

| 候補                                                         | 合う所                               | 擦れる所                                          |
| ------------------------------------------------------------ | ------------------------------------ | ------------------------------------------------- |
| フローの段は警告、body で `exclusive` の組に閉じる物はエラー | 動く閉路と必ず止まる閉路を分ける     | エラーの側は body の記法(U26)を待つ               |
| 全てエラー                                                   | 双方向の強い結合を記述から締め出せる | 動く閉路(思考実験 32 の第3節 3.4)まで書けなくなる |
| 全て警告                                                     | 検査が一段で済む                     | 必ず止まる閉路が、記述の上で誤りとして見えない    |

**決定: 一つ目(推奨の通り)。** フローの段の閉路は警告(W0032-1)、body で `exclusive` の組に閉じる閉路はエラー(E0032-3)とする。決定11(`ask` の閉路)の通りである。

## 机上検証

### 検証1: KVCore の格納 — 思考実験 32 の第3節 3.1 の追い越し

```plaintext
時刻 1  格納(k, A) : 版 = 1 → 待つ(書込記録 k, A, 1)      # exclusive 格納 により、次の格納は始めない
時刻 2  取得(k)    : 受けて KV表[k] を返す                # 取得は組に無いため、格納の待つ所で受ける
時刻 3  格納(k, A) の書込記録が受け付けられ、KV表[k] = (A, 1)。格納(k, A) を終える
時刻 4  格納(k, B) : 版 = 2 → 待つ(書込記録 k, B, 2)      # 取り出した順に始める
```

- 追い越しは起きない。取得は書きの詰まりに巻き込まれない。
- 1 秒詰まった間に溜まる格納は、`格納` の `bound 64 要素` を超えた所で拒まれ、ClientGate には接続の失敗として届く。

### 検証2: OrderIntake — 同時に来た 10 件

- `state none` であり、`exclusive none` と書く。10 件は待つ所で重なり、最後の1件も最大 300 ミリ秒前後で返る。期限 500 ミリ秒は待ち行列の長さで破られない。
- 抱える仕事の数は `受注` の `bound` で抑えられる。溢れた分は Frontdesk に接続の失敗として届き、ADR 0031 の `on failure` が翻訳する。

### 検証3: Aggregator — 時計の締めと受け口の組

```plaintext
component Aggregator {
  constraint {
    expose     正規化済み計測値(計測値) flow in
    expose     集約値(集約) flow out
    state      ウィンドウ volatile
    timer      締め every 1 分
    exclusive  締め, 正規化済み計測値      # 締めの間に届いた計測値は、締めの後のウィンドウに入る
  }
}
```

- 締めが `集約値` を流して待つ間、届いた計測値は受け口の待ち行列に並ぶ。締めを終えてから取り出すため、消えない。
- 待ち行列は `Normalizer -> Aggregator` の `pressure drop(bound 256 要素)` で抑えられる。締めの待ちが長引いて溢れた分は、宣言された廃棄として捨てられる。

### 検証4: Persister — durable の再送と追記の順

- `exclusive 書込記録` により、追記は取り出した順に一件ずつ行う。取り出す順は接続の中の FIFO(決定8)により KVCore が流した順である。
- Persister が m3 の受領を返す前に落ちると、再起動後に m3・m4 の順で届く(決定9)。m3 の重複は `idempotent 書込記録` が受ける。ログの順は崩れず、`再生` の順も崩れない。

### 検証5: Frontdesk — `ask` の応答と `flow` の到着(思考実験 20 の論点3)

- `受注番号` の応答と `受注の状態` の到着の順は保証しない(決定10)。Frontdesk は `受注` の応答を待つ所で `受注の状態` を受け取り得る。
- `受注の状態` の受け口は、`受注番号` で引いて待ちが無い時の扱いを body に書く(ADR 0031 の決定10(鍵の合わない到着))。
  Frontdesk が `exclusive 受注, 受注の状態` と書けば、`受注の状態` は受注の応答の後まで待ち行列で待つ。どちらを選ぶかは記述者の判断であり、宣言に残る。

## 捨てたもの・理由

| 捨てたもの                                     | 理由                                                                                           |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 内側の並行                                     | TypeScript に写せず、混在の適合試験が成り立たない。全ての `state` に欄が増える(決定1)          |
| 待たせる逐次に固定                             | 読みが書きに巻き込まれ、期限が待ち行列で破られる。`exclusive` で全ての仕事を一組にすれば書ける |
| 待つ所で次を受ける逐次に固定(読み直しは記述者) | KVCore の整合性の規則が body に沈む。Persister の害は読み直しでは防げない                      |
| 受け口ごとに再入を選ぶ印(仮の語 `turn`)        | 11 か所で同じ答えを書き写す。時計の仕事を書く所が無い。害は受け口ではなく仕事の組に出る        |
| 言語が `state` と待つ所から害を推す            | Persister の害は `state` に無いログのファイルから出た。推せない所が残る                        |
| 「応答を先に届ける」約束                       | `ask` と `flow` の通り道を動作環境が束ねる事になり、Zenoh への写し(ADR 0001)を縛る             |
| 再送用の別の待ち行列を許す                     | 追い越しが起き、受け手が順序を前提に書けなくなる                                               |
| `ask` の受け口の上限を接続の欄に書く           | 受け口は複数の呼び手が共有し、呼び手ごとの上限の和が受け口の上限にならない                     |
| `latest` にも `bound` を書かせる               | 意味から 1 であり、選択の無い所に宣言を強いる                                                  |
| `exclusive` を該当時のみ書く                   | 書かなければ重なってよい事になり、既定値に見える。言語は害の在る所を名指せない(決めた事1)      |
| 時計の仕事を `expose` に並べる                 | 他から呼べない物が公開面に載り、E0000-3 の読み方が変わる(決めた事2)                            |
| 時計を外部世界との境界(U12)に送る              | 記述の中で閉じる仕事を外に出し、実行モデル(U10)の決定が U12 を待つ(決めた事2)                  |
| `ask` の受け口の上限をコンポーネント全体に一つ | 重い受け口が軽い受け口の枠を食い、読みが書きに巻き込まれる形が戻る(決めた事3)                  |
| `ask` の受け口に上限を置かない                 | 期限だけでは件数が縛られない(決めた事3)                                                        |
| durable の永続の記憶域の上限を別に書かせる     | 接続の欄が重くなり、配置の都合が記述に入る(決めた事4)                                          |
| `ask` の閉路を全てエラーにする                 | 動く閉路(思考実験 32 の第3節 3.4)まで書けなくなる(決めた事5)                                   |
| `ask` の閉路を全て警告にする                   | 必ず止まる閉路が、記述の上で誤りとして見えない(決めた事5)                                      |

## 結果(利点と欠点)

### 利点

- 九つの問いが、待つ所で次を受ける事と、重ならない組の宣言の二つで答えられる。待たせる逐次も宣言の一つの場合として書ける。
- 三つの出力先で同じ意味になる。TypeScript は何もしなくても基本の動き方になる。
- 順序の約束が二つ(接続の中の FIFO と、再送で追い越さない事)に絞られ、それ以外はデータに書く事がはっきりする。
- コンポーネントが同時に抱える仕事と待ち行列が、宣言の和で上から抑えられる。ESP32 の記憶の見積もりに使える。

### 欠点

- 待つ所を跨いだ状態の古さは、`exclusive` の組を誤れば残る。言語は害を推さないため、記述者の判断に頼る(`exclusive` を必須とした(決めた事1)ため、`none` と判断した跡は残る)。
- 害の無いコンポーネントにも `exclusive none` が1行ずつ増える(思考実験 01・02・04 で 8 行)。
- `ask` の受け口の全てと、`block`・`drop` の全ての接続に `bound` が増える。
- 必ず止まる閉路のエラー(E0032-3)は body の記法(U26)を待つ。それまでは警告(W0032-1)だけである。

## 将来の変更想定

- **一件の計算が重い仕事**が出たら、`pure` の層の計算だけを別に走らせる形を検討する。状態に触らないため、決定1 の「状態を同時に触る仕事は無い」を破らずに足せる見込みがある。
- 処理量のための**複製**は、最小の分散動作環境(Phase 2)で Raft の適用範囲(U6)と併せて決める。複製の間の順序は本 ADR の約束の外である。
- `bound` と時計の間隔を、記憶の見積もりとしてコンポーネント記述子に載せるかは、コンポーネントのバージョンと移行(U16)で決める。
- 3言語目以降を足す時、`exclusive` の写しに漏れが出たら、決定13 の表の改訂として記録する。
- 「応答を先に届ける」約束が要る題材が出たら、Zenoh 以外の写し先と併せて見直す。

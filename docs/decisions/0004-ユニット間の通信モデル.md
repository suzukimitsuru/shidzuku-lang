# 0004: ユニット間の通信モデル

- 日付: 2026-08-19
- 状態: 採用
- 関連課題: U2

## 背景(なぜ決める必要があるか)

基本ユニットは「フローの節」であり(第0章 0.3)、ユニット間の通信のみが言語の管轄である(第0章 0.4)。
しかしその通信方式が未定である。論点は次の三つ。

- 非同期メッセージのみか、同期呼び出しも許すか
- バックプレッシャ(下流が詰まった時に上流をどうするか)の扱い
- フロー(接続)そのものに何を記述させるか

思考実験から次の入力を得た。

- 思考実験 01(注文管理): 応答が要る場面(引当可否・受注番号)が2箇所あり、非同期のみでは応答経路を手で組む事になり記述が捻れる。
  また、保存失敗時に引当を解放する補償の流れが必要だった。
- 思考実験 02(センサー収集): 全通信が「流しっぱなし」で足り、同期呼び出しは1箇所も不要だった。
  バックプレッシャの要求は同じユニットの出力でも接続ごとに異なった(欠損不可の保存は block、通知は latest)。
- 両実験共通: 「なぜこの順序か」「なぜこのポリシーか」という判断がどのユニットの intent にも属さず、フローに意図を書く場所が必要だった。
- 思考実験 03(画像変換): ask の世界(応答期限あり)と flow の世界の境目で、期限なしの block が応答期限を破った。
  また、受付 ID を返した後のジョブは「失ってはならない」が、flow の配達保証(ユニットの障害を跨いでメッセージが残るか)が未定だった。

## 検討した選択肢

通信方式について。

- **非同期メッセージのみ**(Erlang 流): モデルが一つで済むが、要求-応答を相関 ID と応答経路の手組みで表す事になる。
- **同期呼び出しのみ**(RPC 流): ストリームとファンアウトが不自然になり、待ちの連鎖で障害が同期的に伝播する。
- **両方式**: 要求-応答(ask)と非同期の流れ(flow)を言語が第一級で提供する。

バックプレッシャについて。

- ユニットの属性として宣言する
- 接続(フロー)の属性として宣言する
- 実行系が暗黙に処理し、言語では書かせない

フローの意図について。

- フローに intent を書かせない(意図はユニットのみ)
- フローの intent を任意とする
- フローの intent を必須とする(ユニットと同じテンプレート)

## 決定

### 通信は ask と flow の2方式

| 方式 | 意味                 | 応答                                         | 用途の例                   |
| ---- | -------------------- | -------------------------------------------- | -------------------------- |
| ask  | 要求-応答            | 必ず返る(成功応答、または失敗・タイムアウト) | 引当の可否、受注番号の発行 |
| flow | 非同期の一方向の流れ | なし                                         | 計測値ストリーム、イベント |

思考実験 01 が「非同期のみ」への反証、思考実験 02 が「同期のみ」への反証であり、両方式を採る。

ask は構文上は要求-応答だが、実行系では非同期メッセージ+応答として実装する。
ユニットを跨ぐ直接呼び出しや共有メモリは存在しない(ユニット=障害境界=配置単位を保つため)。
ask の応答は必ず返る: 相手の障害・タイムアウト時は失敗応答が返り、呼び出し側が待ち続ける事はない。
ask は期限を必ず宣言する(有限値)。期限は「必ず返る」の保証を実行系が果たすための上限であり、既定値は置かない(ADR 0008 による改訂)。

### バックプレッシャは接続の属性

flow の接続ごとに pressure を宣言する(必須。既定は置かない。ADR 0008 による改訂)。

| ポリシー | 意味                                     |
| -------- | ---------------------------------------- |
| block    | 下流が詰まったら上流を待たせる(欠損なし) |
| latest   | 最新値のみ保持し、途中の値を捨てる       |
| drop     | あふれた分を捨てる                       |

- どのポリシーも明示の選択である。黙ってデータが消えるのは「運用の驚き」であり、静かさの理念に反する。捨てる事(latest / drop)は宣言によってのみ起きる。
- block は**期限を必ず宣言する**(無期限も `期限なし` と明示。ADR 0008 による改訂)。期限内に受け付けられない投入は失敗として上流に返り、上流はそれを扱える(受付不可を応答する等)。
  応答期限を持つ ask の世界と flow の境目では、期限なしの待ちが応答期限の違反になるため(思考実験 03)。
- latest / drop で捨てた事実、および block の期限超過は、ログ規約(U4)の対象イベントとする(Phase 2 で具体化)。
- ファンアウト(1出力を複数のユニットへ流す)の各接続は互いに独立とする。片方の詰まりは他方に波及しない。
  これは pressure が接続ごとの属性である事の帰結でもある(思考実験 02 の論点4)。

### 配達保証は接続の属性

flow の接続ごとに配達保証を宣言する(必須。既定は置かない。ADR 0008 による改訂)。

| 保証      | 意味                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------ |
| transient | 平常時は届くが、ユニットの障害・再起動を跨ぐと失われ得る                                         |
| durable   | ユニットの障害・再起動を跨いで失われない。実行系が永続化・再送し、受け口に idempotent を要求する |

- durable は永続化・再送のコストを伴い、全接続に課すと計測値ストリームのような系で無用の重さになる。
  失えない接続(受付 ID を返した後のジョブ等。思考実験 03)だけが durable を明示的に負う。transient を選ぶ事も明示の判断である。
- transient の消失は「黙った消失」にはならない。障害時に何が失われ得るかは `on failure` と「失ってよい状態」の宣言(第2章で定める)に現れ、durable でない事自体が記述から読める。
- durable の実現手段(永続化・再送・Raft の適用)は U6 として Phase 2 で定める。

### フローも intent を持つ(必須)

フロー宣言はユニットと同じ意図テンプレート(ADR 0003: why / rejected / change 必須、refs 任意)を必須で持つ。
検証(E1・E2・W1・W2)もユニットの intent と同じに適用する。

処理の順序(引当を保存より先に)、ポリシーの選択(通知は latest で良い)、補償の設計(保存失敗時は引当を解放)といった判断は接続に宿り、どのユニットにも属さない。
2つの思考実験で連続して必要になったため、任意ではなく必須とする。

### 障害時の記述はフローに書く

フローは `on failure <ユニット>` で、障害を伝播させない事に加えて**何で埋め合わせるか**(補償・代替応答・再起動)を記す。
「伝播させない」だけの宣言は、思考実験 01(補償)・02(失ってよい状態)の通り不完全である。
補償・「失ってよい状態」の語彙の詳細は第2章(制約の体系)で定める。

## 捨てたもの・理由

- **非同期メッセージのみ**: 思考実験 01 で応答経路の手組みが必要になり、この種のシステム(応答を返す API)で記述が捻れる。
- **同期呼び出しのみ**: 思考実験 02 のストリーム処理が不自然になり、待ちの連鎖が障害境界を跨いだ同期的な伝播経路になる。
- **バックプレッシャをユニットの属性にする**: 思考実験 02 で同じユニットの出力が接続ごとに異なるポリシーを要求した。ユニットの属性では表せない。
- **バックプレッシャを実行系任せにして書かせない**: 捨てる/待たせるは設計判断であり、暗黙にすると障害時の挙動が記述から読めなくなる。
- **既定を latest / drop にする**: 黙ってデータが消えるのは驚きであり、欠損の許容は明示の判断としてのみ書けるべき。
- **フローの intent を任意にする・書かせない**: 順序・ポリシー・補償の判断が宿る場所がなくなる。ユニットだけ強制してフローを自由にすると、意図の強制(第0章 0.4)に穴が開く。

## 将来の変更想定

- pressure の語彙の拡張(バッファ上限付き block 等)は、Phase 1 の実装で必要が確認されてから追加する。
- ask のタイムアウト値・再試行の規定は、第2章(制約の体系)と U4(ログ規約)に合わせて定める。
- ADR 0001(Zenoh)へのマッピング(flow=Pub/Sub、ask=Query)は Phase 2 で検証する。
- フローの intent が実務で形骸化しないか(ユニットより書きにくい可能性)は、思考実験 03 以降で継続観察する。
- (改訂済 2026-08-20)ADR 0008(省略の禁止)の採用により、本 ADR の既定規定(pressure の block 既定・配達保証の transient 既定・期限の任意宣言)は「宣言必須・既定なし」に改訂した。

# 0008: 省略の禁止 — 既定値を持たない言語

- 日付: 2026-08-20(初版 2026-08-19 は内部階層宣言のみを扱った。本版で全体原則に改訂)
- 状態: 採用
- 関連課題: 全体(第0章の制約として記述)。U2(ADR 0004 の既定規定を改訂)・U3(ADR 0005 の省略規定を改訂)

## 背景(なぜ決める必要があるか)

初版の本 ADR は「階層を宣言しないユニットは body 全体を io とみなす」という既定の廃止(内部階層宣言の必須化)を扱った。
レビューで、その意図は階層に限らないと明確化された: **全ての省略を無くし明示する事で、記述を読むのに外部知識(言語の既定規則)を不要にする**。

省略時の既定とは、書かれなかった事を言語の既定表で補って意味を決める仕組みである。
既定がある限り、読み手は「書かれた事」に加えて「書かれなかった事+既定表」を知らなければ挙動を読めない。
これは三層記述の思想(ユニットはそれ自体で読める)に反し、書き手にも「既定に任せた」のか「検討して選んだ」のか区別が付かない記述を許す——
ADR 0003 が定めた強制の目的「無自覚な省略の防止」の、言語語彙そのものへの適用である。

この制約はユニット・フローの全語彙に影響するため、第0章(ビジョン)に全体制約として記述する事を目標とする。

## 原則の定義と適用範囲

**原則: 選択のある宣言に、省略時の既定を置かない。該当が無い事も「なし」と明示する。**

この原則は既に仕様の中に萌芽がある。`rejected none`(ADR 0003: 棄却が無い事の明示)と `depends なし`(思考実験の型)である。
本 ADR はこの型を全語彙に一般化する。

原則の対象外を明確にしておく(何でも書かせる事が目的ではない)。

- **言語の不変条件**: 全ユニットが障害境界である事、ask が必ず返る事など。これらは選択肢が無く、既定ではなく言語の意味論である。
- **約束の欠如**: `idempotent` を書かない事は「冪等性を保証しない」であり、既定値ではなく約束の不存在である。
  全ての性質に有無の宣言を強制すると宣言が形骸化する(ADR 0003 の教訓: 項目を増やすほど質が下がる)。
- **挙動を決めない任意情報**: intent の refs 等。書かなくても記述の意味は変わらない。

## 既存仕様の棚卸し

省略できる(または未規定の)箇所を仕様全体から洗い出した。

| 宣言               | 従来                          | 改訂後                                 |
| ------------------ | ----------------------------- | -------------------------------------- |
| layers(ユニット)   | 省略=io(ADR 0005)             | 必須(本 ADR 初版の決定を維持)          |
| depends(ユニット)  | 未規定                        | 必須。依存が無ければ `depends なし`    |
| expose(ユニット)   | 未規定                        | 必須。公開面が無ければ `expose なし`   |
| state(ユニット)    | 省略=状態なし(暗黙)           | 必須。状態を持たなければ `state なし`  |
| pressure(接続)     | 省略=block(ADR 0004)          | 必須                                   |
| 配達保証(接続)     | 省略=transient(ADR 0004)      | 必須                                   |
| block の期限(接続) | 省略=無期限                   | 必須。無期限も `期限なし` と明示       |
| ask の期限(接続)   | 既定値を Phase 1 で定める予定 | 必須(有限値)。既定値は置かない         |
| on failure(フロー) | 書かないユニットの挙動が暗黙  | フローに参加する全ユニットについて必須 |

棚卸しで発見が2つあった。

1. **`isolate failure` は不変条件と重複していた**。第0章 0.3 で全ユニットが障害境界であり、非伝播は宣言する事ではなく言語の意味論である。
  一部のユニットだけが宣言すると「書かれていないユニットは伝播させるのか」という暗黙の意味(誤読)が生まれる。制約の語彙から削除する。
2. **ask の期限は「必ず返る」の保証と一体だった**。相手が沈黙した時に失敗応答を返すには期限が要る。
  期限なしの ask は「必ず返る」を保証できないため、ask の期限は有限値で必須とする(第3章 3.6 の未定事項「既定値を定める」は「既定値を置かない」で解消)。

## 机上検証 — 思考実験 01〜04 への適用

省略を全て明示に直すと何が起きるかを、既存の4フローで確かめた。

| 思考実験    | 省略されていた箇所                              | 明示した結果                               |
| ----------- | ----------------------------------------------- | ------------------------------------------ |
| 01 受注処理 | ask の期限×2、on failure OrderIntake            | **入口ユニットの障害時挙動が未定義**と判明 |
| 02 計測     | 配達保証×4、on failure SensorIntake             | **受信ユニットの障害時挙動が未定義**と判明 |
| 03 画像変換 | 配達保証×2、ask の期限×2、on failure UploadGate | 同上(入口)                                 |
| 04 格納     | ask の期限、on failure ClientGate               | 同上(入口)                                 |

思考実験 04 のフローを全て明示で書き直した例。

```plaintext
flow 格納 {
  intent { ... }                        # 従来と同じ(既に必須)
  ClientGate -> KVCore    : ask 格納(キー, 値) 期限 2s -> 完了 | 失敗
  KVCore     -> Persister : flow 書込記録  pressure block(期限 1s)  durable
  on failure ClientGate : 外部へ失敗を返す(伝播しない)
  on failure KVCore     : ClientGate は失敗を返す。再起動し、Persister の再生() から KV表 を復元する
  on failure Persister  : KVCore は格納に失敗を返す(伝播しない)
}
```

検証から分かった事。

- **負担は接続あたり1〜3語、フローあたり1〜2行**。書けない箇所は無かった。
- **省略の明示化そのものが穴を見つけた**。4フロー中4つで、入口ユニット(OrderIntake・SensorIntake・UploadGate・ClientGate)の障害時挙動が
  書かれておらず未定義だった。既定があると「書き忘れ」と「検討して省略」が区別できない——本原則の必要性の実証である。
- 初版の机上検証(全15ユニットへの layers 適用。15ユニットすべてに pure の芯が見つかった)も本原則の実証として引き継ぐ。

## 決定

1. **原則を第0章 0.4 に全体制約として記述する**。「Shidzuku の記述に省略時の既定は存在しない。選択のある宣言は必ず明示し、
  該当が無い事も『なし』と書く。ユニットとフローは、言語の既定規則という外部知識なしに、それ自体で読める。」
2. **棚卸し表の通り各語彙を必須化する**(第1〜3章を改訂)。ADR 0004 の既定規定(block 既定・transient 既定)と
  ADR 0005 の省略規定は本 ADR が改訂する(各 ADR に注記)。
3. **`isolate failure` を制約の語彙から削除する**。障害の非伝播は全ユニットの不変条件であり、埋め合わせはフローの `on failure` に書く。
4. **検証を追加する**: E9「必須宣言の欠落」(depends・expose・state・layers、接続の pressure・配達保証・期限、on failure)、
  E10「state 宣言に無い状態の保持」(`state なし` を含む)。

## 捨てたもの・理由

- **初版(内部階層のみの必須化)**: 原則の一適用例に過ぎず、他の既定(block・transient・無期限)が残ると
  「ユニットは明示・フローは暗黙」という捻れが生じる。
- **「安全側の既定は残す」案**(block・transient は安全だから省略可のままとする): 安全かどうかは読み手が既定表を知って初めて分かり、
  既定である事自体が外部知識である。しかも「安全側」は文脈依存で、block は KV ストアでは安全だが API の入口では応答期限違反になる(思考実験 03)。
- **全性質の有無宣言の強制**(idempotent を全公開面に必須にする等): 約束の欠如は既定値ではない。
  強制すると「idempotent でない」の羅列で宣言が形骸化する。
- **isolate failure を全ユニット必須にする案**: 不変条件の重複記述は情報量ゼロの行を全ユニットに強制し、形骸化の見本になる。
  語彙から消し、構造(ユニット=障害境界)に語らせる方が明示的である。
- **既定を残して lint で「既定に依存した省略」を警告する案**: 警告は無視できるため既定表の学習は結局必要になり、目的(外部知識の不要化)を達しない。

## 将来の変更想定

- 記述量の不満は、言語の既定(暗黙)ではなく開発ツールの雛形生成(明示の生成)で解決する。Phase 1 で検討する。
- E9・E10 の検証粒度(状態の保持の判定等)は、Phase 1 の検証器とトランスパイル先(U5)の設計で定める。
- 今後の語彙追加(pressure の拡張等)では「既定を置かない・なしを明示できる」を設計規則とする。
- 「なし」の明示が増えて雑音になる場合(該当なしが大半の宣言が現れた場合)は、その宣言の要否自体を見直す(既定の再導入はしない)。

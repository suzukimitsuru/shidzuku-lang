# 0026: shidzuku-lint の作成 — 既存の言語への応用を仕様と共に考える

- 日付: 2026-09-28
- 状態: 採用(suzukimitsuru の判断による。起案と同日。同日に suzukimitsuru の指示で決定1・決定5 を改め、決定6 の採用を確かめた)
- 関連課題: 全体(Phase 1〜継続)。関連 U5・U12
- 依拠: 思考実験 26(判定の表と論点1)、思考実験 24(Hike)、ADR 0012(出力先の言語)、ADR 0003(`rejected` の形)
- 区別: ADR 0008・0013 が lint を退けたのは、言語としての Shidzuku(shidzuku-lang)の判断である。既存の言語を対象とする shidzuku-lint はそれとは別に考える(決定1)

## 背景(なぜ決める必要があるか)

思考実験 26 は、第3章 3.3 の検査と、それを支える宣言を、既存の言語(主に Rust と TypeScript)の lint に移せるかで4つに分けた。

- **そのまま移せる(11件)**: L-1・L-2・L-4・L-5・L-10・L-11・L-17・L-18・L-19・L-22・L-30
- **宣言を足せば移せる(17件)**: L-12・L-16・L-20・L-21・L-23〜L-29・L-32〜L-34・L-36〜L-38
- **既にある(10件)**: L-3・L-6〜L-9・L-13〜L-15・L-31・L-35
- **移せない(9群)**: 障害の非伝播・配達保証・フロー・システムの入れ子・量の種別の算術 等

その上で、shidzuku-lint を作るか・いつ作るかを論点1 として suzukimitsuru に委ねていた。
Phase 0 の間は実装に着手しない原則(計画書 第9節)があり、lint は Shidzuku の実装ではないが、道具を作る点では同じだからである。

判断の材料として、思考実験 26 は**lint にする作業が、Shidzuku の仕様の穴を見つけた**事を記録している。
直和の分岐の「残り全部」(論点2)、警告の抑止の書き方(論点3)、外への要求の期限(論点5)の三つは、
Shidzuku の中だけで考えていた間は見えず、既存の言語に当てた時に初めて見えた。

suzukimitsuru は、**他の言語での応用を言語仕様と共に考える事で得る物がある**と判断し、作る事を決めた。本 ADR はその判断と、時期・範囲を記録する。

## 検討した選択肢

作るかどうかと時期:

- **T1: 作らない**: 思考実験 26 の表を Phase 1 の検証器の設計の入力に留める。
- **T2: Phase 0 のうちに作る**: 「そのまま移せる」11件は Shidzuku の構文を決めずに作れる。
- **T3: Phase 1 の言語実装から作り、継続して改良する**: 検証器と並べて作り、Phase 2 以降も仕様と共に育てる。

範囲:

- **S1: そのまま移せる11件だけ**
- **S2: そのまま移せる11件と既にある10件**
- **S3: S2 に、宣言を足せば移せる17件を加える**(17件は宣言の置き場と構文を決めてから)
- **S4: 移せない物も近似して全件**

## 決定

### 決定1 — shidzuku-lint を作る

**T3 を採る。** shidzuku-lint を、Shidzuku の考え方を既存の言語へ届ける lint として作る。

- 目的は二つある。(1) Shidzuku が届かない既存のコードに、考え方だけを先に届ける(第0章 0.8 の漸進的な導入の手前の足場)。
  (2) **既存の言語に当てる事を、仕様の検証の手段にする**。思考実験(既存のシステムを Shidzuku で書く)が仕様を系の側から試すのに対し、
  lint は仕様を**既存の言語の側から**試す。
- **shidzuku-lang と shidzuku-lint は分けて考える。** ADR 0008・0013 が「警告は無視できる」として lint を退けたのは、
  言語を自分で決められる shidzuku-lang の判断である。言語で拒否できる物を lint に留める理由が無い、という判断であり、shidzuku-lang の中では変わらない。
- shidzuku-lint は、言語を変えられない既存の言語を対象にする。そこでは lint が届く唯一の手段であり、ADR 0008・0013 の判断は前提を共有しない。
  したがって shidzuku-lint の設計——警告に置くか拒否に置くか、抑止を許すか——は、ADR 0008・0013 に縛られず、本 ADR と後続の ADR で決める。
- 二つを混ぜない事は、双方向に効く。shidzuku-lint で警告に置いた検査を理由に shidzuku-lang の検査を警告へ下げる事はしないし、
  shidzuku-lang でエラーだからといって、既存の言語の上でも常に拒否に置くとは限らない(決定4 の深刻度は、その上での shidzuku-lint の選択である)。

### 決定2 — 時期: Phase 1 の言語実装から、継続して改良する

- **Phase 1 の言語実装(パーサ+検証器+トランスパイラ)と並行して着手する。** Phase 0 の間は作らない(計画書 第9節の「仕様だけを先行させない」の逆側——道具だけを先行させない)。
- Phase 1 で終えず、**Phase 2 以降も継続して改良する**。仕様が変われば lint も変わり、lint で見つけた穴は仕様に戻す(決定6)。
- 検証器と**規則の一覧を共有する**。思考実験 26 の L-24(`pure` の層で禁じる IO の一覧)は、Phase 1 の「何を副作用とみなすか」(第3章 3.5)の下書きになる。

### 決定3 — 範囲: S3 を採り、宣言を足す17件は要検討とする

- **そのまま移せる11件**: 作る。
- **既にある10件**: 作る(決定4 の形で)。
- **宣言を足せば移せる17件**: **要検討**。宣言の置き場と構文を決めてから、件ごとに着手を決める。
- **移せない9群**: 作らない。

17件と9群の扱いの理由は次の通りである。

- 17件は、記述者が注釈を足す事を前提にする。注釈の置き場(思考実験 26 第3節の D-1 設定ファイル・D-2 言語の属性・D-3 文書コメント)と、
  注釈の構文(Shidzuku の語彙と構文をそのまま使うか)が決まるまで、作り方が定まらない。
- 置き場と構文は、Phase 1 のパーサと重なる(D-3 で Shidzuku の構文を使うなら、宣言を読む部分はパーサの部分集合になる)。
  そのため U14(プログラムの宣言)の決定を待って検討する。検討の結果は別の ADR に記録する。
- 移せない9群は、動作環境が担う物とプロセスを跨ぐ記述である。lint で近似すると、Shidzuku が一本の記述で貫こうとしている所を、
  届かない道具で真似る事になる。

### 決定4 — 既にある10件は再実装せず、既存の lint を束ねる

- clippy・typescript-eslint 等が既に持つ検査は、shidzuku-lint の中で作り直さない。**既存の lint の設定として束ね**、Shidzuku の検査との対応を示す。
- 深刻度は、shidzuku-lint の選択として shidzuku-lang に合わせる。shidzuku-lang でエラーの検査に当たるもの(L-3 の `confusable_idents` 等)は、
  既存の lint が警告に置いていても拒否に上げる。拒否にした規則も、理由を書けば抑止できる(次項)。
- 抑止には理由を必須にする(L-9)。無視はできても、黙って無視する事はできなくする。これは ADR 0003 の `rejected option … reason …` と同じ形である。

### 決定5 — 対象の言語: Rust と TypeScript から始め、Hike を三つ目として検討する

- **Rust と TypeScript から始める。** ADR 0012 の出力先と揃え、Phase 1 のトランスパイラが出す言語と同じ言語で lint も試す。
- 外への要求(L-4)や IO(L-24)を見分ける API の一覧は、言語とライブラリごとに持つ。
- **Hike(`hike-lang`、<https://github.com/kanryu/hike-lang>)を三つ目の言語として検討する。** suzukimitsuru の指示により、shidzuku-lint の対象としてだけでなく、shidzuku-lang のトランスパイル先としても検討した。
  材料は思考実験 24 である(Go に似た構文の、GC の無いシステム言語。LLVM IR と WebAssembly の WAT へ出力する)。

#### Hike を shidzuku-lint の対象にするか

- **そのまま移せる11件**: 多くは当たる。期限(L-4)・待ち行列の上限(L-5)・壁時計(L-18)は API の一覧で見る形のまま移る。Hike の API の一覧を持てばよい。
- **既にある10件**: **当たらない**。clippy・typescript-eslint に当たる既存の lint が Hike には無く、決定4(束ねる)が使えない。自前で作る事になる。
- **宣言を足せば移せる17件**: Hike は `threadable`・`concurrent` で状態の性質を宣言の側で言う(思考実験 24 の H-1)。L-33(状態の宣言)の置き場の先例になる。
- **構文を読む入口**: Hike は識別子の目録を JSON で出す(思考実験 24 の H-10)。構文木を自分で持たなくても、公開面(L-30・L-32)は目録から読める余地がある。

結論: **対象に加える。ただし Rust と TypeScript で規則の形が固まってから**とする。既にある10件を自前で作る費用が掛かるため、
Hike では「そのまま移せる11件」から始め、既存の lint を持たない言語で shidzuku-lint が単独で立てるかを試す言語と位置づける。
Rust・TypeScript が「束ねる」を試すのに対し、Hike は「束ねる物が無い」場合を試す。

#### Hike を shidzuku-lang のトランスパイル先にするか

- トランスパイル先は ADR 0012 が決める。決定6 で Rust と TypeScript の2言語とし、3言語目以降は決定7 で
  「接合面 H1〜H8 の穴を探す目的」で、凍結と混在の適合試験の後に足すと定めている。順の表(Python・C・Swift / Kotlin・Go / Java・Elixir)に Hike は無い。
- Hike が接合面について試せる物は、**GC を持たない言語での data の写像と、接合面を跨ぐ値の寿命**である。Hike は寿命を `area`・region・参照計数と写し書きで扱い(思考実験 24 の H-14)、
  Rust の所有とも TypeScript の GC とも違う。表の他の候補(C は GC を持たないが寿命の模型を持たない)とも試す物が重ならない。
  加えて、WAT への出力は、コンポーネントを WebAssembly として置く配置を試す入口になる。
- 一方で、Hike は動作環境(常駐する監督)を持たない事を目的の一つにしている(思考実験 24 の H-13)。Shidzuku の動作環境の下に置いた時に、
  Hike の実行時の支援と動作環境の責務が重なるかは、Elixir(決定7 の順7)と同じ種類の問いになる。
- 結論: **ADR 0012 決定7 の候補に Hike を加える事を提案とする。** 本 ADR ではトランスパイル先を変えない。
  加えるかと順序は、ADR 0012 の改訂として、接合面の凍結(Phase 1)の後に判断する。計画書 第4節 4.5 の「Phase 1 の中で決める物」に置く。

- 他の言語も同じ扱いとする。足す時は本 ADR を改訂せず、判定の表(思考実験 26)に言語の列を足す。

### 決定6 — 検査を定める ADR は、既存の言語に移せるかを併せて考える

suzukimitsuru が採用を確かめた(2026-09-28)。

- 以後、Shidzuku に検査(E・W)を足す ADR は、その検査が既存の言語に移せるかを、思考実験 26 の4つの判定のどれに当たるかで一行添える。
- 判定が「そのまま移せる」「既にある」なら、shidzuku-lint の規則に加える。
- 逆に、lint にする中で仕様の穴が見つかったら、思考実験か ADR に戻す(思考実験 26 の論点2・3・5 と同じ扱い)。
- これが決定1 の目的(2)——仕様と lint を共に考える——の具体である。

### 仕様書への反映

- **決定1・決定2**: 第0章 0.8 の実現戦略に、既存の言語へは lint で先に届ける事を足す。
- **決定2・決定3**: 計画書 第1節 Phase 1 と、第4節 4.5 の「Phase 1 の中で決める物」。
- **決定5**: 計画書 第4節 4.5 の「Phase 1 の中で決める物」(Hike をトランスパイル先の候補に加えるか)。
- **決定6**: 計画書 第9節 進め方の原則。

## 捨てたもの・理由

- **T1(作らない)**: 思考実験 26 だけで仕様の穴が3つ見つかった。既存の言語に当てる事が検証の手段として働く事は既に示されており、
  一度きりの思考実験に留めると、仕様が育つたびに同じ突き合わせをやり直す事になる。
- **T2(Phase 0 のうちに作る)**: 仕様の裏付けを得る前に道具を作る事になる。「そのまま移せる」11件は構文に依らないが、
  検証器と規則の一覧を共有する(決定2)には Phase 1 の検証器が要る。別々に作ると、同じ一覧が二か所に生まれる。
- **S1(11件だけ)**: 既にある10件を外すと、Shidzuku の考え方のうち既存の lint が既に持つ部分が、shidzuku-lint の外に散る。
  束ねるだけなら費用は小さく、深刻度を揃える(決定4)事に意味がある。
- **S4(移せない物も近似する)**: 決定3 の理由による。
- **既にある10件を再実装する案**: 同じ検査が二つの道具に生まれ、どちらが正かが分からなくなる。既存の lint が Shidzuku と基準の違う所だけを補えばよい。

## 将来の変更想定

- **宣言を足す17件の検討**(決定3)。U14 の決定を受けて、宣言の置き場と構文を決める ADR を起こす。
  17件のうち、どれから着手するかもそこで決める。層の強度と役割(L-23〜L-28)と、意図の構造(L-36〜L-38)が既存の道具に無く、価値が高い。
- **規則の番号の振り方**(思考実験 26 第4節 4.3)。第3章 3.3 の番号を流用するか、lint 固有の番号を置くか。lint 固有の規則(L-4・L-5・L-9)には元の番号が無い。
  Phase 1 で最初の規則を作る時に決める。
- **置き場所と実装の言語**。リポジトリのどこに置くか、何で書くかは、Phase 1 の着手時に決める。検証器と一覧を共有する(決定2)ため、同じ言語が第一候補になる。
- **思考実験 26 の論点2・3・5** は Shidzuku 側の課題として残っている(計画書 第4節 4.5、第3章 3.5、U12)。
  それらが決まると、対応する lint の規則(L-7・L-9・L-4)も揃える。
- **移せない物のうち、道具が変われば届く物**。接続の両端の型の一致はスキーマの差分の道具で、システムの入れ子は構成図の道具で届く余地がある。
  lint の外の道具との連携は、決定3 の範囲外として、必要が出てから考える。

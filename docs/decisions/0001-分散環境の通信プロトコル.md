# 0001: 分散環境の通信プロトコル

- 日付: 2026-08-18
- 状態: 提案
- 関連課題: U6(※本 ADR はデータ通信プロトコルの選定のみを扱う。「Raft の適用範囲(何を合意対象にするか)」自体は未解決のまま)

## 背景(なぜ決める必要があるか)

分散合意は Raft を用いるが、分散環境でのデータ通信プロトコルを決めていない。
分散環境では通信がボトルネックになるため、軽量で高速な通信プロトコルが必要になる。

## 検討した選択肢

エッジ(組み込み/IoT)からクラウドまでカバーする、効率の良い通信プロトコルを探した。候補は以下。

- **MQTT**: ブローカー経由のシンプルな Pub/Sub。省リソース環境に強いが、クエリ・ストレージ機能は標準にない。
- **DDS**(CycloneDDS / FastDDS 等): ブローカー不要の P2P、豊富な QoS 設定。ROS2 標準で実績があるが、ディスカバリ処理の負荷が大きい。
- **gRPC**: HTTP/2 ベースの RPC。同期的な呼び出しには強いが、Pub/Sub は標準機能でなく、分散データ配信には別途設計が要る。
- **Zenoh**: Pub/Sub・Query・Storage・Compute を1つのプロトコルで統合。マイクロコントローラからデータセンターまでを同一プロトコルでカバーできる。
  - Ethernet では CycloneDDS が優位という報告がある一方、Wi-Fi/4G では Zenoh がより低遅延・高スループットという報告がある([Comparison of DDS, MQTT, and Zenoh in Edge-to-Edge/Cloud Communication with ROS 2](https://arxiv.org/abs/2309.07496v1))。

## 決定

分散合意が必要な箇所は Raft を用い、データ通信には Zenoh を用いる。

## 捨てたもの・理由

- **MQTT**: ブローカーが単一障害点になりやすく、クエリ・ストレージまでを標準でカバーしないため見送り。
- **DDS**: ROS2 等での実績はあるが、ディスカバリのオーバーヘッドが大きく、非力な組み込み機器までを一貫してカバーする用途には重い。
- **gRPC**: Pub/Sub が標準機能ではなく、分散データ配信のために追加設計が必要になるため見送り。

## 将来の変更想定

- 分散環境に特化した効率の良い通信プロトコルが他にあれば移行を考える。
- Phase 2 で U6(Raft の適用範囲)を確定させる際に、本決定(Zenoh の採用可否)も合わせて再検証し、状態を「採用」に更新するか判断する。

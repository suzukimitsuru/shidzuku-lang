# 0005: 内部階層の制約宣言

- 日付: 2026-08-19
- 状態: 提案
- 関連課題: U3

## 背景(なぜ決める必要があるか)

単位の内側は原則自由だが、内部に階層を設け、階層ごとに制約強度を宣言できる(第0章 0.4)。
その「階層の種類は固定か、自由定義か」が未定である(U3)。

思考実験から次の入力を得た。

- 思考実験 01(OrderStore): domain(純粋)/ driver(IO 可)の2階層が自然に書けた。
- 思考実験 02(Aggregator): 同じ2種で足りた。現在時刻のような環境依存値は driver 層から注入する事で、計算の層を純粋に保てた。

## 検討した選択肢

- **完全固定**: 階層の名前も種類も言語が決める(例: 境界層は純粋/中核層は自由)。
- **完全自由**: 階層の名前も制約強度も利用者が定義する。
- **折衷**: 階層の名前と数は自由、制約強度は言語が定めた固定の種類から選ぶ。

## 決定

**名前は自由、制約強度は固定2種**の折衷とする。

- 単位の body 内に階層を任意個宣言できる。階層の名前は利用者が付ける(domain / driver、app / infra など、単位の文脈に合った名前)。
- 各階層は制約強度を次の2種から選ぶ。

| 強度 | 意味                                                  |
| ---- | ----------------------------------------------------- |
| pure | 純粋。IO 不可・外部状態への依存不可。決定的な計算のみ |
| io   | 自由。IO・可変状態を許す(単位の内側の原則通り)        |

- 依存の方向: pure 層は io 層に依存できない。環境依存値(現在時刻・乱数・設定)は io 層が取得し、値として pure 層へ注入する(思考実験 02 の Aggregator が実例)。
- 階層の宣言は必須である。当初は「宣言しない単位は body 全体を io とみなす」としていたが、
  既定規則という外部知識を読み手に要求するため、ADR 0008 で省略を禁止に改訂した。

## 捨てたもの・理由

- **完全固定(名前まで言語が決める)**: 自然な層の名前は単位の文脈で異なる(永続化単位なら domain/driver、集約単位なら計算/時計)。名前は意図の一部であり、言語が奪わない。
- **完全自由(強度も利用者定義)**: 検証器は任意の強度を検証できず、宣言が実質コメントになる。強度が単位ごとに乱立すると、単位を跨いだ読解(この層は信用できるか)が壊れる。2つの思考実験で2種を超える必要は現れなかった。
- **強度3種以上(例: 読み取り専用 IO)**: 必要が現れていない。思考実験で pure / io の2種で表せない例が出たら追加を検討する(「将来の変更想定」参照)。

## 将来の変更想定

- 思考実験・Phase 1 の実装で2種で表せない例(読み取り専用 IO、ログのみ許可等)が出たら、強度の追加を検討する。
- pure の検証範囲(トランスパイル先言語でどこまで純粋性を機械検証できるか)は U5(トランスパイル先)の決定後、Phase 1 で具体化する。
- 階層と intent の関係(階層ごとに intent を書かせるか)は現時点で不要と判断。単位の intent で足りない例が出たら再検討する。

# 0023: 対になる通信の相関 — 二本を結ぶ鍵を宣言する

- 日付: 2026-09-26
- 状態: 提案
- 関連課題: U25(対になる通信)。関連: U13(失敗の体系)・U11(メッセージの順序保証)・U12(外部世界との境界)・U14(プログラムの宣言)
- 改訂する決定: 無し。第4章 4.2 の `flow` 宣言に欄を足す

## 背景(なぜ決める必要があるか)

一つの仕事が、複数の通信に分かれる事がある。

```plaintext
Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
```

受注番号は期限内に返し、確定は決済代行の応答を待って後から流す。
**二本は一つの仕事だが、それを言語は知らない。**

思考実験 20(対になる通信)と思考実験 21(補償と巻き戻し)で、次が分かった。

### 1. 鍵が同じ物である事を、誰も確かめていない

`受注の状態` は `確定(受注番号) | 取消(受注番号, 取消の理由)` であり、`受注番号` を持つ。
しかしその `受注番号` が `ask 受注` の応答と同じ値である事は、**どこにも宣言されておらず検査もされない**。
言語が見るのは接続の両端の型の一致(E0009-1)だけである。

### 2. どの `ask` への戻りかが決まらない

`注文管理` は `受注`・`取消`・`受注の照会` の三つの `ask` を受ける(思考実験 20 の論点2)。
後から届く `受注の状態` は、このうちどれの続きなのか。記述の上では区別が無い。
受け取った側は自分の待ち表を引くしかなく、**照合は body の中に沈む**。

### 3. 鍵は仕事に一つではない

思考実験 21 で、同じ仕事に二つの鍵が要る事が分かった。

| 結ぶ相手                                     | 鍵         | 見える範囲             |
| -------------------------------------------- | ---------- | ---------------------- |
| `ask 受注` の応答と、後から届く `受注の状態` | `受注番号` | 公開面に出る           |
| `ask 引当` の応答と、後から走る `引当の解放` | `引当番号` | システムの内側で閉じる |

「仕事に一つの鍵を書く」形では足りない(思考実験 21 の論点5)。
**結ぶのは仕事ではなく、接続の対である。**

### 4. 書ける材料は既にある

`flow` 宣言は既に「接続と障害時の振る舞い」を持つ単位であり、複数の接続を並べて書ける。
順序は並びが、理由は intent が、障害時の埋め合わせは `on failure` が引き受けている。
**足りないのは単位ではなく検査である**(思考実験 21 の示唆)。

## 検討した選択肢

### 論点1: 相関を言語が見るか

- **D-1: 見ない。** 鍵はデータで表し、対である事は `flow` 宣言の並びと intent に委ねる。
- **D-2: `flow` 宣言に書く。** 接続の属性として鍵を宣言し、型の整合を検査する。
- **D-3: 公開面に書く。** `expose 受注(注文) -> 受注番号 | 受注不可 then 受注の状態` のように、担い手の側に「後から返る物」を書く。

### 論点2: どこに書くか

- **P-1: `flow` 宣言の全体に一つ。** 仕事に一つの鍵を置く。
- **P-2: 接続の対ごと。** 一つの `flow` 宣言に複数の相関を書ける。

### 論点3: 鍵をどう指すか

- **K-1: 型で指す。** `受注番号` と書き、その型が両端に現れる事を検査する。
- **K-2: 欄の経路で指す。** `受注の状態.受注番号` のように、型の内部の位置を書く。

### 論点4: 省略の禁止をどう適用するか

- **O-1: 任意。** 書きたい人だけ書く。
- **O-2: 接続が2本以上ある `flow` 宣言で必須。** 結ぶ対が無ければ `correlate none` と書く。
- **O-3: 常に必須。** 接続が1本の `flow` 宣言にも `correlate none` を要求する。

### 論点5: 何本を結べるか

- **N-1: ちょうど2本。**
- **N-2: 2本以上。** 一つの鍵で三本以上を結べる。

### 論点6: 仕事の期限を含めるか

「確定が何分以内に決まるか」を書く欄(`within` に当たるもの)を、本 ADR で決めるか。

## 決定

### 1. `correlate` を `flow` 宣言に足す(論点1: D-2)

```plaintext
flow 受注の受付と確定 {
  intent { ... }
  Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
  注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  correlate 受注番号 : 受注 -> 受注の状態
  on failure 注文管理  : ...
  on failure Frontdesk : ...
}
```

- 読み方は「**受注番号 で結ぶ: 受注 の後に 受注の状態**」である。
- `ask` の応答を後から返す形(D-3)は採らない。`ask` は期限内に必ず返ると定めており(ADR 0004、第4章 4.1)、
  後から返る形は三つ目の通信方式の新設に当たる(ADR 0018「捨てたもの・理由」、思考実験 20)。

### 2. 相関は**接続の対ごと**に書く(論点2: P-2)

一つの `flow` 宣言に `correlate` を何行でも書ける。

```plaintext
  correlate 受注番号 : 受注 -> 受注の状態
  correlate 引当番号 : 引当 -> 引当の解放
```

- 鍵は仕事に一つではない(背景3)。公開面に出る鍵と、システムの内側で閉じる鍵が同居する。
- 同じ接続が複数の相関に現れてよい。連なる仕事では自然に起きる。

### 3. 接続の指し方は、`ask` は公開面名、`flow` は内容の型名(論点3 の前提)

| 接続の形                               | `correlate` での指し方 |
| -------------------------------------- | ---------------------- |
| `... : ask 受注(注文) deadline … -> …` | `受注`(公開面名)       |
| `... : flow 受注の状態 pressure … (…)` | `受注の状態`(内容の型) |

- どちらも**その行に書かれている名前**であり、新しい名前を導入しない。
- 同じ名前の接続が一つの `flow` 宣言に二本あると一意に決まらない。これは E0023-3 とする。

### 4. 鍵は**型**で指す(論点3: K-1)

`correlate` に書くのは型の名前である。欄の経路(`受注の状態.受注番号`)は書かない。

- Shidzuku は**名前的型付け**である(第6章 6.1)。`受注番号` という型は一つしかなく、
  型の中のどこに現れるかは検査器が辿れる。書き手が位置を書く必要が無い。
- 直和の区分をまたぐ形(`確定(受注番号) | 取消(受注番号, 取消の理由)`)では、経路が区分ごとに違う。
  **型で指せば「どの区分を通っても鍵は同じ型である」事が一度で言える。**
- 鍵の型が現れているかの検査は、型の入れ子(直積の欄・直和の区分の引数・`list` の要素)を辿る。
  E0019-1(論理型の外出し)が入れ子を辿るのと同じ扱いである。

### 5. 接続が2本以上ある `flow` 宣言では必須(論点4: O-2)

- 接続が2本以上あるなら、その宣言は「複数の通信が一つの仕事である」と言っている。
  **その通信どうしの関係を書かせるのが、省略の禁止(ADR 0008)の適用である。**
- 結ぶ対が無い場合は `correlate none` と明示する。逐次に進むだけの仕事(引当 → 保存)はこれに当たる。
- 接続が1本の `flow` 宣言には要求しない(論点4: O-3 を採らない)。結ぶ相手が存在し得ないためである。
- 欠落は E0008-1(必須宣言の欠落)とする。**本 ADR は新しい「書き忘れ」の番号を作らない。**

### 6. 一つの鍵で三本以上を結べる(論点5: N-2)

```plaintext
  correlate 受注番号 : 受注 -> 決済の結果 -> 受注の状態
```

- 連なる仕事(受注 → 決済 → 通知)は、同じ鍵で辿れる一本の道である。対に割ると道が読めなくなる。
- 並びは**時間の順**であり、`flow` 宣言の接続の並びと矛盾してはならない(E0023-4)。

### 7. 相関のある通信は、同じ `flow` 宣言に置く

`correlate` が指せるのは、**その `flow` 宣言の中にある接続だけ**である。宣言を跨いで結ぶ事はできない。

- `flow` 宣言は「一つの仕事」の単位であり(第4章 4.2 の intent が必須である理由)、
  鍵で結ばれる通信は同じ仕事である。跨いで結べるようにすると、仕事の単位が記述から消える。
- 跨ぐ必要が出た時に何が要るかは、名前空間(U14)が決まってからでなければ形にできない。
  接続を宣言の外から一意に指す名前が無いためである。
- **この決定は、書き手のフローの切り方に影響する**(「結果」の欠点を見よ)。

### 8. 仕事の期限は本 ADR で決めない(論点6)

「確定が何分以内に決まるか」を書く欄(`within` に当たるもの)は**入れない**。
思考実験 20 の論点5 は U13(失敗の体系)へ送った(計画書 第7節 7.5)。

- 期限を過ぎた事をどう扱うかは、**何を失敗と呼ぶか**の問いである。
  ドメインの失敗(在庫なし)とも、系の失敗(期限超過・障害)とも違う三つ目に見える。
- 欄の形だけを先に決めると、U13 の ADR が本 ADR を改訂する事になる(ADR 0018 が名前空間に踏み込まなかったのと同じ理由)。

### 9. `on failure` の欄の形も、本 ADR で決めない

思考実験 21 の論点1・2(同じ補償が、業務上は接続・障害時は散文になる)への案 S-a
(`on failure` に接続を書けるようにする)は、第4章 4.6 の未定事項のままとする。

- あれは**補償の記述**の問題であり、相関の問題ではない。
- 決めるなら U13(失敗の体系)と併せてであり、そこで `on failure` の欄を作り直す方が筋が通る。

### 10. 検証

| #       | 検査                                                                       | 段     |
| ------- | -------------------------------------------------------------------------- | ------ |
| E0023-1 | `correlate` が指す接続が、その `flow` 宣言に無い                           | フロー |
| E0023-2 | 鍵の型が、指した接続のいずれかに現れない(型の入れ子を辿る)                 | フロー |
| E0023-3 | `correlate` が指す接続が一意に決まらない(同名の接続が2本ある)              | フロー |
| E0023-4 | `correlate` の並びが、`flow` 宣言の接続の並びと前後している                | フロー |
| W0023-1 | `correlate none` と書いたが、同じ相手との `ask` と後から届く `flow` がある | フロー |

- 接続が2本以上あるのに `correlate` が無い場合は **E0008-1**(既存)とする(決定5)。
- W0023-1 を警告に留めるのは、**結ばない事が正しい場合があるため**である。
  同じ相手と二つの無関係な仕事をしている記述は書ける。エラーにすると、それを書く道が閉じる。

- 書き換える: 第4章 4.2(`flow` 宣言の構文と欄)・4.6(未定事項から相関を外す)、第3章 3.3(検証の一覧)、
  第5章 5.3(語彙に `correlate` を足す)、`docs/PLAN.md`、`README.md`、`docs/roadmap.html`。
- 書き換えない: 本 ADR より前の ADR と思考実験(ADR 0014・0015 決定8 と同じ)。
- 思考実験 01〜04 の `flow` 宣言は接続が2本以上あるため、**採用時に `correlate` が必要になる**。
  ただし本文は改訂しない。書かれた時点の語で読めなければならないためである。

## 机上検証 — 思考実験 20 と 21 を書き直す

### 検証1: 受注の受付と確定(思考実験 20)

```plaintext
flow 受注の受付と確定 {
  intent { ... }
  Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
  注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  correlate 受注番号 : 受注 -> 受注の状態
  on failure 注文管理  : Frontdesk は受注不可を返す(伝播しない)
  on failure Frontdesk : 再起動する。待ちの対応は失われ、客は受注の照会で引き直す
}
```

- 思考実験 20 の論点1(鍵が見えない)は閉じた。`受注番号` が両端に現れる事を E0023-2 が見る。
- 論点2(どの `ask` への戻りか)も閉じた。`受注` を名指しているため、`取消`・`受注の照会` の戻りではないと読める。

### 検証2: 引当と解放(思考実験 21)— フローの切り方が変わった

思考実験 21 は、引当を `flow 受注の受付` に、解放を `flow 受注の確定と取消` に分けて書いていた。
決定7(相関は同じ宣言の中)により、**この切り方では `引当番号` の相関を書けない**。

```plaintext
flow 受注の一生 {
  intent {
    why      "引当・保存・決済の結果・解放・通知を、受注番号と引当番号で辿れる一つの仕事として書く"
    rejected option "受付と確定を別のフローに分ける"
             reason "引当と解放が別の宣言に落ち、在庫を戻す道が記述の上で切れる"
    change   "配送枠の引当が増える事を想定。接続と相関が1行ずつ増える形で吸収する"
  }
  OrderIntake   -> Inventory  : ask 引当(品目ID, 数量) deadline 100 ミリ秒 -> 引当の結果
  OrderIntake   -> OrderStore : ask 保存(注文, 引当番号) deadline 200 ミリ秒 -> 保存の結果
  PaymentBridge -> OrderStore : flow 決済の結果 pressure block(deadline 1 秒) (durable)
  OrderStore    -> Inventory  : ask 引当の解放(引当番号) deadline 100 ミリ秒 -> 解放の結果
  OrderStore    -> Frontdesk  : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  correlate 引当番号 : 引当 -> 保存 -> 引当の解放
  correlate 受注番号 : 保存 -> 決済の結果 -> 受注の状態
  on failure ...
}
```

**発見1: 相関は、フローの切り方を決める。** 鍵で結ばれる通信は同じ宣言に居なければならないため、
「受付」と「確定」を別の仕事として切ると、在庫を戻す道が記述の上で切れる。
これは費用ではなく**効き目**である——切り方が業務の一貫性に従うよう、言語が押す。

**発見2: 一つの仕事に二つの鍵が並ぶ形は、素直に読める。** 内側の鍵(`引当番号`)と外向きの鍵(`受注番号`)が
それぞれ1行であり、どの通信がどの鍵で辿れるかが一望できる。背景3 の問題は閉じた。

**発見3: 三本以上を結ぶ形(決定6)は、この例で必要になった。** 引当 → 保存 → 解放は対ではなく道である。
対に割ると `引当 -> 保存` と `保存 -> 引当の解放` の2行になり、同じ鍵が二度書かれて道が読めない。

### 検証3: 結ばない仕事(思考実験 01)

```plaintext
flow 受注処理 {
  intent { ... }
  OrderIntake -> Inventory  : ask 引当(品目, 数量) deadline 100 ミリ秒 -> 引当の結果
  OrderIntake -> OrderStore : ask 保存(注文) deadline 200 ミリ秒 -> 保存の結果
  correlate none
  on failure Inventory  : ...
  on failure OrderStore : ...
}
```

逐次に進むだけで、後から戻る通信が無い仕事である。`correlate none` の1行が増える。
**これが決定5 の代価であり、省略の禁止が一貫して働いている形でもある**——
「結ぶ物は無い」が宣言になり、読み手は相関を探しに body へ行かなくてよい。

## 捨てたもの・理由

- **D-1(何も足さない)**: 検証できる物を散文と body に残す。鍵が同じ型である事は静的に確かめられるのに、
  確かめないままにする理由が無い。思考実験 20 の論点1・2 が閉じない。
- **D-3(公開面に `then` で書く)**: ADR 0004(通信は ask と flow の2方式)の改訂になる。
  `ask` の「必ず期限内に返る」が同じ宣言の中で割れ、再送の宛先が呼び出しではなくコンポーネントである以上、
  受け取り口は結局 `expose ... flow in` になる。消えるのは `depends` と `flow` 宣言の記述だけである(思考実験 20 の §5)。
- **P-1(フロー全体に一つの鍵)**: 思考実験 21 の論点5 で足りない事が分かった。公開面に出る鍵と内側の鍵が同居する。
- **K-2(欄の経路で指す)**: 経路は型の内部構造に依存する。直和の区分ごとに経路が違う形では書けず、
  型の欄名を変えるだけで相関の宣言が壊れる。名前的型付けを持つ言語が経路を要求する理由が無い。
- **O-1(任意)**: 書いた人の記述だけが検査される。省略の禁止(ADR 0008)は「選択のある宣言に既定を置かない」であり、
  相関の有無は選択である。
- **O-3(常に必須)**: 接続が1本の `flow` 宣言にまで `correlate none` を課す。結ぶ相手が存在し得ない所に宣言を強いるのは、
  省略の禁止ではなく単なる重さである。
- **N-1(ちょうど2本)**: 連なる仕事が対に割れ、同じ鍵が何度も書かれる(検証2 の発見3)。
- **実行系が相関 ID を自動で発行する案**: 記述に現れない物が仕事を結ぶ事になる。
  どの値で結ばれているかが読めず、body が自分の鍵(受注番号)で照合する自由も奪う。
  **言語が見るのは書き手の宣言だけである**という立場(ADR 0018 決定10 と同じ)に反する。
- **`within`(仕事の期限)を本 ADR に含める**: 決定8 の通り U13 へ送った。
- **`flow` 宣言を跨いで結ぶ**: 接続を宣言の外から一意に指す名前が無い(決定7)。U14 の後でなければ決められない。

## 結果(利点と欠点)

### 利点

- **二本が一つの仕事である事が、検査される宣言になる**。鍵の型が両端に現れない記述は通らない(E0023-2)。
- **どの `ask` への戻りかが記述から決まる**。同じ相手に複数の `ask` があっても曖昧にならない(背景2)。
- **鍵が二つ以上ある仕事を書ける**。公開面の鍵と内側の鍵が並ぶ(背景3、検証2)。
- **相関がフローの切り方を押す**。在庫を戻す道が別の宣言に落ちる形を、書き手が気付ける(検証2 の発見1)。
- **新しい単位を作っていない**。`flow` 宣言に欄が1つ増えるだけであり、サーガの語彙も実行系の相関管理も持ち込まない。
- **`ask`・`flow` の2方式(ADR 0004)を改訂しない**。

### 欠点

- **`correlate none` が増える**。接続が2本以上ある全ての `flow` 宣言に1行要る(検証3)。
- **フローの切り方に制約が乗る**(決定7)。相関のある通信を同じ宣言に置くため、大きな仕事は宣言も大きくなる。
- **既存の思考実験の記述が、採用時に足りなくなる**。01〜04 の `flow` 宣言は `correlate` を持たない(決定11 で本文は改訂しない)。
- **鍵の型を専用に作る必要が出る事がある**。相関に使う値が `uint64(0) unitless` のような汎用の型だと、
  E0023-2 は通るが意味が薄い。識別子型(`data 受注番号 (id)`)で書くのが前提になる。
- **仕事の期限は書けないまま**である(決定8)。確定が来ない待ちは U13 を待つ。

## 将来の変更想定

- **U13(失敗の体系)**: 仕事の期限(`within` に当たる欄)と、`on failure` の欄の形(思考実験 21 の S-a)。
  本 ADR の `correlate` が結んだ道の上で、「どこまで進んで止まったか」を語る語彙になる。
- **U14(プログラムの宣言)**: `flow` 宣言を跨いだ相関(決定7)。接続を外から指す名前が要る。
- **U11(メッセージの順序保証)**: `ask` の応答と `flow` の到着の順序(思考実験 20 の論点3)。
  `correlate` は道を宣言するが、到着の順序は保証しない。
- **U12(外部世界との境界)**: 巻き戻しの引き金が `external` の応答である形(思考実験 21 の論点3)。
  外部がフローの端点に書けるようになれば、`correlate` の道は外部まで伸びる。
- **U8(図と実装の一致)/ Phase 3**: 相関を図に描くか。同じ鍵で結ばれた接続を1本の道として描けるが、
  描き過ぎると図が混む。描く/描かないの判断は抽出器の設計と併せて決める。
- **検証の主体**: E0023-2 は型の入れ子を辿る検査であり、E0019-1 と同じ実装を使える。Phase 1 で確かめる。

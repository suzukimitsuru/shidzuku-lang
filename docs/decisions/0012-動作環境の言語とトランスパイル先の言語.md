## 背景(なぜ決める必要があるか)

Phase 1 のトランスパイラはトランスパイル先の言語を必要とする。しかし U5 は、実際には二つの問いが重なった課題である。

1. **動作環境を何の言語で書くか**(Zenoh・Raft・監督・期限・配達保証を担う実行系)
2. **コンポーネントを何の言語に落とすか**(トランスパイル先)

この二つは独立ではない。**動作環境がどこまでを担うかが決まらないと、トランスパイル先の言語に何を要求するかが決まらない**。
最初の草稿は「言語ごとにバックエンドが実行系まで生成する」という暗黙の前提で書かれており、比較の軸そのものが的を外していた。

本 ADR は次の前提を確定させた上で、二つの問いをまとめて決める。

> **Shidzuku の動作環境は Rust で記述する。コンポーネントはトランスパイル先の言語で記述する。**

| 観点              | 実行系を言語ごとに生成する場合           | 動作環境を1実装にする場合            |
| ----------------- | ---------------------------------------- | ------------------------------------ |
| 実行系            | 言語ごとに1つ(2言語なら2つ)              | Rust の1実装。言語が増えても1つ      |
| 移植層            | 生成器の責務(コード生成の一覧)           | コンポーネントと動作環境の**接合面** |
| 意味の一致        | 複数の実行系が同じ意味で動く事を試験する | 実行系が1つなので意味は初めから1つ   |
| 言語を1つ足す費用 | 実行系をもう1つ書く                      | 接合面に繋ぎ、データの写像を書く     |

つまり U5 の核心は「言語ごとに実行系をどう作るか」ではなく、「**コンポーネントと動作環境をどう接ぐか**」に移る。
「トランスパイル方法が大きく違う言語ほど抽象化しやすい」という着眼は変わらない。ただし、それによって試されるのは生成器ではなく**接合面**である。

第0章 0.4 の四位一体(設計=処理=障害=配置)のうち**配置**だけが言語に触れ、残りの三つは接合面の外側——動作環境の側——になければならない。

## 検討した選択肢

### 論点1: 動作環境の言語

動作環境はノードに常駐し、期限を測り、durable な流れを届け切り、コンポーネントを監督する。**ノードの単一障害点であり、止まってはならない唯一の部分**である。

| 言語          | GC の停止時間            | Zenoh(ADR 0001)  | ライブラリとして配れるか | 組込みへの展開     | 安全性                 |
| ------------- | ------------------------ | ---------------- | ------------------------ | ------------------ | ---------------------- |
| Rust          | GC を持たない            | 本家の実装言語   | crate と C ABI の両方    | クロスコンパイル可 | メモリ安全             |
| C / C++       | GC を持たない            | C バインディング | 可                       | 可                 | メモリ安全でない       |
| Go            | 停止時間が期限に乗る     | 公式の対応が無い | cgo 越しで重い           | 難しい             | メモリ安全(GC 前提)    |
| Erlang / BEAM | 軽いが VM の制約を受ける | 公式の対応が無い | 不可(VM が要る)          | 難しい             | プロセス隔離が強い     |
| Java / JVM    | 停止時間が期限に乗る     | 公式の対応が無い | 不可(VM が要る)          | 不可               | メモリ安全(GC 前提)    |
| Zig           | GC を持たない            | C バインディング | 可                       | 可                 | C より安全だが発展途上 |

### 論点2: 責務の分担

- **案 1 — 言語ごとに実行系を生成する**: トランスパイル先ごとに期限・流量制御・配達保証・監督を実装する。
- **案 2 — 動作環境を1実装とし、コンポーネントだけを言語ごとに出す**: 実行系は Rust の1つ。言語が増えても実行系は増えない。

### 論点3: 接合の方式 — コンポーネントのコードは動作環境とどう繋がるか

| 方式             | 内容                                                               | 障害境界                                       | 言語を足す費用             |
| ---------------- | ------------------------------------------------------------------ | ---------------------------------------------- | -------------------------- |
| 同居(ライブラリ) | コンポーネントのプロセスが動作環境をライブラリとして抱える         | プロセス=コンポーネントで保たれる              | 言語ごとに FFI の橋が要る  |
| 埋め込み(ホスト) | 動作環境のプロセスが言語 VM を抱え、その中でコンポーネントを動かす | 弱い。コンポーネントの暴走が動作環境を巻き込む | VM を埋め込める言語に限る  |
| 並置(サイドカー) | コンポーネントのプロセスがローカルの接合面越しに動作環境と話す     | 強い。プロセスの死がそのまま障害境界           | 接合面を喋れれば何でもよい |
| WASM             | コンポーネントを WASM に落とし、動作環境がホストする               | 中。隔離はあるが IO は借り物                   | WASM に落ちる言語に限る    |

### 論点4: 接合面を流れるもの

- **案 a — 言語の値を動作環境が理解する**: 動作環境が動的な値表現を持ち、各言語の値と相互変換する。
- **案 b — 正準形のバイト列と型の指紋だけを流す**: 動作環境は中身を解釈せず、宛先と指紋と期限だけを見る。

### 論点5: トランスパイル先の言語 — 主要言語の一覧比較

動作環境が実行系を担う(論点2 の案 2)なら、**トランスパイル先の言語に求めるものは大きく減る**。
残るのは次の7点であり、これを軸に主要言語を並べた。

1. **data の写像**(ADR 0009: 直積・直和・識別子型・列、名前的型付け)がどれだけ忠実に書けるか
2. **基本型の写像**(ADR 0013・0019・0021)——8〜256 ビットの整数、`dec` のための多倍長整数、ナノ秒の範囲を持つ `時点`、正準形を持たないテキスト——をどれだけ素直に書けるか
3. **再起動の速さ** — コンポーネントは障害境界であり、let it crash で殺され再起動される。起動が重い言語はこの前提と噛み合わない
4. **配置の形** — 単一バイナリか、処理系と依存木を伴うか
5. **同居の可否** — 動作環境を C ABI 越しにライブラリとして抱えられるか(並置なら不要)
6. **主な領域と利用者の広さ**
7. **接合面のクライアントを書けるか** — ローカルの接合面を喋り、正準形を符号化できるか。**現代の主要言語はいずれも可**であるため、表の軸には入れていない

| 言語            | data の写像(直和・名前的型)                    | 再起動の速さ        | 配置の形             | 同居          | 主な領域と利用者の広さ          | 判定             |
| --------------- | ---------------------------------------------- | ------------------- | -------------------- | ------------- | ------------------------------- | ---------------- |
| Rust            | 直和も名前的型もそのまま写る                   | 速い                | 単一バイナリ         | 同一言語      | エッジから雲・組込み / 中       | **1つ目に採用**  |
| TypeScript      | タグ付き共用体で可。型は構造的で実行時に消える | 中(処理系の起動)    | 処理系 + 依存木      | 可(N-API)     | ブラウザからサーバ・道具 / 最大 | **2つ目に採用**  |
| Python          | 動的。写像は実行時の約束になる                 | 中                  | 処理系 + 依存        | 可(pyo3)      | データ処理・機械学習 / 最大     | 3つ目の最有力    |

基本型の写像(軸2)は別の表に分けた。起案時(2026-08-24)には基本型が確定しておらず、ADR 0021 の採用(2026-09-16)で要求が定まったためである。

軸2 は判定を動かさない。どの言語でも符号化器と溢れの検査を生成すれば写せるためである。
ただし **TypeScript が最も素直に写せない**(`number` と `bigint` の使い分け、UTF-16 の文字列)事は、次に述べる「2つ目は接合面を壊しにかかる言語」という選び方をむしろ裏付ける。
Go(128 ビットが無い)と Java(符号なしが無い)の「後回し」も、この軸で理由が1つずつ増えた。

**最初の2つに求めるもの**は「広く使われている事」ではなく「**接合面を壊しにかかる事**」である。

- 1つ目は**接合の距離がゼロ**の言語。動作環境と同じ言語なら、接合面が「本当に必要な呼び出し」だけかを最短で確かめられる。→ Rust
- 2つ目は**接合の距離が最大で、かつ data の写像が最もよく試される**言語。
  - 距離だけなら Python・Erlang でもよいが、**動的型では写像が素通りしてしまい試験にならない**。
  - 写像だけなら Swift・Kotlin だが、直和も名前的型もネイティブに在るため**そのまま写せてしまい**、これも試験にならない。
  - **TypeScript だけが「型を持つのに構造的で、しかも実行時に消える」**。ADR 0009 の名前的型付けをどう守るかを唯一突きつける。
    加えて単一スレッドのイベントループ、別 VM、GC を持ち、利用者は最大級でブラウザまで届く。
  - 基本型でも同じである。`number` が 53 ビットまでしか整数を表せないため、**同じ `int64` が値の表現を変えても正準形は変わらない事**を試験できる。

## 決定

### 1. 動作環境は Rust で書き、1つの実装とする

- **GC を持たない**。動作環境は期限(第4章 4.1)を測る主体であり、その主体に GC の停止時間が乗る事は許容できない。
- **Zenoh(ADR 0001)の本家の実装言語**である。バインディング越しではなく直接使える。
- **crate としても C ABI のライブラリとしても配れる**ため、並置と同居(決定 5)を一つの実装で提供できる。VM を要する言語ではこれができない。
- **ノードの単一障害点になる部分がメモリ安全である**。壊れない事を求められる数少ない場所であり、C / C++ をここに置く判断は取らない。
- クロスコンパイルでエッジまで持って行ける。

### 2. 責務は動作環境に寄せる(論点2 の案 2)

| 責務                                                    | 動作環境(Rust・1実装) | トランスパイル先の言語 |
| ------------------------------------------------------- | --------------------- | ---------------------- |
| ask の期限(必ず返る)                                    | ●                     |                        |
| flow の流量制御(block / latest / drop)                  | ●                     |                        |
| 配達保証(transient / durable)と再送                     | ●                     |                        |
| idempotent の重複検出                                   | ●                     |                        |
| 障害の監視・再起動(let it crash)                        | ●                     |                        |
| Zenoh の通信(ADR 0001)                                  | ●                     |                        |
| コンポーネント記述子の照合と版の交渉                    | ●                     |                        |
| ログ規約の出力(U4)                                      | ●                     |                        |
| 復元元の再生の提供                                      | ●                     |                        |
| data の写像(直積・直和・識別子型・列)                   |                       | ●                      |
| 基本型の写像(整数・浮動小数点・dec・時間の型・テキスト) |                       | ●                      |
| 正準形への符号化・復号                                  |                       | ●                      |
| 公開面の受け口・出口の骨組み                            |                       | ●                      |
| 内部階層(制約強度と役割)の写像                          |                       | ●                      |
| 状態の再構成(復元元の再生を適用する)                    |                       | ●                      |
| body の中身                                             |                       | ●                      |

この分担から、言語ごとに解こうとしていた問題の大半が消える。

- 期限は動作環境が測る。受け手のコンポーネントが遅くても、送り手には期限内に失敗が返る。**「必ず返る」が言語に依存しなくなる**。
- 流量制御は動作環境のキューで適用する。トランスパイル先の言語ごとにキューを実装する必要は無い。
- **ログの自動出力(第0章 0.6)は、接合面を通る事によって初めて可能になる**。コンポーネントの入出力・状態遷移・障害は全て接合面を通るため、コンポーネントが1行も書かなくても動作環境から出力できる。
- 単調時計の読みも動作環境の内側で完結する(ADR 0019)。期限の判定・再送の間隔は言語の型にならず、接合面にも現れない。

### 3. 接合面(ホスト境界)を言語中立に定める

接合面は8つの呼び出しとする。**この表が移植層の実体であり、3言語目の入口である**。

| #   | 呼び出し                                      | 向き                  | 意味                                                 |
| --- | --------------------------------------------- | --------------------- | ---------------------------------------------------- |
| H1  | 結合(コンポーネント記述子)                    | コンポーネント → 環境 | 起動時に記述子を渡して繋がる。照合は動作環境側       |
| H2  | 要求を送る(相手, 公開面, 正準形, 期限) → 応答 | コンポーネント → 環境 | ask の送信。期限の測定は動作環境                     |
| H3  | 要求を受ける / 応答を返す(正準形)             | 環境 → コンポーネント | ask の受け口への配送と応答の返送                     |
| H4  | 流す(出口, 正準形)                            | コンポーネント → 環境 | flow の送出。pressure は動作環境が適用する           |
| H5  | 流れを受ける / 受領を返す(要求 ID)            | 環境 → コンポーネント | flow の受け口への配送。durable の受領確認を含む      |
| H6  | 記録する(事象)                                | コンポーネント → 環境 | ログ規約に載らない、コンポーネント固有の事象のみ(U4) |
| H7  | 復元元を読む() → 正準形の列                   | コンポーネント → 環境 | recoverable な状態の再構成(第3章 3.2 state)          |
| H8  | 終える(理由) / 死                             | 双方向                | 正常終了と異常終了。プロセスの死も監督が同じに扱う   |

- 8つで足りる事は思考実験 04 で机上確認した(後述)。
- **接合面自体が「狭い公開面」の原則に従う**。動作環境はコンポーネントの中身を知らず、コンポーネントは動作環境の中身を知らない。

### 4. 接合面を流れるのは正準形のバイト列と型の指紋であり、言語の値ではない(論点4 の案 b)

- 動作環境が見るのは宛先・型の指紋・期限・要求 ID だけである。中身は解釈しない。
- 橋の形がどの言語でも同じになり、言語を足すたびに動作環境が太る事がない。
- 代償として符号化・復号は各言語のバックエンドが持つ(決定 8 の G2)。これはどの言語でも必ず要る仕事であり、増えた費用ではない。
- 正準形の仕様は言語中立に定める。durable な flow の永続化物と recoverable の復元元も同じ形式で書き、**別言語の出力が同じ状態を復元できる**ようにする。
- **正準形は Shidzuku の型(幅・位取り・単位)だけで決まり、出力言語の値の表現には依存しない**。
  TypeScript が `int32` を `number` に、`int64` を `bigint` に写しても、同じ値は同じバイト列になる。

### 5. 接合の方式は「並置」を基本とし、Rust に限り「同居」を許す

- **基本(並置)**: ノードに監督の動作環境プロセスを1つ置く。コンポーネントは1つ1プロセスとして起動され、ローカルの接合面越しに動作環境と話す。
  - 障害境界=プロセスであり、**言語に依存せず let it crash が成立する**。
  - durable の永続化と再送、記述子の照合、Zenoh のセッションは**コンポーネントの生死を跨いで生き続ける必要がある**ため、コンポーネントのプロセスの外に置く。
    送り手のコンポーネントが壊れたまま戻らなくても、送り出された durable な流れは動作環境が届け切る。
  - 「コンポーネントを跨ぐ直接呼び出し・共有メモリは存在しない」(第2章 2.1・第4章 4.1)が、同一ノードでも**構造的に**保証される。生成コードの行儀に頼らない。
- **Rust に限る同居**: コンポーネントのプロセスが動作環境を crate として直接抱える形も許す。呼び出しは H1〜H8 と同じで**意味は変わらない**。性能のための選択肢であり、Rust を特別扱いする意味論ではない。
- **埋め込みは採らない**。コンポーネントの暴走が動作環境を巻き込み、障害境界(第0章 0.4)が崩れる。
- **二つの実現手段(ローカル接合面と直接結合)で同じ H1〜H8 が成立する事が、接合面が本物である事の最初の試験になる**。

### 6. トランスパイル先は Rust と TypeScript の2言語

論点5 の通り、**接合の距離がゼロの言語と最大の言語**を取る。両端で同じ接合面が成立すれば、その間にある言語は全て載る。

### 7. 3言語目以降は「接合面の穴を探す目的」で足す

- 足す時期は、接合面 H1〜H8 が凍結され(決定 10)、混在の適合試験が通ってからとする。
- 足す順序と、その言語が試すもの。

| 順  | 言語           | それが試すもの                                                                                         |
| --- | -------------- | ------------------------------------------------------------------------------------------------------ |
| 3   | Python         | 動的型での data の写像の下限。利用者が最大級で、道具の連携が広がる                                     |
| 4   | C              | 接合面の最小性。組込み(zenoh-pico と同じ帯)の機器にコンポーネントを置けるか                            |
| 5   | Swift / Kotlin | 端末側にコンポーネントを置く配置。名前的型と直和がネイティブな言語での写像                             |
| 6   | Go / Java      | 直和の無い言語・起動の重い言語・128 ビット整数や符号なし整数の無い言語という**噛み合わない前提**の限界 |
| 7   | Elixir         | 思想が近い実行系の上で、動作環境が担う責務と重複した時に何が起きるか                                   |

**足せない言語が出た場合は、言語ではなく接合面を疑う**。

### 8. トランスパイル先の言語のバックエンドの責務は6つ

| #   | 責務                                                | Rust                          | TypeScript                                       |
| --- | --------------------------------------------------- | ----------------------------- | ------------------------------------------------ |
| G1  | data と基本型の写像(直積・直和・識別子型・列、下表) | struct / enum / newtype / Vec | interface / タグ付き共用体 / branded type / 配列 |
| G2  | 正準形への符号化・復号                              | 符号化器を生成                | 符号化器を生成(復号時に検査)                     |
| G3  | 公開面の受け口・出口の骨組み                        | 関数と分配                    | 関数と分配                                       |
| G4  | 接合面 H1〜H8 の呼び出し                            | crate を直接呼ぶ              | ソケットの実装(FFI は不要)                       |
| G5  | 内部階層(制約強度 pure / io と役割)の写像           | 副作用を持たない関数へ        | 同左                                             |
| G6  | 起動の骨組み(記述子の同梱・復元・終了)              | main の生成                   | 起点の生成                                       |

G1 のうち基本型の写像(ADR 0013・0019・0021)は次の通りとする。表現の選び方は Phase 1 の実装で変えてよいが、正準形(決定 4)は変えない。

| Shidzuku の型                      | Rust                                             | TypeScript                          |
| ---------------------------------- | ------------------------------------------------ | ----------------------------------- |
| `int8`〜`int32`・`uint8`〜`uint32` | `i8`〜`i32`・`u8`〜`u32`                         | `number`                            |
| `int64`・`uint64`                  | `i64`・`u64`                                     | `bigint`                            |
| `int128`・`uint128`                | `i128`・`u128`                                   | `bigint`                            |
| `int256`・`uint256`                | 256 ビット整数の crate                           | `bigint`                            |
| `float64`                          | `f64`                                            | `number`                            |
| `float32`                          | `f32`                                            | `number`(演算ごとに `Math.fround`)  |
| `dec(i.f)`                         | 多倍長整数の crate                               | `bigint`(小数部倍した整数)          |
| `時点`                             | `i64`(ナノ秒で範囲が一致する)                    | `bigint`(`Date` はミリ秒で足りない) |
| `テキスト`                         | (ロケール, 正規化形, 内容) の組。内容は `String` | 同じ組。内容は `string`             |
| `バイト列`                         | `Vec<u8>`                                        | `Uint8Array`                        |

- 責務の全てが「コンポーネントの中身の写像」に閉じており、実行系の再実装が一つも無い。
- **数値の失敗(第3章 3.3、ADR 0021)は、どちらの言語でも生成コードが検査する**。
  Rust の算術は既定で溢れを検査しない構成があり、TypeScript の `bigint` は幅を持たない。出力言語の既定に預けず、宣言した幅を超えたら失敗を返す。
- **テキストは正準形を持たない**(E0013-1)ため、出力言語の等値比較・ハッシュ・連想配列のキーに写さない。
  TypeScript の `string` の長さと添字は UTF-16 の単位であり、そのまま写すと意味が変わる。構造的操作は役割を宣言した層に閉じる(E0013-2)ため、生成する関数を通す。
- **出力言語が受けない名前は、可逆な符号化で綴り直して対応表を添える**(第5章 5.6)。G1・G3 の生成物の名前に掛かる。
- pure(G5)の純粋性の検査は Shidzuku 側で完結させ、バックエンドには要求しない(第3章 3.5 の未定事項への回答)。検査をトランスパイル先の型システムに預けると、動的型の言語を足せなくなる。
  役割の一方向性(E0013-4)と構造的操作の閉じ込め(E0013-2)も同じく Shidzuku 側で検査する。
- **TypeScript のバックエンドは FFI を必要としない**(G4 はソケットの実装で足りる)。これは「拡張しやすさ」の最初の実証である。

### 9. 互換性の単位はコンポーネント記述子であり、言語は実装の詳細である

- コンポーネントは `名前@バージョン` で識別する。記述子に載るのは、**省略の禁止(ADR 0008)で必須化された宣言そのもの**である。
  公開面の署名と data の正準形の指紋、ask の期限、flow の pressure と配達保証、idempotent、state の種別と復元元。省略の禁止は、記述子を完全にするための前提でもあった。
- 記述子の名前は NFC の UTF-8 のまま持つ(ADR 0014、第5章 5.6)。出力言語の綴り直しは記述子に及ばない。
- **同一バージョンの Rust 出力と TypeScript 出力は相互に置換可能でなければならない**。
  実行系が1つであるため、この試験は「**同じ記述子を出し、接合面で同じ振る舞いをするか**」に還元される。
- 版の混在(別言語・別バージョンのコンポーネントが同時に動く)も、動作環境から見れば**同じ記述子の二つの実体**にすぎない。

| #   | 版の更新が課す制約                                             | 本 ADR の前提での帰結                                        |
| --- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| V1  | 版の混在は異常ではなく正常な状態である(更新の途中は必ず通る)   | Zenoh のキー空間に名前と版を含める。判断は動作環境の1箇所    |
| V2  | 省略の禁止により、暗黙の互換は起こり得ない(既定値が無い)       | 互換は自動では発生しない。変換は明示の宣言としてのみ成立する |
| V3  | 移行は旧版から新版への変換である                               | 置き場所は2案が残る(下記)。接合面は両方を許す形にしておく    |
| V4  | 期限は言語をまたいで同じ意味だが、満たせるかは言語と機器による | **測るのは動作環境**なので保証は1つ。遅い受け手は失敗になる  |

移行の変換の置き場所は、(i) コンポーネント側の pure 層に書く、(ii) 記述子に宣言的な写像として載せ動作環境が実行する、の2案が残る。
**(ii) なら言語が何種類あっても変換は1実装で済む**。表現力が足りるかは U16(コンポーネントのバージョンと移行)で決める。本 ADR は接合面(H1 の記述子)に両方の余地を残すところまでを決める。

### 10. 実装の順序 — Rust が先。ただし接合面の凍結は TypeScript が通ってから

- 動作環境と接合面は Rust で作る(必然)。最初のコンポーネントも Rust とし、同居の最も素直な形で H1〜H8 を通す。
- **ただしこの時点の接合面は仮であり、仕様として凍結しない**。Rust だけで作った接合面には Rust の都合(所有権・Result・非同期の作法)が染み込むが、Rust しか見ていない限りそれに気づけない。
- **TypeScript のコンポーネントが同じ H1〜H8 で通った時点で接合面を凍結する**。これが歯止めである。
- Phase 1 の完了条件は2言語とする。成果物は次の通り。
  - 三層記述を持つコンポーネントを2〜3個接続したプログラムが動く。
  - そのうち少なくとも1コンポーネントを別言語の出力に差し替えても、同じフローが同じ意味で動く(混在の適合試験)。

### 本 ADR が決めない事

- 動作環境の内部設計(監督の構造、Raft の適用範囲、Zenoh の使い方)。U6・Phase 2 で決める。
- ローカル接合面の実装(Unix ドメインソケット・共有メモリ等)と正準形の符号化形式。Phase 1 の実装で決める。
- 名前の可逆な符号化の規則(第5章 5.6)。接合面の凍結(決定 10)と併せて決める。
- 256 ビット整数と多倍長整数に使う Rust の crate の選定。Phase 1 の実装で決める。
- コンパイラ自身の実装言語。トランスパイル先とは別の問題である。

## 机上検証 — 思考実験 04 を新しい分担で写す

思考実験 04(分散 KV ストア)の3コンポーネントを、KVCore は Rust、Persister は TypeScript として配置し、H1〜H8 でたどった。

1. **8つの呼び出しで全て書けた**。`ask 格納` は H2 / H3、`flow 書込記録 durable` は H4 / H5(受領確認付き)、KV 表の復元は H7、Persister の障害は H8 とプロセスの死。
  `on failure` の埋め合わせはフローの宣言から動作環境が実行するため、コンポーネント側の呼び出しは増えなかった。
2. **`pressure block(期限 1s)` の上限を書く場所が仕様に無い**。実装の場所が動作環境に移っても、**動作環境がキューを作る時に上限を必要とする**事は変わらない。
  第4章 4.6 の未定事項「バッファ上限付き block」は「実装で必要が確認されてから」とされているが、この検証で**必要は既に確認された**。
  残るのは上限の書き方であり、実装を待つ理由は無い。→ 第4章への入力(第4章 4.6 に本検証を記した)。
3. **durable の永続化と Persister の追記ログが二重に見える**。動作環境は durable な流れを届け切るために永続化し、Persister はアプリケーションの状態として追記ログを書く。
  層は違う(配送の保証と、隠された永続化方式)が、**同じディスクに2回書く**という実務上の重複は残る。
  → U6(Raft の適用範囲・Phase 2)への入力。コンポーネントが「永続化の知識を隠す」場合に、動作環境の永続化を借りられるかは別の判断になる。
4. **置換可能性の検証が軽い**。Rust 版 Persister と TypeScript 版 Persister は、動作環境から見れば同じ記述子を出す二つの実体である。
  実行系が言語ごとに在れば「二つの実行系が同じ意味で動くか」まで試験する必要があったが、実行系が1つなら試験は接合面での振る舞いの一致に絞れる。

また、「同じコンポーネントを別言語で出す」事は、思考実験 04 の 3.2-2 が挙げた**1つの設計単位:N個の配置単位**の緊張の、もう一つの現れである。
これを配置の記述を言語仕様に含めるか(配置の章を立てるか)の判断への入力とした。
この判断は ADR 0015(採用)が「含めない。動作環境(Container)の設定として Phase 2 で決める」と答えており、本 ADR の分担とも整合する。

## 捨てたもの・理由

### 統合前の草稿で採っていた前提

- **言語ごとに実行系を生成する案(論点2 の案 1)**: 同じ意味を二度実装する事になる。**意味を二箇所に置く事は、静かさ(驚きの排除)にとって最大の危険**である。
  実行系が言語ごとに在ると、期限・流量制御・配達保証の微妙な差が言語による振る舞いの差として現れ、しかもそれは記述からは読めない。
- **「貧しい言語から実装する」という順序**: 実行系まで生成する前提では、何も与えてくれない言語から書く事に意味があった。
  責務が動作環境へ移った今、この順序の根拠は失われる。代わりに「Rust で作り、TypeScript が通るまで凍結しない」(決定 10)を置く。
- **「zenoh-ts はルータの中継を前提とするため TypeScript 出力の配置が制約される」という懸念**: コンポーネントは Zenoh を直接触らないため、この懸念自体が消えた。

### 動作環境の言語として

- **C / C++**: メモリ安全でない。ノードの単一障害点であり、止まってはならない部分に置く判断は取らない。
- **Go**: GC の停止時間が期限の保証に乗る。Zenoh の公式の対応が無く、ライブラリとして配る道も cgo 越しになる。
- **Erlang / BEAM**: 監督と分散はそのまま在るが、Zenoh と Raft の実装が無く、VM を要するためライブラリとしてコンポーネントに同居させられない。組込みへの展開も難しい。
- **Java / JVM**: 起動と GC、そして組込みに載らない事が決定的である。
- **Zig**: GC が無くライブラリとしても配れるが、エコシステムと Zenoh の対応が発展途上である。将来の再検討の対象として残す。

### トランスパイル先の言語として

- **Go**: 直和が無く、interface と型スイッチによる写像になるため data の写像(G1)が濁る。128 ビット整数も無い。cgo の橋も独自スケジューラと衝突しやすい。
- **Java / Kotlin**: sealed で直和は書けるが、**VM の起動が重く let it crash と噛み合わない**。コンポーネントは殺されて再起動される前提の存在である。Java は符号なし整数も持たない。
- **C#**: 直和の表現が弱く、Java と同じく起動の重さを抱える(AOT で緩和はする)。
- **Python / Ruby / PHP**: 動的型のため data の写像が実行時の約束になり、**最初の2つに求める「写像の試験」にならない**。Python は3言語目の最有力として残す。
- **Erlang / Elixir**: 思想は最も近い(第0章 0.9)が、動的型で写像が素通りする上、NIF は壊れると VM ごと落ち障害境界と衝突する。並置方式なら安全に足せるため候補には残す。
- **Swift / C++**: 直和も名前的型も在る(C++ は variant)が、Rust と性質が近く**接合の距離が開かない**。端末や既存資産という配置の要求が出た時に足す。
- **WASM をトランスパイル先の言語として数える案**: WASM は言語ではなく配置の形である。Rust バックエンドの副産物として後から得られる。
- **トランスパイル先を1言語に絞る(当初計画)**: 接合面は2つ目が現れて初めて検証される。ただし本 ADR の分担では2つ目の費用が G1〜G6 に縮んだため、この判断の負担は小さい。

## 将来の変更想定

- **3言語目以降(決定 7 の順序)を足す時に、接合面 H1〜H8 の漏れが出る**。その差分が抽象の答え合わせであり、表の改訂として記録する。
- **組込み(zenoh-pico の帯)には動作環境がそのままでは載らない**。動作環境の縮小版が必要になる時期は Phase 2 の実測で判断する。C をトランスパイル先に足す判断と同時に来る。
- **ローカル接合面の往復の費用**が問題になる配置(厳しい制御周期)が出たら、Rust の同居(決定 5)で回避する。H1〜H8 を保つ限り意味は変わらない。
- **U16(コンポーネントのバージョンと移行)の決定により、記述子と H1 の内容は改訂される**。特に移行の変換の置き場所(決定 9 の (i) と (ii))。
- **動作環境プロセスはノードの単一障害点である**。その監督を OS 側の仕組みに委ねるかは Phase 2 で決める。
- Zig のような「GC を持たずライブラリとしても配れる」言語のエコシステムが育ち、Zenoh の対応が揃えば、動作環境の言語は再検討の余地がある(ADR 0001 の再検証と同時に行う)。
- **`float128`・`float16` が数値型に加わったら**(ADR 0021 決定8)、G1 の表に行を足す。Rust の `f128` の安定化と、TypeScript に無い事への対処が要る。
- **Rust の標準に 256 ビット整数が入ったら**、crate を置き換える。正準形は変わらない。

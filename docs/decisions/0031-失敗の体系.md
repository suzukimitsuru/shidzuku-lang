## 背景(なぜ決める必要があるか)

第6章 6.1 は「データとして正常な不在と、系の失敗(期限超過・相手障害)は別の語彙とする。後者の体系は失敗の体系(U13)で定める」と宣言したまま、語彙を持っていない。
第3章 3.3 は数値の失敗を「失敗として戻る値であり、受け取りを書かなければコンパイルが通らない」と定めたが、戻る値の型も、受け取りの形も、検査の番号も無い。
第4章 4.6 には、失敗の体系(U13)を待つ未定事項が二つ残っている——仕事全体の期限と、`on failure` の欄の形である。

### 1. 「失敗」が一語で三つの物を指している

思考実験 22(失敗の棚卸し)は、仕様書と ADR に散らばった「うまくいかない事」を全て並べ、28 件を六つの群に分けた。

| 群                       | 件数 | いまの書き方                                           |
| ------------------------ | ---- | ------------------------------------------------------ |
| データとして正常な不在   | 5    | `choice` の区分(`なし`・`欠損`・`暦の外`)              |
| 業務が拒否した           | 4    | 公開面の直和(`-> 受注番号 \| 受注不可`)                |
| 数値と型の失敗           | 9    | **無い**(「戻る値」と定めたが、その型が無い)           |
| 解析の失敗               | 2    | **無い**                                               |
| 通信の失敗               | 5    | 接続の属性と `on failure` の散文。呼び手の型には出ない |
| 失敗が起きない失敗(待ち) | 3    | **無い**                                               |

前の二群は型に名前があり、呼び手が分岐して受ける。後の四群は名前が無い。
そのうえ、**再試行で変わるか**という軸で切ると境目がずれる——0 除算は何度やっても起きるが、期限超過は次は通るかもしれない。
「系の失敗」を一つの語彙にまとめると、呼び手にとって意味の違う物が混ざる。

### 2. 公開面の宣言に、通信の失敗が現れない

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可
```

この宣言は二つしか返さないように読めるが、第4章 4.1 は期限超過と相手障害でも失敗応答が返ると定めている。**三つ目が型に現れていない。**
省略の禁止(第0章 0.5、ADR 0008)の網に穴がある。

思考実験 25(系の失敗の書き分け)は、この穴の塞ぎ方を三案で書き比べ、どれも決め手に欠ける事を確かめた。
そのうえで、**書いている途中で第四の形に行き着いた**——系の失敗を公開面に書かず、フローが業務の語彙へ翻訳する形である。
思考実験 21(補償と巻き戻し)の記述が、既にそうなっていた。

```plaintext
on failure Inventory : OrderIntake は受注不可を返す(伝播しない)
```

### 3. `on failure` の欄が散文である

同じ補償(引当の解放)が、業務上の取消では検査される接続として書かれ、障害時では散文として書かれる(思考実験 21 の論点1)。
散文に書いた通信は `depends`・公開面・型・期限のどれも検査されず、**補償自身が失敗した時の記述も置けない**(論点2)。

### 4. 待ちには、失敗が起きない

決済代行が生きたまま沈黙すれば、確定は永久に来ない(思考実験 20 の論点5)。
引当の後に受付が落ちれば、どの受注にも結び付かない引当が残る(思考実験 21 の論点4)。
**何も返らないため、受け取って分岐する形では書けない。** 誰かが時間を測らなければ、失敗は永久に起きない。
ADR 0023(対になる通信の相関)はこの問い(仕事の期限)を決定8 で本 ADR へ送った。

### 5. 最小の言語実装(Phase 1)へ移る条件が、本 ADR を待っている

計画書 第4節 4.5 の移行の条件のうち、接合面の写し元(計画書の M3)は、終える呼び出し(ADR 0012 の接合面の8つ目)の理由を失敗の体系(U13)から写すとしている。
失敗の体系(U13)は、Phase 1 の前に決める課題の先頭に置かれている。

## 検討した選択肢

### 論点1: 接続の失敗を、公開面にどう書くか

思考実験 25(系の失敗の書き分け)の四つの形である。

| 選択肢                              | 公開面の語 | 省略の禁止     | 失敗が1つ増えた時        |
| ----------------------------------- | ---------- | -------------- | ------------------------ |
| 書かない案(全ての ask に暗黙で付く) | 増えない   | **満たさない** | 影響なし                 |
| 直和に並べる案                      | +8         | 満たす         | **全公開面の型が変わる** |
| 器を分ける案(`fails` の欄)          | +8 と欄 4  | 満たす         | **全公開面の型が変わる** |
| フローが業務の語彙へ翻訳する案      | 増えない   | 満たす         | 影響なし                 |

### 論点2: `on failure` の欄の形

- **散文のまま**: レビューが担保する。
- **接続を書ける欄にする**(思考実験 21 の案): 散文の代わりに、平常時と同じ形の接続を書く。
- **サーガの単位を新設する**: 手順と補償を並べる単位を足す。

### 論点3: 数値と解析の失敗の型

思考実験 22 の論点2 の三案である。

- **演算の結果を全て直和にする**: 全ての算術に分岐が付く。
- **伝える記法を持つ**: Rust の `?` に当たる記法で、受けずに上へ渡す。
- **境界で受ける**: 幅を出る可能性がある計算を、`丸める`・`収める` のような明示の操作に閉じ込める(ADR 0021 の形を広げる)。

加えて、受けた失敗がどこまで届いてよいか(コンポーネントの外へ出てよいか)を問う。

### 論点4: 再試行で変わる失敗と変わらない失敗を、型で分けるか

- **型の印で分ける**: 失敗の型に「一過性」「決定的」の印を付ける。
- **置き場で分ける**: 二つが同じ型に混ざらない置き場を与え、印は付けない。
- **分けない**。

### 論点5: 待ちに期限を与える場所

思考実験 22 の論点4 の三案に、一つ足した。

- **仕事に期限を書く**: `flow` 宣言に、仕事全体の期限を書く(思考実験 20 の `within`)。
- **状態に期限を書く**: `state` 宣言に、項目の保持の期限を書く。
- **言語は持たず、運用に委ねる**。
- **相関の区間に期限を書く**: `correlate` が結んだ道の、二つの接続の間に期限を書く(本 ADR で足した案)。

## 決定

### 決定1 — 失敗を四つの置き場に分ける(体系の全体)

うまくいかない事を、**どこで受けるか**で四つに分ける。型の名前の有無(誰が決めたか)と、再試行で変わるかは、置き場から決まる。

| 置き場           | 含む物(思考実験 22 の群)                           | 型                             | 受ける所                                 | 再試行で       |
| ---------------- | -------------------------------------------------- | ------------------------------ | ---------------------------------------- | -------------- |
| データの区分     | データとして正常な不在・業務が拒否した             | 記述者の `choice`              | 呼び手の body                            | (失敗ではない) |
| 演算と解析の失敗 | 数値と型の失敗・解析の失敗のうち言語の操作が出す物 | 言語が持つ型(決定7)            | その操作を書いたコンポーネントの body    | 変わらない     |
| 接続の失敗       | 通信の失敗のうち、送った側に返る物                 | 型を持たない(公開面に現れない) | `flow` 宣言の `on failure`(決定2・決定3) | 変わり得る     |
| 待ちの期限切れ   | 失敗が起きない失敗(待ち)                           | 型を持たない                   | `flow` 宣言の `on expiry`(決定9)         | (時間が経った) |

- **前の二つは値であり、後の二つは値ではない。** 値は body が受けて分岐する。値でない物は、フローが宣言した手順で埋め合わせる。
- 業務の区分(データとして正常な不在と業務の拒否)は、本 ADR で何も変えない。第6章 6.1 のまま、記述者の `choice` で書く。
- **接続の失敗**に含めるのは次の三つである。いずれも送った側に返る。
  - `ask` の期限超過
  - `ask` の相手の障害
  - `pressure block` の期限内に投入できない事(第4章 4.3)
- 通信の失敗の群の残り二つは、接続の失敗に含めない。`transient` の流れが再起動を跨いで消える事は送った側に返らず、既に `on failure` と `state` の宣言に現れる(第4章 4.4)。
  `latest`・`drop` で捨てた事は宣言された廃棄であり、失敗ではない(第4章 4.3)。どちらもログ規約(U4)の対象のままである。

### 決定2 — 接続の失敗は公開面に書かない。フローが業務の語彙へ翻訳する(論点1)

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可        # 業務の語彙だけで閉じる
```

- 公開面の応答に書くのは業務の語彙だけである。`期限超過`・`相手障害` のような語は、どの公開面にも現れない。
- 接続が失敗した時に呼び手へ何を返すかは、`flow` 宣言の `on failure` が**業務の区分で**書く(決定3)。
  省略の禁止は既に満たされている——`on failure` はフローに参加する全コンポーネントについて必須である(E0008-1(必須宣言の欠落))。
- 返すべき業務の区分が無ければ、記述者が公開面の直和に区分を足す(`受注不可 = 在庫なし | 受付停止中 | 受け付けられなかった`)。
  客に見せるのは「期限超過」ではなく「受け付けられなかった」であり、第6章 6.1 の「不在の区分名は、何が無いのかを言う」に沿う。
- **言語が接続の失敗の種類を足しても、公開面は変わらない。** 公開面は互換性の単位(ADR 0012 の決定9(コンポーネント記述子))であり、
  言語の語彙の追加がコンポーネントの版を上げてはならない(思考実験 25 の第8節(未解決課題への入力))。
- 第3章 3.2 の `expose <名前>(<引数>) -> <応答> | <失敗>` の `<失敗>` は、業務の区分を指す。採用時に書き換える(決定12(適用範囲))。

### 決定3 — `on failure` を型の付いた欄にする(論点2)

`on failure` の中身を、散文から次の三種の行の並びに変える。

```plaintext
on failure <コンポーネント> [at <接続>, ...] {
  <送り手> -> <受け手> : <接続>                    # 補償・後始末に使う接続(平常時と同じ形)
  <コンポーネント> respond <公開面> : <区分>       # 代わりの応答
  restart | restart none                          # 障害を起こしたコンポーネント自身の扱い
}
```

| 行        | 意味                                                            | 検査                                                                           |
| --------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 接続の行  | 生き残った側が、補償・後始末のために使う接続                    | 平常時の接続と同じ(依存の宣言・公開面・型・期限)                               |
| `respond` | 生き残った側が、待たせている `ask` に業務の区分で答える         | 区分が公開面の応答に含まれるか、答える者がその `ask` の受け手か                |
| `restart` | 障害を起こしたコンポーネントを再起動する。`none` で再起動しない | 再起動で失われる状態と `state` の宣言の整合(E0000-4(状態と障害時の記述の矛盾)) |

- **接続の行は、平常時と同じ検査を受ける。** 依存の宣言にない相手(E0000-2(depends 宣言外への通信))、公開面にない受け口(E0000-3(expose 宣言外の使用))、
  型の不一致(E0009-1(接続の両端の型の不一致))、期限の欠落(E0008-1(必須宣言の欠落))は、`on failure` の中でも同じに見る。思考実験 21 の論点1・2 が閉じる。
- **同じ `flow` 宣言の本文に、同じ送り手・受け手・名前の接続があれば、名前だけで指せる**(`OrderStore -> Inventory : 引当の解放`)。
  属性(期限・`pressure`・配達保証)は本文の行から読む。省略ではなく参照であり、属性が書かれている場所は一つに決まる。
  本文に無い接続を使う時は、平常時と同じ形で全ての属性を書く。接続の指し方は ADR 0023 の決定3(接続の指し方)と同じとする。
- **`respond` が名指すのは公開面の名前である。** その公開面の `ask` は同じ `flow` 宣言にあり、`at` で絞った接続より前に並んでいなければならない。
  答える者は、その `ask` の受け手であり、かつ `at` で絞った接続の送り手でなければならない——**まだ答えていない `ask` にだけ、答えられる**。
- 区分の書き方(`受け付けられなかった` だけで書くか、型の名前で修飾するか)は、直和の区分名の可視範囲と同じ所で決まる。プログラムの宣言(U14)の論点2 に送る。
- **`restart` の行は必須である**(欠落は E0008-1(必須宣言の欠落))。再起動しない事も `restart none` と書く。再起動の回数や間隔のような監督の詳細は、本 ADR では決めない(将来の変更想定)。
- 従来の「伝播しない」の一句は書かない。障害の非伝播は全コンポーネントの不変条件である(第0章 0.4)。
- 語の綴り(`respond`・`restart`・`at`)は仮である。ADR 0014(識別子と言語語彙の表記)に従い ASCII の語彙とし、パーサの実装中に語ごとに再検討する。

### 決定4 — `on failure` を接続で絞れる(`at`)

一つのコンポーネントが一つの `flow` 宣言で複数の接続に現れる時、どの接続で落ちたかで埋め合わせが違う。

```plaintext
on failure Inventory at 引当 {                 # 受注の途中。答えを待たせている
  OrderIntake respond 受注 : 受け付けられなかった
  restart
}
on failure Inventory at 引当の解放 {           # 受注は答え終えている。答える相手が居ない
  restart
}
```

- `at` に書くのは、そのコンポーネントが端点になっている接続である。指し方は決定3 と同じである。`at` は複数並べてよい(`at 決済の依頼, 決済の結果`)。
- **一つのコンポーネントについて、`at` の無い `on failure` を1つ書くか、`at` を付けた `on failure` で全ての接続をちょうど一度ずつ覆うかのどちらかとする。**
  混ぜる事と、覆い残しと、二度覆う事を禁じる(E0031-3)。「残り全部」を受ける書き方は置かない——既定の分岐であり、ADR 0008(省略の禁止)の既定表と同じ形になる。
- `respond` は、`at` で接続を絞った `on failure` の中でだけ書ける。絞らないと、まだ答えていない `ask` が決まらないためである。

### 決定5 — 補償の失敗は入れ子にしない。待ちの期限が引き受ける

補償の接続(決定3 の接続の行)自身が失敗した時の記述を、`on failure` の中に入れ子で書く形は置かない。

- 入れ子には底が無い。補償の補償が失敗した時、さらに一段が要る。
- 底は常に**時間**である——誰も片付けなかった物は、いつか誰かが期限で片付けるしかない。
- したがって補償の失敗は、残った物(孤児の引当など)を待っている側の期限切れ(決定9)が引き受ける。
  待っている側が居なければ、記述者は待つ側を置く(机上検証3(孤児の引当))。
- 補償の接続が失敗した事は、ログ規約(U4)の対象とする。

### 決定6 — 記述の中の接続は、全てどれかの `flow` 宣言に現れる

決定2 は、接続の失敗の翻訳を `flow` 宣言に任せる。`flow` 宣言に現れない接続には `on failure` が無く、翻訳の場所が無い。
今の仕様には「使っている接続がどのフローにも書かれていない」を見る検査が無い(思考実験 25 の第6節(第四の形))。

- コンポーネントの `depends` に書いた相手(兄弟と親の兄弟)のそれぞれについて、その相手と自分を端点とする接続が、少なくとも一つの `flow` 宣言に無ければならない(E0031-4)。
- body が行う通信は、どれかの `flow` 宣言の接続(`on failure`・`on expiry` の中の行を含む)に当たらなければならない(E0031-5)。
  body の記法(U26)が決まるまでは検査できないが、要求は本 ADR で置く。
- **範囲は記述の中の接続に限る**(計画書 第4節 4.5、2026-09-27 の判断)。記述の外にある `external` は今はフローの端点に書けないため、外部世界との境界(U12)がフローの端点を決める時に広げる。

### 決定7 — 演算と解析の失敗は、コンポーネントの中で受け、公開面を越えない(論点3)

第3章 3.3 の「実行時に戻る失敗」の7つと、`時点`・`日付` の範囲外(第6章 6.4)は**演算の失敗**とする。
言語の操作がテキストを数値や日付として読めなかった事は**解析の失敗**とする。

- **二つの型は言語が持つ。** 区分は演算の失敗が「幅を出た」「位取りを揃える所で幅を出た」「変換で幅を出た」「0 除算」「特殊値」「長さが合わない」「宣言桁を超えた」「範囲外」、
  解析の失敗が「形が合わない」である。区分の綴りはパーサの実装中に定める(ADR 0014)。
  計画書 第7節 7.4 は一般的な区分名を言語の組み込みにする案を撤回したが、あれは記述者が文脈ごとに違う意味で使う語の話である。
  ここでの区分は言語の操作が決めた意味しか持たず、記述者の宣言に現れない(次の項)ため、撤回の理由は当たらない。
- **言語の失敗の型は、コンポーネントの外へ出ない。** `record` の欄・公開面・`flow` の内容・`state` に現れたら E0031-7 とする。
  決定2 と同じく、公開面は業務の語彙だけで閉じる。
- **記述者が書いた解析は対象外である。** バイト列が期待の形式(例: JSON(JavaScript Object Notation))でない事は、`parse` の役割の記述者が `choice` で書く
  (`choice 注文の解析 = 読めた(注文) | 読めない(読めない理由)`)。業務の区分と同じ置き場である。
- **受け取りは省略できない**(E0031-6)。第3章 3.3 が番号を持たずに定めていた検査に番号を付ける。受け方は次の三つであり、どれかを明示する。

| 受け方         | 意味                                                                 | 例                                                       |
| -------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| 業務の値にする | 自分の公開面の区分や、自分のデータに翻訳する                         | 合計が幅を出たら `受注不可` の `金額が大きすぎる` を返す |
| 代わりの値     | その場で代わりの値を書く。既定値ではなく、受けるたびに書く           | 平均を取る列が空なら `平均なし` とする                   |
| 障害にする     | コンポーネントの障害として終える。フローの `on failure` が引き受ける | 記述の誤りに近く、続けても意味が無い時                   |

- **障害にした失敗は、接続の失敗として呼び手に届く。** 呼び手の側では相手の障害と区別しない。演算の失敗の種類は、終える呼び出しの理由(決定11)としてログ規約(U4)に残る。
  第0章 0.4(障害の非伝播)と思考実験 22 の論点6(戻った失敗を無視したら伝播と同じではないか)は、受け取りを強制し(E0031-6)、受けなければ障害として閉じ込める事で両立する。
- **受けずに上へ渡す記法と、受ける粒度**(演算ごとか、名前を得る所でまとめてか)は、body の記法(U26)が決める。ADR 0027(body の記法)の物差し「失敗の値の受け方」に当たる。
  本 ADR が決めるのは、渡せるのは body の中までであり、公開面を越えないという上限である。

### 決定8 — 再試行で変わるかは、置き場の違いで表す。再試行の規定は足さない(論点4)

- 決定1 の表の通り、**決定的な失敗(演算と解析)は body の中にあり、一過性の失敗(接続)は `flow` 宣言にある。** 二つは同じ型に混ざらない。
  型に印を付けなくても、呼び手が二つを取り違える場所が無い。
- 接続の失敗を受けた body は、その接続の `on failure` に書かれた手順だけを行う。**同じ接続を呼び直す事は、今は書けない**(E0031-5 の範囲)。
- 再試行を言語に足す時は、接続の属性(第4章 4.6 の未定事項)として、ログ規約(U4)と併せて最小の分散動作環境(Phase 2)で決める。
  今の「再試行しない」は既定値ではなく、再試行という語彙がまだ無い事である。足す時は既定値を置かず、全ての `ask` に書かせる(ADR 0008)。
- 決定的な失敗を障害にした時、**`durable` な受け口では再送で同じ失敗を繰り返す**。同じ入力が届き続け、再起動しても直らない。
  `durable` な受け口の処理の中で演算の失敗を障害にしている記述を W0031-1 とする。正しい場合(必ず直してから流し直す運用)があるため警告に留める。

### 決定9 — 待ちの期限は、相関の区間に書く(論点5)

`correlate` が結んだ道の、二つの接続の間に `within` で期限を書く。期限を過ぎた時の埋め合わせは `on expiry` に書く。

```plaintext
correlate 受注番号 : 受注 -> 保存 -> 決済の依頼 -> 決済の結果 within 30 分 -> 受注の状態
on expiry 決済の結果 {
  OrderStore -> Inventory : 引当の解放
  OrderStore -> Frontdesk : 受注の状態
}
```

- 読み方は「**決済の依頼 の後、決済の結果 が 30 分以内に届く**」である。`within` はその直前の矢印(区間)に付く。
- **待つ側**は、区間の前の接続の端点であり、かつ後ろの接続の受け手であるコンポーネントである。後ろの接続の送り手が待つ側自身なら、それは待ちではない(自分で動く)。
  待つ側が決まらない区間に `within` を書けば E0031-8 とする。
- **待つ側がある区間には、`within` が必須である**(欠落は E0008-1(必須宣言の欠落))。無期限は `within none` と書く——`pressure block(deadline none)` と同じ形である。
  有限の `within` には、後ろの接続を名指す `on expiry` が必須である。
- `on expiry` の中身は `on failure` と同じ行(接続の行・`respond`)で書き、**待つ側が行う**。`restart` は書かない(誰も落ちていない)。
  待つ側が通信せず、自分の中だけで片付ける時は `on expiry <接続> none` と書く(`correlate none`・`restart none` と同じ形。採用時に決めた)。
  後ろの接続の名前で指すのは、同じ `correlate` の道に期限を二つ置けるためである。指した接続に `within` が無ければ E0031-9 とする。
- **期限を測るのは、待つ側の動作環境である。** 一つのコンポーネントの中で測れるため、ノードを跨いだ時計を要らない。
  期限は `量 時間` を持つ数値であり、`時点` は書けない(E0019-2(時点の減算・期限への時点の使用))。動作環境は経過時間計で測り、コードには出さない(ADR 0012 の決定2(責務の分担))。
- **待ちは、後ろの接続が届いた時か、待つ側が同じ鍵を持つ同じ `flow` 宣言の接続を受けた時に解ける。**
  受注の取消が先に届いた時、決済の結果を待ち続けない。
- 仕事全体の期限(思考実験 20 の `within`)は採らない。仕事の始まりと終わりを一つずつに決められず、誰が測るかも決まらない(捨てたもの・理由)。

### 決定10 — 鍵の合わない到着と、期限の後の到着は、失敗と呼ばない

- 期限切れの後に届いた決済の結果や、宛先を失った通知(思考実験 22 の失敗が起きない失敗(待ち)の3件目)は、**普通のデータとして待つ側に届く**。
  鍵で引いても待ちが無い、という事実を body が受けて分岐する。
- 遅れて届いた `決済成立` を捨てるか、返金の流れを起こすかは業務の判断である。言語は判断を持たず、既定の扱い(黙って捨てる)も置かない。
  body の分岐の網羅が、扱いの記述を強いる(body の記法(U26)の網羅の分岐)。
- 届いた物を捨てた事は、ログ規約(U4)の対象とする。

### 決定11 — 接合面への写し(ADR 0012 の決定3 を改訂する)

ADR 0012 の接合面の8つの呼び出しのうち、失敗の体系(U13)が写し元になる物の中身を定める。接合面の凍結(ADR 0012 の決定10)は従来通り TypeScript が通ってからである。

| 呼び出し                          | 本 ADR で定める中身                                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 要求を送る(接合面の2つ目)         | 応答は「相手の応答」か「接続の失敗」の二つ。接続の失敗の種類(期限超過・相手障害)はログのために添えるが、body は分岐しない |
| 流す(接合面の4つ目)               | `pressure block` の期限内に投入できない時、接続の失敗を返す                                                               |
| 終える(接合面の8つ目)             | 理由は「正常」か「障害にした(演算の失敗の区分、または解析の失敗)」。プロセスの死は監督が同じに扱う(従来通り)              |
| 待ちを置く・解く(**9つ目を足す**) | 待つ側の生成コードが、鍵の正準形と期限を動作環境に渡す。期限切れは環境からコンポーネントへ、鍵の正準形を添えて届ける      |

- **待ちを動作環境に置くのは、鍵の値を動作環境が解釈しないためである。** 動作環境が見るのは宛先・型の指紋・期限・要求の識別子だけである(ADR 0012 の決定4(接合面を流れる物))。
  鍵は正準形のバイト列のまま預かり、照合はバイト列の一致で行う。
- 並置(ADR 0012 の決定5(接合の方式))では、動作環境はコンポーネントの生死を跨いで生きるため、待ちは再起動を跨ぐ。
- 待ちの期限の判定は意味の核(ADR 0029 の決定1(意味の核))に置く。一体の書き込みの ESP32 では機器の再起動で待ちが失われる。これは将来の変更想定に置く。
- 呼び出しの番号の振り直しと表の書き換えは、採用時に ADR 0012 に改訂の記録として足す。

## 机上検証

### 検証1: 受注の一生 — 思考実験 21 と ADR 0023 の記述を書き直す

ADR 0023 の検証2(引当と解放)の `flow 受注の一生` に、客からの `ask 受注` を足して書き直した。

```plaintext
choice 受注不可 = 在庫なし | 受付停止中 | 受け付けられなかった

flow 受注の一生 {
  intent { ... }
  Frontdesk     -> OrderIntake   : ask 受注(注文) deadline 500 ミリ秒 -> 受注番号 | 受注不可
  OrderIntake   -> Inventory     : ask 引当(品目ID, 数量) deadline 100 ミリ秒 -> 引当の結果
  OrderIntake   -> OrderStore    : ask 保存(注文, 引当番号) deadline 200 ミリ秒 -> 保存の結果
  OrderStore    -> PaymentBridge : flow 決済の依頼 pressure block(deadline 1 秒) (durable)
  PaymentBridge -> OrderStore    : flow 決済の結果 pressure block(deadline 1 秒) (durable)
  OrderStore    -> Inventory     : ask 引当の解放(引当番号) deadline 100 ミリ秒 -> 解放の結果
  OrderStore    -> Frontdesk     : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  correlate 引当番号 : 引当 -> 保存 -> 引当の解放
  correlate 受注番号 : 受注 -> 保存 -> 決済の依頼 -> 決済の結果 within 30 分 -> 受注の状態

  on failure Inventory at 引当 {
    OrderIntake respond 受注 : 受け付けられなかった
    restart
  }
  on failure Inventory at 引当の解放 {
    restart                                    # 引当は残る。机上検証3 で拾う
  }
  on failure OrderStore at 保存 {
    OrderIntake -> Inventory : ask 引当の解放(引当番号) deadline 100 ミリ秒 -> 解放の結果
    OrderIntake respond 受注 : 受け付けられなかった
    restart
  }
  on failure OrderStore at 決済の依頼, 決済の結果, 引当の解放, 受注の状態 {
    restart                                    # 受注台帳は recoverable。durable の流れは再送される
  }
  on failure OrderIntake   { restart }
  on failure PaymentBridge { restart }
  on failure Frontdesk     { restart }

  on expiry 決済の結果 {
    OrderStore -> Inventory : 引当の解放
    OrderStore -> Frontdesk : 受注の状態          # 取消(受注番号, 決済できなかった) を流す
  }
}
```

**発見1: 平常時の接続と補償の接続が、同じ検査を受けた。** `OrderStore` の障害時に `OrderIntake` が行う解放は、本文の解放(送り手は `OrderStore`)と送り手が違うため、全ての属性を書いた。
`OrderIntake` の `depends` に `Inventory` がある事、`Inventory` の公開面に `引当の解放` がある事、期限が 100 ミリ秒である事が見られる。
思考実験 21 の「たまたま揃っている」は、揃っている事を言語が確かめる形になった。

**発見2: 決定6(全ての接続がフローに現れる)が、書き漏れを見つけた。** ADR 0023 の検証2 は `PaymentBridge` が決済の依頼をどこから受けるかを書いていなかった。
`OrderStore` の `depends` に `PaymentBridge` があれば、`決済の依頼` の接続がどの `flow` 宣言にも無い事を E0031-4 が見つける。上の記述では足してある。

**発見3: `respond` の制約が、答えられる時と答えられない時を分けた。** `Inventory` が `引当` で落ちた時は `受注` がまだ答えられていない。
`引当の解放` で落ちた時は答え終えている。同じ `Inventory` の障害を一つの `on failure` で書くと、後者で `respond` が意味を失う。決定4 の `at` は、この区別のために要った。

**発見4: 期限の和が読めるようになった。** `受注` の 500 ミリ秒の中で、`引当` 100 ミリ秒と `保存` 200 ミリ秒が順に走る。
内側の期限の和が外側を超えていれば、`respond` に辿り着く前に外側が切れる。今は検査しない(将来の変更想定)。

### 検証2: 確定が来ない — 思考実験 20 の論点5

`決済の依頼 -> 決済の結果` の区間の待つ側は `OrderStore` である——`決済の依頼` の端点であり、`決済の結果` の受け手であり、送り手ではない。

- 決済代行が生きたまま沈黙すると、30 分で `OrderStore` に期限切れが届き、`on expiry 決済の結果` の手順(引当の解放と取消の通知)を行う。
- **時計は `OrderStore` の動作環境の中にある。** 決済代行の時計も `PaymentBridge` の時計も要らない。
- 31 分目に `決済成立` が遅れて届いた時、`OrderStore` には待ちが無い(決定10)。返金の流れを起こすかは業務の判断であり、body が書く。
  思考実験 20 の論点5 は閉じた。遅れて届いた物の扱いは、業務の区分として新しく現れた。

### 検証3: 孤児の引当 — 思考実験 21 の論点4

`OrderIntake` が引当の後、保存の前に落ちた。`on failure OrderIntake { restart }` であり、`Inventory` の引当台帳に孤児が残る。
`Inventory` の引当の解放が失敗した時(検証1 の `on failure Inventory at 引当の解放`)も同じである。

**上の記述では、この孤児を誰も待っていない。** `correlate 引当番号 : 引当 -> 保存 -> 引当の解放` の区間で、`Inventory` は待つ側にならない。
`保存` の端点ではなく、`引当の解放` は届くかどうかが決まっていない(取消の時だけ届く)ためである。

決定5(補償の失敗は待ちの期限が引き受ける)に従うと、**記述者は `Inventory` を待つ側にする接続を足す事になる。**

```plaintext
  OrderStore -> Inventory : ask 引当の確定(引当番号) deadline 100 ミリ秒 -> 確定の結果
  correlate 引当番号 : 引当 -> 引当の確定 within 40 分
  on expiry 引当の確定 none                    # 送る物は無い。Inventory の body が引当を戻す
```

- `引当 -> 引当の確定` の区間では、`Inventory` が `引当` の端点であり `引当の確定` の受け手であるため、待つ側になる。
- 取消で `引当の解放` が先に届けば、同じ鍵の接続を受けたので待ちは解ける(決定9)。
- **言語が設計を押した。** 引当に期限を持たせ、確定で期限を解く形は、在庫の引当でよく使われる形である。
  記述の上で孤児を待つ者が居ない事が、E0008-1(必須宣言の欠落)ではなく「待つ側を置く場所が無い」として見えた。言語はこれを検査では見つけない(将来の変更想定)。
- `on expiry` の中身が空の時は `on expiry <接続> none` と書く(決定9。採用時に決めた)。

### 検証4: 合計が幅を出る — 思考実験 22 の第4節(一つの系に全部出す)

`OrderIntake` の body で `合計 = 単価 × 数量` が `int64(2) 円` の幅を出た。body の記法(U26)が決まっていないため、受け方だけを擬似的に書く。

```plaintext
# OrderIntake の body(擬似。記法は U26)
合計 = 掛ける(単価, 数量) を受ける:
  値 なら 続ける
  幅を出た なら 受注 に 受注不可 の 金額が大きすぎる を返す      # 業務の値にする
```

- 受けない記述は E0031-6 で止まる。
- `受注不可` に `金額が大きすぎる` を足すのは記述者の判断である。客には「金額が大きすぎる」と見せる。
- 障害にする道を選べば、`Frontdesk` から見て `OrderIntake` の障害になり、`flow 受注の一生` に書いた `on failure OrderIntake { restart }` が引き受ける。
  同じ注文で再び呼ばれれば再び落ちる。`受注` は `ask` であり durable な受け口ではないため W0031-1 には当たらないが、客の再送が同じ事を起こす。業務の値にする方が正しい場面である。

## 捨てたもの・理由

- **書かない案(全ての ask に接続の失敗が暗黙で付く)**: 宣言に無い物を呼び手が受け取る。第4章 4.2 の「フローは既定表という外部知識なしに読める」に反し、分岐を書き忘れても検査が根拠を持てない。
- **直和に並べる案・器を分ける案**: どの公開面にも同じ二語を書き写す記述になり(思考実験 25 で4本に8回)、言語が接続の失敗の種類を1つ足すだけで、全コンポーネントの公開面の型と版が変わる。
  直和に並べる案は、言語の区分名を記述者の直和に混ぜる点でも、計画書 第7節 7.4 と擦れる。
- **`on failure` を散文のまま残す**: 補償は検証できる記述である。接続として書けば相手も型も期限も機械が見られ、検証できる物を散文に落とす理由が無い(ADR 0003 の立場は検証不能な物を意図に置く事であり、逆ではない)。
- **サーガの単位を新設する**: `flow` 宣言と役割が重なり、どちらに書くかという外部知識が増える。補償の自動実行を動作環境に求め、最小の分散動作環境(Phase 2)の負担が跳ね上がる。
  足りないのは単位ではなく検査だった(思考実験 21 の第6節(示唆))。
- **補償の失敗を入れ子の `on failure` で書く**: 底が無い(決定5)。
- **演算の結果を全て直和にする**: 全ての算術に分岐が付く。受け取りを強制する目的は E0031-6 で果たせ、粒度は body の記法(U26)が選べる。
- **演算と解析の失敗を公開面へ出してよいとする**: 公開面に言語の語彙が現れ、接続の失敗を書かない理由(決定2)と同じ費用がかかる。
- **失敗の型に「一過性」「決定的」の印を付ける**: 置き場が分かれていれば二つは混ざらない(決定8)。印は読み手が覚える語を増やすだけである。
- **再試行を今決める**: 再試行はログ規約(U4)と組であり、動作環境の振る舞いである。最小の分散動作環境(Phase 2)で決める(第4章 4.6)。
- **仕事全体の期限(`flow` 宣言の `within`)**: 一つの `flow` 宣言の中で仕事の始まりと終わりは一つに決まらない(`correlate` の道は二本以上あり、取消と確定のように分かれる)。
  測る者も決まらず、ノードを跨いだ時計が要る。区間の期限なら、待つ側が一つに決まり、その動作環境の中で測れる。
- **状態に期限を書く(`state` の保持の期限)**: `state` の宣言は項目を持たず(第3章 3.2)、どの項目が「待っている」のかが宣言から読めない。
  期限を付ける相手は状態ではなく、相関の鍵で引ける待ちである。
- **言語は持たず、運用に委ねる**: 確定が来ない事は、誰かが測らなければ永久に起きない。ADR 0008 の立場からは、測るかどうかを宣言させるべき選択である。

## 結果(利点と欠点)

### 利点

- **公開面が業務の語彙だけで閉じる。** 言語が接続の失敗の種類を足しても、どのコンポーネントの版も上がらない。
- **補償が平常時の接続と同じ検査を受ける。** 依存の宣言・公開面・型・期限が `on failure` の中でも見られる(思考実験 21 の論点1・2)。
- **第3章 3.3 の「受け取りを書かなければコンパイルが通らない」に番号と範囲が付いた**(E0031-6・E0031-7)。
- **確定が来ない待ちを書けるようになった。** 測る者が一つに決まり、ノードを跨いだ時計が要らない(検証2)。
- **書き漏れた接続が見つかる**(検証1 の発見2)。
- **新しい単位を作っていない。** `on failure` の欄の中身を型の付いた行にし、`correlate` に `within` を、`flow` 宣言に `on expiry` を足しただけである。

### 欠点

- **呼び手が接続の失敗の種類で分岐できない。** 「期限超過なら呼び直し、相手障害なら諦める」は書けない。判断の置き場が body から接続へ動き、その接続の属性(再試行)はまだ無い。
- **`on failure` の記述が増える。** `at` で接続を絞ると、一つのコンポーネントに `on failure` が複数並ぶ(検証1 で `Inventory` と `OrderStore` が2つずつ)。
- **公開面に、翻訳先の区分を足す事になる**(`受け付けられなかった`)。思考実験 01〜04 の公開面は、採用時の書き直しで区分が増える。
- **E0031-5・E0031-6・W0031-1 は body の記法(U26)を待つ。** 本 ADR を採用しても、すぐに検査できるのはフローの側だけである。
- **孤児は検査では見つからない。** 待つ側を置かなければ、孤児は残ったままである(検証3)。言語は置く場所を用意しただけである。
- **接合面に呼び出しが1つ増える**(決定11)。8つで足りるとした ADR 0012 の机上確認を改める。

## 将来の変更想定

- **再試行**(ログ規約(U4)・最小の分散動作環境(Phase 2)): 接続の属性として足す。足す時は全ての `ask` に書かせる(決定8)。補償の接続を呼び直す時は、相手の公開面に `idempotent` を求めるかを併せて決める。
- **期限の和の検査**: 外側の `ask` の期限が、その中で順に走る内側の期限の和より短い記述を警告にするか(検証1 の発見4)。コンポーネントの実行モデル(U10)・メッセージの順序保証(U11)で、`ask` の中で `ask` を待つ形が決まってから決める。
- **外部との接続**(外部世界との境界(U12)): 外部がフローの端点に書けるようになれば、決定6 の範囲と、外部が返す失敗の翻訳(`Frontdesk` が客へ何を返すか)がこの体系に入る。
- **区分名の書き方**(プログラムの宣言(U14)の論点2): `respond` の区分を型の名前で修飾するか。
- **版の混在**(コンポーネントのバージョンと移行(U16)): 古い版のコンポーネントが新しい区分(`受け付けられなかった`)を知らない時。公開面の区分を足す事は版の変更に当たる。
- **監督の詳細**: `restart` の回数・間隔・諦めた後。今は再起動するかしないかだけを書く。最小の分散動作環境(Phase 2)の監督と併せて決める。
- **待ちと機器の再起動**: 一体の書き込みの ESP32 では、機器の再起動で動作環境ごと待ちが失われる(決定11)。recoverable な状態から待ちを置き直すかを、ESP32 の器を作る時に決める。
- **待つ側の居ない区間の警告**: 検証3 の孤児は、`correlate` の道の終わりに「届くか決まっていない接続」しか無い時に見つけられるかもしれない。題材で必要が確認されてから足す。
- **図**(図と実装の一致(U8)): `on failure` と `on expiry` の接続を障害境界図にどう描くか。

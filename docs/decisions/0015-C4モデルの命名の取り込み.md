# 0015: C4 モデルの命名の取り込み — システムコンテキスト層の追加とユニットの改名

- 日付: 2026-08-26(採用 2026-08-28)
- 状態: 採用
- 関連課題: U18(システムコンテキストの記述。本 ADR で新設)。関連 U8(図と実装の一致)・U12(外部世界との境界)・U14(プログラムの宣言)・U15(数値の型と単位)・U17(識別子と語彙の表記)
- 改訂する決定: ADR 0007(C4 の対応表、プログラム全体レベルの intent の不導入)、ADR 0014(語彙の対応表: 単位の綴り)

## 背景(なぜ決める必要があるか)

ADR 0007 は C4 モデルから「原則のみ」を取り込み、語彙と図法は独自とした。その時の対応表は次の通りである。

| C4 レベル | ADR 0007 での対応                                      |
| --------- | ------------------------------------------------------ |
| Context   | システムと外部の境界(adapter 型ユニットと外部アクター) |
| Container | ユニット(=配置単位。C4 の Container 定義と一致)        |
| Component | ユニットの内部階層(当時の第1章 1.4)                    |
| Code      | body(実装)                                             |

この対応は、その後の決定と思考実験によって三つの点で保たなくなった。

### 1. Context 段に、記述する場所が無い

「adapter 型ユニットと外部アクター」は**対応の説明**であって、記述の場所ではない。
システム境界の決定——何を内側に入れ、何を外に置き、誰が使うのか——を書く欄が言語に無い。

ADR 0007 はプログラム全体レベルの intent を「思考実験 01〜04 で必要が現れていない」として見送り、
「refs では足りない場面が出たら再検討する」という条件を残していた。その後、次の二つが未解決課題として登録されている。

- **U12(外部世界との境界)**: 外部(HTTP・機器・DB 等)への依存・公開をどこにどう書くか。省略の禁止(ADR 0008)との整合
- **U14(プログラムの宣言)**: ユニット・フロー・データを束ねる最上位の構成。名前空間、一意性と W1 の範囲

どちらも「システムという単位の記述が無い」という同じ穴の別の面である。再検討の条件は満たされている。

### 2. Container 段の指す物が、動作環境の決定によって動いた

ADR 0012(提案)は、動作環境を Rust の1実装とし、**ノードに常駐する動作環境プロセスがユニットのプロセスを監督する**形(並置)を決めた。

C4 の Container は「実行時に存在し、コードが動く器であり、コンポーネントを載せる物」である。
この定義に一致するのは**動作環境**であって、その上で監督されて動くユニットの側ではない。
ADR 0007 の「ユニット=配置単位だから Container」は、動作環境という器が決まる前の対応づけだった。

### 3. `unit` という綴りを二つの意味が奪い合っている

ADR 0014 は度量衡の単位を `measure` と綴った。その理由は表に明記されている通り
「`unit` はユニット宣言が取っているため衝突を避ける」だけであり、**単位の側に `measure` を選ぶ積極的な理由は無い**。

一方でユニットの側にも、`unit` を占め続ける積極的な理由は無い。ユニットは
「モジュール=フローの節=障害境界=配置単位」という**役割の束の名前**であって、
`unit`(単位)という一般名詞は、その役割の何も語っていない。ADR 0006 が粒度の指針を必要とした理由も、
名前が粒度を示唆しないところにある。

度量衡の側では `unit` は世界共通の語であり、代替語(`measure`)は次元型の系譜に倣った回避策である。
**衝突する二語のうち、一方だけが `unit` を必要としている**。

## 検討した選択肢

### 論点1: Context 段をどう記述するか

- **N1: 対応表を書き換えるだけ**。宣言は足さず、Context 図は「外部と通信するコンポーネント」から抽出する。
- **N2: `system` 宣言を第一級に足す**。コンポーネントと同じく intent と constraint を持たせ、境界の決定を書かせる。
- **N3: U14(プログラムの宣言)の決定まで待つ**。最上位の構成が決まってから Context 段を載せる。

### 論点2: Container 段は何か

- **C-a: Container = コンポーネント**(ADR 0007 の現状維持)。
- **C-b: Container = 動作環境。言語の宣言は持たない**。書き手は Container を書かず、Shidzuku が実行系として実現する。
- **C-c: Container = 動作環境。`container` 宣言を言語に足す**。どのノードに何を載せるかを言語で書く。

### 論点3: 改名するか

- **R1: 改名しない**。C4 の語は対応表の中だけで使い、言語の語彙は `unit` のまま据え置く。
- **R2: `unit` を `component` に改名し、度量衡の単位を `unit` にする**。
- **R3: `unit` を `component` に改名するが、単位は `measure` のまま据え置く**。

### 論点4: Code 段と内部階層(layers)の関係

現在の body は「内側は原則自由」+「名前付きの内部階層(pure / io)の宣言は必須」の二重構造である(改番前の第1章 1.4、改番後の第2章 2.4。ADR 0005・0013)。
C4 は4段しか持たないため、階層をどの段に置くかを決めなければならない。

- **L1: 階層 = Component 段**(ADR 0007 の現状)。コンポーネントを改名した結果、Component 段に二つの物が同居する。
- **L2: 階層 = Code 段の骨格**。Code 段は「body とその内部階層」とし、階層は Code 段の入口の構造とする。
- **L3: 階層を5段目にする**。C4 を4段のまま使わず、Shidzuku 固有の段を足す。

### 論点5: 第三層のブロックの名前

決定4で `unit` を `component` に改める以上、第三層の `body` も段の名前(Code)に合わせるかを決めなければならない。
合わせれば4段のうち3段が宣言の名前と一致する。

- **B1: `body` のまま据え置く**。段の名前は Code、ブロックの名前は `body` とし、両者を別の語に保つ。
- **B2: `code` に改名する**。`system` / `component` / `code` の三つが段の名前と一致する。
- **B3: `impl` に改名する**。三層を「意図・制約・実装」の同じ水準の語で揃える。段の名前とは一致しない。

## 決定

### 1. 四つの段を、Shidzuku の記述に対応づける

| C4 の段   | Shidzuku での名前           | 記述する物                                  | 誰が書くか          |
| --------- | --------------------------- | ------------------------------------------- | ------------------- |
| Context   | システム(`system` 宣言)     | システム境界・外部の人と外部システム        | 書き手              |
| Container | 動作環境(コンテナ)          | ノードに常駐しコンポーネントを載せる実行系  | Shidzuku が実現する |
| Component | コンポーネント(`component`) | 情報隠蔽 = フローの節 = 障害境界 = 配置単位 | 書き手              |
| Code      | コード(`body` と内部階層)   | 名前付きの層(pure / io)と、その中の実装     | 書き手              |

**Container 段だけが、書き手の書く物ではない**。これは C4 との明確な差であり、意図した差である(決定3)。

### 2. Context 段に `system` 宣言を足す(論点1: N2)

システムはコンポーネントと同じ形式で書く。ただし**三層ではなく二層**である。

``` plaintext
system <システム名> {
  intent     { ... }   # 第一層: 意図(コンポーネントと同じテンプレート。ADR 0003)
  constraint { ... }   # 第二層: 制約
}
```

- **body を持たない**。システムの実装は、内側のコンポーネントそのものである。
  システム自身に実装を持たせると、どのコンポーネントにも属さないコードが生まれ、
  「情報隠蔽=障害境界=配置単位」の四位一体(第0章 0.4)の外に置き場ができてしまう。
- **intent は必須である**。システム境界の決定(何を外に置いたか)は、コンポーネント境界の決定と同じ種類の
  検証不能な判断であり、`refs` で外部の ADR を指すだけでは「何を捨てたか」が残らない。
  これが ADR 0007 の見送りを覆す理由である。
- 当面 **1プログラム = 1システム**とする。複数システムの連携(システムがシステムを含む/並ぶ形)は U14 に委ねる。
  他の Shidzuku システムは、当面 `external` として外に置く。

システムの constraint の語彙は次の五つとする。省略の禁止(ADR 0008)は同じく適用し、該当が無い事も `なし` と書く。

| 語彙     | 意味                                                           | 検証時期                   |
| -------- | -------------------------------------------------------------- | -------------------------- |
| actor    | このシステムを使う人・役割の列挙。必須(無ければ `なし`)        | 検証しない(図と意図のため) |
| external | 外部システムの列挙とその説明。必須(無ければ `なし`)            | コンパイル時(名前の解決)   |
| depends  | external のうち、このシステムが呼ぶ相手。必須(無ければ `なし`) | コンパイル時               |
| expose   | システムが外へ見せる面と、それを担うコンポーネント。必須       | コンパイル時               |
| contains | 内側のコンポーネントの列挙。必須                               | コンパイル時               |

`depends` と `expose` はコンポーネントの constraint と**同じ語**を使う。段が変われば指す先が変わる
(コンポーネントの depends は内側のコンポーネント、システムの depends は外部システム)が、
「依存の向き」と「公開面」という意味は段を跨いで同じである。C4 のズームレベルと同じく、語彙も同じ物が違う倍率で現れる。

### 3. Container 段は動作環境であり、言語の宣言を持たない(論点2: C-b)

- Container は ADR 0012 の**動作環境**である。ノードに常駐し、期限を測り、durable な流れを届け切り、コンポーネントを監督する。
- **書き手は Container を書かない**。どのノードの動作環境に何を載せるかは配置の設定であり、言語の記述対象外とする。
  Container 図は、その配置から抽出する(Phase 2 以降)。
- コンポーネントと動作環境の境目は、ADR 0012 の接合面 H1〜H8 である。**その表がこの段の仕様**であり、本 ADR は新しい面を足さない。
- 四位一体(第0章 0.4)は維持する。**配置単位はコンポーネントのままである**。
  動作環境はコンポーネントを**載せる器**であって、コンポーネントを分割したり束ねたりする設計単位ではない。
  1つの動作環境に複数のコンポーネントが載る(1:N)が、これは配置の事実であって、設計・処理・障害の単位を動かさない。
  ADR 0012 の決定5(並置。1コンポーネント=1プロセス、障害境界=プロセス)と整合する。

### 4. `unit` を `component` に改め、度量衡の単位を `unit` にする(論点3: R2)

| 現在の表記     | 改名後                    | 備考                                                 |
| -------------- | ------------------------- | ---------------------------------------------------- |
| ユニット(unit) | コンポーネント(component) | C4 の Component。役割の束の名前を C4 に合わせる      |
| 単位(measure)  | 単位(unit)                | ADR 0014 の回避策が不要になる。`unitless` はそのまま |

- ADR 0014 の語彙表から `measure` を外し、`unit` に置き換える。`strip_measure` / `apply_measure` は
  `strip_unit` / `apply_unit` とする。`unitless`(単位なし)は綴りが変わらない。
- `component` は C4・UML・多くの言語処理系で「内部を隠して境界で繋がる部品」を指す語であり、
  Shidzuku のコンポーネントの意味(深いモジュール=障害境界=配置単位)と衝突しない。
- ユニット記述子(ADR 0012 の H1)は**コンポーネント記述子**と読み替える。接合面の呼び出しの数と意味は変わらない。

### 5. Code 段は body、内部階層は Code 段の骨格(論点4: L2)

- **Code = body**。C4 の Code 段は「必要な時だけ描く、コードから生成すべき最下段」であり、
  Shidzuku の「図はコードからの抽出」(第0章 0.7)と元から同じ立場である。
- **内部階層(layers)は Code 段の骨格**とする。階層は外から見える面ではなく、body の内側の分割だからである。
  コンポーネントの外との相互作用は expose を通る通信だけであり、どの層が何を持つかは外から観測できない。
  外から見えない物を Component 段に置くと、その段が「隠されている物」を描く事になる。

C4 との差は二つあり、いずれも Shidzuku の側が**強い**方へ振れている。

| 観点           | C4 の Code 段                | Shidzuku の Code 段                   |
| -------------- | ---------------------------- | ------------------------------------- |
| 描くかどうか   | 任意。多くの場合は描かない   | 常に構造を持つ。階層の宣言は必須(E9)  |
| 構造の出どころ | 実装から読み取る(クラス図等) | 宣言されている(名前・pure / io・役割) |

- 階層の名前と数は自由、制約強度は pure / io の2種(ADR 0005)、役割は境界・解析・領域・整形(ADR 0013 提案)。
  この三つが揃って初めて Code 段が「抽出できる図」になる。**C4 が諦めた最下段を、宣言によって取り戻す**というのが本決定の狙いである。

#### 第三層のブロックの名前は `body` のまま据え置く(論点5: B1)

決定4は `unit` を `component` に改めたが、**`body` は改めない**。段の名前(Code)とブロックの名前(`body`)を別の語に保つ。
四段のうち三段で名前が揃わなくなるが、それは次の二つの代価より安い。

1. **「コード」の指す範囲が二重になる**。本仕様書で「コード」は intent を含む記述全体を指している——
   「綺麗なコード、静かなシステム」(第0章 0.1)、「コードからの投影」(0.1)、「コードが変われば図が変わる」(0.7)、
   「コードそのものがモデル」(ADR 0007)。第三層だけを `code` と名付けると、同じ文書で「コード」が
   「記述全体」と「第三層」の二つを指す。しかも Shidzuku の主張は**意図もコードである**事であり、
   第三層だけが `code` なら「intent と constraint はコードではない」と読める。**理念に正面から当たる**。
2. **`code` ブロックが Code 段と一致しない**。Code 段は body と内部階層だが、`layers` は constraint の語彙である
   (第3章 3.2)。ブロック名と段名が同じになると「`code` ブロック = Code 段」と読めるのに、
   段の半分(層の宣言)はブロックの外に残る。一致させるには `layers` を constraint から移す事になり、
   「層の制約強度は検証可能な制約である」という ADR 0005 の決定を覆す。

段の名前が語彙に現れる事の効き目(決定4)は `body` では得られない。それは承知の上で、上の二点を優先する。
**段の名前とブロックの名前が違う事自体は、Container 段(言語の宣言を持たない)で既に起きている**。

### 6. 章立てを段の順に再構成する

C4 のズーム順(Context → Container → Component → Code)と章の順序を一致させる。

| 章    | 題名                 | 対応する段        | 由来     |
| ----- | -------------------- | ----------------- | -------- |
| 第0章 | ビジョン             | 全段              | 据え置き |
| 第1章 | システムコンテキスト | Context           | 新設     |
| 第2章 | コンポーネントの定義 | Component と Code | 旧第1章  |
| 第3章 | 制約の体系           | Component と Code | 旧第2章  |
| 第4章 | 通信モデル           | 段を跨ぐ関係      | 旧第3章  |

- Container 段は独立の章を持たない。決定3の通り言語の宣言が無いためであり、
  対応と接合面(ADR 0012)への参照を第1章に置く。動作環境そのものの仕様は Phase 2 の課題である。
- 通信(ask / flow)は C4 の「関係(relationship)」に当たり、段に属さず段を跨ぐ。したがって最後の章に置く。

### 7. 検証の追加

第2章 2.3(改番後は第3章 3.3)のエラー一覧に三つ足す。

| #   | 検査                                                                            | 由来   |
| --- | ------------------------------------------------------------------------------- | ------ |
| E11 | system 宣言の欠落、または intent / constraint の欠落                            | 本 ADR |
| E12 | contains の網羅性違反(どのシステムにも属さないコンポーネント、二つ以上への所属) | 本 ADR |
| E13 | システムの expose と、担当コンポーネントの expose の不一致                      | 本 ADR |

- E9(必須宣言の欠落)の対象に、システムの actor・external・depends・expose・contains を加える。
- **外部との通信そのものの検証は本 ADR では定めない**。外部システムとの接続の方式・障害時の記述は U12 の管轄であり、
  system 宣言は「誰が外にいるか」「境界のどこを通るか」までを引き受ける。

### 8. 改名の適用範囲は仕様書と索引に限る

- 書き換える: `docs/spec/` の全章、`docs/PLAN.md`、`README.md`、`docs/roadmap.html`。
- 書き換えない: `docs/decisions/`(本 ADR より前の全 ADR)と `docs/experiments/`。
  **ADR と思考実験は決定の履歴であり、書かれた時点の語で読めなければならない**。
  ADR 0014 が同じ理由で「各 ADR の本文は履歴として残す」としたのと同じ扱いとする。
- 読み替えは決定4の対応表による。

## 机上検証 — 既存の思考実験にシステム層を被せる

新しい段が既存の思考実験に無理なく載るかを確かめる(仕様は思考実験で裏付ける、という進め方の原則)。

### 思考実験 01(注文管理サービス)

``` plaintext
system 注文管理 {
  intent {
    why      "受注から引当・保存までを一つの境界に収める。在庫の台帳そのものと決済は外に置き、この系は「注文の一生」だけを知る"
    rejected option "在庫台帳を内側に持つ"
             reason "在庫は注文以外の系(仕入・棚卸)からも動く。内側に入れると、この系が在庫の真実の持ち主になってしまう"
    change   "配送の追跡が加わる想定。外部システムが1つ増える方向で吸収し、内側のコンポーネントの境界は変えない"
  }
  constraint {
    actor    顧客 "注文を送り、受注番号を受け取る"
    external なし
    depends  なし
    expose   受注(注文) -> 受注番号 | 受注不可   担当 OrderIntake
    contains OrderIntake, Inventory, OrderStore
  }
}
```

- **発見1**: 思考実験 01 の3コンポーネントは全て内側であり、外部システムは無い。
  しかし OrderStore が隠す「永続化方式(RDB)」の RDB は外部にある。
  **外部システムと「外部の技術」の区別**が要る。前者は system の external、後者はコンポーネントが隠す知識である。
  判定は「その相手が独立に設計され、独立に壊れるか」とする。RDB は OrderStore の内側の選択であり、外部システムではない。
- **発見2**: `expose ... 担当 <コンポーネント>` が要る。システムの公開面は必ずどれか1つのコンポーネントが担う。
  担当が自分の expose に同じ受け口を持たなければ E13 とする。

### 思考実験 02(センサー収集パイプライン)

``` plaintext
system センサー収集 {
  constraint {
    actor    運用者 "閾値超過の通知を受け取る"
    external センサー機器群 "多数の機器。MQTT で計測値を送ってくる"
    external 通知基盤 "外部の通知手段。Alerter が使う"
    depends  通知基盤
    expose   計測値の受け入れ(計測値) の受け口   担当 SensorIntake
    contains SensorIntake, Normalizer, Aggregator, MetricStore, Alerter
  }
}
```

- **発見3**: 外部からの流れの受け口も expose に載る(第3章の flow の受け口の形をそのまま使える)。
  センサー機器群は `depends` に入らない。**送ってくるだけの相手と、こちらから呼ぶ相手を分ける**必要があり、
  external(存在の宣言)と depends(呼ぶ相手)を別の語にした決定2が、ここで効いている。
- **発見4**: 時系列 DB は MetricStore が隠す「永続化方式」であり、発見1の判定により external ではない。
  一方、通知基盤は Alerter が呼ぶ独立の系であり external である。同じ「外の技術」に見えて、判定が分かれる。

### 思考実験 04(分散 KV ストア)

``` plaintext
system 分散KV {
  constraint {
    actor    クライアント "get / put する"
    external なし
    depends  なし
    expose   受付(要求) -> 結果 | 失敗   担当 ClientGate
    contains ClientGate, KVCore, Persister
  }
}
```

- **発見5**: 思考実験 04 が扱った3ノード複製は、**同じシステムが複数の動作環境に載る**形として素直に書ける。
  複製数はシステムの constraint に現れない。これは決定3(Container は言語の外)の結果であり、
  思考実験 04 が残した論点「配置・複製の記述を言語仕様に含めるか」への部分的な答えになる——
  **含めない。ただし配置の記述が要る事は変わらないので、Phase 2 の動作環境の設定として決める**。

三つとも、コンポーネントの記述を一切変えずにシステム層を被せられた。
`actor` は検証されないが、思考実験 01〜04 のどれにも「誰が使うか」が本文の散文としては書かれており、
書く場所が無かっただけである事が確認できた。

## 捨てたもの・理由

- **N1(対応表の書き換えのみ)**: Context 段が「抽出できる図」になるには、外部の人・外部システムがコードに宣言されていなければならない。
  外部と通信するコンポーネントから逆算すると、**誰が使うか(actor)は永久に抽出できない**。散文の README に戻る。
- **N3(U14 を待つ)**: U14 は名前空間と一意性の課題であり、Context 段は境界の課題である。
  待っても答えは出ず、その間 U12 も動けない。system 宣言を先に置き、U14 は「system をどう束ねるか」として再定義する方が順序が正しい。
- **C-a(Container = コンポーネント)**: 動作環境という器が実在すると決まった(ADR 0012)以上、
  「コンポーネントが器である」という説明は実装と食い違う。図を抽出した時に、コンポーネントの箱の中に動作環境が描けない。
- **C-c(`container` 宣言を言語に足す)**: 配置は設計判断ではあるが、**コンポーネントの境界の決定とは変更の理由が違う**。
  同じノードに何を載せるかは、負荷・機器・地理で変わる。これをコードに書くと、設計を変えていないのにコードが変わる。
  第0章 0.7「コードが変われば図が変わる」の逆——図(配置)が変わるたびにコードが変わる——を招く。
  ただし配置の記述そのものは必要であり、Phase 2 の動作環境の設定として決める。
- **R1(改名しない)**: 命名を取り込まないなら、段の対応表は文書の中だけの説明に留まり、
  読み手は `unit` を見て C4 の Container を思い出す事になる。ADR 0007 が取り込んだ「ズームレベル」という知見は、
  **段の名前が語彙に現れて初めて読み手に届く**。
- **R3(単位は `measure` のまま)**: `unit` が空くのに使わない理由が無い。ADR 0014 の `measure` は
  衝突の回避策として選ばれた綴りであり、衝突が消えれば回避策も要らない。世界共通の語に戻す。
- **L1(階層 = Component 段)**: 改名の結果、Component 段にコンポーネントと階層の二つが同居する。
  段の名前が二つの物を指すのは、ズームレベルという考えの核(1段=1つの倍率)を壊す。
- **L3(階層を5段目にする)**: C4 の4段は「読者の種類の数」に対応している(利用者・運用者・設計者・実装者)。
  階層を見る読者は実装者であり、Code 段の読者と同じである。読者が同じなら段を分ける理由が無い。
- **B2(`body` を `code` に改名する)**: 決定5の通り、理念の「コード」と衝突し、`code` ブロックが Code 段と一致しない。
  書き手の名前との衝突(`code` は区分コード・商品コードなど業務ドメインで最頻の語の一つ。ADR 0013)も増えるが、
  `body` もメッセージ本体として衝突しうるため、この点は決め手にしていない。
- **B3(`body` を `impl` に改名する)**: 三層の語の水準は揃う(意図・制約・実装)。理念とも段の名前とも衝突しない。
  それでも採らないのは、**改名の利益が語の水準を揃える事だけ**だからである。`body` は思考実験 01 以来
  15 コンポーネントで使われて誤読を生んでおらず、決定8で ADR と思考実験を旧称のまま残す以上、
  読み替えの負債だけが増える。改名は衝突が実在する時に行う(決定4の `unit` はそれに当たる)。
- **システムに body を持たせる**: 決定2の通り、四位一体の外にコードの置き場ができる。
- **`system` を `context` と綴る**: C4 の段の名前は「System Context」であり、主語はシステムである。
  `context` は多くの言語処理系で実行時の文脈を指し、意味が濁る。

## 結果(利点と欠点)

### 利点

- **四段が全て記述に対応する**。図の4段はコードから抽出でき、Context 段だけが散文に残る、という穴が塞がる。
- **外部との境界が省略の禁止の対象になる**。U12 が扱う「外部への依存・公開」は、これまで書く場所が無かったため
  省略の禁止(ADR 0008)の網の外にあった。system の constraint に入る事で、外部の存在も `なし` の明示を要求される。
- **`unit` が本来の意味に戻る**。度量衡の単位が世界共通の綴りを取り戻し、ADR 0014 の回避策が1つ減る。
- **語彙が C4 の読み手に通じる**。既存エコシステムへの漸進的導入(第0章 0.8)は語彙にも効く。
  Structurizr DSL / Mermaid C4 へのエクスポート(ADR 0007)も、語が同じであれば写像が説明不要になる。

### 欠点

- **書く量が増える**。1システムにつき intent(why・rejected・change)と5つの制約が必ず要る。
  小さなプログラムほど、この前払いは重い。ADR 0008 の「省略の禁止」が払わせている代価と同じ種類のものである。
- **「コンポーネント」は長い**。`unit` の4文字に対し `component` は9文字であり、日本語でも6拍から7拍に増える。
  最も頻繁に書く語が長くなる事は、実際の記述の負担になる。短縮形は導入しない(略語は語彙の一意性を崩す)。
- **既存の文書に二つの語が併存する**。決定8により ADR と思考実験は `unit` のまま残るため、
  読み手は対応表を一度は見る必要がある。ADR 0014 と同じ負債であり、Phase 1 のパーサ実装時に語彙表を一本化する。
- **Container 段の仕様が空のまま残る**。四段のうち一段だけが「Phase 2 で決める」であり、
  今の仕様書では対応表と接合面への参照しか書けない。

## 将来の変更想定

- **U12(外部世界との境界)**: 外部システムとの接続の方式(HTTP・MQTT・機器)・障害時の記述・省略の禁止の適用を決める。
  本 ADR の `external` / `depends` / `expose` がその宣言の受け皿になる。発見1の判定基準
  (独立に設計され、独立に壊れるか)を、その ADR で機械検証可能な形に落とせるかを検討する。
- **U14(プログラムの宣言)**: 「1プログラム = 1システム」の制限を外すかを決める。
  システムがシステムを含む形(C4 の System Landscape)を許すなら、contains の対象にシステムを加える。
  名前空間は system 単位が第一候補になる(ADR 0014 の E23 の範囲もこれに従う)。
- **Container 段の仕様(Phase 2)**: 配置の設定の形式、複製数、動作環境の監督の範囲。
  思考実験 04 の3ノード複製が最初の題材になる。
- **U8(図と実装の一致)**: Phase 3 の抽出器は本 ADR の四段をそのまま図の段とする。
  ADR 0007 が留保した Structurizr / Mermaid C4 エクスポートは、語彙が一致したため写像がより直接になる。
- **第三層のブロックの名前**: 決定5は `body` を据え置いたが、Phase 1 のパーサ実装で
  書き手の名前との衝突が実際に問題になったら、論点5 を B3(`impl`)で開き直す。
  `code` は理念と衝突するため、この再検討の対象には入れない。
- **思考実験 08**: 本 ADR の机上検証は既存の思考実験への後付けである。
  新しい題材(外部システムを複数持ち、システム境界の判断が難しい系)で system 宣言を一から書き、
  発見1の判定基準を試す。

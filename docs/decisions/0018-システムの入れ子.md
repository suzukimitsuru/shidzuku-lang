# 0018: システムの入れ子 — C4 の System Landscape を許容する

- 日付: 2026-08-29
- 状態: 提案
- 関連課題: U14(プログラムの宣言)の一部。関連: U18(システムコンテキスト)・U12(外部世界との境界)・U8(図と実装の一致)・U17(名前空間)
- 改訂する決定: ADR 0015(決定2 の「当面 1プログラム = 1システム」、決定7 の E11〜E13 = E0015-1〜E0015-3、机上検証の発見1「外部システムの判定基準」)

## 背景(なぜ決める必要があるか)

ADR 0015 は Context 段に `system` 宣言を置き、その最後に条件を一つ付けた。

> 当面 **1プログラム = 1システム**とする。複数システムの連携(システムがシステムを含む/並ぶ形)は U14 に委ねる。
> 他の Shidzuku システムは、当面 `external` として外に置く。

この制限を外す必要が、三つの所から出ている。

### 1. C4 の段が一つ足りていない

C4 モデルは System Context の上に **System Landscape**(ある範囲の中に複数のソフトウェアシステムが並ぶ図)を持つ。
ADR 0015 は四段(Context / Container / Component / Code)を取り込んだが、Landscape は取り込まなかった。
結果、Shidzuku で書ける最大の単位は「1つのシステム」であり、**システムが複数ある世界を記述できない**。

C4 において Landscape は五段目ではない。同じモデルを一段引いて眺めた図であり、
System Context 図の「外部システム」の箱の中身を開いたものである。**倍率の話であって、段の話ではない。**

### 2. 外に置くしかない — 書き手に選択肢が無い

ADR 0015 決定2 の但し書き「他の Shidzuku システムは、当面 `external` として外に置く」は、
**外に置く事を強制している**。自分たちが設計し、自分たちが Shidzuku で書いている系であっても、
`external` にしか書けない。

`external` に置いた系は、その intent(なぜその境界か)・contains(何が内側か)・障害境界が記述から消え、
説明文の散文に落ちる。それが**書き手の判断**であるなら何も問題は無い——外に置くと決めたのだから。
問題は、**判断する余地が無い**事である。内に入れたいと思っても入れられない。
**Shidzuku が最も嫌う「設計意図の喪失」(第0章 0.2)が、書き手の選択ではなく言語の都合で起きている。**

同じ制限は、ADR 0015 が置いた判定基準にも表れている。机上検証の発見1 は
「その相手が独立に設計され、独立に壊れるか」を external の判定基準としたが、
思考実験 08 の論点5 はそこで割れた——自社で運用する全文検索基盤は「独立に壊れる」が「独立に設計されない」。
**割れたのは基準の書き方が悪かったからではない**。二つの問いはどちらもコードの外にある事実を尋ねており、
機械検証できないものを規則の形にしたためである。

### 3. 大きな系を割る手段が、コンポーネントの分割しかない

現在、系が大きくなったときに取れる手は「コンポーネントを増やす」だけである。
20 個のコンポーネントが1つの `contains` に並ぶと、Context 図は箱が 20 個の一枚絵になり、
**読者によって必要な高度が違う**という C4 の前提(第0章 0.3)が最上段で崩れる。

ADR 0006 が「1コンポーネント = 隠す設計判断が1つ」としている以上、コンポーネントを粗くして数を減らす事はできない。
段を増やすのではなく、**同じ段を入れ子にする**のが C4 の答えである。

## 検討した選択肢

### 論点1: 複数のシステムをどう表すか

- **S-a: `contains` の対象にシステムを加える**(入れ子)。システムはコンポーネントとシステムの両方を含める。
- **S-b: 上位に `landscape` 宣言を足す**。システムを並べる新しい宣言を作り、段を5つにする。
- **S-c: 並置だけを許す**。`system` を複数書けるようにするが、入れ子にはしない。

### 論点2: 最上位(ルート)は1つか、複数か

- **R-1: ちょうど1つ**。プログラムの外周が一意に決まる。
- **R-2: 複数を許す**。C4 の Landscape 図がそのまま「複数のルートが並ぶ形」になる。

### 論点3: システムどうしの依存をどこに書くか

- **D-1: `depends` を拡張する**。相手が `external`(記述の外)か兄弟システム(記述の中)かで意味を分ける。
- **D-2: 兄弟システムも `external` に書く**。既存の語彙を一切変えない。
- **D-3: 新しい語(`uses` 等)を足す**。外部と内側を語で分ける。

### 論点4: 段を飛ばした参照を許すか

内側のシステムの中にあるコンポーネントを、外から直接 `depends` に書けるか。

- **P-1: 禁じる**。システム間の通信は必ず `expose` を通る。
- **P-2: 許す**。深い木で公開面を段ごとに転記する手間を避けられる。

### 論点5: 名前空間

入れ子を許すと、別のシステムに同じ名前のコンポーネントを置きたくなる。

- **N-1: 現状維持**(プログラム内で一意)。決めるのは U14。
- **N-2: 本 ADR で system 単位の名前空間を決める**。修飾名の構文も併せて決める。

### 論点6: 外部システムの判定基準をどうするか

ADR 0015 の机上検証の発見1 は「独立に設計され、独立に壊れるか」を判定基準として置いた。
思考実験 08 の論点5 でそれが割れている。

- **J-1: 基準を精緻にする**。連言か選言かを決め、境界例(自社運用の基盤)の答えを定める。
- **J-2: 基準を廃する**。`external` に書いた物が外部システムである、とし、それ以外の規則を持たない。
- **J-3: 記述で決める**。「Shidzuku で書いているか」を判定の手前に置き、書いていれば内側とする。

## 決定

### 1. `contains` の対象にシステムを加える(論点1: S-a)

システムは、コンポーネントとシステムの両方を含められる。

``` plaintext
system 通販 {
  intent     { ... }
  constraint {
    ...
    contains 注文管理, 商品カタログ検索      # いずれも system
  }
}

system 注文管理 {                            # 通販の内側にある
  intent     { ... }
  constraint {
    ...
    contains OrderIntake, Inventory, OrderStore   # いずれも component
  }
}
```

- **入れ子の深さに制限を設けない**。深さの上限は設計の問題であって言語の問題ではなく、
  「3段まで」のような数はどこから来たかを説明できない(ADR 0006 が粒度に数値基準を置かなかったのと同じ理由)。
- **循環は禁じる**。システムが直接・間接に自分自身を含む記述は E0018-1 とする。
- 一つの `contains` にコンポーネントとシステムが混在する事は許す。禁じる理由が無く、
  禁じると「システムを1つ足すために、隣のコンポーネントも全部システムで包む」という無意味な作業が生じる。

### 2. 段は増やさない。System Landscape は Context 段の倍率違いである

第0章 0.3 の四段の表は**変えない**。`system` の入れ子は、Context 段を一段引いて見た図であり、五段目ではない。

- C4 でも System Landscape は独立の段ではなく、Context 図の外側を描いた図である。
- 図(Phase 3)は、ルートから `contains` を1段掘るごとに Context 図を1枚出す。
  最上段の1枚が Landscape 図に当たる。**図の枚数が段の数ではない。**

### 3. ルートシステムはちょうど1つとする(論点2: R-1)

`contains` のどこにも現れないシステムを**ルート**と呼ぶ。ルートはちょうど1つとし、0個または2個以上は E0018-2 とする。

- プログラムの**外周**が一意に決まらないと、`contains` の網羅性(E0015-2)・名前の一意性・図の起点のいずれも定義できない。
- 「どこまでが自分たちの範囲か」も境界の判断であり、intent を書く価値がある。
  C4 の Landscape 図は「その企業/その部門」という枠を暗黙に持つが、**Shidzuku はそれを明示させる**。
  省略の禁止(ADR 0008)が段を跨いで効く形である。
- ルートも普通のシステムであり、二層で書き、五つの制約を全て書く。特別扱いの構文は無い。

### 4. 内側のシステムも二層。body は持たない

ADR 0015 決定2 のまま変えない。システムの実装は内側のコンポーネントそのものであり、
入れ子になっても「どのコンポーネントにも属さないコード」の置き場は作らない(四位一体。第0章 0.4)。

### 5. `depends` は external と兄弟システムを取る(論点3: D-1)

`depends` に書けるのは、次の二つだけとする。

| 相手                 | 意味                                                | 通信の記述     |
| -------------------- | --------------------------------------------------- | -------------- |
| `external` の名前    | 記述の外にある系。方式も障害時の記述も U12 で決める | まだ書けない   |
| 同じ親を持つシステム | 記述の中にある系。相手の `expose` を通る            | フローに書ける |

どちらでもない名前は E0018-3 とする。

**コンポーネントの `depends` にも兄弟システムを書ける**。段が違っても「呼ぶ相手」という意味は同じである(ADR 0015 決定2 の考え)。
コンポーネント `c` が兄弟システム `B` を呼ぶとき、

- `c` の `depends` に `B` を書く。
- `c` の親システム `A` の `depends` にも `B` を書く(A が B を呼ぶ、という事実は A の段でも真である)。
- 親に書かれていなければ E0018-3 とする。

これは思考実験 08 の論点3(外部を呼ぶのはコンポーネントなのに、コンポーネントの `depends` に書けない)の
**半分**を塞ぐ。相手が記述の中にあるときだけ塞がり、真に外にある `external` は U12 のままである。

`external` を親から継承させる案は採らない。各段の記述はそれ自体で読めなければならず(第0章 0.5)、
親を読まないと外部が分からない記述は、既定値の表を読ませるのと同じ種類の外部知識になる。
その代わり、内側のシステムの `external` は親の `external` にも現れる事を要求する(E0018-5)。
**外部は、段を上がっても外部である。**

### 6. システム間の通信は必ず `expose` を通る(論点4: P-1)

`depends` と `expose ... by` が指せるのは、**自分の `contains` に直接ある**コンポーネントまたはシステムだけである。
段を飛ばして内側のコンポーネントを指す記述は E0018-4 とする。

- 情報隠蔽はコンポーネントだけの性質ではない。システムも「内側を隠して境界で繋がる」物であり、
  段を飛ばせるなら、システムの境界は図の上の線でしかなくなる。
- 深い木では公開面が段ごとに転記される。この費用は承知の上で払う(「結果」の欠点を見よ)。

### 7. `expose ... by` の担い手はコンポーネントまたはシステム(E0015-3 の改訂)

``` plaintext
expose 注文受付(注文) -> 受注番号 | 受注不可   by 注文管理           # 担い手はシステム
expose 受注(注文) -> 受注番号 | 受注不可      by OrderIntake        # 担い手はコンポーネント
```

- 担い手が同じ公開面を自分の `expose` に持たなければ E0015-3 とする(検査の内容は変えない。対象にシステムが加わる)。
- 検査は**段ごとに1段だけ**行う。ルートの expose はその担い手の expose と、担い手の expose はさらにその担い手の expose と
  突き合わせる。C4 のズームと同じで、一度に見るのは1段である。

### 8. `contains` の網羅性(E0015-2 の改訂)

- プログラム内の全てのコンポーネントとシステムは、**ルートを除き、ちょうど1つの `contains` に属する**。
- 属さない、または二つ以上に属する場合は E0015-2 とする(検査の内容は変えない。対象にシステムが加わる)。

### 9. 名前空間は動かさない(論点5: N-1)

システム名・コンポーネント名は、引き続き**プログラム内で一意**とする(第1章 1.2、第2章 2.1)。

- 入れ子を許しても、この規則は破綻しない。厳しすぎるだけである。
- 修飾名の構文・名前の解決規則・E0014-3(混同可能な識別子)の範囲は、まとめて U14 で決める。
  本 ADR がそこへ踏み込むと、境界の話と名前の話が一つの決定に混ざる。
- ADR 0014 の採用の記録が書いた通り、**名前空間を system 単位にする案は本 ADR で現実味を持った**。
  入れ子が入ってから決める方が、判断の材料が多い。

### 10. 外部システムの判定基準を廃する(論点6: J-2)

**`external` に書いた物が外部システムである。それ以外の規則を持たない。**
ADR 0015 の机上検証の発見1(独立に設計され、独立に壊れるか)を取り消す。

- **Shidzuku で書いた系かどうかは関係しない**。自分たちが Shidzuku で設計している系でも、
  `external` に書けば外部システムであり、`contains` に書けば内側のシステムである。**どちらにするかは書き手が決める。**
- 外部の技術も同じである。RDB を `external` に書けば外部システムであり、書かなければ、それを隠すコンポーネントの
  intent の `why` に現れる。
- 同じ名前を `external` と `contains` の両方には置けない。外か内かは記述の上で一つに決まる。
- 言語が検査するのは**宣言どうしの整合**だけである(E0018-3・E0018-5・E0015-2)。
  「その相手が本当に外部か」は検査しない。

基準を持たないのは、基準を置いても**機械検証できない**からである。
「独立に設計されるか」「独立に壊れるか」は、コードの外にある事実を尋ねている。
検証できない判断を規則の形で書くと、規則があるのに守られたか分からないという状態になる。
これは ADR 0003 が拒否語リストを、ADR 0006 が粒度の機械検証を捨てたのと同じ立場である。
それらと違うのは、粒度の指針が**指針として残る**のに対し、ここは**指針も残さない**点である。
何を外に置くかは、粒度のように「良い/悪い」で語れる判断ではない。系の範囲そのものであり、
書き手が決めた事がそのまま正解である。理由は intent の `why` と `rejected` が引き受ける。

これは背景2 の裏返しでもある。ADR 0015 は「外に置くしかない」と「外かどうかは基準で決まる」を同時に課していた。
決定1 が前者を外し、本決定が後者を外す。**残るのは書き手の宣言だけである。**

W0018-1 を警告に留めるのは、**同じ問いがコンポーネントの `depends` にも立つ**のに、そちらに検査が無いためである。
「宣言したが使わない」の扱いは片方だけをエラーにできない。両方まとめてエラーへ上げるかは U12 と併せて決める。

### 12. 適用範囲

- 書き換える: `docs/spec/` の第0〜5章、`docs/PLAN.md`、`README.md`、`docs/roadmap.html`。
- 書き換えない: 本 ADR より前の ADR と思考実験。**書かれた時点の語で読めなければならない**(ADR 0014・0015 決定8 と同じ)。
- 思考実験 01・02・04・08 の `system` 宣言は、そのまま**ルートシステム**として読める。改訂は要らない。

## 机上検証 — 思考実験 01 と 08 を一つのプログラムに置く

思考実験 01(注文管理サービス)と思考実験 08(多言語商品カタログ検索)は、同じ通販事業の別の系として自然に並ぶ。
入れ子で書けるかを確かめる。

``` plaintext
system 通販 {                                          # ルート
  intent {
    why      "商品を探す所から注文の一生までを一つの範囲に収める。決済と機械翻訳の事業者は外に置き、
              この範囲は「客が商品に出会ってから受注番号を受け取るまで」を引き受ける"
    rejected option "商品カタログ検索を external に置く"
             reason "同じ設計者が同じ版で設計している。外に置くと、その系の intent と障害境界が記述から消え、
                     説明文の散文に落ちる"
    change   "配送追跡の追加を想定。external が1つ増える方向で吸収し、内側の二つの境界は変えない"
  }
  constraint {
    actor    買い物客 "商品を探し、注文する"
    actor    運用者 "索引の再構築と閾値の監視を行う"
    external 決済代行 "外部の事業者。注文管理が呼ぶ"
    external 翻訳サービス "外部の機械翻訳。商品カタログ検索が呼ぶ"
    depends  none
    expose   注文受付(注文) -> 受注番号 | 受注不可    by 注文管理
    expose   商品検索(検索語) -> 商品の列 | 該当なし  by 商品カタログ検索
    contains 注文管理, 商品カタログ検索
  }
}

system 商品カタログ検索 {
  intent { ... }
  constraint {
    actor    none
    external 翻訳サービス "外部の機械翻訳。TranslationStore が呼ぶ"
    depends  翻訳サービス
    expose   商品検索(検索語) -> 商品の列 | 該当なし   by SearchGate
    contains SearchGate, ProductIndex, TranslationStore, ProductStore
  }
}
```

### 発見1: 判定基準は、精緻にするのではなく無くなる

書き始めてすぐに、`商品カタログ検索` を内に入れるか外に置くかを決める必要が出た。
ADR 0015 の判定基準(独立に設計され、独立に壊れるか)を当てると、思考実験 08 の論点5 と同じ所で割れる——
同じ設計者が設計しているが、別プロセスで別に壊れる。

しかし、**書き手はもう決めている**。この例では「内に入れる」と決めて `contains` に書いた。
理由(同じ版で設計しており、外に置くと intent と障害境界が記述から消える)は、ルートの intent の `rejected` に書いた。
基準は、その判断を**後から正当化する**役にしか立っていない。

そこで基準そのものを捨てた(決定10)。`external` に書いた物が外部システムである。
「Shidzuku で書いているか」を判定の手前に置く案(論点6: J-3)も採らない——
Shidzuku で書いた系を `external` に置きたい場面(段階的な移行、別の設計者への委譲の予定)があり、
記述の形が書き手の判断を上書きしてしまう。

**論点5 は解決したのではなく、問い自体が消えた**。割れる基準が無ければ、割れようが無い。

### 発見2: 外部は段を上がっても外部である(E0018-5)

`翻訳サービス` は商品カタログ検索の external だが、通販の Context 図にも現れなければならない。
現れなければ、上段の図だけを見た読者は「この範囲は外に何も頼っていない」と読む。
外部の繰り上がりを検査として要求する必要が、この例で分かった(E0018-5)。

逆に **actor は繰り上げを要求しない**。内側の `actor none` は「このシステムを直接使う人は居ない」の意味であり、
通販の買い物客が SearchGate に届く事と矛盾しない。actor は検証しない宣言であり(ADR 0015 決定2)、その扱いを変えない。

### 発見3: ルートの intent が、これまで書く場所の無かった判断を受け取った

「商品カタログ検索を external に置く案を捨てた」は、**どの系にも属さない判断**である。
1プログラム = 1システムの時代には、この判断は README の散文にしか書けなかった。
ADR 0015 が system の intent を必須にした理由(境界の決定は検証不能な判断である)が、そのまま一段上でも成り立つ。

### 発見4: 論点3 の穴は、半分しか塞がらない

`注文管理` の中のコンポーネントが `決済代行`(external)を呼ぶ形は、依然として書けない。
`商品カタログ検索` を呼ぶ形(記述の中の相手)は書けるようになった。
**U12 に残るのは「記述の外にある相手」だけになった**——課題が縮んだのであって、消えたのではない。

### 発見5: 既存の思考実験は、改訂なしでルートとして読める

思考実験 01・02・04・08 の `system` 宣言は、`contains` にコンポーネントだけを並べた木の深さ1の形である。
ルートがちょうど1つという規則(決定3)を、そのまま満たしている。**入れ子は既存の記述の上位互換である。**

## 捨てたもの・理由

- **S-b(`landscape` 宣言を足す)**: 段が5つになる。C4 の Landscape は Context の倍率違いであって独立の段ではなく、
  段を足すと第0章 0.3 の「読者によって必要な高度が違う」四段の対応が崩れる。
  読み手は `system` と `landscape` の違いという外部知識を覚える事にもなる。
- **S-c(並置だけを許す)**: ルートが複数になり、プログラムの外周が決まらない。
  「どこまでが自分たちの範囲か」が言語の外(暗黙)に戻る。R-2 と同じ問題である。
- **R-2(ルート複数)**: 同上。加えて、`contains` の網羅性(E0015-2)が「どのルートにも属さないシステム」を
  検出できなくなる。ルートが1つなら、木に繋がっていない記述は必ず見つかる。
- **D-2(兄弟システムも `external` に書く)**: `external` は「記述の外」を意味する語である。
  記述の中にある系をそこへ書くと、E0018-5(外部の繰り上がり)も `contains` の網羅性も意味を失い、
  何より**背景2 の問題がそのまま残る**。
- **D-3(新しい語を足す)**: `depends` が既に「呼ぶ相手」を意味しており、相手が段を跨ぐかどうかは
  相手の側の性質である。同じ意味に二つ目の語を与えると、ADR 0015 が段を跨いで `depends` / `expose` を
  同じ語にした理由(同じ物が違う倍率で現れる)に逆らう。
- **P-2(段を飛ばした参照を許す)**: システムの境界が図の上の線になる。
  情報隠蔽が段を跨いで成り立つ事は、入れ子を許す前提そのものである。
- **N-2(名前空間を本 ADR で決める)**: 境界の決定と名前の決定が一つの ADR に混ざる。
  U14 は名前空間・修飾名・一意性の範囲をまとめて決める課題であり、そこへ半分だけ先に手を付けると、
  U14 の ADR が本 ADR を改訂する形になる(ADR 0015 が 0014 を改訂したのと同じ負債)。
- **J-1(判定基準を精緻にする)**: 連言か選言かを決めても、どちらの問いも**コードの外にある事実**を尋ねている。
  精緻にすればするほど、機械検証できない規則が長くなるだけである。
  境界例(自社運用の基盤)に答えを与えても、次の境界例で同じ事が起きる。基準の書き方の問題ではない。
- **J-3(「Shidzuku で書いているか」を判定の手前に置く)**: 記述の形が書き手の判断を上書きする。
  Shidzuku で書いた系を外に置きたい場面——段階的な移行、別の設計者への委譲の予定、意図的に境界を切りたい——が実在し、
  そこで「書いてあるなら内側である」と言われると、外に置くという判断そのものができなくなる。
  背景2 で外した「外に置くしかない」の裏返し(内に入れるしかない)を招く。
- **入れ子の深さに上限を設ける**: 数の根拠が無い。深すぎる木は粒度の問題(ADR 0006)であり、
  レビューが受け持つ。機械検証しない判断が段を上がっても残る事は、第2章 2.5 と同じ立場である。
- **内側のシステムに body を許す**: 四位一体の外にコードの置き場ができる(ADR 0015 決定2 と同じ理由)。

## 結果(利点と欠点)

### 利点

- **大きな系を段で割れる**。Context 図が箱 20 個の一枚絵になる事を、コンポーネントを粗くせずに避けられる。
- **外に置くか内に入れるかを、書き手が選べる**。ADR 0015 は外に置く事を強制していた(背景2)。
  内に入れれば intent・contains・障害境界が記述に残り、外に置けば図の外の箱になる。どちらも正当な判断である。
- **外部システムの判定基準が消えた**。`external` は宣言であり、機械検証できない規則を1つ減らした(決定10、発見1)。思考実験 08 の論点5 は、問い自体が無くなる。
- **論点3 の穴が半分塞がった**。記述の中の相手なら、どのコンポーネントが呼ぶかを書ける(発見4)。
- **C4 の Landscape 図が抽出できる**。ADR 0015 が四段を揃えた上に、倍率の自由が乗る。
- **既存の記述と互換である**。深さ1の木として、そのまま読める(発見5)。

### 欠点

- **書く量がさらに増える**。システムを1つ足すたびに intent(why・rejected・change)と五つの制約が要る。
  ADR 0015 の欠点(小さなプログラムほど前払いが重い)が、段の数だけ掛かる。
- **`external` が段の数だけ重複する**(決定5、E0018-5)。各段がそれ自体で読める事と引き換えである。
- **公開面が段ごとに転記される**(決定6)。深い木で同じ `expose` が何段も並ぶ。
  これは情報隠蔽の代価であり、コンポーネントの `expose` が既に払っているものと同じ種類である。
- **名前空間が未決のまま入れ子だけが入る**(決定9)。深い木で同名を使えない不便が、U14 まで残る。
- **W0018-1 が片側だけの検査になる**。同じ問いがコンポーネントの `depends` にも立つのに、そちらに検査が無い。

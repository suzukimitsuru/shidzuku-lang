# 0020: 暦の拡張 — 紀年法を書き手が宣言する

- 日付: 2026-08-29
- 状態: 提案
- 関連課題: U22(関連: U9・U12・U16・U13)
- 改訂: ADR 0019(基本型の体系)決定5 の「言語が持つ暦は算術暦だけとする」を改訂する。0019 の他の決定は1つも取り消さない

## 背景(なぜ決める必要があるか)

ADR 0019(提案)は `日付` に暦の欄を置き、言語が持つ暦をグレゴリオ暦とユリウス暦の2つに限った。理由はこう書かれている。

> **算術暦**(規則だけで定まる暦)に限る。(中略)元号は法令で決まり、イスラム暦は月の観測に依る。
> これらは**版が変わる表**であり、分散したノードで表が食い違えば同じ入力から違う結果が出る。

この理由そのものは正しい。しかし**退けた対象を取り違えている**(思考実験 11)。

- 退けるべきなのは「**言語が**表を持つ事」である。tzdata のように実行環境から表が来ると、ノードごとに版が違い得る。
- 退けた事になっているのは「表を要する暦を**書ける**事」である。**書き手がソースの中に表を書く**なら、表はプログラムの一部であり版は食い違わない。

ADR 0010 は既に同じ形の判断をしている。**インチの定義を言語は知らない。書き手が `単位 インチ : 長さ = メートル × 127/5000` と宣言する。**
暦にも同じ形が使える。

思考実験 11 で、和暦・仏暦・民国紀元・イスラム暦を書こうとして、暦が3つの種に割れる事が分かった。

| 種                               | 何を知れば日付が決まるか   | 例                                      |
| -------------------------------- | -------------------------- | --------------------------------------- |
| **算術暦**                       | 規則だけ                   | グレゴリオ暦・ユリウス暦                |
| **紀年法**(年の呼び方だけが違う) | 基準の暦 + **起点の表**    | 和暦(明治6年以降)・仏暦・民国紀元・皇紀 |
| **表暦**                         | 各月の長さの表、または観測 | ウンム・アルクラー暦・天保暦            |

**紀年法は、月日を一切変えない。** 変わるのは年の呼び方だけである。したがって必要な宣言は**改元日の一覧だけ**で足りる。

## 検討した選択肢

- **ADR 0019 のまま2つに限る**: 型は軽いが、和暦の帳票が書けない。日本の業務システムでは事実上必須である。
- **言語が元号表を持つ**: 書く量は最少だが、改元のたびに言語の更新が要り、実行環境の版でノードが食い違う。
- **書き手が紀年法を宣言する**: ADR 0010 の量と単位と同じ形。表がソースにあるため版は食い違わない。
- **書き手が任意の暦を宣言する(閏年の規則も月の長さも書ける)**: イスラム暦も書けるが、宣言の語彙が桁違いに複雑になる。
- **暦をテキストや直積で持ち、言語の型にしない**: 比較・日数差・曜日を書き手が全部実装する事になる。

## 決定

### 1. 暦を3つの種に分け、線は「表がどこから来るか」で引く

| 種     | 綴り   | 誰が持つか       | 換算の性質       |
| ------ | ------ | ---------------- | ---------------- |
| 算術暦 | —      | **言語**         | 厳密・全域       |
| 紀年法 | `eras` | **書き手が宣言** | 厳密・**部分的** |
| 表暦   | —      | **持たない**     | —                |

- 分ける基準は「表が要るか」ではない。**表がどこから来るか**である。
  ソースの中にある表はプログラムの一部であり、分散したノードで食い違わない。実行環境から来る表(tzdata・ウンム・アルクラー暦)は食い違う。
- **算術暦は言語が持つ**。現在はグレゴリオ暦とユリウス暦の2つ(ADR 0019 決定5。変えない)。
- **表暦は持たない**。書けない事を認める(下記「捨てたもの」)。

### 2. 紀年法の宣言

```plaintext
暦 <名前> : <基準の算術暦> の紀年法 {
  紀元 <名前> : <基準の暦の日付> から <年番号> 年
  ...
}
```

日本の元号(明治6年以降)。

```plaintext
暦 和暦 : グレゴリオ暦 の紀年法 {
  紀元 明治 : 1873-01-01 から 6 年
  紀元 大正 : 1912-07-30 から 1 年
  紀元 昭和 : 1926-12-25 から 1 年
  紀元 平成 : 1989-01-08 から 1 年
  紀元 令和 : 2019-05-01 から 1 年
}
```

起点が1つだけの紀年法も同じ形で書ける。

```plaintext
暦 仏暦       : グレゴリオ暦 の紀年法 { 紀元 仏滅紀元 : 0001-01-01 から 544 年 }
暦 民国紀元   : グレゴリオ暦 の紀年法 { 紀元 民国     : 1912-01-01 から 1 年 }
暦 皇紀       : グレゴリオ暦 の紀年法 { 紀元 神武天皇即位紀元 : 0001-01-01 から 661 年 }
```

規則は3つである。

- **月日は基準の暦とまったく同じ。** 紀年法が変えるのは年の呼び方だけである。
- **年番号は基準の暦の年が変わる所で 1 増える。** 昭和元年は 1926-12-25 から 12-31 までの7日間しかなく、翌 1927-01-01 が昭和2年である。
- **表の最初の起点より前は、その紀年法では呼べない**(決定4)。

`から <年番号> 年` は、**その紀元がその年番号から始まる**事を書く。和暦の `明治 : 1873-01-01 から 6 年` は、
1年目からではなく6年目から始まる表である——**明治5年以前は太陰太陽暦(天保暦)であり、月日がグレゴリオ暦と違うため紀年法では書けない**という事実を、宣言がそのまま表す。

### 3. 内部表現も演算も変わらない

- `日付` の内部表現は**エポック日からの `整数 日` のまま**である(ADR 0019 決定5)。紀年法は型情報のみであり、実行時の表現に現れない。
- したがって比較・`日数`・`曜日`・`日を足す` は**そのまま効く**。紀年法を使っても失うものが無い。
- 型としては `日付 和暦` であり、`日付 グレゴリオ暦` とは別の型である。取り違えは既存の型検査(ADR 0009 の E0009-1)が落とす。

### 4. 換算は厳密なまま、全域でなくなる

ADR 0019 決定5 は「暦の換算は常に厳密であり、往復は必ず一致する」と書いた。**紀年法を足すと後半に条件が付く。**

| 換算            | 厳密か(丸めが無いか) | 全域か                       |
| --------------- | -------------------- | ---------------------------- |
| 算術暦 ↔ 算術暦 | 厳密                 | 全域                         |
| 算術暦 ↔ 紀年法 | 厳密                 | **部分的**(表の外がある)     |
| 紀年法 ↔ 紀年法 | 厳密                 | **部分的**(両方の表の中のみ) |

```plaintext
換算(2026-08-29 グレゴリオ暦, 和暦)  ->  令和8年8月29日
換算(1500-01-01 グレゴリオ暦, 和暦)  ->  暦の外
```

- 紀年法が絡む `換算` の結果は**直和** `日付 <紀年法> | 暦の外` とする。ADR 0009 の「『無い』は直和で明示する」がそのまま効く。
- `暦の外` は**データとして正常な不在**であり、系の失敗ではない(思考実験 05 の 3.2-3 の切り分け)。
- **表の中では往復は一致する。** 厳密さ(丸めが起きない事)は一つも失わない。

### 5. 表がソースの中にある事が、この決定の根拠である

| 観点               | tzdata(時間帯)   | 紀年法の宣言                |
| ------------------ | ---------------- | --------------------------- |
| 表の出所           | 実行環境(外)     | **ソース(中)**              |
| ノード間の食い違い | 起き得る         | **起きない**                |
| 更新の仕方         | 実行環境の更新   | プログラムの変更            |
| 更新が見える所     | どこにも見えない | **差分・レビュー・W0003-2** |

**改元がプログラムの変更として見える事は、欠点ではなく利点である。** 新しい元号が来たら宣言を1行足す。
それは公開面の変更(W0003-2)であり、レビューを通り、版として記録される。分散したノードは同じソースから動くため、表は食い違わない。
ADR 0001(Raft)の前提は保たれる。

### 6. イスラム暦は紀年法では書けない

思考実験 11 の判定をそのまま決定に写す。

| イスラム暦の種類     | 定まり方                         | 本 ADR での扱い                              |
| -------------------- | -------------------------------- | -------------------------------------------- |
| タブラー暦法(算術)   | 30年周期に 11 回の閏年。規則だけ | **書けない**(紀年法ではない)。将来の検討対象 |
| ウンム・アルクラー暦 | メッカでの天文計算 + 一部観測    | **書けない**(版を持つ表)                     |
| 観測ベース           | 月の観測                         | **書けない**(表)                             |

- タブラー暦法は算術暦だが、**年の呼び方ではなく月の切れ目の規則が違う**。紀年法の宣言(起点の列挙)では表せない。
- さらに**閏年の配置に流派が複数ある**(30年周期の 2・5・7・10・13・16・18・21・24・26・29 年目とする形が最も広く使われるが、16 の代わりに 15 を採る形、イスマーイール派タイイブ派の形などがある)。
  規則は固定でも、**どの規則を採るかは書き手の判断**である。言語が1つを選べば他を使う系が書けなくなる。
  → 算術暦を書き手が宣言する仕組みは「将来の変更想定」に送る。
- ウンム・アルクラー暦と観測ベースは**版を持つ表**であり、tzdata と同じ理由で持たない。

### 7. 語彙の追補(ADR 0014)

| 語     | 綴り           | 備考                                       |
| ------ | -------------- | ------------------------------------------ |
| 紀年法 | `eras`         | 暦の宣言の種類                             |
| 紀元   | `era`          | 紀年法の区切り。改元日と開始の年番号を持つ |
| 暦の外 | `outside_eras` | 紀年法の表の外。`換算` の直和の区分        |
| から   | `from`         | 紀元の起点。`era 令和 : 2019-05-01 from 1` |

ADR 0019 決定8 の `暦`(`calendar`)・`グレゴリオ暦`(`gregorian`)・`ユリウス暦`(`julian`)・`換算`(`convert`)はそのまま使う。

### 8. 検証の追加(第3章 3.3)

出自は `0020` である。

| #       | 検査                                                                        | 段        |
| ------- | --------------------------------------------------------------------------- | --------- |
| E0020-1 | 紀年法の宣言の起点が単調増加でない、または同じ日を2つの紀元が起点にしている | Component |
| E0020-2 | 紀年法が絡む `換算` の結果を直和で受けていない(`暦の外` を扱っていない)     | Code      |
| E0020-3 | 紀年法の基準に、算術暦でない暦(別の紀年法)を書いている                      | Component |

- E0020-2 は ADR 0009 の直和の網羅性で落ちる場合が多いが、**紀年法の `換算` だけ直和になる**という非対称は読み手を驚かせるため、番号を立てて明示する。
- E0020-3 は紀年法の入れ子を禁じる。基準は算術暦に限る。表の解決が連鎖すると、`暦の外` が二重になり規則が増える。

| #       | 検査                                                                                               |
| ------- | -------------------------------------------------------------------------------------------------- |
| W0020-1 | 紀年法の表の最後の紀元に終わりが無く、現在より未来の日付を換算している(改元があれば呼び方が変わる) |

W0020-1 は「令和8年」と書いた値が、将来の改元で呼び方を失う事を告げる。**表が有限である事の帰結**であり、防ぐ手段は無い。

## 結果(利点と欠点)

### 利点

#### 和暦の帳票が書ける

日本の業務システムで、届出・登記・元号表記の帳票は避けて通れない。テキストで持てば ADR 0013 決定4 に当たって年を取り出せず、
直積で持てば比較・日数差・曜日を書き手が全部実装する事になる。**紀年法を宣言すれば、`日付` の性質を一つも失わずに書ける。**

#### 失うものが無い

内部表現は日番号のままであり、紀年法は型情報のみである。実行時コストはゼロ、比較・`日数`・`曜日`・`日を足す` はそのまま効く。
ADR 0010 の単位が「型に載せても実行時コストがゼロ」だったのと同じ性質である。

#### 表の版の問題が構造から消える

表がソースの中にあるため、ノード間で食い違わない。**改元は差分に現れ、レビューを通り、版として記録される。**
tzdata が抱える問題(どこにも見えない更新)が、そもそも起きない。

#### 和暦の断絶が宣言に現れる

`紀元 明治 : 1873-01-01 から 6 年` は、**明治6年から始まる表**である。
「明治元年から書ける」と誤解する余地が無く、明治5年以前が別の暦(天保暦)である事が読んで分かる。
言語が元号表を持つ設計では、この断絶はどこにも書かれない。

#### 3つの種の線が、他の判断と同じ形になる

「表がどこから来るか」という線は、ADR 0019 がうるう秒を退けた理由・ADR 0013 が照合キーの永続化を禁じた理由と同じである。
**版が外から来る知識は、合意の対象になる場所に置かない。** 一貫した規則が1本増えるのではなく、既にある規則が暦にも適用される。

### 欠点

#### 換算が全域でなくなる

- ADR 0019 の「暦の換算は常に厳密で、往復は必ず一致する」が弱まる。**表の中では**という条件が付く。
- 紀年法が絡む `換算` だけ直和になり、算術暦どうしの `換算` と形が違う。**同じ語で結果の形が違う**事は読み手の負担になる(E0020-2 で明示する)。

#### 書く量が増える

- 和暦を使う系は、元号表を自分で書く。5行だが、**間違えれば静かに間違う**——1926-12-25 を 1926-12-26 と書いても、コンパイラは気付かない。
- 表の正しさは言語の管轄外であり、ADR 0010 の換算比(インチの定義)と同じ立場である。

#### 改元でプログラムが変わる

- 新しい元号が来たら宣言を足し、再配備する。**言語が表を持つ設計より手間が多い。**
- 永続化済みの `日付 和暦` の読み方は変わらないが、新しい元号の値を古い版のプログラムが読めない(U16 の版の混在)。
- W0020-1 は警告を出すが、**未来の日付を和暦で持つ事そのものを防げない**。

#### イスラム暦は依然として書けない

- タブラー暦法は算術だが紀年法ではないため、本 ADR の仕組みでは書けない。閏年の配置に流派があるため、言語が1つを選ぶ事もできない。
- ウンム・アルクラー暦と観測ベースは版を持つ表であり、持たない。**イスラム圏の暦を必要とする系は、この言語では書けない。**
- 太陰太陽暦(天保暦・中国暦・ヘブライ暦)も同じである。**月の切れ目が規則で決まらない暦は、すべて書けない。**

### 総括 — 何と引き換えに何を得るか

**表を、言語からソースへ移す。**

ADR 0019 は「版が変わる表を持つ暦は書けない」とした。本 ADR はその判断を否定しない。**表の置き場所を変える**。

| ADR 0019                 | 本 ADR                                       |
| ------------------------ | -------------------------------------------- |
| 表を要する暦は書けない   | 表がソースに書ける暦は書ける                 |
| 版の食い違いを避けるため | 版の食い違いは、表がソースにあれば起きない   |
| 言語が知っている暦だけ   | 言語が知らない暦を、書き手が名前を付けて置く |

これは ADR 0010 が量と単位で採った形そのものである。**言語はインチを知らないが、インチを書ける。**
暦も同じで、言語は令和を知らないが、令和を書ける。

## 捨てたもの・理由

- **ADR 0019 のまま暦を2つに限る案**: 日本の業務システムで和暦の帳票が書けない。
  テキストで持てば ADR 0013 決定4(部分取得の禁止)に当たり、直積で持てば `日付` の性質(全順序・日数差・曜日)を全部失う。
- **言語が元号表を持つ案**: 改元のたびに言語の更新が要る。実行環境の版でノードが食い違い、ADR 0001 の前提が壊れる。
  さらに和暦の断絶(明治5年以前が別の暦である事)がどこにも書かれない。
- **書き手が任意の暦を宣言できる案(閏年の規則・月の長さも書ける)**: イスラム暦も太陰太陽暦も書けるが、宣言の語彙が桁違いに複雑になる。
  紀年法は「起点の列挙」だけで済むのに対し、月の切れ目を書く語彙は暦ごとに形が違う。**必要が確認されるまで置かない**(ADR 0009 が継承と型引数を退けたのと同じ判断)。
- **紀年法の基準に別の紀年法を書ける案**: 表の解決が連鎖し、`暦の外` が二重になる。基準は算術暦に限る(E0020-3)。
- **`暦の外` を失敗にする案**: データとして正常な不在であり、系の失敗ではない(思考実験 05 の 3.2-3)。直和で受ける。
- **紀年法の表に終わりを書かせる案(`紀元 令和 : 2019-05-01 から 1 年、2026-12-31 まで`)**: 現在の元号に終わりは無い。
  書かせると嘘の日付を書く事になる。W0020-1 の警告で扱う。
- **タブラー暦法のイスラム暦を言語が算術暦として持つ案**: 閏年の配置に流派が複数あり、言語が1つを選べば他を使う系が書けなくなる。
  どの規則を採るかは書き手の判断である。
- **ウンム・アルクラー暦の表をソースに書き写す案**: 形の上は書けるが、100 年分の月の長さを人が書き写す事になり、間違いが静かに混ざる。
  さらに表は毎年更新される。**書けないと認める方を採る。**

## 将来の変更想定

- **算術暦を書き手が宣言する仕組み**。閏年の配置と月の長さを書けるようにすれば、タブラー暦法のイスラム暦が書ける。
  紀年法(起点の列挙)とは別の語彙になる。必要が確認されてから設計する。
- **紀年法の表の外部化**。元号表を別ファイルに切り出す案は、**表がソースの中にある**という本 ADR の根拠を崩すため、
  切り出すとしても「ビルド時に取り込む」形に限る(実行時に読む形は採らない)。
- **改元への追随**(U16)。新しい元号を足した版と足していない版が同時に動く場合の扱い。永続化済みの値の読み方は変わらないが、
  新しい元号の値は古い版で読めない。ADR 0012 の記述子(H1)の版の規則と併せて決める。
- **ISO 週日付・序数日付**。いずれも算術暦であり、言語が持つ暦に足せる(ADR 0019 の将来の変更想定と同じ)。

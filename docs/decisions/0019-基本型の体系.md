# 0019: 基本型の体系 — 整数・論理・時間の型

- 日付: 2026-08-29
- 状態: 提案
- 関連課題: U22(関連: U9・U15・U12・U13・U20・U5)
- 改訂: ADR 0009(データ型の記述)の基本型の一覧を確定する。ADR 0010 の量の体系に `量 時間` を加え、ADR 0017 の E0017-1 の対象に整数を加える。ADR 0014 の基本型の語彙表を差し替える

## 背景(なぜ決める必要があるか)

束 B(ADR 0009・0010・0017)は基本型を確定するための3本である。しかし**確定しているのは数値だけ**である。

ADR 0009 の決定は、基本型を本文1行で挙げているにすぎない。

> 基本型として文字列・数値・真偽・時刻・期間・時間量を言語が持つ(時間3種は期限宣言と共通)。

思考実験 05 が検証したのは**構成子**(直積・直和・識別子型・列)であって、基本型ではない。
その後、文字列は ADR 0013 が作り直し(思考実験 08 が新題材で裏付けた)、数値は ADR 0010・0017 が思考実験 06・07 を伴って作り直した。
**残る真偽・時刻・期間・時間量は、一度も検証されていない。** ADR 0014 の語彙表に `bool`・`instant`・`period`・`duration` という綴りだけが載っており、中身——基準時刻・分解能・壁時計か単調時計か・暦・うるう秒——は無い。

さらに、一覧には**整数が無い**。

思考実験 09 で、8実験に現れた数値以外の値を横断で書き下ろし、`instant` が既存の体系で何を指すかを調べた。

- 真偽は8実験の公開面に**一度も現れなかった**。「有無」「可否」「成否」はすべて名前の付いた直和で書かれている。しかし body の条件式には必ず要る。
- 整数に当たる値は3か所に現れた(数量・版・添字)。`実数` は 19 桁の値(ナノ秒の時点・64 ビットの識別子)を壊し、`十進数(19.0)` は 8 バイトで足りる値に 16 バイトを払う。
- `Instant` は体系によって**正反対の意味**を持つ。Java は壁時計の一点、Rust は単調時計の読みである。
- ISO 8601・Java・Noda Time の `Period` は「暦上の量(1か月)」であり、ADR 0014 が書いた「時点と時点の間」ではない。後者は `Interval` と呼ばれる。
- ADR 0013 が文字列を廃した結果、**暦上の日(締め日・誕生日・保持期間)を書く場所が言語から消えている**。
- 時間量は本来「`量 時間`」の値であり、ADR 0010 自身が将来想定でそう書いている。

**ADR 0017 は数値型を軽くしたが、その副作用として 19 桁の値の置き場所を失った。** 時点をナノ秒で持つ設計は整数型を要求する。
基本型の一覧を確定しない限り、束 B のねじれ(層は仕様書に入ったが基本型は入っていない)は解けない。

## 検討した選択肢

### 整数

- **置かない(`十進数(i.0)` で代用)**: 型が増えないが、桁の宣言が全ての「数えた値」に掛かり、19 桁で記憶域が倍になる。
- **置かない(`実数` で代用)**: 最も軽いが、2^53 を超える整数が壊れる。ナノ秒の時点・64 ビットの識別子が書けない。
- **置く(機械の語長で1種)**: 桁を書かない完結した型。ADR 0017 が `実数` で採った論法と同じ。
- **置く(桁または範囲を宣言させる)**: `整数(範囲 0..999)`。値域が型に出るが、`十進数` の重さがそのまま戻る。
- **置く(任意精度)**: 桁溢れが無いが、所要記憶域が実行時まで決まらない(ADR 0010 が有理数を退けた理由と同じ)。

### 論理

- **持たない(2値の直和だけにする)**: 名前が必ず付くが、比較演算子の結果を受ける型が無くなり、条件式が書けない。
- **持ち、どこにでも書ける**: 他言語と同じ。`在庫あり: 真偽` の真が何を意味するかは型に現れない。
- **持つが、公開面と data に書けない**: 条件の値としてだけ存在させる。書き手は名前の付いた直和を宣言する事になる。

### 時点

- **壁時計の一点(Java の `Instant`)**: 記録・突き合わせに使える。単調でないため経過時間の測定には使えない。
- **単調時計の読み(Rust の `Instant`)**: 経過時間の測定に使える。ノードを跨いで意味を持たず、記録にも使えない。
- **両方を別の型として持つ**: 誤用は型で落ちるが、基本型が1つ増え、`state` に持てる型と持てない型の規則も要る。
- **時間帯付きの日時(`ZonedDateTime`)を基本型にする**: 表示に近いが、暦と時間帯の規則(版が変わる)が言語の中核に入る。

### 暦の日と日時

- **`日付` だけを置く**: 「毎日 09:00 開店」のような、日を持たない時計の読みが書けない。
- **`日付` と `時刻` を置き、日時は直積で書く**: 基本型が2つで済み、組の作り方は書き手が決める。
- **`日時`(時間帯を持たない `LocalDateTime`)を基本型にする**: 日常の記述は短くなるが、日だけ・時計の読みだけを別に置く事になり型が3つになる。
- **`日時`(時間帯を持つ `ZonedDateTime`)を基本型にする**: 表示に近いが、暦と時間帯の規則(版が変わる)が言語の中核に入る。

### 日付の範囲と紀元前

- **西暦1年から9999年まで**: 業務システムには足りるが、歴史・年代の記述が書けない。
- **紀元(BC / AD)の欄を別に持つ**: 人の読み方に近いが、年の比較と減算が欄をまたいで分岐する。
- **天文学的年番号(0 = 紀元前1年)で紀元前まで広げる**: 比較と減算が1つの整数の規則で済む。ISO 8601 と同じ数え方。
- **暦を複数持つ(ユリウス暦・和暦)**: 史料の日付をそのまま書けるが、改暦の時期が地域ごとに違い、言語が1つの答えを持てない。

### 暦の種類

- **先発グレゴリオ暦の1つに固定する**: 型が軽いが、1582 年より前のヨーロッパの史料をそのまま書けない。当時の日付は全てユリウス暦である。
- **暦を型の欄にする(`日付 <暦>`)**: 単位と同じ形。取り違えがコンパイル時に落ち、実行時コストはゼロ。
- **暦を値(基本型)にする**: 行ごとに暦が違うデータを書けるが、暦が型から読めず、取り違えが実行時まで残る。
- **表を要する暦(元号・イスラム暦)も言語が持つ**: 史料に近いが、表の版で結果が変わる。

### 時間帯

- **時間帯を型として持たない(U12 へ送る)**: ログの日時を他の時間帯で読み替える事が書けない。
- **`時間帯` を基本型に置き、時間帯付きの日時は(`時点`, `時間帯`)の直積で書く**: 読み替えが欄の差し替えになり、`時点` は動かない。
- **時間帯を `日付`・`時刻` の欄にする**: 暦と同じ形になるが、行ごとに時間帯が違う多地域のログが書けない。
- **時間帯付きの日時(`ZonedDateTime`)を基本型にする**: 表示に近いが、時間軸の値と表示の都合が同じ型に同居する。

### 期間・時間量

- **ADR 0009 のまま3つ(時刻・期間・時間量)を基本型に置く**: 綴りは決まっているが中身が無い。
- **期間を直積へ、時間量を `量 時間` へ寄せる**: 基本型が2つ減り、単位の検査が時間量に効く。

## 決定

### 1. 基本型の一覧を確定する

構成子(直積・直和・識別子型・列)は ADR 0009 のまま変えない。基本型は次の10 とする。

| 基本型     | 綴り      | 欄                 | 内容                                     | 出自     |
| ---------- | --------- | ------------------ | ---------------------------------------- | -------- |
| `論理`     | `bool`    | 無い               | 条件の値。body 内にのみ置ける(決定3)     | 本 ADR   |
| `整数`     | `int`     | 単位が**必須**     | 符号付き 64 ビット。刻みは常に 1(決定2)  | 本 ADR   |
| `実数`     | `real`    | 単位が**必須**     | IEEE 754 binary64                        | ADR 0017 |
| `十進数`   | `decimal` | 単位と桁が**必須** | 十進固定小数点                           | ADR 0010 |
| `テキスト` | `text`    | 無い               | 値としての自然言語。正準形を持たない     | ADR 0013 |
| `バイト列` | `bytes`   | 無い               | 不透明な媒体・外部表現                   | ADR 0013 |
| `時点`     | `instant` | 無い               | 壁時計の一点。UTC のエポック起点(決定4)  | 本 ADR   |
| `日付`     | `date`    | 暦が**必須**       | 暦上の日。紀元前から(決定5)              | 本 ADR   |
| `時刻`     | `clock`   | 無い               | 1日の中の時計の読み。日を持たない(決定5) | 本 ADR   |
| `時間帯`   | `zone`    | 無い               | どこの時計で読むか。IANA の地帯名(決定5) | 本 ADR   |

識別子型(`id`)は基本型ではなく**宣言の形**である(`data 受注番号 (id)`)。ADR 0009 のまま変えない。
**暦**(`グレゴリオ暦`・`ユリウス暦`)は型ではなく `日付` の**欄**である。単位が数値の欄であるのと同じ形であり、実行時の表現には現れない(決定5)。

一覧から外れるもの。

| ADR 0009 の基本型 | 本 ADR での扱い                                                        |
| ----------------- | ---------------------------------------------------------------------- |
| 文字列            | ADR 0013 が廃止済み(テキスト・バイト列へ)                              |
| 数値              | ADR 0010・0017 が `実数`・`十進数` へ。本 ADR が `整数` を足す         |
| 真偽              | `論理` に改名し、置き場所を body に限る(決定3)                         |
| 時刻              | 名前を2つに割る。`時点`(時間軸の点・決定4)と `時刻`(時計の読み・決定5) |
| 期間              | **基本型から外す**。直積で書く(決定6)                                  |
| 時間量            | **基本型から外す**。`量 時間` の値とする(決定6)                        |

### 2. 整数型を置く

```plaintext
整数 <単位 | 単位なし>

整数 単位なし        # 個数・回数・添字・長さ・版・連番
整数 ナノ秒          # 時間量(量 時間 を持つ)
```

- **符号付き 64 ビット2の補数**とする。範囲は `-9223372036854775808` 〜 `9223372036854775807`(19 桁)。
- **桁を書かない**。整数の刻みは常に 1 であり、宣言しても情報が増えない。決まっていないのは窓の幅だけであり、それは1つに固定する。
  ADR 0017 が `実数` について書いた「桁という欄を持たない完結した型である」がそのまま当たる。桁が無い事は E0008-1(必須宣言の欠落)ではない。
- **単位の欄は省略できない**。持たない事は `単位なし` と明示する(ADR 0010・0017 と同じ)。量と単位の検査(E0010-1・E0010-2・E0010-5)は整数にも載る。
- **符号は常に持つ**。符号なし整数は置かない(ADR 0010 の「符号の有無を選択にしない」と同じ判断)。
- **演算子は `+ - ×` の3つ**。`÷` は持たない。除算は ADR 0010 の `分ける(a, b)`(商と余りを同時に返す)だけとする。
  整数の `/` が切り捨てになる事は**宣言されていない丸め**であり、ADR 0010 が `÷` を置かなかった理由がそのまま当たる。
- **巻き戻らない**。加減乗の結果が範囲を出たら失敗とする(U13)。`分ける(a, 0)` も失敗である。
  検査は**演算ごと**に行う。`十進数` は中間の桁が自動で広がるため「値が名前を得る所」で足りたが、整数は 64 ビットで閉じており中間で広がる余地がないためである。
- **比較は全順序、等価は素直**。正準形が一意に定まるため、ADR 0013 決定3 の一般規則によりハッシュ可能である(識別子型の中身にも使える)。
- **列の添字・長さ・繰り返し回数は `整数 単位なし` に限る**(E0019-4)。

### 3. 論理型を置き、置き場所を body に限る

```plaintext
論理        # bool。値は 真 と 偽 の2つ
```

- 演算は `かつ`・`または`・`でない`(`and`・`or`・`not`)と、比較演算子の結果である。
- **`data` のフィールド・公開面(`expose`)の引数と応答・`flow` の内容・`state` に論理型は書けない**(E0019-1)。
  そこには**名前の付いた直和**を書く。

```plaintext
expose 在庫確認(品目ID) -> 真偽                  # 書けない。真が何を意味するかが型に無い
expose 在庫確認(品目ID) -> 在庫あり | 在庫なし   # これを書く
```

- 理由は ADR 0009 の「『無い』は直和で明示する」と同じである。**2値の直和は実行時表現が同じで、失うものが1つも無い。** 得るのは名前だけであり、名前は公開面の語彙の全てである。
- 思考実験 09 の裏付け: 8実験の公開面に真偽は一度も現れず、「有無」「可否」「成否」はすべて名前の付いた直和で書かれていた(`受注(受注番号) | 受注不可(理由)`、`見つかった(値) | なし`、`済 | 訳なし`)。
- ADR 0013 が「テキストを制御フローの条件に使う事」を禁じた規則と対になる。テキストは条件になれず、論理はデータになれない。
- 制約の語彙(`idempotent`・`durable` 等)は宣言であって値ではないため、この規則の対象外である。
- **3値論理は無い**。null を持たないため(ADR 0009)、「不明」は直和で書く。
- 型名は ADR 0009 の「真偽」から `論理` に改める。「真偽」は値(真・偽)の名であり、型の役割——条件の値——を表すのは「論理」である。綴り `bool`(ADR 0014)は変えない。

### 4. `時点` は壁時計の一点とする

```plaintext
時点        # instant
```

- **UTC のエポック(1970-01-01T00:00:00Z)を原点とする時間軸上の一点**とする。Java の `java.time.Instant` と同じ立場であり、Rust の `std::time::Instant`(単調時計)とは別物である。
- **内部表現はエポックからの整数ナノ秒**(`整数 ナノ秒`)。表せる範囲は `1677-09-21T00:12:43.145224192Z` 〜 `2262-04-11T23:47:16.854775807Z` であり、範囲外は失敗とする(U13)。
- **暦・時間帯・書式を持たない**。年月日への分解と表示は、暦と時間帯を要する変換である(決定5)。
- **うるう秒を持たない。1 日は常に 86400 秒とする。**
  うるう秒表を持つと `時点 + 時間量` の結果が表の版に依存し、分散したノードで表が食い違えば同じ入力から違う状態へ遷移する。ADR 0001(Raft)の前提が壊れる。
  うるう秒は 6 か月前にしか決まらないため、未来の時点の演算も確定しない。Java の時間軸(Java Time-Scale)が UTC-SLS でうるう秒を薄めているのと同じ選択である。

演算は次の4つとする。

| 演算                       | 結果                          | 備考                     |
| -------------------------- | ----------------------------- | ------------------------ |
| `時点 + <量 時間 の値>`    | `時点`                        | 範囲外は失敗             |
| `時点 - <量 時間 の値>`    | `時点`                        | 範囲外は失敗             |
| `時点` どうしの比較        | `論理`                        | 記録された壁時計の値の順 |
| `隔たり(<始め>, <終わり>)` | 直和(`整数 ナノ秒` か `逆行`) | 減算演算子は置かない     |

- **`時点 - 時点` は演算として持たない**(E0019-2)。壁時計は巻き戻る(NTP の補正・仮想機の停止・時計の手動変更)ため、差が負になり得る。
  差が要る場面(受注から出荷までの所要時間)は `隔たり` で書き、`逆行` を直和で受ける。**黙って負の時間量が流れる事はない。**
- **期限(`deadline`)と経過時間の測定に `時点` を使えない**(E0019-2)。期限は `量 時間` の値でのみ宣言し、測るのは動作環境の仕事とする。
  第4章の `deadline <時間量>` は既にこの形であり、本決定はその**理由**を与える。
- **順序比較は「記録された壁時計の値の順」であって「起きた順」ではない。** 因果の順序が要るなら、単調増加の版(`整数 単位なし`)を使う(思考実験 04 の KVCore がこれである)。
- 現在の時点の取得が io の強度を持つ層に限られる事は、第2章 2.4 の既存規則(環境依存値は io 層が取得し値として pure 層へ注入する)がそのまま適用される。

### 5. 暦と時間帯 — `日付 <暦>`・`時刻`・`時間帯`

暦の側には値が4つある。**日**・**時計の読み**・**その組**・**どこの時計か**である。
日と時計の読みと時間帯を基本型に置き、組は書き手が直積で宣言する。そして**暦は型の欄**とする。

```plaintext
日付 <暦>     # date。暦上の日。暦の欄は省略できない
時刻          # clock。1日の中の時計の読み
時間帯        # zone。どこの時計で読むか

data 予約日時 { 日: 日付 グレゴリオ暦, 時: 時刻 }              # 日時は直積で書く
data ログ記録 { 起きた: 時点, 記録地: 時間帯, 内容: 事象 }     # ログの日時
```

#### 暦は型の欄とする — 単位と同じ形

`日付` は暦の欄を持ち、**省略できない**。ADR 0010 が数値に単位の欄を課したのと同じ形である。

| 数値(ADR 0010・0017)                 | 日付(本 ADR)                       |
| ------------------------------------ | ---------------------------------- |
| `実数 メートル`                      | `日付 グレゴリオ暦`                |
| 単位の欄は省略できない               | 暦の欄は省略できない               |
| 単位は型情報のみ。実行時コストはゼロ | 暦は型情報のみ。実行時コストはゼロ |
| `換算(値, 単位)` で単位を移す        | `換算(値, 暦)` で暦を移す          |
| 換算は丸めを伴い得る(E0010-3)        | **換算は常に厳密。丸めが無い**     |

- **暦の換算は単位の換算より強い性質を持つ。** 内部表現は暦に依らない日番号1つであり、暦は「その日番号を年月日でどう呼ぶか」だけを決める。
  したがって `換算` は無損失であり、**往復は必ず一致する**(単位換算の W0010-1・W0017-2 に当たる警告は要らない)。
- **比較と `日数` は暦をまたげる。** 日番号を比べるだけであり、丸めも曖昧さも無い(ADR 0010 の「比較は換算しない」と同じ)。
  `日を足す` も暦に依らない。**暦が効くのは、年月日を取り出す時と、読み書きする時だけ**である。
- 暦の取り違えは**新しい検査を要さない**。暦は型の一部であり、既存の型検査(ADR 0009 の E0009-1)がそのまま落とす。

#### 言語が持つ暦は算術暦だけとする

```plaintext
日付 グレゴリオ暦     # gregorian。先発グレゴリオ暦
日付 ユリウス暦       # julian。先発ユリウス暦
```

- **算術暦**(規則だけで定まる暦)に限る。グレゴリオ暦とユリウス暦はどちらも閏年の規則だけで決まり、**表を持たず、版を持たない**。
- **元号(和暦)・イスラム暦・ヘブライ暦は言語が持たない。** 元号は法令で決まり、イスラム暦は月の観測に依る。
  これらは**版が変わる表**であり、分散したノードで表が食い違えば同じ入力から違う結果が出る——うるう秒を持たない理由(決定4)・照合キーを永続化しない理由(ADR 0013)と同じである。
  表を要する暦は `format` の役割を持つ層が持つ(「将来の変更想定」に、書き手が暦を宣言する仕組みを残す)。
- ユリウス暦を持つ事で、**史料の日付をそのまま書ける**。1582 年より前のヨーロッパの記録、英国の 1752 年より前の記録は全てユリウス暦である。

  | 出来事                 | 史料の日付(`日付 ユリウス暦`) | `換算` 後(`日付 グレゴリオ暦`) |
  | ---------------------- | ----------------------------- | ------------------------------ |
  | カエサル暗殺           | `-0043-03-15`                 | `-0043-03-13`                  |
  | ヘイスティングズの戦い | `1066-10-14`                  | `1066-10-20`                   |
  | グレゴリオ暦改暦の前日 | `1582-10-04`                  | `1582-10-14`                   |
  | 英国の改暦の前日       | `1752-09-02`                  | `1752-09-13`                   |

  **どちらの欄も同じ日である。** 違うのは呼び方だけであり、換算に丸めは無い。
  暦の欄が型にあるため、`1582-10-05`(ユリウス暦では存在するがグレゴリオ暦の改暦で飛ばされた日)を取り違える事も起きない。

#### `日付` — 紀元前を含む

- **年は天文学的年番号の整数**とする。`0` が紀元前1年、`-1` が紀元前2年、`-9999` が紀元前10000年である。
  「紀元前か否か」の欄は持たない。**紀元(BC / AD)を別の欄にすると、年の大小比較と減算が欄をまたいで分岐する。**
  符号付きの1つの整数なら、比較も差も他の年と同じ規則で書ける。
- **範囲は日番号で定める。** エポック日(1970-01-01)から `-4371587` 日 〜 `2932896` 日とし、範囲外は失敗とする(U13)。
  グレゴリオ暦では `-9999-01-01` 〜 `9999-12-31`、ユリウス暦では `-9999-03-19` 〜 `9999-10-19` にあたる。
  文字の記録が残る歴史(最古の文字はおよそ紀元前3400年)を全て含み、`整数` の範囲を大きく下回る。
- 内部表現はエポック日からの `整数 日`。**暦は実行時の表現に現れない。**
- 表記は `<年>-<月>-<日> <暦>`。年は4桁以上で書き、負なら先頭に `-` を付ける(`-0043-03-15 ユリウス暦`)。
- 演算は `日を足す(日付, <整数 日>)`・比較・`日数(始め, 終わり) -> 整数 日`・`換算(日付, <暦>)` の4つとする。
  **月と年の加算は持たない。** 「1 か月後」は末日の扱い(1月31日の1か月後)を決めない限り書けず、その規則は言語ではなく設計判断である(「将来の変更想定」)。
- 置く理由は、**暦上の日を書く場所が言語から消えているから**である。ADR 0013 が文字列を廃したため、締め日・誕生日・保持期間ポリシー(思考実験 02 の change 欄)をテキストで書けば決定4(部分取得・分割の禁止)に当たり、年月日を取り出す事すらできない。識別子型で書けば順序も差も取れない。

#### `時刻` — 1日の中の時計の読み

- **1日の中の時計の読み**とする。`00:00:00.000000000` 〜 `23:59:59.999999999`。
- 内部表現は日の始まりからの `整数 ナノ秒`(0 以上 86400000000000 未満)。うるう秒を持たない(決定4)ため、1日は常に 86400 秒であり、この対応は例外なく一対一である。
- **日付・暦・時間帯を持たない。** 「毎日 09:00 開店」「締切は 17:00」は日を持たない値である。暦にも依らない(どの暦でも1日は同じ長さである)。
- 演算は比較と等価だけとする。**`時刻 + <量 時間 の値>` は持たない**(下記「暦の上に時間軸の加算を持ち込まない」)。
- 名前は ADR 0009 の「時刻」を引き継ぐ。0009 の「時刻」は時間軸上の点(本 ADR の `時点`)を指していたが、
  **`時点` と `時刻` はこの ADR で別の物になった**——`時点` は時間軸の点、`時刻` は時計の読みである。
  綴りは `clock` とする。`time` は量の名(`quantity time base 秒`・決定6)が取っている。

#### `時間帯` — ログの日時が「他の時間帯に変換できる」仕組み

ログ行の `2026-08-29T14:30:00+09:00` は、**2つの値が混ざった外部表現**である。

| 混ざっているもの     | Shidzuku での置き場所       |
| -------------------- | --------------------------- |
| いつ起きたか         | `時点`(時間帯に依らない)    |
| どこの時計で読んだか | `時間帯`(または オフセット) |

```plaintext
data ログ記録 { 起きた: 時点, 記録地: 時間帯, 内容: 事象 }
```

- **`時間帯`(zone)を基本型に置く。** 値は IANA tz database の地帯名(`Asia/Tokyo`・`UTC`)である。値の出所は動作環境であり、
  環境依存値として io の強度を持つ層が取得して注入する(第2章 2.4)。
- **他の時間帯への「変換」は、時間帯の欄を差し替えるだけである。`時点` は動かない。**
  同じログを東京で読んでもロンドンで読んでも、起きた瞬間は1つである。**変換ではなく読み替えである。**
- **時間帯は `日付`・`時刻` の欄にはしない。** 暦は設計判断(どの暦で語るか)だが、時間帯は実行時のデータ(どこで記録されたか)であり、
  同じ `data` の行ごとに違い得る。型の欄にすると多地域のログが書けなくなる。
- **オフセット(`+09:00`)は基本型にしない。** `量 時間` の値(`整数 分`)で書ける。
  ただしオフセットは**その1点の読みしか持たない**。夏時間の規則を持たないため、他の日時を読む事も、他の時間帯へ読み替える事もできない。
  記録するなら地帯名の方が情報が多い——これは指針であって禁止ではない。

#### 日時は基本型に置かない

- 日と時計の読みの組は**直積で書ける**。`期間` を基本型から外したのと同じ判断である(決定6)。
- 言語が `日時` を持つと、時間帯を持つのか持たないのかを言語が決める事になる。持たない日時(`LocalDateTime`)と持つ日時(`ZonedDateTime`)は別の型であり、
  Shidzuku では前者が(`日付`, `時刻`)、後者が(`時点`, `時間帯`)にあたる。**後者を1つの型にすると、時間軸の値と表示の都合が同じ型に同居する。**

#### 時間軸と暦のあいだの変換

| 変換                                   | 結果                                         | 失敗                             |
| -------------------------------------- | -------------------------------------------- | -------------------------------- |
| `暦で読む(<時点>, <時間帯>, <暦>)`     | (`日付 <暦>`, `時刻`)                        | なし(時間軸から暦へは常に決まる) |
| `時点にする(<日付>, <時刻>, <時間帯>)` | `時点 \| 存在しない \| 二度ある(時点, 時点)` | 範囲外                           |

- **向きによって性質が違う。** 時間軸から暦へは常に1つに決まるが、暦から時間軸へは夏時間で**存在しない時刻**(進む日)と**二度ある時刻**(戻る日)があり、直和で受ける。
  暦の読みだけを持つ言語は、この曖昧さを黙って1つに畳む。Shidzuku は畳まない。
- **変換は `boundary` または `format` の役割を持つ層でのみ書ける**(E0019-5)。`domain` は暦も時間帯も知らない。
- **tzdata の版依存は、合意の外に閉じ込められる。** 状態・記録・比較・順序は全て `時点` の上で行い、時間帯が要るのは暦の読みへ移す時だけである。
  版が食い違えば表示がずれるが、**複製された状態機械は割れない**(ADR 0001 の前提が保たれる)。これが `時点` と `時間帯` を分けた事の見返りである。
- **時間帯を用いて得た暦の読みを `state`・`data` に持つと警告(W0019-3)。** tzdata の版が変わると、後から計算し直した値と食い違う。
  記録は `時点` で持ち、暦の読みは読むたびに作るのが既定である。ADR 0013 が照合キーの永続化を禁じたのと同じ形であり、こちらは禁止ではなく警告とする——
  「その日の売上」のように、暦の読みそのものが業務上の値になる場合があるためである。

#### 暦の上に時間軸の加算を持ち込まない

**`日付` と `時刻` に `量 時間` を足す演算は持たない**(E0019-6)。時間の量を足す事は時間軸の上の操作であり、暦の上の操作ではない。

| 書きたい事               | 書き方                                                                          |
| ------------------------ | ------------------------------------------------------------------------------- |
| 翌日の同じ時刻(暦の操作) | `日を足す(日, 1)`。`時刻` はそのまま                                            |
| 3時間後(時間軸の操作)    | `時点にする` で時間軸へ移し、`時点 + 3 時` を計算し、必要なら `暦で読む` で戻す |

「2026-03-08 02:30 の3時間後」は、時間帯が分からなければ答えが決まらない(夏時間のある地域では 02:30 自体が存在しない日がある)。
暦の上で足せてしまう言語は、この曖昧さを黙って1つの答えに畳む。**Shidzuku は畳まず、時間帯を要求する変換の側へ寄せる。**

**`時点` と暦の型は別物である。** 「2026-08-29 が誕生日」はどの時間帯で見ても 2026-08-29 でなければならず、時間軸上の一点ではない。
時間帯を選ばされる型で誕生日を持つ言語は、その選択を書き手から隠している。

### 6. `時間量` は `量 時間` の値とし、`期間` は基本型から外す

ADR 0010 の将来想定(「時間量は本来『量 時間』の値であり、単位を持つ」)に答える。

```plaintext
量 時間 base 秒                      # 言語が最初から持つ量
unit ナノ秒     : 時間 = 秒 × 1/1000000000
unit ミリ秒     : 時間 = 秒 × 1/1000
unit 分         : 時間 = 秒 × 60
unit 時         : 時間 = 秒 × 3600
unit 日         : 時間 = 秒 × 86400
```

- **`時間量` という基本型は置かない**。時間の長さは `整数 ミリ秒`・`実数 秒`・`十進数(3.3) 秒` のように、数値型と単位で書く。表現は書き手が選ぶ。
- 得るものは単位の検査である。ミリ秒と秒の取り違えが E0010-1 で落ちる。ADR 0010 の換算の規則(有理数比・連鎖換算の禁止・往復の非一致)もそのまま効く。
- **「月」「年」は単位にしない。** 1 か月は 28〜31 日であり、固定の比を持たない。暦上の量は `日付` の上の操作であって、時間の量ではない(Noda Time の `Period` と `Duration` の区別と同じ)。
- `deadline` の欄は「`量 時間` を持つ数値」を受ける。第4章の `deadline <時間量>` は `deadline 200 ミリ秒` と読み替える。
- **`期間` を基本型から外す。** 時点と時点の間は直積で書ける。

```plaintext
data 集約区間 { 始まり: 時点, 終わり: 時点 }
```

  基本型として置くと、開区間か閉区間かを言語が決める事になり、選択が1つ増える。
  併せて、**区間を指す語に `period` の綴りを使わない**。ISO 8601・Java・Noda Time の `Period` は「暦上の量」であり、意味が逆になる。

### 7. 3つの数値型は暗黙に混ざらない

ADR 0017 の「2つの型は暗黙に混ざらない」を、整数を含む3つへ広げる。

| 変換          | 語彙                                 | 丸めの宣言             | 失敗           |
| ------------- | ------------------------------------ | ---------------------- | -------------- |
| 整数 → 実数   | `近似する(値)`                       | 不要(最近接偶数)       | なし(W0019-1)  |
| 整数 → 十進数 | `収める(値, 十進数(i.f))`            | 不要(原理的に起きない) | 整数部の桁溢れ |
| 実数 → 整数   | `丸める(値, 整数, 丸め <方式>)`      | 必須                   | 範囲外         |
| 十進数 → 整数 | `丸める(値, 整数, 丸め <方式>)`      | 必須                   | 範囲外         |
| 十進数 → 実数 | `近似する(値)`                       | 不要                   | 桁溢れ時のみ   |
| 実数 → 十進数 | `厳密にする(値, 十進数(桁), 丸め …)` | 必須                   | 整数部の桁溢れ |

- 語彙は ADR 0010(`収める`・`丸める`)と ADR 0017(`近似する`・`厳密にする`)を使い回す。新しい語は増やさない。
- **変換の前後で単位は保たれる。** 量の検査は変換を跨いで効く。
- 明示の変換なしに混ざった式はコンパイル時エラー(E0019-3。ADR 0017 の E0017-1 を整数へ広げる)。

使い分けの指針(ADR 0017 の表を改訂する)。判断の基準は「**その値を、数えたのか・刻みを決めたのか・測ったのか**」である。

| 数えた(→ `整数`)             | 刻みを決めた(→ `十進数`) | 測った・計算で作った(→ `実数`) |
| ---------------------------- | ------------------------ | ------------------------------ |
| 個数・注文数・在庫数・回数   | 金額・単価・手数料       | 距離・質量・温度・電圧         |
| 列の添字・長さ・繰り返し回数 | 税率・利率・割引率       | 座標・角度・速度               |
| 版・連番・世代番号           | 按分の結果・帳簿の値     | 平均・分散・標準偏差           |
| 時間の量(ナノ秒・ミリ秒)     | 会計・請求の値           | 確率・尤度・スコア             |

ADR 0017 の表は「在庫数・注文数」を `十進数` 側に置いていた。整数を置いたため `整数` へ移す。按分の**結果**(1 円を分けた値)は `十進数` のままである。

### 8. 語彙の追補(ADR 0014)

ADR 0014 決定7 の基本型の表を、次に差し替える。

| 語       | 綴り      | 備考                                             |
| -------- | --------- | ------------------------------------------------ |
| 論理     | `bool`    | 綴りは変えない。日本語の表記を「真偽」から改める |
| 整数     | `int`     | `int unitless`・`int ナノ秒`                     |
| 実数     | `real`    | ADR 0017                                         |
| 十進数   | `decimal` | ADR 0010・0017                                   |
| テキスト | `text`    | ADR 0013                                         |
| バイト列 | `bytes`   | ADR 0013                                         |
| 時点     | `instant` | 壁時計の一点。中身は決定4                        |
| 日付     | `date`    | 暦上の日。紀元前から。新設                       |
| 時刻     | `clock`   | 時計の読み。`time` は量の名が取っている。新設    |
| 時間帯   | `zone`    | IANA の地帯名。新設                              |
| 識別子   | `id`      | 宣言の形。ADR 0009                               |
| 列       | `list`    | ADR 0009                                         |

表から外す語。

| 外す語 | 綴り       | 理由                                            |
| ------ | ---------- | ----------------------------------------------- |
| 期間   | `period`   | 基本型から外す(決定6)。意味が既存体系と逆になる |
| 時間量 | `duration` | `量 時間` の値とする(決定6)                     |

追加する語。

| 語           | 綴り          | 備考                                          |
| ------------ | ------------- | --------------------------------------------- |
| かつ         | `and`         | 論理積                                        |
| または       | `or`          | 論理和                                        |
| でない       | `not`         | 否定                                          |
| 真           | `true`        | 論理の値                                      |
| 偽           | `false`       | 論理の値                                      |
| 隔たり       | `between`     | 時点どうしの差。結果は直和                    |
| 逆行         | `backwards`   | `隔たり` の直和の区分(終わりが始めより前)     |
| 日を足す     | `add_days`    | 日付の加算                                    |
| 日数         | `days`        | 日付どうしの差                                |
| 暦           | `calendar`    | `日付` の欄。単位が数値の欄であるのと同じ形   |
| グレゴリオ暦 | `gregorian`   | 先発グレゴリオ暦                              |
| ユリウス暦   | `julian`      | 先発ユリウス暦                                |
| 暦で読む     | `to_calendar` | 時点 + 時間帯 + 暦 → (日付, 時刻)             |
| 時点にする   | `to_instant`  | (日付, 時刻) + 時間帯 → 時点。結果は直和      |
| 存在しない   | `nonexistent` | `時点にする` の直和の区分(夏時間で進む日)     |
| 二度ある     | `ambiguous`   | `時点にする` の直和の区分(夏時間で戻る日)     |
| 時間         | `time`        | `quantity time base 秒`。言語が最初から持つ量 |

### 9. 検証の追加(第3章 3.3)

検証番号は ADR 0016 の `E<出自>-<連番>` 形式で書く。本 ADR が新設する検査の出自は `0019` である。

| #       | 検査                                                                                       | 段        |
| ------- | ------------------------------------------------------------------------------------------ | --------- |
| E0019-1 | 論理型が `data` のフィールド・公開面・`flow` の内容・`state` に現れる                      | Component |
| E0019-2 | `時点` どうしの減算、または `deadline`・経過時間の測定に `時点` を使う                     | 両段      |
| E0019-3 | 整数と他の数値型(`実数`・`十進数`)が明示の変換なしに混ざる(E0017-1 を広げる)               | Code      |
| E0019-4 | 列の添字・長さ・繰り返し回数に `整数 単位なし` 以外を使う                                  | Code      |
| E0019-5 | 暦・時間帯を要する変換(`暦で読む`・`時点にする`)が `boundary`・`format` 以外の役割に現れる | Code      |
| E0019-6 | 暦の値(`日付`・`時刻`)に `量 時間` を足す(時間軸の加算は `時点` で行う)                    | Code      |

| #       | 検査                                                                                           |
| ------- | ---------------------------------------------------------------------------------------------- |
| W0019-1 | 19 桁を超え得る整数を `近似する` で `実数` にしている(1 の刻みが失われる)                      |
| W0019-2 | `時点` と暦の値(`日付`・`時刻`)のあいだを往復変換している(時間帯の曖昧さで一致しない)          |
| W0019-3 | 時間帯を用いて得た暦の読みを `state` または `data` に持っている(tzdata の版が変わると食い違う) |

実行時の失敗(U13 で体系を定める)は4つである。

- 整数の加減乗が表せる範囲を出る
- `分ける(a, 0)`(0 除算)
- `時点` が表せる範囲(1677〜2262 年)を出る
- `日付` が表せる範囲(紀元前10000年〜西暦9999年)を出る

E0008-1(必須宣言の欠落)の対象は「型名・`整数` と `実数` と `十進数` の単位の欄・`十進数` の桁」である。
E0008-1 の対象には **`日付` の暦の欄**も含む(単位の欄と同じ)。
`整数` に桁が無い事、`論理`・`時点`・`時刻`・`時間帯` に単位の欄が無い事は E0008-1 ではない(ADR 0017 が `実数` の桁について書いた規則と同じ)。

### 10. 束 B の3本への改訂

| ADR  | 改訂する箇所                                                                                                                           |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 0009 | 基本型の一覧を決定1 の10 に差し替える。「真偽・時刻・期間・時間量」の行が消え、`論理`・`整数`・`時点`・`日付`・`時刻`・`時間帯` が入る |
| 0010 | 量の体系に `量 時間` を加える(決定6)。`収める`・`丸める` の対象に `整数` を加える(決定7)。`換算` の対象に `日付` の暦を加える(決定5)   |
| 0017 | E0017-1 を E0019-3 が広げる(整数を含む)。使い分けの指針の表を決定7 の3列に差し替える                                                   |
| 0014 | 決定7 の基本型の表を決定8 に差し替える。`period`・`duration` を外し、`int`・`date`・`clock`・`zone` と暦・論理の語を加える             |

**ADR 0010 と 0017 の決定は1つも取り消さない。** 十進固定小数点の規則も、strict IEEE の規則も、量と単位の検査も、そのまま生きる。
ADR 0009 についても、構成子(直積・直和・識別子型・列)・名前的型付け・トップレベルの `data` 宣言・「無い」は直和・`data` に intent を課さない、はいずれも変えない。変わるのは基本型の一覧だけである。

## 結果(利点と欠点)

### 利点

#### 束 B のねじれが解ける

基本型の一覧が確定するため、ADR 0013 が採用済みでありながら反映できていない基本型(テキスト・バイト列)と、
ADR 0014 の基本型の語彙が、まとめて仕様書に入る。第2章に「データの宣言」の節を立てる条件が揃う。

#### 数えた値が軽く書ける

| ADR 0017 までの書き方              | 本 ADR             |
| ---------------------------------- | ------------------ |
| `十進数(4.0) unitless`(注文の数量) | `整数 単位なし`    |
| `十進数(19.0) ナノ秒`(時点)        | `時点`(内部は整数) |
| `十進数(9.0) unitless`(版)         | `整数 単位なし`    |

桁の見積りが設計判断でない値から、桁の宣言が消える。ADR 0017 が `実数` で得た軽さを、数えた値にも広げる。

#### 19 桁が壊れない

`実数` は 53 ビット(≒15.95 桁)しか持たない。ナノ秒の時点(19 桁)・64 ビットの識別子・ハッシュ値は、
本 ADR より前は `十進数(19.0)`(16 バイト)しか置き場所が無かった。整数を置くと 8 バイトで厳密に持てる。

#### 真が何を意味するかが必ず名前を持つ

公開面から論理型が消えるため、`在庫確認 -> 真偽` のような「真の意味が型に無い」公開面が書けなくなる。
2値の直和は実行時表現が同じであり、**払うのは宣言1行、得るのは名前**である。

#### 時計の性質が型と検証に出る

- 壁時計の差で期限を測る誤り(Kleppmann が指摘した典型)は、E0019-2 でコンパイル時に落ちる。
- 時計の巻き戻りは `隔たり` の `逆行` として直和に現れる。黙って負の時間量が流れる事はない。
- うるう秒表を持たないため、`時点 + 時間量` は表の版に依存しない。分散したノードで結果が一致する(ADR 0001 の前提)。

#### 歴史と暦が書ける

- `日付` は紀元前10000年から西暦9999年まで(グレゴリオ暦の呼び方で)を表す。年は天文学的年番号の1つの整数であり、**紀元前と西暦をまたぐ比較と減算が分岐しない**。
- **暦が型の欄にあるため、史料の日付をそのまま書ける。** 1582 年より前のヨーロッパ、1752 年より前の英国の記録は全てユリウス暦であり、
  グレゴリオ暦に直してから書く必要が無い。直した値と直していない値の取り違えは、型検査が落とす。
- **暦の換算は無損失であり、往復が必ず一致する。** 内部表現は暦に依らない日番号1つであり、暦は呼び方だけを決めるためである。
  単位換算(ADR 0010)が丸めを伴い得るのに対し、暦の換算に丸めは無い。
- 日と時計の読みを分けたため、「毎日 09:00 開店」(日を持たない)と「2026-08-29」(時計の読みを持たない)を、どちらも余分な欄なしに書ける。

#### ログの日時が、他の時間帯で読み替えられる

- ログ行の `2026-08-29T14:30:00+09:00` は、**`時点`(いつ起きたか)と `時間帯`(どこの時計で読んだか)が混ざった外部表現**である。
  この2つを分けて持てば、他の時間帯への読み替えは**時間帯の欄の差し替え**になり、`時点` は動かない。**変換ではなく読み替えである。**
- **tzdata の版依存が、合意の外に閉じ込められる。** 状態・記録・比較・順序は全て `時点` の上で行い、時間帯が要るのは暦の読みへ移す時だけである(E0019-5)。
  版が食い違えば表示がずれるが、複製された状態機械は割れない(ADR 0001 の前提が保たれる)。
- **夏時間の曖昧さが直和で見える。** 暦から時間軸への変換は `存在しない`・`二度ある` を含む直和を返し、呼び手が扱う。黙って1つに畳まない。

#### 暦と時間帯に、新しい検査がほとんど要らなかった

- 暦の取り違えは既存の型検査(ADR 0009 の E0009-1)が落とす。暦は型の一部だからである。
- 暦の欄の欠落は E0008-1(必須宣言の欠落)である。単位の欄と同じ扱いで済む。
- 時間帯の誤用は E0019-5(役割の制限)と W0019-3(版依存の値の永続化)の2つだけで足りた。
  **既にある仕組み——単位の欄・役割・省略の禁止——に載せられたという事である。**

#### 基本型はほとんど増えていない

5つ足して(`整数`・`時点` の中身・`日付`・`時刻`・`時間帯`)2つ外す(`期間`・`時間量`)。
ADR 0009 の6つ(文字列・数値・真偽・時刻・期間・時間量)は、本 ADR の10(論理・整数・実数・十進数・テキスト・バイト列・時点・日付・時刻・時間帯)になる。
増えた4つは、文字列が2つに割れた分(テキスト・バイト列)と数値が3つに割れた分、そして時間の型が3つ(時刻・期間・時間量)から4つ(時点・日付・時刻・時間帯)になった分である。
**暦は型ではなく欄であり、数には入らない。**

### 欠点

#### 数値型が3つになる

- ADR 0017 が「型が2つになる」を欠点に挙げたものが、3つになる。選ぶ判断は全ての数値に発生する。
- 変換の語彙が6通りになる(決定7 の表)。往復の非一致(W0017-2)に加えて、19 桁の丸め(W0019-1)という落とし穴が増える。
- 公開面で型が食い違う組み合わせが増え、直す作業は書き手に来る。

#### 論理を公開面に書けない事は、必ず引っかかる

- 他言語からの移植で最初に当たる規則になる。`bool` を返す関数は珍しくない。
- 2値の直和を毎回宣言する手間がかかる。`在庫あり | 在庫なし` は `真偽` より長い。
- 「まだ名前が思いつかない」段階の記述が書けない。**それは意図的な摩擦である**が、摩擦である事は変わらない。

#### 時点の範囲が ±292 年

- 1677 年より前、2262 年より後の時点が書けない。歴史・長期の年金計算は `時点` では書けず、暦の型(`日付`・`時刻`)で書く事になる。
- 「1500 年のある瞬間」は `日付` と `時刻` の直積で書けるが、それは**暦と時計の読み**であって時間軸上の一点ではない。
  時間帯を与えて `時点` に直そうとすると範囲外で失敗する。

#### 言語が持つ暦は2つだけである

- 元号(和暦)・イスラム暦・ヘブライ暦は書けない。表(法令・観測)に依存し、版が変わるためである。
- 日本の系では和暦の表示が要る場面が多い。それは `format` の役割の層が持つ事になり、**言語の型検査は効かない**。
- 天文学的年番号(`0` = 紀元前1年)は人の読み方とずれる。表示の際に「紀元前」へ直すのも `format` の役割である。
- 先発暦であるため、**当時その暦が使われていなかった日付も書けてしまう**。`日付 グレゴリオ暦` の `1500-01-01` は、当時どこにも存在しない表記である。
  型は「どの規則で呼ぶか」を告げるだけであり、「当時そう呼ばれていたか」は保証しない。

#### 時間帯を持つと、版依存の知識が言語に入る

- tzdata は年に数回更新され、**過去のオフセットも遡って修正される事がある**。同じ `時点` と `時間帯` から得る暦の読みが、版によって変わり得る。
- 合意の外に閉じ込めたとはいえ(E0019-5)、表示・帳票・締め処理の結果は版に依存する。W0019-3 は警告であって禁止ではない。
- 時間帯の値そのもの(地帯名)は安定しているが、**廃止・改名される地帯もある**(`Asia/Calcutta` → `Asia/Kolkata`)。永続化した地帯名が将来解決できなくなり得る。

#### 日時に時間量を足せない

- `日付` と `時刻` の組に「3時間後」を足す記述が書けない(E0019-6)。時間帯を与えて `時点` へ移す必要がある。
- 時間帯が要らない場面(1つの地域に閉じた業務)でも同じ手間がかかる。**曖昧さが無い場合でも払う税**である。

#### うるう秒を持たない事の代償

- 天文・測地・時刻同期そのものを扱う系では正確でない。うるう秒の秒(23:59:60)を記録できない。
- UTC-SLS で薄めた時間軸は、うるう秒の当日に限り実際の UTC と最大 1 秒ずれる。

#### U12 に残る宿題

時間帯の型と変換は本 ADR で決めたが、**外部表現の解析**(ISO 8601 の文字列・Unix 秒・DB の `TIMESTAMP` を `時点` と `時間帯` に分解する事)と、
**tzdata をどう動作環境が供給するか**は U12(外部世界との境界)に残る。現在の時点・現在の時間帯を得る記述も同じである。

#### 整数の桁溢れ検査は実行時コストになる

演算ごとに検査するため、`十進数`(名前を得る所でのみ検査)より頻度が高い。
64 ビットの加減乗のオーバーフロー検出は多くの実行環境が命令を持つが、ゼロではない。

### 総括 — 何と引き換えに何を得るか

**型の名前が、値の出どころを告げる。**

ADR 0017 の総括は「型の名前と実際の性質を一致させる」だった。本 ADR はそれを数値以外へ広げる。

| 型       | 名前が告げている事                                                     |
| -------- | ---------------------------------------------------------------------- |
| `整数`   | 数えたものである。刻みは 1 であり、途中の値は無い                      |
| `実数`   | 近似である(ADR 0017)                                                   |
| `十進数` | 刻みを人が決めた(ADR 0010)                                             |
| `時点`   | 壁時計の読みである。巻き戻り得るし、経過時間には使えない               |
| `日付`   | 暦の上の日である。時間軸上の点ではなく、どの暦で呼ぶかは欄に書いてある |
| `時刻`   | 時計の読みである。どの日かは持たない                                   |
| `時間帯` | どこの時計で読むかである。いつ起きたかは持たない                       |
| `論理`   | 条件の値である。データの語彙ではない                                   |

黙って壊れる物——切り捨てられる整数除算、巻き戻る時計の差、意味の無い真、うるう秒表に依存する加算——は、
どれも型か検証で表に出す。**「運用で驚きがない」(第0章 0.5)は、値の出どころが型から読める事に帰着する。**

## 捨てたもの・理由

- **整数を置かず `十進数(i.0)` で代用する案**: 桁の宣言が全ての「数えた値」に掛かる。列の長さの上限を型に書く事になり、書いていない仕様が型に紛れ込む。19 桁で記憶域が倍になる(ADR 0010 の「19・39・77 桁の境目」)。
- **整数を置かず `実数` で代用する案**: 2^53 を超える整数が壊れる。ナノ秒の時点・64 ビットの識別子・ハッシュ値が書けない。ADR 0017 が主に使う型を `実数` にした事の副作用であり、整数はその穴を塞ぐ。
- **整数に桁または範囲を宣言させる案(`整数(範囲 0..999)`)**: 値域が型に出るのは魅力だが、ADR 0017 が退けた重さがそのまま戻る。値域の宣言は `十進数` の側と U15 の「将来の変更想定」に既に置き場所がある。
- **任意精度整数(多倍長)を既定にする案**: 桁溢れが無くなるが、所要記憶域が実行時まで決まらない。ADR 0010 が有理数を退けた理由(組込みで使えない)と同じである。
- **巻き戻り(wrapping)を既定にする案**: 速いが、黙って値が壊れる。ADR 0010 が桁溢れを直和で受けさせた判断に正面から反する。ビット演算が要る場面は、必要が確認されたら別の語彙で足す(「将来の変更想定」)。
- **符号なし整数を持つ案**: 2の補数では符号にコストがない。選択を減らせば書くべき宣言も減る(ADR 0010 の符号の判断と同じ)。
- **論理型を持たない案(2値の直和だけにする)**: 比較演算子の結果を受ける型が無くなり、条件式そのものが書けない。判定は領域の役割の中核である。
- **論理型を公開面にも許す案**: `在庫あり: 真偽` の真が何を意味するかは型に現れない。ADR 0013 がテキストを条件に使う事を禁じた判断と対称である。**書けなくして困ったのは、名前が無い時だけ**であり、それは名前を付けるべき時である。
- **`時点` を単調時計(Rust の `Instant`)にする案**: ノードを跨いで意味を持たず、記録・突き合わせに使えない。`data` にも `state` にも置けない型になり、公開面の語彙にならない。
- **壁時計と単調時計を両方の型として持つ案**: 誤用は型で落ちるが、基本型が1つ増え、「`state` に持てる型と持てない型」の規則も要る。
  単調時計の読みは**動作環境の内側で完結する**——期限の判定・再送の間隔・計測の経過時間はいずれも動作環境の仕事であり、言語の型にする必要が無い(ADR 0012 の接合面)。必要が確認されたら足す(「将来の変更想定」)。
- **うるう秒を持つ案(TAI や UTC を厳密に表す)**: `時点 + 時間量` がうるう秒表の版に依存する。分散したノードで表が食い違えば、同じ入力から違う状態へ遷移し、Raft の前提(ADR 0001)が壊れる。うるう秒が 6 か月前にしか決まらないため、未来の時点の演算も確定しない。
- **秒+ナノ秒の2語(12〜16 バイト)で時点を持ち、範囲を広げる案**: Java の `Instant` と同じ形で ±2900 億年を表せるが、記憶域が倍になり、比較と加算が2語の演算になる。想定用途(業務システム・計測・分散制御)で 1677〜2262 年を超える必要は確認できなかった。歴史・天文の日付は `日付` が受ける。
- **時間帯付きの日時型(`ZonedDateTime`)を基本型に置く案**: 暦と時間帯の規則(IANA tz database。版が変わる)が言語の中核に入る。表示に近い型であり、ADR 0013 の役割でいえば `format` の内側の関心である。
- **時間帯を持たない日時型(`LocalDateTime`)を基本型に置く案**: 日常の記述は短くなるが、日だけの値(誕生日)と時計の読みだけの値(開店時刻)は結局それぞれ必要であり、型が3つになる。
  日と時計の読みを持てば組は直積で書けるため、**3つ目は要らない**。`期間` を外したのと同じ判断である。
- **`時刻`(時計の読み)を置かず `量 時間` で代用する案**: 「日の始まりからの経過」として数学的には同じ値になるが、`開店: 整数 ミリ秒` は**時間の量に見えて時計の読みに見えない**。
  本 ADR の総括(型の名前が値の出どころを告げる)に反する。加えて `量 時間` の値は 25 時間も表せてしまい、1日の中である事が型から読めない。
- **暦の値に `量 時間` を足せるようにする案**: 「2026-03-08 02:30 の3時間後」は時間帯が分からなければ決まらず(夏時間で存在しない時刻がある)、
  足せる言語はその曖昧さを黙って1つの答えに畳む。時間軸の加算は `時点` の上でだけ行う。
- **`日付` を西暦1年からに限る案**: 歴史・年代の記述が書けない。範囲を紀元前へ広げる費用は、内部表現(`整数 日`)には掛からない——紀元前10000年でもエポックから -4371587 日であり、`整数` の範囲を大きく下回る。
- **紀元(BC / AD)の欄を別に持つ案**: 人の読み方に近いが、年の比較と減算が欄をまたいで分岐する。天文学的年番号なら1つの整数の規則で済む。ISO 8601 も同じ数え方を採る。
- **暦を先発グレゴリオ暦の1つに固定する案**: 1582 年より前のヨーロッパ、1752 年より前の英国の史料をそのまま書けない。
  換算を書き手が毎回行う事になり、直した値と直していない値の取り違えが型に現れない。暦を欄にすれば、既存の型検査がそのまま落とす。
- **暦を値(基本型)にする案**: 行ごとに暦が違うデータを書けるが、暦が型から読めず、取り違えが実行時まで残る。
  行ごとに違う暦が要る場面は、暦ごとの区分を持つ直和(`ユリウスの日(日付 ユリウス暦) | グレゴリオの日(日付 グレゴリオ暦)`)で書ける——**その方が、どの暦が現れ得るかが型に列挙される。**
- **元号(和暦)・イスラム暦・ヘブライ暦も言語が持つ案**: 元号は法令で決まり、イスラム暦は月の観測に依る。**版が変わる表**であり、
  分散したノードで表が食い違えば同じ入力から違う結果が出る。うるう秒を持たない理由・照合キーを永続化しない理由(ADR 0013)と同じである。
- **時間帯を型として持たず U12 へ送る案**(本 ADR の初稿): ログの日時を他の時間帯で読み替える事が書けない。
  時間帯は tzdata の版に依存するが、**`時点` と分けて持てば版依存は合意の外に閉じ込められる**——送る理由が無くなった。
- **時間帯を `日付`・`時刻` の欄にする案(暦と同じ形)**: 暦は設計判断(どの暦で語るか)だが、時間帯は実行時のデータ(どこで記録されたか)であり、
  同じ `data` の行ごとに違い得る。型の欄にすると多地域のログが書けない。
- **時間帯付きの日時(`ZonedDateTime`)を1つの型にする案**: 時間軸の値(いつ起きたか)と表示の都合(どこの時計で読むか)が同じ型に同居する。
  分けて持てば、他の時間帯への読み替えが欄の差し替えになり、`時点` が動かない事が型から読める。
- **オフセット(`+09:00`)を基本型にする案**: `量 時間` の値で書ける。基本型を増やす価値が無い。
- **`期間` を基本型に置く案**: 直積で書ける。基本型にすると開区間か閉区間かを言語が決める事になり、選択が1つ増える。ADR 0009 が「継承・型引数は必要にならなかったため持たない」とした判断と同じ形である。
- **`時間量` を基本型のまま置く案**: 単位の検査(ミリ秒と秒の取り違え)が効かない。`量 時間` へ寄せれば ADR 0010 の換算の規則がそのまま使え、基本型が1つ減る。
- **「月」「年」を時間の単位にする案**: 1 か月は 28〜31 日であり固定の比を持たない。ADR 0010 の単位は有理数比で定義するため、そもそも書けない。
- **対応表(map)・集合(set)を構成子に加える案**: 8実験の公開面に一度も現れなかった。思考実験 08 の論点6(要求ロケールで文言を引く)は整形の層の内側であり、body 内部の型は自由である(ADR 0009)。
- **文字(char)型を置く案**: テキストの分解・添字が禁じられている(ADR 0013 決定4)ため、置いても使えない。
- **空の型(unit / void)を置く案**: 値を持たない直和の区分(`済`・`完了`)で書ける。

## 将来の変更想定

- **単調時点の型**。Phase 2 の動作環境で、経過時間をコンポーネントの記述に持ち込む必要が確認されたら足す。置くなら Rust と同じく不透明型(差と比較だけ)とし、`state`・`data`・公開面に置けない型にする。
- **月・年の加算**。`月を足す(日付, 整数 月, 末日 <方式>)` のように、末日の扱いを宣言させる形が候補である。ADR 0010 の丸めの宣言と同じ形になる。
- **時間帯の型と `時点` ↔ `日付` の変換**(U12)。夏時間で存在しない時刻・二度ある時刻は直和で受ける必要がある。tzdata の版依存は ADR 0013 の照合キーと同じ扱い(永続化しない)が候補である。
- **書き手が暦を宣言する仕組み**。量と単位を書き手が宣言できる(ADR 0010)のと同じ形で、`暦 和暦 : グレゴリオ暦 + 元号表 …` のように書けるようにする案。
  版が変わる表(元号・観測)をどう供給し、版の食い違いをどう扱うかを先に決める必要がある。tzdata と同じ問題であり、U12 と併せて検討する。
- **ISO 週日付・序数日付**。`2026-W35-6`・`2026-241` は暦の一種であり、暦の欄に足せる。いずれも算術暦であり版を持たない。
- **時間帯の版の固定**。分散したノードで tzdata の版を揃える仕組み(版を合意の対象に含める)は Phase 2 の動作環境で検討する。
- **`日時` を一つの型として置くか**。`日付` と `時刻` の直積を書く回数が多いと分かったら、名前の付いた組を言語が持つ案を検討する。ただし時間帯を持たない事は変えない。
- **整数のビット演算**。ハッシュ・圧縮・プロトコルの実装で必要が確認されたら、巻き戻りを持つ別の語彙(`バイト列` の上の操作)として足す。整数の算術に巻き戻りを混ぜる事はしない。
- **整数の範囲宣言**(`整数 範囲 0..999`)。ADR 0010 の「将来の変更想定」にある値域の宣言と併せて Phase 1 で検討する。
- **対応表・集合**。公開面に現れる例が出たら再検討する。キーは「正準形が一意に定まる型」に限る規則(ADR 0013 決定3)が既にある。
- **128 ビットの時点**。1677〜2262 年の範囲が足りない用途が出たら検討する。トランスパイル先(ADR 0012)の要件が増える。
- 採用時の反映先: 第2章に「データの宣言」の節を立て、構成子(ADR 0009)・基本型(決定1)・量と単位(ADR 0010)を置く。
  第3章 3.3 に E0019-1〜E0019-6・W0019-1〜W0019-3 を追加し、E0017-1 を E0019-3 が広げる旨を書く。
  第4章の `deadline <時間量>` を `deadline <量 時間 を持つ数値>` に改める。
  第5章(記述の表記)の語彙に決定8 の表を反映する。

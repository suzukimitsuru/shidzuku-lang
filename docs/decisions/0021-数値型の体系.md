## 背景(なぜ決める必要があるか)

数値型は 2026-09-03 に白紙へ戻った(計画書 第7節 7.1)。ADR 0010(十進固定小数点・桁を2つ宣言)と ADR 0017(実数を主に使う)を破棄し、
思考実験 14 で他言語を比較した後、本 ADR で3度の案を経て現在の形に至った。経緯を残す。

| 版         | 数値型                              | 解いた事                         | 残した問題                                      |
| ---------- | ----------------------------------- | -------------------------------- | ----------------------------------------------- |
| ADR 0010   | `数値(i.f)`(十進固定小数点)         | 誤差の場所が型に出る             | 上限の見積り・桁溢れの直和・中間桁の膨張        |
| 2026-09-10 | `整数`・`実数`・`十進数(s)`(可変長) | 上限の見積りが消える             | 暗黙の橋が1本要る                               |
| 2026-09-15 | `実数`・`十進数(s)`(可変長)         | 暗黙の変換がゼロになる           | **「厳密かつ上界あり」の型が無い**(思考実験 16) |
| **本版**   | `intN(s)`・`uintN(s)`・`floatN`     | **上界が型に戻り、空白が埋まる** | 幅の見積りと桁溢れが戻る(承知の上)              |

前版の最大の欠点は、**厳密でありながら記憶域と実行時間の上界を型が言う型が1つも無い**事だった。
具体的には、期限(`deadline`)が値の大きさで超過し得る・失敗し得る演算が全ての算術になる・多倍長の確保による停止が Raft の締切に乗り得る、という3点である(思考実験 16 の 7.3、ADR の欠点)。

**本版はその空白を埋める。** 幅を型に書けば、記憶域も1回の演算の時間も型から決まる。代償として ADR 0010 の負担(幅の見積りと桁溢れ)が戻るが、
**上限は外部形式・機器・記憶域という実在の制約から来ており、業務の都合ではない**——書き手はそれを知った上で幅を選ぶ。

## 検討した選択肢

型の数と暗黙変換の2軸は思考実験 14 が、幅を持つ言語の実態は思考実験 17 が比較を済ませている。本版が決めたのは、思考実験 18 が書き下ろしで見つけた3つの論点である。

### 論点1 — 除数・乗数の型をどこまで揃えさせるか

| 案                                                   | `金額 ÷ 人数` | 書き手の負担                   |
| ---------------------------------------------------- | ------------- | ------------------------------ |
| (a) 型が完全に同じ場合のみ                           | **書けない**  | 位取りまで揃える変換が要る     |
| (b) **幅と符号だけ揃え、位取りと単位は規則で決まる** | 書ける        | 幅を揃えるだけ                 |
| (c) 幅も違ってよい(自動で広い方へ)                   | 書ける        | どちらへ寄るかを覚える事になる |

(b) を採る。**幅は器の話、位取りと単位は値の意味の話**であり、後者は規則で決まる(ADR 0010 の演算規則がそのまま使える)。

### 論点2 — `float` の演算語彙

`float` の演算は常に丸まるため、`割る(…, 丸め <方式>)` の丸めの欄が意味を持たない(思考実験 18 の3節)。
**`float` は演算子 `÷` を持ち、`割る(…)` は `int`/`uint` 専用**とする。丸めを宣言できる型にだけ、宣言を求める。

### 論点3 — 乗算で幅が足りなくなったら

| 案                                   | 利点                       | 欠点                                  |
| ------------------------------------ | -------------------------- | ------------------------------------- |
| (a) **同じ幅で計算し、溢れたら失敗** | 規則が単純。上界が保たれる | 実務で溢れ得る                        |
| (b) 幅が倍になる                     | 溢れにくい                 | `int256` の先が無い。型が勝手に変わる |
| (c) 結果の型を書かせる               | 全て書き手が決める         | 乗算が演算子で書けなくなる            |

(a) を採る。溢れは失敗として観測でき(U13)、**記憶域と実行時間の上界は保たれる**。
中間で幅が要る計算は `変換(a, int128(2))` を書く——**幅を選ぶ責任を型に出す**というこの体系の趣旨に合う。

## 決定

### 1. 数値型は `int`・`uint`・`float`・`dec` の4種とする

```plaintext
int8(s)  int16(s)  int32(s)  int64(s)  int128(s)  int256(s)     <単位 | unitless>
uint8(s) uint16(s) uint32(s) uint64(s) uint128(s) uint256(s)    <単位 | unitless>
float32  float64                                                <単位 | unitless>
dec(<整数部>.<小数部>)                                          <単位 | unitless>   # 内部計算のみ

int64(2) 円       # 金額。刻み 0.01 円、上限 ±約 9.2 京
int64(0) unitless # 個数・添字・版・連番
int64(0) ナノ秒   # 時間の量(±約 292 年)
int64(4) unitless # 税率(0.1000 = 10%)
uint8(0) unitless # バイトの値
float64 メートル  # 測った長さ
```

- 基本型の数え方は **`int`・`uint`・`float`・`dec` の4つ**であり、**幅は型名の一部、位取りと桁は型の欄**である(`日付` の暦が型の欄であるのと同じ形。ADR 0019 決定5)。
- 幅は 8/16/32/64/128/256 の6種。符号あり/なしで 12 通り、`float` は 2 通りになる。
- **役割が層で分かれる。**

  | 型                    | 上限を決めるもの | 格納       | 書ける場所                  | 主な用途                      |
  | --------------------- | ---------------- | ---------- | --------------------------- | ----------------------------- |
  | `intN(s)`・`uintN(s)` | 幅               | 固定       | どこでも                    | 公開面・`data`・`state`・外部 |
  | `floatN`              | 幅               | 固定       | どこでも                    | 測った値                      |
  | `dec(i.f)`            | 宣言した桁       | **可変長** | **body の式と局所の値だけ** | 中間計算(決定5-3)             |

- 基本型の一覧は11(`論理`・`int`・`uint`・`float`・`dec`・`テキスト`・`バイト列`・`時点`・`日付`・`時刻`・`時間帯`)になる。

### 2. `intN(s)` は「幅 N の位取り整数」— 幅が上限を、位取りが刻みを決める

- 値は `m × 10^-s` である。`m` は幅 N の2進整数(符号付きは2の補数)。**位取り `s` は型情報のみ**で、実行時の値は `m` だけである。
- 演算は全て整数演算になる。ADR 0010 の内部表現をそのまま引き継ぐ。変わったのは**幅を型が決める**事だけである。
- 実効範囲の例。

  | 型          | 刻み   | 値の範囲    | 主な用途                   |
  | ----------- | ------ | ----------- | -------------------------- |
  | `uint8(0)`  | 1      | 0 〜 255    | バイト・小さな符号なしの値 |
  | `int32(0)`  | 1      | ±約 21 億   | 個数・外部の 32 ビット整数 |
  | `int64(0)`  | 1      | ±約 922 京  | 添字・連番・時間の量       |
  | `int64(2)`  | 0.01   | ±約 9.2 京  | 金額                       |
  | `int64(4)`  | 0.0001 | ±約 92 兆   | 税率・利率                 |
  | `int64(9)`  | 1e-9   | ±約 92.2 億 | 秒をナノ秒刻みで持つ場合   |
  | `int128(2)` | 0.01   | ±約 1.7e36  | 桁の大きい金額・中間結果   |
  | `int256(0)` | 1      | ±約 5.79e76 | 暗号・分散台帳             |

- **同じ値は同じ表現を持つ**(`m` は一意)。比較は全順序、等価は素直であり、ハッシュ可能である(ADR 0013 決定3)。

### 3. 位取りの宣言は必須。`float` は位取りの欄を持たない

- 整数でも `int32(0)` と書く。**刻みは設計判断であり、型から読めなければならない**(省略の禁止・ADR 0008)。
  `int32` と `int32(0)` の両方を許せば、書かれなかった欄を言語が補う事になる。
- `float32`・`float64` に位取りの欄は無い。刻みが値の大きさで変わるため、書いても情報が増えない
  (ADR 0017 が `実数` について書いた「欄そのものを持たない完結した型」と同じ形)。`float64(2)` はエラー(E0021-2)。
- E0008-1(必須宣言の欠落)の対象は「型名・幅・`int`/`uint` の位取り・単位の欄」である。

### 4. 単位の欄は必須。単位なしは `unitless`

- ADR 0010 の量と単位の体系をそのまま引き継ぐ——`量`・`単位` の宣言、比は既約の有理数、換算比を持たない量(通貨・温度)、組立の量は宣言されたものだけ。
- **単位を持たない事は `unitless` と明示する**。書かれなかった欄を既定で補わない(ADR 0008)。
- 単位は型情報のみであり、実行時コストはゼロである。検査 E0010-1・E0010-2・E0010-5、警告 W0010-1・W0010-2 はそのまま生きる。
- `unitless` との乗除算(スカラー倍)は単位を変えない。`int64(2) 円 × int64(0) unitless` は `円` のままである。

### 5. 演算 — 幅と符号を揃え、位取りと単位は規則で決まる

**同じ幅・同じ符号の型どうしは演算できる。** 位取りと単位は規則で決まり、書き手は揃えなくてよい(論点1)。

| 演算                                 | 結果の位取り | 結果の幅   | 失敗し得る所                     |
| ------------------------------------ | ------------ | ---------- | -------------------------------- |
| `a + b` / `a - b`                    | 細かい方     | 同じ       | 位取りを揃える所と、和差の範囲外 |
| `a × b`                              | 両辺の和     | 同じ       | 積の範囲外                       |
| `分ける(a, b)`(商と余り)             | `a` と同じ   | 同じ       | `b` が 0                         |
| `合算(列)`                           | 要素と同じ   | 同じ       | 途中の範囲外                     |
| `割る(a, b, <型>, 丸め <方式>)`      | 宣言した型   | 宣言した型 | 範囲外・`b` が 0                 |
| `丸める(a, <型>, 丸め <方式>)`       | 宣言した型   | 宣言した型 | 範囲外                           |
| `換算(a, <単位>, <型>, 丸め <方式>)` | 宣言した型   | 宣言した型 | 範囲外                           |

- **桁溢れはラップもトラップもせず、失敗とする**(U13)。検査は**演算ごと**に行う(ADR 0019 決定2 の判断を引き継ぐ。幅が有限で中間が広がらないため、「名前を得る所」では足りない)。
- **加算は位取りの細かい方へ揃える。揃える所で溢れ得る**——`int64(0) 円 + int64(2) 円` は前者の `m` を 100 倍する(思考実験 18 の論点5)。
- **乗算は位取りが和になる。** 元の型に戻すには `丸める` を書く(`int64(2) × int64(4)` は `int64(6)`)。丸めの宣言はここに残る。
- **除算の演算子は持たない。** `割る(…)` と `分ける(…)` だけとする。整数の `/` が切り捨てになるような、宣言されていない丸めは起こさない(ADR 0010・ADR 0019 決定2 と同じ)。
- **`float` は演算子 `+ - × ÷` を持ち、`割る(…)` を持たない**(論点2)。`平方根(値)`・`累乗(底, 指数)` も丸めの宣言を要らない。

### 5-2. `dec(<整数部>.<小数部>)` — 内部計算の型

```plaintext
dec(9.4) 円          # 整数部9桁・小数部4桁。±999,999,999.9999
dec(18.2) 円         # int64(2) の値を受けられる桁
dec(36.2) 円         # int64(2) どうしの積を受けられる桁
```

- **演算は小数部倍した整数で行う**(`int`/`uint` と同じ)。値は `m × 10^-f` であり、`m` は符号付きの2進整数である。
- **格納は値による可変長**とする。小さい値は1ワードに収め、収まらなくなった時点で広げる。
- **宣言した桁は上界であり、可変長は表現の最適化である。** この2つは矛盾しない。

  | 何を決めるか         | 決めるもの     | 効く場面                             |
  | -------------------- | -------------- | ------------------------------------ |
  | 値の上限と刻み(意味) | **宣言した桁** | 検査・記憶域の見積り・実行時間の上界 |
  | 実際に使うバイト数   | **値の大きさ** | 実行時の記憶域                       |

  `dec(9.4)` は 13 桁 = 最大 6 バイトと**静的に見積もれる**。実際の値が小さければ1ワードで足りる。
  前版の可変長 `十進数` が上界を持たなかったのとは違い、**上界は宣言が言う**(思考実験 18 の 7.1)。
- **中間の桁は自動で広がり、検査は値が名前を得る所で行う**(ADR 0010 の規則がここで復活する)。
  加算は整数部が大きい方 + 1、乗算は整数部・小数部とも和である。式の途中では溢れず、受ける所で宣言桁と照合し、超えていれば失敗とする。
  `int`/`uint` が演算ごとの検査を要するのは幅が有限で中間が広がらないためであり、`dec` にはその制約が無い。
- **`合算(列)` が素直に書ける。** ADR 0010 が「桁の上界が静的に決まらない唯一の演算」として直和を義務づけた穴は、`dec` の中で閉じる。

### 5-3. `dec` は内部計算のみ — 跨ぐ値には書けない

| 場所                                       | `dec`    | 理由                                                           |
| ------------------------------------------ | -------- | -------------------------------------------------------------- |
| body の式・局所の値                        | 書ける   | 中間計算がこの型の用途である                                   |
| `data` のフィールド・公開面・`flow` の内容 | 書けない | コンポーネントを跨ぐ値は、受け手が記憶域を見積もれる必要がある |
| 外部インターフェイス(`復号`・`符号化`)     | 書けない | 外部形式は幅で定義されている                                   |
| `state`                                    | 書けない | 状態の大きさは配置単位(障害境界)の資源に直結する               |

- 検査は E0021-4(`dec` が跨ぐ値・状態・外部に現れる)。
- 累計や残高は `int64(2) 円` のような固定幅で持ち、**伸びる中間だけ `dec` で受ける**。
- 書き方は「**持ち上げて・計算して・収める**」の3段になる。

  ```plaintext
  素   = 変換(小計, dec(18.2)) × 変換(税率, dec(1.4))   # dec(19.6) 円
  税額 = 収める(素, int64(2), 丸め 切り捨て)             # 名前を得る所で int へ戻す
  ```

- `収める(<値>, <型>, 丸め <方式>)` は `dec` から `int`/`uint` へ戻す操作である。整数部が入らなければ失敗、小数部を粗くするなら丸めの宣言が要る。

### 6. 型を跨ぐ変換は明示する — 暗黙の変換は1本も無い

```plaintext
変換(<値>, <型>)                       # 幅・符号を変える。int/uint → dec もこれ。範囲外は失敗
丸める(<値>, <型>, 丸め <方式>)        # 位取りを粗くする
収める(<値>, <型>, 丸め <方式>)        # dec → int/uint。整数部が入らなければ失敗
近似する(<値>, float64)                # int/uint/dec → float。丸めは最近接偶数
厳密にする(<値>, <型>, 丸め <方式>)    # float → int/uint/dec
```

- **幅・符号・`int`/`float` の別を跨ぐ変換は、すべて書く**。無損失な向き(`int32(0)` → `int64(0)`)も例外にしない。
  幅が 12 通りある以上、暗黙の昇格を認めると規則が組み合わせで増え、「どちらへ寄るか」を書き手が覚える事になる。**例外ゼロを保つ**(Swift・Rust と同じ立場。思考実験 14)。
- 明示の変換なしに型が混ざった式はコンパイル時エラー(E0019-3)。
- 変換の前後で**単位は保たれる**。量の検査は変換を跨いで効く。

### 7. `float` は IEEE 754 に厳密に従う — 型に序列は置かない

- `float32` は binary32、`float64` は binary64 とする。**両者は別の型**であり、混ぜるには `変換` を書く。
- **丸めは最近接偶数に固定**し、実行時の丸めモードを持たない。FMA への融合・再結合・拡張精度での中間保持・近似逆数・代数的な書き換えを禁じる。
  超越関数は正しく丸めた結果を要求し、満たせない関数は語彙に入れない。列の合算は先頭から順に行い、実装の並べ替えを禁じる。
  これにより、分散した複数ノードで結果が一致する(Raft の前提・ADR 0001)。
- **NaN・±∞・-0 を値として持たない**。生む演算は失敗とし(U13)、検査は「値が名前を得る所」で例外フラグを見る。比較は全順序、等価は素直である。
- **「主に使う型」は置かない**(2026-09-15 の判断を維持)。型は書き手が値ごとに指定する物であり、省略時に補われる型は無い以上、言語が序列を置いても記述は変わらない。

### 8. `float128` は置かない — 実現性の判定

書き手の問い「`float128` は実現しやすいか」への答えを記録する。**現時点では置かない。**

| 観点             | 実態                                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ハードウェア     | **x86-64 と AArch64 は ISA に規定すら無い**。必ずソフトウェア実装になる。規定しているのは POWER と RISC-V の Q 拡張(任意機能)だけで、実装する実機は限られる |
| 速度             | ソフトウェア実装は binary64 より大幅に遅い(演算あたり数十倍の桁)                                                                                            |
| トランスパイル先 | **Rust の `f128` は nightly 限定の実験的 API**。TypeScript/JavaScript には無い(ADR 0012 の出力先が両方とも安定して持たない)                                 |
| 名前の罠         | NumPy の `float128` は多くの環境で **80 ビットの拡張精度**であり、binary128 ではない。名前だけ同じで中身が違う                                              |
| 本 ADR の要件    | strict IEEE で結果を一致させる要件は、ソフトウェア実装なら**満たせる**(決定的である)。問題は速度と出力先である                                              |
| 需要             | これまでの思考実験に `float128` が要る計算は**一度も現れていない**                                                                                          |

**判定: 実現は可能だが、現時点では割に合わない。** 出力先が安定して持ち、必要が確認された時点で再検討する(将来の変更想定)。
同じ理由で `float16` も置かない(機械学習・GPU を対象に含める判断と一体である)。

### 9. 外部との詰め替えは、型とバイト順で書く

```plaintext
復号(<バイト列>, <型>, <バイト順>) -> <型> unitless | 長さ違い
符号化(<値>, <バイト順>)           -> バイト列

受信値 = 復号(受信, int32(0), ビッグエンディアン)     # int32(0) unitless
応答   = 符号化(変換(値, int32(0)), ビッグエンディアン)
```

- **幅は型が言うため、詰め替えに書くのはバイト順だけ**になった(前版では幅・符号・バイト順の3つを書いていた)。
- 8 ビット幅にはバイト順の欄が無い(選択肢が無いため。E0008-1 には当たらない)。
- 詰め替えは **`境界` の役割でのみ書ける**(E0021-1)。外部形式の知識が領域層へ漏れない。
- 復号した値は `unitless` である。単位を付けるのは `単位を付ける`(body 内でのみ書ける操作)。
- 名前付きの外部形式(`外部形式 ヘッダ { 版: uint8(0), 長さ: uint32(0) ビッグエンディアン }`)は U12 で扱う。

### 10. `時点`・`日付`・`時刻` は範囲を仕様が定め、内部表現は実装に委ねる

ADR 0019 の決定4〜6 は「内部表現はエポックからの `整数 ナノ秒`」と書かれていた。次のように読み替える。**決定の意味は変わらない。**

| ADR 0019 の記述                       | 本 ADR での読み替え                                                 |
| ------------------------------------- | ------------------------------------------------------------------- |
| 内部表現はエポックからの整数ナノ秒    | **表せる範囲を仕様が定める**(1677〜2262 年)。内部表現は実装に委ねる |
| `隔たり` の結果 `整数 <単位>`         | `int64(0) <単位>`                                                   |
| `日を足す(日付, 整数 日)`             | `日を足す(日付, int64(0) 日)`                                       |
| `日数(始め, 終わり) -> 整数 日`       | `日数(始め, 終わり) -> int64(0) 日`                                 |
| `時計を進める` の繰り上がり `整数 日` | `int64(0) 日`                                                       |

`int64(0) ナノ秒` は ±約 292 年であり、`時点` の範囲と整合する。

### 11. 添字・長さ・繰り返し回数は `uint64(0) unitless` とする

- 長さと添字は**負にならない**。それを型に出す(E0019-4 を改訂)。
- 差を取る場合は `変換(値, int64(0))` を書く。
- 幅は 64 に固定する。列の長さが幅で環境ごとに変わると、同じ記述の意味が環境に依存する(ADR 0010 の「意味はバイト数に依存しない」と同じ判断)。

### 12. 検証 — 4つ改訂、E0021 を4つ新設

| 識別子  | 検査                                                               | 本 ADR での扱い                                                       |
| ------- | ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| E0010-1 | 異なる量の加減算・比較                                             | 引き継ぐ(変更なし)                                                    |
| E0010-2 | 換算比を持たない量の、単位を跨ぐ演算・換算                         | 引き継ぐ(変更なし)                                                    |
| E0010-3 | 丸めが避けられない演算に丸めの宣言がない                           | **改訂**。`int`/`uint` の除算・換算・位取りを粗くする受け渡しに当たる |
| E0010-5 | 宣言のない組立の量の出現                                           | 引き継ぐ(変更なし)                                                    |
| E0019-3 | 数値型が明示の変換なしに混ざる                                     | **改訂**。幅・符号・`int`/`float` の別が違えばエラー。例外は無い      |
| E0019-4 | 列の添字・長さ・繰り返し回数の型                                   | **改訂**。`uint64(0) unitless` に限る                                 |
| E0021-1 | 外部との詰め替え(`復号`・`符号化`)が `境界` 以外の役割に現れる     | **新設**(ADR 0013 の役割の向きを数値の詰め替えに当てる)               |
| E0021-2 | `float` に位取りの欄を書いている                                   | **新設**                                                              |
| E0021-3 | 幅を跨ぐ演算に `変換` が無い(E0019-3 のうち幅だけが違う場合)       | **新設**(診断を分けて出す)                                            |
| E0021-4 | `dec` が `data`・公開面・`flow`・`state`・外部との詰め替えに現れる | **新設**(決定5-3)                                                     |
| W0010-1 | 換算先の分解能が換算元より粗い                                     | 引き継ぐ                                                              |
| W0010-2 | 合算する状態の刻みが、足し込む値の刻みより粗い                     | 引き継ぐ                                                              |
| W0017-1 | 通貨の量を持つ値に `float` を使っている                            | 引き継ぐ(対象を `float` に読み替える)                                 |
| W0017-2 | `float` と `int`/`uint` のあいだで往復変換している                 | 引き継ぐ(対象に `dec` を加える)                                       |
| W0019-1 | 大きな整数を `近似する` で `float` にしている                      | **改訂**。`float` の仮数に収まらない大きさが対象                      |

実行時の失敗(U13)は次の7つになる。

| 失敗                                         | 起きる所                                |
| -------------------------------------------- | --------------------------------------- |
| 加減乗の結果が幅を出る                       | 演算ごと(決定5)                         |
| 位取りを揃える所で幅を出る                   | 加減算・`丸める`・`換算`(決定5)         |
| `変換` の結果が幅を出る                      | 幅・符号を跨ぐ変換(決定6)               |
| `分ける(a, 0)`・`割る(a, 0, …)`(0 除算)      | 除算                                    |
| `float` が特殊値を生む(0 除算・負数の平方根) | 名前を得る所での例外フラグの検査(決定7) |
| `復号` のバイト列の長さが幅と合わない        | 境界(決定9)                             |
| `dec` が名前を得る所で宣言した桁を超える     | `dec` の受け渡しと `収める`(決定5-2)    |

**`十進数` の「記憶域を確保できない」失敗は消える。** 幅が有限になったため、確保は静的に決まる。

### 13. 使い分けの指針

| 問い               | 答え                                                    |
| ------------------ | ------------------------------------------------------- |
| 厳密か、測った値か | 厳密なら `int`/`uint`、測った値なら `float`             |
| 刻みはいくつか     | 位取り `s`(金額は 2、税率は 4、数えるなら 0)            |
| 上限はいくつか     | 幅(業務の上限ではなく、**器として足りる幅**を選ぶ)      |
| 負になり得るか     | なるなら `int`、ならないなら `uint`(差を取るなら `int`) |

- **迷ったら `int64`** とする。64 ビットは金額(±9.2 京)・時間の量(±292 年)・連番のいずれにも足り、出力先(Rust の `i64`・TypeScript の `BigInt`)にも素直に落ちる。
- `int8`/`int16`/`int32` は**外部形式と記憶域が理由のとき**に選ぶ。`int128`/`int256` は中間結果と暗号・分散台帳のためにある。
- `uint` の使い所は狭い(バイト・長さ・外部形式)。**業務の値は `int` が基本**である——差を取ると負になり得るため(思考実験 18 の論点7)。
- **中間計算で幅が足りなくなったら `dec` を使う**。`変換(a, dec(18.2))` で持ち上げ、`収める(素, int64(2), 丸め …)` で戻す。
  公開面と `state` は固定幅のままにする——跨ぐ値と状態は、受け手と配置単位が記憶域を見積もれる必要がある(決定5-3)。
- **通貨の量を持つ値に `float` を使うと警告(W0017-1)。**

## 机上検証(思考実験 18 の要約)

思考実験 18 で、思考実験 06・12・13 の数値をこの型で書き下ろした。

| 確かめた事           | 結果                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------ |
| 明細行の金額(U23)    | `単価 int64(2) 円 × 数量 int64(0) unitless` が**そのまま書ける**。特別規則は要らない |
| 税額(位取りの増加)   | `int64(2) × int64(4)` は `int64(6)`。`丸める` で `int64(2)` に戻す                   |
| 合算                 | 要素と同じ型。`int32(2) 円` を選ぶと 3 行で溢れる——**幅の見積りが要る**              |
| 按分                 | `分ける(合計, 人数)` は幅が同じなら書ける(論点1 の規則による)                        |
| 計測                 | `float64 摂氏`。位取りの欄が無い事は自然に読める                                     |
| 時間の量             | `int64(0) ナノ秒` = ±292 年。`時点` の範囲と整合する                                 |
| 外部との詰め替え     | 幅が型にあるため、宣言はバイト順だけになった                                         |
| 「厳密かつ上界あり」 | **戻った**。思考実験 16 が挙げた空白(期限・失敗の範囲・確保の停止)は塞がる           |

## 結果(利点と欠点)

### 利点

- **記憶域と実行時間の上界が型から読める**。前版の最大の欠点(思考実験 16 の 7.3)が解消する。
  期限(`deadline`)を守れる事を静的に裏づけられ、ヒープを持たない環境でも動き、失敗し得る演算が有限個に定まる。
- **外部形式と型が直接対応する**。8/16/32/64/128/256 は、プロトコル・DB・機器のレジスタの幅そのものである。詰め替えの宣言はバイト順だけになった。
- **スカラー倍(U23)が特別規則なしに書ける**。位取りと単位が規則で決まるため、`金額 × 数量` がそのまま通る。
- **暗黙の変換が1本も無い**。例外ゼロの規則を保ったまま、演算は書きやすい(幅を揃えるだけでよい)。
- **刻みが型から読める**。`int64(2) 円` は「1 銭刻み」と読める。ADR 0010 が守ろうとした性質はそのまま残る。
- **丸めは宣言した所だけで起きる**(`int`/`uint`)。誤差の出る場所は除算・粗い単位への換算・位取りの縮小の3つである。
- **中間計算の溢れを `dec` が引き受ける**。乗算で幅を食う問題と、合算の桁が定まらない問題(ADR 0010 が認めた唯一の穴)は `dec` の中で解ける。
  しかも**上界は宣言した桁が言う**ため、記憶域と実行時間の見積りは失われない。
- 分散での再現性は保たれる(整数演算と strict IEEE)。特殊値・巻き戻り・未定義動作を持たない。

### 欠点

- **幅の見積りが全ての値に戻る**。ADR 0010 の「上限の見積り」と同じ負担であり、外せば桁溢れ、広く取れば記憶域の無駄になる。
  ただし**上限は器の話であって業務の上限ではない**——迷ったら `int64` という指針で多くは済む。
- **桁溢れが実行時の失敗として戻る**。加算・乗算・位取りの揃え・変換のいずれでも起き得る。**検査は演算ごと**であり、`float` の「名前を得る所」より重い。
- **乗算が幅を食う**。`int64` どうしは `m` が約 30 億を超えると溢れる。中間で `変換(a, int128(2))` を挟む場面が出る。
- **型の見た目が増える**。幅6 × 符号2 + `float` 2 = 14 通りの綴りが現れる。基本型としては3つだが、読み手が目にする型名は増える。
- **`uint` と `int` の選択が増える**。差を取る場面で `uint` を選ぶと変換が要る。
- **序数(U24)は解けない**。`版 int32(0) unitless × 3` は依然として書ける。
- **`dec` を使う計算は3段になる**(持ち上げ・計算・収める)。`変換` と `収める` が対で現れ、式が長くなる。
- **型が4種になり、書ける場所が型ごとに違う**。`dec` だけが場所の制限を持つため、書き手はそれを覚える事になる。
- **`float128` を持たない**(決定8)。四倍精度が要る計算は書けない。

### 総括 — 何と引き換えに何を得るか

**「どれだけ細かいか」と「どれだけ大きいか」を、両方とも型に書く。**

| 版                       | 刻み       | 上限           | 記憶域                       | 桁溢れ             |
| ------------------------ | ---------- | -------------- | ---------------------------- | ------------------ |
| ADR 0010(`数値(i.f)`)    | 型が答える | 型が答える     | 静的                         | コンパイル時       |
| 前版(`十進数(s)` 可変長) | 型が答える | 答えない       | **値で決まる**               | 起きない(確保失敗) |
| **本版(`intN(s)`)**      | 型が答える | **幅が答える** | **静的**                     | **実行時の失敗**   |
| 本版の `dec(i.f)`(内部)  | 型が答える | **桁が答える** | 上界は静的・実際は値で決まる | 受ける所だけ       |

ADR 0010 との違いは、**上限の書き方が「十進の桁数」から「器の幅」に変わった**事である。
桁数は業務の言葉に見えて実は器の話だった——幅と書けば、器の話である事が読み手に分かる。
そして幅は外部形式・機器・記憶域という実在の制約に直接対応しており、**選ぶ根拠が言語の外にある**。

## 捨てたもの・理由

- **`dec` を跨ぐ値にも書ける案**: 受け手が記憶域を見積もれなくなり、状態の大きさが配置単位の資源から読めなくなる。
  前版(可変長の `十進数`)が抱えた問題がそのまま戻るため、**内部計算に閉じる**(決定5-3)。
- **`dec` の桁を宣言させない案(任意精度)**: 上界が消え、記憶域と実行時間の上界が読めなくなる。
  **桁の宣言は上界の宣言であり、可変長は表現の最適化である**——この2つを分けた事が、前版との違いである。
- **可変長の `十進数(s)`(前版)**: 幅の見積りは要らないが、**厳密かつ上界ありの型が1つも無くなる**。
  期限が値の大きさで超過し得る・失敗し得る演算が全ての算術になる・多倍長の確保による停止が Raft の締切に乗り得る——
  組込み・実時間・低遅延の分散を対象に含める以上、この空白は埋めるべきだった(思考実験 16 の 7.3)。
- **桁を「十進の桁数」で宣言する案(ADR 0010 の `数値(i.f)`)**: 上限を十進で書くと業務の言葉に見えるが、実体は器の大きさである。
  幅で書けば器の話である事が明らかになり、外部形式とも直接対応する。
- **桁溢れをラップする案(Java・Go・C#)**: 最大値 + 1 が最小値になる。静かに壊れる事は「運用で驚きがない」に正面から反する(思考実験 17 の 5.1)。
- **桁溢れをトラップする案(Swift)**: 落ちる事は気づけるが、失敗として扱えない。この言語は失敗を値で返す体系を持つ(U13)。
- **符号付き整数の桁溢れを未定義動作にする案(C・C++)**: 最適化器が「起きない」と仮定して分岐を消し得る。論外である。
- **無損失な向きだけ暗黙に変換する案(C# 型の非対称な橋)**: 幅が 12 通りある以上、どの向きが無損失かの表を書き手が覚える事になる。例外ゼロを保つ方を採る。
- **乗算で幅を倍にする案**: `int256` の先が無く、型が勝手に変わる。溢れは失敗として出し、中間の幅は書き手が選ぶ。
- **`float` に `割る(…, 丸め <方式>)` を持たせる案**: `float` は常に丸まるため、丸めの欄が意味を持たない(思考実験 18 の論点2)。
- **`float128` を今置く案**: x86-64・AArch64 は ISA に規定が無く必ずソフトウェア実装になり、Rust は nightly 限定、TypeScript には無い(決定8)。
- **「主に使う型」を決める案(ADR 0017)**: 型は書き手が値ごとに指定する物であり、言語が序列を置いても記述は変わらない。

## 将来の変更想定

- **`float128`・`float16` の追加**(決定8)。出力先(Rust の `f128` の安定化・WebAssembly 等)が持ち、必要が確認された時点で再検討する。
- **値域の宣言**(`int64(2) 円 範囲 0..999999999`)。幅では表せない業務上の上限を書く案。幅の見積りとは別の軸であり、Phase 1 で必要が確認されたら検討する。
- **型の別名**(`data 金額 = int64(2) 円`)。同じ幅と位取りの組を何度も書く負担を減らす。U9(データ型の記述)の識別子型と揃えて決める。
- **中間結果の幅を助ける手段**。乗算で `変換(a, int128(2))` を挟む場面が続くようなら、書き方を検討する(思考実験 18 の論点4)。
- **外部形式の名前付き**(U12)。`外部形式 ヘッダ { 版: uint8(0), 長さ: uint32(0) ビッグエンディアン }`。
- **失敗の体系との統合**(U13)。決定12 の6つの失敗を同じ語彙に載せる。
- **序数と基数**(U24)。`int32(0) unitless` に掛け算が書ける事は型の体系では解けない。
- 採用時の反映先:
  - 第6章 6.1 の基本型の一覧を `論理`・`int`・`uint`・`float`・`dec`・`テキスト`・`バイト列`・`時点`・`日付`・`時刻`・`時間帯` に改める(11)。

| 単位の欄は必須。単位なしは `unitless`            | 第6章 6.3、第5章 5.3(語彙)                              |
| 演算は幅と符号を揃え、位取りと単位は規則で決まる | 第6章 6.3                                               |
| 桁溢れは失敗。検査は演算ごと                     | 第6章 6.3、第3章 3.3(実行時の失敗)                      |
| 暗黙の変換は1本も無い                            | 第6章 6.3、第3章 3.3(E0019-3・E0021-3)                  |
| `dec` は内部計算のみ                             | 第6章 6.3、第3章 3.3(E0021-4)                           |
| `float` は strict IEEE。`float128` は置かない    | 第6章 6.3                                               |
| 外部との詰め替えは型とバイト順                   | 第6章 6.3、第3章 3.3(E0021-1)。名前付きの外部形式は U12 |
| 時間の型は範囲を仕様が定める                     | 第6章 6.4(内部表現の記述を読み替え)                     |
| 添字・長さは `uint64(0) unitless`                | 第3章 3.3(E0019-4 を改訂)                               |

これに伴う他の ADR の扱い。

- **ADR 0019 の決定2(整数型)は本 ADR が置き換える。** 決定7(3つの数値型は暗黙に混ざらない)も本 ADR の決定6 が置き換える。**両決定の凍結は解ける。**
- ADR 0019 の決定1・3〜6・8・9 は有効のままである(決定1 の基本型の一覧は、本 ADR が数値の行を差し替える)。
- ADR 0010・ADR 0017 は破棄のままであり、**本 ADR が後継として確定した**。両 ADR の量と単位・strict IEEE・丸めの語彙は本 ADR が引き継いでいる。
- ADR 0014 の基本型の語彙表(`int`・`real`・`decimal`)は、本 ADR の綴り(`int`・`uint`・`float`・`dec`)に差し替える。
  **単位なしは ADR 0014 の `unitless` をそのまま使う**(下記「単位なしの綴り」)。

### 単位なしの綴り — `none` を捨てて `unitless` に戻す(2026-09-17)

起案時は単位なしを `none` と仮に置いていた。「該当なし」を表す既存の語(`depends none`・`state none`・`collator none`)に
揃えれば語彙が1つ増えないという理由である。**書き手の判断でこれを捨て、ADR 0014 が定めていた `unitless` に戻す。**

- **`unitless` の方が直接的である。** 単位の欄に書くのは「単位が無い」事であって「該当が無い」事ではない。
  `int64(0) unitless` は読んだとおりに「単位を持たない整数」と読める。
- **`none` は他の `none` と混同する。** 同じ綴りが「宣言する相手が居ない」(`depends none`)・「状態を持たない」(`state none`)・
  「期限を設けない」(`deadline none`)を既に表しており、そこへ「単位が無い」を重ねると、`none` が何を否定しているのかが
  文脈ごとに変わる。**語を共有して得られるのは字面の統一だけで、読み手の負担はむしろ増える。**
- 語彙は1つ増えるが、`unitless` が現れるのは型の単位の欄だけであり、他の位置には現れない。

この変更は綴りだけであり、決定4 の内容(単位の欄は必須・書かれなかった欄を既定で補わない・スカラー倍は単位を変えない)は変わらない。

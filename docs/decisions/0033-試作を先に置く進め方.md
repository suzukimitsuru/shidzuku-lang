## 背景(なぜ決める必要があるか)

2026-11-07 に、suzukimitsuru の依頼で Shidzuku の進め方を振り返った。物差しにしたのは、次の問題と三つの要件である。

- **解きたい問題**: 設計意図から実装までを記述する言語により、開発するシステムを把握しやすくしたい
- **試作を繰り返して定義する**: この様な言語は使った事が無いため、試作を繰り返して定義して行く。仕様に抜け漏れがあっても、動作する物を作って洗練して行く
- **データフロー言語とする**: 動作を把握しやすくするため
- **分散環境で、動作環境が再起動と版の更新を行う**: 運用の手間を減らすため

振り返りの時点(2026-08-18 からの約80日)の数字は次の通りである。

| 項目                       | 量                                                     |
| -------------------------- | ------------------------------------------------------ |
| コミット                   | 164(マージを除くと111)                                 |
| 仕様・思考実験・ADR        | 約1万9千行(思考実験33本、ADR 32本)                     |
| `compiler/`・`runtime/`    | 空(`.gitkeep` だけ)                                    |
| 型・単位・暦の検討         | 思考実験の約3分の1。ADR 9本のうち2本(0010・0017)は破棄 |
| 文書の体裁と運営のコミット | マージを除く111のうち約2割                             |

要件ごとに見ると、次の事が分かった。

1. **試作を繰り返して定義する事は、達成できていなかった。**
   Phase 1 へ移る条件(計画書 第4節 4.5。五つのうち判断待ちの ADR が無い事は同日に外し、四つが残っていた)は、Phase 1 の前に決める課題が全て ADR として採用されている事を求めていた。
   仕様を先に固める形であり、要件と逆である。CLAUDE.md の中でも「仕様だけを先行させない」と「実装は仕様の裏付けができてから」が食い違い、後者が勝っていた。
   body の記法(ADR 0027)が提案のままのため、コンポーネントの中身を書く形が無く、パーサにも着手できなかった。
   思考実験は机の上で書いてみる確かめ方であり、書けない所は見つかっても、動かない所は見つからない。
2. **データフロー言語の骨格は合っているが、決める順が逆だった。**
   `flow`・`pressure`・配達保証・障害境界は、データフローの芯として筋が通っている。
   一方で、節がいつ動き、どの順に受けるかという実行モデル(ADR 0032(実行モデルと順序保証))が最後に残り、数値型と暦の作り込みが先に厚くなった。
3. **分散環境での運用の自動化は、最も薄かった。**
   再起動は `restart` と `restart none` の二択だけであり、監督の詳細は最小の分散動作環境(Phase 2)へ送られていた。
   運用の手間を減らす中心である版の更新(コンポーネントのバージョンと移行(U16))は未着手だった。一方で ESP32 のボード(ADR 0030(ESP32 ボードの選定))は選定済みだった。

良かった所も残る。判断の理由が ADR に残り、破棄の経緯まで追える。既存の系を書いてみる進め方と、反証の思考実験(思考実験 31)で、仕様を自分で疑う姿勢がある。
意図を必ず書かせる事・省略の禁止・障害境界の明示は、一貫した設計思想になっている。

この振り返りを受け、suzukimitsuru が「全面的にこの振り返りの方針になる様に組み替える」と決めた。本書はその組み替えの記録である。

## 決定

「試作を先に置き、仕様へ書き戻す」を採る。

### 決定1 — 言語仕様(Phase 0)を閉じ、最小の言語実装(Phase 1)へ今移る

- 2026-11-07 に Phase 1 へ移る。計画書 第4節 4.5 の移行の条件(四つ)と、同日に計画した「先に着手する部分」は廃する
- 先に着手する部分に挙げた作業(データ宣言と型・正準形・動作環境の意味の核・shidzuku-lint)は、試作の順の中で、その試作に要る分だけ作る。そこで決めるとしていた物(コンパイラ自身の実装言語・正準形の符号化の形式 等)は、計画書 第4節の「Phase 1 の中で決める物」へ移す
- 言語仕様(Phase 0)の成果物は、初稿の仕様書(第0〜6章)と、採用済みの ADR とする。裏付けは試作で得る
- 言語仕様(Phase 0)は「動く最小の成果物」で締められなかった。その事をここに記録する

### 決定2 — 未決の課題は、試作の中で仮に決め、動かして確かめてから決める

仮置きは**決まった事ではない**。仕様書には書かず、計画書 第4節(最小の言語実装の進め方)の「仮置き」の表にだけ置く。確かめた後は決定4(書き戻し)に従って仕様に入れる。

| 課題                                                    | 仮の決め方                                                                                                                                                                                               | 確かめて決める時                     |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 実行モデルと順序保証(U10・U11、ADR 0032 は提案)         | ADR 0032 の決定の通りに動作環境を作る。細い縦の試作は `flow` だけなので、コンポーネントの中は逐次(ADR 0032 の決定1(コンポーネントの中は逐次))と、接続の中は FIFO(同じく決定8(接続の中は FIFO))だけを使う | 細い縦の試作の後に、結果を材料に採否 |
| body の記法(U26、ADR 0027 は提案)                       | ADR 0027 の候補「出力言語で直に書く」を仮に使う。生成した Rust の骨組みに手で書く。その間は `pure` の層の検査をしない                                                                                    | 混在の試作(TypeScript)の前           |

### 決定3 — 最小の言語実装(Phase 1)は、三つの試作を順に作る

各試作は動く物で締め、`examples/` に置く。前の試作が動くまで次へ進まない。

| 試作                       | 題材と範囲                                                                                                                                                                                                                                                                                                                                                                                                                         | 確かめる要件                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 細い縦の試作               | [思考実験 02(センサー収集パイプライン)](../experiments/02-センサー収集パイプライン.md) の SensorIntake と Normalizer を `flow` 一本で繋ぎ、1プロセスで動かす。パーサは `system`・`component`・`intent`・`constraint`・`flow` を読み、body は読まない。検証器は省略の禁止のうち、`intent` と、接続の `pressure`・配達保証の必須だけを見る。生成器は Rust の骨組みを出す。データの型は計測値の `record` 一つを読むのに要る分だけ作る | データフロー言語として動く事         |
| 再起動と版の入れ替えの試作 | 同じ題材で、Normalizer が落ちたら動作環境が再起動し、流れが止まらない事を見る。`durable` の流れは再起動を跨いで失われない事を見る。Normalizer の新しい版を、流れを止めずに入れ替える。1プロセスのまま                                                                                                                                                                                                                              | 動作環境が再起動と版の更新を行う事   |
| 混在の試作                 | これまでの Phase 1 の成果物。1つのコンポーネントを TypeScript の出力に差し替えても同じ流れが動く。題材は第1段から第3段へ増やす(計画書 第4節)。接合面の凍結はここで行う(ADR 0012(動作環境の言語とトランスパイル先の言語)の決定10(凍結の時期))                                                                                                                                                                                       | 一本の記述から二つの言語へ落とせる事 |

- 動作環境は Rust で作り、意味の核を標準ライブラリに依らない1つのクレートにする事は、細い縦の試作から守る(ADR 0029(最小の動作環境)の決定1(意味の核を1つのクレートにする))
- shidzuku-lint は、細い縦の試作の検証器ができてから着手する。検証器と規則の一覧を共有する相手ができてから、という ADR 0026 の決定2(時期)の範囲の中である
- 分散(複数のプロセスとノード)は、最小の分散動作環境(Phase 2)のままとする。ESP32 の器も変えない(ADR 0029(最小の動作環境)の決定7(ESP32 の器は Phase 2))

### 決定4 — 仕様書は、試作で動いた事を書き戻す場所にする

- 二つ以上の候補を比べて選ぶ時だけ ADR を起こす。試作で一つに決まった事は、採用の作業で仕様書に書き戻し、担当する領域の README の経緯に一行残す
- 仕様書と実装が食い違ったら、動いた方を正とする。仕様書を直すか、直せない時は担当する領域の README の「次に決める事」に書く
- 仮置きを確かめた結果は、仮置きの表の行を消し、決まった先(ADR か仕様書の節)を担当する領域に書く

### 決定5 — 思考実験は、試作で決められない時に限る

- 思考実験を起こすのは、候補を比べる時と、まだ作れない段(分散・可視化)を考える時に限る
- 既存の系を書いてみる確かめ方は、`examples/` の動く例へ移して行く。思考実験の題材を例にする時は、思考実験の記述を最新の仕様で書き直さず、動く例の側を正とする

### 決定6 — 文書の運営の規則を増やさない

- CLAUDE.md の制約と、領域の木の規則([docs/areas/README.md](../areas/README.md))は今のまま保ち、新しく足さない。足したくなったら、試作を妨げた事を理由として ADR に書く。
  本書より前に同じ日に足した三つの決まり(経緯は一行で書きリンクする・受けた入力を保留として書く・何も決めずに終えた検討をその場で確かめる)は、「今のまま」に含めて保つ
- ADR の検討順(計画書 第4節の、同時に採否を決めるステップと、それを決める三つの規則)は役目を終えたため廃する。「判断の材料が揃う前に前倒ししない」規則は、決定2(仮に決めて確かめる)と逆になるためである。
  第4節にあった物は計画書から外し、外す直前の版へのリンクを計画書に残す。経緯に表や決定の一覧を写さない決まり(2026-11-07、[docs/areas/README.md](../areas/README.md))に従うためである
- 道のりの図([docs/roadmap.html](../roadmap.html))の第3節(ADR の検討順)と第4節(Phase 0 の検証ループ)は、試作の順と試作のループに置き換える

## 捨てたもの・理由

- **仕様を固めてから実装する進め方**: 要件の「試作を繰り返して定義する」と逆であり、約80日で動く物が出なかった
- **仕様を捨て、実装だけで決める進め方**: 「意図を残す」思想を開発の進め方自身にも当てるという ADR の README の方針に反する。採用済みの決定は試作の入力として生きている
- **最初の試作に分散 KV ストア(思考実験 04)を使う案**: これまで第1段の題材だったが、`ask` と `durable` と状態の復元を一度に要し、実行モデル(U10)の再入が最初から要る。細い縦の試作は `flow` だけで済む題材にした。思考実験 04 は混在の試作の第1段に残す
- **最初の試作から TypeScript の出力も作る案**: 接合面の凍結は TypeScript が通ってから(ADR 0012(動作環境の言語とトランスパイル先の言語)の決定10(凍結の時期))であり、二つの言語を同時に追うと細い縦が太くなる

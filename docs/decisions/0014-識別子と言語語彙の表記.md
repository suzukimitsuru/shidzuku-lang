# 0014: 識別子と言語語彙の表記

- 日付: 2026-08-26(採用 2026-08-29)
- 状態: 採用
- 関連課題: U17(識別子と言語語彙の表記)。関連: U9・U15・U3(基本型と制約の語彙の名前)・U5(トランスパイル先への写像)・U14(名前空間)

## 背景(なぜ決める必要があるか)

思考実験 01(2026-08-19)以来、コード例は英字の語彙と日本語の語彙を混ぜて書かれてきた。

``` plaintext
unit OrderIntake {                      # キーワードもユニット名も英字
  constraint {
    depends  なし                       # キーワードは英字、値は日本語
    expose   受注(注文) -> 受注番号     # 公開面もデータも日本語
  }
}
```

この混在に決定は無い。思考実験 01 が題材の業務語彙をそのまま書いたのが始まりで、以後の思考実験と ADR 0009・0010・0013 がそれを踏襲した。ADR 0013 の決定8は「表記の統一は第1章への反映時に一括で決める」として明示的に保留している。

決めなければならない理由は三つある。

1. **基本型の名前を決められない**。ADR 0009・0010・0013 は基本型を共に改訂するため揃えて採否を判断する(計画書 第3節)。しかし ADR 0013 は `text` を退けた理由として「数値・真偽・時刻・識別子型が日本語の表記であるため、基本型の表記が割れる」を挙げており、既成事実への整合だけが根拠になっている。基準が無いまま3件を採用すると、日本語の語彙が言語の中核に固定される。
2. **既決の方針と割れる**。ADR 0003 は拒否語リスト・最小文字数を「拒否語も文字数下限も自然言語(日本語/英語)に依存し、言語仕様が特定の自然言語を仮定する事になるため不採用」として捨て、ADR 0006 も同じ理由で指針の機械検証を捨てた。言語の語彙そのものが日本語であれば、同じ理由が言語自身に当たる。
3. **名前は言語の外へ出る**。ADR 0012 の動作環境はユニット記述子で名前を扱い、Zenoh のキー空間に名前と版が乗る(V1)。トランスパイル先は Rust と TypeScript である。名前に何を許すかを決めない限り、接合面(H1〜H8)を凍結できない。

一方で、識別子まで英字に限る事には別の代償がある。ADR 0009 の名前的型付けは「公開面の語彙は名前で語るのが情報隠蔽と整合」する事を根拠に採られており、`受注番号` と `受付ID` の区別はドメインの語彙そのものである。これを綴り直せば、設計意図から実装までを一本の記述で貫く(第0章 0.1)道筋に翻訳が1段入る。

したがって決めるべきは「日本語か英語か」ではなく、**言語が定める語と、書き手が定める名前の線引き**である。

## 検討した選択肢

### 論点1: 言語が定める語彙の表記

- **日本語にする**: `ユニット` `依存` `公開` のように全て母語で書く。読み下しは自然だが、言語仕様が特定の自然言語を仮定する。
- **ASCII にする**: 現在の `unit` / `intent` / `depends` を基準として、日本語で書かれてきた語(`なし`・`量`・`単位`・`照合器`)も英字へ揃える。
- **両方を認める(別名)**: 同じ語に二つの綴りを与える。移行は楽だが、同じプログラムに二つの書き方が生まれる。

### 論点2: 書き手が定める名前の文字集合

- **ASCII に限る**: 道具立てが単純。ドメインの語彙に翻訳が入る。
- **UTF-8 を無制限に許す**: ドメインの語彙をそのまま書ける。正規化の差と双方向制御文字で「同じに見えて違う名前」が生じる。
- **UTF-8 を規則付きで許す**: 使える文字と正準形を規格に従って定め、見分けのつかない名前を拒む。

### 論点3: 混在の読みやすさ

英字の語彙と日本語の名前が1行に同居する見え方をどう評価するか。`expose 受注(注文) -> 受注番号` は、語彙(expose)と名前(受注)が字種で見分けられる形でもある。字種の違いを欠点と見るか、構文色分けに頼らない可読性の手掛かりと見るか。

## 決定

### 1. ソースファイルの符号化は UTF-8 に固定する

- Shidzuku のソースファイルは UTF-8 とする。他の符号化は受け付けない。BOM は付けない(あれば読み飛ばすが、書き出しでは付けない)。
- 改行は LF とする。行末の CR は E21 とする。
- 符号化の宣言(`# -*- coding: -*-` の類)は持たない。選べない事は宣言する事が無い事であり、省略の禁止(ADR 0008)は選択のある宣言に掛かる規則である。

### 2. 言語が定める語彙は ASCII とする

キーワード・基本型の名前・属性の値・演算子・区切り・組み込みの操作名は、US-ASCII の図形文字(U+0020〜U+007E)だけで綴る。

- 対象は「言語が定義し、書き手が変更できない語」である。`depends` を別の綴りで書く事はできず、`none` を `なし` と書く事もできない。
- 日本語で書かれてきた語彙は決定7の対応表で英字へ移す。
- 根拠は ADR 0003・0006 と同じ「言語仕様が特定の自然言語を仮定しない」である。言語の語彙は、言語の実装・トランスパイル先(ADR 0012)・動作環境のキー空間と共有される最小の集合であり、ここが特定の自然言語に依存すると、外部の道具立てとの接合が全て翻訳を伴う。

### 3. 書き手が定める名前は UTF-8 の文字を許容する

書き手が名付ける対象は、決定4の規則の範囲で UTF-8 の任意の文字を使える。日本語の名前は正規の記述であり、例外的な許容ではない。

対象は次の通り。

| 種別                    | 例                                       |
| ----------------------- | ---------------------------------------- |
| ユニット名              | `unit 受注受付`                          |
| フロー名                | `flow 注文の流れ`                        |
| データ名・フィールド名  | `data 注文 { 品目: 品目ID, 数量: ... }`  |
| 公開面の名前・引数名    | `expose 受注(注文) -> 受注番号`          |
| 状態名                  | `state 索引 recoverable(商品原簿の再生)` |
| 内部階層の名前          | `layers { 照合 { pure domain } }`        |
| 量・単位の名前          | `quantity 長さ base メートル`            |
| body 内の関数名・変数名 | 実装の記述に現れる名前すべて             |
| 直和の枝の名前          | `= 受注(受注番号) \| 受注不可(理由)`     |

- ADR 0009 の名前的型付けは「名前が違えば別型」である。名前がドメインの語彙そのものである事は、その狙いの一部である。
- 内部階層の名前は書き手のものだが、ADR 0013 の**役割**(境界・解析・領域・整形)は言語が定める語であり決定2に従う(`domain` 等)。名前と役割は同じ行に並ぶが、出自が違う。

### 4. 識別子に使える文字は UAX #31 に従う

- 開始文字は `XID_Start` または `_`、継続文字は `XID_Continue` とする(Unicode Standard Annex #31, Default Identifiers)。
- 制御文字・双方向制御文字(U+202A〜U+202E, U+2066〜U+2069)・書式文字・私用領域・未割り当てのコードポイントは識別子に使えない。
- `Pattern_Syntax` と `Pattern_White_Space` の文字は構文のために予約し、識別子に使えない。
- 全角空白(U+3000)は空白として扱わず、識別子にも使えない(E21)。空白は ASCII の空白と改行だけである。

双方向制御文字を禁じるのは、見た目の並びと構文解析の結果が食い違うソースを書けなくするためである(Trojan Source, CVE-2021-42574)。これは実行時ではなく**読解時の驚き**であり、静けさ(第0章 0.5)の対象に含める。

### 5. 識別子の正準形は NFC とする

- 識別子は NFC(正規化形 C)で書く。NFC でない識別子は E22 とする。
- 同一性の判定は、NFC のコードポイント列の一致とする。
- **正規化して受け入れる事はしない**。書き手の綴りをコンパイラが書き換えると、書いた通りに読めなくなる。拒否して書き手に直させる。

ADR 0013 は、テキストが正準形を持たない事を理由に等値比較とハッシュを外した。識別子はその逆で、**正準形を一つに限る事で同一性を持てる型**の側に置く。ADR 0013 の一般規則「ハッシュ可能なのは正準形が一意に定まる型だけ」と同じ立場である。

### 6. 見分けのつかない名前を同じ名前空間に置けない

同一の名前空間に、UAX #39 の skeleton(混同可能性の骨格)が一致する別の識別子が二つ以上あるとき、E23 とする。

``` plaintext
data 注文 { … }
data 注 文 { … }        # E21: 識別子に空白は使えない
data ＩＤ { … }
data ID  { … }          # E23: 全角と半角が同じ名前空間で見分けられない
```

- NFKC で正規化して同一視する案は採らない(「捨てたもの・理由」)。**別の名前として拒む**のであって、同じ名前として畳むのではない。
- 名前空間の範囲は U14(プログラムの宣言)が決める。それまでは1プログラム内を範囲とする。
- 混同の判定表は Unicode の版に依存する。検査はコンパイル時のみとし、判定結果を永続化しない(版を跨いで一致しなくなるため。ADR 0013 の照合キーと同じ扱い)。

### 8. 言語の外への写像

- **ユニット記述子**(ADR 0012)は言語中立であり、名前は NFC の UTF-8 のまま持つ。Zenoh のキー空間に載る名前と版も同じとする。
- **トランスパイル先の識別子**は出力言語の規則に従う。TypeScript と Rust はいずれも非 ASCII 識別子を受けるが、Rust は非 ASCII の識別子に lint を持ち、出力先によっては ASCII しか使えない。したがってトランスパイラは、出力言語が受けない名前を**可逆な符号化**で綴り直し、元の名前との対応表を出力に添える。
- 可逆である事を要求するのは、ログ(U4)・図(Phase 3)・診断が元の名前で読めなければならないためである。名前の往復で綴りが失われると、コードからの投影という原則(第0章 0.6)が破れる。
- 符号化の具体的な規則は Phase 1 の接合面(H1〜H8)の凍結と併せて決める。

### 9. 診断・文書の自然言語は本 ADR の対象外

本 ADR が定めるのはソースの綴りである。コンパイラの診断メッセージ、ログの本文、仕様書と ADR の記述言語は対象外とする。診断は E 番号で識別されるため(第2章 2.3)、メッセージの自然言語は実装の選択に委ねられる。

### 10. 検証の追加(第2章 2.3)

| #   | 内容                                                                                          |
| --- | --------------------------------------------------------------------------------------------- |
| E21 | 識別子に使えない文字(UAX #31 の規則外、制御・双方向制御・書式文字、全角空白)、または行末の CR |
| E22 | 識別子が NFC 正準形でない                                                                     |
| E23 | 同一の名前空間に、混同可能な(UAX #39 の skeleton が一致する)別の識別子が共存する              |

いずれもコンパイル時に判定する。記述から静的に決まる違反はコンパイル時に拒否する(第2章 2.4)。

## 根拠 — 先行例と規格

### 同じ線引きを採る言語

| 言語      | 語彙  | 識別子                | 備考                                                      |
| --------- | ----- | --------------------- | --------------------------------------------------------- |
| Rust      | ASCII | UAX #31 + NFC + lint  | RFC 2457。混同は `confusable_idents` 等の lint(警告)      |
| Python    | ASCII | UAX #31 + NFKC 正規化 | PEP 3131。正規化して受け入れる(本 ADR は拒否する側を採る) |
| Java / C# | ASCII | Unicode 識別子        | 正規化と混同の規則は持たない                              |
| Go        | ASCII | Unicode 識別子        | 正規化の規則を持たない                                    |
| Swift     | ASCII | UAX #31 準拠          |                                                           |

主要な言語は「語彙は ASCII、識別子は Unicode」でほぼ一致している。本 ADR はこの線引きを踏襲し、Rust が lint(警告)に置いた正規化と混同の規則を**エラー**に上げる点だけが異なる。破っても動く検出を採らないのは、ADR 0013 が「文字列を残し lint で検出する」を捨てたのと同じ理由である。

### 語彙を母語にした言語

なでしこ・ひまわり(日本語)、Excel の数式の各国語版などがある。読み下しの自然さと引き換えに、外部の道具立て・文献・実行環境と語が切れる。Shidzuku はトランスパイルを実現戦略に据えており(第0章 0.7、ADR 0012)、切れる側の代償が大きい。

### 規格

- Unicode Standard Annex #31, *Unicode Identifier and Pattern Syntax* — 識別子の文字集合、構文用文字の予約
- Unicode Standard Annex #15, *Unicode Normalization Forms* — NFC / NFKC
- Unicode Technical Standard #39, *Unicode Security Mechanisms* — skeleton による混同検出
- Nicholas Boucher, Ross Anderson (2021), *Trojan Source: Invisible Vulnerabilities* — 双方向制御文字による見た目と意味の乖離(CVE-2021-42574)

## 捨てたもの・理由

### 語彙について

- **言語の語彙も日本語にする**: ADR 0003・0006 が拒否した「言語仕様が特定の自然言語を仮定する」に正面から当たる。加えて `単位`(measure)と `ユニット`(unit)のように、母語では別語でも英字では衝突する組が翻訳のたびに再発する。実装・トランスパイル先・キー空間との接合が全て翻訳を伴う。
- **キーワードに日本語の別名を与える**: 同じプログラムに二つの書き方が生まれ、読み手は両方を知る必要がある。ADR 0008 が目指した「言語の既定規則という外部知識なしに、それ自体で読める」記述に反する。別名は既定値と同じ性質の外部知識である。
- **`単位` を `unit` と綴る**: ユニット宣言のキーワードと衝突する。同じ語が設計単位と度量衡の両方を指すのは、静けさの前提である語彙の一意性を崩す。次元型の系譜(Kennedy 1994)と F# の `[<Measure>]` に倣い `measure` を採る。

### 識別子について

- **識別子も ASCII に限る**: ドメインの語彙に翻訳が1段入る。ADR 0009 の名前的型付けは「公開面の語彙は名前で語る」事を根拠に採られており、`受注番号` と `受付ID` の区別が翻訳者の語彙力に左右されるようになる。設計意図から実装までを一本の記述で貫く(第0章 0.1)という理念に対し、名前だけが別の言語で書かれる事になる。思考実験 01〜07 の全記述が書き換えになるが、それは費用であって理由ではない。
- **UTF-8 を無制限に許す**: 正規化の差(NFC / NFD)で同じに見えて違う名前が生じ、双方向制御文字で見た目と構文が食い違うソースが書ける。読解時の驚きであり、静けさに反する。
- **NFKC で正規化して受け入れる**(Python の方式): `ＩＤ` と `ID`、`①` と `1` が同じ名前になる。書き手の綴りをコンパイラが書き換えるため、書いた通りに読めなくなる。本 ADR は正規化ではなく拒否を採り、NFC を要求して NFKC の差は E23 で別名として弾く。
- **混同の検出を警告に留める**(Rust の方式): 破っても動く検出は強制ではない。設計と実装が一体であるという原則に反する(ADR 0013 の同名の棄却理由)。
- **識別子の文字集合をプロジェクトごとに宣言させる**: 「この現場では日本語を禁じる」といった宣言を言語に持たせる案。言語が二つの方言を持つ事になり、ユニットの再利用が現場の宣言に依存する。組織の方針は言語の外(レビューと規約)に置く。

### 第5章を新設した理由

表記は段に属さない。ソースの符号化も識別子の規則も、Context から Code まで同じに掛かる。
段を跨ぐという点で第4章(通信=C4 の関係)と同じ立場であり、章立ての段の順(ADR 0015 決定6)を崩さずに置ける
最後尾へ置いた。ADR 0015 決定6 の章の表に第5章「記述の表記」を足す。

既存の章に混ぜる案は採らなかった。第3章(制約の体系)に置けば検証の一覧とは近くなるが、
第3章は「コンポーネントの制約」を扱う章であり(3.1)、段に属さない規則がそこに紛れる。

### 決定7 の表に足した語

本 ADR の起案(2026-08-26)より後に採用された ADR 0015 と、ADR を持たないまま第3章 3.2 に入っていた公開面の形が、
日本語の語彙を三つ持っていた。決定2 は「言語が定義し、書き手が変更できない語」の全てに掛かるため、これらも英字へ移す。
綴りの決定の重みは決定7 の表と同じ(基準であり、最終決定は Phase 1 のパーサ実装)。

| 現在の表記 | 英字     | 出自           | 備考                                               |
| ---------- | -------- | -------------- | -------------------------------------------------- |
| 担当       | by       | ADR 0015 決定2 | `expose 受注(注文) -> 受注番号 by OrderIntake`     |
| の流れ     | flow out | 第3章 3.2      | flow の出口。接続の宣言(第4章)と同じ `flow` を使う |
| の受け口   | flow in  | 第3章 3.2      | flow の受け口                                      |

`flow out` / `flow in` に `emit` / `accept` のような独立の語を当てなかったのは、
公開面が受け渡す物(ask か flow か)は第4章の通信方式そのものであり、
同じ物に二つ目の語を与えると、読み手が対応表を覚える事になるためである。

決定7 が基本型・数値・層・共通の四つの表しか持たなかったのは、**公開面の形を語彙として数え落としていた**からである。
「言語が定める語」の棚卸しは、決定2 の宣言だけでは終わらない事が分かった。

### まだ反映できない事

基本型の表(decimal・bool・instant・text・bytes・id・list)と数値の語彙(quantity・base・divide …)は、
依拠する ADR 0009・0010・0017 が未採用であり、仕様書にデータ型の章が無いため反映先が無い。
ADR 0013 の text・bytes が入っていないのと同じ理由である(ADR 0013 の採用の記録)。
段2(束 B)の採否と同時に、この表がそのまま章の語彙になる。

`measure` の行は ADR 0015 決定4 により既に無効であり、単位は `unit` と綴る。
決定7 の表は履歴として残し、読み替えは ADR 0015 決定4 の対応表による(`strip_measure` → `strip_unit`、`apply_measure` → `apply_unit`)。

### 反映して分かった事

- **決定3 の効き目が確かめられた**。英字へ移したのは語彙だけであり、`受注`・`計測値`・`センサー機器群`・`名前順` といった
  名前は1つも綴りが変わっていない。第1章 1.6 の記述例は、語彙が英字になっても業務の語彙をそのまま読める。
- **論点3(混在の読みやすさ)の形がはっきりした**。`照合器 名前順(ロケール ja-JP, 強度 二次)` は
  `collator 名前順(locale ja-JP, strength secondary)` になり、1行の中で字種が語彙と名前を分ける。
  字種の違いは、構文色分けに頼らない可読性の手掛かりとして働いている。
- **決定6 の名前空間の範囲は動いていない**。依然として1プログラム内である。
  ADR 0018(提案)がシステムの入れ子を許すと、名前空間を system 単位にする案が現実味を持つが、範囲の確定は U14 のままとする。

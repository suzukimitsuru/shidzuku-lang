# 0009: データ型の記述

- 日付: 2026-08-20
- 状態: 提案
- 関連課題: U9

## 背景(なぜ決める必要があるか)

公開面(expose)と flow の内容には「注文」「計測値」といったデータが現れるが、その型を定義する構文も型システムの有無も未定である。
接続の整合検査(E4・E5・E11)は「両端が同じデータを指しているか」の判定を型に依存し、トランスパイラ(Phase 1)も型なしには書けない。
見落とし課題の点検(2026-08-20)で U9 として登録し、思考実験 05(既存4実験の全データの書き下ろし)で入力を集めた。

- 直積(レコード)・直和(選択)・識別子型・列で、4実験の全データが書けた。
- 受注番号と受付ID のような識別子は、中身が同じでも取り違えを検出したい。
- `注文` は複数ユニットの公開面に現れる共有語彙であり、どのユニットの内側にも置けなかった。

## 検討した選択肢

- **型を持たない(動的)**: 宣言は軽いが、接続の不整合が実行時まで分からない。
- **構造的型付け**: 形が同じなら同じ型。識別子の取り違えが素通りする。
- **名前的型付け+トップレベルの data 宣言**: 名前が違えば別型。共有語彙をユニットの外に置く。

## 決定

### データはトップレベルの data 宣言で定義する

- 公開面と flow の内容を流れるデータは、ユニット・フローと並ぶトップレベルの `data` 宣言で定義する。
- 語彙は4つ: **直積**(レコード)、**直和**(選択)、**識別子型**(名前で区別される ID)、**列**。
  基本型として文字列・数値・真偽・時刻・期間・時間量を言語が持つ(時間3種は期限宣言と共通)。
- 思考実験 01〜04 の全データがこの語彙で書けた(思考実験 05)。継承・型引数は必要にならなかったため持たない(「将来の変更想定」参照)。

### 名前的型付け

- 構造が同じでも名前が違えば別型とする(受注番号 ≠ 受付ID)。取り違えはコンパイル時に落ちる。
- 公開面の語彙は名前で語るのが情報隠蔽と整合し、取り違えの静的検出は静かさ(驚きの排除)に直結する。

### 接続の型検査(E11)

- ask / flow の接続の両端で型が一致しない場合はコンパイル時エラーとする(E11。第2章の検証一覧に追加)。
- W2(陳腐化)の「公開面の変更」には、公開面が参照する data の変更を含める。

### 「無い」は直和で明示する

- 欠損・不在は直和で書く(`数値 | 欠損`、`見つかった(値) | なし`)。null は存在しない。
  「値が無い」事も型に書かれる——省略の禁止(ADR 0008)の型への適用である。
- データとして正常な「なし」と、系の失敗(期限超過・相手障害)は別の語彙とする。後者の体系は U13 で定める。

### body 内部の型は自由

- data はユニット間の語彙のみを対象とする。body 内部の型・表現は自由であり(内側の原則)、DB スキーマ等の内部表現は隠されたままとなる。

### data 宣言に intent は課さない

- データ形状の設計判断は、それを公開面に持つユニット・フローの intent(why / change)に宿る。
  data ごとの intent はユニット intent との二重記述になり形骸化する(ADR 0003 の教訓)。

## 捨てたもの・理由

- **動的型**: 接続の不整合が実行時の驚きになり、静かさの理念に反する。コンパイル時に拒否できる違反はコンパイル時に拒否する(第2章 2.4)。
- **構造的型付け**: 識別子の取り違え(受付ID を受注番号として渡す)が検出できない。思考実験 05 で名前的な区別の価値が確認された。
- **data をユニット内に置き公開面で輸出する案**: 共有語彙を参照するためだけに depends が発生し、「依存=通信相手」という意味が濁る。
- **data ごとの intent 必須**: 二重記述で形骸化する。強制は判断の宿る場所(ユニット・フロー)に絞る。
- **継承**: 公開面の語彙に階層は不要で、直和で表せる。深いモジュールの思想とも合わない。

## 将来の変更想定

- 型引数(ジェネリクス)は列のみ組み込みで始め、Phase 1 の実装で必要が確認されたら導入を検討する。
- 単位付き数値(℃/℉ 等)は Normalizer 型の変換の静的検証として魅力があるが、複雑さが大きい。必要が出たら検討する(思考実験 05 の論点5)。
  → U15 として引き上げ、思考実験 06 で検証した。ADR 0010(提案)が基本型「数値」を `数値(整数部.小数部) <単位>` に置き換える案を示している。両 ADR は揃えて採否を判断する。
- data 宣言の置き場所の最終形(名前空間・可視範囲)は U14(プログラムの宣言)で定める。
- 採用時の反映先: 第1章に「データの宣言」の節を追加し(または独立の章を立て)、第2章の検証一覧に E11 を加える。

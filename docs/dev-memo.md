> 1. U23 —「`単位なし` の値とのスカラー倍は単位も型も変えない」
>   問題1(最も重い)— 9組のうち4組で、宣言のない丸めが起きる
> 問題2 —「型も変えない」の「型」が桁を含むかが未定

「`単位なし` の値とのスカラー倍は単位も型も変えない」は撤回します。

単位ありと単位なしの計算結果の単位は、単位ありの単位とします。
計算結果の型は、格納する変数の型とします。
計算途中の型は、同じ型ならその型を、違う型なら変換する型(や丸め方)を指定するものとして、検証ループで検証して下さい。

- 検証の目的は、変換する型(や丸め方)を指定するのは煩雑になるか？です。


> ## 問題3 — `整数` をスカラーにすると中間桁が大きくなる

`整数` は桁を持たないので最大 19 桁と見なすほかなく、`十進数(9.2) × 整数` は `十進数(28.2)` = 30 桁 = 16 バイトになります。ADR 0010 の「中間の桁は自動で広がる/所要記憶域は実行前に見積もれる」に反しませんが、**`整数` を桁の無い型にした代償**です。

## 問題4〜8(要点)

- **除算が未定** — ADR 0010 は「乗除算」と書いています。`割る(…)` の除数に `整数 単位なし` を書けないと `金額 ÷ 人数` が書けません
- **可換性** — 「左の型」と書くと非可換になります。「**単位を持つ側**の型と単位を保つ」と書く必要があります
- **両辺とも `単位なし`** で型が違う場合の規則がありません
- **E0019-3 と第6章 6.3 が例外を持つ規則になります**(文面の書き直しが必要)
- **序数に掛け算が書けるようになります**(`版 × 3`)。U24 が未解決のまま範囲が広がります

# 2. U14 論点1 —「`data` はシステムに属し、`expose` で外から見える」

## 問題1 — `expose` が2つの意味を持つ

第3章 3.2 の `expose` は公開面(ask の受け口・flow の出入り)で、形は3種に限られています。型の可視性を書くと4つ目の形になり、**同じ語が「通信の口」と「型の可視性」を指します**。

## 問題2(最大の未決事項)— 参照する側が何を書くのか

| 案 | 起きる事 |
| --- | --- |
| B の `depends` に A を書く | 通信していなくても依存が生まれ、**ADR 0009 が退けた「依存の意味が濁る」が再発** |
| 何も書かない | `expose` された型はどこからでも参照でき、**可視性の宣言が実質的に働かない** |
| 参照の宣言を別に持つ | 宣言が1種増える。ADR 0008 とは整合するが ADR 0009 と緊張する |

**この3案のどれを採るかで、論点1 の決定の意味そのものが変わります。**

## 問題3〜6(要点)

- **兄弟間を流れるデータの帰属に基準がありません** — A/B/共通の親の3通りに書けます
- **言語が持つ型と `量 時間` は名前空間の外にある**と明示する必要があります
- **システムを跨ぐ型の循環** — `contains` の循環は E0018-1 で禁じていますが、型の参照の循環は別です(木構造は正当)
- **外部システムの型の置き場所が消えます** — `external` は `system` 宣言を持ちません

# 3. U14 論点4・5 —「名前空間で分ける。ユニークな名前空間にする」

## 問題1 — Java のユニーク性は言語ではなく慣習が支えている

Java のパッケージ名が衝突しないのは逆ドメイン名という**慣習**によるもので、言語は同じパッケージ名を持つ2つの成果物を防げません(split package は実在の問題です)。「ユニークだから衝突しない」を前提にすると、**誰が保証するのかが書かれていない前提**になり、ADR 0008 の精神に反します。

## 問題2 — 逆ドメイン名は組織の名前を記述に持ち込む

`com.example.受注管理.注文`。**組織が変われば(買収・分社)全ての型名が変わります。** ADR 0015 の改名と同じ痛みが書き手の名前全体に及びます。

## 問題3(重要)— 逆ドメイン名は要らないはずです

論点1 で「`data` はシステムに属する」と決めました。ならば**名前空間はシステムの入れ子の経路**にするのが素直です。Java 風の名前空間を別に導入すると、システムの入れ子と名前空間という**2つの階層が並立**します。

そして**一意性はすでに保証されています** — ADR 0018 が「ルートシステムはちょうど1つ」(E0018-2)と定めているので、`ルート.内側システム.注文` はプログラム内で一意に決まります。

→ **論点1 と揃えれば、階層は1つで済み、逆ドメイン名は不要です。**

## 問題4・5

- 修飾名が長くなります(`受注基盤.受注管理.受付.注文`)。短縮の記法は「省略の禁止は宣言の欄の話、参照の記法は別」という整理の後で決まります
- **E0014-3 の検査範囲** — 名前空間ごとにすると、別の名前空間の `ＩＤ` と `ID` が共存できます。修飾名では区別できても読み手の目には見分けが付きません

# 4. U14 論点2 —「一般的な区分名は言語の組み込みとする」

## 問題1 — 第6章 6.1 の指針と正面から衝突します

思考実験 12 を受けて**ついさっき**置いた指針です。

> **不在の区分名は、何が無いのかを言う。** `欠損`(計測が取れなかった)・`暦の外`(その暦では呼べない)・`訳なし`(訳文が無い)のように、不在の理由が名前に出る。言語が単一の `なし` を持たないのは、不在の意味が文脈ごとに違うためである。

`なし` を組み込みにするなら、**この指針を取り下げるかどうかを先に決める必要があります**。

## 問題2 — `理由` は組み込みにできません

`失敗(理由)` の `理由` は系ごとに中身が違います(在庫不足・与信超過・変換失敗・訳なし)。共通の中身が無いのでテキストで持つほかなくなり、テキストを制御フローの条件に使うと **E0013-1(コンパイル時エラー)となりコンパイルできません**。

## 問題3 — `失敗` は U13 の名前を先に消費します

U13(失敗の体系。ドメインの失敗と系の失敗の区別)は**未着手**です。`失敗` を今組み込みにすると U13 が使える名前を1つ取ってしまいます。**U13 の後が素直です。**

## 問題4・5

- 言語は既に `桁溢れ`・`逆行`・`存在しない`・`二度ある`・`暦の外` を持ちますが、これらは**特定の操作の結果**であり汎用の区分ではありません。`なし`・`失敗`・`理由` は性質が違うので、**線引きの基準**が要ります
- 組み込みの区分が**型か区分か** — `照会結果.なし` と `検索結果.なし` が同じ値なら型を跨いで渡せてしまい、名前的型付けが緩みます。別の値なら組み込みの意味は「名前の予約」だけになります

- 目的: 仕様の検討を領域の木に分け、領域ごとの作業を並列に進めても、共通のファイルで衝突しないようにする

それまでは、どの検討も計画書([docs/PLAN.md](../PLAN.md))・道のりの図([docs/roadmap.html](../roadmap.html))・[README.md](../../README.md) の三つに書き足していた。

いまは、全体を表すファイルは領域を取り込むだけの枠であり、検討の作業は自分の領域のファイルだけを書き換える。

## 領域の形

領域は、この `docs/areas/` の下のフォルダである。段の数は決めない。どの段の領域も、次の二つのファイルを持つ。

| ファイル     | 中身                                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------- |
| `README.md`  | 上位の領域への道筋・担当する課題と状態・次に決める事・課題と ADR と思考実験の表・他の領域への入力・下位の領域・経緯 |
| `roadmap.js` | 道のりの図に差し込む、その領域の節(関係図と一覧と検証ループ)と、下位の領域の名前の一覧                              |

`docs/areas/` そのものも一つの領域(領域の根)であり、この README と、一段目の領域の名前を並べた [roadmap.js](roadmap.js) を持つ。

- 道のりの図([docs/roadmap.html](../roadmap.html))は、領域の根の `roadmap.js` を読み込み、`children` に並んだ名前をたどって、木の葉まで各領域の `roadmap.js` を差し込む
- 計画書([docs/PLAN.md](../PLAN.md))は、Markdown に取り込みの仕組みが無いため、この README へリンクする。木は README のリンクを親から子へたどって読む
- ADR と思考実験の頭の「領域:」には、一番深い領域を書く

## 段を増やしても衝突しないための規則

1. **子の一覧は親だけが持ち、親の状態は子から写さない。**
   親の README は子へのリンクを並べるだけで、子の状態の要約を書かない。子の状態が変わっても、親のファイルは変わらない
2. **領域を作る・除く・移すのは予約の作業とする。**
   main の上で、子のフォルダ(中身は雛形)と、親の README・`roadmap.js` の一行を一度に作ってから枝を切る。兄弟の領域を同時に足しても、予約は一度に一つなので衝突しない
3. **並列にできるのは、互いに祖先と子孫の関係に無い領域どうしである。**
   検討の作業は一つの領域とその下を持ち、その外を触らない。上の段の論点を扱いたい時は、その領域の作業を別に立てる

## 作業の三つの種類

| 作業の種類 | 並列にできるか                               | 触ってよいファイル                                                                                                                                                    |
| ---------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 予約       | できない(main で一度に一つ)                  | [docs/numbering.md](../numbering.md)・領域の作成と移動(新しいフォルダの雛形と、親の README・`roadmap.js` の一行)                                                      |
| 検討       | できる(祖先と子孫の関係に無い領域どうしなら) | 持っている領域とその下のファイル・予約したファイル・その領域の既存の思考実験と提案中の ADR                                                                            |
| 採用と節目 | できない(main で一度に一つ)                  | `docs/spec/`・ADR の状態の行・[docs/PLAN.md](../PLAN.md) の第1節と第4節・[docs/roadmap.html](../roadmap.html) の第1節と第3節・[README.md](../../README.md) の「状態」 |

- 検討の作業が仕様書の章を直したくなったら、領域の README の「次に決める事」に書いておき、採用の作業で反映する
- ADR の採用と仕様書への反映は、suzukimitsuru の判断の後に一本ずつ行う
- 二つの領域に跨る ADR は主な課題の領域に置き、相手の領域へは「他の領域への入力」で渡す
- 経緯の見出しは「日付 + 名前」にし、節の番号を振らない

## 領域を作る手順

予約の作業として、main の上で一度に行う。

1. 親の領域のフォルダの下に、新しい領域のフォルダを作る(フォルダ名に空白を入れない)
2. 新しい領域の `README.md` を、既存の領域の README の見出しに揃えて作る。頭に上位の領域への道筋を書く(例: `[全体](../../../PLAN.md) › [検討の領域](../../README.md) › [通信と失敗](../README.md) › 失敗の体系`)
3. 新しい領域の `roadmap.js` を作る。中身は次の形である

   ```js
   Shidzuku.area({
     path: "areas/通信と失敗/失敗の体系",
     title: "失敗の体系",
     children: [],
     html: `<p class="lead">状態: …</p>`,
   });
   ```

4. 親の README の「下位の領域」にリンクを一行足し、親の `roadmap.js` の `children` に名前を一つ足す
5. 新しい領域へ移す課題・ADR・思考実験があれば、[docs/numbering.md](../numbering.md) の領域の欄と、各ファイルの頭の「領域:」を書き換える
6. commit してから、検討の枝を切る

## roadmap.js の書き方

- リンク先は、どの段でも [docs/roadmap.html](../roadmap.html) から見た相対パスで書く(例: `href="experiments/32-実行モデルと順序.md"`)
- 断片の中で `id` を作らない(本体の図と重なるため)
- `html` は JavaScript のテンプレート文字列なので、本文に逆引用符と、ドル記号と波括弧の組を書かない
- 図(SVG)の節点は、`<rect>` と `<text>` をまとめて `a.node` で包む。様式は本体の物がそのまま効く
- 他の領域と結ぶ関係は線を引かず、節点の下に「他の領域: 〜」と注記する

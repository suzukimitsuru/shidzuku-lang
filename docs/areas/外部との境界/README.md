- 担当する課題: 外部世界との境界(U12)・役割の向きと通信の関係(U20)
- 状態: 検討中。ADR 0015(C4 モデルの命名の取り込み)・ADR 0018(システムの入れ子)が一部を決めている。思考実験 33(外部との境界)で外部依存の書き場所の三案とフローの端点の二案を書き比べ、論点を出した。何も決めていない。試作の間は外部を書かない(ADR 0033(試作を先に置く進め方))。実行モデルからの入力を一件保留
- 道のりの図: この領域の節は [roadmap.js](roadmap.js) に書き、[docs/roadmap.html](../../roadmap.html) の「検討の領域」に差し込まれる

## 次に決める事

- 思考実験 33(外部との境界)の論点1〜10 を suzukimitsuru に示し、外部世界との境界(U12)と役割の向きと通信の関係(U20)の ADR を起案する。決めるのは外部を持つ題材(注文管理 等)を試作に足す前でよい。それまでの試作は外部を書かず、題材の両端を、試験から値を流し込む口と値を受け取る口にする(計画書 第4節「仮置き」、ADR 0033(試作を先に置く進め方))。U12 と U20 は同時に採否を判断する
- 起案の前に、外部依存の書き場所(論点1)の三案——`depends` を広げる案・システムの `depends` に担い手を書く案・コンポーネントにも `external` を置く案——を一つに絞るかを確かめる。
  W0018-1 の扱い(論点7)とフローの端点(論点2)の答えの幅は、これで狭まる
- 外部の公開面と期限の形(論点2・3)を、思考実験 08 の翻訳サービスと商品原簿にも当てる
- 採用の時に仕様書へ反映する所の候補: 第1章 1.4(「外部」という語の範囲)・1.8、第2章 2.4 の未定事項(「外部」の語義と E0013-4 の範囲)、第4章 4.1・4.6、第6章 6.6
- システムの公開面(ルートの system の `expose`)には、流量(`pressure`)と配達保証を書く場所が無い。細い縦の試作では試験の口の振る舞いを動作環境が決め打った([examples/細い縦の試作](../../../examples/細い縦の試作/README.md) の「試作で分かった事」)。外部を書く時に、境界の端の流量と配達保証をどこに書くかを、思考実験 33 の論点2(フローの端点)と併せて決める
- 受けた入力を片付ける: [実行モデル](../実行モデル/README.md) の「他の領域への入力」(ADR 0032 の採用までは仮の入力)から、外部への入出力を待つ所に含めた事(ADR 0032 の決定2)。時計で始まる仕事は外部の入力とは見ず、記述の中の `timer` とする事(ADR 0032 の決めた事2(時計の仕事))

## 経緯

### 2026-11-05 思考実験 33 で外部との境界を書き比べた

外部世界との境界(U12)と役割の向きと通信の関係(U20)の材料として、[思考実験 33(外部との境界)](../../experiments/33-外部との境界.md) を行った。**何も決めていない。**
題材は思考実験 02 のシステム「センサー収集」、ADR 0031 の机上検証1(受注の一生)の PaymentBridge と決済代行、比べるために思考実験 08 の外の相手である。
領域の木に分けてから(2026-11-05)初めての検討であり、実行モデルの領域の検討と並べて進めた。

| 見た事             | 分かった事                                                                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 外の相手の棚卸し   | 14 のコンポーネントのうち 10 が外の形式で授受する。`external` の相手は 5、外部の技術(データベース)が 3、actor の窓口(HTTP)が 2                |
| 外部依存の書き場所 | 送ってくる相手と往復する相手まで書けるのは、コンポーネントにも `external` を置く案だけ。代わりに全てのコンポーネントに一行増える(9 が `none`) |
| フローの端点       | 外部を端点に書くと、外部の公開面・期限の測り手・外から来る流れの属性・`restart`・鍵の五つで今の規則が立たない                                 |
| 外部の時刻表現     | 入りの道で `時点にする` を書ける層が無い。時差は `時間帯` に分かれない。起動からの経過は型に無い                                              |

- **「外部」は二つの軸の語だった。** `external`(誰が相手か)と、役割「境界」(何の形で授受するか)である。思考実験 08 の論点1・2(「境界」が指す外部・役割の向きと通信)は、二つの軸を一つの語で呼んだ所から起きていた。
  U12 と U20 を同じ段で決める理由は、外部を端点に書いた時にだけ二つの範囲が重なる事にある。
- **システムの `expose` が、動作環境の受け口か、境界の層が外の形式で受ける入口の要約かが書かれていない。** SensorIntake は MQTT、SearchGate は HTTP で受けている。
- **外部への要求には期限を書く場所が無く、その失敗は ADR 0031(失敗の体系)の四つの置き場のどれにも決まって入らない。** 障害にすると、durable の再送が回数の無い再試行になる。
- **ADR 0031 の決定6(記述の中の接続は全てフローに現れる)が、W0018-1 の非対称を逆向きにしていた。** 外部への `depends` は、今の判定では必ず W0018-1 になる。
- **actor が届く所は、入口(`expose`)と、外部を経た出口の二つに分かれた。** センサー収集の運用者は、通知基盤の向こうに居る。
- 次は、論点を suzukimitsuru に示し、外部依存の書き場所の案を絞ってから ADR を起案する。

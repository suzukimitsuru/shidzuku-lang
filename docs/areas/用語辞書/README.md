### 2026-10-14 思考実験 29 で用語辞書による名前の規則を検討した

suzukimitsuru の指示により、用語辞書(名詞・動詞を記述者が宣言する仕組み)を言語が提供する事で、名前(コンポーネント名・クラス名・メンバー名・メソッド名・変数名)を規則に従わせられるかを
[思考実験 29(用語辞書による名前の規則)](../../experiments/29-用語辞書による名前の規則.md)で検討した。**何も決めていない。**

- 思考実験 01〜28 の名前を棚卸しし、揺れを拾った。識別子を表す語(`ID`・`番号`・`コード`・`キー`)、公開面の名前の形(`受注` と `請求する`)、「の」の有無(`受注の照会` と `実績照会`)、
  送り仮名(`引当済` と `引当済み`)、同じ事態の別の語(`在庫不足`・`在庫なし`・`在庫切れ`)、字種の混在、`受注` が公開面の名前と区分名の両方に現れる事である。
- 用語辞書を仮に置き、語の**役**を品詞ではなく Shidzuku の宣言の種類に結び付けた(担い手・物・働き・添える語)。
- 同日、suzukimitsuru の指示で三つを改めた。
  - 呼び名を「用語辞典」から**「用語辞書」**に改めた。規則は呼び名に依らないため、結論は変わらない。母国語と英語の対応表を兼ねるなら「辞書」の方が合う。
  - **用語辞書に母国語と英語の対応表を兼ねさせ、コードの名前は英語(ASCII)だけで書く**前提を置いた。記述者の名前を UTF-8 とした ADR 0014(識別子と言語語彙の表記)の決定3 と食い違うため、論点7(名前を英語に限る事)に残し、ADR 0014 は改めていない。
  - 置き場の三案の比較、同じ目的の lint の調査、Swift の API 設計の指針の要約を足した。

| 規則                   | 母国語で書く場合           | 英語(ASCII)で書く場合      |
| ---------------------- | -------------------------- | -------------------------- |
| 語の閉包               | 言語が強制できる           | 言語が強制できる           |
| 退けた語               | 言語が強制できる           | 言語が強制できる           |
| 語の並びの衝突         | 言語が強制できる           | 言語が強制できる           |
| 大文字小文字の形       | —                          | 言語が強制できる           |
| 対応の一意             | —                          | 言語が強制できる           |
| 役の一致               | 自然言語の性質の宣言が要る | 英語を仮定すれば強制できる |
| 表現語と型             | 自然言語の性質の宣言が要る | 英語を仮定すれば強制できる |
| 欄名と型名             | 強制できない               | 強制できない               |
| 定義の質・英語である事 | 強制できない               | 強制できない               |

- **答えは「一部は出来る」で、前提を置くと出来る所が広がる。** 語の閉包・退けた語は記述者の宣言と照らすだけなので、自然言語を仮定せずに強制できる
  (ADR 0003(検証不能な意図の記述形式)が拒否語リストを退けた理由には当たらない)。前提の下では語の切れ目が文字で決まり、日本語の分け方の曖昧さが消える。
  名詞と動詞の規則は、英語を仮定すれば強制できるが、言語が特定の自然言語を仮定する事になる(論点8(英語の文法を仮定するか))。
- 前提を採ると、第5章 5.6 の可逆な符号化は要らなくなり、用語辞書が母国語への対応表になる。ソースを読む人が英語を読む費用は残る。
- **置き場の三案**(言語の宣言にする案・言語の外に置き lint で見る案・新しい宣言を足さない案)を11の物差しで比べた。
  lint の案は Rust・TypeScript にも当てられる汎用性があり、言語の宣言にする案は強制と図・ログへの投影に強い。辞書の書式を言語に依らないファイルにすれば、二つは組み合わせられる。
  新しい宣言を足さない案は、母国語との対応表を持てないため前提と両立しない。
- **同じ目的の lint** は、調べた範囲では見つからなかった。cspell(辞書と禁じる語)・typescript-eslint の `naming-convention`(宣言の種類ごとの形)・PMD の `LinguisticNaming`(名前と型の食い違い)・
  codic(日本語から英語の名前の提案)・Contextive(用語集の表示)がそれぞれ一部を持つ。母国語との対応表を検査に使う所が、shidzuku-lint で新しく作る所になる。
- 2026-10-15、suzukimitsuru の指示で「用語」を「語彙」に替えた「語彙辞書」を比べ、**suzukimitsuru の判断で「用語辞書」のままとした**。
  語彙は語の集まりで見出し語を指さず、仕様の「言語が定める語彙」と紛れるためである。他の候補(単語辞書・命名辞書・対訳辞書・ドメイン辞書)も比べ、次点は「単語辞書」とした(思考実験 29 の第1節 1.4)。
  キーと値の対応の型は、第6章 6.6 の通り対応表(map)と呼び、辞書とは呼ばない(suzukimitsuru の判断)。
- 論点は9つ。名前空間(U14)と外部世界との境界(U12)の答えに依るため、課題(U)は足していない。論点7 は記述の表記(U17)の決定を改めるため、別の課題として切り出す事もできる。

### 2026-10-15 思考実験 30 で開発の流れの中で用語辞書を育てる形を検討した

suzukimitsuru の指示により、システム・人(actor)・外部システムから記述し、次にコンポーネント、最後に欄や DB の項目を記述してゆく流れの中で、
用語を記述の中で定義して用語辞書を育てる形を、[思考実験 30(開発の流れと用語辞書)](../../experiments/30-開発の流れと用語辞書.md)で検討した。思考実験 20(対になる通信)の通販を、思考実験 29 の前提(コードは英語(ASCII))で段を追って書き直した。**何も決めていない。**

- 流れは Shidzuku の段の順(システム → コンポーネント → コード)と一致する。ユーザーの種類は `actor` に当たる。
- 辞書を先に書き上げる案は採らず、**宣言の場所で名前の母国語と定義を書き、宣言を持たない語は使った段の辞書に足す**形で書いた。辞書はシステムの入れ子に沿って分かれる。
- 新しい語は段ごとに 13・10・8 の計 31 で、宣言から定義されたのは5に留まった。語の大半は辞書のブロックに入る。名前1つにつき新しい語がほぼ1つ要った。
- 複合語の名前9つのうち7つで、語を並べた母国語の名前が業務の名前と違った(`OrderNumber` は `注文番号` で、業務の語は `受注番号`)。名前ごとの母国語の名前は宣言の場所に書く事になる。
- 詳細の段で、内側の辞書の語(`stockout`・`cancel`)が外の型に現れ、外の辞書へ移す**語の昇格**が起きた。データ宣言の届く範囲(第5節 5.10)と同じ形である。
- DB の列は Shidzuku の記述に現れないため、辞書を書き出して shidzuku-lint で SQL の列名を検査する形になる。
- 無理なく扱う形として、コンパイラが無い語の置き場と雛形を示す事、辞書を段ごとに書き出して関係者のレビューに使う事を挙げた。
- 論点は7つ(データ宣言の定義の文・母国語の名前を必須にするか・段ごとの母国語の名前・コンポーネントの辞書・語の範囲と名前空間・役の綴り・未熟な定義)。

### 2026-10-16 用語辞書から母国語の欄を除き、公開する名前への限定を検討した

suzukimitsuru の指示により、[思考実験 29(用語辞書による名前の規則)](../../experiments/29-用語辞書による名前の規則.md)と
[思考実験 30(開発の流れと用語辞書)](../../experiments/30-開発の流れと用語辞書.md)を改めた。**何も決めていない。**

- **用語辞書から母国語の欄を除いた。** 辞書の中身は英語の語・役・定義になる。母国語との対応(図・ログ・診断に母国語の名前を出す事)は、ローカライズと共に後で考える。
  コードの名前を英語(ASCII)だけで書く前提は残した。定義はテキストであり、語の訳ではない。
- これに伴い、思考実験 29 から対応の一意(英語の語と母国語の語の一対一の対応)と、母国語の欄の重なりで同義を疑う手掛かりを外した。
  新しい宣言を足さない案は、母国語との対応表を持てない事ではなく、働きと担い手の語・退けた語・定義を置けない事で外れる。
  思考実験 29 の論点3 は「ローカライズ」に改め、思考実験 30 で見えた事(語を並べても業務の名前にならない、段ごとに呼び方が違う)を渡す事柄として並べた。
  思考実験 30 の論点2(母国語の名前を必須にするか)と論点3(段ごとの母国語の名前)は、ローカライズへ送った。
- **辞書に無い語を公開する名前に使わせない形を検討した**(思考実験 29 の第9節(公開する名前への限定))。
  - コンポーネントの内側の名前か否かで分ける。システム・コンポーネント・`actor`・`external`・公開面・`flow`・データ宣言・欄・区分の名前は公開する名前、
    `state`・階層・照合器の名前は宣言に現れる内側の名前、body の中の名前と DB の表と列は内側の名前である。
  - どちらに入るかは宣言の種類で決まるため、限っても語の閉包は「言語が強制できる」のままである。情報隠蔽と同じ所に線が引け、データ宣言が公開面の語彙だけを対象とする事(ADR 0009)と揃う。
  - 公開する名前の語は、その名前が見える範囲の最も内側のシステムの辞書に置く。語の昇格は公開の段が上がる事と同じになり、コンポーネントの辞書は要らなくなる。
  - 既存の言語では可視性(Rust のクレートの外から届く `pub`、TypeScript のパッケージの入口からの `export` など)で線を引く。
    FxCop の CA1704・CA1726 が、外部から見える識別子に限って現場の辞書と照らし、廃した語に代わりの語を示した先例である。
  - 残る問題は、内と外の語の食い違い(ログの語が揃わない)、退けた語を内側にも掛けるか、`state`・階層・照合器の名前をどちらに入れるか、
    名前を ASCII に限る事も公開する名前に留めるか(ADR 0014 を改める幅が狭くなる)である。

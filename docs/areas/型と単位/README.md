## 型と単位の決定(U9・U15・U22・U23・U24)

### 文字列を廃し、テキストとバイト列を置く(ADR 0013)

- ADR 0013 は U9 の基本型から「文字列」を外してテキストとバイト列に置き換え、併せて U3 の内部階層に**役割**(境界・解析・領域・整形)の宣言を足した。
- 層をコンポーネントの属性にする案は、情報隠蔽の単位・障害境界・配置単位が層で割れるため却下し、既存の `layers` の拡張とした(思考実験 01・03 で机上検証)。
- ADR 0009・0010・0013 は基本型を共に改訂するため揃えて判断する予定だったが、**0013 のみが先に採用された**(2026-08-28)。
  層(役割・照合器・E0013-1〜E0013-4)は仕様書に入り、基本型(テキスト・バイト列)は入らないねじれが残った。
  ねじれの内容と解消の条件は ADR 0013 の「採用の記録」にあり、翌日のステップ2 の採用(2.8)で解消した。

### 数値と単位 — 十進固定小数点の系譜(ADR 0010 → 0017)

> **この項は 2026-08-25〜08-29 時点の記録である。ADR 0010・0017 は 2026-09-03 に破棄し、数値型は ADR 0021 が引き取った(第7節 7.1)。**

- U15 は ADR 0009 が保留した単位付き数値を引き上げたものであり、思考実験 06 で検証して ADR 0010 を提案した。
  U15 は U9(基本型「数値」の置き換え)・U12(単位の付け外しは型の外へ出る操作)・U13(桁溢れの位置づけ)・U5(多倍長整数を持つ出力先が要る)へ入力を残している。
- 思考実験 07 で ADR 0010 の反証を探し、書けない数(循環小数・無理数)と書けない計算(平方根・累乗)を洗い出した。
- 形式は「単位付き・静的位取りの十進固定小数点数」であり、既存の体系(PL/I の `FIXED DECIMAL(p,q)`・Ada の十進固定小数点型・SQL の厳密数値型)との対応と、
  二進浮動小数点(IEEE 754)との違いを ADR 0010 に対比表として置いた。
- ADR の様式(ADR 0007)に従い「結果(利点と欠点)」を加えた。要点は**実行時の驚きを、記述の重さとして前払いする**であり、
  分散した複数ノードで同じ計算が同じ結果になる事(Raft の前提・ADR 0001)を利点の中心に置いた。
- 指数部は「桁の窓の位置」を解くが「窓の幅」は解かないため、静的指数(型に書く)を採用し、動的指数(十進浮動小数点)は棄却して ADR 0010 を改訂した(2026-08-25)。
- **ADR 0017(提案)は、その重さを厳密さが要る値だけに絞るものだった**(2026-08-28)。
  数値型を `実数`(IEEE 754 binary64)と `十進数`(0010 の型)の2つとし、主に使うのは `実数` とした。
  0010 の決定は1つも取り消さず、量と単位の検査(E0010-1・E0010-2・E0010-5)は両方の型に載せた。
  既定は置かない(型名は必ず書く。省略の禁止・ADR 0008)——「主に使う」は指針であって省略時の補完ではない。
- 分散ノードでの結果の一致は、strict IEEE(binary64 のみ・最近接偶数固定・FMA と再結合の禁止)・超越関数の正しい丸め・合算順序の固定で保つ。
  NaN・±∞・-0 は値として持たず、生む演算は失敗とする(U13 への入力)。外部の double をそのまま受けられるため、U12 の境界も軽くなる。
- ADR 0017 は起案時 0016 を名乗っていたが、同日に採用された ADR 0016(検証番号の採番規則)と衝突したため振り直した(2026-08-29)。
  併せて本文の E21・W5・W6 と ADR 0010 由来の E12〜E16・W3・W4 を `E<出自>-<連番>` 形式へ改めた。

### 基本型の棚卸しと、時間・暦(U22・ADR 0019・0020)

- ステップ2(基本型)の検討で、**確定しているのは数値だけである**事が分かった。
  ADR 0009 は基本型を本文1行で挙げているにすぎず、思考実験 05 が検証したのは構成子(直積・直和・識別子型・列)であって基本型ではない。
  文字列は ADR 0013 が、数値は ADR 0010・0017 がそれぞれ思考実験を伴って作り直したが、
  **真偽・時刻・期間・時間量は一度も検証されておらず、整数は一覧にすら無かった**。
- これを U22「基本型の体系(数値以外)」として登録し、思考実験 09 で検証して ADR 0019 を提案した(2026-08-29)。
  基本型を `論理・整数・実数・十進数・テキスト・バイト列・時点・日付・時刻・時間帯` の10 に確定し、
  `期間`(直積で書ける)と `時間量`(`量 時間` の値)を外した(数値の3つは後に ADR 0021 が置き換え、現在は11種である)。

決まった事は次の五つである。

- **`日付` は紀元前10000年から西暦9999年までを表す**(年は天文学的年番号の符号付き整数。紀元の欄を分けると比較と減算が分岐する)。
  ADR 0013 が文字列を廃した結果、締め日・誕生日を書く場所が消えていたための新設である。
- **暦は `日付` の型の欄とする**——ADR 0010 が数値に単位の欄を課したのと同じ形であり、`1582-10-04` がユリウス暦かグレゴリオ暦かが型から読める。
  暦の換算は日番号の付け替えであり、単位換算と違って**常に厳密で往復も一致する**。
  言語が持つのは算術暦(グレゴリオ暦・ユリウス暦)だけとし、元号・イスラム暦は版が変わる表を要するため持たない(後に ADR 0020 が記述者の宣言として許した)。
- **`時間帯` を基本型に置く。** ログ行の `2026-08-29T14:30:00+09:00` は「いつ起きたか」と「どこの時計で読んだか」が混ざった外部表現であり、
  `時点` と `時間帯` を分けて持てば他の時間帯への読み替えは欄の差し替えになる——**変換ではなく読み替えであり、`時点` は動かない**。
  tzdata の版依存は境界・整形の役割の内側に閉じ込められ、複製された状態機械は割れない(ADR 0001 の前提が保たれる)。時間帯の扱いは U12 へ送る。
- **日時は基本型に置かず直積で書く**(暦の読みは `日付`+`時刻`、時間帯付きは `時点`+`時間帯`)。
  暦の値に `量 時間` を足す演算は持たない——「02:30 の3時間後」は時間帯が無ければ決まらないため、時間軸の加算は `時点` の上で行う。
- **`時点` はシステム時刻の一点とする。** `instant` は体系によって意味が正反対である(Java はシステム時刻、Rust は経過時間計)ためである。
  `時点 - 時点` を持たず、期限は `量 時間` でのみ宣言できる。うるう秒は持たない(表の版に依存すると Raft の前提が壊れる)。

整数と論理型を置いた理由は、他の決定の副作用である。

- `実数` は 53 ビットしか持たないためナノ秒の時点(19 桁)を表せず、`十進数(19.0)` は 8 バイトで足りる値に 16 バイトを払う。
  **ADR 0017 が数値型を軽くした副作用として 19 桁の値の置き場所が消えていた**事が、整数を置く直接の理由である。
- 論理型は置くが、置き場所を body に限る(公開面とデータ宣言には名前の付いた直和を書く)。8実験の公開面に真偽は一度も現れなかった。

### 数値型の確定(ADR 0021・0022)

- 破棄した 0010・0017 の後継として、思考実験 14〜18 を経て ADR 0021 を起案し、2026-09-16 に採用した。
  幅(`dec` は宣言した桁)が上限を、位取りが刻みを決める形である。経緯は第7節 7.1 にある。
- ADR 0022(2026-09-17 起案・同日採用)は量を比率・計数・計量・位置の4種別に分けた。
  版・ページ番号・添字は**位置**の量になり、足し算が型で落ちる(U24)。

### U23 — 「`単位なし` の値とのスカラー倍は単位も型も変えない」

> **この節は 2026-08-29 時点の記録である。U23 は ADR 0021(採用、2026-09-16)が解いた。**
> 数値型を幅と位取りで分け直し、暗黙の変換を1本も置かなかったため、ここに挙げた問題1〜7 は前提ごと消えている
> (問題8 の序数は U24 として残る)。以下は、その決着に至る前の検討の記録として残す。

#### 問題1: 9つの組み合わせのうち4つで、宣言のない丸めが起きる

規則を字義どおり全組み合わせに当てると次になる。

| 単位を持つ側 | `単位なし` 側 | 結果(規則どおり) | 起きる事                                             |
| ------------ | ------------- | ---------------- | ---------------------------------------------------- |
| `整数`       | `整数`        | `整数`           | 安全(既存の規則)                                     |
| `整数`       | `十進数`      | `整数`           | **小数を掛けて整数を返す。宣言のない丸めが起きる**   |
| `整数`       | `実数`        | `整数`           | **同上。加えて近似が厳密に化ける**                   |
| `実数`       | `整数`        | `実数`           | 2^53 を超える整数は丸まる(W0019-1 と同じ性質)        |
| `実数`       | `実数`        | `実数`           | 安全(既存の規則)                                     |
| `実数`       | `十進数`      | `実数`           | **`十進数` → `実数` の丸めが暗黙に起きる**           |
| `十進数`     | `整数`        | `十進数`         | 安全。`整数` → `十進数` は原理的に丸めが起きない     |
| `十進数`     | `十進数`      | `十進数`         | 安全。ただし**桁は和になる**(型は同じでも桁は変わる) |
| `十進数`     | `実数`        | `十進数`         | **近似が厳密に化ける。丸めが宣言されない**           |

太字の4つは、ADR 0010 の「誤差の出る場所を3つに限る」と ADR 0017 の総括「型の名前と実際の性質を一致させる」に反する。
**とくに `十進数 円 × 実数 単位なし` は、金額が静かに近似になる経路である。** ADR 0017 が「主に使う型は `実数`」と決めたため、
`単位なし` の値が `実数` で書かれる事は起きやすい。W0017-1(通貨の量に `実数` を使っている)はこの経路を検出しない。

→ **スカラーに使える型を絞る必要がある。** `整数 単位なし` だけに限れば、上の表の危険な4つは全て消える
(`整数` → 他の型への変換は原理的に丸めが起きないか、起きる場合は W0019-1 が既に警告する)。

#### 問題2: 「型も変えない」の「型」が桁を含むかどうかが決まっていない

`十進数(7.2) 円 × 十進数(1.4) 単位なし` の結果を、ADR 0010 の乗算規則は `十進数(8.6) 円` とする(整数部・小数部とも和)。
「型も変えない」を字義どおり取ると `十進数(7.2) 円` になり、**小数部が 2 に切り詰められる = 宣言のない丸めが起きる**。

→ 「型の**種類**は変えないが、桁は ADR 0010 の規則で決まる」と書き分ける必要がある。

#### 問題3: `整数` をスカラーにすると中間の桁が大きくなる

`整数` は桁を持たない型であるため、乗算では最大値(19 桁)と見なすほかない。

| 式                            | 結果の桁       | 記憶域            |
| ----------------------------- | -------------- | ----------------- |
| `十進数(7.2) × 整数 単位なし` | `十進数(26.2)` | 28 桁 = 16 バイト |
| `十進数(9.2) × 整数 単位なし` | `十進数(28.2)` | 30 桁 = 16 バイト |

ADR 0010 は「中間の桁は自動で広がる」「所要記憶域は実行前に見積もれる」としているため**規則には反しない**が、
**`整数` を桁の無い型にした代償が乗算の中間桁に出る**事は記録しておく。値が名前を得る所で `収める` すれば元の桁に戻る。

#### 問題4: 除算の側が決まっていない

ADR 0010 は「`単位なし` の値との**乗除算**(スカラー倍)は単位を変えない」と書いており、除算を含む。
しかし `十進数` の除算は `割る(<被除数>, <除数>, <結果の桁>, 丸め <方式>)` であり、除数に `整数 単位なし` を書けるかが決まっていない。
乗算だけ決めると、`金額 ÷ 人数` が書けないまま残る。

#### 問題5: 可換性 — 規則の書き方が非対称になる

乗算は可換である。`整数 単位なし × 十進数 円` と `十進数 円 × 整数 単位なし` は同じ結果でなければならない。
規則を「左の型と単位を保つ」と書くと非可換になる。**「単位を持つ側の型と単位を保つ」**と書く必要がある。

#### 問題6: 両辺とも `単位なし` で型が違う場合の規則が無い

`整数 単位なし × 実数 単位なし` には「単位を持つ側」が無い。この場合に規則が適用できない。
E0019-3(コンパイル時エラー)のままとするのか、どちらかへ寄せるのかを決める必要がある。

#### 問題7: E0019-3 の文面を書き直す事になる

現在の E0019-3 は「3つの数値型が明示の変換なしに混ざる」である。スカラー倍を許すと例外が1つできるため、
「混ざる」の定義を書き直す必要がある。**第6章 6.3 の「3つの数値型は暗黙に混ざらない」も、例外を持つ規則になる。**

#### 問題8: 序数(U24)に掛け算が書けるようになる

`版 整数 単位なし × 3` が書けるようになる。序数と基数の区別(U24)が未解決のまま、書ける範囲だけが広がる。

### 2026-08-29(2)の採用と検証ループ — ステップ2

ADR 0009・0010・0017・0019・0020 を採用した。**2026-08-28 から続いていた「層は仕様書に入ったが基本型は入っていない」ねじれは、これで解消した。**

- **第6章「データと型」を新設した**。データは段に属さず段を跨ぐため、第4章(通信)・第5章(表記)と同じ立場として段の順の後ろに置いた。
  内容はデータ宣言と構成子(6.1)・基本型10(6.2)・数値3種と量と単位(6.3)・時間の3層と暦(6.4)・型が告げる事(6.5)・未定事項(6.6)である。
- **他の章への反映**: 第3章 3.3(E0009-1・E0010-1〜5・E0019-1〜6・E0020-1〜3 と対応する警告。E0008-1 の対象に型の欄を追加)、
  第4章 4.2(`deadline` の欄が `量 時間` を持つ数値になった)、第5章 5.3(型の語彙を8区分)、第2章 2.1(公開面の型の参照先)。
- **ADR 0013 の基本型(テキスト・バイト列)も同時に入った**。反映先の章が無いために保留されていたものである。
- **検証ループ(思考実験 12)**: 思考実験 01〜11 の全データを、仕様書(第6章)だけを読んで書き直した。
  **11 実験の全データが書けた**。真偽は一度も要らず、`期間`・`時間量` を外した事でも困らなかった。数値型の使い分けは 6.3 の3列がそのまま当たった。
  一方で5つの論点が出た。
- **仕様書の修正で閉じた事**: E0019-1 の対象を**型の入れ子**(`list<論理>`・直和の区分の引数)へ広げた(論点3)。
  不在の区分名は「何が無いのかを言う」という指針を 6.1 に足した(論点5)。
- **新設した課題**: U23(数値型を跨ぐスカラー倍)。`十進数(7.2) 円 × 整数 単位なし` が E0019-3 で落ちる。
  単位の側は既に答えを持つ(スカラー倍は単位を変えない)が、型の側が決まっていない。
  `整数` → `十進数` は原理的に丸めが起きないため危険は少ないが、「暗黙の変換を置かない」の例外になるため決定が要る。
- **U14 に足した論点**: 直和の区分名の可視範囲(`理由`・`なし` が複数の `choice` に現れる)と、
  `量`・`単位`・`暦` の宣言の置き場所(トップレベルだが `contains` に現れない)。**U14 の論点は第5節に展開した。**
- **U23 の検証(思考実験 13)**: 「数える値にも `個` のような単位を持たせる」案を書き下ろした。
  **単位の軸と数値型の軸は直交しており、この案は U23 を解かない**——次元は通るようになるが、`整数` を `十進数` の式に混ぜる事は依然として書けない。
  加えて、割合・税率は本当に無次元(ISO 80000-1 の「次元が 1 の量」)であるためスカラー倍の規則はどのみち要り、
  列の長さ(E0019-4)で原則が破れ、助数詞の数だけ量の宣言が増え、採用済みの決定(個数は `単位なし`)と衝突する。
  ただし**数える単位が落とす誤りは本物**であり(ケースと個の換算忘れ、件数と行数の取り違え)、
  第6章 6.3 の指針を「換算比を持つなら数える単位にも付けてよい」へ緩める事は有効である(指針の明確化で足りる)。
  U23 そのものは型の軸で解く。実験は `倍する(<値>, <整数>)` という**名前のある操作**を推している——例外を作らずに済むためである。
- **新設した課題**: U24(序数と基数の区別)。`版`・`ページ番号`・`列の添字`・`連番` は数えた値だが足し算に意味が無い。
  ADR 0010 が量と単位で「距離 + 重さ」を落としたのと同じ問題が、数える値の中に残っている。

### 2026-09-03 U23・数値型全体 — ADR 0010・0017 を破棄し、思考実験 14 から再検討する

第6節 6.1 の指摘(9組中4組で宣言のない丸めが起きる)を受け、suzukimitsuru は**スカラー倍の規則だけでなく数値型の設計そのもの**を
問い直す事にした。ADR 0010(数値の型と単位)・ADR 0017(数値型の体系)を破棄し(両 ADR の「破棄の記録」参照)、
ADR 0019 の決定2(整数)・決定7(3つの数値型の変換規則)を凍結した(ADR 0019「決定2・決定7 の凍結」参照)。

思考実験 14(数値型の再検討)で、金融機関(COBOL の圧縮10進数・Java の `BigDecimal`・C# の `decimal`)と
科学技術計算(Fortran の `KIND`・単精度が主役の領域・区間演算)それぞれの他言語の実例を、
「型をいくつ持つか」「変換をどこまで暗黙に許すか」の2軸で比較した。要点は次の3つである。

- **型を分けるという Shidzuku の根本方針自体は、Swift・Ada・Haskell という強い先行例に支持されている。** 疑う根拠は出ていない。
- **C# の `decimal` が、整数 → 十進数 だけを暗黙にする非対称な橋の先例になっている。** 思考実験 13 の推奨(スカラーを `整数` に限る)を裏付ける。
- **数値の塔(Scheme・Julia)は「暗黙変換が無い」のではなく「暗黙変換の規則を型ごとに1つ書く」という第三の道である。** Haskell の型クラスは塔に見えて実際は Shidzuku と同じくらい明示的であり、「塔=自動」という連想は誤りだと分かった。

論点は7つ(思考実験 14 第10節)に整理してある。次に必要なのはこの7論点についての suzukimitsuru との相談であり、
決まり次第、新しい ADR(暫定 ADR 0021)を起案する。

#### ADR 0021 の起案(2026-09-10)

7論点への答えを含む形で **ADR 0021(数値型の体系)を起案した(提案)**。中心は2つの決定である。

- **`十進数` の宣言を刻みだけにする。** `十進数(2) 円` のように小数点以下の桁数だけを書き、上限を型から外す。
  内部表現は ADR 0010 のまま(小数桁倍した符号付き2進整数)で、幅を型ではなく値が決める(可変長)。
- **`整数` → `十進数` の昇格1本だけを暗黙にする**(C# の `decimal` の先例)。上限を持たない `十進数` には `整数` の値が
  丸めも桁溢れもなく必ず入るため、この橋は原理的に安全である。

#### `整数` の要否を調べた(思考実験 16、2026-09-15)

ADR 0021 が `十進数(0) 単位なし` を「刻み 1・上限なし・厳密」の型にしたため、**`整数` はそこへ畳めるのではないか**という問いが立った。
思考実験 16 で調べたところ、**ADR 0019 が `整数` を置いた3つの根拠(桁の宣言が全ての数えた値に掛かる・19 桁で記憶域が倍になる・
任意精度は記憶域が実行時まで決まらない)は、ADR 0021 によってすべて失効している**事が分かった。第6章で `整数` が現れる 10 か所も、すべて `十進数(0)` で書ける。

- **無くすと得るもの**: 決定6 の暗黙の橋が不要になり(U23 は問題ごと消える)、桁溢れの検査と整数専用の換算規則も消え、基本型が1つ減る。
- **無くすと失うもの**: **「厳密かつ、記憶域と実行時間の上界を型が言う」型が1つも無くなる**。添字と長さの上界も型から消え、
  `時点`・`日付`・`時刻`(内部表現が `整数`。凍結の対象外で採用済み)まで書き直す事になり、トランスパイル先では多倍長が常用になる。

当初の判定は「`整数` は残すが、残す理由を『厳密かつ上界を型が言う唯一の型だから』に書き直す」だった。

#### 前提の指定と ADR 0021 の改訂(2026-09-15)

suzukimitsuru から、その判定が立っていた前提を覆す指定が3点あった。

| 指定                                                   | 帰結                                                       |
| ------------------------------------------------------ | ---------------------------------------------------------- |
| `十進数` を Raft など外部システムとの接合には使わない  | 接合の器を数値型に求めない                                 |
| 外部との接合では 8/16/32/64 ビットの整数を限定的に扱う | 幅は**外部表現の性質**であり、境界の宣言として持てばよい   |
| `時点`・`日付`・`時刻` は内部で整数で保持すればよい    | 内部表現は実装の話であり、言語の型として `整数` を要さない |

これで `整数` を残す最後の論拠が外れたため、**ADR 0021 を改訂して数値型を2つにした**。

- **数値型は `十進数(s)` と `実数` の2つ**。数える値・添字・版・時間の量は `十進数(0)` で書く。基本型は10 から9 になる。
- **暗黙の変換は1本も無い**(初版の `整数` → `十進数` の昇格は、相手が消えたため不要になった)。U23 は問題ごと消える。
- **外部との詰め替えは境界の語彙**とする。`復号(受信, 符号付き 32 ビット, ビッグエンディアン)` は**必ず成功**し(任意精度に必ず入る)、
  外へ出す `符号化` だけが幅に入らなければ失敗する。詰め替えは `境界` の役割でのみ書ける(E0021-1 を新設)。
- **`時点`・`日付`・`時刻` は表せる範囲を仕様が定め**、内部表現は実装に委ねる(ADR 0019 決定4〜6 の読み替え。決定の意味は変わらない)。
- 残る欠点は、**内側に「厳密かつ上界あり」の型が無い**事である。何が起きるかは8つの場面に分けて ADR 0021 の欠点に書き出した。
  要点は「**期限(`deadline`)が値の大きさで超過し得る**」「**失敗し得る演算が全ての算術になる**」「**多倍長の確保による一時停止が Raft の締切に乗り得る**」の3つで、
  いずれも第0章 0.5 の「運用で驚きがない」に当たる——ただし入るのは「値が壊れる驚き」ではなく「**資源と時間が値に依存する驚き**」である。
  値が壊れる事・複製の状態が食い違う事・境界の先を壊す事は無く、危険は自ノードの資源と応答時間に閉じている。
  埋めるのは値域の宣言であり、組込み・実時間・低遅延の分散を対象に含めるなら前倒しが要る。

#### 数値型の確定と検証ループ(思考実験 18、2026-09-16)

suzukimitsuru が数値型を確定した。**`int8/16/32/64/128/256(s)`・`uint8/16/32/64/128/256(s)`・`float32/64`**、単位の欄は必須で単位なしは `unitless` である(起案時は `none` としていたが、2026-09-17 に suzukimitsuru の判断で改めた)。
位取り(小数点以下の桁数)の宣言は整数でも必須とする(`int32(0)`)。可変長の `十進数` と `実数` は廃止した。

思考実験 18 で、思考実験 06・12・13 の数値をこの型で書き下ろし、3つの論点を見つけて ADR 0021 で決めた。

| 論点                                 | 決定                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------- |
| 除数・乗数の型をどこまで揃えさせるか | **幅と符号だけ揃え、位取りと単位は規則で決まる**。`金額 ÷ 人数` が書ける         |
| `float` の演算語彙                   | `float` は演算子 `÷` を持ち、`割る(…, 丸め …)` は `int`/`uint` 専用とする        |
| 乗算で幅が足りなくなったら           | **同じ幅で計算し、溢れたら失敗**。中間で幅が要るなら `変換(a, int128(2))` を書く |

**思考実験 16 が「埋まらない」と書いた空白(厳密かつ上界あり)は、この体系で埋まる。** `int64(2) 円` は記憶域も実行時間の上界も型が言う。
代わりに ADR 0010 の負担(幅の見積りと桁溢れ)が戻る。桁溢れはラップもトラップもせず**失敗**とし、検査は演算ごとに行う。

併せて**内部計算用の十進数型 `dec(<整数部>.<小数部>)`** を足した(例: `dec(9.4)`)。桁を宣言し、演算は小数部倍した整数で行い、**格納は値による可変長**である。
**データフロー・外部インターフェイス・`state` には書けず、body の式と局所の値だけ**に使う。

- **宣言した桁は上界、可変長は表現の最適化**であり、この2つは矛盾しない。`dec(9.4)` は 13 桁 = 最大 6 バイトと静的に見積もれる。
  前版の可変長 `十進数` が上界を持たなかったのとは違い、**上界は宣言が言う**。
- **中間の桁は自動で広がり、検査は名前を得る所で行う**(ADR 0010 の規則がここで復活する)。
  これにより、思考実験 18 の論点4(乗算が幅を食う)・論点5(加算が位取りを揃える所で溢れる)と、
  ADR 0010 が「桁の上界が定まらない唯一の演算」とした `合算(列)` の穴が**内部計算では消える**。
- 型の役割が層で分かれた——**跨ぐ値と状態は幅で上界を言う `int`/`uint`/`float`、内部の中間は桁で上界を言う `dec`**。
  代償は「持ち上げて・計算して・収める」の3段になる事である(`変換` と `収める` が対で現れる)。

**`float128` は置かない**(suzukimitsuru の問いへの回答)。x86-64 と AArch64 は ISA に規定が無く必ずソフトウェア実装になり、
Rust の `f128` は nightly 限定、TypeScript には無い(ADR 0012 の出力先が両方とも安定して持たない)。
NumPy の `float128` が多くの環境で 80 ビット拡張精度である事も、名前の一致が中身の一致を意味しない例として記録した。

#### 主要言語の数値型を並べた(思考実験 17、2026-09-15)

「なぜ幅の違う整数型が複数あるのか」を確かめるため、Rust・TypeScript・Go・Java・C#・Python・Swift・C/C++・Zig・Haskell・Erlang の数値型を、
ビット幅と範囲の表つきで並べた。要点は4つである。

- **幅で分ける理由は4つあり、層が違う**——記憶域・実行時間の上界(内側)、外部形式との一致(境界)、ハードウェアの語長(実装)。
  ADR 0021 は**境界の理由だけを言語の語彙に残し**、残りを実装と将来の値域の宣言に委ねている。
- **最も分かれるのは桁溢れの扱い**で、ラップ(Java・Go・C#)・トラップ(Swift・Rust の debug)・未定義動作(C の符号付き)・
  起きない(Python・Erlang・JS の `bigint`)の4通りある。Shidzuku は4番目と「境界で失敗」の組み合わせであり、ラップもトラップも採らない。
- **型を1つに絞った言語は、後から取り戻している**。JavaScript は `number`(binary64)だけだったが ES2020 で `bigint` を足し、
  両者を混ぜると実行時エラーになる——ADR 0021 の E0019-3 と同じ形の先例である(こちらはコンパイル時に落ちる)。
- **幅は 8/16/32/64 の4種で足りる**(決定9)。128 ビット整数を持つのは Rust・C#・Zig 程度で、外部形式で現れる事は稀である。
  `実数` を binary64 に絞った判断も、JavaScript・Go・Python と一致する。

`実数`(IEEE 754 binary64)は型としては引き継ぐが、**ADR 0017 の「主に使う型」という位置づけは引き継がない**(2026-09-10、suzukimitsuru の判断)。
型は記述者が値ごとに指定する物であり、省略時に補われる型が無い以上、言語が序列を置いても記述は変わらない——「主に使う」は言語の決定として成立しない。
選び方は指針(数えたか・刻みを決めたか・測ったか)に置く。
結果として、6.1 の問題1(9組中4組の宣言のない丸め)は**危険な4組が全てコンパイル時エラーになり**、
問題2〜7 も解ける(問題8 の序数は U24 として残る)。`収める` と桁溢れの直和・静的指数・中間桁の膨張も同時に消える。

代償は**記憶域の上界が実行時まで決まらない**事であり、当初は「実行時間の上界(最悪実行時間・WCET)が要る所・
ヒープを持たない組込みでは `整数 <細かい単位>`(例: `整数 銭`)を使う」という指針を置いた。
論点4(binary32)・論点5(区間演算)は保留、論点6(序数)は U24 に残る。

**`十進数(i.f)` は廃止して置き換える**(2つの形は併存させない)。固定長の受け皿は `整数 <細かい単位>` であり、静的指数の受け皿は `実数` である。
この形式は既存の体系では**単位付き・静的位取り・任意精度の十進固定小数点数**にあたる。完全な先行例は Haskell の `Data.Fixed`
(`newtype Fixed a = MkFixed Integer`。位取りを型に持ち、中身は任意精度の整数)であり、Java の `BigDecimal`・Smalltalk の `ScaledDecimal`・
Go の `shopspring/decimal` は**位取りが値ごと**である点だけが違う(ADR 0021「この形式の名前」)。

#### ADR 0021 の採用 — 数値型の確定(2026-09-16)

suzukimitsuru の判断により **ADR 0021 を採用した**。2026-09-03 に破棄した ADR 0010・0017 の後継が決まり、
**「層は仕様書に入ったが数値型は宙に浮いている」状態は 13 日で解消した**。ADR 0019 の決定2・決定7 の凍結も同時に解けている
(決定7 は 0021 が置き換え、決定2 の `整数` は `intN(s)`・`uintN(s)` に置き換わった)。

仕様書への反映は次のとおりである。

| 反映先                   | 内容                                                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| 第6章 6.2                | 基本型を 11 種に確定(`int`・`uint`・`float`・`dec` の4つが数値)。`単位なし` を `unitless` に改めた                                  |
| 第6章 6.3                | 全面改訂。4つの数値型・実効範囲・演算・桁溢れ・`dec` の内部限定・変換・外部との詰め替え・量と単位                                   |
| 第6章 6.4・6.5・6.6・6.7 | 時間の型の読み替え(`隔たり` は `int64(0) <単位>`)、型が告げる事、未定事項、裏付けの表                                               |
| 第3章 3.3                | E0021-1〜E0021-4 を新設、E0010-3・E0019-3・E0019-4・W0017-1・W0017-2・W0019-1 を改訂、E0010-4 は欠番。実行時に戻る失敗7つの表を追加 |
| 第5章 5.3                | 基本型の語彙を `bool` `int` `uint` `float` `dec` … に差し替え、単位なしは `unitless` のまま残した                                   |
| ADR 0019                 | 状態に「決定2・決定7 は ADR 0021 が置き換えた」を明記し、凍結の節に解除(2026-09-16)を書き足した                                     |

**単位なしの綴りは `unitless` に戻した**(2026-09-17、suzukimitsuru の判断)。起案時は「該当なし」の `none` に揃えていたが、
単位の欄に書くのは「単位が無い」事であって「該当が無い」事ではなく、`depends none`・`state none`・`deadline none` と
同じ綴りを重ねると `none` が何を否定しているのかが文脈ごとに変わる。ADR 0014 が定めていた `unitless` をそのまま使う。

**残る宿題は値域の宣言**(`int32(0) 個` に「0 以上 1000 以下」と書けるか)である。
これは幅より細かい上界を型に載せる話であり、桁溢れの失敗を減らす唯一の手段として第6章 6.6 の未定事項に置いた。
序数と基数の区別(U24)も未着手のまま残っていた(2026-09-17 に ADR 0022 で決着した。下記)。

### 2026-09-17 単位の種別 — ADR 0022 の起案と採用

suzukimitsuru から「`unitless` で書いていた個数・版・連番、列の添字・長さ、税率も単位として指定してよいのではないか」という問いがあった。
検討の上で suzukimitsuru が2点を指定した——**数える量は掛けると単位が消える**(`円 × 個 = 円`。単価は通貨として円・米ドルと同じ扱い)、
**単位を種別に分け、記述者が量を定義できるようにする**。

思考実験 19 で単位の性質を洗い出し、足し算(できる・差とだけ・できない)× 掛け算(残る・消える・できない)の9通りのうち、
意味を持つのが3つしかない事を確かめた。これを4つの種別に固定し、ADR 0022 として起案した。

| 種別 | 足し算       | 掛け算                     | 例                     |
| ---- | ------------ | -------------------------- | ---------------------- |
| 比率 | 同じ量どうし | 消える                     | `unitless`・パーセント |
| 計数 | 同じ量どうし | 消える(相手が比率なら残る) | 個・人・件・要素       |
| 計量 | 同じ量どうし | 残る(組立の量の宣言が要る) | メートル・秒・円       |
| 位置 | 差の量とだけ | できない                   | 版目・要素目・座標     |

- **乗除算は強さの順(比率 < 計数 < 計量)で決まる。** 強い方の単位が残り、同じ強さどうしは(比率を除き)組立の量の宣言が要る。
  `件 ÷ 人` も宣言を要する——どちらを残すかを言語が決めると、読み手が左右の順を覚える事になるためである。
- **比率の量は言語が1つだけ持ち、基準単位は `unitless`** とする。記述者は `パーセント` のような単位だけを足せる。
  比が 10 の冪なら、単位が消える所でその比を位取りに畳み込む(`int64(2) 円 × int64(2) パーセント` → `int64(6) 円`)。
- **位置は `時点` と `量 時間` の関係の一般化**であり、`版目 + 版` は書けるが `版目 + 版目`・`版目 × 3` は落ちる。
  **U24 が、新しい基本型を足さずに解ける。**
- **言語が `要素`(計数)と `要素目`(位置)を持ち**、E0019-4 を「長さと回数は `uint64(0) 要素`、添字は `uint64(0) 要素目`」に改める。
- 代償は、量の宣言が増える事、単価と金額が同じ `円` になり単位では区別できない事、`要素` と業務の計数の往来に2段の操作が要る事である。

思考実験 13(2026-08-29)は「数える単位では U23 は解けない」としていたが、主な理由(型を跨ぐ)は ADR 0021 で消えていた。
13 が挙げた残りの障害のうち、単位なしのスカラー倍・列の長さ・序数は種別で解け、助数詞の数だけ宣言が増える事だけが残った。

**suzukimitsuru の判断により、ADR 0022 を起案と同じ日に採用した。** U24 が決着し、ADR 0021 の決定4・決定11 は 0022 が改訂した。仕様書への反映は次のとおりである。

| 反映先    | 内容                                                                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 第6章 6.2 | 選択のある欄の説明に量の種別を加えた                                                                                                                      |
| 第6章 6.3 | 数値型の例を `int64(0) 個`・`int64(0) 版目`・`uint64(0) 要素`・`int64(2) パーセント` に改め、「量と単位」に種別・強さの順・位置の量・言語が持つ量を加えた |
| 第6章 6.5 | 型が告げる事に「単位(量の種別)」の行を加えた                                                                                                              |
| 第6章 6.6 | 原点をずらした位置の単位・型の別名・種別とリテラルの綴り・`バイト列` の長さの量を未定事項に加えた                                                         |
| 第3章 3.3 | E0022-1〜E0022-5 を新設し、E0008-1・E0010-1・E0010-3・E0010-5・E0019-4 を改訂した                                                                         |
| 第5章 5.3 | 量の種別の語彙 `ratio` `count` `amount` `position` `delta` を加え、`unitless` を比率の基準単位と読むと明記した                                            |
| ADR 0021  | 決定4・決定11 に、0022 が改訂した旨を書き足した                                                                                                           |

計量の綴りに `measure` を使わなかったのは、ADR 0015 が `measure` を単位の語から外した経緯と紛れるためである。
綴りは第5章 5.3 の他の語と同じく、Phase 1 のパーサ実装で最終確認する。

### 2026-09-29 ADR 0028 でデータ宣言の語を分けた

Phase 1 の残る作業に入る前に、suzukimitsuru が `data` の語を見直す事にした。**`data` は一般的すぎる**——Shidzuku のデータ宣言は
コンポーネントの外側を流れる語彙に限られるが、その限定が語に表れず、直積・直和・識別子型のどれかも頭の語から読めない。

参照している言語から候補を集めて比べた(`type`・`message`・`shape`・`term`・`value`、形ごとに分ける案)。
一語で三つの形を包む限り、どの語も一般的になる。suzukimitsuru の判断で**形ごとに分ける**事にし、[ADR 0028](../../decisions/0028-データ宣言の語.md) として採用した。

``` plaintext
record 注文     { 品目: 品目ID, 数量: int64(0) 個 }   # 直積
choice 照会結果 = 見つかった(値) | なし              # 直和
id     受注番号                                      # 識別子型
```

- 直和は ASN.1 の `CHOICE` に倣って `choice` とした。`union`・`enum` は区分が値を持つ判別共用体に合わない。
- 識別子型は `id` を頭に置く。`id` は既存の語であり、増えた語は `record` と `choice` の二つである。
- 型の別名(第6章 6.6)には `choice` を使わない。語は別名を採る時に定める。
- 反映: 第5章 5.3・第6章 6.1・6.6、第1〜3章の言及、計画書、`data` を書いた思考実験 17 本。**思考実験の古い記述も書き換えた。**
  ADR は履歴として本文を残し、0009 に付記を足した。

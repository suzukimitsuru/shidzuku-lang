持たない意味は配置の設定の時に拒みます。ESP32 の器は最小の分散動作環境(Phase 2)で作り、状態の確認はコンポーネントのコードには出しません(計画書 第7節 7.16)。

期限超過や相手障害のような接続の失敗は公開面に書かず、フローの `on failure` が業務の区分へ翻訳し、補償は平常時の接続と同じ検査を受けます。

内側の並行は TypeScript に写せない事、待つ所で次を受けると状態と待つ所の両方を持つ仕事どうしで追い越しが起きる事、順序は接続の中の FIFO(先に入った物が先に出る)と再送で追い越さない事の二つで足りる事が分かりました。何も決めておらず、論点は計画書の第7節 7.22 にあります。

同じ所はいずれも suzukimitsuru の構想から出ており、本書から取り込んだ物は無いため、第0章 0.9(参照する系譜)には含めません。
同日、suzukimitsuru の指示で思考実験 29 を行い、用語辞書(名詞・動詞を記述者が宣言する仕組み)を言語が提供する事で名前を規則化できるかを検討しました —
名前を宣言された語だけで組ませる事と、退けた語を使わせない事は言語が強制できます。辞書に母国語と英語の対応表を兼ねさせ、コードの名前を英語(ASCII)だけで書く前提を置くと、
名詞と動詞の規則も英語を仮定すれば強制できますが、ADR 0014 の決定3(記述者の名前は UTF-8)と食い違うため論点に残しました。
2026-10-15 には「語彙辞書」などの呼び名と比べ、suzukimitsuru の判断で「用語辞書」のままとしました。キーと値の対応の型は対応表(map)と呼びます(第6章 6.6)。
同日、suzukimitsuru の指示で思考実験 30 を行い、システム・人・外部システムからコンポーネント、欄や DB の項目へと進む開発の流れの中で、用語辞書を育てる形を検討しました —
宣言の場所で名前の母国語と定義を書き、宣言を持たない語は使った段の辞書に足します。使う範囲が広がった語は外の辞書へ移ります。何も決めていません。
2026-10-16 には suzukimitsuru の指示で、用語辞書から母国語の欄を除きました。辞書は英語の語・役・定義を持ち、母国語との対応はローカライズと共に後で考えます。
同じ指示で、辞書に無い語を公開する名前(システム・コンポーネント・公開面・データ宣言・欄・区分の名前)に使わせない形を検討しました —
コンポーネントの内側の名前は辞書に掛けず、線は宣言の種類で引けるため、言語が強制できるままです。情報隠蔽と同じ所に線が引け、コンポーネントの辞書も要らなくなります。何も決めていません。
2026-10-18 には suzukimitsuru の指示で思考実験 31 を行い、言語仕様に対する反証(今のプログラマに受け入れられない所)と肯定(プログラマ以外の人に与える良い影響)を、外部の研究と事例に照らしてまとめました —
費用は書き手が払い、利益は読み手が受けます。強い反証は生態系・外部世界・警告の抑止という未完成の部分で、最も強い肯定は単位と暗黙の変換で値が化けない事です(計画書 第7節 7.26)。何も決めていません。

#### ADR の検討順(旧 第4節)

ADR は互いを改訂する。改訂される側を先に採ると、採用した直後に改訂が入って仕様書を二度書き直す事になる。
改訂する側を先に採ると、依拠先が提案のままで決定が宙に浮く。したがって順序が要る。

順序を決める規則は三つである。

- **R1** 改訂の関係にある ADR は同じ**ステップ**に入れ、同時に採否を判断する(片方だけ採らない)
- **R2** ステップの順序は依拠の向きに従う。**名前 → 型 → 指針 → 接合面**の順である
- **R3** 第2節の「決定フェーズ」より前倒ししない。前倒しは、判断の材料が揃う前に決める事を意味する

課題と ADR とステップの関係図は [docs/roadmap.html](../../roadmap.html) 第3節に置く。

ステップは 2026-08-28 の採用(ADR 0005・0013・0015)と 2026-08-29 の採用(ADR 0014)、2026-09-17 の採用(ADR 0012)、2026-09-18 の採用(ADR 0006)、2026-09-25 の採用(ADR 0018)を反映してある。
採用済みの ADR はステップから外れ、全てのステップが一度空になった。2026-09-26 に起案した 0024・0025 はステップ3 に入れ、2026-09-28 に採用した。**残るのはステップ4 の新規 ADR(U10〜U14・U20・U26)である。U26 は ADR 0027 として起票した。** ステップの番号は動かさない(採用の記録と対応が付かなくなるため)。

H2・H3 は ask の応答待ち(U10)を、H5 は durable な受領と順序(U11)を、H8 は終了の理由(U13)を、H6 はログ規約(U4)を写している。
これらが未決のまま凍結すると、Phase 1 の途中で接合面を書き直す事になる。
なお 0012 の**採否**はステップ2 の後であれば判断できる(出力先の言語に何を要求するか——整数の幅と十進固定小数点——は 0021 が決めた)。
ADR 0021 の採用により、要求は「8〜256 ビットの整数」と「`dec` のための多倍長整数」になり、`float32`・`float64` の側は IEEE 754 を持つ言語ならそのまま通る。
凍結の時期は 0012 の決定10(TypeScript のコンポーネントが同じ H1〜H8 で通ってから)に従う。
**0012 は 2026-09-17 に採用した**(第7節 7.1)。採用したのは接合面の形と分担であり、H1〜H8 の凍結ではない。
したがって上の「写し」の関係は採用後も生きており、ステップ4 の決定が H1〜H8 を改訂し得る。

##### 移行の条件(2026-09-28 確定)

Phase 1 へ移るのは、次の五つが揃った時とする。

- **M1** Phase 1 の前に決める課題(U10〜U14・U20・U26)が、ADR として採用されている
- **M2** U21 は、採用されているか、Phase 1 の期中へ送る判断が記録されている
- **M3** 接合面の写し元が決まっている——H2・H3(U10)、H5(U11)、H8(U13)。
  H1(U16)と H6(U4)は Phase 1 以降でよい(ADR 0012 決定10: 凍結は TypeScript が通ってから)
- **M4** 成果物の題材を最新の仕様だけで書き下ろし、書けない所が無い(移行点検の思考実験)
- **M5** 判断待ちの ADR が無い。ステップ3 の 0024・0025 は 2026-09-28 に採用した。同日に起票した 0027(U26)を含む。2026-10-08 に起案した 0031(U13)は同日に採用した。
  どちらも Phase 1 の実装には影響しない(7.8)が、提案を残したまま段を移ると、仕様書と ADR のどちらに依拠するかが曖昧になる

M4 は Phase 0 の検証方法(第1節)をそのまま移行の試験に使う。書けない所が出たら、該当する課題へ戻す。
M5 は 0024・0025 の起案を受けて足した。U14 の起案より前に採否を決めるとしていた——0025 の決定3(強く結ぶ物を同じ `contains` に束ねる)と、
思考実験 23 が U14 に渡した K-a(データ宣言は届く範囲に属する)が、同じ物差しに立つためである。2026-09-28 の採用で、この分は満たされた。
以後に起案する ADR(U13・U10・U11・U12・U20・U14・U26)も、採否を移行の前に決める。

**M1 と M2 の中身は、2026-09-28 の決定に合わせて動かした。** U14 を Phase 1 の前に決める事にしたため M2 から M1 へ移し、
新設した U26(body の記法)を M1 に加えた。条件の数と記号は変えていない。
条件の記号を M(移行)としたのは、ADR 0012 のバックエンドの責務 G1〜G7 と取り違えないためである。

**shidzuku-lint の着手も、この条件に従う。** ADR 0026 決定2 は shidzuku-lint を Phase 1 の言語実装と並行して着手し、Phase 0 の間は作らないとした(道具だけを先行させない)。
したがって M1〜M5 は、shidzuku-lang の実装と shidzuku-lint の実装の両方の着手条件になる。
移せる11件と既にある10件の多くは採用済みの検査に依るが、先に作っても、検証器と規則の一覧を共有する(決定2)相手がまだ無い。

  U12 と組にして決める案は採らない——U13 と U12 を束ねると、U13 が U10・U11 を越えて U12 を待つ事になり、4.3 の順序が崩れる。
- **U13・U10・U11・U12・U20・U14・U26 の ADR は、既存の言語に移せるかを併せて書く**(ADR 0026 決定6)。いずれも検査(E・W)を足す見込みが高い——

##### U26 body の記法の候補(2026-09-28)

body は「原則自由」(第2章 2.4)とされたまま、記法が決まっていない。候補を並べる。決めるのは思考実験で書き比べてからである。

| 候補                         | 先行例                                             | 合う所                                                                                                             | 擦れる所                                                                                                  |
| ---------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| B-1 Go・Hike 風              | Go、[Hike](../../experiments/24-Hikeの取り組み.md) | 構文が小さい。失敗を値で返す作法(Go)。`Async` と `<-` で送り出しと待ちを分ける(Hike の H-2)。GC の無い写像を試せる | Go のゼロ値は暗黙の既定値である(ADR 0008)。`nil` の扱い                                                   |
| B-2 Rust 風                  | Rust                                               | 式指向、網羅の `match`、`Result` と `?` による失敗の伝播(U13 論点2)。Rust への写像が素直                           | 所有と寿命の構文は TypeScript に写す先が無い。記述が重くなる                                              |
| B-3 TypeScript 風            | TypeScript                                         | 馴染みが広い。TypeScript への写像が素直                                                                            | 暗黙の変換・`undefined`・例外が、ADR 0008・0021 と正面から擦れる。削ると別の言語になる                    |
| B-4 ML 系                    | OCaml・F#・Elm                                     | 式のみ、パターン照合、`null` が無い。`pure` の層と相性が良い。Elm は実行時例外を持たない                           | 馴染みが薄い。字下げに意味を持たせる方言(F#)がある                                                        |
| B-5 宣言の層に揃えた独自記法 | Shidzuku の宣言の層                                | 一本の記述で貫く(第0章)。ASCII の語彙と UTF-8 の名前(ADR 0014)、単位と `dec`、既定値の無さを最初から組み込める     | 設計の費用。先行例が無い                                                                                  |

- **物差し**: 既定値を置かない(ADR 0008)、暗黙の変換を置かない(ADR 0021)、役割ごとのテキスト操作(ADR 0013)、`pure` の検査(ADR 0005・0012 決定8)、
  失敗の値の受け方(U13)、待つ所の印(U10)、Rust と TypeScript の両方への写像(ADR 0012)、既存の言語に移せるか(ADR 0026 決定6)。
- **次の行動**: 同じ body——思考実験 04 の KVCore の格納と、思考実験 01 系の受注——を候補ごとに書き比べる思考実験を起こす。
  B-5 を軸に、B-2 の網羅の分岐と失敗の伝播、B-1(Hike)の待つ所の印を借りる組み合わせが有力と見るが、書き比べる前に決めない。

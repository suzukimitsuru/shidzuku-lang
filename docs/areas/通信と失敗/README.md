## 経緯

### 2026-09-25 U25 — 対になる通信を思考実験にした

ADR 0018 の採用の過程で、逆向きの通信を「元の `ask` への後からの戻り(コールバック)」で説明する案を捨てた。
捨てたのは `ask` の定義を壊すからであり、**二本の通信が一つの仕事である事をどう書くか**は未決のまま第4章 4.6 に残った。
これを[思考実験 20](../../experiments/20-対になる通信.md)として書き下ろした。

題材は「受注番号は期限内に返し、確定は決済代行の応答を待って後から流す」系である。
現在の語彙で書けた事と書けなかった事は、はっきり分かれた。

| 書けた事                                           | 担った語彙                            |
| -------------------------------------------------- | ------------------------------------- |
| 二本が一つの仕事である事・なぜ二段なのか           | `flow` 宣言の単位と intent            |
| 両端の障害時の埋め合わせ・確定を失わない事         | `on failure`・`durable`・`idempotent` |
| 再起動で客との対応が消える事と、引き直す道が要る事 | `state volatile` と `expose` の照会   |

書けなかったものは7つあり、**重いのは次の二つ**である。

- **論点1・2(相関)**: 二本を結ぶ鍵(受注番号)が同じ物である事は、どこにも宣言されておらず検査もされない。
  同じ相手に `受注`・`取消`・`受注の照会` の三つの `ask` があると、後から届く `受注の状態` がどれの続きかは記述から決まらない。
- **論点5(仕事の期限)**: `ask` の `deadline` は受注番号を返すまでの期限、`pressure block` の期限は投入が受け付けられるまでの期限であり、
  **「確定が何分以内に決まるか」を書く場所が無い**。決済代行が生きたまま沈黙すると、客は確定しない受注番号を持ったままになる。
  相関は body の照合で凌げるが、期限はどこにも書けない。

案は3つに整理した。**D-2(`flow` 宣言に相関の鍵と仕事の期限を書く)を第一候補とする**——
`ask`・`flow` の2方式(ADR 0004)を保ったまま、論点1・2・5 を宣言と検査へ移せるためである。
D-3(公開面で対を宣言する)は ADR 0004 の改訂になる上、論点5・6 を1つも解かない。

残る論点3(同じ事実が二経路で届く)・論点4(宛先を失って捨てた通知)・論点6(仕事の途中の巻き戻し)は、
どの案でも残る。**一つの仕事が複数の通信に跨る事そのものの帰結**であり、補償の語彙(サーガ)に踏み込むかの判断が要る。
これを確かめる題材(在庫の引当と解放)は、次の思考実験に送った。

論点7(第4章 4.3 の `pressure block(deadline 1s)` が単位の語彙に無い綴りである事)は、同日に仕様書の文面で閉じた。

#### 論点5(仕事の期限)を U13 へ送る(2026-09-25)

**suzukimitsuru の判断により、思考実験 20 の論点5(仕事全体の期限)は U25 から外し、U13(失敗の体系)が引き取る。**
「相手は生きているが、いつまでも確定しない」は**何を失敗と呼ぶか**の問いであり、二本の通信を結ぶ書き方の問いではない。
U25 が引き受けるのは相関(論点1・2)だけとし、期限を書く欄の形は U13 が失敗の体系を決めた後に、その語彙の上で決める。

#### 思考実験 21 — 補償と巻き戻し(2026-09-25)

D-2 を起案する前の、もう一段の検証である。引当 → 決済 → 確定という**巻き戻しが要る系**を書き下ろし、
思考実験 20 の論点6(仕事の途中の巻き戻し)がどこまで書けるかを測った。

**業務上の巻き戻しは、新しい語彙なしで書けた。** 補償(引当の解放)は普通の接続であり、順序は `flow` 宣言の並びが、
理由は intent が、二度走ってよい事は `idempotent` が引き受ける。サーガの単位を持ち込む必要は無かった。
書けなかったのは次である。

| 論点                                 | 中身                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------- |
| 1・2 同じ補償が二つの形で書かれる    | 業務上の取消は接続(検査される)、障害時は `on failure` の散文(検査されない)       |
| 3 巻き戻しの引き金が記述に現れない   | 取消を起こすのは `external` の応答だが、外部はフローの端点に書けない(U12)        |
| 4 途中まで進んだ仕事の残骸           | どの受注にも結び付かない引当が残る。掃除の主体も期限も記述に無い                 |
| 5 補償を結ぶ鍵は、元の仕事の鍵と違う | 受注番号(公開面)と引当番号(内側)。**鍵は仕事に一つではなく、接続の対ごとにある** |

- **論点4 は、論点5 を U13 へ送った判断を裏付けた。** 「確定がいつまでも来ない」と「引当がいつまでも残る」は同じ穴であり、
  どちらも相関の語彙では閉じない。
- **論点5 は D-2 の設計を直させる。** `correlate` を書く位置は `flow` 宣言の全体ではなく**接続の対**である。
- 論点1・2 への案は3つ出し、**S-a(`on failure` に接続を書けるようにする)**を第一候補とした。
  補償は検証可能な記述であり、散文に落ちているのは欄の形の都合にすぎない。
  サーガの単位(S-b)は `flow` 宣言と役割が重なり、実行系に分散トランザクションを要求するため採らない。

### 2026-09-26 U25 — ADR 0023 を起案した

思考実験 20・21 が材料を出し切ったため、U25(対になる通信)の ADR を起案した。**`flow` 宣言に相関の鍵を書く**形である。

```plaintext
  Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
  注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  correlate 受注番号 : 受注 -> 受注の状態
```

| 決定                                         | 中身                                                              |
| -------------------------------------------- | ----------------------------------------------------------------- |
| 1. `correlate` を `flow` 宣言に足す          | 公開面に書く案(`then`)は ADR 0004 の改訂になるため採らない        |
| 2. 相関は接続の対ごと                        | 鍵は仕事に一つではない(公開面の受注番号と、内側の引当番号)        |
| 3〜4. 接続は行に書かれた名前で、鍵は型で指す | 名前的型付けがあるため、欄の経路(`受注の状態.受注番号`)は要らない |
| 5. 接続が2本以上なら必須                     | 結ぶ対が無ければ `correlate none`。欠落は既存の E0008-1           |
| 6. 三本以上を一つの鍵で結べる                | 連なる仕事は対ではなく道である                                    |
| 7. 相関のある通信は同じ `flow` 宣言に置く    | 宣言を跨ぐ相関は、接続を外から指す名前(U14)が決まってから         |
| 8〜9. 期限と `on failure` の欄の形は決めない | 仕事の期限は U13 へ(7.5)、補償の記述も U13 と併せて判断する       |

- 検証は E0023-1〜E0023-4 と W0023-1 である。**「書き忘れ」は新しい番号を作らず E0008-1 に寄せた。**
- 机上検証で**相関がフローの切り方を押す**事が分かった。思考実験 21 は受付と確定を別の `flow` 宣言に分けていたが、
  その切り方では `引当番号` の相関を書けない。引当と解放を同じ仕事として書き直すと、在庫を戻す道が記述の上で繋がる。
- 起案と同日に、suzukimitsuru の判断で**採用した**。反映先は次の通りである。

| 反映先          | 内容                                                                          |
| --------------- | ----------------------------------------------------------------------------- |
| 第4章 4.2       | `flow` 宣言に `correlate` を置き、接続の指し方・鍵・必須の条件を書いた        |
| 第4章 4.6       | 未定事項から相関を外し、残るのは仕事の期限(U13)と `on failure` の欄の形とした |
| 第3章 3.3       | E0023-1〜E0023-4・W0023-1 を加え、段の欄に「フロー」を足した                  |
| 第5章 5.3       | 通信の語彙に `correlate` を加えた                                             |
| 第2節・3節・4節 | U25 の状態、ADR 一覧、ステップ4 を改めた                                      |

- U25 は本 ADR で閉じた。**判断待ちの ADR は無い。** 次は U13(失敗の体系)であり、
  そこで仕事の期限と `on failure` の欄の形を扱う。
- 思考実験 01〜04・20・21 の `flow` 宣言は `correlate` を持たないが、本文は改訂しない(書かれた時点の語で読む)。

### 2026-09-26 U13 — 失敗を棚卸しした

ADR 0023 の採用で U25 が閉じ、第4章 4.6 に残ったのは**仕事の期限**(思考実験 20 の論点5)と
**`on failure` の欄の形**(思考実験 21 の論点1・2)である。どちらも「何を失敗と呼ぶか」に依るため、
[思考実験 22](../../experiments/22-失敗の棚卸し.md)で仕様書と ADR に散らばった「うまくいかない事」を全て並べた。**28 件あった。**

| 群                         | 件数 | いまの書き方                                           |
| -------------------------- | ---- | ------------------------------------------------------ |
| A データとして正常な不在   | 5    | `choice` の区分(`なし`・`欠損`・`暦の外`)              |
| B 業務が拒否した           | 4    | 公開面の直和(`-> 受注番号 \| 受注不可`)                |
| C 数値と型の失敗           | 9    | **無い**(「戻る値」と定めたが、その型が無い)           |
| D 解析の失敗               | 2    | **無い**                                               |
| E 通信の失敗               | 5    | 接続の属性と `on failure` の散文。呼び手の型には出ない |
| F 失敗が起きない失敗(待ち) | 3    | **無い**                                               |

分かった事は三つである。

- **「失敗」が一語で三つの物を指している。** 直和の区分(A・B)・戻る値(C・D)・接続の失敗(E)であり、
  F(待ち)はどれでもない。**何も返らない**ため、受け取って分岐する形では書けない。
- **軸1(誰が決めたか)と軸2(型に名前があるか)はほぼ一致する**——業務が決めた失敗には名前があり、系の事情による失敗には無い。
  第6章 6.1 が「別の語彙とする」と言った境目はここである。
- **しかし軸3(再試行で変わるか)は境目が違う。** 0 除算は何度やっても起きるが、期限超過は次は通るかもしれない。
  「系の失敗」を一つの語彙にまとめると、呼び手にとって意味の違うものが混ざる。

U13 で決めるべき事が四つに分かれた。

| # | 問い                                                | 案の素描                                         |
| - | --------------------------------------------------- | ------------------------------------------------ |
| a | 系の失敗を公開面にどう書くか(論点1)                 | 書かない / 直和に並べる / 器を分ける             |
| b | 数値と解析の失敗の型(論点2)                         | 直和にする / 伝播の記法 / 境界の操作に閉じ込める |
| c | 再試行で変わる失敗と変わらない失敗を分けるか(論点3) | —                                                |
| d | 待ちに期限を与える場所(論点4)                       | フローに書く / 状態に書く / 言語は持たない       |

- 論点1 は**省略の禁止の網の穴**である。`expose 受注(注文) -> 受注番号 | 受注不可` は二つしか返さないように読めるが、
  第4章 4.1 は期限超過と相手障害でも失敗応答が返ると定めている。三つ目が型に現れていない。
- 論点5(`on failure` が受け持つのは通信の失敗だけで、C 群の落ちる場所が無い)は、思考実験 21 の S-a と同じ所で決まる。

### 2026-09-27 U13 論点1 — 三案を書き比べ、第四の形に行き着いた

思考実験 22 の論点1(系の失敗を公開面にどう書くか)の三案を、[思考実験 25](../../experiments/25-系の失敗の書き分け.md)で同じ系に書き下ろした。

| 案               | 公開面の語 | 省略の禁止     | 失敗が1つ増えた時        |
| ---------------- | ---------- | -------------- | ------------------------ |
| F-1 書かない     | 増えない   | **満たさない** | 影響なし                 |
| F-2 直和に並べる | +8         | 満たす         | **全公開面の型が変わる** |
| F-3 器を分ける   | +8 と欄 4  | 満たす         | **全公開面の型が変わる** |

- F-2・F-3 は `期限超過 | 相手障害` を全ての `ask` に書き写す事になり、**常に同じ物を並べる**記述になった。
- さらに**言語が語を1つ足すだけで全コンポーネントの版が上がる**(公開面は互換性の単位。ADR 0012、U16)。
- F-2 は、言語が直和の区分名を持つ事にもなる。第7節 7.4(一般的な区分名を組み込みにする案は撤回)と筋が擦れる。

**書いている途中で第四の形(F-4)に行き着いた。** 系の失敗を公開面に書かず、**フローが業務の語彙へ翻訳する**形である。
思考実験 21 の記述は既にそうなっていた——`on failure Inventory : OrderIntake は受注不可を返す` は、
期限超過を `受注不可` に翻訳している。

- 公開面は業務の語彙だけで閉じ、系の語彙は一つも現れない。
- 省略の禁止は**既に満たされている**。`on failure` は参加する全コンポーネントについて必須である。
- 新しい語を増やさない。既にある欄を**型の付いた形**にするだけである(思考実験 21 の S-a と同じ変更)。
- 代わりに二つを要求する——(1) `on failure` が型の付いた記述を取れる事、
  (2) **全ての接続がどれかのフローに現れる**事(今は「使っているのにどのフローにも書かれていない」を見る検査が無い)。

U13 の ADR は (a) 系の失敗は公開面に書かない、(b) `on failure` を型の付いた欄にする、
(c) 全ての接続がフローに現れる事を要求する、の三つを軸に起案する。
思考実験 22 の論点2(数値と解析の失敗の型)と論点4(待ちの期限)は、本実験では解いていない。
(c)の範囲は記述の中の接続に限り、外部との接続は U12 で扱う(第4節 4.5、2026-09-27)。

### 2026-10-08 失敗の体系(U13)を ADR 0031 として起案した

suzukimitsuru の指示により、Phase 1 の前に決める課題の先頭である失敗の体系(U13)を、[ADR 0031(失敗の体系)](../../decisions/0031-失敗の体系.md) として起案した(提案)。
材料は思考実験 22(失敗の棚卸し)・25(系の失敗の書き分け)と、思考実験 20 の論点5(仕事全体の期限)・21 の論点1・2・4(補償と孤児の引当)である。

| 7.7 の問い                         | 決定                                                                                                             |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 系の失敗を公開面にどう書くか       | 書かない。フローが `on failure` で業務の区分へ翻訳する(思考実験 25 の第四の形)                                   |
| 数値と解析の失敗の型               | 言語が型を持つが、コンポーネントの外へ出さない。受け取りは必須で、業務の値・代わりの値・障害にするのどれかを書く |
| 再試行で変わる失敗と変わらない失敗 | 型に印を付けず、置き場(body と `flow` 宣言)で分ける。再試行の規定は足さない                                      |
| 待ちに期限を与える場所             | `correlate` の区間に `within` を書き、期限切れは `on expiry` に書く。測るのは待つ側の動作環境                    |

- **失敗を四つの置き場に分けた。** データの区分(業務の `choice`)・演算と解析の失敗(body)・接続の失敗(`on failure`)・待ちの期限切れ(`on expiry`)である。
- **`on failure` を型の付いた欄にした。** 中身は接続の行・`respond`(待たせている `ask` に業務の区分で答える)・`restart` の三種で、補償は平常時と同じ検査を受ける。
  一つのコンポーネントが複数の接続に現れる時は `at` で接続を絞る。補償の失敗は入れ子にせず、待ちの期限が引き受ける。
- **記述の中の接続は、全てどれかの `flow` 宣言に現れる事を求めた**(2026-09-27 の判断の通り、外部との接続は外部世界との境界(U12)へ)。
  机上検証で、ADR 0023 の検証2 に決済の依頼の接続が書かれていない事が見つかった。
- **接合面に9つ目の呼び出し(待ちを置く・解く)を足す。** ADR 0012 の決定3(接合面)の改訂になる。要求を送る呼び出しの応答と、終える呼び出しの理由も定めた。
  これで接合面の写し元(移行の条件の M3)のうち、失敗の体系(U13)の分が揃う。
- 検査は E0031-1〜E0031-9 と W0031-1。body を読む E0031-5・E0031-6・W0031-1 は body の記法(U26)を待つ。
- 孤児の引当は検査では見つからない。言語は待つ側を置く場所(`within` と `on expiry`)を用意し、記述者が `引当の確定` を足す形になる(ADR 0031 の検証3)。
- 仕様書は提案の段階では書き換えていない。採用時に第3〜6章と ADR 0012 の改訂の記録を書き換える(ADR 0031 の決定14(適用範囲))。
- 判断待ちの ADR は 0027(body の記法)と 0031(失敗の体系)の2本になった。

### 2026-10-08 ADR 0031 を採用した

suzukimitsuru の判断により、[ADR 0031(失敗の体系)](../../decisions/0031-失敗の体系.md) を起案と同日に採用した。

- 起案で「採用時に決める」としていた、`on expiry` の中身が空の時の書き方は `on expiry <接続> none` とした。`correlate none`・`restart none` と同じ形である。
- 決定14(適用範囲)に従い、仕様書へ反映した。

| 反映先              | 反映した事                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| 第1章 1.6           | 接合面を H1〜H9 とし、待ちの期限を待つ側の動作環境が測る事を足した                                      |
| 第3章 3.2           | `expose` の `<失敗>` は業務の区分を指し、接続の失敗は公開面に書かない                                   |
| 第3章 3.3           | E0031-1〜E0031-9・W0031-1 を足し、E0008-1(必須宣言の欠落)の対象を広げ、実行時に戻る失敗に受け方を書いた |
| 第3章 3.5           | 待つ側の居ない区間の警告を未定事項に足した                                                              |
| 第4章 4.1・4.2      | 接続の失敗の語、`on failure` の新しい形、全ての接続がフローに現れる事、`within` と `on expiry`          |
| 第4章 4.5           | 四つの置き場と、接続の行・`respond`・`restart`・`at` の規則に書き直した                                 |
| 第4章 4.6           | 仕事全体の期限と `on failure` の欄の形を外し、再試行・監督の詳細・期限の和を残した                      |
| 第5章 5.3           | 語彙に `at`・`respond`・`restart`・`within`・`on expiry` を足した                                       |
| 第6章 6.1・6.3・6.6 | 正常な不在と接続の失敗の切り分け、演算の失敗の受け方を書き、未定事項から失敗の体系を外した              |
| ADR 0012            | 接合面の表に9つ目の呼び出し(待ちを置く・解く)を足し、改訂の記録(2026-10-08)を置いた                     |

- 思考実験 01〜04・20・21 の散文の `on failure` は、書かれた時点の語のまま残す(ADR 0031 の決定14)。移行点検(M4)で題材を書き下ろす時に新しい形で書く。
- shidzuku-lint の規則の候補に、E0031-7(言語の失敗の型がコンポーネントの外へ出る。宣言を足せば移せる)と、E0031-6(失敗を受けていない)の Rust の側(既にある)を足した。
- 移行の条件のうち、M1(Phase 1 の前に決める課題の採用)は失敗の体系(U13)の分が満たされた。M3(接合面の写し元)は、終える呼び出し(H8)の理由が決まった。
- 判断待ちの ADR は 0027(body の記法)の1本に戻った。次はコンポーネントの実行モデル(U10)とメッセージの順序保証(U11)である。

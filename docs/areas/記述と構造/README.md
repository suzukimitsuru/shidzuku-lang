## 記述と構造の決定(U3・U5・U7・U17・U18)

### 表記 — 語彙は ASCII、名前は UTF-8(ADR 0014)

- コード例の表記(英字のキーワードと日本語の識別子・型名の混在)は思考実験 01 以来の慣行であり決定が無かったため、U17 として登録し ADR 0014 を提案した(2026-08-26)。
- 線引きは「言語が定める語彙は ASCII、記述者が定める名前は UTF-8 を許容」であり、ADR 0013 が保留していた表記の統一(決定8)に基準を与える。
- 採用(2026-08-29)に伴い、識別子と語彙の規則を置く第5章「記述の表記」を新設した。表記は段に属さないため、段を跨ぐ第4章(通信)の後ろに置いた。
- 併せて ADR 0015 が持ち込んだ日本語の語彙(`担当`)と、ADR を持たないまま第3章に入っていた公開面の形(`の流れ`・`の受け口`)を、
  それぞれ `by`・`flow out`・`flow in` として決定7の表に足した。

### C4 の命名と章立て(ADR 0015)

- C4 モデルの命名を仕様に取り込む決定を U18 として登録し、ADR 0015 を提案した(2026-08-26。2026-08-28 に採用)。
- 四段は Context = システム(新設の第1章)・Container = 動作環境(言語の記述対象外)・Component = コンポーネント(旧ユニット)・Code = body と内部階層である。
- これに伴い章立てを段の順に振り直し、度量衡の単位の綴りを `measure` から `unit` に戻した(ADR 0014 の回避策が不要になったため)。
- ADR 0015 は ADR 0007 の C4 対応表と ADR 0014 の語彙表を改訂し、U12(外部世界との境界)の一部——外部の人と外部システムを宣言する場所——に答えている。
- 改名は仕様書と索引(本書・README・roadmap)に限り、ADR と思考実験は決定の履歴として旧称のまま残す(ADR 0014 の先例)。
  ただし提案中だった ADR 0012 は、採用時に読み替えを持ち越さないよう本文も改名した(2026-09-17、第7節 7.1)。
- 第三層の `body` を段の名前に合わせて `code` に改める案は据え置いた(ADR 0015 決定5・論点5)。
  本仕様書で「コード」は intent を含む記述全体を指しており(第0章 0.1・0.7)、第三層だけを `code` と名付けると
  「意図はコードではない」と読めて理念に当たる事、`layers` が constraint の語彙であるため `code` ブロックが Code 段と一致しない事が理由である。

### システムの入れ子(ADR 0018)

- ADR 0015 が残した「1プログラム = 1システム」の制限を外す ADR 0018 を提案した(2026-08-29)。
  C4 の System Landscape に当たる**システムの入れ子**を許し、`contains` の対象にシステムを加える。ルートはちょうど1つとする。
- 2026-09-25 に採用した。採用に先立ち、コンポーネントとシステムが混在した `contains` の中で互いを呼べない穴を塞いでいる(第7節 7.1)。

### 配置の記述は言語に含めない(ADR 0015)

- 思考実験 04 で「配置・複製の記述を言語仕様に含めるか(章を立てるか、実行系の設定に置くか)」という Phase 0 の骨格論点が出ていた。
- ADR 0015 が「含めない。動作環境(Container)の設定として Phase 2 で決める」と答えた(採用)。

## 経緯

### 2026-08-28 の採用と検証ループ

ADR 0005・0013・0015 を採用した。反映と、そこで見つかった事は次の通りである。

- 仕様書への反映: 第0章 0.3・0.5(層の強度と役割)、第2章 2.3・2.4(照合器の宣言、役割の4種と対応表)、
  第3章 3.2・3.3(制約の語彙に `照合器`、検証に E0013-1〜E0013-4)、第1章・第4章(依拠の確定と未定事項の追加)。
- **検証ループ**: ADR 0013 が求めた「テキストが主役の系」と ADR 0015 が求めた「外部システムを複数持つ新題材」を
  一つに載せ、思考実験 08(多言語商品カタログ検索)を行った。system 宣言・役割・照合器はいずれも書けたが、
  8つの論点が出た。
- **新設した課題**: U19(検証番号の採番規則。ADR 0016 で即日決着)・U20(役割の向きと通信の関係)・U21(全文検索と照合キーの永続化)。
- **反映できなかった事**: ADR 0013 の基本型(テキスト・バイト列)は、依拠する ADR 0009 が未採用で
  仕様書にデータ型の章が無いため入れられない。役割の表は「テキスト」への権能を語るのに、その型の定義が仕様書に無い。
  ADR 0009(と 0010)の採否で解消する。
- **番号の衝突と、その決着**: ADR 0015 が使う E11〜E13 は、提案中の ADR 0009(E11)・ADR 0010(E12〜E16)と衝突していた。
  通し番号が「採用された順序」を表してしまう事が原因である。検証番号は識別のためのものであり順序を表す必要がないため、
  **`E<出自>-<連番>` 形式**(出自 = その検査を定めた ADR の番号、`0000` は仕様書本体)に改め、ADR 0016 として記録した。
  出自ごとに採番するため衝突は原理的に起きず、E14〜E16 のような未採用の決定のための予約も要らなくなった。
  仕様書と索引だけを書き換え、ADR と思考実験は旧番号のまま残す(読み替え表は第3章 3.3)。
- **変更した反映方針**: ADR 0013 は「思考実験 01〜05 の `layers` に役割を補う」としていたが、行わなかった。
  ADR 0015 決定8(ADR と思考実験は書かれた時点の語で読めなければならない)と衝突するためである。
  既存実験への役割の適用は ADR 0013 の机上検証節が、新題材での検証は思考実験 08 が担う。

### 2026-08-29 の採用と起案

ADR 0014 を採用し、ADR 0018 を提案した。

- **第5章「記述の表記」を新設した**。ADR 0014 の決定1・4・5・6(符号化と識別子の規則)は、それまで置き場が無かった。
  表記は段に属さない規則であり、段を跨ぐ第4章(通信)と同じ立場として段の順の後ろに置いた。ADR 0015 決定6 の章の表に1行足す形になる。
- **語彙を英字へ移した**。`なし` → `none`、`照合器` → `collator`、`ロケール`/`強度` → `locale`/`strength`、
  役割の4種 → `boundary`/`parse`/`domain`/`format`、`期限` → `deadline`。記述者の名前(`受注`・`名前順`・`センサー機器群`)は1つも変わっていない。
- **語彙の棚卸しが足りていなかった**。ADR 0014 の決定7 は基本型・数値・層・共通の四表しか持たず、
  `担当`(ADR 0015)と `の流れ`・`の受け口`(第3章 3.2)を数え落としていた。採用の記録で3語を足した。
- **反映できなかった事**: 基本型(decimal・text・bytes …)と数値の語彙は、依拠する ADR 0009・0010・0017 が未採用で
  データ型の章が無いため入れられない。ADR 0013 の基本型と同じねじれである(第2節)。
- **ADR 0018(提案)**: システムの入れ子。ADR 0015 の「他の Shidzuku システムは external として外に置く」は、
  自分たちが設計し Shidzuku で書いている系を記述の外へ追い出しており、設計意図の喪失(第0章 0.2)を言語が強制していた。
  併せて **ADR 0015 が置いた外部システムの判定基準(独立に設計され、独立に壊れるか)を廃した**。
  `external` に書いた物が外部システムであり、それ以外の規則を持たない。Shidzuku で書いた系かどうかも関係しない。
  机上検証(思考実験 01 と 08 を一つのプログラムに並べる)で、判定基準は記述者の判断を後から正当化する役にしか
  立っていない事が分かったためである。思考実験 08 の論点5(判定基準が割れる)は、解決したのではなく**問い自体が消えた**。
  外部が段を上がっても外部である事(E0018-5)も、この検証で見つかった。
  論点3(外部を呼ぶコンポーネントを書けない)は、相手が記述の中にあるときだけ塞がり、半分は U12 に残る。
  名前空間は動かさず、U14 に残した。
- **ADR 0019(提案)**: 基本型の体系。ステップ2 の検討で、**確定しているのは数値だけである**事が分かった。
  ADR 0009 は基本型を本文1行で挙げているにすぎず、思考実験 05 が検証したのは構成子であって基本型ではない。
  真偽・時刻・期間・時間量は一度も検証されておらず、整数は一覧にすら無い。これを U22 として登録し、思考実験 09 で検証した。
  基本型を10(`論理・整数・実数・十進数・テキスト・バイト列・時点・日付・時刻・時間帯`)に確定し、`期間` と `時間量` を外す。
  `日付` は紀元前まで表し(天文学的年番号)、**暦は型の欄**とする(単位と同じ形。換算は常に厳密で往復も一致する)。言語が持つのは算術暦の2つだけ。
  **`時間帯` を置き、ログの日時は `時点` と `時間帯` の直積で書く。** 他の時間帯への「変換」は欄の差し替えであり `時点` は動かない。
  日時は基本型に置かず直積で書き、暦の値への `量 時間` の加算は持たない。
  **整数を置く直接の理由は ADR 0017 の副作用**である——主に使う型を `実数`(53 ビット)にした結果、
  ナノ秒の時点(19 桁)と 64 ビットの識別子の置き場所が消えていた。
  論理型は body に限り(公開面には名前の付いた直和)、`時点` はシステム時刻と定めて `時点 - 時点` を持たない。
  0010・0017 の決定は1つも取り消さない。
- **反証試験(思考実験 10)**: ADR 0019 は棚卸し(思考実験 09)から導いた決定であり、系を書いた裏付けを持たなかった。
  時間軸(`時点`)・暦(`日付`・`時刻`)・時間帯が全部出る系——多地域シフト勤怠——を書き下ろし、9つの論点を得た。
  打刻を `時点` で受ける形が境界の設計をそのまま決めた事、夏時間の曖昧さが公開面の直和に出た事、
  暦の値(締め期間)を鍵にした事で締めの冪等が成り立った事は、決定が効いた側である。
  一方で **`時刻` に長さを足せずシフトの終了時刻が書けない・曜日が無い・`整数` の単位換算の規則が無い・
  `隔たり` が 584 年で桁溢れする**という穴が出た。同日 ADR 0019 を改訂して埋めた——
  `時計を進める(時刻, 量 時間) -> (時刻, 整数 日)`(繰り上がりを返すため時間軸の加算と混ざらない)、
  `曜日(日付)`(日番号 mod 7 であり暦に依らない)、整数の単位換算(粗い単位へは丸めの宣言、細かい単位へは桁溢れの失敗)、
  `隔たり` の結果の単位と丸めの宣言、W0019-3 の書き分け(業務規則が決めた暦の値は対象外)である。
  地帯名の解決失敗(U12)と、body 内の判断を intent に書く場所(U1)は欠点として記録し、送った。
- **暦の拡張(思考実験 11 → ADR 0020 提案)**: ADR 0019 は「元号は版が変わる表だから言語が持たない」としたが、
  **退けた対象を取り違えていた**。退けるべきは「言語が表を持つ事」であり、「記述者がソースに表を宣言する事」は
  ADR 0010 が量と単位で既に採っている形である(インチの定義を言語は知らないが、インチは書ける)。
  暦は「表がどこから来るか」で3つに割れる——**算術暦**(言語が持つ)・**紀年法**(記述者が宣言)・**表暦**(持たない)。
  紀年法は年の呼び方だけが違う暦であり、月日を変えないため**改元日の一覧だけ**で宣言できる。和暦・仏暦・民国紀元・皇紀が同じ仕組みで書ける。
  内部表現は日番号のままで、比較・日数差・曜日・`日を足す` を一つも失わない。
  代わりに**換算が全域でなくなる**(表の外は `暦の外` として直和で受ける)。厳密さは保つ。
  `紀元 明治 : 1873-01-01 から 6 年` は、明治5年以前が天保暦であるという断絶を宣言がそのまま表す。
  **イスラム暦は依然として書けない**——タブラー暦法は算術だが紀年法ではなく閏年の配置に流派が複数あり、
  ウンム・アルクラー暦と観測ベースは版を持つ表である。太陰太陽暦も同じ理由で書けない。
- **新設した課題**: U22(基本型の体系。数値以外)。

### 2026-09-25 ADR 0018 の改訂 — 混在した `contains` の穴

採否の判断(第4節 4.1 のステップ4)に先立って読み直したところ、**決定1 と決定5 が噛み合っていない**事が分かった。
決定1 は一つの `contains` にコンポーネントとシステムが混在してよいと定めたが、
決定5 の `depends` は相手を「兄弟**システム**」「親の兄弟**システム**」に限っており、
**混在させた当人どうしがどの行にも当たらない**。書けなかったものは三つある。

| # | 関係                                          | 例                               |
| - | --------------------------------------------- | -------------------------------- |
| 1 | コンポーネント → 同じ `contains` のシステム   | 窓口が内側のシステムに受注を頼む |
| 2 | システム → 同じ `contains` のコンポーネント   | 内側のシステムが共有の採番を頼む |
| 3 | 内側のコンポーネント → 親の兄弟コンポーネント | 2 を実際に書くと必ず要る         |

1 だけを直すと同じ検査(E0018-3)が片側だけ緩むため、三つをまとめて決めた。
規則は「**兄弟か、親の兄弟か**」だけを見る形になり、相手がコンポーネントかシステムかを問わない。
E0018-4(相手の内側は指せない)はそのまま効くため情報隠蔽は変わらず、検証番号も増えていない。

逆向き(2)を「元の `ask` への後からの戻り(コールバック)」として説明する案も検討し、**捨てた**。
`ask` は期限内に必ず返ると定めており(ADR 0004、第4章 4.1)、後から返る形は三つ目の通信方式の新設に当たる。
再送の宛先が呼び出しではなくコンポーネントである以上(1コンポーネント = 1プロセス。ADR 0012)、記述の形は結局 `ask` と `flow` の二本になる。
加えて、これで説明できるのは元の `ask` と対になる戻りだけであり、内側のシステムが自分から出す `ask`・`flow`(採番・監査)は説明できない。
**対になる通信の書き方そのものは別の問い**として、第4章 4.6 の未定事項に残した。

併せて、起案後に採用された ADR と思考実験へ追従させた。

| 追従の元                       | ADR 0018 で変えた箇所                                                                     |
| ------------------------------ | ----------------------------------------------------------------------------------------- |
| ADR 0012 (動作環境)            | Container 段の項に、1コンポーネント = 1プロセスと、設定の受け手が動作環境である事を足した |

| 第6章 (データ。新設)           | 適用範囲に、第6章は入れ子の影響を受けない事を書いた                                       |
| 思考実験の番号                 | 予告していた「思考実験 09」は別の題材で使用済みのため、番号を決めない書き方に改めた       |

### 2026-09-26 思考実験 23 から ADR 0024・0025 を起案した

仕様が系譜に挙げる APoSD(深いモジュール)は**一つのコンポーネントの形**を問う。
**コンポーネントの間の関係**を問う知見——Vlad Khononov の結合バランス(統合の強度・距離・変動性)——は参照していなかった。
そこで、既存の思考実験 01・02・08・20・21 を三軸で読み直した(思考実験 23)。新しい系は書いていない。

| 軸     | 仕様が持っている物                                                            | 欠けている物                                   |
| ------ | ----------------------------------------------------------------------------- | ---------------------------------------------- |
| 強度   | 侵入結合の禁止(E0018-4)、境界の層による契約、`correlate` による機能結合の宣言 | **モデル結合**(データ宣言の共有)が宣言されない |
| 距離   | `contains` の木。コンポーネント間の最短距離がプロセスの境界(ADR 0012)         | 型の**届く範囲**を測らない                     |
| 変動性 | intent の `change` と `rejected` の理由(12件が変動性の論証だった)             | 機械は読まない(読ませない)                     |

- **ADR 0023 は機能結合の距離を既に制限していた。** 相関は同じ `flow` 宣言に置き(決定7)、内側の鍵は外へ出ない(決定2)。
- **思考実験 08 の `商品の見出し` と 20 の `注文` は、強いモデル結合を最も遠い距離(actor)まで張っていた。** 今の語彙でも型を分ければ直せるが、言語は何も知らせない。
- **既定値は、言語との見えない結合である。** APoSD は既定値を勧めるが、ADR 0008 はそれを捨てた。結合の見方でも ADR 0008 は支えられる。

これを受けて次を起案した。いずれも**提案**であり、ステップ3 に入れた(第4節 4.1)。

| ADR 0025 粒度の指針に結合の釣り合いを加える     | 変わる理由による分割、共有と同じ変化による統合、強く結ぶ物を同じ `contains` に束ねる |

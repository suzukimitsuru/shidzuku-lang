[全体](../../PLAN.md) › [検討の領域](../README.md) › 動作環境

- 担当する課題: ログ規約の内容(U4)・トランスパイル先の言語(U5)・Raft の適用範囲(U6)・コンポーネントのバージョンと移行(U16)
- 状態: トランスパイル先の言語(U5)は ADR 0012 で、最小の動作環境は ADR 0029・0030 で決着。ログ規約(U4)と Raft の適用範囲(U6)は Phase 2、版の混在と移行(U16)は再起動と版の入れ替えの試作で仮に置いて確かめる
- 道のりの図: この領域の節は [roadmap.js](roadmap.js) に書き、[docs/roadmap.html](../../roadmap.html) の「検討の領域」に差し込まれる

## 次に決める事

- 動作環境(意味の核と PC の器)は細い縦の試作から作る。意味の核は標準ライブラリに依らない1つのクレートにする(ADR 0029(最小の動作環境)の決定1(意味の核を1つのクレートにする))
- U16 は、再起動と版の入れ替えの試作で仮に置いて確かめ(版の番号を一つ持たせ、公開面と制約が同じなら入れ替えてよい、とだけ置く)、接合面の凍結(混在の試作)の前に決める(計画書 第4節「仮置き」、ADR 0033(試作を先に置く進め方))
- ESP32 の器は最小の分散動作環境(Phase 2)で作る

## 動作環境とトランスパイル先(ADR 0012)

- U5 は ADR 0012 で、動作環境の言語(Rust の1実装)とトランスパイル先の言語(TypeScript + Rust)をまとめて決めた。
- 主要言語11種を比較した上で、接合の距離がゼロの言語と最大の言語を取っている。
  移植層はコンポーネントと動作環境の接合面(8つの呼び出し)であり、互換性の単位は言語中立の「コンポーネント記述子」である。
- 併せて、版の混在(別言語・別バージョンの同時稼働)の扱いを U16「コンポーネントのバージョンと移行」として登録した。

## 経緯

### 2026-09-17 ADR 0012 の改訂 — 後続 ADR への追従

ADR 0012(提案)は起案(2026-08-24)の後に一度も改訂されておらず、その間に採用された ADR と仕様書の章の振り直しから取り残されていた。
採否の判断(第4節 4.2 のステップ5)に先立ち、次を反映した(同日に採用。次項)。**決定の骨格(Rust の1実装・並置・H1〜H8・2言語)は変えていない。**

| 改訂の元                          | ADR 0012 で変えた箇所                                                                               |
| --------------------------------- | --------------------------------------------------------------------------------------------------- |
| ADR 0021(数値型)・ADR 0019(時点)  | 論点5 に「基本型の写像」の軸と11言語の表を足し、決定8 に Rust / TypeScript の写像の表を置いた       |
| ADR 0013(テキスト・役割)          | テキストを出力言語の等値比較・キーに写さない事、G5 に役割を含める事を決定8 に足した                 |
| ADR 0014・第5章 5.6(名前の符号化) | 名前の可逆な符号化を決定8・決定9 に足し、規則は接合面の凍結と併せて決める事を「決めない事」に置いた |
| ADR 0015(命名・章の振り直し)      | 「ユニット」を「コンポーネント」に改めた。第0〜4章への参照を現行の節番号に合わせた                  |
| 第4章 4.6                         | 机上検証 2(block の上限は実装を待たずに要る)と仕様書の食い違いを解き、第4章 4.6 にその旨を記した    |

基本型の写像では **TypeScript が最も素直に写せない**(`int64` 以上と `時点` は `bigint`、テキストは UTF-16)。
これは「2つ目は接合面を壊しにかかる言語を選ぶ」という ADR 0012 の選び方を裏付ける方向の発見であり、判定は変わらない。
正準形は Shidzuku の型だけで決まり、出力言語の値の表現には依存しない事を決定4 に明記した。

### 2026-09-17 ADR 0012 の採用 — 動作環境の言語とトランスパイル先の確定

suzukimitsuru の判断により、上の改訂を経た **ADR 0012 を採用した**。U5 が決着し、第4節のステップ5 は空になった。
新しく足した基本型の写像の2つの表はこのまま採り、各言語の対応の細部はその言語をトランスパイル先に足す時に詳しく検討する。

| 反映先     | 内容                                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------------------------- |
| 第0章 0.8  | 実現戦略に「トランスパイル先は Rust と TypeScript、動作環境は Rust の1実装」を足した                       |
| 第1章 1.6  | 動作環境とコンポーネントの分担、正準形だけが流れる接合面、並置と同居、記述子による互換、凍結の時期を足した |
| 第3章 3.5  | pure の検証範囲に「Shidzuku 側で完結させ、トランスパイル先には要求しない」と答えを入れた                   |
| 第4章 4.6  | 机上検証 2(block の上限)の出典を採用済みの ADR 0012 とした                                                 |
| 各章の依拠 | 第1・3・4・5章の依拠行で ADR 0012 を採用の側へ移した                                                       |
| 第2節・3節 | U5 を「ADR 0012 採用」に、ADR 一覧の状態を「採用」にした                                                   |
| 第4節      | ステップ5 を「なし(採用済み)」にした                                                                       |

**接合面 H1〜H8 は採用しても凍結しない**(ADR 0012 決定10)。表は凍結まで ADR 0012 に置き、TypeScript のコンポーネントが通った時点で第1章へ移す。
それまでに U10・U11・U13(ステップ4)と U4・U16(第4節 4.4)の決定が、H2・H3・H5・H8・H6・H1 を改訂し得る。
判断待ちの ADR は 0006(ステップ3)と 0018(ステップ4)の2本になった。

### 2026-09-30 思考実験 27 で ESP32 を最小の動作環境として検討した

suzukimitsuru の指示により、ESP32 を最小の動作環境(Container)にできるかを[思考実験 27(ESP32 の最小動作環境)](../../experiments/27-ESP32の最小動作環境.md) で検討した。
前提は「管理機能は使わず、通信プロトコルと状態の確認とプログラムのロードだけになる」という見込みである。本書は何も決めていない。

- **三つでは足りない。** ask の期限・上限付きの待ち行列・`on failure` の再起動は、管理ではなく ask と flow の約束であり、外せない。
- **外すのは管理だけではない。** durable・recoverable・`collator` の意味も最小の機器には持てない。外し方は**弱めずに拒む**——動作環境の能力を記述子と照らし、ロードで受け付けない。
- **障害境界がプロセスから離れる。** ESP32 にはプロセスが無い。一体の書き込み(動作環境とコンポーネントを1つのイメージに焼く)なら障害境界は機器に下がり、1機器1コンポーネントなら四位一体が保たれる。
  WASM(WebAssembly)でのロードなら障害境界はコンポーネントに残り、wasm の import と export が接合面の8つの呼び出し(H1〜H8)の三つ目の実現手段になる。
- **Rust の出力だけで載る。** C をトランスパイル先に足す必要は無く、ADR 0012(動作環境の言語とトランスパイル先の言語)の「将来の変更想定」の前提の一つが外れる。
- **題材**: 思考実験 02(センサー収集パイプライン。flow だけの系)は載り、思考実験 04(分散 KV ストア。durable と recoverable を使う第1段の題材)は載らない。
  最小の分散動作環境(Phase 2)の最初の成果物の候補として、PC 1台と ESP32 1台で思考実験 02 の上流を動かす形を挙げた。

判断を待つ論点は六つである——動作環境の2つ目の実装になるか(意味の核を1クレートにする案)、能力の宣言とロードでの拒否、一体の書き込みか WASM でのロードか、
状態の確認の中身をデータ宣言(ADR 0028(データ宣言の語))で書くか、ロードの認証、フェーズの位置。どれも最小の言語実装(Phase 1)へ移る条件(4.5 の M1〜M5)は動かさない。

### 2026-09-30 ADR 0029 で最小の動作環境を決めた

suzukimitsuru が、思考実験 27(ESP32 の最小動作環境)の論点1〜6 を決めた。[ADR 0029(最小の動作環境)](../../decisions/0029-最小の動作環境.md) として起票し、同日に採用した。
論点4(状態の確認)は判断の前に調べる事を求められ、思考実験 27 の第10節(状態の確認の調べ)で調べた。

| 論点                  | 決定                                                                                            | ADR 0029                                  |
| --------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 論点1(2つ目の実装)    | 意味の核を `no_std` の1クレートにし、PC と ESP32 の器が共に使う。ADR 0012 は改訂しない          | 決定1(意味の核)・決定2(ADR 0012 との関係) |
| 論点2(能力と拒否)     | 動作環境は能力を宣言し、配置の設定の時に拒む                                                    | 決定3(能力と配置の設定)                   |
| 論点3(ロードの方式)   | 一体の書き込みと1機器1コンポーネントで始め、1台に複数を載せる時に WASM でのロードを足す         | 決定4(ロードの段)                         |
| 論点4(状態の確認)     | 状態の確認はコードに出さない。組み込みのデータ型は提供しない                                    | 決定5(状態の確認)                         |
| 論点5(ロードの認証)   | ロードの認証を含める。一体の書き込みはセキュアブート、WASM でのロードは動作環境が署名を確かめる | 決定6(ロードの認証)                       |
| 論点6(フェーズの位置) | 最小の分散動作環境(Phase 2)に置く                                                               | 決定7(フェーズの位置)                     |

- **状態の確認の調べ**: 状態の確認の各項目は、どれも動作環境・配置・監督・運用が判断するための物だった。コードが知るべき事は、
  相手の障害と期限切れは ask の失敗として、背圧は `pressure` の宣言として、再起動は `state` の宣言として、既に別の形で届いている。
  読ませると同じ事実が二つの道で届き、配置でコードの振る舞いが変わり(ADR 0015(C4 モデルの命名の取り込み))、接合面が広がる。
  経過時間計を言語に出さなかった ADR 0012 の決定2(責務の分担)と同じ線引きである。
- **決定に伴って足した事**: 意味の核は最小の言語実装(Phase 1)の動作環境の着手時から `no_std` で作る(後から切り出すと PC の都合が染み込む)。
  能力と照らすため、`collator` と記憶の見積もりをコンポーネント記述子に加える事を、コンポーネントのバージョンと移行(U16)に送った。
- 反映: 第1章 1.6(動作環境は言語の記述対象外)、計画書の第1節(フェーズ計画)の最小の分散動作環境・第2節 2.1(いまの状態)・第3節(ADR 一覧)・第4節 4.5(Phase 1 へ移るまでの計画)。
  最小の言語実装(Phase 1)へ移る条件(M1〜M5)は動かない。

### 2026-10-03 ADR 0030 で ESP32 ボードを選んだ

suzukimitsuru の指示で、Shidzuku で使う ESP32 のボードを選び、[ADR 0030(ESP32 ボードの選定)](../../decisions/0030-ESP32ボードの選定.md) として起票した(提案)。

- ADR 0029(最小の動作環境)の決定から、ボードに求める事を7つにした。Rust で ESP-IDF の上に書ける・zenoh-pico が動く・セキュアブート・OTA(回線越しの更新)の区画を2面取れるフラッシュ・
  USB だけで繋がる・PSRAM(外付けの擬似 SRAM)と WAMR(組込み向けの WebAssembly 実行系)の対応・USB の口の分離。
- **一体の書き込みのボードは ESP32-C6-DevKitC-1(N8)**。rustc 本流のターゲットで書け、`esp-idf-svc` の対応も成熟している。
  思考実験 02(センサー収集パイプライン)の上流に2枚、セキュアブートの確かめに1枚(eFuse を焼くと戻せない)、予備に1枚で4枚。
- **WASM でのロードのボードは ESP32-S3-DevKitC-1(N16R8)**。8MB の PSRAM と WAMR の対応がある。Xtensa のため Espressif の分岐した道具が要るが、意味の核は `no_std` の1クレートなので中身は変わらない。
- 思考実験 27 の後に量産に入った **ESP32-C5** は、PSRAM と WAMR の対応を持ち、両方の段を RISC-V の1品種で揃えられる唯一の候補である。
  Rust の ESP-IDF の上の対応がまだ若いため、WASM でのロードに入る時に比べ直す。ESP32-C61 は WAMR が対応していないため採らない。
- 型番が手に入らない時のために、代わりを選ぶ条件(フラッシュ 8MB 以上・USB・PSRAM 4MB 以上・回路図の公開)を置いた。
- 同日、suzukimitsuru の指示で公式ボード以外も比べた(XIAO ESP32C6・XIAO ESP32C5・M5Stack AtomS3R・Raspberry Pi Pico 2 W)。
  **推奨は変わらない。** 公式の DevKitC-1 だけが USB の口を2つ持ち(UART 変換と USB シリアル/JTAG)、zenoh-pico をシリアルで繋ぎながら書き込みとログが取れる。これを「USB の口の分離」として求める事に足した。
  XIAO ESP32C5(PSRAM 8MB)は ESP32-C5 を採る時の小型の候補とし、XIAO ESP32C6 はフラッシュ 4MB で外した。Pico 2 W は zenoh-pico が動くが、ESP-IDF の1つの SDK で揃う利点が無い。

### 2026-10-03 ADR 0030 を採用した

suzukimitsuru の判断により、**公式ボード以外に適したボードが無い事を前提として**、[ADR 0030(ESP32 ボードの選定)](../../decisions/0030-ESP32ボードの選定.md) を採用した。

- 一体の書き込みのボードは ESP32-C6-DevKitC-1(N8)を4枚(開発2・セキュアブートの確かめ1・予備1)、WASM でのロードのボードは ESP32-S3-DevKitC-1(N16R8)とする。
- WASM でのロードは「1台に複数を載せたくなった時」に来るため、ESP32-S3-DevKitC-1 は今は買わない。その時に ESP32-C5 の Rust の ESP-IDF の上の対応を確かめ、比べ直す。
- 前提が崩れた時は ADR 0030 を破棄して新しい ADR を起こす。
- 判断待ちの ADR は 0027(body の記法)の1本に戻った。

# 思考実験 29: 用語辞典による名前の規則 — 語を宣言すれば名前を揃えられるか

- 状態: Draft
- 日付: 2026-10-14
- 目的: 用語辞典(名詞・動詞を記述者が宣言する仕組み)を言語が提供する事で、名前(コンポーネント名・クラス名・メンバー名・メソッド名・変数名)を規則に従わせられるかを検討する。
  規則に従わせられる物、宣言を足せば従わせられる物、従わせられない物に分ける
- 経緯: suzukimitsuru の指示による
- 題材: これまでの思考実験 01〜28 と仕様書に現れた名前(コンポーネント名・公開面の名前・データ宣言の名前・欄名・区分名)
- 進め方: 先に既存の名前を棚卸しして、揺れを拾う(第2節)。次に用語辞典の形を仮に置き(第3節)、規則の候補を一つずつ揺れに当てて判定する(第4節)。
  最後に既存の決定と突き合わせ(第5節)、仕様に跳ね返る物を論点として残す(第6節)。
  **本書は何も決めない。** 用語辞典を言語に入れるかどうかも決めない

## 1. 問いの置き直し

### 1.1 Shidzuku の名前の種類

問いに挙がった名前の種類は、オブジェクト指向の言語の語である。Shidzuku にはクラスもメソッドも無いため、先に写す。

| 問いの語         | Shidzuku で当たる物                                                                   | 定める所            |
| ---------------- | ------------------------------------------------------------------------------------- | ------------------- |
| コンポーネント名 | `system`・`component`・`actor`・`external` の名前                                     | 第1章・第2章        |
| クラス名         | `record`・`choice`・`id` の名前、量・単位・暦の名前                                   | 第6章               |
| メンバー名       | `record` の欄名、`choice` の区分名、`state` の名前、内部階層(`layers`)の名前          | 第2章・第3章・第6章 |
| メソッド名       | 公開面(`expose`)の名前、`flow` 宣言の名前                                             | 第3章・第4章        |
| 変数名           | 公開面の引数名、body の中の関数名・変数名(body の記法(U26)が決まっていないため未確定) | 第3章・第5章 5.4    |

いずれも「記述者が定める名前」(第5章 5.1、ADR 0014(識別子と言語語彙の表記))であり、UTF-8 で書け、日本語の名前は正規の記述である。
言語が名前に課している規則は、文字集合(UAX #31(Unicode 標準附属書 第31号、識別子の構文))・正準形(NFC(正規化形 C))・見分けのつかない名前の禁止(E0014-3)の三つだけで、**語の選び方には何も言っていない**。

### 1.2 なぜ名前の規則が Shidzuku の問題になるか

Shidzuku は名前に多くを負わせている。

- **名前的型付け**: 構造が同じでも名前が違えば別型である(第6章 6.1)。`受注番号` と `受付ID` の区別は名前だけが担う。
- **型の名前が値の出どころを告げる**(第6章 6.6)。論理型を公開面に書けず、名前の付いた直和を書かせるのも(論理型の置き場の検査、E0019-1)、名前に語らせるためである。
- **図はコードからの投影である**(第0章 0.7)。図の節に載るのは名前であり、名前が揃っていなければ図も揃わない。

名前の語が揃っていない事は、型の検査では見つからない。`受注番号` と `注文番号` が同じ物を指すつもりで書かれても、名前的型付けは二つを別型として**正しく**拒む。
拒まれた記述者は変換を書くか、片方に寄せるかを迫られるが、どちらに寄せるべきかを言語は知らない。

## 2. 既存の名前の棚卸し

思考実験 01〜28 に現れた名前から、同じ物か近い物を指すのに語が揃っていない所を拾った。題材ごとに書かれた時期が違うため揺れは当然であり、責める物ではない。**用語辞典があれば何が見えたか**を見るための材料である。

| 揺れ                   | 現れた名前                                                                                                                                       | 出どころ                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| 識別子を表す語         | `品目ID`・`受付ID`・`従業員ID`・`拠点ID`・`センサーID` / `受注番号`・`引当番号`・`打刻番号` / `商品コード` / `キー`                              | 思考実験 05・08・10・12・21 |
| 公開面の名前の形       | `受注`・`引当`・`照会`(名詞の形) / `請求する`・`按分する`(動詞の形)                                                                              | 思考実験 01・06             |
| 「の」の有無           | `受注の照会` / `実績照会`、`引当の結果`・`決済の結果` / `受注結果`・`検索結果`                                                                   | 思考実験 05・10・12・20・21 |
| 送り仮名               | `引当済` / `引当済み`・`正規化済み` / `済`                                                                                                       | 思考実験 01・02・08・21     |
| 同じ事態の別の語       | `在庫不足` / `在庫なし` / `在庫切れ`                                                                                                             | 思考実験 01・20・21         |
| 字種                   | `OrderIntake`・`Frontdesk`・`PaymentBridge` と `注文管理` が同じ `contains` に並ぶ。`在庫同期` は日本語                                          | 思考実験 18・20             |
| 一つの語が二つの役     | `受注` が公開面の名前(`expose 受注(注文)`)と、直和の区分名(`choice 受注結果 = 受注(受注番号) \| …`)の両方                                        | 思考実験 01・05・12         |
| コンポーネント名の品詞 | 担い手(`Frontdesk`・`SearchGate`・`PaymentBridge`)/ 物(`Inventory`・`ShiftPlan`・`ProductIndex`)/ 働き(`OrderIntake`・`CatalogSync`・`在庫同期`) | 思考実験 01・08・10・18・20 |

棚卸しから分かった事は三つある。

1. **揺れの多くは「同じ概念に二つの語」である。** 識別子を表す語(`ID`・`番号`・`コード`・`キー`)と、在庫が足りない事態(`不足`・`なし`・`切れ`)がその例である。
   別の概念として使い分けているのか、同じ物を別の語で書いただけなのかは、名前からは分からない。
2. **語の並びは同じで、繋ぎだけが違う物がある。** `受注の照会` と `実績照会` は「何を照会するか」の書き方が二通りある。`引当の結果` と `受注結果` も同じである。
3. **名詞と動詞の境目が日本語では曖昧である。** `受注`・`引当`・`照会` はサ変名詞(「する」を付けて動詞になる名詞)で、物(受けた注文)も働き(注文を受ける事)も指す。
   `受注` が公開面の名前と区分名の両方に現れたのは、この曖昧さによる。英語でも `Order` は名詞と動詞を兼ねる。

## 3. 用語辞典の形(試案)

規則を当てるために、用語辞典を仮に置く。語彙(`glossary`・`term` など)は全て仮であり、綴りは ADR 0014 に従って ASCII とする。

```plaintext
glossary 通販の用語 {
  term 注文     thing    "客が品目と数量を示して出す依頼"
  term 受注     action   "店が注文を受け、受注番号を振る事"
  term 照会     action   "記録を変えずに読む事"
  term 番号     thing    "店が振る連番。外部の符号は コード と書く"
  term コード   thing    "外部の事業者が振った符号。店は振らない"
  term 窓口     agent    "外からの依頼を受け、内側の言葉に直して渡す役"
  term 不可     modifier "業務の規則により受け付けない事"
  term 済み     modifier "働きが終わった後の状態"
  joint の
  rejected term ID   use 番号, コード reason "店が振るか外部が振るかを語で分けるため"
  rejected term 済   use 済み         reason "送り仮名を揃える"
}
```

- `term` は語と、その**役**と、定義を持つ。定義は機械が検証しない文であり、意図の層(第0章 0.5)と同じ扱いになる。
- **役は品詞ではなく、Shidzuku の宣言の種類に結び付ける。** 名詞・動詞という文法の区別は自然言語ごとに違うが(第2節の三つ目)、宣言の種類は言語が定めている。

| 役         | 意味             | 名前の中心に据えてよい宣言                                                      |
| ---------- | ---------------- | ------------------------------------------------------------------------------- |
| `agent`    | 担い手           | `system`・`component`・`actor`・`external`                                      |
| `thing`    | 物               | `record`・`choice`・`id`・`state`・`record` の欄・`choice` の区分・量・単位・暦 |
| `action`   | 働き             | `expose`(公開面の名前)・`flow` 宣言                                             |
| `modifier` | 他の語に添える語 | 単独では名前の中心にならない                                                    |

- `joint` は語と語の間に置ける繋ぎ(日本語の「の」、英語の `_` など)を宣言する。言語は繋ぎの意味を知らない。
- `rejected term` は**退けた語**と、代わりに使う語と、理由を持つ。意図の層の `rejected`(ADR 0003(検証不能な意図の記述形式))と同じ形である。
  何を退けたかが残らなければ、後から来た記述者が同じ揺れを持ち込む。

## 4. 規則の候補と判定

規則の候補を一つずつ、第2節の揺れに当てる。判定は次の三つである。

| 判定                       | 意味                                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------- |
| 言語が強制できる           | 宣言された文字列と宣言の種類だけを比べて判定できる。自然言語の文法に踏み込まない       |
| 自然言語の性質の宣言が要る | 語順や活用など、自然言語ごとに違う性質を記述者が宣言すれば判定できる。宣言が方言になる |
| 強制できない               | 意味の正しさに踏み込む。意図の層と同じく、書かせる事はできても検証はできない           |

### 4.1 語の閉包 — 名前は辞典の語だけで組む

名前は、辞典の語と繋ぎの並びに**ちょうど一通りに**分けられなければならない。分けられない名前、二通り以上に分けられる名前はエラーとする。

- 判定: **言語が強制できる**。文字列の分割であり、分かち書きの無い日本語でも、語が宣言されていれば分けられる(最長一致ではなく全ての分け方を調べ、一通りである事を求める)。
- 第2節で捕まる物: `請求する`・`按分する`(`する` が語に無い)、`済` と `済み` の混在(片方しか宣言しない)、`ID` と `番号` の混在(片方を退けるか、両方を別の定義で宣言するかを迫られる)、
  `OrderIntake` と `注文管理` の字種の混在(`Order` と `注文` の両方を宣言するなら、同じ概念に二つの語を置く事になり、次の 4.2 に掛かる)。
- 新しい語を使うには辞典に足すしかなく、**語の追加が差分に現れる**。語彙の変化がレビューの対象になる事が、この規則の一番の効果である。
- 二通りに分けられる例: `検索語` を一語として宣言し、`検索` と `語` も宣言すると、`検索語` は二通りに分けられる。
  複合語を一語として持つか、二語の並びとするかを記述者が決める事になる(論点3(複合語))。

### 4.2 退けた語 — 退けた語を名前に使わない

`rejected term` に挙げた語を名前に含めない。

- 判定: **言語が強制できる**。ただし退けたと宣言された語だけが対象である。
- 宣言されていない同義語(ある記述者が `在庫切れ`、別の記述者が `在庫不足` と書く)は、語の閉包で辞典に足される時に初めて人の目に触れる。
  **同義である事を機械は判定できない**。語の閉包と合わせて、同義語が辞典に入る瞬間をレビューで捕まえる形になる。

### 4.3 語の並びの衝突 — 繋ぎだけが違う名前を並べない

同じ名前空間に、繋ぎを除いた語の並びが一致する別の名前が二つ以上あるとき、エラーとする(`受注の照会` と `受注照会`)。

- 判定: **言語が強制できる**。E0014-3(見分けのつかない名前)の、語の段での対応物である。E0014-3 が字形の骨格を比べるのに対し、こちらは語の並びを比べる。
- 第2節で捕まる物: 同じ名前空間に `受注の照会` と `受注照会` が並べば捕まる。`実績照会` と `受注の照会` は語の並びが違うため捕まらない。
  **繋ぎの付け方を一つに揃える事までは強制できない**(論点4(繋ぎ))。

### 4.4 役の一致 — 宣言の種類に合う役の語を名前の中心に置く

`component` の名前の中心は `agent` の語、公開面の名前の中心は `action` の語、という規則である。

- 判定: **自然言語の性質の宣言が要る**。「名前の中心」がどの語かは語順で決まり、語順は自然言語ごとに違う。
  日本語と英語の複合語は末尾が中心(`受注番号`・`OrderNumber`)だが、英語の句(`NumberOfOrders`)やフランス語は先頭が中心である。
- **日本語の中でも末尾が中心とは限らない。** `受注不可`・`在庫なし` の末尾は `modifier` の語で、名前全体は「受注できない事」という物(`choice` の名前)である。
  末尾を中心とすれば `不可` が中心になって規則に合わず、`modifier` を飛ばせば `受注`(`action`)が中心になって、やはり合わない。
- 中心の位置を記述者が宣言する(`head last` のような宣言)形は、ADR 0014 が退けた「識別子の文字集合をプロジェクトごとに宣言させる」と同じ方言の問題を持つ。
- サ変名詞の二つの役(第2節の三つ目)も、この規則に正面から当たる。`受注` を `action` とすれば区分名 `受注(受注番号)` が拒まれ、両方の役を許せば規則が働かない(論点2(一つの語の二つの役))。
- 規則が働くのは、**語が一つだけの名前**(`照会`・`窓口`)と、役を一つしか持たない語で組んだ名前に限られる。

### 4.5 表現語と型 — 名前の末尾の語が型の形を告げる

`id` の名前は識別子を表す語(`番号`・`コード`)で終わる、量の欄の名前は量を表す語で終わる、という規則である。
データ項目の命名の規格である ISO/IEC 11179-5(国際標準化機構と国際電気標準会議の規格。メタデータ登録簿の命名と識別の原則)の表現語(representation term。名前の末尾に置き、値の形を指す語。`Amount`・`Code`・`Identifier` 等)に当たる。

- 判定: **自然言語の性質の宣言が要る**。末尾という位置を使うため、4.4 と同じ語順の問題を持つ。
- 一方で、Shidzuku の名前的型付けとの相性は良い。`id 受注番号` の `番号` は、型の名前が値の出どころを告げる(第6章 6.6)事をそのまま語の段で支える。
  位置を使わず「`id` の名前は表現語を**含む**」とすれば語順に依らないが、`番号の種類` のような `choice` の名前と区別が付かなくなる。

### 4.6 欄名と型名 — 欄の名前と、その型の名前の語を揃える

`record 注文 { 品目: 品目ID, … }` の欄名 `品目` は、型名 `品目ID` の語の一部である。これを規則にする案である。

- 判定: **強制できない**。`取消の理由: 取消の理由` のように型名をそのまま欄名にする書き方と、`理由: 取消の理由` と役割だけを書く書き方のどちらも正しい。
  同じ型の欄が二つある時(`発送元: 住所`・`発送先: 住所`)は、欄名が型名と違う事が要点になる。指針には書けるが、規則にはならない。

### 4.7 定義の質と、宣言されていない同義語

- 定義の文が正しいか、定義と使い方が合っているかは**強制できない**。意図の層と同じで、書かせる事はできても検証はできない(ADR 0003)。
- 宣言されていない同義語を見つける事も**強制できない**(4.2)。研究では、識別子の語と概念の対応表を作って同義語(一つの概念に複数の名前)と同音異義語(一つの名前に複数の概念)を見つける方法があるが
  (Deissenboeck と Pizka、2006)、その対応表は人が作る物であり、Shidzuku の用語辞典がまさにその表に当たる。

### 4.8 判定の集計

| 規則             | 判定                       | 第2節で捕まる揺れ                                |
| ---------------- | -------------------------- | ------------------------------------------------ |
| 語の閉包         | 言語が強制できる           | 公開面の名前の形・送り仮名・識別子を表す語・字種 |
| 退けた語         | 言語が強制できる           | 一度退けた後の、同じ揺れの再発                   |
| 語の並びの衝突   | 言語が強制できる           | 同じ名前空間での「の」の有無                     |
| 役の一致         | 自然言語の性質の宣言が要る | コンポーネント名の品詞(語が一つの名前のみ)       |
| 表現語と型       | 自然言語の性質の宣言が要る | 識別子を表す語(位置を使えば)                     |
| 欄名と型名       | 強制できない               | —                                                |
| 定義の質・同義語 | 強制できない               | 同じ事態の別の語(辞典に入る時に人が見る)         |

**問いへの答えは「一部は出来る」である。** 用語辞典を言語が持てば、名前を**宣言された語だけで組ませる**事と、**退けた語を使わせない**事は、自然言語に踏み込まずに強制できる。
名詞と動詞という**文法の規則**は、語順と活用が自然言語ごとに違うため、言語の規則にはならない。
役を宣言の種類に結び付ければ一部は救えるが、日本語のサ変名詞と述語を含む名前(`受注不可`)で崩れる。

## 5. 既存の決定との突き合わせ

### 5.1 自然言語を仮定しない(ADR 0003・0006・0014)

ADR 0003 は拒否語リストと最小文字数を、ADR 0006(コンポーネントの粒度の指針)は指針の機械検証を、いずれも「言語仕様が特定の自然言語を仮定する」として退けた。
ADR 0014 は同じ理由で、言語の語彙を ASCII に、記述者の名前を UTF-8 にした。

用語辞典の規則のうち、語の閉包・退けた語・語の並びの衝突は、**記述者が宣言した文字列と照らすだけ**である。拒否語リストとの違いは、語を決めるのが言語ではなく記述者である所にある。
言語は日本語も英語も知らないまま、宣言との一致だけを見る。したがって ADR 0003 の退けた理由には当たらない。
役の一致と表現語と型は語順を使うため、当たる。第4節の判定の線は、この先例の線と一致している。

### 5.2 方言の問題(ADR 0014 の捨てた選択肢)

ADR 0014 は「識別子の文字集合をプロジェクトごとに宣言させる」案を、言語が方言を持つ事になり、コンポーネントの再利用が現場の宣言に依存するとして退けた。

用語辞典も現場ごとに違う。しかし事情が一つ違う。**コンポーネントの公開面は既にデータ宣言に依存している**(`expose 受注(注文)` の `注文` はトップレベルの `record`)。
語彙の共有は名前的型付けを採った時から始まっており、用語辞典はそれを型の名前から全ての名前へ広げる物である。
コンポーネントを別のシステムへ持って行く時に辞典の語が足りなければ、それは「語彙が違う所へ持って行った」事が見えたのであって、方言の害とは言い切れない。
ドメイン駆動設計(Domain-Driven Design)の言葉で言えば、ユビキタス言語(関係者が共有する一つの語彙)は境界づけられたコンテキストごとに違ってよく、境界を跨ぐ所では訳が要る。

ただし、文字集合の宣言が「何を書けるか」を変えるのに対し、用語辞典は「何という語で書くか」を変える。後者は前者より業務に近く、方言である事を受け入れる理由も強い。

### 5.3 省略の禁止(ADR 0008)

用語辞典を言語に入れるなら、辞典を書かない事は省略時の既定(検査しない)になる。ADR 0008 に従えば、辞典は必須とし、使わない事も `glossary none` と書く事になる。
一方で ADR 0008 は「約束の欠如」(`idempotent` を書かない事は冪等を約束しない事)を既定と区別しており、辞典を書かない事を「語を揃える約束をしない」と読む余地もある(論点1(置き場))。

### 5.4 名前空間(プログラムの宣言(U14))

辞典がどの範囲に掛かるかは、名前空間の範囲と同じ問いである。システムの入れ子(ADR 0018(システムの入れ子))を許した今、境界づけられたコンテキストはシステムに当たるのが素直で、
内側のシステムは親の辞典を受け継いで語を足すか、別の辞典を持つかを選ぶ形になる。プログラムの宣言(U14)の論点4(名前空間の分け方)と同時に決まる。

プログラムの宣言(U14)の論点2(直和の区分名)も関わる。`見つかった`・`なし` が複数の `choice` に現れるのは、同じ語を辞典に一度宣言し、多くの名前で使う形として自然に読める。

### 5.5 言語の外への写像(第5章 5.6)

第5章 5.6 は、出力先が受けない名前を**可逆な符号化**で綴り直すとしている。符号化された名前は読めない。
辞典の語に訳語を持たせれば(`term 受注 action "…" as order_intake`)、出力先の識別子を語の訳の並びで作れ、読める名前になる。
語の閉包により全ての名前が語の並びに分けられるため、訳語が一対一である限り可逆も保てる。
ただし訳語は同じ概念のもう一つの綴りであり、ソースには書かせず出力にだけ使う、と線を引く必要がある。

### 5.6 図とログ(第0章 0.7、ログ規約(U4))

辞典そのものが、コードから抽出できる用語集になる。図の凡例・ログの読み方・運用の手引きに、定義の文をそのまま載せられる。
図は名前を載せるため、名前が揃うほど図も揃う。投影の原則(第0章 0.7)の範囲を、構造から語彙へ広げる事になる。

### 5.7 shidzuku-lint(ADR 0026)

語の閉包・退けた語・語の並びの衝突は、既存の言語(Rust・TypeScript)へもそのまま移せる。英字の識別子は大文字と `_` で語に分かれるため、日本語より分割が易しい。
既存の lint にも綴りの検査(cspell 等)はあるが、それは**綴りの誤り**を見る物で、**語の選択**を揃える物ではない。
思考実験 26(shidzuku-lint)の判定で言えば「宣言を足せば移せる」に当たり、宣言は辞典のファイルになる。

### 5.8 body の記法(U26)

body の中の変数名は、body の記法(U26)が決まるまで規則を当てられない。body は原則自由(第0章 0.5)であり、辞典を body の中にまで掛けるかどうか自体が論点になる(論点5(範囲))。

## 6. 論点

### 論点1: 置き場 — 用語辞典を言語の宣言にするか

| 案                           | 中身                                                                                   | 利点                                               | 欠点                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------- |
| 言語の宣言にする案           | `glossary` をトップレベルの宣言にし、語の閉包・退けた語・語の並びの衝突をエラーにする  | 強制になる。図・ログ・出力先の識別子に辞典を使える | 宣言が増える。方言の問題(5.2)を正面から引き受ける                           |
| 言語の外に置き lint で見る案 | 辞典は別のファイルとし、shidzuku-lint が検査する                                       | 言語を変えない。既存の言語と同じ仕組みで済む       | 無視できる(ADR 0008・0013 が lint を退けた理由)。図と出力先には使いにくい   |
| 新しい宣言を足さない案       | データ宣言の名前を辞典とみなし、公開面と欄の名前がそれらの語で組まれている事だけを見る | 宣言が増えない。名前的型付けの延長で済む           | 働き(`action`)と担い手(`agent`)の語が辞典に入らない。退けた語を書く所が無い |

### 論点2: 一つの語の二つの役

サ変名詞(`受注`・`引当`)や英語の `Order` は、物と働きを兼ねる。役を一つに限ると `受注(受注番号)` のような区分名が書けず、二つを許すと役の一致(4.4)が働かない。
役を語に持たせず、**語の閉包だけを言語が強制し、役は指針に留める**のが一つの答えである。

### 論点3: 複合語 — `受注番号` は一語か二語か

`受注番号` を一語として宣言すれば固有の定義を書けるが、`受注` と `番号` も宣言されていると分け方が二通りになる(4.1)。
「宣言された複合語は分けない」を優先規則にするか、「複合語は構成する語の並びとして宣言する」(`term 受注番号 = 受注 番号`)とするかを決める必要がある。
後者なら語の並びの衝突(4.3)とも整合する。

### 論点4: 繋ぎ — 「の」を付けるか付けないかを揃えるか

`受注の照会` と `実績照会` の揺れは、語の並びの衝突(4.3)では捕まらない。「の」の有無は日本語の文体の問題であり、言語が揃えれば自然言語を仮定する事になる。
繋ぎを辞典で宣言できるようにしたまま、付け方は指針に留めるのが ADR 0003 の線に沿う。

### 論点5: 範囲 — どの名前に辞典を掛けるか

公開面に現れる名前(システム・コンポーネント・公開面・データ宣言・欄・区分)だけに掛けるか、内部階層の名前・`state` の名前・body の中の名前まで掛けるか。
コンポーネントの内側は原則自由(第0章 0.5)であり、情報隠蔽の内側の語は外の語彙に縛られないとも読める。一方で、ログ規約(U4)のログと図に出る名前は内側の物も含む。

### 論点6: 外部の語彙

`external` の公開面は外部の事業者の語彙で書かれる(`決済代行` の API(Application Programming Interface)の名前)。
外部の語を自分の辞典に入れると、退けた語(4.2)が外部との境界で使えなくなる。外部世界との境界(U12)で、外部の語彙を別の辞典として持つか、訳の置き場とするかを決める事になる。
プログラムの宣言(U14)の論点8(外部システムの語彙)と同じ所で決まる。

### 論点7: 課題として登録するか

本実験は課題(U)を足していない。用語辞典を言語に入れる方向へ進めるなら、「名前の規則」を新しい課題として登録し、
プログラムの宣言(U14)・外部世界との境界(U12)・body の記法(U26)の後ろか並びに置く事になる。名前空間と外部の語彙の答えに依るためである。
Phase 1 へ移る条件(計画書 第4節 4.5)には含めず、Phase 1 の中で shidzuku-lint と共に試す道もある。

## 8. まとめ

- **出来る事**: 用語辞典を言語が持てば、名前を宣言された語だけで組ませる事(語の閉包)、退けた語を使わせない事、繋ぎだけが違う名前を並べさせない事は、
  自然言語に踏み込まずに強制できる。新しい語は辞典への追加として差分に現れ、語彙の変化がレビューの対象になる。既存の名前の揺れの多くはこれで捕まる。
- **出来ない事**: 名詞・動詞という文法の規則、名前の中心の語の役、表現語の位置は、語順と活用が自然言語ごとに違うため、言語の規則にはならない。
  日本語のサ変名詞と、述語を含む名前(`受注不可`)が、役の規則を崩す。定義の正しさと、宣言されていない同義語の発見も強制できない。
- **Shidzuku に合う所**: 名前的型付けで既に語彙を共有している事、図はコードからの投影である事、出力先の識別子を可逆に綴り直す必要がある事の三つに、辞典はそのまま効く。
- **決める事**: 置き場(論点1)、語の役(論点2)、複合語(論点3)、範囲(論点5)、外部の語彙(論点6)、課題として登録するか(論点7)。
  名前空間(U14)と外部世界との境界(U12)の答えに依るため、それらと並べて決めるのが素直である。

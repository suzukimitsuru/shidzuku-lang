## 1. lint にすると何が変わるか

先に、この実験の前提と ADR 0008・0013 の関係を確かめておく。

ADR 0008 は「既定を残して lint で警告する案」を、ADR 0013 は「文字列を残して lint で検出する案」を、
いずれも**警告は無視できる**という理由で退けている。これは **Shidzuku の中の話**である。
Shidzuku は言語を自分で決められるので、lint に留める理由が無い——エラーにできる物を警告に置く事は、設計と実装の一体を自ら崩す事になる。

既存の言語では事情が逆になる。言語は変えられず、**届く手段は lint しか無い**。
したがって本実験は ADR 0008・0013 の判断を覆すものではなく、Shidzuku が届かない所へ考え方だけを運ぶ場合の話である。
無視できるという弱さは残る。その扱いは第4節 4.2 で見る。

もう一つの違いは**単位の写し方**である。

| Shidzuku         | Rust                                  | TypeScript                               |
| ---------------- | ------------------------------------- | ---------------------------------------- |
| システム         | ワークスペース                        | モノレポ(ワークスペース)                 |
| コンポーネント   | クレート                              | パッケージ                               |
| 内部階層(層)     | モジュール(`mod`)                     | ディレクトリ・ファイル                   |
| 公開面(`expose`) | クレート根から `pub` で届く項目       | `package.json` の `exports` から届く名前 |
| `ask`            | ネットワーク越しの要求(HTTP・gRPC 等) | 同左(`fetch` 等)                         |
| `flow`           | チャネル・メッセージキューへの送出    | 同左・イベント発行                       |
| `data`           | 公開面に現れる `struct`・`enum`       | 公開面に現れる `type`・`interface`       |

写しは一対一ではない。Rust のクレートは Shidzuku のコンポーネントと違って障害境界ではなく、
クレートを跨ぐ呼び出しは関数呼び出しである。**障害境界と配置単位は lint では作れない**(第0章 0.4 の四位一体のうち、設計単位だけが写る)。

## 2. 検査の一覧と判定

判定は次の4つである。

| 判定               | 意味                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------- |
| そのまま移せる     | 注釈を足さずに、ソースだけから判定できる                                                     |
| 宣言を足せば移せる | 書き手が宣言(第3節)を足せば判定できる。Shidzuku の構文が語っていた事を、注釈が代わりに語る   |
| 既にある           | 出力先の言語か、広く使われる lint が既に同じ検査を持つ。shidzuku-lint は束ねて番号を振るだけ |
| 移せない           | Shidzuku の構文か動作環境を前提にしており、既存の言語の上に同じ物が無い                      |

### 2.1 ソースの表記(第5章)

| #   | 検査                                                             | 出自    | 判定           | 既存の言語・lint                                                                                 |
| --- | ---------------------------------------------------------------- | ------- | -------------- | ------------------------------------------------------------------------------------------------ |
| L-1 | 双方向制御文字・書式文字・全角空白・行末の CR をソースに置かない | E0014-1 | そのまま移せる | rustc `text_direction_codepoint_in_literal` 等(双方向制御のみ)、ESLint `no-irregular-whitespace` |
| L-2 | 識別子を NFC で書く(正規化して受け入れず、拒む)                  | E0014-2 | そのまま移せる | Rust は NFC に**正規化して受け入れる**(RFC 2457)。拒む lint は無い                               |
| L-3 | 同じ名前空間に見分けのつかない識別子を置かない                   | E0014-3 | 既にある       | rustc `confusable_idents`・`mixed_script_confusables`(警告)                                      |

L-1 は既存の lint が双方向制御文字だけを見ているのに対し、第5章 5.5 は書式文字・全角空白・CR まで広げている。
日本語で書く現場では全角空白の混入が最も多く、ここは足す価値がある。
L-2 は Rust と立場が違う。Rust は書き手の綴りを NFC に畳んで同一視するが、Shidzuku は**書いた通りに読めなくなる**として拒む(第5章 5.5)。
lint にすると、Rust が黙って畳んでいる所を書き手に見せる事になる。

### 2.2 省略の禁止(第0章 0.5、ADR 0008)

省略の禁止は既存の言語に最も広く当たる。既存の言語は既定値だらけであり、そのうち**運用の驚き**(第0章 0.1)に直結する物を選ぶ。

| #   | 検査                                                                           | 出自                  | 判定           | 既存の言語・lint                                                                  |
| --- | ------------------------------------------------------------------------------ | --------------------- | -------------- | --------------------------------------------------------------------------------- |
| L-4 | 外への要求に期限を明示する(既定の無期限に頼らない)                             | 第4章 4.1(`deadline`) | そのまま移せる | Python の Bandit `B113`(`requests` の期限なし)。Rust・TypeScript には無い         |
| L-5 | 待ち行列に上限を明示する(上限の無いチャネルを作らない)                         | 第4章 4.3(`pressure`) | そのまま移せる | 無い                                                                              |
| L-6 | 送出の失敗を捨てない(`let _ = tx.send(…)`・投げ放しの Promise)                 | 第4章 4.3             | 既にある       | clippy `let_underscore_must_use`、typescript-eslint `no-floating-promises`        |
| L-7 | 直和の分岐に「残り全部」(`_`・`default`)を書かない                             | ADR 0008・ADR 0009    | 既にある       | clippy `wildcard_enum_match_arm`、typescript-eslint `switch-exhaustiveness-check` |
| L-8 | 文字列の整列に既定の順を使わない(`arr.sort()`・ロケールなしの `localeCompare`) | 第3章 3.2(`collator`) | 既にある       | typescript-eslint `require-array-sort-compare`(比較関数の有無のみ)                |
| L-9 | lint の抑止に理由を書く                                                        | ADR 0003(`rejected`)  | 既にある       | clippy `allow_attributes_without_reason`、eslint-comments `require-description`   |

- **L-4 と L-5 が最も価値が高い。** どちらも既定が「無限」であり、壊れ方が静かではない——期限の無い要求は相手の沈黙で呼び手を止め、
  上限の無い待ち行列は下流の詰まりを記憶域の枯渇に変える。Rust の `std::sync::mpsc::channel()` と tokio の `unbounded_channel()` は上限を持たず、
  `sync_channel(n)`・`channel(n)` が上限を持つ。判定は呼び出す API の名前だけで済むため、注釈が要らない。
- L-4 の「外への要求」は、HTTP クライアント等の既知の API の一覧で見る。一覧は言語とライブラリごとに持つ事になる。
  Shidzuku の側では、記述の外(`external`)への接続の書き方がまだ無い(U12)。**既存の言語では要求の大半が外へのものであり、lint の方が先に外を扱う**。
- L-5 は、上限を明示させるだけでは足りない。Shidzuku の `pressure` は溢れた時の振る舞い(`block`・`latest`・`drop`)まで言わせる。
  既存のチャネルは溢れると待つか失敗を返すかの二択で、`latest` に当たる物は `tokio::sync::watch` のような別の型になる。
  lint が見られるのは「上限がある事」までであり、振る舞いの宣言は第3節の注釈に頼る。
- L-7 は既にあるが、既存の lint は網羅性のための規則として置かれている。Shidzuku の理由は別で、**「残り全部」は既定の分岐**だからである——
  直和に区分が一つ増えた時、既定の分岐は黙ってそれを受け入れる。理由が違っても、検査は同じになる。
- L-9 は Shidzuku の検査ではない。lint の弱さ(無視できる)への手当てとして要る物であり、第4節 4.2 で扱う。

### 2.3 型(第6章)

| ---- | --------------------------------------------------------------------------- | ----------------------- | ------------------ | ----------------------------------------------------------------------------------- |
| L-10 | 公開面に `bool` を出さない(引数・応答・公開する構造体の欄)                  | E0019-1                 | そのまま移せる     | clippy `fn_params_excessive_bools`・`struct_excessive_bools`(個数で見る。1つは通す) |
| L-11 | 公開面に素の数値を出さない(単位の無い `f64`・`i64`・`number`)               | E0008-1(単位の欄)       | そのまま移せる     | 無い                                                                                |
| L-12 | 公開面に素の文字列の識別子を出さない(`String` の ID を新しい型で包む)       | E0009-1(名前的型付け)   | 宣言を足せば移せる | 無い                                                                                |

| L-16 | 通貨の量に浮動小数点を使わない                                              | W0017-1                 | 宣言を足せば移せる | 無い(名前からの推測に留まる)                                                        |
| L-17 | 浮動小数点と整数のあいだを往復させない                                      | W0017-2                 | そのまま移せる     | 無い                                                                                |
| L-18 | 壁時計で経過時間を測らない                                                  | E0019-2                 | そのまま移せる     | 無い                                                                                |
| L-19 | 暦の日時に時間の量を足さない(`NaiveDateTime + Duration`)                    | E0019-6                 | そのまま移せる     | 無い                                                                                |
| L-20 | 時間帯で変換した結果をそのまま保存しない                                    | W0019-3                 | 宣言を足せば移せる | 無い                                                                                |
| L-21 | テキストを素の `==` で比べない・ハッシュの鍵にしない                        | E0013-1                 | 宣言を足せば移せる | 無い                                                                                |
| L-22 | 照合キーを保存しない(ICU の sort key・`Intl.Collator` の結果を永続化しない) | E0013-3                 | そのまま移せる     | 無い                                                                                |

- **L-10・L-11 は「名前は公開面の語彙の全てである」(第6章 6.2)をそのまま移せる。** 公開面の型の中に `bool` や素の数値が現れる事は構文から分かり、
  注釈は要らない。既存の lint は `bool` を**個数**で見て、一つなら通す。Shidzuku は一つでも拒む——`真` が何を意味するかが型に無い事は、個数によらないためである。
- L-11 は単位の検査そのもの(E0010-1・E0022-1 等)を移すのではない。**単位を型に載せる場所を作らせる**だけである。
  単位の演算の検査は、新しい型(Rust の newtype、TypeScript のブランド型)か `uom` のようなライブラリに委ね、lint は素の数値が公開面へ漏れる事だけを見る。
  量の種別(比率・計数・計量・位置)の検査は既存の言語に写せない。型の算術を lint で再実装する事になるためである(2.6)。
- **L-18 は注釈なしで最も確実に当たる。** Rust の `SystemTime::now()` の差・`elapsed()`、TypeScript の `Date.now()` の差で期限や所要時間を測るコードは、
  壁時計の巻き戻りで負の時間を得る。`Instant`・`performance.now()` を使えば済み、判定は API の名前で足りる。
- L-21 は、どの文字列が**値としての自然言語**(テキスト)で、どれが識別子かが型に出ていないと判定できない。
  テキストを新しい型で包むか、層の注釈(第3節)で `domain` の層を示せば、そこでの `==` とハッシュを拒める。
- L-12・L-16・L-20 も同じく、値が何であるかの宣言が要る。L-16 は名前(`price`・`amount`・`金額`)からの推測なら注釈なしで書けるが、誤検出を持つため警告に留まる。

### 2.4 内部階層(第2章 2.4、ADR 0005・0013)

層の宣言は既存の言語に無い。宣言を足せば、ほぼ全てが移る。

| #    | 検査                                                               | 出自              | 判定               | 既存の言語・lint                                                                        |
| ---- | ------------------------------------------------------------------ | ----------------- | ------------------ | --------------------------------------------------------------------------------------- |
| L-23 | どの層にも属さないモジュールを置かない                             | E0008-1(`layers`) | 宣言を足せば移せる | 無い                                                                                    |
| L-24 | `pure` の層で IO をしない・`pure` の層から `io` の層に依存しない   | E0005-1           | 宣言を足せば移せる | ESLint `no-restricted-imports`(パスごとの上書き)、import-linter(Python)、ArchUnit(Java) |
| L-25 | 役割と強度の組み合わせを守る(`io` の `parse` 等を宣言しない)       | E0013-2           | 宣言を足せば移せる | 無い(宣言そのものの検査)                                                                |
| L-26 | 外部表現との詰め替え(直列化・バイト列化)を `boundary` の層に閉じる | E0021-1・E0013-4  | 宣言を足せば移せる | 無い                                                                                    |
| L-27 | 文字列の部分取得・分割・正規表現を `parse` の層に閉じる            | E0013-2           | 宣言を足せば移せる | 無い                                                                                    |
| L-28 | 暦と時間帯の変換を `boundary`・`format` の層に閉じる               | E0019-5           | 宣言を足せば移せる | 無い                                                                                    |

- 層を**依存の向き**で見る道具は既にある(依存の許可リスト)。Shidzuku が足すのは**二つの直交する軸**である——
  強度(何をしてよいか)と役割(何を扱ってよいか)。既存の道具は層の名前ごとに規則を書かせるが、Shidzuku は**規則を語彙に固定し、層には語を選ばせる**。
  書き手が規則を組み立てない分、どのプロジェクトでも `pure domain` の意味が同じになる。
- L-24 の「IO」は、禁じる API の一覧で見る(ファイル・ネットワーク・現在時刻・乱数・環境変数)。Rust の clippy は `disallowed_methods` で一覧を持てるが、
  設定はクレート単位でモジュール単位にならない。層ごとに一覧を切り替える所が shidzuku-lint の仕事になる。
  何を副作用とみなすかの具体は、Shidzuku でも Phase 1 の検証器で決める事になっている(第3章 3.5)。**lint の一覧は、その決定の下書きになる**。
- L-26 の直列化は、Rust なら `serde` の `Serialize`・`Deserialize` の導出と `to_be_bytes` 等、TypeScript なら `JSON.stringify`・`TextEncoder` で見る。
  `domain` の型が `Serialize` を導出している事は、外部表現の知識が領域へ漏れている事であり、宣言があれば構文だけで拒める。

### 2.5 コンポーネントの境界と意図(第2章・第3章、ADR 0003)

| #    | 検査                                                                          | 出自                      | 判定               | 既存の言語・lint                                                                   |
| ---- | ----------------------------------------------------------------------------- | ------------------------- | ------------------ | ---------------------------------------------------------------------------------- |
| L-29 | 宣言した相手の他と通信しない(依存の許可リスト。無ければ `none`)               | E0000-2・E0018-3          | 宣言を足せば移せる | cargo-deny(クレート単位の禁止)、Nx `enforce-module-boundaries`、dependency-cruiser |
| L-30 | 相手の内側を直に参照しない(公開面を通さない深い import)                       | E0018-4                   | そのまま移せる     | TypeScript は `exports` で塞げる。Rust は可視性で塞がれる                          |
| L-31 | 宣言した依存を使う                                                            | W0018-1                   | 既にある           | rustc `unused_crate_dependencies`、cargo-udeps、depcheck                           |
| L-32 | 公開面の宣言と実際の公開項目が一致する                                        | E0000-3                   | 宣言を足せば移せる | cargo-public-api、API Extractor(差分の検出。宣言との突き合わせではない)            |
| L-33 | 再起動を跨ぐ状態を宣言なしに持たない(大域の可変状態に `state` の宣言を求める) | E0008-2                   | 宣言を足せば移せる | clippy `static_mut_refs` 等(存在の検出のみ)                                        |
| L-34 | 失えない受け口に冪等の宣言を求める                                            | E0004-1                   | 宣言を足せば移せる | 無い                                                                               |
| L-35 | 要求の閉路を作らない                                                          | 第3章 3.5(未定事項)       | 既にある           | Cargo はクレートの循環を拒む。dependency-cruiser `no-circular`                     |
| L-36 | モジュールに意図(`why`・`rejected`・`change`)を書く                           | E0000-1・E0003-1・E0003-2 | 宣言を足せば移せる | rustc `missing_docs`(文書の有無のみ)                                               |
| L-37 | 意図の本文を写さない                                                          | W0003-1                   | 宣言を足せば移せる | 無い                                                                               |
| L-38 | 公開面が変わったのに意図が変わっていない                                      | W0003-2                   | 宣言を足せば移せる | 無い                                                                               |

- **L-36〜L-38 は、既存の言語に最も欠けている物である。** 既存の lint は文書が**有るか**だけを見る。
  Shidzuku の意図は、捨てた選択肢とその理由(`rejected`)を組で書かせる所に芯がある(ADR 0003)。
  文書コメントの見出し(Rust の `# Why`、JSDoc のタグ)を決めれば、構造の検査(組が0件なら拒む)は構文だけでできる。内容の正しさは見ない——Shidzuku と同じである(第3章 3.4)。
- **L-38 は lint の方が Shidzuku より先に形を持てる。** 第3章 3.5 は W0003-2 の判定基準を未定としている。
  lint なら「同じ変更(コミット・プルリクエスト)の中で、L-32 の公開面が変わったのに、そのモジュールの意図が変わっていない」と定められる。
  版管理の差分に頼る判定であり、Shidzuku のコンパイラが持てる物ではないが、W0003-2 の基準の一案にはなる(第5節 論点4)。
- L-29 の既存の道具は、許可リストが**無い**事を許す(書かなければ全て許す)。Shidzuku は `depends none` を書かせる。
  lint にする時も、宣言の無いコンポーネントを通さない所まで移すかが分かれ目になる。移さなければ省略の禁止は写らない。
- L-33 は大域の可変状態(`static` の `Mutex`、`lazy_static`、モジュールの最上位の `let`)を見つけるまでは注釈なしでできる。
  それが再起動で失われてよいか(`volatile`)、復元できるか(`recoverable`)を言わせるのが宣言の仕事である。

### 2.6 移せない物

| 検査・宣言                                       | 出自                                        | 移せない理由                                                                     |
| ------------------------------------------------ | ------------------------------------------- | -------------------------------------------------------------------------------- |
| 障害の非伝播                                     | 第0章 0.4                                   | 実行時の不変条件であり、動作環境が保証する。lint は静的にしか見ない              |
| 配達保証・`pressure` の振る舞い・期限の実施      | 第4章 4.3・4.4                              | 動作環境の仕事。lint は宣言がある事までしか見られない                            |
| 接続の両端の型の一致                             | E0009-1                                     | プロセスを跨ぐ。スキーマの差分の道具(`buf breaking`・OpenAPI の差分)の領分       |
| `correlate`・`on failure`                        | E0023-1〜E0023-4・E0008-1                   | フローの宣言が既存の言語に無い。フローはコードではなく構成に散っている           |
| システムの入れ子と `contains`                    | E0015-1〜E0015-3・E0018-1・E0018-2・E0018-5 | 既存のワークスペースは入れ子の境界を持たない。構成図の道具(Structurizr 等)の領分 |
| 量の種別と単位の算術                             | E0010-1・E0010-2・E0010-5・E0022-1〜E0022-5 | 型の算術を lint で再実装する事になる。型の側(newtype・`uom`)に委ねる             |
| 紀年法                                           | E0020-1〜E0020-3・W0020-1                   | 暦を宣言する語彙が既存の言語に無い                                               |
| `dec` を内部計算に閉じる・浮動小数点の厳密な意味 | E0021-2・E0021-4、第6章 6.3                 | 同じ型が無い。Rust も TypeScript も既定で FMA に融合しないため、後者は既に満たす |
| 状態の宣言と障害時の記述の矛盾                   | E0000-4                                     | `on failure` の記述が無い                                                        |

移せない物は二つに分かれる。**動作環境が担う物**(障害・配達・期限の実施)と、**プロセスを跨ぐ記述**(フロー・システム・接続の型)である。
どちらも、Shidzuku が一本の記述で貫こうとしている所そのものであり、lint が届かない事は予想どおりである。
逆に言えば、**lint で届く範囲はコンポーネントの内側と、その公開面まで**である。

### 2.7 判定の集計

| 判定               | 件数 | 主な物                                                                 |
| ------------------ | ---- | ---------------------------------------------------------------------- |
| そのまま移せる     | 11   | 期限の明示・待ち行列の上限・公開面の `bool` と素の数値・壁時計での計測 |
| 宣言を足せば移せる | 17   | 層の強度と役割・依存の許可リスト・状態の宣言・意図の構造               |
| 既にある           | 10   | 混同可能な識別子・網羅の分岐・暗黙の変換・整数の除算・未使用の依存     |
| 移せない           | 9 群 | 障害の非伝播・配達保証・フロー・システムの入れ子・量の種別の算術       |

「そのまま移せる」の11件は、shidzuku-lint の宣言の構文を決めずに作れる。「宣言を足せば移せる」の17件は、次節の宣言の置き場が決まって初めて作れる。

## 3. 宣言の置き場

「宣言を足せば移せる」の17件は、Shidzuku の構文が語っていた事を別の所に書かせる。置き場は三つ考えられる。

| 案               | 置き場                                           | 良い所                                     | 悪い所                                                                          |
| ---------------- | ------------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------- |
| D-1 設定ファイル | リポジトリの根の `shidzuku-lint.toml` 等         | 既存の道具(dependency-cruiser 等)と同じ形  | コードと離れる。第0章 0.2 の「設計と実装の乖離」をそのまま作る                  |
| D-2 言語の属性   | Rust の `#[…]`、TypeScript のデコレータ          | コンパイラが綴りを見る                     | Rust の道具の属性の登録は不安定(`register_tool`)。TypeScript は型に付けられない |
| D-3 文書コメント | モジュールの先頭の `//!`・ファイルの先頭の JSDoc | コードと同じファイルに居る。両言語で同じ形 | コンパイラは中身を見ない。綴りの誤りは lint が拾うしかない                      |

D-3 で、**Shidzuku の語彙と構文をそのまま使う**形を素描する。

```rust
//! component 在庫引当
//! intent {
//!   why      "引当の規則(先着と予約枠)を隠す"
//!   rejected option "受注の側で在庫を数える"
//!            reason "在庫の規則が二つのクレートに散る"
//!   change   "予約枠の種類が増える。規則はこのクレートの中で吸収する"
//! }
//! constraint {
//!   depends  在庫原簿
//!   expose   引当(品目ID, 数量) -> 引当の結果
//!   state    none
//!   collator none
//!   layers   { 受付 { io boundary } 規則 { pure domain } 応答 { pure format } }
//! }
```

```rust
//! layer 規則
// src/rules.rs — このファイルの全ては層「規則」(pure domain)に属する
```

TypeScript では同じ本文をファイルの先頭の JSDoc に置く。

- **語彙を Shidzuku と揃えると、lint の宣言がそのまま Shidzuku の記述の下書きになる。** 既存のコードに lint を被せた後で Shidzuku へ移る時、
  宣言は書き直さずに持ち込める。第0章 0.8 の漸進的な導入の、さらに一段手前の足場になる。
- 読む側は Shidzuku のパーサの部分集合(`intent` と `constraint`)で足りる。Phase 1 のパーサとの共有が効く。
- 名前は UTF-8 のまま書ける(第5章 5.4)。Rust のモジュール名やファイル名は ASCII に寄せる事が多いが、宣言の層の名前は `layer 規則` の一行でファイルに結べる。
- 代わりに、宣言の本文は**言語のコンパイラから見えない**。宣言と実装の食い違い(宣言に無い `pub` 項目、宣言に無い依存)を見つけるのは lint だけである。

## 4. lint にする事で変わる物

### 4.1 エラーと警告の段が一つ下がる

Shidzuku のエラーはコンパイルを止めるが、lint の拒否は CI の設定で止めるだけである。深刻度の二段(ADR 0003)は写せても、**強制の根拠が言語から運用へ移る**。
第5章 5.9 が「Rust が lint(警告)に置いた正規化と混同の規則をエラーに上げる」と書いた事の、ちょうど逆向きになる。

### 4.2 無視できる事への手当て — 抑止に理由を書かせる

ADR 0008・0013 が lint を退けた理由は、警告を無視できる事だった。lint では無視を無くせないが、**無視を記録に変える**事はできる。

```rust
#[expect(clippy::wildcard_enum_match_arm, reason = "外部の区分は増え続け、未知の区分は全て受付不可に落とすと決めた")]
```

Rust の `#[expect(…, reason = …)]` と ESLint の抑止コメントへの説明の要求(L-9)は、抑止に理由を書かせる。これは ADR 0003 の `rejected option … reason …` と同じ形である——
**規則を捨てた事と、その理由を組で残す**。理由の無い抑止を拒めば、無視はできても黙って無視する事はできなくなる。

### 4.3 番号の振り方

shidzuku-lint の規則に、第3章 3.3 の番号をそのまま振るかが問題になる。

- 振れば、診断から ADR を引ける(ADR 0016 の目的)。`E0019-2` を見た書き手は ADR 0019 を読めばよい。
- ただし lint の規則と Shidzuku の検査は一対一ではない。L-11(公開面に素の数値を出さない)は E0008-1 の単位の欄の一部を写した物で、同じ検査ではない。
  L-4・L-5 は第4章の宣言から来ており、元の番号が無い。L-9 は Shidzuku に元が無い。
- 番号を流用すると、**同じ番号が二つの道具で違う範囲を指す**事になる。番号は検査の識別のためにあり(第3章 3.3)、範囲が違えば別の検査である。

## 5. 論点

本実験は何も決めない。次の論点を残す。

### 論点1: shidzuku-lint を作るか・いつ作るか

「そのまま移せる」11件は、Shidzuku の構文を一つも決めずに作れる。しかし CLAUDE.md の原則は、Phase 0 の間は実装に着手しないとしている。
shidzuku-lint は Shidzuku の実装(compiler/・runtime/)ではないが、仕様の裏付けを得る前に道具を作る点は同じである。

- 作るなら、Phase 1 の検証器と**規則の一覧を共有する**形が筋である。lint の IO の一覧(L-24)は、Phase 1 の「何を副作用とみなすか」の下書きになる。
- 宣言の置き場(第3節)を D-3 にするなら、宣言を読む部分は Phase 1 のパーサと重なる。先に作ると、U14(プログラムの宣言)の決定前にパーサの一部を固める事になる。

**書き手に決めてもらう事**である。作らない場合も、本実験の表は Phase 1 の検証器の設計の入力として残る。

### 論点2: 直和の分岐に「残り全部」を書けるか(Shidzuku への逆輸入)

L-7 を書いていて、**Shidzuku 自身がこれを決めていない**事に気付いた。
第6章 6.1 は「無い」を直和で明示させ、ADR 0020 は E0020-2 を「ADR 0009 の直和の網羅性で落ちる場合が多い」と書く。網羅性は前提にされている。
しかし、body の中で直和を分岐する時に**「残り全部」の分岐を書けるか**はどこにも無い。

- 書けるなら、区分が一つ増えた時に既定の分岐が黙って受け入れる。これは ADR 0008 が退けた既定表と同じ形である。
- 書けないなら、区分の多い直和(区分コード等)で分岐が長くなる。
- body は原則自由である(第2章 2.4)が、直和は `data` の語彙であり、区分の増減は公開面の変更(W0003-2)である。body の自由に委ねてよいかが問いになる。

body の記法は Phase 1 で決まる。そこへの入力として残す。

### 論点3: 警告を黙らせる書き方が無い(Shidzuku への逆輸入)

第4章 4.2 は W0023-1 を「結ばない事が正しい場合があるため、エラーにはしない」とする。
警告であれば、正しい場合には**毎回出続ける**。Shidzuku には警告を抑止する書き方も、抑止の理由を書く場所も無い。

- 抑止を持たなければ、正しい記述が警告を出し続け、警告は読まれなくなる。ADR 0008 が退けた「無視できる警告」を、仕様自身が生む事になる。
- 抑止を持つなら、4.2 の形——**抑止と理由を組で書かせる**——が ADR 0003 の `rejected` と揃う。

第3章 3.5 の未定事項への入力である。W0023-1 の他に、W0018-1(誰も呼ばない `depends`)と W0003-1(意図の写し)も同じ問いを持つ。

### 論点4: W0003-2(意図の陳腐化)の判定基準の一案

第3章 3.5 は W0003-2 の判定基準を未定としている。L-38 は「同じ変更の中で公開面が変わったのに、意図が変わっていない」を基準にした。
Shidzuku のコンパイラは版管理の差分を見ないため、そのままは使えない。代わりに、コンポーネント記述子(ADR 0012 決定9)に公開面の要約と意図の要約を並べて持ち、
**前の版の記述子と比べる**形なら、コンパイラの外の道具としては同じ基準を持てる。U16(版の混在)の検討と併せて見る余地がある。

### 論点5: 外への要求の期限は、Shidzuku の `external` より先に形を持つ

L-4 は外への要求に期限を求める。既存の言語では要求の大半が外へのものであり、lint は外を扱うしかない。
Shidzuku では、記述の外(`external`)への接続の方式・属性・障害時の記述が未定である(U12、第4章 4.6)。
lint で「外への要求に期限が無い」を拒むなら、Shidzuku でも `external` への接続に `deadline` を必須にする事になるはずである。U12 への入力として残す。
計画書 第4節 4.5 は、U13 の軸(c)(全ての接続がどれかのフローに現れる)も外部との接続は U12 がフローの端点を決める時に広げるとした(2026-09-27)。
外部を端点に書けるようになれば、その接続の `deadline` も同じ所で問われる。二つは U12 で一緒に扱える。

## 6. まとめ

- 検査を既存の言語に当てると、**そのまま移せる11件・宣言を足せば移せる17件・既にある10件・移せない9群**に分かれた。
- **lint が届くのは、コンポーネントの内側とその公開面まで**である。障害・配達・期限の実施(動作環境)とプロセスを跨ぐ記述(フロー・システム)には届かない。
- 注釈なしで最も効くのは、**既定が「無限」になっている所**——期限の無い要求(L-4)、上限の無い待ち行列(L-5)——と、
  **公開面に名前の無い値を出す所**——`bool`(L-10)と素の数値(L-11)——、それに**壁時計での計測**(L-18)である。
- 宣言を足せば、**層の強度と役割**(L-23〜L-28)と**意図の構造**(L-36〜L-38)が移る。どちらも既存の道具に同じ物が無い。
- lint の弱さ(無視できる)は消せないが、**抑止に理由を書かせる**事で、ADR 0003 の `rejected` と同じ形の記録に変えられる。
- Shidzuku へ跳ね返る論点が3つ出た——直和の分岐の「残り全部」(論点2)、警告の抑止の書き方(論点3)、外への要求の期限(論点5)。

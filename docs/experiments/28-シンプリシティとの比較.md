## 1. 本書の主張

| 主張                       | 中身                                                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 複雑さと煩雑さを分ける     | 複雑(complex)な物でも規則に従えば理解できる(雪の結晶)。規則に従わない煩雑さ(complicated)が予測を難しくする |
| 方向を定め、一歩進み、学ぶ | Orient・Step・Learn の繰り返しを、個人とチームの両方の進め方の軸にする                                     |
| 規則より判断               | 固定した規則や「ベストプラクティス」を退け、シンプルさを一人ひとりの態度として扱う                         |
| 削る                       | 肥大を減らし、不要な依存を取り除く。作業の流れと意思疎通も簡素にする                                       |
| コードを素直に保つ         | データ駆動の設計、状態機械など、コードを読み易く変え易く保つ実践を挙げる                                   |
| 持続可能で人間的である     | 速さよりも、続けられる事と、人が無理なく働ける事を重く見る                                                 |

## 2. 同じ所

| 本書                       | Shidzuku                                                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 複雑さと煩雑さを分ける     | 分散システムが本来持つ複雑さは消さず、規則から外れる部分を取り除く。コンポーネントの四位一体(第0章 0.4)、四つの段の固定(第0章 0.3)、省略時の既定を持たない事(第0章 0.5 三層記述)   |
| 方向を定め、一歩進み、学ぶ | 各フェーズを「動く最小の成果物」で締める。仕様に迷ったら思考実験に戻って方向を確かめ、学んだ事を ADR に残す(計画書 第9節(進め方の原則))                                            |
| 持続可能で人間的である     | 「静かなシステム」——運用で驚きがない事、障害が伝播しない事(第0章 0.1 理念・0.6 静かさの構造化)。設計意図を残し、将来の保守者の負担を減らす(第0章 0.2 解決したい問題・0.5 三層記述) |

## 3. 違う所

| 観点                     | 本書                                 | Shidzuku                                                                                                                                             |
| ------------------------ | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 規則か、判断か           | 固定した規則を退け、人の判断に任せる | 判断を言語に組み込み、機械に強制させる。意図の記述は必須で、制約に違反すればコンパイラが拒否する(第0章 0.5 三層記述)                                 |
| 何を「シンプル」と見るか | 余計な物を削る                       | 省略時の既定を採らず、該当が無い事も `none` と書かせる。書く量は増えるが、外部の知識なしにそれだけで読める(第0章 0.5 三層記述、ADR 0008(省略の禁止)) |
| 手を入れる対象           | 開発者とチームの習慣                 | 成果物の構造。習慣に頼らずに済む形を作る                                                                                                             |
| 依存への態度             | 不要な依存を削る                     | 依存を宣言させて検証する。依存を減らす事自体は目的にしない。トランスパイラ・動作環境・Raft・Zenoh という道具立ては、本書の観点からは問われる所       |

一言で言えば、**目指す所(煩雑さを無くし、持続可能で人間的な開発)は同じで、手段が違う**。本書は人の習慣と判断に頼り、Shidzuku は言語による強制に頼る。

## 4. 系譜に含めない理由

第2節(同じ所)に並べた Shidzuku の考え方は、いずれも **suzukimitsuru の構想から出ており、本書から取り込んだ物ではない**。
この比較は、その構想に従って本書を読んだ物である。

第0章 0.9(参照する系譜)は、Shidzuku が**取り込んだ物**を出典と共に挙げる節である(John Ousterhout『A Philosophy of Software Design』の深いモジュール、結合バランスの物差し、Erlang/OTP の障害境界など)。
本書から取り込んだ物は無いため、suzukimitsuru の判断により系譜には含めない。
思考実験 24(Hike の取り組み)が系譜に足さなかったのと同じ扱いである。

検討した事は本書に残す。第3節(違う所)の「規則か、判断か」と「何を『シンプル』と見るか」は、Shidzuku が意図して逆を選んだ所であり、
採った道の説明として後で参照できるようにしておく。

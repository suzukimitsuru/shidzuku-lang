# 思考実験 30: 開発の流れと用語辞書 — 段を追って用語を育てる

- 状態: Draft
- 日付: 2026-10-15
  (改訂 2026-10-16: suzukimitsuru の指示で、用語辞書と宣言から母国語の名前を除いた。母国語との対応はローカライズと共に後で考える(思考実験 29 の論点3(ローカライズ))。

- 目的: 開発の初期にシステム・外部システム・人(actor)から記述し、次にコンポーネント、最後にデータの欄や DB(データベース)の項目のような詳細を記述してゆく流れの中で、
  用語を記述の中で定義し、開発の進みと共に用語辞書を育ててゆく方法を検討する。流れを止めずに、無理なく扱える形を探す
- 経緯: suzukimitsuru の指示による。思考実験 29(用語辞書による名前の規則)の続きである
- 前提: 思考実験 29 の前提をそのまま使う。**コードの名前は英語(ASCII)だけで書く。用語辞書は英語の語・役・定義を持ち、母国語の欄を持たない。**
  これは ADR 0014(識別子と言語語彙の表記)の決定3 と食い違い、思考実験 29 の論点7(名前を英語に限る事)で未決である。言語の語彙(`glossary`・`term` など)は全て仮である
- 題材: 思考実験 20(対になる通信)の通販を、段を追って書き直す
- 進め方: 用語辞書の扱い方の案を三つ置き(第2節)、通販をシステムの段・コンポーネントの段・詳細の段の順に書きながら、語がどこで生まれ、どこに置かれるかを数える(第3節)。
  分かった事を整理し(第4節)、仕様に跳ね返る物を論点として残す(第5節)。**本書は何も決めない**

## 1. 開発の流れと記述の段

suzukimitsuru が考える流れは、Shidzuku の段(第0章 0.3、ADR 0015(C4 モデルの命名の取り込み))の順と一致する。

| 流れ                     | Shidzuku の段  | 書く宣言                                                                               | 定める所         |
| ------------------------ | -------------- | -------------------------------------------------------------------------------------- | ---------------- |
| これから開発するシステム | システム       | `system`(入れ子にできる)                                                               | 第1章            |
| ユーザーの種類           | システム       | `actor`(システムを使う人・役割)                                                        | 第1章 1.4        |
| 外部システム             | システム       | `external`(記述の外にある系)                                                           | 第1章 1.4        |
| コンポーネント           | コンポーネント | `component`・`expose`・`flow`・`state`                                                 | 第2〜4章         |
| データの欄・DB の項目    | コード         | `record` の欄・`choice` の区分・`state` の中身。DB の表と列は body の内側か `external` | 第2章 2.4・第6章 |

- **ユーザーの種類は `actor` に当たる。** 第1章は「システムを使う人・役割の列挙」としており、`actor 買い物客 "商品を探し、注文する"` のように説明の文を添える。
- DB は二通りに現れる。コンポーネントが内側に持つ DB は `state` の宣言だけが外に見え、表と列は body の内側である(第2章 2.4 の境界の層)。
  外部の技術として図に出したい DB は `external` に書く(第1章 1.4)。

## 2. 用語辞書を扱う三つの形

| 案                     | 中身                                                                                  | 流れとの相性                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 辞書を先に書く案       | 開発の初めに用語辞書を書き上げ、記述はその語だけで書く                                | 悪い。語は記述を進める中で見つかる。先に書き上げる事は、仕様だけを先行させる事と同じになる |
| 宣言の場所で定義する案 | 宣言(`actor`・`external`・`system`・`component`・`record` 等)が、その名前の定義を持つ | 良い。段を進めると宣言が増え、辞書もそれに連れて増える                                     |
| 使ってから足す案       | 名前を先に書き、辞書に無い語をコンパイラが一覧する。記述者が後から辞書に足す          | 良い。書く手を止めない。ただし足すまではエラーのままである(省略の禁止。ADR 0008)           |

第3節では、**宣言の場所で定義する案と、使ってから足す案を組み合わせて**書く。宣言を持つ名前は宣言の場所で、宣言を持たない語(`number`・`refusal` など)は、使った段の用語辞書のブロックに足す。

## 3. 段を追って書く

書き方は次の通りとする(全て仮)。

- `actor` と `external` は既に説明の文を持つため、それを定義とする。`system`・`component`・`flow` の定義は意図の層(`intent`)が既に語っているため、何も足さない。
  データ宣言(`record`・`choice`・`id`)には、名前の後に定義の文を置く。
- 宣言を持たない語は、その段のシステムの `glossary` ブロックに `term <英語の語> <役> "<定義>"` と書く。役は思考実験 29 の第3節(担い手・物・働き・添える語)である。
- 定義はテキストであり、本書の例は日本語で書いた。定義は語の意味を縛る文であって、語の訳ではない。
  (改訂前は、宣言の名前の後と `term` の行に `ja "<母国語の名前>"` を置いていた。母国語の欄を除いたため外した)
- 一語だけの名前の宣言(`actor shopper`・`record Order`)は、その語の定義を兼ねる。

### 3.1 システムの段 — システム・人・外部システム

```plaintext
system Commerce {
  intent { ... }
  constraint {
    actor    shopper      "商品を選んで注文し、確定の知らせを受け取る人"
    external paymentAgent "カード決済を代行する外部の事業者"
    depends  none
    expose   placeOrder   (Order) -> OrderNumber | OrderRefusal by OrderDesk
    expose   inquireOrder (OrderNumber) -> OrderState | UnknownOrder by OrderDesk
    contains OrderDesk, OrderOffice
  }
}

record Order        "客が品目と数量を示して出す依頼" { ... }
id     OrderNumber  "店が受け付けた注文に振る番号"
choice OrderRefusal "注文を受け付けられない理由" = ...
choice OrderState   "受け付けた注文が確定したか、取り消されたか" = ...
choice UnknownOrder "照会された番号が記録に無い事" = ...

glossary Commerce {
  term payment  thing    "代金を受け取る手続き"
  term agent    agent    "他者に代わって手続きを行う者"
  term desk     agent    "客との接続を受け持ち、内側の言葉に直して渡す役"
  term office   agent    "注文を受けてから確定までを預かる内側の系"
  term number   thing    "店が振る連番"
  term refusal  thing    "業務の規則により受け付けない事"
  term state    thing    "ある時点で決まっている様子"
  term place    action   "依頼を相手に差し出す事"
  term inquire  action   "記録を変えずに読む事"
  term unknown  modifier "記録に無い事"
}
```

この段で辞書に入った語は 13 である。

| 置き場              | 語                                                                                                | 数  |
| ------------------- | ------------------------------------------------------------------------------------------------- | --- |
| 一語の名前の宣言    | `commerce`(`system`)・`shopper`(`actor`)・`order`(`record`)                                       | 3   |
| `glossary` ブロック | `payment`・`agent`・`desk`・`office`・`number`・`refusal`・`state`・`place`・`inquire`・`unknown` | 10  |

分かった事は三つある。

- **宣言の場所で定義できる語は少ない。** 名前の多くは複合語(`OrderNumber`・`paymentAgent`)であり、宣言はその名前を定義するが、名前を組む語(`number`・`agent`)は定義しない。
  語の大半は `glossary` ブロックに入る。
- **母国語の名前は、語を並べても得られない事が多い。** 改訂前は宣言の場所に母国語の名前も書いており、その時に見えた事である。
  複合語の名前9つのうち、語の母国語を並べて業務の名前になったのは `paymentAgent`(`決済代行`)と `OrderOffice`(`注文管理`)の2つだけだった。
  `OrderNumber` は `注文番号` になり、業務の語 `受注番号` と違う。`placeOrder` は英語が動詞・目的語の順で、並べると `出す注文` になる(日本語は `注文を出す` の順)。
  母国語の欄を除いたため、この事はローカライズへ渡す材料とする(思考実験 29 の論点3(ローカライズ))。
- **言語の語彙と記述者の語がぶつかる。** 役の語 `agent` と、記述者の語 `agent`(代行)が同じ綴りで、`term agent agent` という行ができる。
  役の綴りに一般的な英語を使うと、前提(コードは英語)の下では記述者の語と衝突しやすい(論点6(役の綴り))。

### 3.2 コンポーネントの段

```plaintext
component OrderDesk {
  intent { ... }
  constraint {
    depends    OrderOffice
    expose     placeOrder       (Order) -> OrderNumber | OrderRefusal
    expose     inquireOrder     (OrderNumber) -> OrderState | UnknownOrder
    expose     notifyOrderState (OrderState) flow in
    ...
  }
}

system OrderOffice {
  intent { ... }
  constraint {
    actor    none
    external paymentAgent "PaymentBridge が呼ぶ"
    depends  paymentAgent
    expose   placeOrder       (Order) -> OrderNumber | OrderRefusal by OrderIntake
    expose   cancelOrder      (OrderNumber) -> CancelResult by OrderIntake
    expose   inquireOrder     (OrderNumber) -> OrderState | UnknownOrder by OrderStore
    expose   notifyOrderState (OrderState) flow out by OrderStore
    contains OrderIntake, Inventory, OrderStore, PaymentBridge
  }
}

component Inventory {
  constraint {
    expose reserve (Order) -> Reserved | Stockout
    ...
  }
}

glossary OrderOffice {
  term intake   agent    "注文を業務として受け付け、番号を振る役"
  term store    agent    "記録を持ち続ける役"
  term bridge   agent    "外部との手続きを内側の言葉に直す役"
  term cancel   action   "受け付けた注文を無かった事にする"
  term notify   action   "相手に知らせる"
  term reserve  action   "在庫を注文のために取り置く"
  term reserved modifier "取り置きが済んだ状態"
  term stockout thing    "引き当てる在庫が無い事"
  term result   thing    "働きの後に返る値"
}
```

この段で辞書に入った語は 10 である(一語の名前の宣言 `Inventory` から1、`glossary` ブロックから9)。

- **内側のシステムは自分の `glossary` を持つ。** `intake`・`reserve` は `OrderOffice` の内側でだけ使う語であり、`Commerce` の辞書には要らない。
  語の範囲がシステムの入れ子(ADR 0018(システムの入れ子))に従うので、内側の語彙が外に漏れない。
- **入れ子の段で宣言し直す `external` は、定義を持たない。** 第1章 1.5 は内側の `external` を親にも宣言させ(E0018-5)、説明の文は段ごとに違ってよい
  (`Commerce` では「カード決済を代行する外部の事業者」、`OrderOffice` では「PaymentBridge が呼ぶ」)。前者は語の定義で、後者は**その段での関わり**である。
  語の定義は最も外の宣言の一か所に置き、内側の宣言は関わりだけを書く形が素直である。
- **同じ公開面の名前に、段ごとに違う母国語の名前を付けたくなる。** 改訂前に母国語の名前を書いていた時に見えた事である。
  外から見れば `placeOrder` は `注文受付`、`OrderOffice` の内側から見れば `受注` である(思考実験 20 も、外は `注文受付`、内は `受注` と書いた)。
  母国語の欄を除いたため、この事もローカライズへ渡す材料とする(思考実験 29 の論点3(ローカライズ))。
- **語の追加がレビューに掛かった。** `intake`(受付)を足した時、`Commerce` の `desk`(窓口)と意味が近い事が差分に現れた。
  定義を見比べ、`desk` は外との接続(HTTP・JSON)を受け持つ役、`intake` は業務として受け付ける役と分けて、両方を残した。
  **語が足される瞬間に、近い語との違いを定義で言わされる。** 用語を育てるとは、この定義の研ぎ直しの繰り返しである。

### 3.3 詳細の段 — データの欄・区分・DB の項目

```plaintext
record Order "客が品目と数量を示して出す依頼" {
  item:     ItemCode,
  quantity: uint32(0) piece
}
id     ItemCode     "仕入先が品目に振った符号"
choice OrderState   "…" = Confirmed(OrderNumber) | Cancelled(OrderNumber, CancelReason)
choice CancelReason "注文が取り消された訳" = Stockout | PaymentFailure | ShopperCancel

glossary Commerce {
  ...
  term item      thing    "店が売る物の種類"
  term code      thing    "外部が振った符号。店は振らない"
  term quantity  thing    "数えた量"
  term confirmed modifier "受け付けた注文が覆らなくなった状態"
  term cancelled modifier "取消が済んだ状態"
  term reason    thing    "そうなった訳"
  term failure   thing    "手続きが成り立たなかった事"
}
```

この段で辞書に入った語は 8 である(単位の宣言 `piece` から1、`glossary` ブロックから7)。

- **語の昇格が起きた。** `CancelReason` は `OrderState` の欄を通って `OrderDesk`(`Commerce` の直下)まで届くため、`Commerce` の段の型である。
  その区分 `Stockout` と `ShopperCancel` は、`OrderOffice` の辞書にしか無い語 `stockout`・`cancel` を使う。`Commerce` からは見えないため、エラーになる。
  区分名は公開する名前であり(思考実験 29 の第9節(公開する名前への限定))、規則を公開する名前に限っても、このエラーは変わらない。
  コンパイラは語を使う全ての名前の**最も近い共通の親**(ここでは `Commerce`)を示せ、記述者は語をそこへ移す。
  **語の範囲は、使われる範囲が広がるにつれて外へ育つ。** これはデータ宣言の届く範囲(計画書 第5節 5.10 の帰属の基準の案)と同じ形であり、思考実験 23(結合の釣り合い)のモデル結合の距離が、語の段でも見える。
- **DB の項目はコンポーネントの内側の名前である。** `OrderStore` が内側に持つ DB の表と列は body の内側であり、Shidzuku の記述には現れない。
  全ての名前に辞書を掛けるなら、用語辞書を言語に依らないファイルとして書き出し(思考実験 29 の第6節 6.4(組み合わせの余地))、shidzuku-lint が DB の定義(SQL の `create table`)の列名を同じ辞書で検査する事になる。

```sql
create table order_log (
  order_number text,     -- order・number: 辞書にある
  item_code    text,     -- item・code: 辞書にある
  quantity     integer,  -- quantity: 辞書にある
  created_at   timestamp -- created・at: 辞書に無い。lint が知らせる
);
```

その場合、`created`・`at` のように DB の中でだけ使う語は `OrderStore` の範囲に置くのが素直であり、コンポーネントも自分の `glossary` を持つ事になる(論点4(コンポーネントの辞書))。

**辞書に無い語を公開する名前にだけ使わせない形**(思考実験 29 の第9節)を採るなら、DB の表と列は内側の名前であり、辞書に掛からない。
`created`・`at` を辞書に足す必要は無く、コンポーネントの辞書も要らない。`order_number` が公開する型 `OrderNumber` と同じ語で組まれている事は、望ましいが求めない。

### 3.4 集計

| 段                 | 書いた名前 | 新しい語 | うち宣言から | うち `glossary` から | 昇格 |
| ------------------ | ---------- | -------- | ------------ | -------------------- | ---- |
| システムの段       | 12         | 13       | 3            | 10                   | 0    |
| コンポーネントの段 | 10         | 10       | 1            | 9                    | 0    |
| 詳細の段           | 10         | 8        | 1            | 7                    | 2    |

- この規模では、**名前1つにつき新しい語がほぼ1つ要った。** 語の使い回し(`order` は 13 の名前に現れた)は増えていくが、小さな系では新しい語の数は減り切らない。
- 宣言から定義される語は5で、全体(31)の六分の一に留まる。**語の大半は `glossary` ブロックに入る。**
- 表に数えた名前は、いずれも公開する名前である(思考実験 29 の第9節)。規則を公開する名前に限っても、この表の数は変わらない。限る事で減るのは、DB の列(3.3)や body の中の名前の分である。

## 4. 無理なく扱うための形

第3節から、流れを止めずに用語辞書を育てる形を次のようにまとめる。

1. **段ごとに、その段のシステムに辞書を置く。** 辞書は一つの大きなファイルではなく、システムの入れ子に沿って分かれる。内側の語は外に漏れず、外の語は内側から使える。
2. **宣言の場所に、定義を書く。** `actor` と `external` の説明の文、`system`・`component`・`flow` の意図、データ宣言の定義の文が、その名前の定義を兼ねる。
3. **宣言を持たない語は、使った段の辞書に足す。コンパイラが雛形を出す。** 辞書に無い語を含む名前はエラーとし(省略の禁止)、
   コンパイラは無い語ごとに、置くべき辞書(使う名前の最も近い共通の親)と、`term <語> <役の候補> ""` の雛形を示す。記述者は定義を埋めるだけである。
4. **使う範囲が広がった語は、外の辞書へ移す。** コンパイラが移す先を示す。移した事は差分に現れ、語彙の結合が広がった事がレビューに掛かる。
5. **語の追加と改名は差分に現れ、退けた語は残す。** 定義を研ぎ直す時は語を書き換え、改名した時は古い語を `rejected term` として残す。思考実験 29 の退けた語(4.2)が、改名の履歴を兼ねる。
6. **辞書は段ごとに書き出す。** システムの段を書き終えた時点で、`Commerce` の辞書(語・役・定義・使われている名前)を文書として書き出せる。
   コードを読まない関係者(業務の担当者)が、開発の初めから用語の一覧をレビューできる。図がコードからの投影である(第0章 0.7)のと同じく、用語集もコードからの投影になる。

## 5. 論点

### 論点1: データ宣言に定義の文を書かせるか

`actor` と `external` は説明の文を持ち、`system`・`component`・`flow` は意図の層を持つ。データ宣言(`record`・`choice`・`id`)だけが、現在は説明を持たない。
用語辞書を宣言の場所で育てるなら、データ宣言にも定義の文を足す事になる。省略の禁止(ADR 0008)に沿えば必須だが、`record` の欄や `choice` の区分まで求めるかは別に決める。

### 論点2: 母国語の名前を全ての宣言に書かせるか(ローカライズへ送った)

改訂前は、語を並べた母国語の名前が業務の名前と一致したのが複合語の名前9つのうち2つだった事から、名前ごとの母国語の名前を全ての宣言で必須にするかを論点にした。
母国語の欄を除いたため、ローカライズと共に後で考える(思考実験 29 の論点3(ローカライズ))。

### 論点3: 段ごとの母国語の名前(ローカライズへ送った)

改訂前は、同じ公開面の名前 `placeOrder` を外は `注文受付`、内は `受注` と呼びたい事(3.2)を論点にした。
これもローカライズと共に後で考える(思考実験 29 の論点3(ローカライズ))。

### 論点4: コンポーネントの辞書

DB の列や内部階層の名前など、コンポーネントの内側でだけ使う語の置き場として、コンポーネントにも辞書を持たせるか。
思考実験 29 の論点5(範囲)と同じ所で決まる。持たせるなら、語の範囲はシステムの入れ子とコンポーネントの両方に従う。
辞書に無い語を公開する名前にだけ使わせない形(思考実験 29 の第9節)を採るなら、内側の名前は辞書に掛からないため、コンポーネントの辞書は要らない(3.3)。

### 論点5: 語の範囲と名前空間

語の範囲をシステムの入れ子に沿わせる事は、プログラムの宣言(U14)の論点4(名前空間の分け方)と同じ問いである。
語の昇格(3.3)は、データ宣言を届く範囲に属させる案(計画書 第5節 5.10)と同じ形をしており、二つは一緒に決めるのが素直である。

### 論点6: 役の綴り

役の語 `agent` と記述者の語 `agent` がぶつかった(3.1)。前提(コードは英語)の下では、言語の語彙を一般的な英語で綴るほど記述者の語と衝突する。
役を英語の一般語でない綴りにするか、言語の語彙を予約語として記述者の語に使わせないかを決める。後者は、記述者が業務の語を選べなくなる。

### 論点7: 未熟な定義

開発の初めの定義は粗い。粗い事を示す印(仮の定義)を持たせると、書いた後に研ぎ直す所が辞書から読める。
一方で、印は省略時の既定ではないが、いつまでも外されない印は意図の陳腐化(W0003-2)と同じ問題になる。定義の中身は検証しない(ADR 0003(検証不能な意図の記述形式))ため、印を持たずに差分の履歴に任せる道もある。

## 6. まとめ

- 開発の流れ(システム・人・外部システム → コンポーネント → 欄と DB の項目)は、Shidzuku の段の順と一致する。ユーザーの種類は `actor` に当たる。
- 用語辞書を先に書き上げる必要は無い。**宣言の場所で名前の定義を書き、宣言を持たない語は使った段の辞書に足す**形で、段を追って辞書が育つ。
  辞書に無い語はエラーになるが、コンパイラが置き場と雛形を示せば、書く手を止めずに埋められる。
- 辞書はシステムの入れ子に沿って分かれ、使う範囲が広がった語は外の辞書へ移る。語の追加・改名・移動は差分に現れ、定義を研ぎ直す機会になる。
- 費用も見えた。小さな系では名前1つにつき新しい語がほぼ1つ要り、語の大半は宣言からではなく辞書のブロックに入る。
- 規則を公開する名前に限るなら、DB の列や body の中の名前は辞書に掛からず、コンポーネントの辞書は要らない。Shidzuku の記述に現れる名前はほとんどが公開する名前なので、上の数は変わらない。
- 母国語の名前について見えた事(語を並べても業務の名前にならない、段ごとに呼び方が違う)は、ローカライズへ渡す。
- 決める事は5つある。データ宣言の定義の文(論点1)、コンポーネントの辞書(論点4)、語の範囲と名前空間(論点5)、役の綴り(論点6)、未熟な定義(論点7)である。
  母国語の名前を必須にするか(論点2)と段ごとの母国語の名前(論点3)は、ローカライズへ送った。

# 思考実験 06: 数値と単位の記述(金額・計測・国際出荷)

- 状態: Draft
- 日付: 2026-08-23
- 目的: U15(数値の型と単位)の入力収集。誤差の出ない十進固定小数点と、単位付き数値が実際の計算で書けるかを確かめる
- 進め方: 計画書の検証方法に従い、既存の小さなシステムを Shidzuku で記述してみる。書けない事があれば仕様に戻す。ADR 0009 が「必要が出たら検討する」として保留した単位付き数値(思考実験 05 の論点5)を対象に引き上げる

## 1. 対象システム

数値の性質が異なる3つの小さな系を選ぶ。1つの系だけでは「誤差の出なさ」と「単位」の両方を試せないため、性質で選び分けた。

| 系             | 数値の性質                                    | 試したい事                           |
| -------------- | --------------------------------------------- | ------------------------------------ |
| 請求計算       | 通貨。1円の狂いも許されない。除算が必ず現れる | 桁の宣言、端数処理、按分の余り       |
| 計測の正規化   | 物理量。機種ごとに単位が違う(mm/m、℉/℃)       | 桁単位の換算、比で書けない単位       |
| 国際出荷の荷姿 | 長さと質量が同居する。単位系が2つ(SI/ヤード)  | 量の取り違えの検出、単位系を跨ぐ換算 |

3系とも既存の思考実験と地続きである(請求計算は 01 注文管理の下流、計測の正規化は 02 センサー収集の Normalizer の内側、国際出荷は新規)。

## 2. 仮構文による記述

数値型・量・単位の構文は未定のため仮。データは ADR 0009(提案)の `data` 宣言に従う。

### 2.1 桁の宣言

数値は整数部と小数部の桁数を必ず伴う。`数値(7.2)` は整数部7桁・小数部2桁、すなわち `-9999999.99` から `9999999.99` までを 0.01 刻みで表す。

```plaintext
数値(7.2)      # 整数部7桁・小数部2桁
数値(4.0)      # 整数部4桁。小数を持たない事も桁で書く
数値(0.6)      # 小数部6桁のみ。|値| < 1
数値           # エラー: 桁の宣言がない(省略の禁止)
```

桁を書かない `数値` は存在しない。値の範囲と刻みは、型を読めば分かる。

### 2.2 請求計算 — 誤差の出ない金額

```plaintext
量   通貨 基準 なし              # 通貨間の比は時価であり、言語は持たない
単位 円   : 通貨
単位 ドル : 通貨

data 明細 { 品目: 品目ID, 単価: 数値(7.0) 円, 数量: 数値(4.0) 単位なし }
data 請求 { 小計: 数値(9.0) 円, 消費税: 数値(9.0) 円, 合計: 数値(10.0) 円 }
```

```plaintext
unit Billing {
  intent {
    why      "請求金額の計算規則(端数処理の方式、按分時の余りの行き先)をこのユニットに閉じ込める。上流は金額の作り方を知らない。"
    rejected option "各ユニットが必要な所で金額を計算する"
             reason "端数処理の方式が散らばり、合計が突き合わない原因が追えなくなるため。"
    change   "税率の変更・軽減税率の導入を想定。税率は値として外から入り、規則はこのユニットに残る。"
  }
  constraint {
    depends  なし
    expose   請求する(明細列, 税率: 数値(1.4) 単位なし) -> 請求 | 請求不可
    expose   按分する(金額: 数値(9.0) 円, 人数: 数値(3.0) 単位なし) -> 数値(9.0) 円列
    state    なし
    layers   { 計算 { pure } }
  }
  body {
    # 小計: 単価 × 数量 は 数値(7.0) × 数値(4.0) = 数値(11.0) 円(桁は和)。
    # 列の合算は要素数が静的に決まらないため桁も決まらない。名前を得る所で 収める。
    小計 = 収める(合算(明細列.単価 × 明細列.数量), 数値(9.0) 円)   # 数値(9.0) 円 | 桁溢れ

    # 消費税: 12345 円 × 0.10 は 1234.5 円。円は小数部0桁なので丸めが避けられない。
    # どちらへ丸めるかは事業者の判断であり、書かなければコンパイルが通らない。
    消費税 = 丸める(小計 × 税率, 数値(9.0) 円, 丸め 切り捨て)      # 1234.5 -> 1234

    合計 = 小計 + 消費税                                            # 数値(10.0) 円(桁上がりで +1)

    # 按分: 1000 円を3人で分けると 333 円が3つと余り 1 円。余りは消えない。
    { 商, 余り } = 分ける(金額, 人数)                               # 商 333 円、余り 1 円
    # 余りを誰に寄せるかはこのユニットの規則(先頭の1人に加える)。
  }
}
```

### 2.3 計測の正規化 — 桁単位の違いと、比で書けない単位

思考実験 02 の Normalizer の内側を数値として書く。機種Aは変位を mm、機種Bは m で送る。温度は機種Cが ℉、機種Dが ℃ で送る。

```plaintext
量   長さ 基準 メートル
単位 ミリメートル : 長さ = メートル × 1/1000       # 比は 10 のべき

量   温度 基準 なし                                 # ℃ と ℉ の変換はオフセットを伴い、比では書けない
単位 摂氏 : 温度
単位 華氏 : 温度

data 変位計測 { センサー: センサーID, 時刻: 時刻, 生値: 数値(7.0) ミリメートル | 欠損 }
data 温度計測 { センサー: センサーID, 時刻: 時刻, 生値: 数値(4.1) 華氏     | 欠損 }
data 正規化済み変位 { センサー: センサーID, 時刻: 時刻, 値: 数値(4.3) メートル }
data 正規化済み温度 { センサー: センサーID, 時刻: 時刻, 値: 数値(4.2) 摂氏  }
```

```plaintext
body {
  # 長さ: mm -> m は 1/1000。整数部が3減り、小数部が3増える。桁が足りるので無損失、丸めの宣言は要らない。
  値 = 換算(生値, メートル)                    # 数値(7.0) mm -> 数値(4.3) m

  # 温度: ℉ -> ℃ は (F - 32) × 5/9。比ではないため言語は換算しない(欠損の枝は別に扱う)。
  # 変換はこのユニットの知識であり、単位を外して計算し、結果に単位を与える。
  素の摂氏 = 割る(( 単位を外す(生値) - 32 ) × 5, 9, 数値(4.2), 丸め 四捨五入)
  値       = 単位を付ける(素の摂氏, 摂氏)      # 68.0 ℉ -> 20.00 ℃
}
```

`換算(生値, 摂氏)` と書くとコンパイル時に落ちる(温度は換算比を持たない)。変換が必要な事は型が示し、変換の中身はユニットが隠す。

### 2.4 国際出荷 — 量の取り違えと、単位系を跨ぐ換算

```plaintext
量   質量 基準 キログラム
単位 グラム  : 質量 = キログラム × 1/1000
単位 ポンド  : 質量 = キログラム × 45359237/100000000    # 0.45359237 kg(定義値。正確)
単位 センチメートル : 長さ = メートル × 1/100
単位 インチ         : 長さ = メートル × 127/5000         # 0.0254 m(1959年の国際定義。正確)

量   体積 = 長さ × 長さ × 長さ 基準 立方メートル
単位 立方センチメートル : 体積 = 立方メートル × 1/1000000

data 荷姿     { 縦: 数値(2.1) センチメートル, 横: 数値(2.1) センチメートル, 高さ: 数値(2.1) センチメートル, 重量: 数値(2.3) キログラム }
data 米国荷姿 { 縦: 数値(2.2) インチ,         横: 数値(2.2) インチ,         高さ: 数値(2.2) インチ,         重量: 数値(3.2) ポンド     }

# 換算先の桁も静的に検査される。99.9 cm は 39.33 インチであり 数値(2.2) に収まる。
# 99.999 kg は 220.46 ポンドであり、数値(2.2) では整数部が足りず 数値(3.2) がいる。
```

```plaintext
body {
  合計 = 縦 + 重量                              # エラー: 長さと質量は足せない(異なる量)

  幅の和 = 縦 + 横                              # 数値(3.1) センチメートル(桁上がりで +1)
  全長   = 縦 + 0.5 メートル                    # 細かい方(cm)へ揃える: 0.5 m は 数値(3.0) cm、和は 数値(4.1) cm

  # cm -> インチ。比は (1/100) ÷ (127/5000) = 50/127。基準(メートル)経由の比を約分し、1回だけ適用する。
  米国縦 = 換算(縦, インチ, 数値(2.2), 丸め 四捨五入)   # 12.3 cm -> 4.842519... -> 4.84 インチ

  # kg -> ポンド。比は 100000000/45359237(既約)。
  米国重量 = 換算(重量, ポンド, 数値(3.2), 丸め 四捨五入)  # 2.500 kg -> 5.511556... -> 5.51 ポンド

  # 容積重量(体積 5000 cm³ = 1 kg)は業界の規則であり、量が変わる。言語の換算では書けない。
  容積 = 縦 × 横 × 高さ                          # 数値(6.3) 立方センチメートル(30.0×20.0×15.0 = 9000.000)
  容積重量 = 単位を付ける(割る(単位を外す(容積), 5000, 数値(3.3), 丸め 切り上げ), キログラム)
}
```

比較は換算せずに行える。`縦 < 5 インチ` は、両辺を基準単位の共通の分母へ交差乗算して整数として比べるため、丸めが介在せず厳密である。

## 3. 検証結果

### 3.1 書けた事

- **桁の宣言で「誤差が出ない」が型になった**。加減算(小数部は大きい方、整数部は大きい方+1)と乗算(桁は和)は結果の桁が静的に決まり、値は必ず収まる。誤差が生じ得るのは除算・単位換算・桁を狭める受け渡しだけであり、その3箇所は丸めの宣言を要求すれば塞げる。
- **丸めの明示が実務と一致した**。消費税の端数処理(切り捨て/切り上げ/四捨五入)は日本では事業者の選択であり、既定を置く方が誤りである。書かなければ通らない規則は、実務の判断をコードの表面へ引き上げる。
- **按分の余りが型で守られた**。`分ける` は商と余りを同時に返し、`金額 = 商 × 人数 + 余り` が厳密に成り立つ。1000 円が 999 円に痩せる事故は書けない。
- **10 のべきの換算は桁の付け替えとして無損失に書けた**(mm ↔ m、cm ↔ m)。固定小数点の内部表現(小数桁倍した整数)と噛み合い、丸めの宣言も要らない。
- **異なる量の加算が落ちた**(`縦 + 重量`)。単位を型に載せる目的の中心であり、狙い通りに機能した。
- **比で書けない単位を「換算比のない量」として宣言できた**。通貨(時価)と温度(オフセット付き)が同じ形で扱え、変換はユニットの body に落ちる。これは思考実験 02 の Normalizer の why(機種ごとの癖=単位系の違いを吸収する)そのものであり、仕様と既存の設計が噛み合った。
- **換算の誤差の上限が宣言から読めた**。`換算(縦, インチ, 数値(2.2), 丸め 四捨五入)` の誤差は 0.005 インチ 以下と型から決まる。誤差は消せないが、隠れない。

### 3.2 書きにくかった事 — 仕様に戻す論点

1. **乗算の桁の上界が実務では広すぎる**。`数値(7.0) 円 × 数値(4.0) 単位なし` は上界 `数値(11.0)` だが、明細1件が1000億円になる事はない。上界のまま代入先を宣言すると桁が急速に膨らみ、逆に狭く宣言すると式のたびに `収める`(直和)の分岐が現れる。
  → **桁の検査は値が名前を得る所(data のフィールド・公開面・状態)でのみ行い、式の中間は自動で広げる**、という規則で決着した(本記述もそれに従っている)。値域の宣言(`範囲 0..99999`)は別案として残る。
2. **単位の付け外しが抜け道になる**。℉→℃ と容積重量の2箇所で `単位を外す` が必要になった。型の外へ出る操作であり、`単位を外す(距離) + 単位を外す(重さ)` を封じる手段はない。
  → 名前のある1操作に閉じ込め、body 内でのみ書けるものとする。外部世界から値が入る所と同じ性質であり、**U12(外部世界との境界)への入力**とする。
3. **組立の量をどこまで持つか**。体積は `長さ × 長さ × 長さ` の宣言で書けたが、`単価(円/個)` を厳密に書こうとすると `量 個数`・`量 単価` の宣言が連鎖する。
  → 単位を付ける対象は物理量と貨幣に限り、個数・回数・割合・税率は `単位なし` とする指針で3系とも書けた。無名の組立の量は作らない(宣言のない `長さ × 長さ` はエラー)。
4. **往復の換算は一致しない**。12.3 cm → 4.84 インチ → 12.2936 cm であり、`数値(3.1)` へ戻せば 12.3 cm に一致するが `数値(3.3)` では一致しない。型では表せない性質である。
  → 保持は1つの単位(基準単位を推奨)で行い、**換算は境界で1回だけ**という指針を仕様に書く。連鎖換算(cm → m → インチ)を禁じ、基準経由の比を約分して1回だけ適用する規則も、丸めの回数を1回に固定するためにいる。
5. **桁溢れの型が失敗の体系と重なる**。`収める` の結果 `数値(9.0) 円 | 桁溢れ` は、ADR 0009 の「無いは直和で明示する」と同じ形だが、桁溢れはデータとして正常な不在ではなく、設計の見積り違いである。
  → **U13(失敗の体系)への入力**とする。直和で受けるか、コンパイル時に閉じるかの判断が残る。
6. **列の合算だけ桁が静的に決まらない**。加減乗の桁は結果から逆算できるが、`合算(明細列.単価 × 明細列.数量)` は要素数の上限が型に無いため上界が定まらない。
  → 列の合算の結果は必ず `収める` で受ける(直和で桁溢れを扱う)、という規則で決着した。列に最大長を宣言させる案は、列の型を重くするため採らなかった。
7. **通貨の換算をどこに置くか**。円 → ドルは比が時価であり、レート取得は IO である。言語が持たないと決めた事で、換算ユニット(レートの知識を隠す)が必要になる事は導けるが、その形は本実験の外である。

### 3.3 未解決課題への入力

- **U15(数値の型と単位)**: 桁の宣言・丸めの明示・量と単位の分離で3系とも書けた。→ ADR 0010 を起案。
- **U9(データ型の記述)**: ADR 0009 の基本型「数値」を `数値(整数部.小数部) <単位>` に置き換える必要がある。ADR 0009 が保留した論点(思考実験 05 の論点5)の決着であり、採用時は両 ADR を揃えて反映する。
- **U12(外部世界との境界)**: `単位を外す` / `単位を付ける` は型の外へ出る操作であり、外部入力と同じ扱いがいる(本実験 3.2-2)。
- **U13(失敗の体系)**: 桁溢れは「正常な不在」でも「系の失敗」でもない第三の種であり、語彙の設計に含める(本実験 3.2-5)。
- **U5(トランスパイル先の言語)**: 内部表現が多倍長整数を要求するため、比較軸が1つ増える(TypeScript の BigInt、Go の math/big、Erlang の組み込み多倍長整数)。浮動小数点しか持たない出力先は選べない。
- **U14(プログラムの宣言)**: `量`・`単位` の宣言も data と同じくトップレベルであり、置き場所の器を要求する(思考実験 05 の 3.2-1 と同じ要請の3件目)。

## 4. 次の行動

- ADR 0010(数値の型と単位)を起案する → 済
- 採用時は ADR 0009 の基本型「数値」の記述を揃え、第2章の検証一覧に E12〜E16・W3 を加える
- U12(外部世界との境界)・U13(失敗の体系)の検討時に本実験の 3.2-2・3.2-5 を入力とする

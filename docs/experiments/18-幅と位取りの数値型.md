# 思考実験 18: 幅と位取りの数値型 — 書き下ろしと反証

- 状態: Draft
- 日付: 2026-09-16
- 目的: 書き手が定めた数値型(`intN(s)`・`uintN(s)`・`floatN`。単位は必須、単位なしは `none`)で、
  これまでの思考実験に出た数値を**実際に書き下ろし**、書けない事・困る事を探す
- 進め方: 思考実験 06(金額計算・計測の正規化・国際出荷)と思考実験 12・13 の論点を新しい型で写す。
  演算のたびに幅と位取りがどう動くかを追い、溢れる所・変換が要る所を数える。結論は ADR 0021 に渡す

## 1. 型の形

```plaintext
int8(s)  int16(s)  int32(s)  int64(s)  int128(s)  int256(s)     <単位 | none>
uint8(s) uint16(s) uint32(s) uint64(s) uint128(s) uint256(s)    <単位 | none>
float32  float64                                                <単位 | none>
```

- `intN(s)` は「幅 N ビットの2進整数 `m` を格納し、値は `m × 10^-s`」である。**幅が上限を、位取りが刻みを決める。**
- `s` は型情報のみで、実行時の値は `m` だけである(ADR 0010 の内部表現をそのまま引き継ぐ)。
- 幅と位取りの組で実効範囲が決まる。

| 型          | `m` の範囲                      | 刻み | 値の範囲                         |
| ----------- | ------------------------------- | ---- | -------------------------------- |
| `int32(0)`  | -2,147,483,648 〜 2,147,483,647 | 1    | ±約 21 億                        |
| `int32(2)`  | 同上                            | 0.01 | ±約 2,147 万                     |
| `int64(0)`  | ±約 9.22e18                     | 1    | ±約 922 京                       |
| `int64(2)`  | 同上                            | 0.01 | ±約 9,223 京の 1/100 = 約 9.2 京 |
| `int64(9)`  | 同上                            | 1e-9 | ±約 92.2 億                      |
| `uint8(0)`  | 0 〜 255                        | 1    | 0 〜 255                         |
| `int128(2)` | ±約 1.70e38                     | 0.01 | ±約 1.70e36                      |
| `int256(0)` | ±約 5.79e76                     | 1    | ±約 5.79e76                      |

## 2. 書き下ろし1 — 金額計算(思考実験 06 の1系)

```plaintext
data 明細 {
  単価: int64(2) 円,
  数量: int64(0) none,
}

data 請求 {
  小計:   int64(2) 円,
  税率:   int64(4) none,      # 0.1000 = 10%
  税額:   int64(2) 円,
  合計:   int64(2) 円,
}
```

### 2.1 明細の金額 — 乗算

```plaintext
金額 = 単価 × 数量        # int64(2) 円 × int64(0) none
                          # 位取り = 2 + 0 = 2、単位 = 円 × none = 円  →  int64(2) 円
```

**書ける。** U23(スカラー倍)は、幅と位取りが型に出た事で素直に通る。`m` の積は `123456 × 100 = 12,345,600`(1234.56 円 × 100 個 = 123,456.00 円)。

ただし**溢れる条件がある**。`m1 × m2` が `int64` を超えるのは、両者の `m` が約 30 億(`√9.22e18`)を超えたときである。
`int64(2) 円` なら 3,000 万円どうしの乗算にあたり、実務では稀だが**起こり得る**。

### 2.2 税額 — 位取りが増える

```plaintext
税込の素 = 小計 × 税率     # int64(2) × int64(4) → 位取り 6。int64(6) 円
税額     = 丸める(税込の素, int64(2), 丸め 切り捨て)
```

- **乗算のたびに位取りが増える。** 元の型に戻すには `丸める` を書く——ADR 0010 と同じ形であり、丸めの宣言はここに残る。
- `int64(6) 円` の実効範囲は ±約 92 億であり、小計が 92 億円を超えると**中間で溢れる**。

### 2.3 合算

```plaintext
合計 = 合算(明細.金額)      # int64(2) 円。要素と同じ型
```

明細 100 行 × 最大 1,000 万円なら `m` は約 1e11 で余裕がある。
**しかし上限は幅が決めるため、`int32(2) 円`(±2,147 万円)を選んでいたら 3 行で溢れる。** 幅の見積りが設計判断として戻ってきた。

### 2.4 按分 — 商と余り

```plaintext
分ける(合計, 人数)          # int64(2) 円 ÷ int64(0) none … 型が違う
```

**ここで詰まった。** `分ける` と `割る` は「同じ型どうし」では書けない——被除数は金額、除数は人数(`none`)であり、位取りも単位も違う。
ADR 0010 は除数の型を問わなかったが、幅が型に入った今は**除数の型を規則で決める必要がある**(論点1)。

### 2.5 除算

```plaintext
単価 = 割る(合計, 数量, int64(2), 丸め 切り捨て)     # 結果の型と丸めを宣言する
```

結果の**型**(幅と位取り)を宣言する形なら、ADR 0010 の「結果の桁と丸めを宣言する」がそのまま通る。

## 3. 書き下ろし2 — 計測の正規化(思考実験 06 の2系)

```plaintext
data 計測 {
  温度: float64 摂氏,
  圧力: float64 パスカル,
  時刻: int64(0) ナノ秒,       # 量 時間
}
```

- 測った値は `float64`。位取りの欄が無いのは「刻みが値の大きさで変わる」からであり、書かせても情報が増えない。
- 時間の量は `int64(0) ナノ秒` で ±292 年。`時点` の範囲(1677〜2262 年)と整合する。

```plaintext
平均 = 割る(合算(計測.温度), 個数, float64, 丸め なし)   # ← float に「丸め」は書けない
```

**ここでも詰まった。** `float64` の演算は常に丸まる(最近接偶数)ため、`割る` の丸めの欄が意味を持たない。
`int` と `float` で**演算の語彙が分かれる**(論点2)。

## 4. 書き下ろし3 — 外部との接合

```plaintext
component 在庫同期 {
  layers { 境界: io, 領域: pure }

  # 外部の 32 ビット符号付き整数(ビッグエンディアン)
  受信値 = 復号(受信, int32(0), ビッグエンディアン)     # int32(0) none
  数量   = 変換(受信値, int64(0))                        # 領域で使う幅へ
  在庫   = 単位を付ける(数量, 個)

  # 外へ出す
  応答 = 符号化(変換(単位を外す(在庫), int32(0)), ビッグエンディアン)   # 範囲外は失敗
}
```

- **幅が型に入った事で、境界の宣言はバイト順だけになった**。詰め替え先の型がそのまま幅を言う。
- 一方で、**外部の幅と内側の幅を揃えるための `変換` が増える**。`int32(0)` のまま領域で使えば変換は要らないが、合算で溢れやすくなる。

## 5. 見つかった論点

| #  | 論点                                        | 中身                                                                                     |
| -- | ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1  | **除数と乗数の型**                          | `金額 ÷ 人数` は型が違う。同じ型どうしに限ると按分が書けない(2.4)                        |
| 2  | **`int` と `float` で演算の語彙が分かれる** | `float` に丸めの宣言は書けない(3)。`割る` の形が2つになる                                |
| 3  | **乗算で位取りが増える**                    | `int64(2) × int64(4)` は位取り 6。元に戻すには `丸める` が要る(2.2)                      |
| 4  | **乗算は幅を食う**                          | `m` の積が幅を超えると失敗する。`int64` なら両辺 30 億が境目(2.1)                        |
| 5  | **加算は位取りを揃える所で溢れ得る**        | `int64(0) 円 + int64(2) 円` は前者の `m` を 100 倍する。9.2 京を超えれば失敗             |
| 6  | **幅の見積りが戻ってきた**                  | `int32(2) 円` を選ぶと 2,147 万円で頭打ち。上限の設計判断が全ての値に要る(2.3)           |
| 7  | **`uint` の使い所は狭い**                   | 差を取ると負になり得るため、業務の値は `int` が基本。`uint` はバイト・長さ・外部形式向け |
| 8  | **添字と長さの型を決める必要**              | `uint64(0) none` か `int64(0) none` か。E0019-4 を書き直す事になる                       |
| 9  | **`int256` の使い所**                       | 暗号・ブロックチェーン以外では現れなかった。持つ事の害は無いが、実務の裏づけも無い       |
| 10 | **型の総数**                                | 幅6 × 符号2 + `float` 2 = 14 通り。語彙としてどう数えるか(型3つ + 欄と読むか)            |

### 5.1 論点1・2 への案

| 論点           | 案                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------- |
| 除数・乗数     | **単位と位取りは規則で決まり、幅だけ揃える**。`int64(2) 円 ÷ int64(0) none` は書ける。幅が違えば `変換` を書く |
| `float` の割る | `float` の除算は演算子 `÷` とし、`割る(…)` は `int`/`uint` 専用にする(丸めが宣言できる型に限る)                |

この案なら、2.4 の按分は `分ける(合計, 人数)`(どちらも `int64`)で書ける。

### 5.2 論点4 への案 — 乗算の幅

| 案                                                       | 利点                       | 欠点                                          |
| -------------------------------------------------------- | -------------------------- | --------------------------------------------- |
| (a) 同じ幅で計算し、溢れたら失敗                         | 規則が単純。記憶域が読める | 実務で溢れ得る(2.1)。失敗の扱いが呼び手に出る |
| (b) 幅が倍になる(`int64 × int64 → int128`)               | 溢れにくい                 | `int256` の先が無い。型が勝手に変わる         |
| (c) 結果の型を書かせる(`掛ける(a, b, int64(2), 丸め …)`) | 溢れも丸めも書き手が決める | 乗算が演算子で書けなくなる                    |

**(a) を推す。** 溢れは失敗として観測でき(U13)、記憶域と実行時間の上界は保たれる。
中間で幅が要る計算は、書き手が `変換(a, int128(2))` を明示すればよい——**幅を選ぶ責任を型に出す**という、この体系の趣旨に合う。

## 6. 検証結果

### 6.1 書けた事

- 明細行の金額(U23)が**素直に書けた**。幅と位取りが型にあるため、スカラー倍の特別規則が要らない。
- 金額・税率・按分・計測・時間の量・外部との詰め替えが、すべて型で表せた。
- **「厳密かつ上界あり」の型が戻った**(思考実験 16 の最大の欠点が解消)。`int64(2) 円` は記憶域も実行時間の上界も型が言う。
- 境界の詰め替えは、幅が型にあるため**バイト順の宣言だけ**で済むようになった。

### 6.2 書けなかった事・戻ってきた事

- **幅の見積り**が全ての値に戻ってきた(論点6)。ADR 0010 の「上限の見積り」と同じ負担であり、`十進数` の可変長案が消した物がそのまま戻る。
- **桁溢れ**が実行時の失敗として戻ってきた(論点4・5)。加算・乗算・位取りの揃えのいずれでも起き得る。
- **除数・乗数の型**と **`float` の演算語彙**は、規則を決めないと書けない(論点1・2)。
- 中間結果のために `変換` を挟む場面が出る(論点4・4節)。

### 6.3 判定

**この体系は書ける。** 論点1・2 を規則で塞げば、これまでの思考実験に出た数値はすべて表せる。
交換したのは次の一組である。

| 可変長案(2026-09-15)が持っていたもの | 幅と位取りの案が持つもの                 |
| ------------------------------------ | ---------------------------------------- |
| 幅の見積りが要らない                 | **記憶域と実行時間の上界が型から読める** |
| 桁溢れが存在しない                   | **ヒープを使わない**(組込みで動く)       |
| 中間結果が自動で広がる               | **外部形式と幅がそのまま対応する**       |
| ——                                   | 上限が業務の言葉ではなく幅で表れる(欠点) |

**思考実験 16 が「埋まらない」と書いた空白(厳密かつ上界あり)は、この体系で埋まる。** 代わりに ADR 0010 の負担(幅の見積りと桁溢れ)が戻る。

## 7. `dec(i.f)` の追加(2026-09-16)

書き手が**十進数型 `dec(<整数部>.<小数部>)`** を足した。性質は3つである。

- **整数部と小数部を宣言する**(例: `dec(9.4)`)。演算は小数部倍した整数で行う(`int`/`uint` と同じ)。
- **実際の格納は値による可変長**である。
- **内部演算のみ**に使える。データフロー(`flow`)や外部インターフェイスには指定できない。

### 7.1 宣言した桁は上界、可変長は表現 — この2つは矛盾しない

一見すると「桁を宣言する」と「可変長」は相反するが、役割が違う。

| 何を決めるか         | 誰が決めるか   | 効く場面                             |
| -------------------- | -------------- | ------------------------------------ |
| 値の上限と刻み(意味) | **宣言した桁** | 検査・記憶域の見積り・実行時間の上界 |
| 実際に使うバイト数   | **値の大きさ** | 実行時の記憶域                       |

**可変長は表現の最適化であって、上界を捨てる事ではない。** `dec(9.4)` は 13 桁 = 最大 6 バイトと静的に見積もれ、
実際の値が小さければ1ワードに収まる。思考実験 16 が挙げた空白(上界が型から読めない)は**起きない**——ここが、前版の可変長 `十進数` との決定的な違いである。

### 7.2 第5節の論点が解けるか

| #  | 論点(5節)                      | `dec` を使った場合                                                          |
| -- | ------------------------------ | --------------------------------------------------------------------------- |
| 4  | 乗算が幅を食う                 | **解ける**。中間を `dec` で受ければ、桁は規則どおり伸びて溢れない           |
| 5  | 加算が位取りを揃える所で溢れる | **解ける**。同上                                                            |
| 6  | 幅の見積りが戻ってきた         | **半分解ける**。公開面の幅は要るが、**中間計算の幅の見積りは要らなくなる**  |
| 3  | 乗算で位取りが増える           | 変わらない。`丸める` の宣言は残る(誤差の出る場所を型に出すための宣言である) |

### 7.3 書き直し — 税額と合算

```plaintext
data 請求 { 小計: int64(2) 円, 税率: int64(4) none, 税額: int64(2) 円 }

# int だけで書くと、中間の int64(6) が 92 億円で溢れる(2.2)
税額 = 丸める(小計 × 税率, int64(2), 丸め 切り捨て)

# dec を挟むと中間が溢れない
素   = 変換(小計, dec(18.2)) × 変換(税率, dec(1.4))   # dec(19.6) 円。桁は規則で伸びる
税額 = 収める(素, int64(2), 丸め 切り捨て)             # 名前を得る所で int64(2) へ戻す
```

```plaintext
# 合算 — ADR 0010 が「桁の上界が定まらない」と認めた唯一の穴
合計の素 = 合算(変換(明細.金額, dec(18.2)))    # 式の中では桁が自動で広がる
合計     = 収める(合計の素, int64(2))           # 受ける所で検査。溢れたら失敗
```

**ADR 0010 の「桁の検査は値が名前を得る所でのみ行い、式の中間の桁は自動で広がる」が、`dec` の中で復活する。**
`int`/`uint` は幅が有限で中間が広がらないため演算ごとの検査が要るが、`dec` は中間で広がるため名前を得る所だけでよい。

### 7.4 内部演算のみに限る事の帰結

| 場所                                       | `dec`    | 理由                                                         |
| ------------------------------------------ | -------- | ------------------------------------------------------------ |
| body の式・局所の値                        | 書ける   | 中間計算がこの型の用途そのもの                               |
| `data` のフィールド・公開面・`flow` の内容 | 書けない | コンポーネントを跨ぐ値は、相手が記憶域を見積もれる必要がある |
| 外部インターフェイス(`復号`・`符号化`)     | 書けない | 外部形式は幅で定義されている                                 |
| `state`                                    | **論点** | 状態の記憶域は配置単位の資源に直結する(下記)                 |

`state` は書き手の指定に明示が無い。**書けない側に倒すのが筋が通る**——状態の大きさは配置単位(= 障害境界)の資源であり、
公開面と同じく「見積もれる必要がある」側だからである。累計は `int64(2) 円` のような固定幅で持ち、伸びる中間だけ `dec` で受ける。

### 7.5 新しく見つかった事

1. **`変換` と `収める` が対で現れる。** `dec` を使う計算は「持ち上げて・計算して・収める」の3段になる。
   これは ADR 0010 の `収める` が戻ってきた形だが、**戻る先が公開面の境目だけ**である点が違う。
2. **`dec` の桁の宣言は、値域の宣言に近い。** `dec(9.4)` は「9 桁を超えたら失敗」という意味であり、
   ADR 0021 が「将来の変更想定」に送った値域の宣言の役割を、内部計算については先に果たす。
3. **誤差の出る場所は変わらない。** 除算・粗い単位への換算・位取りを粗くする受け渡しの3つのままである。
4. **型の役割が層で分かれた。** 公開面と外部は `int`/`uint`/`float`(幅で上界を言う)、内部の中間は `dec`(桁で上界を言い、表現は縮む)。
   ADR 0013 の役割(境界・領域)と噛み合う。

### 7.6 判定

**`dec` の追加で、第6節 6.2 に挙げた「戻ってきた事」のうち2つが内部計算から消える。**

| 6.2 で挙げた物                 | `dec` 追加後                                        |
| ------------------------------ | --------------------------------------------------- |
| 幅の見積りが全ての値に戻る     | **公開面だけになる**。中間計算は `dec` が引き受ける |
| 桁溢れが実行時の失敗として戻る | **受ける所だけになる**。中間では起きない            |
| 除数・乗数の型(論点1)          | 変わらず規則で決める                                |
| 中間結果のための `変換`        | **増える**(持ち上げと収めの2回)                     |

交換は「中間の溢れ」と「持ち上げ・収めの2回の記述」であり、**溢れを実行時の失敗から記述の重さへ移す**取引である。
ADR 0010 の総括「実行時の驚きを、記述の重さとして前払いする」がそのまま当たる。

## 8. 未解決課題への入力

- **U23(数値型の設計全体)**: 論点1(除数・乗数の型)・論点2(`float` の演算語彙)・論点4(乗算の幅)を ADR 0021 で決める。
- **U13(失敗の体系)**: 失敗に「加算・乗算・位取りの揃え・変換での範囲外」が入る。**演算ごとの検査**になる(ADR 0019 決定2 と同じ)。
- **U12(外部世界との境界)**: 詰め替えの宣言はバイト順だけになった。名前付きの外部形式は引き続き U12 で扱う。
- **U24(序数と基数)**: `版 int32(0) none × 3` は依然として書ける。型の体系では解けない。
- **U15**: `int256` の使い所(論点9)と、型の数え方(論点10)を ADR で整理する。

## 9. 次の行動

# 思考実験 15: 名前空間の再検討 — 他言語のアプローチの比較

- 状態: Draft
- 日付: 2026-09-03
- 目的: U14 論点4・5(名前空間の分け方・修飾名)を**白紙から**検討し直す。「ユニークな名前空間にすれば衝突は無くなる」という Java 風の案を出発点に、他言語の名前空間戦略を比較して、Shidzuku に合う形を探る
- 経緯: 前回の報告で Java の逆ドメイン名案に4つの問題(慣習が支える一意性、組織名を記述に持ち込む、階層の二重化、修飾名の長さ)を挙げた。それを踏まえて再検討する
- 進め方: 「誰が一意性を保証するか」「階層の形は何か」の2軸で言語を分類し、Shidzuku の事情(システムの入れ子・ADR 0018・1プログラム内という現在の範囲)に照らす

## 1. 分類の軸

- **軸A: 一意性を誰が保証するか。** 慣習/中央集権的レジストリ/URLのような外部の一意な識別子/プログラム内に限定/内容そのもの(ハッシュ)。
- **軸B: 階層の形は何か。** フラットな名前に慣習的な接頭辞を付けるだけか、木構造そのものが名前空間を成すか、木構造とは独立した名前空間オブジェクトを持つか。

| 言語 / 体系      | 軸A(一意性の保証者)                                | 軸B(階層の形)                                             |
| ---------------- | -------------------------------------------------- | --------------------------------------------------------- |
| Java             | 慣習(逆ドメイン名)                                 | フラット + 接頭辞の慣習                                   |
| Go               | URL(VCS のリポジトリパス)                          | フラット + パスの慣習                                     |
| Rust             | 中央レジストリ(crates.io)+ プログラム内の木        | **木構造そのものが可視性の単位**                          |
| C#               | 中央レジストリ(NuGet の強い名前)+ 自由な namespace | namespace は木構造だが、アセンブリ(配布単位)とは独立      |
| OCaml            | 緩い(opam のパッケージ名)                          | **モジュールそのものが名前空間**                          |
| Common Lisp      | **プログラム(イメージ)内限定**                     | 独立した名前空間オブジェクト(package)                     |
| ECMAScript / npm | 中央レジストリ(npm)+ スコープ(`@org/name`)         | ファイル = モジュール。名前空間オブジェクトは実行時に生成 |
| Unison           | **内容そのもの(コンテンツハッシュ)**               | 名前は単なるラベル。階層は任意                            |

## 2. フラット + 慣習的接頭辞 — Java・Go

### 2.1 Java の逆ドメイン名

> Companies use their reversed Internet domain name to begin their package names—for example, com.example.mypackage. Reverse-DNS names are a simple way of eliminating namespace collisions, since any registered domain name is globally unique to its owner.

一意性を保証しているのは**言語ではなくインターネットのドメイン名登録機関**である。言語自身は同じパッケージ名を持つ2つの成果物を拒否する仕組みを持たない。

> The split package problem occurs when multiple JAR files or modules contain classes in the same package... JPMS will simply refuse to start a modulepath where two modules have the same name, even if they contain different packages.

JPMS(Java 9 のモジュールシステム)は**モジュール名**の重複だけを検査する。パッケージが複数の JAR にまたがる「分割パッケージ」はモジュールとして扱えず、これは今も実務上のトラブルの種である。
**Java の一意性は、言語の保証ではなく社会的な慣習と、後から足された検査(JPMS)の組み合わせで成り立っている。**

### 2.2 Go のモジュールパス

Go はパッケージの import path をリポジトリの URL(`github.com/org/repo` のような形)にする事で一意性を得る。

> The module path should be a globally unique identifier for the module, typically taking the form of an internet domain name in reverse order, followed by the module name.

Java と発想は同じ(外部の一意な識別子に相乗りする)だが、**ドメイン名ではなく実在の取得先 URL を使う**点が違う。Go プロキシがキャッシュと検証を行い、社会的慣習だけに頼らない層を足している。

**フラット+接頭辞の系列に共通する弱点**: 一意性の根拠が**言語の外**(ドメイン登録・VCS)にあり、Shidzuku が言語の中で閉じた保証(コンパイル時の検査)を志向してきた事(ADR 0008 の省略の禁止、E0014-3 の混同検査)とは方向が違う。

## 3. 木構造そのものが名前空間 — Rust・OCaml

### 3.1 Rust の module tree

Rust の可視性は、**モジュールの木構造に沿った相対指定**である。

> `pub(crate)` makes an item visible within the current crate only, while `pub(super)` makes an item visible to the parent module only... Starting with the 2018 edition, paths for `pub(in path)` must start with `crate`, `self`, or `super`.

`pub`(どこからでも見える)・`pub(crate)`(同じコンパイル単位)・`pub(super)`(親モジュールまで)・`pub(in path)`(指定した経路まで)——**フラットな名前空間ではなく、木構造の位置そのものが可視性を決める。**

これは Shidzuku の**システムの入れ子(ADR 0018)と極めて相性が良い**。`contains` の木構造がすでにあり、`pub(super)` に当たる「親のシステムまで見える」、`pub(in path)` に当たる「特定の祖先まで見える」は、
Shidzuku の入れ子構造にそのまま対応付けられる。**一意性は crate(コンパイル単位)ごとに中央レジストリ(crates.io)が保証するが、crate 内部の名前の一意性はモジュール木の位置で決まる**——ちょうど「ルートシステムはちょうど1つ」(ADR 0018 の E0018-2)という Shidzuku の既存の保証と対応する。

*Rust by Example*(公式)の実際のコード例で、5段階の可視性と、木構造ならではの1つの性質を確認した。

```rust
mod my_mod {
    pub mod nested {
        // 経路(祖先モジュール)を指定する形
        pub(in crate::my_mod) fn public_function_in_my_mod() { /* ... */ }
        // 親モジュールの中だけ
        pub(super) fn public_function_in_super_mod() { /* ... */ }
        // 宣言したモジュール自身の中だけ(非公開と同じ)
        pub(self) fn public_function_in_nested() { /* ... */ }
    }

    // 親モジュール自体が非公開
    mod private_nested {
        // pub(crate) と宣言しても……
        pub(crate) fn restricted_function() { /* ... */ }
    }
}

fn main() {
    // エラー: private_nested が非公開モジュールのため、
    // 中の pub(crate) 項目も外からは見えない
    // my_mod::private_nested::restricted_function();
}
```

| 修飾子             | 見える範囲                                           |
| ------------------ | ---------------------------------------------------- |
| `pub`              | モジュール木のどこからでも                           |
| `pub(crate)`       | 同じクレート(コンパイル単位)内ならどこからでも       |
| `pub(super)`       | 直接の親モジュールまで                               |
| `pub(in <経路>)`   | 指定した祖先モジュールまで(経路は親または祖先に限る) |
| `pub(self)` / 無印 | 宣言したモジュール自身の中だけ(この2つは同義)        |

**祖先の可視性がボトルネックになる。** `private_nested`(非公開モジュール)の中身を `pub(crate)` と宣言しても、外からは見えない
——可視性は木を下りる方向にしか広がらず、途中の非公開なノードが必ず遮る。これは「木構造の位置が可視性を決める」を一歩進めた性質であり、
Shidzuku で `share` を採るなら、**あるシステムの `contains` の途中に可視性の宣言が無いシステムがあると、その下のデータは(宣言の有無に関わらず)外から見えなくなる**、という同じ規則を持つ事になる。

### 3.2 OCaml — モジュールそのものが名前空間

OCaml には Java のような「パッケージ宣言」が無い。**モジュールという言語機構そのものが名前空間である。**

> In OCaml, modules themselves serve the namespace function... Functors stand for modules that take other modules as parameters.

ファイルはそのままモジュールになり、モジュールは他のモジュールを含められる(入れ子)。パッケージ名の一意性は opam(パッケージマネージャ)が緩く管理するが、
**プログラムの内側の名前空間は言語の構文だけで完結している**——外部のレジストリに頼らない部分と頼る部分が、Rust よりもさらにはっきり分かれている。

## 4. プログラム内限定 — Common Lisp

Common Lisp のパッケージは、**そのプログラム(Lisp イメージ)の中で一意であれば足りる**。

> Packages are a facility in Common Lisp to divide the namespace, allowing one to isolate all of their function, macro, and variable definitions from the rest of the system... A symbol has the printed form PACKAGE-NAME::SYMBOL-NAME.

グローバルな一意性(世界中のどのプログラムとも衝突しない)を要求しない。`defpackage` で `:use`(継承)と `:export`(公開)を明示し、`::`(二重コロン)で非公開のシンボルも強制的に参照できる。

**これは Shidzuku の現在の規則(名前空間の範囲は1プログラム内)と完全に一致する立場である。** Java・Go のようなグローバル一意性を最初から求めていない。
`:export` は、まさに U14 論点1(型の可視性をどう宣言するか)への直接の先行例である——**パッケージが「これを外に見せる」と宣言し、使う側は `:use` で取り込む**。

## 5. 内容で一意にする — Unison

Unison は、定義を**構文木のハッシュ**で識別する。

> Each Unison definition is identified by a hash of its syntax tree... Because definitions are identified by content hashes rather than human-assigned names, this approach eliminates naming conflicts entirely.

**名前は付随するラベルにすぎず、実体はハッシュで一意に決まる。** 同じ名前で違う実体が共存でき、名前の衝突という概念そのものが無くなる。
512 ビットの SHA3 を使い、衝突の確率は実務上無視できる。

これは最も radical な解だが、**Shidzuku の理念とは相性が悪い部分がある**。第0章 0.5 の「名前で語る」・intent(なぜそう書いたか)の記録という思想は、
**書き手が選んだ名前そのものに意味を持たせる**立場であり、ハッシュを主とし名前を従とする Unison とは方向が逆になる。本実験ではこの案を退けるが、記録として残す。

## 6. Shidzuku の事情との照合

Shidzuku には、他言語には無い前提がすでに2つある。

1. **`contains` の木構造がすでにある**(ADR 0018)。システムはシステムを入れ子にでき、ルートシステムはちょうど1つである(E0018-2)。
2. **1プログラム = 1回のコンパイル**である(現在の名前空間の範囲)。Java・Go のように「複数の組織が別々に開発した成果物を後から1つに繋ぐ」事を、いまのところ言語の対象にしていない。

この2つの前提は、**Rust の module tree(木構造が可視性を決める)** と **Common Lisp のプログラム内限定(グローバル一意性を求めない)** の組み合わせに最も近い。

| Shidzuku の前提                | 対応する先行例                                    |
| ------------------------------ | ------------------------------------------------- |
| `contains` の木構造            | Rust の module tree(`pub(super)`・`pub(in path)`) |
| ルートはちょうど1つ(E0018-2)   | Rust の crate(コンパイル単位の根)                 |
| 1プログラム内の一意性で足りる  | Common Lisp のパッケージ(イメージ内限定)          |
| 「これを外に見せる」宣言が要る | Common Lisp の `:export`、Rust の `pub`           |

**逆ドメイン名(Java)は、この2つの前提のどちらにも対応しない。** グローバルな一意性は Shidzuku がまだ必要としておらず(1プログラム内という前提の外)、
フラットな名前空間は `contains` の木構造という既存の資産を活かさない。前回報告した「逆ドメイン名は要らないはずである」という指摘は、この比較によって裏付けられる。

## 7. 比較の総括

| 観点                              | 逆ドメイン名(Java・Go)   | 木構造 = 可視性(Rust・OCaml)     | プログラム内限定(Common Lisp) | 内容ハッシュ(Unison)     |
| --------------------------------- | ------------------------ | -------------------------------- | ----------------------------- | ------------------------ |
| 一意性の保証者                    | 外部(DNS・VCS)           | 外部(レジストリ)+ 内部(木構造)   | **プログラムそのもの**        | 数学的(ハッシュ関数)     |
| Shidzuku の `contains` との親和性 | 低い(独立した階層になる) | **高い(木構造をそのまま使える)** | 中間(階層を持たない)          | 無関係                   |
| 組織名を記述に持ち込むか          | 持ち込む                 | 持ち込まない                     | 持ち込まない                  | 持ち込まない             |
| 修飾名の記法                      | ドット区切りの長い接頭辞 | `::` または `.`(木の経路)        | `PACKAGE::SYMBOL`             | 不要(名前は任意のラベル) |
| 名前で語る思想との整合            | 中立                     | 中立                             | 中立                          | **相性が悪い**           |

## 8. 論点 — 次の ADR に渡す問い

1. **名前空間をシステムの入れ子の経路そのものにするか。** Rust の module tree がそのまま対応する。採るなら、修飾名は `ルートシステム.内側システム.データ名` のような経路になる。
2. **可視性の段階をいくつ持つか。** Rust は4段階(`pub`・`pub(crate)`・`pub(super)`・`pub(in path)`)、Common Lisp は2段階(`:export` の有無)である。Shidzuku にどちらが合うかは U14 論点1(可視性のキーワード)と合わせて決める。
3. **グローバルな一意性をいつか必要とするか。** 複数の組織が作った Shidzuku プログラムを後から組み合わせる想定があるなら、Common Lisp 的な「プログラム内限定」では足りなくなる。現時点でその想定が無いなら、後回しにしてよい。
4. **修飾名の省略記法(`import` に相当するもの)を持つか。** 持たないなら常に完全な経路を書く事になり、入れ子が深い程その重さが増す。
5. **E0014-3(混同可能な識別子)の検査範囲を、名前空間の単位に合わせるか。** 別の名前空間にある似た名前をどう扱うかが未定である。

## 9. 次の行動

- 論点1〜5 について、ユーザーとの相談を経て方向を定める
- 方向が決まり次第、ADR 0018 を改訂する形で名前空間の規則を確定する(U14 の一部として)
- U14 論点1(可視性のキーワード)は、論点2 の可視性の段階の数と合わせて最終決定する

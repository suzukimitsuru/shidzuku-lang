## 2. 実行モデルの三案

| 案                     | 中の動き                                                                   | 先行例                                                 |
| ---------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------ |
| 待たせる逐次           | 仕事を一件ずつ処理する。`ask` の応答を待つ間も、次の仕事を取り出さない     | Erlang の `gen_server:call` の呼び手側、Orleans の既定 |
| 待つ所で次を受ける逐次 | 仕事を一件ずつ処理するが、待つ所で止まっている間は次の仕事を取り出してよい | JavaScript のイベントループ、Orleans の再入可能な型    |
| 内側の並行             | 複数の仕事を同時に走らせる。状態は共有され、同期は言語か記述者が担う       | Hike の `threadable`・`concurrent`、Java のスレッド    |

- 三案とも、**コンポーネントの間**は変わらない。共有メモリは無く、通信は `ask` と `flow` だけである(ADR 0004)。違いはコンポーネントの**中**だけである。
- Orleans(Microsoft の分散アクターの枠組み)は既定で待たせる逐次とし、型や操作ごとに再入を許す印(`Reentrant`・`AlwaysInterleave`)を持つ。
  一つの言語の中で二案を選べる先行例である。

## 3. 三案で書き下ろす

### 3.1 KVCore — 格納の応答を、永続化の受付まで待たせる

思考実験 04 の `flow 格納` は「格納の完了応答は永続化の完了を待って返す」とした。`flow` は応答を返さないため、KVCore が待てるのは
**動作環境が書込記録を durable として受け付けた所**(接合面の受領。ADR 0012 の5つ目の呼び出し)までである。`pressure block(deadline 1 秒)` なので、詰まれば最大 1 秒待つ。

```plaintext
# KVCore の body(擬似)
格納(キー, 値) を受けたら:
  版 = KV表[キー].版 + 1
  待つ 書込記録(キー, 値, 版) を Persister へ流す        # 受け付けられるまで最大 1 秒
  KV表[キー] = (値, 版)
  完了 を返す
取得(キー) を受けたら:
  KV表[キー] を返す
```

| 案                     | 1 秒詰まった時に起きる事                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| 待たせる逐次           | **取得も止まる。** 読みだけの要求が、書きの詰まりに巻き込まれる。KV ストアとして使えない                |
| 待つ所で次を受ける逐次 | 取得は通る。ただし**同じキーへの二つ目の格納も通り**、二つが同じ `版` を計算する(下)                    |
| 内側の並行             | 取得は通る。`KV表` を二つの仕事が同時に触るため、`KV表` に並行時の扱いの宣言が要る(思考実験 24 の論点1) |

**待つ所で次を受ける逐次で、追い越しが起きた。**

```plaintext
時刻 1  格納(k, A) : 版 = 1 を計算 → 待つ(書込記録 k, A, 1)
時刻 2  格納(k, B) : 版 = 1 を計算 → 待つ(書込記録 k, B, 1)       # 時刻 1 の仕事は待つ所で止まっている
時刻 3  格納(k, B) の書込記録が先に受け付けられ、KV表[k] = (B, 1)
時刻 4  格納(k, A) の書込記録が受け付けられ、KV表[k] = (A, 1)     # 後から来た B を、先に来た A が上書きする
```

- **待つ所の前に読んだ状態は、待つ所の後には古い。** 待つ所で次を受ける以上、これは避けられない。
- 直し方は二つある。待つ所の後で読み直すか、**格納だけは待たせる逐次にする**か。KVCore の整合性の規則(第2節の intent)は後者を求める。
- 取得は待つ所を持たないため、どの案でも追い越しは起きない。**再入の害は、待つ所を持つ仕事どうしの間にだけ出る。**

### 3.2 OrderIntake — 受注を処理する間に、二つの `ask` を順に待つ

ADR 0031 の机上検証1(受注の一生)の OrderIntake は、`受注`(期限 500 ミリ秒)の中で `引当`(100 ミリ秒)と `保存`(200 ミリ秒)を順に待つ。

```plaintext
# OrderIntake の body(擬似)
受注(注文) を受けたら:
  引当の結果 = 待つ Inventory へ 引当(品目, 数量)
  引当済み(引当番号) でなければ 受注不可 を返す
  保存の結果 = 待つ OrderStore へ 保存(注文, 引当番号)
  ...
```

| 案                     | 1 件あたりの所要 | 同時に来た 10 件の最後の1件                                 |
| ---------------------- | ---------------- | ----------------------------------------------------------- |
| 待たせる逐次           | 最大 300 ミリ秒  | 前の 9 件を待つ。**受注の期限 500 ミリ秒を大きく超える**    |
| 待つ所で次を受ける逐次 | 最大 300 ミリ秒  | 10 件が待つ所で重なる。最後の1件も最大 300 ミリ秒前後で返る |
| 内側の並行             | 最大 300 ミリ秒  | 同上                                                        |

- 待たせる逐次では、**期限は一件の所要ではなく、待ち行列の長さで破られる。** ADR 0031 の机上検証1 の発見4(期限の和)は一件の中の和を見たが、待ち行列の分も足す事になる。
- OrderIntake の状態は `state none` である(引当番号は仕事の中の値)。**状態が無ければ、再入しても追い越しの害は出ない。**
- 待たせる逐次でこれを凌ぐには、OrderIntake を複数動かすしかない。複製は最小の分散動作環境(Phase 2)の課題(U6)であり、言語の外である。

**送り出しと待ちを分ける**(思考実験 24 の論点2)と、互いに依存しない `ask` は並べて待てる。

```plaintext
在庫 = 送る Inventory へ 在庫の照会(品目)
与信 = 送る CreditCheck へ 与信(客)
待つ 在庫, 与信                                        # 二つを同時に待つ。所要は和ではなく最大
```

- これは**待ちの並行**であり、計算の並行ではない。状態を同時に触る物は増えない。三案のどれでも書ける。
- 待つ所が印として現れていれば(論点3)、`送る` と `待つ` の間に挟んだ処理が、二つの応答のどちらより先に走るかが読める。

### 3.3 内側の並行 — 宣言の数と出力先

内側の並行を許すと、思考実験 24 の論点1 の通り、全ての `state` に並行時の扱いの欄が要る(省略の禁止。ADR 0008)。

```plaintext
state KV表 recoverable(Persister.再生) shared(lock)      # 仮の欄
state none                                               # 状態が無ければ欄も無い
```

それ以上に重いのは、**出力先2言語で同じ意味にならない**事である(ADR 0012 の決定9(互換性の単位))。

| 出力先      | 待つ所で次を受ける逐次                                              | 内側の並行                                                                         |
| ----------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| TypeScript  | イベントループと `async`・`await` そのものである                    | **書けない。** Worker は状態を共有せず、`SharedArrayBuffer` は記録型を載せられない |
| Rust        | 一本の非同期実行系(`tokio` の `current_thread`)で書ける             | スレッドと `Mutex` で書ける                                                        |
| Rust(ESP32) | Embassy(組込み向けの非同期実行系。標準ライブラリに依らない)で書ける | FreeRTOS のタスクで書けるが、意味の核(ADR 0029 の決定1)にロックの規則を持ち込む    |

- **内側の並行は TypeScript に写せない。** 同じ記述子の Rust 出力と TypeScript 出力を置き換えられる(混在の適合試験)という Phase 1 の成果物が成り立たない。
- 待つ所で次を受ける逐次は、**TypeScript では何もしなくてもそうなる**。待たせる逐次は、TypeScript では生成コードが受け口に待ち行列を持って一件ずつ流す事になる。
- 第0章 0.9 の Erlang/OTP の系譜(プロセスの中は逐次)とも、内側の並行は擦れる。

### 3.4 `ask` の閉路

A が B へ `ask` し、B がその応答の前に A へ `ask` する。

| 案                     | 起きる事                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| 待たせる逐次           | A は待つ所で止まり、B の `ask` を取り出さない。**B の `ask` は毎回期限切れになり、A の `ask` も期限切れになる** |
| 待つ所で次を受ける逐次 | A は待つ所で B の `ask` を受けて答える。閉路は**動く**。ただし A の状態は待つ所を跨いで変わり得る               |
| 内側の並行             | 動く。状態の扱いは `state` の欄に依る                                                                           |

- 待たせる逐次では、閉路は**静かに必ず失敗する**(思考実験 24 の 3.3)。ADR 0031 の `on failure` が毎回走り、記述の上では何の誤りも見えない。
- **閉路はコンパイル時に見つけられる。** ADR 0031 の決定6(記述の中の接続は全てどれかの `flow` 宣言に現れる)により、`ask` の接続の一覧は `flow` 宣言から漏れなく取れる。
  `depends` から作るより正確である——`depends` は相手しか言わず、どの公開面を呼ぶかを言わない。`flow` の辺は数えない(応答を待たないため)。
- 待つ所で次を受ける逐次でも、閉路は**双方向の強い結合**である(ADR 0024(結合バランスの取り込み)の物差し)。動くとしても、警告に値する。

## 4. 順序

### 4.1 一本の `flow` の中

思考実験 02 の `SensorIntake -> Normalizer : flow 計測値` は、計測値が送った順に届く事を前提に読める。今の仕様はそれを言っていない。

- 動作環境は接続ごとに待ち行列を作る(ADR 0012 の机上検証2)。待ち行列が一本なら、**送り手1つ・受け手1つの接続の中では FIFO** が自然に成り立つ。
- Zenoh(ADR 0001)は、一つの発行者から一つの購読者への順序を、信頼できる通信路の上で保つ。写し先とも矛盾しない。
- `latest`・`drop` は途中を捨てるが、**残った物の順は入れ替えない。**

### 4.2 durable の再送

受け手が落ちて再起動した時、動作環境は受領の返っていない物を再送する(ADR 0012 の5つ目の呼び出し)。

```plaintext
送った順        : m1 m2 m3 m4
受け手が処理    : m1 m2 m3            # m3 の受領を返す前に落ちた
再起動後に届く  : m3 m4               # m3 は二度目
```

- 再送を**受領の返っていない最も古い物から、元の順で**行えば、追い越しは起きない。起きるのは**重複**だけであり、重複は `idempotent` が受ける(E0004-1(durable と idempotent))。
- 「重複はあり得るが、追い越しは無い」と言えれば、受け手は順序を前提に書け、重複だけを `idempotent` で吸収すればよい。
- 逆に、再送を別の通り道で行う実装(再送用の待ち行列を後ろに付ける)では、m4 が m3 より先に届き得る。**これを禁じるかどうかは、実装を縛る言語の約束である。**
- 送り手の側が落ちた時、durable な流れは動作環境が持っているため、送り手の再起動を跨いで順は保たれる(ADR 0012 の決定5(並置))。
  一体の書き込みの ESP32 は durable を持たず(ADR 0029 の決定3)、配置の設定で拒まれるため、この問いに当たらない。

### 4.3 接続を跨ぐ順序

思考実験 02 の Aggregator は、複数の SensorIntake から(Normalizer を経て)計測値を受ける。

- **送り手が違えば、届く順に意味は無い。** 二つの機器の計測値のどちらが先に届くかは、通信路と負荷で決まる。
- 時間の順に並べたいなら、計測値が持つ `時点` で並べる。到着順で並べる記述は、**データに書くべき順序を通信に頼っている。**
- これは言語が保証しない事として書けばよく、新しい語は要らない。

### 4.4 `ask` の応答と `flow` の到着(思考実験 20 の論点3)

```plaintext
Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
correlate 受注番号 : 受注 -> 受注の状態
```

注文管理が `受注番号` を返してすぐ `受注の状態` を流すと、Frontdesk には**どちらが先に届くか分からない**。別の接続だからである。

- `correlate` の並び(`受注 -> 受注の状態`)は**送った時間の順**であり、届く順ではない。ADR 0023 はこれを区別していない。
- Frontdesk の body は、`受注の状態` が `受注番号` の応答より先に届く場合を書かなければならない。鍵で引いても待ちが無い——ADR 0031 の決定10(鍵の合わない到着は失敗と呼ばない)の形である。
- 言語に「応答を先に届ける」約束を置く案もある。だが送り手と受け手の間の二本の通り道を、動作環境が束ねて並べる事になり、
  Zenoh の写し(`ask` は問い合わせ、`flow` は発行と購読)では通り道が別である(ADR 0001)。**置くと写し先を縛る。**
- 待つ所で次を受ける逐次なら、Frontdesk は `受注` の応答を待つ所で `受注の状態` を受け取れる。**待たせる逐次では受け取れず、`受注の状態` は待ち行列で待つ。**
  順序の問いが、実行モデルの問いに戻ってくる。

### 4.5 待つ所で次を受けると、出る順が入れ替わる

4.1 の FIFO は**入る順**である。待つ所で次を受ける逐次では、**出る順**は入る順と違ってよい。

- KVCore の 3.1 では、格納(k, A) より後に入った 格納(k, B) が先に書込記録を流した。入る順は保たれても、Persister に届く順は入れ替わった。
- 下流の `flow` の FIFO は、上流が**入れ替えた後の順**を保つだけである。全体を通した順は、待つ所を持つ仕事を待たせる逐次にした所でだけ保たれる。

## 5. 上限

### 5.1 `pressure block` の上限

ADR 0012 の机上検証2 で、動作環境が待ち行列を作る時に上限が要る事は確認済みである。残るのは書き方である。

```plaintext
SensorIntake -> Normalizer : flow 計測値 pressure block(deadline 1 秒, bound 64 要素) (transient)   # 仮の語 bound
Aggregator   -> Alerter    : flow 集約値 pressure latest (transient)                                  # 上限は 1。意味から決まる
Normalizer   -> Aggregator : flow 正規化済み計測値 pressure drop(bound 256 要素) (transient)          # あふれる所を決めるのに上限が要る
```

- 上限の数は列の長さであり、`uint64(0) 要素` で書く(E0019-4(列の長さ・添字の型))。新しい量は要らない。
- **`drop` にも上限が要る。** 「あふれた分を捨てる」は、どこからあふれるかが決まらないと意味を持たない。今の第4章 4.3 は `drop` に何も書かせていない。
- **`latest` の上限は 1 である。** 意味から決まるため、書かせない。省略の禁止(ADR 0008)は既定値を禁じるが、選択の無い所に宣言を強いるのは単なる重さである(ADR 0023 が `correlate` を常に必須にする案を捨てた理由)。
- durable の待ち行列は記憶ではなく永続の記憶域に溜まる。同じ `bound` を記憶域の上限として使うか、別に書かせるかは分かれる。
- ESP32 の最小の動作環境では、上限は記憶の見積もりそのものである(ADR 0029 の決定3(能力と配置の設定))。`bound` が書かれていれば、配置の設定の時に足りるかを照らせる。

### 5.2 `ask` の受け口の待ち行列

`ask` の受け口にも待ち行列はある。待たせる逐次では、3.2 の 10 件は受け口の待ち行列に並ぶ。

- 期限が待ち行列の**寿命**を縛るため、無限には溜まらない。ただし**件数**は縛らない。毎秒 1000 件来て期限が 500 ミリ秒なら、500 件が並び得る。
- 上限を超えた `ask` を動作環境が拒めば、呼び手には**接続の失敗**として届き、ADR 0031 の `on failure` が引き受ける。新しい失敗の種類は要らない。
- 上限をどこに書くかは三つ考えられる。`expose` の欄、`flow` 宣言の接続の欄、コンポーネント全体の欄である。
  受け口は複数の呼び手が共有するため、**接続の欄には書けない**(呼び手ごとの上限の和が受け口の上限にならない)。

### 5.3 同時に抱える仕事の上限

待つ所で次を受ける逐次では、待つ所で止まっている仕事が溜まる。3.2 で 10 件が重なったように、溜まる数に上限が無い。

- 各仕事は待つ所で局所の値を抱えたまま止まるため、記憶を食う。ESP32 では特に効く。
- Orleans は再入を許しても、一つの活性化に入れる要求の数を設定で縛る。
- 上限を `ask` の受け口の待ち行列(5.2)と一つにまとめる案がある——「取り出したが終わっていない仕事」と「まだ取り出していない仕事」の和を縛る。

### 案の素描(ADR へ渡す)

- **論点1**: 内側の並行は採らない方向が強い。理由は TypeScript への写し(ADR 0012)と、`state` の欄の増加(思考実験 24 の論点1)である。
- **論点2・3**: 二つの形が考えられる。
  - **公開面ごとに宣言する**: `expose 格納(キー, 値) -> 完了 | 失敗 turn serial`・`expose 取得(キー) -> 値 | なし turn interleave` のように、待つ所で次を受けてよいかを公開面ごとに書く(仮の語)。
    省略の禁止により、全ての `ask` の受け口と `flow` の受け口に書く事になる。
  - **待つ所を持たない仕事だけを並べる**: 言語は待つ所で次を受ける逐次に固定し、追い越しを避けたい時は記述者が待つ所の後で読み直す。宣言は増えないが、KVCore の整合性の規則が body に沈む。
- **論点5**: 待たせる逐次の公開面を含む閉路はエラー、待つ所で次を受ける公開面だけの閉路は警告、という分け方が考えられる。論点3 の宣言に依る。
- **論点7**: 「重複はあり得るが追い越しは無い」を第4章 4.4 の durable の意味に足す案。
- **論点9**: `pressure block(deadline <時間>, bound <要素>)`・`pressure drop(bound <要素>)` と書く案。`latest` は書かせない。
  `ask` の受け口と待つ所の仕事の上限は、受け口が複数の呼び手に共有されるため、`expose` の側に書く案が有力である。

## 7. 所見

- **九つの問いは、止まり方一つに集まった。** 待つ所で何をするかが決まると、閉路の成否(3.4)、出る順の入れ替わり(4.5)、`ask` の応答と `flow` の到着の扱い(4.4)、
  溜まる物の上限(5.3)が決まる。U10 と U11 を同時に決めるとした計画書 第4節 4.3 の判断は、書き下ろしても正しかった。
- **再入の害は、状態と待つ所の両方を持つ仕事にだけ出る。** OrderIntake(状態なし)では無害、KVCore の取得(待つ所なし)でも無害、KVCore の格納(両方あり)でだけ追い越しが起きた。
  害の起き得る所は宣言から絞れる——`state` を持ち、待つ所を持つ公開面である。
- **順序について言語が言える事は少なく、それで足りる。** 一本の接続の中の FIFO と、再送で追い越さない事の二つである。それ以外の順序はデータ(`時点`・鍵)に書く。
- **写し先が判断を絞った。** 内側の並行は TypeScript に、応答を先に届ける約束は Zenoh の写しに、それぞれ擦れた。ADR 0012 の「同じ記述子の二つの出力は置き換えられる」が、ここでも物差しになった。

## 10. 論点3 の数え上げ — 再入を公開面ごとに選ぶと、宣言はどれだけ増えるか(2026-10-15)

### 10.1 数え方

- **数えるのは受け口である。** 再入は仕事を受け取る側の問いであり、`ask` の受け口と `flow` の受け口が対象になる。`flow` の出口は数えない。
- **今の仕様の形に直して数える。** 思考実験 01〜03 は `flow` の受け口の宣言を省いていた(第3章 3.2)。今の仕様では受け口も `expose` に書くため、省かれた受け口を補った。
  記述の外から届く物(SensorIntake が機器から受ける計測値、ClientGate がクライアントから受ける要求)は外部世界との境界(U12)の物であり、`expose` が無いものは数えない。
- 各受け口について三つを見た。
  - **待つ所があるか**: 処理の中で `ask` の応答、`pressure block` の受付、外部への入出力(データベース・ファイル・通知)のどれかを待つか。
  - **状態があるか**: `state` に宣言した状態か、`io` の層の向こうにある記憶(データベース・ログのファイル)を触るか。
  - **待つ所で次を受けると害が出るか**: 第3節の KVCore のように、待つ所を跨いで読んだ値が古くなるか、出る順が入れ替わるか。

### 10.3 公開面から始まらない仕事

数えている途中で、**受け口の一覧に載らない仕事**が見つかった。

```plaintext
# Aggregator の body(擬似)
時計で 1 分ごとに:
  集約値 = 集約する(ウィンドウ)
  待つ 集約値 を MetricStore へ流す            # pressure block。詰まれば待つ
  ウィンドウ = 空                              # ← 待つ間に足された計測値も消える
正規化済み計測値 を受けたら:
  ウィンドウ に足す
```

- 害は**受け口どうしではなく、時計で始まる仕事と受け口の間**に出る。待つ所で次の計測値を受けると、締めたウィンドウに足され、締めの後で空にされて消える。
- **時計で始まる仕事は、言語に形が無い。** 思考実験 02 は「現在時刻は driver から注入する」と書いたが、1 分ごとに仕事を起こす物が何かは書いていない。
  経過時間計はコードに出さない(ADR 0012 の決定2(責務の分担))ため、body が自分で眠って起きる形も書けない。
- ADR 0031 の `on expiry` も、公開面から始まらない仕事である。待つ側の動作環境が期限切れを届け、待つ側が処理する。
- したがって**公開面ごとに再入を選ぶ形では、全ての仕事を覆えない。** 時計と `on expiry` の分を、別に書く場所が要る。

| 数えた物                                   | 思考実験 01 | 思考実験 02         | 思考実験 04 | 合計 |
| ------------------------------------------ | ----------- | ------------------- | ----------- | ---- |
| コンポーネント                             | 3           | 5                   | 3           | 11   |
| 受け口                                     | 4           | 5                   | 5           | 14   |
| 公開面から始まらない仕事                   | 0           | 1(時計)             | 0           | 1    |
| 待つ所がある受け口(選んだ結果が変わる所)   | 2           | 4                   | 4           | 10   |

- **害が出るのは 3 か所であり、残りは全て待つ所で次を受けてよい。** 14 の受け口のうち、待たせたいのは KVCore の `格納` と Persister の `書込記録` の二つ、加えて Aggregator の時計の仕事である。
- **答えが一つのコンポーネントの中で分かれたのは KVCore だけである。** Aggregator と Persister は、コンポーネント全体を待たせる逐次にしても困らない
  (Aggregator は受け口が一つ、Persister の `再生` は起動時の復元にしか使わない)。

### 10.5 宣言の形ごとの費用

| 形                               | 増える物                            | 3 か所の害を防げるか                                            | 擦れる所                                                       |
| -------------------------------- | ----------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------- |
| 受け口ごとに全て書く             | 14 の受け口の行に語が1つずつ(14 語) | KVCore・Persister は防げる。**Aggregator の時計は書く所が無い** | 11 か所で「次を受けてよい」を書き写す                          |
| コンポーネントごとに1行書く      | 11 行                               | Aggregator・Persister は防げる。**KVCore は取得まで待たせる**   | 第3節 3.1 の問題が残る                                         |
| 待つ所のある受け口だけに書く     | 10 語(+時計の分)                    | 防げる(時計の分を書く所があれば)                                | 待つ所の有無は body を読むまで分からない(body の記法(U26)待ち) |
| 待たせたい所だけ、排他を宣言する | 3 行                                | 防げる。時計と受け口の組も「この二つは重ならない」と書ける      | 書かなければ次を受ける事になる。既定値に見える(ADR 0008)       |

最後の形は、例えば次のように書く(仮の語)。

```plaintext
component KVCore {
  constraint {
    ...
    exclusive 格納                                  # 格納どうしは重ならない
  }
}
component Aggregator {
  constraint {
    ...
    exclusive 締め, 正規化済み計測値                 # 時計で始まる締めと、受け口は重ならない
  }
}
component Persister {
  constraint {
    ...
    exclusive 書込記録                              # 追記どうしは重ならない
  }
}
```

- **排他は害の起きる組を名指す。** 害は一つの受け口の性質ではなく、二つの仕事の組に出る(10.3)。受け口ごとの印より、組の宣言の方が害の形に合う。
- **省略の禁止との関係**: 書かなければ排他は無い、という形は既定値に見える。しかし `idempotent` は既に「該当時のみ」の約束として宣言させている(第3章 3.2)。
  排他も「重ならない」という約束であり、該当しない時に `exclusive none` を書かせるかは、`idempotent` と揃えて決める事になる。
- `締め` は時計で始まる仕事の名前である。この形を採るなら、**時計で始まる仕事に名前を付けて宣言する場所**(10.3)が先に要る。

### 10.6 分かった事

- **宣言を足すべき所は少ない。** 3 つの思考実験の 14 の受け口と 1 つの時計の仕事のうち、待たせたいのは 3 か所だった。全ての受け口に書かせると、11 か所で同じ答えを書き写す。
- **害は受け口ではなく、仕事の組に出る。** KVCore は `格納` と `格納`、Persister は `書込記録` と `書込記録`、Aggregator は時計の締めと受け口であった。論点3 の「公開面ごとに選ぶ」は、問いの立て方が一段ずれていた。
- **状態の宣言だけでは害を見つけられない。** Persister の害は `state` に宣言されていないログのファイルから出た。言語が `state` と待つ所から害を推して宣言を省かせる形は、ここで外れる。
  記述者が「重ならない」を書く形が要る。
- **待つ所の範囲を決める必要がある。** `ask` の応答と `pressure block` の受付だけでなく、`io` の層の外部への入出力も待つ所になる。TypeScript では `await` が付く所が全て当たる。
- **公開面から始まらない仕事に、言語の形が無い。** 時計で始まる仕事は思考実験 02 から書かれていたが、名前も起点も宣言されていなかった。ADR 0031 の `on expiry` も同じ種類の仕事である。U10 の ADR で、仕事の起点の一覧(受け口・時計・期限切れ)を決める事になる。

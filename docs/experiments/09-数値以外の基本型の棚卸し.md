# 思考実験 09: 数値以外の基本型の棚卸し(ADR 0009 の裏付け試験)

- 状態: Draft
- 日付: 2026-08-29
- 目的: ADR 0009 が一覧に挙げただけで裏付けを持たない基本型——真偽・時刻・期間・時間量、および**一覧に無い整数**——の要否を洗い出す。併せて `instant` が既存の体系で何を指す型かを調べ、Shidzuku の時間の型に何を選ぶかの材料にする(歴史を扱える日付の範囲と、日時の置き場所を含む)
- 進め方: 思考実験 05 が「公開面を流れる全データ」を横断で書き下ろしたのと同じ形で、今度は**数値以外の値**を横断する。書けない事があれば仕様に戻す

## 1. 検証の起点 — 基本型の一覧に裏付けが無い

ADR 0009(提案)の決定は、基本型を本文1行で挙げているだけである。

> 基本型として文字列・数値・真偽・時刻・期間・時間量を言語が持つ(時間3種は期限宣言と共通)。

思考実験 05 が検証したのは**構成子**(直積・直和・識別子型・列)であって、基本型ではない。
その後、文字列は ADR 0013 が、数値は ADR 0010・0017 が、それぞれ思考実験を伴って作り直した。残りは手つかずのまま束 B に入っている。

| 基本型             | 出自     | 裏付けの思考実験         | いまの状態                        |
| ------------------ | -------- | ------------------------ | --------------------------------- |
| 文字列             | 0009     | 08(テキストが主役の系)   | 0013 が廃止し、テキストに置換     |
| テキスト・バイト列 | 0013     | 08                       | ADR 0013 は採用済み(反映待ち)     |
| 数値               | 0009     | 06(単位)・07(限界)       | 0010・0017 が `実数`・`十進数` へ |
| 識別子             | 0009     | 05                       | 変更なし                          |
| 列                 | 0009     | 05・08(`列<商品コード>`) | 変更なし                          |
| **真偽**           | 0009     | **なし**                 | **本実験で検証する**              |
| **時刻**           | 0009     | **なし**                 | **本実験で検証する**              |
| **期間**           | 0009     | **なし**                 | **本実験で検証する**              |
| **時間量**         | 0009     | **なし**                 | **本実験で検証する**              |
| **整数**           | **無い** | —                        | **一覧に無い。要否から検証する**  |

裏付けの無い4つは、いずれも `instant`・`period`・`duration`・`bool` として ADR 0014 の語彙表に綴りだけが載っている。
綴りはあるが中身——基準時刻・分解能・壁時計か単調時計か・暦・うるう秒——が無い。

## 2. 数値以外の値の棚卸し(思考実験 01〜08 の横断)

公開面(`expose`)・`flow` の内容・`data` 宣言・接続の宣言に現れた値のうち、数値型(`実数`・`十進数`)・テキスト・バイト列・識別子型で受けられないものを全部挙げる。

| 実験 | 現れた値                      | いまの受け皿                     | 問題                                       |
| ---- | ----------------------------- | -------------------------------- | ------------------------------------------ |
| 01   | 数量(注文の個数)              | `数値`(= `十進数(i.0)`)          | 桁の見積りが設計判断にならない             |
| 02   | 時刻(計測値)                  | `時刻`                           | 中身が未定義                               |
| 02   | 期間(集約値の対象区間)        | `期間`                           | 中身が未定義。名前が既存体系と衝突         |
| 02   | 保持期間ポリシー(change 欄)   | —                                | 暦上の日が要る(「何日で間引くか」)         |
| 04   | 期限(`期限 1s`・`期限 200ms`) | `時間量`                         | `量 時間` の値と二重                       |
| 04   | 版(単調増加する世代番号)      | `数値`                           | 比較と +1 しかしない。桁の宣言に意味がない |
| 04   | 照会結果の有無                | 直和(`見つかった(値)` と `なし`) | 直和で書けている(真偽を使っていない)       |
| 08   | ロケール                      | 区分(直和)                       | 直和で書けている                           |
| 08   | 列の要素数・添字              | —                                | 公開面に出ていないが body では必ず要る     |

**真偽は8実験の公開面に一度も現れなかった。** 「有無」「可否」はすべて名前の付いた直和(`受注(受注番号) | 受注不可(理由)`、`見つかった(値) | なし`、`済 | 訳なし`)で書かれている。

**整数に当たる値は3か所に現れた**(数量・版・添字)。いずれも「数えたもの」であり、刻みは常に 1 である。

## 3. 整数 — `十進数` と `実数` で代用できるか

ADR 0017 は数値型を2つに定めた。整数を置かないなら、数えた値はこのどちらかで書く事になる。

```plaintext
data 注文 { 品目: 品目ID, 数量: 十進数(3.0) unitless }   # 十進数で代用
data 書込記録 { キー: キー, 値: 値, 版: 実数 unitless }   # 実数で代用
```

### 3.1 代用が破れる3箇所

#### (1) `実数` は 2^53 を超える整数を表せない

`実数` の有効桁は 53 ビット ≒ 十進 15.95 桁である。これを超える整数は、隣の値と区別できない。

| 値                          | 桁数   | `実数` で表せるか           |
| --------------------------- | ------ | --------------------------- |
| 注文の個数(〜1万)           | 4      | 表せる                      |
| 連番・世代番号(〜1兆)       | 13     | 表せる                      |
| ナノ秒の Unix 時刻(2026 年) | 19     | **表せない**(1 ns が消える) |
| 64 ビットの識別子・ハッシュ | 19〜20 | **表せない**                |

ナノ秒の時刻は思考実験 07 が既に数えている(19 桁)。**`実数` を主に使う型にした結果、ナノ秒の時点を置く場所が無くなっている。** これは ADR 0017 の穴である。

#### (2) `十進数` は桁の境目が機械の語長と噛み合わない

`十進数(19.0)` は 16 バイトになる(ADR 0010 の記憶域の表: 18 桁までが 8 バイト)。
64 ビット整数がちょうど収まる 19 桁で、記憶域が倍になる。ADR 0010 自身が欠点として挙げている「19・39・77 桁の境目」がそのまま出る。

ナノ秒の時点を `十進数(19.0) ナノ秒` で持つと、8 バイトで足りる値に 16 バイトを払う事になる。

#### (3) 桁の見積りが設計判断にならない値がある

ADR 0017 の使い分けの指針は「その値の刻みを、人が十進で決めたか」である。数量・版・添字はいずれも「決めた」側であり `十進数` に落ちる。
しかし `十進数` は桁の宣言を要求し、桁は公開面の一部になる(後から広げると W0003-2 の対象)。

- `注文の数量` の上限は、設計者が決めたい値ではない。決めさせると「9999 個までの注文を受ける」という**書いていない仕様**が型に紛れ込む。
- `版` は +1 と比較しかしない。上限は「機械が数え切れなくなるところ」であって設計判断ではない。
- `列の添字・長さ` に桁を宣言させると、列の長さの上限を型に書く事になる。列は型引数を1つしか持たない(ADR 0009)。

ADR 0017 が `実数` について書いた論法——「桁という欄を持たない完結した型である」——は、そのまま整数に当たる。**整数の刻みは常に 1 であり、宣言しても情報が増えない。** 決まっていないのは窓の幅だけであり、それは機械の語長が1つに定める。

### 3.2 判定

**整数型が要る。** 根拠は3つあり、いずれも代用では消えない。

1. `実数` では 19 桁の値(ナノ秒の時点・64 ビットの識別子)が壊れる
2. `十進数(19.0)` は 8 バイトで足りる値に 16 バイトを払う
3. 数えた値の桁の宣言は、設計判断ではなく作文である(ADR 0017 が `実数` で退けたのと同じ重さ)

そして**時点の型が整数を要求する**(第5節)。整数を置かないなら、時点は `十進数(19.0)` か、言語が隠す不透明な表現になる。前者は重く、後者は「型を読めば分かる」に反する。

### 3.3 整数の除算 — 暗黙の丸めが入る穴

整数の `/` は多くの言語で切り捨てになる。これは**宣言されていない丸め**であり、ADR 0010 が除算演算子 `÷` を置かなかった理由がそのまま当たる。

ADR 0010 は既に答えを持っている。`分ける(a, b)` が商と余りを同時に返し、`a = 商 × b + 余り` が厳密に成り立つ。整数の除算はこれだけで足りる。

## 4. 論理(真偽) — 公開面に現れたか

### 4.1 現れなかった

第2節の棚卸しのとおり、8実験の公開面・`data`・`state` に真偽は一度も現れていない。「有無」「可否」「成否」はすべて名前の付いた直和で書かれた。

```plaintext
data 受注結果 = 受注(受注番号) | 受注不可(理由)     # 実験 01
data 照会結果 = 見つかった(値) | なし               # 実験 04
expose 訳の取り寄せ(商品コード) -> 済 | 訳なし      # 実験 08
```

真偽で書くと、こうなる。

```plaintext
expose 在庫確認(品目ID) -> 真偽        # 真が「在庫あり」か「在庫切れ」かは型に無い
data 注文 { …, 至急: 真偽 }            # 偽が「通常」か「未設定」かは型に無い
```

**真が何を意味するかは型に書かれない。** これは ADR 0013 が「テキストを制御フローの条件に使う事」を禁じた理由(区分コードの代用)の裏返しであり、ADR 0009 の「『無い』は直和で明示する」の延長でもある。

### 4.2 しかし body には要る

条件分岐・比較・不変条件の判定は真偽を通る。`a < b` の結果を受ける型が無ければ、比較演算子そのものが書けない。
ADR 0013 の役割(境界・解析・領域・整形)のうち領域は判定の場所であり、そこに条件式が無い言語は書けない。

### 4.3 判定

**論理型は置く。ただし置き場所を body に限る。** 型としては要るが、公開面の語彙としては一度も要らなかった——この非対称が検証の結果である。

## 5. `instant` とは何か — 既存体系の調査

ADR 0014 の語彙表は `時刻 = instant`(時点)とだけ書いている。既存の体系で `Instant` が何を指すかを調べた。

### 5.1 同じ名前で正反対の2つがある

| 体系                      | `Instant` の意味    | 単調か         | 中身                                     |
| ------------------------- | ------------------- | -------------- | ---------------------------------------- |
| Java `java.time.Instant`  | 時間軸上の一点(UTC) | **単調でない** | エポック秒(`long`)+ 秒内ナノ秒(`int`)    |
| Rust `std::time::Instant` | 単調時計の読み      | **単調**       | 不透明。エポックを持たず、差だけが取れる |

Java の `Instant` は 1970-01-01T00:00:00Z を原点とする時間軸上の点であり、大きい値が必ず後の時点を指す。値としては壁時計であり、NTP の補正で巻き戻り得る。

Rust の `Instant` は逆に、**壁時計から切り離した単調時計**である。`SystemTime`(壁時計・巻き戻り得る)と型で分けられており、`Instant` は「秒数を取り出す」操作を持たない不透明型で、差(`Duration`)と比較しか許さない。
`SystemTime` の演算は失敗し得る(`Result` を返す)のに対し、`Instant` の演算は失敗しない——この非対称が、時計の性質を API の形で告げている。

**同じ綴りで意味が正反対である。** `時点 = instant` とだけ書いた ADR 0014 の語彙表は、この分岐を素通りしている。

### 5.2 主要な体系の型の対応

| 概念                     | Java `java.time` | Noda Time       | TC39 Temporal             | Go                 | Rust         |
| ------------------------ | ---------------- | --------------- | ------------------------- | ------------------ | ------------ |
| 時間軸上の一点(壁時計)   | `Instant`        | `Instant`       | `Temporal.Instant`        | `time.Time`        | `SystemTime` |
| 単調時計の読み           | (無い)           | (無い)          | (無い)                    | `time.Time` に内包 | `Instant`    |
| 暦上の日                 | `LocalDate`      | `LocalDate`     | `Temporal.PlainDate`      | (無い)             | (無い)       |
| 時計の読み(日を持たない) | `LocalTime`      | `LocalTime`     | `Temporal.PlainTime`      | (無い)             | (無い)       |
| 暦上の日時(時間帯なし)   | `LocalDateTime`  | `LocalDateTime` | `Temporal.PlainDateTime`  | (無い)             | (無い)       |
| 時間帯付きの日時         | `ZonedDateTime`  | `ZonedDateTime` | `Temporal.ZonedDateTime`  | `time.Time`        | (無い)       |
| 経過時間(正確な長さ)     | `Duration`       | `Duration`      | `Temporal.Duration`(一部) | `time.Duration`    | `Duration`   |
| **暦上の量**(1か月・1年) | `Period`         | `Period`        | `Temporal.Duration`(一部) | (無い)             | (無い)       |
| **時点と時点の間**(区間) | (無い)           | `Interval`      | (無い)                    | (無い)             | (無い)       |

この表から3つ分かる。

1. **壁時計と単調時計を型で分けている体系がある**(Rust)。分けていない体系(Java・Go)では、経過時間の測定に壁時計を使う誤りが実際に起きている。
2. **`Period` は「暦上の量」であり「時点と時点の間」ではない**。ISO 8601 の `P1M`(1か月)も同じ意味である。「時点と時点の間」は Noda Time では `Interval` と呼ばれる。
3. **暦上の日(`LocalDate` / `PlainDate`)を持つ体系が多い**。誕生日・締め日・営業日は時間軸上の点ではないためである。
4. **日時(`LocalDateTime` / `PlainDateTime`)を持つ体系は、日と時計の読みも別に持っている**。日時はその二つの組であり、独立した概念ではない。

### 5.3 うるう秒 — Java の選択

UTC は 1 日を 86399 秒または 86401 秒にする事がある(うるう秒)。Java の時間軸(Java Time-Scale)は、1972-11-03 以降について **UTC-SLS と一致する**と定めている——うるう秒を当日の最後の 1000 秒に等分して薄め、1 日を常に 86400 秒に見せる方式である。

これは正確さを捨てて**一様さ**を取った選択であり、Shidzuku には直接効く理由がある。

- うるう秒表を持つと、`時点 + 時間量` の結果が表の版に依存する。分散したノードで表が食い違えば、同じ入力から違う状態へ遷移する。ADR 0001(Raft)の前提が壊れる。
- うるう秒は 6 か月前にしか決まらない。未来の時点の演算が確定しない。

### 5.4 分解能と範囲 — 64 ビットのナノ秒

エポックからのナノ秒を符号付き 64 ビットで持つと、表せる範囲は約 ±292 年、すなわち **1677-09-21 〜 2262-04-11** である(Go の `time.Time` のナノ秒 API と同じ限界)。

| 表現                        | 分解能 | 範囲       | バイト |
| --------------------------- | ------ | ---------- | ------ |
| 64 ビットのナノ秒           | 1 ns   | ±292 年    | 8      |
| 64 ビット秒 + 32 ビットナノ | 1 ns   | ±2900 億年 | 12〜16 |
| 64 ビットのマイクロ秒       | 1 µs   | ±29 万年   | 8      |
| 64 ビットのミリ秒           | 1 ms   | ±2.9 億年  | 8      |

想定用途(業務システム・計測・分散制御)で必要な分解能はナノ秒であり、必要な範囲は数十年である。歴史・天文の日付は**時間軸上の点としては要らない**——それらは暦上の日である。

### 5.5 暦と時間帯を持つ型は要るか

`時点` は暦を持たない。しかし次は暦の値である。

- 締め日・支払期日・保持期間ポリシー(思考実験 02 の change 欄。「何日で間引くか」は暦上の日数である)
- 誕生日・有効期限・営業日

これらを `時点` で持つと、時間帯を1つ選ばされる。「2026-08-29 が誕生日」は、どの時間帯で見ても 2026-08-29 でなければならない。

ADR 0013 が文字列を廃した今、**暦上の日を書く場所が言語に無い**。テキストで書けば ADR 0013 決定4(部分取得・分割・パターン照合の禁止)に当たり、年月日を取り出す事すらできない。識別子型で書けば順序も差も取れない。

#### 日を持たない「時計の読み」も書けない

暦の値には、日を持たないものもある。

- 毎日 09:00 開店・17:00 締切・03:00 の日次バッチ
- 営業時間・受付時間の帯

これらは `日付` では書けず、`時点` でも書けない(どの日か決まらない)。`量 時間`(`整数 ミリ秒`)で「日の始まりからの経過」として書く事はできるが、
**時間の量に見えて時計の読みに見えない**。25 時間も表せてしまい、1日の中である事が型から読めない。

#### 日時は日と時計の読みの組である

「2026-08-29 14:30」は、日と時計の読みの**組**である。第5.2節の表のとおり、日時型を持つ体系はいずれも日と時計の読みも別に持っており、日時はその二つの合成である。
日と時計の読みを基本型に置けば、日時は直積で書ける——`期間` を直積で書けるのと同じ形である(第5.7節)。

#### 暦の日時に時間量を足す事は、暦の操作ではない

「2026-03-08 02:30 の3時間後」は、**時間帯が分からなければ答えが決まらない**。夏時間のある地域では 02:30 自体が存在しない日があり、02:00 が二度ある日もある。
暦の上で足せてしまう言語は、この曖昧さを黙って1つの答えに畳む。時間の量を足す事は時間軸の上の操作であり、暦の上の操作ではない。

一方「翌日の同じ時刻」は暦の操作であり、日に 1 を足すだけで曖昧さが無い。**二つは別の操作であり、別の型の上に置くのが素直である。**

### 5.6 紀元前は書けるか — 年の数え方と暦の限界

歴史を扱うには、紀元前の日付が要る。数え方は2つある。

| 数え方                      | 紀元前1年 | 紀元前2年 | 比較・減算                    |
| --------------------------- | --------- | --------- | ----------------------------- |
| 紀元(BC / AD)の欄を別に持つ | BC 1      | BC 2      | 欄をまたいで分岐する          |
| 天文学的年番号(ISO 8601)    | `0`       | `-1`      | 1つの符号付き整数の規則で済む |

天文学的年番号なら、紀元前と西暦をまたぐ比較も減算も他の年と同じ規則で書ける。記憶域の費用も無い——紀元前10000年でもエポックから **-4371587 日**であり、64 ビット整数の範囲を大きく下回る。

ただし**紀元前を表せる事と、当時の暦の日付を表せる事は別である**。先発グレゴリオ暦(proleptic Gregorian)は、グレゴリオ暦を制定前まで遡って当てはめたものにすぎない。

| 出来事                    | 当時の暦(ユリウス暦) | 先発グレゴリオ暦 |
| ------------------------- | -------------------- | ---------------- |
| カエサル暗殺(3月15日)     | 紀元前44年3月15日    | `-0043-03-13`    |
| ユリウス暦の紀元1年1月1日 | 0001-01-01           | `0000-12-30`     |
| グレゴリオ暦改暦の前日    | 1582-10-04           | `1582-10-14`     |

暦の換算は歴史学の知識であり、改暦の時期は地域ごとに違う(グレゴリオ暦の採用は 1582 年から 20 世紀まで散らばる)。
言語が1つの答えを持てば必ず嘘になるため、**暦は先発グレゴリオ暦の1つに限り、換算は `format` の役割の層に置く**のが素直である。

### 5.7 `期間` は直積で書ける

思考実験 02 の `集約値 { センサー, 期間, 平均, 最大, 最小 }` の `期間` は、集約の対象区間である。

```plaintext
data 集約区間 { 始まり: 時点, 終わり: 時点 }     # 直積で書ける
```

ADR 0009 の語彙(直積)でそのまま書ける。基本型として言語が持つと、**開区間か閉区間かを言語が決める**事になり、選択が1つ増える。

### 5.8 判定

- `時点`(instant)は **Java 側**——壁時計・UTC・エポック起点——とする。単調時計は言語の型にしない(第8節の論点3)。
- うるう秒は持たない。1 日は常に 86400 秒とする。
- 内部表現はエポックからの**整数ナノ秒**。範囲は 1677-09-21 〜 2262-04-11。
- **暦上の日の型が要る**(`日付`)。年は天文学的年番号の符号付き整数とし、**紀元前まで**表す。暦は先発グレゴリオ暦の1つに限る。
- **時計の読みの型も要る**(`時刻`)。`量 時間` での代用は、名前が値の出どころを告げない。
- **日時は基本型に置かない**。`日付` と `時刻` の直積で書く。暦の値への `量 時間` の加算は持たない(時間軸の加算は `時点` の上で行う)。
- `期間` は基本型から外す。直積で書ける。
- 名前の衝突を避けるため、区間を指す語に `period` を使わない。

## 6. `時間量` は基本型か、`量 時間` の値か

ADR 0010 は既にこう書いている。

> **時刻・期間・時間量との統合**。時間量は本来「量 時間」の値であり、単位(秒・ミリ秒)を持つ。基本型として別に置くか、量の体系へ寄せるかは U14(プログラムの宣言)で整理する。

量の体系へ寄せると、次が自動で付いてくる。

| 得られる事           | 中身                                                         |
| -------------------- | ------------------------------------------------------------ |
| 単位が型に載る       | `整数 ミリ秒` と `整数 秒` の取り違えが E0010-1 で落ちる     |
| 表現を書き手が選べる | `整数 ナノ秒`(厳密・軽い)・`実数 秒`(計測)・`十進数(3.3) 秒` |
| 換算の規則が既にある | 有理数比・連鎖換算の禁止・往復の非一致(ADR 0010)             |
| 基本型が1つ減る      | `時間量` を基本型に置かない                                  |

「月」「年」は単位にできない。1 か月は 28〜31 日であり、固定の比を持たないためである(第5節の `Period` と `Duration` の区別がこれである)。

## 7. 不足の洗い出し — 他に要る型

8実験と、一般的な業務システム・計測・分散制御の記述で要りそうな型を並べ、Shidzuku で書けるかを判定した。

| 候補                     | 8実験に現れたか   | 既存の語彙で書けるか                            | 判定            |
| ------------------------ | ----------------- | ----------------------------------------------- | --------------- |
| 整数                     | 3か所             | **書けない**(第3節)                             | **置く**        |
| 論理                     | body のみ         | 公開面には要らない(第4節)                       | **body に限る** |
| 時点                     | 実験 02           | **書けない**                                    | **置く**        |
| 時刻(時計の読み)         | 現れず            | **書けない**(第5.5節)。定期処理・営業時間に要る | **置く**        |
| 日時(日と時計の読みの組) | 現れず            | 日付と時刻を置けば直積で書ける(第5.5節)         | 置かない        |
| 日付(暦上の日)           | 実験 02 の change | **書けない**(第5.5節)                           | **置く**        |
| 時間量                   | 実験 03(期限)     | `量 時間` の値として書ける(第6節)               | 量へ寄せる      |
| 区間(時点と時点の間)     | 実験 02           | 直積で書ける                                    | 置かない        |
| 対応表(map)              | 現れず            | 公開面に一度も現れず。body 内は自由             | 置かない        |
| 集合(set)                | 現れず            | 同上                                            | 置かない        |
| 文字(char)               | 現れず            | テキストの分解が禁止(ADR 0013)                  | 置かない        |
| 空の型(unit / void)      | 現れず            | 値を持たない直和の区分(`済`・`完了`)            | 置かない        |
| 有理数                   | 換算比のみ        | 換算比の宣言に限ると ADR 0010 が決定済み        | 置かない        |
| 複素数・ベクトル・行列   | 現れず            | 直積と列で書ける。量の代数は未定                | 置かない        |
| 範囲(range)              | 現れず            | body 内の反復。公開面には出ない                 | 置かない        |
| URL・パス・メール        | 現れず            | 識別子型または直和(ADR 0013 決定1)              | 置かない        |
| 通貨                     | 実験 06           | `量 通貨`(ADR 0010)                             | 置かない        |
| 関数・第一級の手続き     | 現れず            | 振る舞いは ask / flow が担う                    | 置かない        |
| 参照・ポインタ           | 現れず            | 値のみ。同一性は識別子型                        | 置かない        |

**対応表と集合について。** 思考実験 08 の論点6(実行時に決まるロケールで定型の文言を引く)は、一見すると `対応表<ロケール, テキスト>` を要求する。
しかし文言のカタログは**整形の役割を持つ層の内側**にあり、ADR 0009 は「body 内部の型は自由」と定めている。公開面には現れない。
ADR 0009 が「継承・型引数は必要にならなかったため持たない」と判断したのと同じ理由で、置かない。

## 8. 検証結果 — 仕様に戻す論点

1. **整数型が無い**。`実数` は 19 桁の値を壊し、`十進数(19.0)` は 8 バイトで足りる値に 16 バイトを払う。時点の内部表現も整数を要求する。→ 基本型に `整数` を置く。除算は `分ける`(商と余り)だけとし、`÷` は置かない(ADR 0010 と同じ理由)。
2. **真偽は公開面に一度も現れなかった**。「有無」「可否」は名前の付いた直和で書かれている。しかし body の条件式には必ず要る。→ `論理` を置き、`data`・公開面・`state` に書けない型とする。
3. **`instant` は体系によって正反対の意味を持つ**。Java は壁時計、Rust は単調時計である。Shidzuku の `時点` を壁時計と定め、単調時計は型にしない。
  その帰結として、**時点どうしの差で経過時間を測ってはならない**(壁時計は巻き戻る)。経過時間と期限は `量 時間` の値で表し、測るのは動作環境の仕事とする。
  第4章の `deadline <時間量>` が既にこの形である事の**理由**が、ここで初めて与えられる。
4. **うるう秒を持たない**。持つと `時点 + 時間量` が表の版に依存し、分散したノードで結果が割れる(ADR 0001 の前提が壊れる)。Java Time-Scale と同じ選択である。
5. **暦上の日の型が無い**。ADR 0013 が文字列を廃した結果、締め日・誕生日・保持期間の日数を書く場所が言語から消えている。→ `日付` を置く。
  **範囲は紀元前まで広げる**。年は天文学的年番号(`0` = 紀元前1年)の1つの符号付き整数とし、紀元(BC / AD)の欄は持たない。
  欄を分けると比較と減算が欄をまたいで分岐するためであり、記憶域の費用も無い(紀元前10000年でエポックから -4371587 日)。
  ただし**暦は先発グレゴリオ暦の1つに限る**。当時の暦(ユリウス暦・和暦)への換算は改暦の時期が地域ごとに違い、言語が1つの答えを持てば嘘になる。
6. **日を持たない「時計の読み」の型も無い**(第5.5節)。「毎日 09:00 開店」は `日付` でも `時点` でも書けない。
  `量 時間` で代用できるが、時間の量に見えて時計の読みに見えず、25 時間も表せてしまう。→ `時刻` を置く。
7. **日時は基本型に置かなくてよい**。日と時計の読みの**組**であり、直積で書ける(`期間` と同じ形)。
  ただし**暦の値に `量 時間` を足す演算は持たせない**。「02:30 の3時間後」は時間帯が分からなければ決まらず(夏時間)、
  足せる言語はその曖昧さを黙って畳む。時間軸の加算は `時点` の上でだけ行い、暦の上の操作は `日を足す` に限る。
8. **`期間` は基本型から外せる**。直積で書ける。基本型にすると開区間・閉区間の選択を言語が決める事になる。
  併せて `period` の綴りは使わない。ISO 8601・Java・Noda Time の `Period` は「暦上の量」であり、意味が逆になる。
9. **`時間量` は `量 時間` の値へ寄せられる**。単位の検査(ミリ秒と秒の取り違え)が無料で付き、基本型が1つ減る。ADR 0010 の将来想定への回答になる。
10. **対応表・集合・文字・空の型は要らなかった**。公開面に現れず、既存の語彙で書ける。

## 9. 未解決課題への入力

- **U9(データ型の記述)**: 基本型の一覧を `論理・整数・実数・十進数・テキスト・バイト列・時点・日付・時刻` に確定する。構成子は変えない(直積・直和・識別子型・列)。日時は直積で書く。→ ADR 0019 を起案。
- **U15(数値の型と単位)**: 数値型は3つになる(`整数`・`実数`・`十進数`)。ADR 0017 の E0017-1(混在の禁止)は整数を含むよう改訂が要る。`量 時間` を言語が最初から持つ量とする。
- **U13(失敗の体系)**: 整数の桁溢れ・0 除算・表せる範囲外の時点と日付は失敗である。ADR 0010 の桁溢れ・ADR 0017 の特殊値と同じ体系で扱う。
- **U12(外部世界との境界)**: 外部の時刻表現(ISO 8601 の文字列・Unix 秒・DB の `TIMESTAMP`)を `時点` で受ける規則。時間帯の型もここで決める。
  暦から時間軸への変換は曖昧(夏時間で存在しない・二度ある時刻)であり、直和で受ける必要がある。逆向き(時間軸から暦へ)は常に決まる。
- **U20(役割の向きと通信の関係)**: 暦と時間帯を要する変換(`時点` ↔ `日付`・`時刻`)と、暦どうしの換算(先発グレゴリオ暦 ↔ ユリウス暦・和暦)は、ADR 0013 の役割のうち境界・整形にのみ許すのが素直である。領域は暦を知らない。
- **U5(トランスパイル先の言語)**: `整数` は Rust の `i64` にそのまま落ちる。TypeScript の `number` は binary64 であり 19 桁を表せないため、`bigint` が要る。ADR 0012 の要件に1行加わる。

## 10. 次の行動

- ADR 0019(基本型の体系)を起案する → 済
- ADR 0009 の基本型の一覧、ADR 0014 の語彙表、ADR 0017 の E0017-1 の改訂を 0019 に集約し、束 B を 0009・0010・0017・0019 の4本として判断する
- U13 の検討時に、整数の桁溢れ・0 除算・時点の範囲外を入力とする
- 対応表・集合は、公開面に現れる例が出たら再検討する
- 暦の複数化(ユリウス暦・和暦)と時間帯の型は、U12・U20 の検討時に入力とする

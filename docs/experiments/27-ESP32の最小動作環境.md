## 1. 「管理機能を使わない」とは何を外す事か

ADR 0012 の決定2(責務の分担)は、次の責務を動作環境に寄せた。これを**言語の意味**を担う物と、**運用の管理**を担う物に分けて見る。

| 責務                                         | 分け | 最小の動作環境で                          | 理由                                                                                                |
| -------------------------------------------- | ---- | ----------------------------------------- | --------------------------------------------------------------------------------------------------- |
| ask の期限(必ず返る)                         | 意味 | 持つ                                      | 「ask は必ず返る」は言語の約束である(第4章 4.1(二つの通信方式))。経過時間計と時限が一つあれば足りる |
| flow の流量制御                              | 意味 | 持つ(上限付きの待ち行列)                  | 記憶が小さい機器ほど要る。`pressure block` の上限(第4章 4.6(未定事項))はここでも要る                |
| 配達保証 transient                           | 意味 | 持つ                                      | 送って、落ちたら落ちたままでよい                                                                    |
| 配達保証 durable と再送                      | 意味 | 持たない(ロードで拒む)                    | フラッシュの容量と書き込み寿命が効く。永続化と再送の機構は最小ではない                              |
| idempotent の重複検出                        | 意味 | 持たない                                  | 再送をしない動作環境には、重複検出の出番が無い                                                      |
| 障害時の再起動(`on failure`)                 | 意味 | 持つ                                      | `on failure` に書いた「再起動する」はフローの意味である。外すと宣言が嘘になる                       |
| Zenoh の通信                                 | 意味 | 持つ(zenoh-pico)                          | 通信の全てである(第3節(通信))                                                                       |
| コンポーネント記述子の照合                   | 意味 | 持つ                                      | ロードの入口そのものである(第5節(プログラムのロード))                                               |
| 版の交渉                                     | 管理 | 持たない(同じ版だけを受ける)              | 版の混在と移行は、コンポーネントのバージョンと移行(U16)で未定である                                 |
| ログ規約の出力                               | 管理 | 持たない                                  | ログ規約(U4)が未定である。状態の確認(第4節(状態の確認))とは分ける                                   |
| 復元元の再生の提供(復元元を読む呼び出し、H7) | 意味 | 持たない(ロードで拒む。論点2(能力と拒否)) | 再生の元は durable な流れであり、durable を持たないなら提供できない                                 |
| Raft・配置の設定・複製・監督の方針           | 管理 | 持たない                                  | 最小の分散動作環境(Phase 2)の物であり、ESP32 の1台には要らない                                      |

分けてみると、見込みの三つ(通信・状態の確認・ロード)だけでは足りない。**ask の期限・上限付きの待ち行列・再起動の三つは、通信の意味から切り離せない**。
これらは管理ではなく、ask と flow という語が約束している事である。
最小の動作環境は「通信・状態の確認・ロード」に「意味の最小限(期限・待ち行列・再起動)」を足した物になる。

もう一つ分かる事は、**外すのは管理だけではない**事である。durable と recoverable は言語の意味だが、最小の動作環境では持てない。
ここで意味を弱めて実装する(durable を「なるべく届ける」で済ませる)と、同じ語が動作環境によって違う物を指す。
ADR 0012 は「意味を二箇所に置く事は、静かさにとって最大の危険」として、言語ごとに実行系を作る案を捨てている。同じ理由が動作環境の縮小版にも当たる。
したがって外し方は**弱めずに拒む**——持たない意味を要るコンポーネントは、ロードの時に理由を付けて受け付けない——になる(論点2(能力と拒否))。

## 2. 機器 — ESP32 の系列

| 品種     | CPU                      | 内蔵 RAM | PSRAM | 浮動小数点の演算器 | Rust の道具                    | 無線                   |
| -------- | ------------------------ | -------- | ----- | ------------------ | ------------------------------ | ---------------------- |
| ESP32    | Xtensa LX6、2コア 240MHz | 520KB    | 付く  | 単精度のみ         | Espressif の分岐した道具が要る | Wi-Fi 4・Bluetooth     |
| ESP32-S3 | Xtensa LX7、2コア 240MHz | 512KB    | 付く  | 単精度のみ         | 同上                           | Wi-Fi 4・BLE           |
| ESP32-C3 | RISC-V、1コア 160MHz     | 400KB    | 無い  | 無い               | rustc 本流のターゲット         | Wi-Fi 4・BLE           |
| ESP32-C6 | RISC-V、1コア 160MHz     | 512KB    | 無い  | 無い               | rustc 本流のターゲット         | Wi-Fi 6・BLE・802.15.4 |

- Wi-Fi を動かすと内蔵 RAM の多くを取られ、動作環境とコンポーネントに使えるのは数百 KB になる。PSRAM の有無が、ロードの方式(第5節(プログラムのロード))の選択を左右する。
- Rust は ESP-IDF の上で標準ライブラリを使う形(`esp-idf-svc`)と、標準ライブラリを使わない形(`esp-hal`)の両方がある。
  zenoh-pico(第3節(通信))と WASM の実行系(第5節(プログラムのロード))がどちらも ESP-IDF の部品として配られているため、**ESP-IDF の上の形が素直**である。
- 品種の選び方は、ロードの方式に従う。一体の書き込み(第5節(プログラムのロード))なら本流の道具で済む ESP32-C6、WASM でのロードなら PSRAM の付く ESP32-S3 が向く。
- ボードは [ADR 0030](../decisions/0030-ESP32ボードの選定.md)(提案)で選んだ。本節の後に量産に入った ESP32-C5・ESP32-C61 も比べている(2026-10-03)。

## 3. 通信 — zenoh-pico

[ADR 0001](../decisions/0001-分散環境の通信プロトコル.md)は、マイクロコントローラからデータセンターまでを一つのプロトコルで覆える事を理由に Zenoh を選んだ。ESP32 は正にその帯にある。

- **zenoh-pico** は ESP-IDF の上で UDP・TCP・シリアルを持つ。サーバの動作環境が使う Rust の Zenoh は非同期の実行系と記憶の量を前提とするため、ESP32 には載らない。
  ESP32 の動作環境は、C の zenoh-pico を Rust から呼ぶ事になる(論点1(2つ目の実装))。
- 繋ぎ方は、**クライアントとしてルータ(zenohd)に繋ぐ**のが基本である。ピア同士の繋ぎ方は、ユニキャストが TCP に限られ、マルチキャストは実験的な扱いである。
  最小の構成は「PC 1台(ルータとサーバの動作環境)+ ESP32 1台」になる。
- **シリアルで繋げる**事は、最小の開発環境に向く。USB で PC と繋げば、Wi-Fi の設定も無線の記憶の消費も無しに始められる。
- ask は Zenoh の問い合わせと応答に、flow は発行と購読に写る。ただし期限は**動作環境が測る**(ADR 0012 の決定2(責務の分担))。Zenoh の問い合わせの時限に預けると、期限の意味が通信の実装に移る。
- キー空間には名前と版を含める(ADR 0012 V1)。動作環境の語彙は ASCII、コンポーネントの名前は UTF-8 とする(ADR 0014)。形の一例を示す。

``` plaintext
shidzuku/<システム>/<コンポーネント>@<版>/<公開面>   # ask と flow
@shidzuku/node/<ノード>/status                          # 状態の確認(第4節(状態の確認))
@shidzuku/node/<ノード>/load                            # ロード(第5節(プログラムのロード))
```

名前をキーにどう綴るか(Zenoh のキーで特別な意味を持つ文字の扱い)は、名前の可逆な符号化(第5章 5.6(言語の外への写像)、ADR 0012「本 ADR が決めない事」)と同じ所で決まる。

## 4. 状態の確認

状態の確認は「今どうなっているか」を答える。**「何が起きたか」を記録するログ規約(U4)とは分ける。** ログは時間と共に増え、状態は増えない。

| 項目           | 中身                                                                      | 出どころ                               |
| -------------- | ------------------------------------------------------------------------- | -------------------------------------- |
| 動作環境       | 動作環境の版、機器の品種、能力(第8節(論点)の論点2(能力と拒否))            | 焼き込み                               |
| 起動           | 起動からの時間、最後の再起動の理由(電源投入・パニック・ウォッチドッグ等)  | 経過時間計、ESP-IDF の再起動の理由     |
| コンポーネント | 載っている記述子(`名前@版`・型の指紋)と、それぞれの状態(稼働・停止・失敗) | 結合の呼び出し(H1)・終える呼び出し(H8) |
| 待ち行列       | 接続ごとの長さと上限、`latest`・`drop` で捨てた数                         | 流量制御                               |
| 期限           | 期限切れで失敗を返した ask の数                                           | 期限の測定                             |
| 記憶           | 空き(内蔵・PSRAM)と、起動からの最小の空き                                 | ESP-IDF                                |
| 通信           | ルータとの繋がりの有無                                                    | zenoh-pico                             |

- **取りに行く形(問い合わせ)だけにする**のが、静かさ(第0章 0.6(静かさの構造化))に合う。周期的に送り出すと、誰も見ていない時にも回線と電力を使う。
- 数の項目は、起動からの累計にする。差を取るのは見る側である。動作環境は時点(システム時刻)を持たなくても答えられる(第6節(型と時間))。
- 中身の符号化は、コンポーネントの間と同じ正準形(ADR 0012 の決定4(正準形))にすれば、読む側の道具が一つで済む。
  ただし、その型を Shidzuku のデータ宣言(`record`・`choice`・`id`、ADR 0028)で書くかは別の問題である。動作環境は言語の記述対象外(第1章 1.6(動作環境は言語の記述対象外))だからである(論点4(状態の確認))。

## 5. プログラムのロード

ここが最大の変化になる。ADR 0012 の決定5(接合の方式)は、コンポーネントを1つ1プロセスとして動作環境と並置し、**障害境界=プロセス**とした。
**ESP32 にはプロセスが無い。** FreeRTOS のタスクは一つの番地空間を共有し、一つのタスクのパニックは機器全体を再起動する。
ロードの方式は、そのまま障害境界をどこに置くかの選択になる。

| 案                   | 何を載せるか                                                 | 障害境界       | ロードの単位               | 記憶                                | ADR 0012 との関係                                                                                                               |
| -------------------- | ------------------------------------------------------------ | -------------- | -------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 一体の書き込み       | 動作環境と Rust のコンポーネントを1つのイメージに焼く        | 機器           | イメージ全体。再起動を伴う | 小さい                              | Rust に限る同居(ADR 0012 の決定5(接合の方式))そのもの。ESP-IDF の OTA(区画2面と巻き戻し)を使う                                  |
| WASM でのロード      | コンポーネントを wasm32 に落とし、動作環境(WAMR)がホストする | コンポーネント | コンポーネント             | 線形記憶が 64KiB 単位。PSRAM が要る | ADR 0012 の論点3(接合の方式)で「中」とした WASM。「IO は借り物」は、IO が 接合面の8つの呼び出し(H1〜H8)だけなので欠点にならない |
| ネイティブの動的読込 | コンポーネントの機械語を実行中に読み込む(ELF の読込器)       | 機器           | コンポーネント             | 小さい                              | 暴走が動作環境を巻き込む。捨てた「埋め込み」と同じ弱さを持つ                                                                    |
| スクリプトの処理系   | MicroPython・Lua 等                                          | 処理系による   | コンポーネント             | 中                                  | トランスパイル先の言語に無い。範囲外                                                                                            |

### 5.1 一体の書き込み

- 最も小さく、道具も揃っている。ロードは「イメージを送る → 空いている区画に書く → 再起動 → 起動に失敗したら前の区画に戻る」である。
- ただし、**障害境界が機器に下がる**。1つのコンポーネントのパニックが、同じ機器の全てのコンポーネントを巻き込む。
  フローに「Normalizer は再起動する」と書いても、実際には同じ機器の Aggregator も再起動される。障害が伝播しない事(第0章 0.2(解決したい問題))が、機器の内側で崩れる。
- これを避ける最も簡単な規則は、**1機器に1コンポーネント**である。そうすれば コンポーネント=機器=障害境界=配置単位となり、四位一体(第0章 0.4(コンポーネント — 四位一体))はそのまま保たれる。
  ESP32 は安く、「コンポーネントごとに1台」は現実的な選択肢である。

### 5.2 WASM でのロード

- WAMR(WebAssembly Micro Runtime)は ESP-IDF の部品として Espressif から配られ、ESP32・S3・C3・C6 に対応する。
  wasm の線形記憶は隔離されており、トラップは動作環境が捕まえられる。**1台に複数のコンポーネントを載せても、障害境界はコンポーネントに残る**。
- 接合面の8つの呼び出し(H1〜H8)は、wasm の import(コンポーネント → 環境)と export(環境 → コンポーネント)に写る。
  ADR 0012 の決定5(接合の方式)は「ローカル接合面と直接結合の二つで同じ接合面の8つの呼び出し(H1〜H8)が成立する事が、接合面が本物である事の最初の試験」としている。**wasm の import と export は三つ目の実現手段**になる。
- 同じ `.wasm` は PC の動作環境でも動く。**同じ出力を PC と ESP32 で動かして振る舞いを比べる**事は、混在の適合試験(ADR 0012 の決定10(実装の順序と接合面の凍結))と同じ形の試験になる。
- 代わりに記憶が重い。線形記憶は 64KiB を単位に取るため、PSRAM の無い品種では載るコンポーネントの数が限られる。インタプリタの速さも問題になり得る(WAMR は AOT の翻訳も持つ)。

### 5.3 ロードの手順

どちらの案でも、ロードの入口は結合の呼び出し(H1。記述子を渡して繋がる)である。

1. 送る — 記述子、本体(イメージか `.wasm`)、本体のハッシュ
2. 照らす — 記述子を動作環境の能力(論点2(能力と拒否))に照らす。durable・recoverable・照合器(`collator`)・記憶の見積もりを見て、持たない物が要るなら理由を付けて拒む
3. 書く — フラッシュに書き、ハッシュを確かめる
4. 起こす — 一体の書き込みは再起動、WASM でのロードはインスタンスを作る
5. 答える — 載った記述子を返す。以後は状態の確認(第4節(状態の確認))に現れる

**「管理機能を使わない」事と「誰でも載せられる」事は別である。** 回線の上の誰でもコードを載せられる機器は、最小であっても置けない。
本体の署名と、その確かめ方を最小の動作環境に含めるかは論点5(ロードの認証)に残す。

## 6. 型と時間 — ESP32 で変わる物

- **正準形は変わらない。** 正準形は Shidzuku の型だけで決まり、出力言語の値の表現にも機器にも依らない(ADR 0012 の決定4(正準形))。32 ビットの機器である事は表に現れない。
- **`float64` はソフトウェアで計算する。** ESP32・S3 の演算器は単精度だけで、C3・C6 には演算器が無い。
  ソフトウェアの計算は決定的であり、strict IEEE で結果を一致させる要件(ADR 0021)は満たせる。問題は速さだけである。
  単精度の演算器で `float32` を計算する時は、積和の融合(FMA)を生成しない事を確かめる必要がある(ADR 0021 は融合を禁じている)。
- **`int64`・`int128`・`dec` もソフトウェアで計算する。** 意味は変わらない。
- **`時点` は起動しただけでは決まらない。** ESP32 は電源を入れた時にシステム時刻を知らない。時刻の同期(SNTP 等)か、相手から受け取るまでは `時点` の値を作れない。
  これは外部との境界(U12)のうち、外部の時刻の扱いへの入力である。期限と再送の間隔は経過時間計(ESP-IDF の高分解能時計)で測るため、システム時刻が無くても困らない(ADR 0019: 経過時間計は動作環境の内側)。
- **照合器(`collator`)は載らない。** ロケールごとの照合の表は、最小の機器には大きすぎる。`collator` を宣言したコンポーネントは、能力で拒む対象になる。

## 7. 題材を載せてみる

### 7.1 思考実験 02 — センサー収集パイプライン

[思考実験 02](02-センサー収集パイプライン.md)の接続は全て transient で、`pressure` は `block` と `latest` である。durable も recoverable も使わない。

| コンポーネント | 使う物                             | 最小の動作環境に載るか                                                    |
| -------------- | ---------------------------------- | ------------------------------------------------------------------------- |
| SensorIntake   | flow の送出                        | 載る                                                                      |
| Normalizer     | flow の受け口と送出                | 載る                                                                      |
| Aggregator     | flow、集約の窓(再起動で失ってよい) | 載る                                                                      |
| MetricStore    | 時系列 DB(外部)                    | 意味の上では載るが、外部の DB に届く手段が機器側に要る(外部との境界、U12) |
| Alerter        | 通知基盤(外部)                     | 同上                                                                      |

- **意味の上では全てが載る**。ESP32 の最小の動作環境は、flow だけの流れの系に向いている。
- 気づいた事が一つある。思考実験 02 では、センサー機器群は `external`(外部システム)である。SensorIntake を ESP32 の上に置くと、
  **機器はシステムの内側に入り、外部は機器に繋がったセンサー素子(I2C 等の先)になる**。境界の位置が、配置によって一段内側へ動く。
  これは配置が設計を動かさないとする ADR 0015 と擦れるように見えるが、実際には**別の設計**である——どちらを書くかは記述者が選び、選んだ方がシステムの境界の宣言に現れる。
  素子との境目は、境界の役割(ADR 0013)を持つ層が担う。外部との境界(U12)への入力とする。

### 7.2 思考実験 04 — 分散 KV ストア

| コンポーネント | 使う物                                     | 最小の動作環境に載るか                         |
| -------------- | ------------------------------------------ | ---------------------------------------------- |
| ClientGate     | ask の受け口と送出                         | 載る                                           |
| KVCore         | durable な flow の送出、recoverable な状態 | 載らない(durable と、復元元を読む呼び出し(H7)) |
| Persister      | durable な flow の受け口、idempotent       | 載らない(durable)                              |

- 最小の言語実装(Phase 1)の第1段の題材(思考実験 04(分散 KV ストア))は、**ESP32 の最小の動作環境には載らない**。第1段は PC の動作環境で行い、ESP32 は第2段の思考実験 02(センサー収集パイプライン)から載せる事になる。
- 能力で拒む仕組み(5.3 の手順2)は、この表をそのまま機械が出す物である。どのコンポーネントがどの機器に載るかが、記述子から読める。

## 8. 論点

### 論点1: ESP32 の動作環境は、動作環境の2つ目の実装になるか

ADR 0012 の決定1(動作環境の言語)は「動作環境は Rust の1実装」とし、意味を一箇所に置く事を最も重く見た。
ESP32 の動作環境は、通信の下(Rust の Zenoh か zenoh-pico か)とロードの手段(プロセスか、イメージか、wasm か)が PC と違う。

- 案として、**意味の核を標準ライブラリに依らない1つのクレートにし、PC と ESP32 の両方が使う**形が考えられる。
  核に置くのは期限の判定・待ち行列と `pressure`・記述子の照合と能力の判定・`on failure` の規則であり、違いは通信とロードの差し込み口だけにする。
  そうすれば意味は1箇所のまま、実装の器が2つになる。
- ADR 0012 の「将来の変更想定」は、組込みの帯に動作環境の縮小版が要る時期を、最小の分散動作環境(Phase 2)の実測で判断するとし、「C をトランスパイル先に足す判断と同時に来る」としていた。
  本実験では、**C を足さなくても Rust の出力だけで ESP32 に載る**事が分かった。前提の後半が外れるため、ADR 0012 の改訂の要否を判断する必要がある。

- **決定(2026-09-30)**: 意味の核を標準ライブラリに依らない1つのクレートにし、PC と ESP32 の両方が使う。ADR 0012 は改訂せず、[ADR 0029](../decisions/0029-最小の動作環境.md)を起票した(決定1・決定2)

### 論点2: 動作環境の能力を宣言し、ロードで拒むか

- 最小の動作環境は、持たない意味(durable・recoverable・`collator`・版の交渉)を**弱めずに拒む**(第1節(責務の分け))。そのために、動作環境が持つ能力の一覧を持ち、記述子と照らす。
- 拒む時期は、ロードの時(本実験)と、配置の設定の時(Phase 2)の二つがあり得る。配置の設定で先に分かる方が驚きは少ない。
- どちらも言語には入れない。配置は言語の記述対象外であり(ADR 0015)、能力は動作環境の側の事実だからである。
- recoverable の復元元が別のノード(PC)にある場合、再生は通信だけで取り寄せられる可能性がある。その時は recoverable を拒まずに済む。durable の送り手になる事とは分けて考える。

- **決定(2026-09-30)**: 能力は動作環境が宣言し、**配置の設定の時に拒む**([ADR 0029](../decisions/0029-最小の動作環境.md)の決定3(能力と配置の設定))

### 論点3: ロードの方式と障害境界 — 一体の書き込みか WASM でのロードか

- 一体の書き込みは小さいが、障害境界が機器に下がる。**1機器1コンポーネントを規則にする**なら四位一体は保たれる。
- WASM でのロードは障害境界をコンポーネントに残し、接合面の三つ目の実現手段として試験の価値も持つが、記憶が重く PSRAM を要する。
- 段を踏むなら、一体の書き込みと1機器1コンポーネントで始め、1台に複数を載せたくなった時に WASM でのロードを足す順が考えられる。
- どちらの案でも、ESP32 に載るのは Rust の出力だけである。TypeScript の出力は載らない。混在の適合試験は、機器を跨いで(ESP32 の Rust と PC の TypeScript で)行う事になる。

- **決定(2026-09-30)**: 段を踏む。一体の書き込みと1機器1コンポーネントで始め、1台に複数を載せたくなった時に WASM でのロードを足す([ADR 0029](../decisions/0029-最小の動作環境.md)の決定4(ロードの段))

### 論点4: 状態の確認の中身を、Shidzuku のデータ宣言で書くか

- 書けば、状態の確認の読み手は Shidzuku の道具で読め、正準形も揃う。動作環境の版と共に型の指紋も持てる。
- ただし動作環境(Container)は言語の記述対象外である(第1章 1.6(動作環境は言語の記述対象外))。動作環境が公開する型だけを言語で書く事は、その線引きに例外を作る。
  言語の組み込みのデータ宣言(例えば `record 動作環境の状態`)にするか、動作環境の文書に置くかの判断が要る。最小の分散動作環境(Phase 2)の配置の設定の形式と同じ所で決まる。

- **決定(2026-09-30)**: 第10節(状態の確認の調べ)で調べた結果、Shidzuku のコードが状態の確認を読む必要は無い。組み込みのデータ型は提供しない([ADR 0029](../decisions/0029-最小の動作環境.md)の決定5(状態の確認))

### 論点5: ロードの認証を最小の動作環境に含めるか

- 「管理機能を使わない」に署名の検査まで含めると、回線の上の誰でもコードを載せられる機器になる。
- 最小の案は、焼き込んだ公開鍵で本体の署名を確かめる事だけを持つ形である。鍵の配布や失効は管理であり、持たない。
- 一体の書き込みなら ESP32 のセキュアブートが同じ役を担える。WASM でのロードは動作環境の側で確かめる事になる。

- **決定(2026-09-30)**: ロードの認証を最小の動作環境に含める。一体の書き込みは ESP32 のセキュアブートが担い、WASM でのロードは動作環境の側で確かめる([ADR 0029](../decisions/0029-最小の動作環境.md)の決定6(ロードの認証))

### 論点6: この検討をどのフェーズに置くか

- 最小の言語実装(Phase 1)の動作環境は、Raft も複製も要らない(計画書の第1節(フェーズ計画))。**最小の動作環境と、最小の言語実装(Phase 1)が要る動作環境は、durable と recoverable を除けばほぼ同じ物**である。
- 一方で、最小の言語実装(Phase 1)の第1段の題材(思考実験 04(分散 KV ストア))は durable と recoverable を使うため、ESP32 では試せない(第7節(題材を載せてみる))。
- 現在は言語仕様(Phase 0)の段であり、runtime/ への実装は仕様の裏付けができてから行う。本実験が示すのは、最小の分散動作環境(Phase 2)の最初の成果物の候補として、
  **「PC 1台+ ESP32 1台で、思考実験 02 の上流(SensorIntake・Normalizer)を ESP32 に載せる」**形があり得る事である。
  Raft を持たない分散の最小形であり、ノードを跨いだ `pressure` と障害の非伝播を実機で見られる。

- **決定(2026-09-30)**: 最小の分散動作環境(Phase 2)に置く([ADR 0029](../decisions/0029-最小の動作環境.md)の決定7(フェーズの位置))

## 9. 所見

- 最小の動作環境に要るのは、見込みの三つ(通信・状態の確認・ロード)に、**意味の最小限(期限・上限付きの待ち行列・再起動)**を足した物である。後の三つは管理ではなく、ask と flow の約束である。
- 外すのは管理だけではない。durable・recoverable・`collator` の意味も外れる。**外し方は、弱めずに拒む**である。弱めると同じ語が動作環境によって違う物を指す。
- 最大の変化は、**障害境界がプロセスから離れる**事である。一体の書き込みなら機器に、WASM ならコンポーネントに置き直す事になる。
- ESP32 には Rust の出力だけで載り、C をトランスパイル先に足す必要は無い。これは ADR 0012 の「将来の変更想定」の前提の一つを外す。
- 題材では、思考実験 02(flow だけの系)が載り、思考実験 04(durable と recoverable を使う系)は載らない。

## 10. 状態の確認の調べ — 状態の確認を Shidzuku のコードが読む必要があるか

suzukimitsuru の見立ては「状態の確認の中身は、動作環境が判断して再起動や再配置を行うための物だけに見える」である。
第4節(状態の確認)の項目ごとに、**誰がそれを見て判断するか**と、**コンポーネントのコードが読む必要があるか**を確かめた。

| 項目                 | 見て判断する者                                       | コードが読む必要 | 理由                                                                                                                                               |
| -------------------- | ---------------------------------------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 動作環境の版・能力   | 配置の設定の検査(ADR 0029 の決定3(能力と配置の設定)) | 無い             | コードが読めば、配置によって振る舞いが変わる。配置が変わってもコードは変わらない(ADR 0015)                                                         |
| 起動・再起動の理由   | 監督と運用者                                         | 無い             | 再起動を跨ぐ扱いは `state`(volatile / recoverable)の宣言が決めている                                                                               |
| コンポーネントの状態 | 監督(`on failure`)                                   | 無い             | 相手の障害は、ask の失敗としてコードに届く(第4章 4.1(二つの通信方式)。失敗の体系(U13)では、系の失敗をフローが翻訳する形(思考実験 25 の F-4)を採る) |
| 待ち行列             | 流量制御(`pressure` の宣言)                          | 無い             | 長さを見て分岐すると、宣言の外に二つ目の流量制御が生まれる。背圧は宣言で決まっている                                                               |
| 期限                 | 運用者                                               | 無い             | 一つ一つの期限切れは、ask の失敗としてコードに届く。数は運用の関心である                                                                           |
| 記憶                 | 監督と配置の設定                                     | 無い             | 足りるかは配置の設定で先に確かめる(ADR 0029 の決定3(能力と配置の設定))。実行中に足りなくなれば、それは障害である                                   |
| 通信                 | 動作環境                                             | 無い             | 相手に届かない事は ask の失敗として、flow では配達保証の宣言として現れる                                                                           |

- **どの項目も、コードが知るべき事は既に別の形で届いている。** 相手の障害と期限切れは ask の失敗として、背圧は `pressure` の宣言として、再起動は `state` の宣言として。
  状態の確認を読ませると、同じ事実が二つの道でコードに届き、どちらで判断するかが記述から読めなくなる。
- **前例がある。** ADR 0012 の決定2(責務の分担)は、経過時間計の読みを動作環境の内側で完結させ、言語の型にも接合面にも出さなかった(ADR 0019)。
  期限を測る道具をコードに渡さなかったのと同じ理由で、期限を測った結果もコードに渡さない。
- **接合面が広がる。** 読ませるには、コンポーネントから動作環境へ問う9つ目の呼び出しが要る。接合面は狭い公開面の原則に従う(ADR 0012 の決定3(接合面))。
- **結合が強くなる。** 組み込みのデータ型にすると、全てのプログラムが動作環境の版と結び付く。動作環境は最小の分散動作環境(Phase 2)以降も変わり続けるため、
  変動性の高い相手とのモデル結合になる(ADR 0024 の物差し)。
- **例外の候補は、運用を監視する系を Shidzuku で書く場合である。** その時、状態の確認は系の外にある物であり、`external`(外部システム)として境界の役割(ADR 0013)の層で読む。
  型はその系が自分のデータ宣言で書く。外部との境界の記述(U12)に従えばよく、組み込みの型は要らない。

結論として、**Shidzuku のコードが状態の確認を読む必要は無く、組み込みのデータ型は提供しない。**
状態の確認は動作環境と、配置・監督・運用の道具のための物とする。中身は動作環境の文書に置き、符号化は正準形(ADR 0012 の決定4(正準形))にして道具を揃える。

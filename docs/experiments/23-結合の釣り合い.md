# 思考実験 23: 結合の釣り合い — 既存の記述を強度・距離・変動性で読み直す

- 状態: Draft
- 日付: 2026-09-26
- 目的: Vlad Khononov『ソフトウェア設計の結合バランス』(*Balancing Coupling in Software Design*)の三つの軸で既存の思考実験を読み直す。
  Shidzuku の構造がどの軸を既に持ち、どの軸を持たないかを確かめ、U14 論点1・2(`data` の可視範囲と帰属)と U7(粒度の指針)への入力を得る
- 経緯: 仕様は John Ousterhout『A Philosophy of Software Design』(以下 APoSD)の深いモジュールと、Parnas の情報隠蔽を系譜に挙げている(第0章 0.9)。
  しかし結合の釣り合いについての知見は参照していない。APoSD が問うのは**一つのモジュールの形**(深さ)であり、
  結合バランスが問うのは**モジュールの間の関係**(強さと遠さ)である。
  Shidzuku の制約層(`depends`・`expose`・`contains`)は後者を記述する層なので、物差しが欠けていないかを確かめる
- 進め方: 新しい系は書かない。思考実験 01・02・08・20・21 の記述を三軸の表に写す。
  書き直しはせず、書かれた時点の語で読む(計画書 7.6 と同じ方針)

## 1. 物差し — 三つの軸を Shidzuku の語に写す

### 1.1 統合の強度

二つの部品の間で**どれだけの知識が共有されるか**である。Khononov は強い順に4段に分ける。

| 強度(強い順) | 共有される知識                         | Shidzuku で現れる形                                                            | 言語の扱い                                                        |
| ------------ | -------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| 侵入結合     | 相手が公開していない内部               | 相手の内側のコンポーネントを指す。共有メモリ・直接呼び出し                     | **書けない**(E0018-4、第4章 4.1)                                  |
| 機能結合     | 同じ業務の手順、または一つの仕事の分担 | 一つの仕事を複数の接続で分担する。補償の手順を呼び手が知る                     | `correlate` の分は宣言する(ADR 0023)。`on failure` の散文は見ない |
| モデル結合   | 同じ業務モデル                         | 同じ `data` を複数の公開面が使う                                               | **宣言されない**。`data` はプログラム全体に属する(ADR 0009)       |
| 契約結合     | 統合のためだけに作った型               | 公開面のためだけの `data`。境界の層(`boundary`・`parse`・`format`)での詰め替え | 型の一致を名前で検査する(E0009-1)                                 |

### 1.2 距離

二つの部品が**どれだけ離れているか**である。離れているほど、両方を同時に変える費用が高い。
Shidzuku では `contains` の木が距離を与える。

| 距離(近い順)       | Shidzuku での形                                     | 通信の可否                         |
| ------------------ | --------------------------------------------------- | ---------------------------------- |
| 同じコンポーネント | 内部階層の層どうし                                  | 通信ではない(層の向き E0013-4)     |
| 兄弟               | 同じ `contains` にある                              | 相手の `expose` を通る             |
| 親の兄弟           | 親と同じ `contains` にある。親の `depends` に現れる | 同上                               |
| 遠い枝             | 最も近い共通の親が二段以上上にある                  | 直接は呼べない。型でだけ繋がり得る |
| 記述の外           | `external`、または `actor` への公開面               | 境界の層だけが授受する             |

**Shidzuku ではコンポーネントの間の最短距離が既に遠い。** 1コンポーネントは1プロセスであり(ADR 0012)、
兄弟であっても通信はプロセスの境界を越える。近い距離は、1つのコンポーネントの中の層にしか無い。

### 1.3 変動性

部品が**どれだけ頻繁に変わるか**である。Khononov は業務の区分(中核・支援・汎用)から見積もる。
Shidzuku に区分の語彙は無く、intent の `change`(将来どう変わると想定するか)が唯一の置き場である。

### 1.4 釣り合いの規則

強度と距離が**逆向きなら釣り合う**。強く結ぶ物は近くに置き、遠くに置く物は弱く結ぶ。

| 組合せ   | 近い                                 | 遠い                                               |
| -------- | ------------------------------------ | -------------------------------------------------- |
| 強く結ぶ | 釣り合う(凝集)                       | 釣り合わない。一つの変更が遠くまで届く(分散一枚岩) |
| 弱く結ぶ | 釣り合わない。無関係な物が近くに並ぶ | 釣り合う(疎結合)                                   |

釣り合わない組でも、**変わらない物どうしなら害は小さい**。したがって変動性は、不釣り合いを直す順番を決める。

## 2. 既存の記述を読み直す

### 2.1 思考実験 01 — 注文管理

| 結合                                           | 強度             | 距離 | 変動性(`change`)                   | 判定                     |
| ---------------------------------------------- | ---------------- | ---- | ---------------------------------- | ------------------------ |
| OrderIntake → Inventory `ask 引当(品目, 数量)` | 契約             | 兄弟 | 複数倉庫への分割。公開面は変えない | 釣り合う                 |
| OrderIntake → OrderStore `ask 保存(注文)`      | モデル(`注文`)   | 兄弟 | イベントソーシングへの移行         | 釣り合う                 |
| `on failure OrderStore` で OrderIntake が解放  | 機能(引当の寿命) | 兄弟 | —                                  | 近いので許せるが見えない |
| OrderIntake と HTTP・JSON                      | 契約(境界の層)   | 外   | gRPC の追加                        | 釣り合う                 |

01 は全ての結合が兄弟の距離に収まり、釣り合っている。
唯一の機能結合(保存に失敗したら引当を戻す)は散文にあり、思考実験 21 の論点1・2 と同じ穴である。

### 2.2 思考実験 02 — センサー収集パイプライン

```plaintext
SensorIntake ─計測値─▶ Normalizer ─正規化済み計測値─▶ Aggregator ─集約値─┬▶ MetricStore
                                                                           └▶ Alerter
```

- **一歩ごとに型が変わる**。計測値・正規化済み計測値・集約値は、それぞれの接続のための型であり、契約結合に近い。
  型が隣の兄弟の間でしか共有されず、下流は機種を知らない。
- `集約値` だけは三者(Aggregator・MetricStore・Alerter)が共有するモデル結合である。三者とも兄弟なので釣り合う。
- **分割の理由が変動性で書かれている。** Normalizer の `rejected` は「集約の知識と機種の知識は変更の理由が異なり、
  機種追加の度に集約を触る事になるため」である。ADR 0006 はこの分割を「why が2文になった」事で説明したが、
  書き手が実際に使った理屈は**変わる理由が違う**だった。

### 2.3 思考実験 08 — 多言語商品カタログ検索

`商品の見出し` という一つの型が、次の5か所に現れる。

| 現れる所                                       | 役目                   | 距離(ProductIndex から) |
| ---------------------------------------------- | ---------------------- | ----------------------- |
| CatalogSync → ProductIndex `flow 商品の見出し` | 原簿から取り込んだ内容 | 兄弟                    |
| ProductIndex `expose 原簿更新(商品の見出し)`   | 索引の更新の単位       | —                       |
| TranslationStore `expose 見出し(…)`            | 訳文の保管の単位       | 兄弟                    |
| SearchGate `expose 検索(…) -> 列<…>`           | 検索の応答             | 兄弟                    |
| system `expose 検索(…) -> 列<…>`               | 買い物客への応答       | **記述の外(actor)**     |

一つのモデルが、取込・索引・訳文・応答を兼ね、**系の外の人への公開面にまで届いている**。強いモデル結合を最も遠い距離で張っている形である。

変動性も記述の中に書かれている。system の `rejected` は原簿を外に置く理由を
「原簿は仕入・価格改定・改廃など検索以外の系からも動く」としている。
原簿に欄が一つ増えれば `商品の見出し` が変わり、買い物客への応答も変わる。**強い・遠い・よく変わる**の三つが揃っている。

今の語彙でも直せる。取込には `原簿の断片`(既に system の受け口にある)、内側には `商品の見出し`、
公開には `検索の応答` と、型を三つに分ければよい。
**書けない事は無いが、言語は何も知らせない。** `data` がプログラム全体に属するため、
一つの型が内側と外側の両方で使われている事は、どの宣言からも読めない。

### 2.4 思考実験 20・21 — 入れ子を跨ぐ

```plaintext
system 通販        contains Frontdesk, 注文管理
system 注文管理    contains OrderIntake, Inventory, OrderStore, PaymentBridge
```

| 結合                                                   | 強度           | 距離                         | 判定                            |
| ------------------------------------------------------ | -------------- | ---------------------------- | ------------------------------- |
| `注文` を通販の `expose`・Frontdesk・OrderStore が使う | モデル         | actor から入れ子の二段目まで | 釣り合わない(08 と同じ形)       |
| `correlate 受注番号 : 受注 -> 受注の状態`              | 機能(宣言済み) | Frontdesk ↔ 注文管理(兄弟)   | 釣り合う                        |
| `correlate 引当番号`(引当と解放)                       | 機能(宣言済み) | 注文管理の内側(兄弟)         | 釣り合う                        |
| PaymentBridge ↔ 決済代行                               | 契約(境界の層) | 記述の外                     | 釣り合う。ただし `depends none` |

- **ADR 0023 は機能結合の距離を既に制限している。** 決定7(相関のある通信は同じ `flow` 宣言に置く)は、
  最も強い宣言可能な結合を一つの宣言の中に閉じ込める。決定2(鍵は接続の対ごと)により、内側の `引当番号` は注文管理の外へ出ない。
  **強い物を近くに置く**規則が、結合の語彙を使わずに書かれていた。
- `注文` は 08 の `商品の見出し` と同じ形である。システムの境界(E0018-4)はコンポーネントを隠すが、**型は隠さない**。

## 3. 分かった事

### 3.1 強度 — 侵入は禁じ、契約は促し、モデル結合だけが見えない

侵入結合は書けない(E0018-4・共有メモリ無し)。契約結合は境界の層と名前的型付けが促す。
機能結合のうち `correlate` の分は宣言される。
**モデル結合だけが、どの宣言にも現れない。** `data` の参照は依存ではないという ADR 0009 の立場(計画書 5.2)が、そのまま盲点になっている。

### 3.2 距離 — 木から機械的に求まるが、型は測られない

コンポーネント間の距離は `contains` の木から求まる。同じ事が型にも言える。
ある `data` を使う公開面を全て集め、その持ち主の**最も近い共通の親**を取れば、それが型の**届く範囲**である。

| 型               | 使う所                                     | 届く範囲                                |
| ---------------- | ------------------------------------------ | --------------------------------------- |
| 集約値(02)       | Aggregator・MetricStore・Alerter           | 1つのシステムの中(兄弟)                 |
| 商品の見出し(08) | 4コンポーネントと system の `expose`       | **ルートの外(actor)まで**               |
| 注文(20)         | 通販の `expose`・Frontdesk・注文管理の内側 | **ルートの外(actor)から入れ子の二段目** |
| 引当番号(21)     | Inventory・OrderStore                      | 注文管理の中(兄弟)                      |

届く範囲は今の構文からも計算できるが、言語はそれを使っていない。

### 3.3 変動性 — 既に書かれているが、機械は読まない

思考実験 01〜04・08 の `rejected` の理由のうち、**12件が変動性の論証**だった
(「変更の理由が異なり」4件、「変更が全ユニットに波及する」8件)。
書き手は分割の判断を、隠す知識の数よりも**変わる理由の違い**で説明している。
一方、`change` 欄は自由文であり(ADR 0003)、比べる仕組みは無い。

### 3.4 粒度(U7)への含意

ADR 0006 の基準「隠す設計判断が1つ」は APoSD と Parnas から来ており、**一つのコンポーネントの中**を見ている。
結合の見方を足すと、**二つのコンポーネントの間**を見るシグナルが得られる。

- 分割: why は1文でも、`change` が**変わる理由の違う**二つの変化を挙げる(02 の Normalizer と Aggregator が分かれた理屈)。
- 統合: 二つのコンポーネントが公開面の型をほとんど共有し、`change` が**同じ変化**を挙げる。
  兄弟であってもプロセスの境界を越えるため(1.2)、強い結合を払う理由が無い。
- 束ね方: システムの入れ子(ADR 0018)には束ねる基準が無い。**強く結ぶ物を同じ `contains` に置く**が基準の候補になる。

### 3.5 既定値は、言語との見えない結合である

APoSD はインターフェースを単純にする手段として既定値を勧める(よく使う場合を簡単にする)。
Shidzuku は ADR 0008 で既定値を全て捨てた。この二つは衝突しているように見える。

結合の見方では、既定値は**全ての記述と言語の既定の表とのモデル結合**である。
その相手は最も遠く(記述の外、言語の版)、変わり得る(Phase 1 の出力先が2言語、U16 の版の混在)。
既定の表が版で変われば、書かれていない箇所の意味が黙って変わる。**強い・遠い・変わり得る**の三つが揃う。
ADR 0008 の判断は、APoSD の「未知の未知を減らす」と結合バランスの両方から支えられる。この対比はまだどこにも記録されていない。

## 4. 案 — U14 論点1・2 への入力

計画書 6.2 の問題2(参照する側が何を書くか)と問題3(兄弟間を流れるデータの帰属に基準が無い)に、距離の見方を当てる。

### K-a: `data` は、使う相手の最も近い共通の親に属する

帰属の基準を距離で与える。3.2 の届く範囲が、そのまま置き場所になる。

- 参照する側は何も書かない(型の参照は依存ではない。ADR 0009 の立場を保つ)。届く範囲の外からの参照は検査で落とす。
- 名前空間を入れ子の経路にする案(計画書 6.3 の問題3)と向きが揃う。
- 08 の `商品の見出し` はルートに置くしかなくなり、**内側の型がルートに上がっている事**が記述から読める。

### K-b: プログラム全体のまま、届く範囲を知らせる

今の置き場所を変えず、届く範囲を計算して、図(U8)と警告で示す。

- 例: 内側のコンポーネントどうしで使う `data` が、システムの `expose` にもそのまま現れたら警告する(内側のモデルと外への契約の兼用)。
- 帰属の基準(問題3)には答えない。

### K-c: 何も足さない

不釣り合いの判断は書き手とレビューに任せる。

### 比較

| 観点                          | K-a                        | K-b          | K-c      |
| ----------------------------- | -------------------------- | ------------ | -------- |
| 問題3(帰属の基準)             | 答える                     | 答えない     | 答えない |
| 問題2(参照する側が書く物)     | 書かない。届く範囲で決まる | 書かない     | 書かない |
| 08・20 の不釣り合いが見えるか | 間接に(型がルートへ上がる) | 直接に(警告) | 見えない |
| 省略の禁止(ADR 0008)          | 整合する                   | 整合する     | 整合する |
| Phase 1 のパーサへの影響      | 名前の解決が木に沿う       | 無い         | 無い     |

K-a と K-b は排他ではない。K-a が帰属を決め、K-b の警告が不釣り合いを知らせる。
**本実験では決めない。** U14 はステップ4 の最後であり(計画書 4.3)、前倒ししない(規則 R3)。

## 5. 示唆

- **三軸のうち強度と距離は、Shidzuku の構造が既に持っている。** 侵入結合の禁止、境界の層による契約、`contains` の木、
  `correlate` の同じ宣言の制約は、どれも結合の語彙を使わずに釣り合いを保つ規則になっていた。
- **欠けているのは、モデル結合の距離と、変動性の機械可読性の二つである。**
- 変動性の機械可読性は**足さない**。`change` を構造化して比べる事は自然言語の内容に踏み込む(ADR 0003)。
  Khononov の釣り合いの数式のような定量化も、ADR 0006 が定量基準を捨てたのと同じ理由で採らない。
  変動性はレビューとシグナルの指針で扱う。
- モデル結合の距離は U14 で扱う(第4節)。
- 粒度の指針には、コンポーネントの間を見るシグナルを足せる(3.4)。
- APoSD と結合バランスのどこを取り込み、どこを取り込まないか(3.5 を含む)は、ADR 0007 と同じ形で決めておく値打ちがある。

## 6. 未解決課題への入力

- **U14(プログラムの宣言)**: 論点1・2 に K-a(帰属を届く範囲で決める)と K-b(届く範囲の警告)を当てる。計画書 第5節に入力として記した。
- **U7(粒度の指針)**: 変わる理由の違いによる分割、同じ変化と共有モデルによる統合、束ね方の基準。**ADR 0025 として起案した**。
- **全体(第0章 0.9)**: 系譜への結合バランスの追加と、既定値についての APoSD との対比。**ADR 0024 として起案した**。
- **U8(図と実装の一致)**: 型の届く範囲を図に載せるか。K-b を採るなら図が主な出口になる。
- **U12(外部世界との境界)**: PaymentBridge と決済代行の契約結合が `depends` に記録されない(思考実験 08 の論点3 と同じ穴)。

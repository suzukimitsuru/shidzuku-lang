# 思考実験 25: 系の失敗の書き分け — 三案を同じ系で書き比べる

- 状態: Draft
- 日付: 2026-09-27
  (改訂 2026-09-29: ADR 0028 の採用で `data` を `record`・`choice`・`id` に書き換えた)
- 目的: 思考実験 22 の論点1(系の失敗を公開面にどう書くか)の三案を、同じ系で書き下ろして費用を測る
- 経緯: 思考実験 22 で、`expose 受注(注文) -> 受注番号 | 受注不可` は二つしか返さないように読めるのに、
  第4章 4.1 は期限超過と相手障害でも失敗応答が返ると定めている事が分かった。**三つ目が型に現れていない。**
  案は F-1(書かない)・F-2(直和に並べる)・F-3(器を分ける)の三つを素描してあった
- 進め方: 同じ四つの公開面を三案それぞれで書き、**公開面の行・呼び手の分岐・失敗が増えた時の影響**を数える

## 1. 題材と測り方

思考実験 21 の受注の系から、公開面を四つ取る。

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可                    # OrderIntake
expose 取消(受注番号) -> 取消の結果                         # OrderIntake
expose 受注の照会(受注番号) -> 受注の状態 | 照会不可        # OrderStore
expose 引当(品目ID, uint32(0) 個) -> 引当の結果             # Inventory
```

系の失敗として扱うのは、思考実験 22 の E 群のうち `ask` に現れる二つ——**期限超過**と**相手障害**である。

測るのは五つ。

| 指標                  | 何を見るか                                                |
| --------------------- | --------------------------------------------------------- |
| 公開面の重さ          | 宣言に現れる語の数と、同じ語の重複                        |
| 呼び手の分岐          | 受け取った側が書く分岐の形                                |
| 省略の禁止(第0章 0.5) | 宣言を読むだけで、返る物が全て分かるか                    |
| 失敗が増えた時        | 言語が系の失敗を1つ足した時、既存の記述がどれだけ変わるか |
| 業務と系の混ざり      | 業務の語彙と系の語彙が、型の上で混ざるか                  |

## 2. F-1 — 書かない(系の失敗は全ての ask に暗黙で付く)

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可
expose 取消(受注番号) -> 取消の結果
expose 受注の照会(受注番号) -> 受注の状態 | 照会不可
expose 引当(品目ID, uint32(0) 個) -> 引当の結果
```

呼び手は、宣言に無い物を受け取る。

```plaintext
# Frontdesk の body(擬似)
受注(注文) の結果で分岐する:
  受注番号 なら ...
  受注不可 なら ...
  期限超過 なら ...      # 宣言に無いが来る
  相手障害 なら ...      # 同上
```

- **公開面は最も軽い。** 4本のままで、語は1つも増えない。
- **しかし「既定表という外部知識」が生まれる。** 第4章 4.1 を読んだ人だけが、三つ目・四つ目の分岐を書ける。
  これは ADR 0008(省略の禁止)が退けたものそのものである——
  「既定で補われる箇所は無く、フローは既定表という外部知識なしに読める」(第4章 4.2)。
- 呼び手が分岐を書き忘れても、宣言の上では何も欠けていない。**検査が根拠を持てない。**

## 3. F-2 — 直和に並べる

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可 | 期限超過 | 相手障害
expose 取消(受注番号) -> 取消の結果 | 期限超過 | 相手障害
expose 受注の照会(受注番号) -> 受注の状態 | 照会不可 | 期限超過 | 相手障害
expose 引当(品目ID, uint32(0) 個) -> 引当の結果 | 期限超過 | 相手障害
```

- **同じ二語が4本すべてに並ぶ**(8回の重複)。公開面を1つ足すたびに2語増える。
- 呼び手の分岐は F-1 と同じ形になるが、**宣言から読める**。省略の禁止は満たす。

書いてみて、二つの問題が出た。

### 問題1: 言語が区分名を持つ事になる — 7.4 の撤回と衝突する

`期限超過`・`相手障害` は、どの `choice` にも属さない区分である。言語が持つ区分名という事になる。
しかし計画書 第7節 7.4 は、**一般的な区分名を言語の組み込みにする案を撤回したまま確定**している。

> 「`なし`・`失敗`・`理由` のような一般的な区分名を言語の組み込みにする」案は、**文脈ごとに意味が違うため**撤回した。

`期限超過` は文脈ごとに意味が違わない(系の事情であって業務の語彙ではない)ため、撤回の理由がそのまま当たるわけではない。
しかし**同じ場所(直和の区分)に、言語の語と記述者の語が混ざる**事になる。
第6章 6.1 の「不在の区分名は、何が無いのかを言う」という指針は記述者の語に向けたものであり、ここで筋が二つになる。

### 問題2: 失敗が1つ増えると、全ての公開面が変わる

言語が系の失敗を1つ足した時(例: `投入不能`)、**全ての `ask` の公開面の型が変わる**。
公開面の変更は互換性の単位(コンポーネント記述子。ADR 0012)に響き、U16(版の混在)の対象になる。
**言語の都合による語の追加が、全コンポーネントの版を上げる。**

## 4. F-3 — 器を分ける

応答の型とは別に、系の失敗だけを受ける欄を公開面に持つ(`fails` は仮の語)。

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可 fails 期限超過 | 相手障害
expose 取消(受注番号) -> 取消の結果 fails 期限超過 | 相手障害
expose 受注の照会(受注番号) -> 受注の状態 | 照会不可 fails 期限超過 | 相手障害
expose 引当(品目ID, uint32(0) 個) -> 引当の結果 fails 期限超過 | 相手障害
```

- **業務と系が型の上で分かれる。** 呼び手は「業務の結果」と「系の失敗」を別の器として受け取る。
- 省略の禁止は満たす。`fails` の欄は必須であり、系の失敗が無い公開面は `fails none` と書く事になる。
- 重複は F-2 と同じ(4本に同じ二語)。ただし**並ぶ場所が業務の直和と分かれている**ため、読む時に混ざらない。
- 失敗が1つ増えた時の影響も F-2 と同じである。`fails` の欄の中身が変わり、公開面の型が変わる。
- 語が1つ増える(`fails`)。

書いてみると、`fails` の中身は**常に同じ**であった。四つとも `期限超過 | 相手障害` である。
系の失敗は相手や公開面によって変わらないためである。**記述者が毎回同じ物を書き写す欄になる。**

## 5. 三案の比較

| 指標              | F-1 書かない           | F-2 直和に並べる         | F-3 器を分ける                 |
| ----------------- | ---------------------- | ------------------------ | ------------------------------ |
| 公開面の語の増加  | 0                      | +8(4本×2語)              | +8 と欄の語 4                  |
| 呼び手の分岐      | 業務と系が混ざる       | 業務と系が混ざる         | 分かれる                       |
| 省略の禁止        | **満たさない**         | 満たす                   | 満たす                         |
| 失敗が1つ増えた時 | 影響なし               | **全公開面の型が変わる** | **全公開面の型が変わる**       |
| 業務と系の混ざり  | 呼び手の body で混ざる | 型で混ざる               | 分かれる                       |
| 言語が持つ区分名  | 暗黙に持つ             | **7.4 の撤回と擦れる**   | 欄の語彙として持つ(擦れは弱い) |
| 増える語          | 0                      | 2                        | 3(`fails` と二つの区分)        |

**どれも決め手に欠ける。** F-1 は省略の禁止に反し、F-2・F-3 は「常に同じ物を書き写す」上に、
言語が語を1つ足すだけで全コンポーネントの版が上がる。

## 6. 書いている途中で出てきた第四の形 — フローが翻訳する

三案を並べて眺めていて、**呼び手が系の失敗を受け取る必要が本当にあるのか**という問いが出た。

第4章 4.5 は `on failure` にこう書ける事を既に定めている。

> 埋め合わせの種類: 補償(引当の解放等)、**代替応答**(受付不可を返す等)、再起動(Let it crash)。

思考実験 21 で書いた記述も、実はそうなっていた。

```plaintext
on failure Inventory  : OrderIntake は受注不可を返す(伝播しない)
on failure OrderStore : OrderIntake は引当を解放し、受注不可を返す(伝播しない)
```

**`Inventory` が期限超過で応えなかった時、`OrderIntake` が呼び手へ返すのは `受注不可` である。**
系の失敗は `OrderIntake` の中で止まり、業務の語彙に翻訳されている。

### F-4: 系の失敗を公開面に書かず、フローが業務の語彙へ翻訳する

```plaintext
# 公開面は業務だけ(F-1 と同じ4行)
expose 受注(注文) -> 受注番号 | 受注不可

# フローが、接続ごとに「系の失敗が起きたら呼び手に何を返すか」を型で書く
flow 受注処理 {
  intent { ... }
  OrderIntake -> Inventory  : ask 引当(品目ID, 数量) deadline 100 ミリ秒 -> 引当の結果
  OrderIntake -> OrderStore : ask 保存(注文, 引当番号) deadline 200 ミリ秒 -> 保存の結果
  correlate 引当番号 : 引当 -> 保存
  on failure Inventory  : OrderIntake は 受注不可(受付停止中) を返す
  on failure OrderStore : OrderIntake は 引当の解放 を行い、受注不可(受付停止中) を返す
}
```

- **公開面は業務の語彙だけで閉じる。** 系の語彙は一つも現れない。
- **省略の禁止は既に満たされている。** `on failure` はフローに参加する全コンポーネントについて必須である(E0008-1)。
  記述者は「系の失敗が起きた時に何を返すか」を、**既にある欄**で書いている。
- **翻訳の結果は検査できる。** `on failure` に書いた代替応答の型が、呼び手の公開面の応答に含まれるかを見ればよい。
  今は散文なので見られない——思考実験 21 の論点1・2(補償が散文になる)と**同じ穴で塞がる**。
- **失敗が1つ増えても、公開面は変わらない。** 増えるのは実行系が検出する事象であり、記述は `on failure` の側で吸収する。

### F-4 で書けなくなる事

- **呼び手が失敗の種類で分岐できない。** 「期限超過なら再試行、相手障害なら諦める」は書けない。
  再試行は接続の属性(第4章 4.6 の未定事項)へ移す事になる。**判断の置き場が body から接続へ動く。**
- **翻訳できない場合がある。** 返すべき業務の区分が無い時、記述者は公開面に区分を足す事になる
  (`受注不可 = 在庫なし | 受付停止中 | 受け付けられなかった`)。
  これは面倒に見えるが、**第6章 6.1 の「不在の区分名は、何が無いのかを言う」に沿う**——
  客に見せるのは「期限超過」ではなく「受け付けられなかった」である。
- **全ての `ask` がフローに現れている必要がある。** 現在の仕様に、その要求は無い。
  `depends`・`expose` の整合(E0000-2・E0000-3)は見るが、**「使っている接続がどのフローにも書かれていない」を見る検査が無い**。
  F-4 を採るなら、この検査が要る。

## 7. 示唆

- **F-2 と F-3 は採らない。** 「常に同じ物を書き写す」記述が全公開面に並び、
  言語が語を1つ足すだけで全コンポーネントの版が上がる(U16)。得るものに対して代価が大きい。
- **F-1 も採らない。** 省略の禁止に反し、検査が根拠を持てない。
- **F-4 を推す。** 公開面は業務の語彙で閉じ、系の失敗はフローが翻訳する。
  新しい語を増やさず、既にある必須の欄(`on failure`)を型の付いた形に変えるだけである。
- ただし F-4 は二つの前提を要求する。
  1. `on failure` の欄が**型の付いた記述**を取れる事(思考実験 21 の S-a と同じ変更)。
  2. **全ての接続がどれかのフローに現れる**事(新しい検査)。
- 思考実験 22 の論点3(再試行で変わる失敗と変わらない失敗)は、F-4 では**接続の属性**の問題になる。
  呼び手の型の問題ではなくなる。U13 の中で、再試行の規定(第4章 4.6)と併せて決める。

## 8. 未解決課題への入力

- **U13(失敗の体系)**: 論点1 の答えとして F-4 を提案する。併せて、`on failure` の欄を型の付いた形にする
  (思考実験 21 の S-a)事が前提になる。**二つは同じ ADR で決めるのが筋である。**
- **U2・第4章 4.2**: 「全ての接続がどれかのフローに現れる」検査の要否。F-4 の前提である。
- **U16(版の混在)**: F-2・F-3 を採らない理由が、そのまま U16 への入力になる——
  **言語の語彙の追加が、コンポーネントの版を上げてはならない。**
- **U4(ログ規約)**: 翻訳された系の失敗を、運用はどう知るか。呼び手には業務の語彙しか届かないため、
  元の失敗はログにしか残らない。

## 9. 次の行動

- U13 の ADR を起案する。中身は (a) 系の失敗は公開面に書かない(F-4)、(b) `on failure` を型の付いた欄にする、
  (c) 全ての接続がフローに現れる事を要求する、の三つが軸になる
- 思考実験 22 の論点2(数値と解析の失敗の型)は、本実験では触れていない。F-4 は**通信の失敗**の話であり、
  演算の失敗は呼び手の body の中で起きる。別に測る必要がある
- 論点4(待ちに期限を与える場所)も残っている。F-4 は「返らない」事を解かない——
  期限を過ぎた事を誰が検出するかは、U13 の四つ目の問いのままである

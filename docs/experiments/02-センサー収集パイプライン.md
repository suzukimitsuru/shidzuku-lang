# 思考実験 02: センサー収集パイプライン(ストリーム処理)

- 状態: Draft
- 日付: 2026-08-19
- 目的: U2(非同期メッセージ・バックプレッシャ)の実地検証。副次的に U3(内部階層)・U7(粒度)の再検証、U1(意図テンプレート)の適用範囲確認
- 進め方: 計画書の検証方法に従い、既存の小さなシステムを Shidzuku で記述してみる。書けない事があれば仕様に戻す。思考実験 01 が request-reply 中心だったため、本実験は非同期ストリーム中心の系を選ぶ

## 1. 対象システム

よくあるセンサーデータ収集の最小構成。

- 多数のセンサー機器が計測値を送ってくる(機器側プロトコルは MQTT を想定)
- 機種ごとの癖(単位系の違い・欠損値)を正規化する
- 1分のウィンドウで集約し、時系列 DB に保存する
- 集約値が閾値を超えたら通知する

ユニットは5つ。

| ユニット     | 隠す知識                           | 公開面             |
| ------------ | ---------------------------------- | ------------------ |
| SensorIntake | センサー機器のプロトコルと接続管理 | 計測値の流れ       |
| Normalizer   | 機種ごとの癖(単位系・欠損の扱い)   | 正規化済み計測値   |
| Aggregator   | 時間ウィンドウ(締め・遅着値の扱い) | 1分毎の集約値      |
| MetricStore  | 永続化方式(時系列DB)               | 集約値の保存・照会 |
| Alerter      | 閾値判定と通知手段                 | 異常の通知         |

## 2. Shidzuku による記述(仮構文)

ユニット・制約・フローの構文は第1〜3章が未定のため仮。意図(intent)は ADR 0003 に従って書く。

### 2.1 SensorIntake — 計測値の受信

```plaintext
unit SensorIntake {
  intent {
    why      "センサー機器のプロトコル(MQTT)と接続管理の知識をこのユニットに閉じ込める。内側のユニットは機器を知らず、計測値というデータだけを扱う。"
    rejected option "各ユニットが機器と直接通信する"
             reason "プロトコルや機器構成の変更が全ユニットに波及するため。"
    change   "機器側プロトコルの追加(CoAP 等)を想定。追加しても内側への公開面(計測値の流れ)は変えない。"
  }
  constraint {
    depends  Normalizer
    expose   計測値(センサーID, 時刻, 生値) の流れ
    isolate  failure                # 機器側の障害(切断・不正データ)を内側へ伝播させない
  }
  body { ... }
}
```

### 2.2 Normalizer — 計測値の正規化

```plaintext
unit Normalizer {
  intent {
    why      "機種ごとの癖(単位系の違い・欠損値・異常値)を吸収する知識をこのユニットに閉じ込める。下流は機種を知らない。"
    rejected option "Aggregator が集約時に機種差を吸収する"
             reason "集約の知識と機種の知識は変更の理由が異なり、機種追加の度に集約を触る事になるため。"
    change   "対応機種の追加を想定。追加は変換表の追加で済み、公開面(正規化済み計測値)は変えない。"
  }
  constraint {
    depends  Aggregator
    expose   正規化済み計測値(センサーID, 時刻, 値) の流れ
  }
  body { ... }
}
```

### 2.3 Aggregator — 時間ウィンドウ集約

```plaintext
unit Aggregator {
  intent {
    why      "時間ウィンドウの知識(1分の区切り、遅れて届いた値の扱い、締めのタイミング)をこのユニットに閉じ込める。"
    rejected option "MetricStore が保存時に集約する"
             reason "永続化方式の知識と時間の知識が混ざり、DB 移行がウィンドウ仕様の変更を巻き込むため。"
    change   "ウィンドウ幅の可変化(1分固定 → 設定値)を想定。公開面(集約値の流れ)は変えない。"
  }
  constraint {
    depends  MetricStore, Alerter
    expose   集約値(センサーID, 期間, 平均, 最大, 最小) の流れ
    layers {
      domain { pure }               # ウィンドウ計算は純粋。現在時刻は driver から注入する
      driver { io }                 # タイマー・時計のみ IO 可
    }
  }
  body { ... }
}
```

### 2.4 MetricStore — 集約値の永続化

```plaintext
unit MetricStore {
  intent {
    why      "集約値の永続化方式(現在は時系列DB)の知識をこのユニットに閉じ込める。"
    rejected option "各ユニットが直接 DB に書く"
             reason "スキーマや DB 製品の変更が全ユニットに波及するため。"
    change   "保持期間ポリシーの導入(古いデータの間引き)を想定。公開面(保存・照会)は変えない。"
  }
  constraint {
    depends  なし
    expose   保存(集約値)
    expose   照会(センサーID, 期間) -> 集約値列
    idempotent 保存                 # 同一(センサーID, 期間)の再保存は上書きで二重にならない
  }
  body { ... }
}
```

### 2.5 Alerter — 閾値超過の通知

```plaintext
unit Alerter {
  intent {
    why      "閾値判定の規則と通知手段(現在はチャット通知)の知識をこのユニットに閉じ込める。"
    rejected option "Aggregator が集約のついでに判定・通知する"
             reason "集約は全系の要であり、通知先の障害や遅延を集約に持ち込みたくないため。"
    change   "通知手段の追加(メール・電話)を想定。判定規則と通知手段はユニットの内側で分ける。"
  }
  constraint {
    depends  なし
    expose   (外部への通知のみ。内側への公開面なし)
    isolate  failure                # 通知先の障害を上流へ伝播させない
  }
  body { ... }
}
```

### 2.6 フロー — 計測パイプライン

```plaintext
flow 計測パイプライン {
  SensorIntake -> Normalizer  : flow 計測値               # 非同期: 応答不要
  Normalizer   -> Aggregator  : flow 正規化済み計測値     # 非同期
  Aggregator   -> MetricStore : flow 集約値  pressure block   # 詰まったら上流を待たせる(欠損不可)
  Aggregator   -> Alerter     : flow 集約値  pressure latest  # 最新値のみ保持(通知は最新だけで足りる)
  on failure Normalizer   : 当該計測値を捨て、障害イベントを記録する(伝播しない)
  on failure Aggregator   : 再起動する。集約途中のウィンドウ1個分は失ってよい
  on failure MetricStore  : 再起動し、pressure block により上流が待つ(欠損させない)
  on failure Alerter      : 再起動する。通知の欠落は許容し、障害イベントを記録する
}
```

## 3. 検証結果

### 3.1 書けた事

- **非同期の流れ(`flow`)**: 本システムのユニット間通信は全て「流しっぱなし」で足り、request-reply は1箇所も要らなかった(`照会` は運用・ダッシュボード向けで、本フローの外)。
  思考実験 01 では request-reply が2箇所必須だったため、両実験を合わせると **ask(要求-応答)と flow(非同期の流れ)の両方式が必要**という結論になる。
- **U3(内部階層)**: Aggregator を domain(純粋)/driver(IO 可)の2階層で自然に書けた。現在時刻を driver から注入すれば、ウィンドウ計算は純粋に保てる。
  思考実験 01 の OrderStore と合わせ、**固定の制約強度2種(純粋/IO 可)で2例とも足りた**。
- **U7(粒度)**: 「隠す設計判断が1つ = 1ユニット」の基準を再検証。当初 Normalizer と Aggregator を1ユニット(Preprocessor)にまとめようとしたが、why が「機種差を吸収し、かつ時間ウィンドウで集約する」と2文になり、基準が**分割のシグナルとして機能した**。
- **U1(意図テンプレート)**: 5ユニットすべてで必須3項目を実質的に書けた。SensorIntake の why は思考実験 01 の OrderIntake と似た形(プロトコルを隠す adapter 型)になったが、これは形骸化ではなく**設計の型**であり、W1(コピペ検出)は完全一致のみ検出するため誤検出しない。

### 3.2 書きにくかった事 — 仕様に戻す論点

1. **バックプレッシャのポリシーはユニットでなく接続に属する**。同じ Aggregator の出力でも、MetricStore 行きは欠損不可(block)、Alerter 行きは最新のみで良い(latest)と、**接続ごとに要求が異なる**。
  ユニットの constraint に書くと1ユニット1ポリシーになり矛盾する。
  → バックプレッシャはフロー(接続)の属性として宣言する。U2・第3章の論点。
2. **フロー(接続)に意図が書けない(再)**。「なぜ Alerter 行きは latest で良いか」「なぜ正規化を集約の前に置くか」という判断は、どのユニットの intent にも属さない。
  思考実験 01 の指摘(補償の順序の意図)と合わせて2回目の要請であり、**フローにも intent が必要**という結論を強める。→ U2・第3章の論点。
3. **「壊れてよい」には「失ってよい」の宣言が伴う**。Aggregator は集約途中のウィンドウ状態を持ち、Let it crash で再起動すると1ウィンドウ分が失われる。
  これを許容するかは設計判断であり、`失ってよい` と書けない障害境界の記述は不完全になる。
  → 障害境界の宣言に「失ってよい状態」を含める。第2章(制約の体系)の論点。状態を失いたくない場合の手段(合意・永続化)は U6(Raft の適用範囲)への先行入力として記録。
4. **fan-out の意味論が未定**。Aggregator の出力を2ユニットへ流す記述自体は書けたが、片方(MetricStore)が詰まった時にもう片方(Alerter)も道連れに待つのかは、仕様が決めていない。
  pressure が接続ごとの属性なら「接続は互いに独立」と定まる。→ U2 の論点。

### 3.3 未解決課題への入力

- **U2(通信方式)**: 思考実験 01(ask が2箇所必須)と本実験(flow のみで完結)を合わせ、**ask と flow の両方式を言語が持つ**必要がある。「非同期のみ」案・「同期のみ」案の双方への反証が揃った。
- **U2(バックプレッシャ)**: ポリシーは接続(フロー)の属性。本実験で必要になったのは block(上流を待たせる)と latest(最新のみ保持)の2種。
- **U2(フローの intent)**: 2実験連続で必要になった。フローにも intent(少なくとも理由と棄却)を持たせる。
- **U3(内部階層)**: 固定の制約強度2種(純粋/IO 可)で2実験とも足りた。自由定義の必要は現れていない。
- **U7(粒度)**: 「隠す設計判断が1つ = 1ユニット」が、分割の判定(why が2文になったら分ける)として2実験で機能した。
- **U4・U6 への先行入力(Phase 2 で決定)**: 「失ってよい状態」の宣言は、ログ規約(何を障害イベントとして残すか)と Raft の適用範囲(失いたくない状態をどう守るか)の入力になる。

# 思考実験 31: 反証と肯定 — 今のプログラマが受け入れない所と、プログラマ以外への良い影響

- 状態: Draft
- 領域: [全体](../areas/全体/README.md)
- 日付: 2026-10-18
- 目的: Shidzuku の言語仕様(第0〜6章)に対する反証と肯定をまとめる。反証は**今のプログラマに受け入れられない所**を、
  肯定は**プログラマ以外の人に与える良い影響**を、外部の研究と事例に照らして調べる
- 経緯: suzukimitsuru の指示による
- 調べた範囲: 外部の知見はウェブ検索の要約と、論文の要旨・著者の紹介文・書評に拠る。**論文の本文を読んだ物は無い。**
  数値は要旨か二次資料の値であり、引用する時は第8節(出典)の原典で確かめる。食い違いがあれば本書を直す
- 進め方: 新しい系は書かない。仕様の特徴ごとに、受け入れられない理由と根拠、仕様に既にある手当てを並べ(第3節(反証))、
  同じく良い影響と根拠を並べ(第4節(肯定))、両方を突き合わせる(第5節(反証と肯定の突き合わせ))。**本書は何も決めない**

## 1. 問いの置き直し

ここでの**反証**は、仕様が誤りだという証拠ではない。仕様が解こうとする問題(第0章 0.2(解決したい問題)の設計と実装の乖離・設計意図の喪失・実行時の騒がしさ)が、
**使われない事によって解けずに終わる**根拠である。**肯定**は、その効果がプログラマ以外の人にまで届く根拠である。

Shidzuku の記述に関わる人を、関わり方で分ける。

| 読み手                         | 記述との関わり                                                               |
| ------------------------------ | ---------------------------------------------------------------------------- |
| 今のプログラマ                 | 書く。Rust・TypeScript・Go・Java など既存の言語の慣習を持ち込む              |
| 業務の専門家・発注者           | 読む。システムの段、名前、直和の区分名                                       |
| 運用者                         | 読む。障害時の記述、捨てる流れ、図とログ                                     |
| 監査・品質保証・規制への対応   | 追う。意図・捨てた選択肢・図                                                 |
| 科学技術・計測・金融の担当者   | 値の意味(単位・刻み・丸め)を確かめる。自分で書かなくても、結果の正しさに頼る |
| 母国語で学ぶ人                 | 名前を母国語で読む                                                           |
| AI(人工知能)に実装を書かせる人 | 意図と制約を書き、実装の当否を機械に見させる                                 |
| 後任・将来の保守者             | 読む。なぜこの分割か、何を捨てたか                                           |

以下では、一行目を**書き手**、残りを**読み手**と呼ぶ。

## 3. 反証 — 今のプログラマが受け入れない所

各項に、仕様の所・受け入れられない理由・根拠・仕様に既にある手当て・強さを書く。強さは次の三段とする。

| 強さ | 意味                                                         |
| ---- | ------------------------------------------------------------ |
| 強い | 外部の根拠があり、仕様に手当てが無いか、手当てが未定         |
| 中   | 外部の根拠があるが、仕様に手当てがある。または根拠が推論だけ |
| 弱い | 反発は予想されるが、根拠が乏しいか、反対向きの根拠もある     |

### 3.1 書く量 — 省略の禁止

- **仕様の所**: 第0章 0.5(三層記述)と ADR 0008(省略の禁止)。依存・公開面・状態・照合器・内部階層、接続の `deadline`・`pressure`・配達保証、
  `on failure` と `restart`、`correlate`、`within` と `on expiry`、数値の幅・位取り・単位・量の種別、`日付` の暦を全て書き、無い事も `none` と書く。
- **受け入れられない理由**: 今の言語は既定値で書く量を減らす方向に進んできた。`int` と書けば済む所に `int64(0) 個` と書き、
  呼び出しの一つ一つに期限を書く事は、理由が分かっていても日々の手間として積み上がる。
  APoSD(John Ousterhout『A Philosophy of Software Design』)は既定値を勧めており、Shidzuku はその逆を選んだ(ADR 0024(APoSD と結合バランスの考え方の取り込み))。
- **根拠**: Java の検査例外は「宣言を書かせる」点で同じ形をしており、Hejlsberg は大きな系で宣言が積み上がり手枷になると述べた。
  Go の未使用の import をエラーにする規則も、意図は理解されながら回避の書き方が広まった。
- **手当て**: ADR 0008(省略の禁止)は負担を「接続あたり1〜3語、フローあたり1〜2行」と測り、記述量の不満は言語の既定ではなく道具の雛形生成で解くと将来想定に書いた。
  雛形生成はまだ形が無い。
- **強さ**: 中。手当ての方向はあるが、検査例外の轍と違うと言える根拠は、思考実験の記述量の数え上げだけである。
  検査例外との違いは、Shidzuku の宣言が版の変更で呼び手へ伝播しない事(接続の失敗を公開面に書かない。ADR 0031(失敗の体系)の決定2)にある。これは検査例外の一番の欠点を避けている。

### 3.2 意図を書かせる事 — 書かれても形骸化する

- **仕様の所**: 第2章 2.2(意図)と ADR 0003(検証不能な意図の記述形式)。`why`・`rejected`・`change` は必須で、空欄は E0003-1 になる。
- **受け入れられない理由**: プログラマの多くは、文章を書く事をコードを書く事の一部と見ていない。書かされた文は「とりあえず埋める」文になりやすく、
  空欄を拒んでも中身の誠実さは拒めない。
- **根拠**: 設計の文書は最も多く古び、コメントはコードの変更に追従しない(Rost ほか、Wen ほか、Jiang & Hassan)。
  一方で、契約を持つ言語では要素の3割超に契約が書かれ、実装より安定していた(Estler ほか)。**書く場所が言語の中にあれば書かれる**という反対向きの根拠である。
  ただし契約は機械が検査する物で、意図は検査されない。Estler ほかの結果が意図にも及ぶかは分からない。
- **手当て**: コピペの検出(W0003-1)と、公開面・制約の変更に意図が追従しない事の検出(W0003-2、判定基準は未定)。
- **強さ**: 中。古びる事への手当ては警告であり、内容の質は検査できない事を仕様自身が認めている(第3章 3.4(検証時期の原則))。

### 3.3 逃げ道の無さ — 警告を黙らせられず、検査をエラーに上げる

- **仕様の所**: 第3章 3.3(検証の一覧)。Rust が lint(警告)に置いた識別子の正規化と混同の検査をエラーに上げた(第5章 5.9(参照する規格と先行例))。
  警告(W0023-1・W0018-1・W0003-1)には黙らせる書き方が無い(第3章 3.5(未定事項))。
- **受け入れられない理由**: 今のプログラマは、検査を自分の判断で外せる事を当然と考えている(`#[allow]`・`// eslint-disable`・`@SuppressWarnings`)。
  外せない検査は、正しい時にも書き方を曲げさせる。
- **根拠**: Go の未使用の変数のエラーは、ダミーの代入(`_ = n`)という意味の無い行を生んだ。
- **手当て**: 思考実験 26(shidzuku-lint)の論点3(警告を黙らせる書き方が無い)が、抑止と理由を組で書かせる形を出している。未決である。
- **強さ**: 強い。抑止の書き方が未定のまま警告が増えれば、警告は読まれなくなる。

### 3.4 慣れた操作が無い — 文字列・null・論理値・既定の数値型

- **仕様の所**: 第6章(データと型)。テキストに素の等値比較とハッシュが無い(E0013-1)。`null` が無い。論理値をコンポーネントの外へ出せない(E0019-1)。
  既定の数値型が無く、数値型は暗黙に混ざらない(E0019-3・E0021-3)。テキストの部分取得や連結は役割を宣言した層に閉じる(E0013-2)。
- **受け入れられない理由**: `name == "abc"` や `Map<String, …>` は、今のプログラマが最初に書く操作である。それが書けない言語は、最初の一時間で「書けない」と判断される。
- **根拠**: Rust は所有権という新しい規則で、使わなくなった人の約3割に「学ぶのが難しすぎる」と言わせた(Rust の利用者調査 2022)。
  Rust は性能と安全という分かりやすい見返りを持ちながら、この率である。Shidzuku の規則の見返り(照合の正しさ、名前の付いた区分)は、より遅れて現れる。
- **手当て**: 識別子型・直和・照合器という代わりの道具がある。規則ごとに理由が第6章に書いてある。
- **強さ**: 中。代わりの道具はあるが、学ぶ量が増える事は避けられない。

### 3.5 言語の外の物 — ライブラリ・既存のコード・慣れを持たない

- **仕様の所**: 第0章 0.8(実現戦略)。新しい言語であり、動作環境は Shidzuku が提供する Rust の1実装である(ADR 0012(動作環境の言語とトランスパイル先の言語))。
- **受け入れられない理由**: プログラマが言語を選ぶ時に重く見るのは、言語の機能ではなく、使えるライブラリ、既にあるコード、自分と同僚の慣れである。
- **根拠**: Meyerovich & Rabkin は、普及を決めるのは外の要因(ライブラリと慣れ)で、意味論や性能は従であると示した。Rust の調査でも、使わない理由の上位は「会社が使わない」である。
- **手当て**: Rust と TypeScript へのトランスパイル(TypeScript が既存の生態系に型を被せた前例)と、既存の言語に考え方を先に届ける shidzuku-lint(ADR 0026(shidzuku-lint の作成))。
  shidzuku-lint は、言語を乗り換えずに考え方の一部を試せる入口であり、Meyerovich & Rabkin の結果に合う道である。
- **強さ**: 強い。普及の研究が最も強く支持する反証であり、手当ては方向が決まっただけで形は無い。

### 3.6 設計を書く層 — モデル駆動工学と UML の轍

- **仕様の所**: 第0章 0.1(理念)・0.7(可視化)。設計意図から実装までを一本の記述で貫き、図はコードから抽出する。
- **受け入れられない理由**: 設計をコードと同じ所に書かせる試みは、UML(Unified Modeling Language)とモデル駆動工学で一度行われ、多くの現場は離れた。
  プログラマは「また図と設計の層を書かされる」と受け取る。
- **根拠**: Petre は50人の聞き取りで、UML を使わない人が35、全面的に使う人は0だった。Hutchinson ほかは、モデル駆動工学の成否が技術より組織の要因で決まると示した。
- **手当て**: 向きが逆である。UML は図から書き始め、コードを生成するか、後から図を合わせた。Shidzuku は図を描かせず、記述から図を抽出する(第0章 0.7(可視化))。
  設計の層(意図と制約)も、図ではなくコードの隣の宣言である。
- **強さ**: 中。向きの違いは本質的だが、「設計の層を書く負担」という点では同じ反発を受ける。組織の要因が支配的であるという結果は、そのまま当たる。

### 3.7 実行の枠の強制 — 1コンポーネント1プロセス、ask と flow だけ

- **仕様の所**: 第0章 0.4(コンポーネント — 四位一体)、第4章 4.1(二つの通信方式)。コンポーネントを跨ぐ直接呼び出しと共有メモリは無く、通信は `ask` と `flow` だけである。
  同じノードでも1コンポーネント1プロセスで動作環境と並置する(第1章 1.6(動作環境は言語の記述対象外))。
- **受け入れられない理由**: 今のプログラマは Web の枠組み、ORM(Object-Relational Mapping、オブジェクトと関係データベースの対応付け)、スレッドと共有の状態の上で書いている。
  関数呼び出しで済む所がメッセージになる事は、性能と書きやすさの両方で抵抗を受ける。
- **根拠**: 同じ形の Erlang/OTP は障害に強い系で実績を持つが、利用は限られた分野に留まっている。これは外部の調査ではなく、言語の利用の広がりからの推論である。
- **手当て**: Rust のコンポーネントは動作環境をライブラリとして同居させてよい(第1章 1.6(動作環境は言語の記述対象外))。1コンポーネントの粒度は「隠す設計判断が1つ」で、細かく割る事は勧めない(第2章 2.5(粒度の指針))。
- **強さ**: 中。根拠が推論に留まる。性能の損得は、最小の言語実装(Phase 1)で測るまで分からない。

### 3.8 外部世界が書けない — 外部世界との境界(U12)が未定

- **仕様の所**: 第1章 1.8(未定事項)、第4章 4.6(未定事項)。コンポーネントの `depends` に `external` を書けず、外部を呼ぶコンポーネントが `depends none` と宣言する事になる。
  フローの端点に外部システムを書けない。
- **受け入れられない理由**: 今のプログラマが書くシステムの大半は、データベース・HTTP(Hypertext Transfer Protocol)の相手・機器・外部のサービスと繋がる事が仕事の大部分である。
  そこが書けない言語は、試す前に外される。
- **根拠**: 仕様自身が「省略の禁止の網に穴が開いている」と書いている(第1章 1.8(未定事項))。思考実験 08(多言語商品カタログ検索)の論点3(外部を呼ぶコンポーネントの `depends`)と論点7(フローの端点の外部システム)が発見した。
- **手当て**: 外部世界との境界(U12)として、Phase 1 の前に決める課題に入っている(計画書 第4節 4.5)。
- **強さ**: 強い。反証というより未完成であり、決まるまでは今のプログラマに見せられる記述例が限られる。

### 3.9 名前の言語 — 母国語の名前と英語の前提の間

- **仕様の所**: 第5章(記述の表記)。言語の語彙は ASCII、記述者の名前は UTF-8 で、日本語の名前は正規の記述である(ADR 0014(識別子と言語語彙の表記))。
  一方、思考実験 29(用語辞書による名前の規則)は、コードの名前を英語(ASCII)だけで書く前提を置いて検討しており、未決である。
- **受け入れられない理由**: 母国語の識別子は、国をまたぐチームやオープンソースでは読めない人を作る。英語に限れば、今度は業務の語との間に翻訳が一段入る。
  どちらを選んでも、一方の側のプログラマは受け入れない。
- **根拠**: Rust は非 ASCII の識別子に lint を持つ(第5章 5.6(言語の外への写像))。主要な言語は Unicode の識別子を許すが、慣習は英語である。後者は外部の調査で確かめていない。
- **手当て**: 名前を ASCII に限る事を公開する名前に留める形が、思考実験 29(用語辞書による名前の規則)の第9節(公開する名前への限定)で検討されている。
- **強さ**: 弱い。どちらの側の反発も予想できるが、量を示す根拠は無く、選び方で反発の向きが変わるだけである。

### 3.10 動く物が無い — 主張はまだ検証されていない

- **仕様の所**: 計画書 第1節(フェーズ計画)。現在は言語仕様(Phase 0)であり、パーサも検証器も動作環境も無い。
- **受け入れられない理由**: プログラマは動く物を見て判断する。「静かなシステム」は、障害を起こして見せるまで主張でしかない。
- **根拠**: 外部の調査は当たっていない。進め方の原則(各フェーズを動く最小の成果物で締める)が、同じ事を内側から言っている。
- **手当て**: 最小の言語実装(Phase 1)の成果物(コンポーネントを2〜3個接続して動かし、1つを別言語の出力に差し替える)と、最小の分散動作環境(Phase 2)の ESP32 での障害の非伝播の確かめ。
- **強さ**: 中。時間が解く反証であり、仕様の誤りではない。

## 4. 肯定 — プログラマ以外への良い影響

### 4.1 業務の専門家 — 業務の語がそのまま型と区分の名前になる

- **仕様の所**: 名前的型付け(`受注番号` と `受付ID` は中身が同じでも別の型。第6章 6.1(データの宣言))。不在の区分名が何が無いのかを言う(`欠損`・`暦の外`・`訳なし`)。
  論理値を外へ出さず、`在庫あり | 在庫なし` と名前の付いた直和で書く(第6章 6.2(基本型))。名前に日本語を使える(第5章 5.4(記述者が定める名前))。
- **良い影響**: 公開面と直和の区分は、業務の専門家が使う語の一覧になる。「在庫なしの時に何を返すか」が、`true`/`false` ではなく業務の語で書かれ、専門家が読んで誤りを指せる。
- **根拠**: ドメイン駆動設計は、業務の専門家と開発者が同じ語を使い、コードの名前も揃える事を勧め、翻訳が意思疎通を鈍らせると述べる。
  Shidzuku はそれを慣習ではなく型の規則(名前的型付け・論理値の禁止・不在の区分名)で支える。
- **留保**: 思考実験 29(用語辞書による名前の規則)の英語の前提を採ると、母国語の名前による効果は名前ではなく辞書の定義と、後で考えるローカライズに移る。

### 4.2 業務の専門家・経営 — システムの境界を読める

- **仕様の所**: 第1章(システムコンテキスト)。`actor`・`external`・`contains` だけでシステムの段が書け、境界の判断は `rejected` に残る(「決済は外に置く」)。
- **良い影響**: 技術の詳細を含まない段が言語の中にあり、そこから図が出る(第0章 0.7(可視化))。経営・業務の側が「何を自分たちで持ち、何を外に頼るか」を、古びない図で確かめられる。
- **根拠**: C4 モデルの Context 図は、技術者以外に見せる図として使われている。
- **留保**: 図の抽出は可視化(Phase 3)であり、最も後のフェーズである。それまで読み手はソースを読む事になる。

### 4.3 運用者 — 驚きを前もって宣言で知る

- **仕様の所**: 第4章(通信モデル)。データを捨てる事は `latest`・`drop` の宣言によってのみ起きる。配達保証(`transient`・`durable`)・障害時の埋め合わせ(`on failure`)・
  再起動(`restart`)・待ちの期限(`within`・`on expiry`)が全ての接続に書かれる。ログは規約から生成する(第0章 0.6(静かさの構造化))。
- **良い影響**: 運用者は、障害の後にコードを読んで振る舞いを探るのではなく、「どの流れが何を捨て得るか」「どこが落ちたら何が返るか」を前もって読める。
  障害境界がコンポーネントと一致するため、障害を図の上の一つの箱として扱える。
- **根拠**: 外部の調査は当たっていない。設計の文書が最も多く古びるという結果(Rost ほか)は、宣言から図とログを出す形を間接に支える。
- **留保**: ログ規約(U4)は最小の分散動作環境(Phase 2)で決める。効果は推論の段にある。

### 4.4 監査・品質保証・規制への対応 — 判断の跡と構造の追跡

- **仕様の所**: 意図の `rejected` と `refs`(第2章 2.2(意図))。ADR の参照。宣言外の通信の拒否(E0000-2・E0031-5)。図の抽出。
- **良い影響**: 「このコンポーネントはなぜこう分けたか」「何を検討して捨てたか」と「宣言に無い通信が無い事」を、記述から示せる。
  監査の側にとって、文書とコードの食い違いを探す作業の一部が、コンパイラの検査に置き換わる。
- **根拠**: 航空機搭載ソフトウェアの指針 DO-178C は、要求とコードの双方向の追跡を求め、要求の無いコードを指摘にする。医療機器ソフトウェアの規格 IEC 62304 も追跡を求める。
- **留保**: Shidzuku には要求の層が無い。追跡できるのは設計判断と構造までで、要求からの追跡は言語の外に残る。
  また DO-178C の改訂は追跡の情報を運用コードに埋め込む事を退けたと報じられており、意図をコードの隣に置く Shidzuku の形がどう評価されるかは原典で確かめる必要がある(論点5(意図の置き場と規制の追跡))。

### 4.5 科学技術・計測・金融の担当者 — 値の意味が化けない

- **仕様の所**: 第6章 6.3(数値型 — 4種と、量と単位)。全ての数値に単位と量の種別を書き、異なる量の加減算(E0010-1)、換算比を持たない単位の跨ぎ(E0010-2)、
  宣言の無い丸め(E0010-3)を拒む。金額は `int64(2) 円` のように刻みを型に書き、通貨に `float` を使えば警告(W0017-1)。
  テキストを数値や日付として読むのは解析の役割(`parse`)の明示の操作だけで、読めなかった事は受けなければならない(E0031-6)。
- **良い影響**: 自分ではコードを書かない研究者・計測の技術者・経理の担当者が頼る結果について、単位の取り違えと暗黙の変換が言語の段で起きない。
- **根拠**: 火星探査機 Mars Climate Orbiter は、地上のソフトウェアがポンド秒で出した値を航法がニュートン秒として受けて失われた。
  表計算が遺伝子名を日付に変えた化けは、遺伝子の一覧を補足に持つ論文の約2割に及んだ。
- **留保**: 探査機の事故には検証と意思疎通の不足も重なっており、型の検査だけで防げたとは言えない。
  遺伝子名の化けは表計算の自動変換であり、Shidzuku が使われる場面(コンポーネント間の通信)とは直接は重ならない。示すのは「暗黙の変換が専門家の結果を壊す」という型の問題である。

### 4.6 母国語で学ぶ人 — 名前を母国語で書ける

- **仕様の所**: 第5章 5.4(記述者が定める名前)。日本語の名前は例外的な許容ではなく正規の記述である。
- **良い影響**: 英語を読む負担なしに、業務と記述の対応を追える。
- **根拠**: Dasgupta & Hill は、Scratch の語彙と環境を母国語にした初学者が新しい概念を速く示した事を示した。
- **留保**: 研究が測ったのは**言語の語彙と環境**の局所化であり、Shidzuku は語彙を ASCII に固定し、名前だけを UTF-8 にする。効果がそのまま当たるとは言えない。
  思考実験 29(用語辞書による名前の規則)の英語の前提を採れば、この肯定はローカライズ(図・ログ・診断に母国語の名前を出す事)の側に移る。

### 4.7 AI に実装を書かせる人 — 枠を人が書き、中身を機械が見る

- **仕様の所**: 三層記述(第0章 0.5(三層記述))。意図と制約を書き、実装(body)が制約に違反すればコンパイラが拒む。
  純粋な層での IO(E0005-1)、役割に許されない操作(E0013-2)、宣言に無い通信(E0031-5)、受けていない失敗(E0031-6)、単位の取り違え(E0010-1)は、誰が body を書いても拒まれる。
- **良い影響**: コードの細部を読めない人が AI に実装を書かせても、境界・依存・失敗の扱い・単位は機械が見る。人が確かめるのは、意図と、公開面と直和の区分の名前になる。
  これは 4.1 の「業務の語で読める」と組み合わさる。
- **根拠**: 仕様を先に書いて AI に実装させる流れ(GitHub Spec Kit、Kiro)が広がっている。ただしそれらの仕様は自然言語の文書であり、実装を機械が拒む仕組みは持たない。
  Shidzuku の制約層は、その仕様のうち検証できる部分を言語の検査にした物と読める。
- **留保**: 推論である。非プログラマがこれらの道具を使えるかを測った調査は見つからなかった。

### 4.8 後任・将来の保守者 — 捨てた選択肢が残る

- **仕様の所**: `rejected` の必須(ADR 0003(検証不能な意図の記述形式))。捨てた選択肢が無い時も `rejected none` と理由を書く。
- **良い影響**: 「なぜこうしなかったのか」を、人が居なくなった後にも読める。発注者が保守を別の会社に移す時の引き継ぎの費用が下がる。
- **根拠**: 設計の文書の陳腐化の研究(Rost ほか)は、意図を別の文書に置くと古びる事を示す。Shidzuku は意図をコンポーネントの宣言の中に置き、公開面の変更への未追従を警告する(W0003-2)。
- **留保**: 意図そのものもコメントと同じく古び得る(第3節 3.2(意図を書かせる事))。肯定と反証が同じ所にある。

## 5. 反証と肯定の突き合わせ

### 5.1 同じ特徴の両面

反証と肯定の多くは、**同じ特徴を書き手の側と読み手の側から見た物**である。

| 特徴                   | 書き手(今のプログラマ)の費用       | 読み手(プログラマ以外)の利益         |
| ---------------------- | ---------------------------------- | ------------------------------------ |
| 省略の禁止             | 全ての宣言と `none` を書く         | 既定の表を知らずに、記述だけで読める |
| 意図の必須             | 文章を書く                         | なぜ・何を捨てたかが残る             |
| 単位と量の種別         | 全ての数値に幅・位取り・単位を書く | 値の意味が化けない                   |
| テキストと論理値の制限 | 慣れた操作が使えない               | 区分が業務の語で書かれる             |
| 障害時の記述の必須     | 全ての接続に期限と埋め合わせを書く | 運用で驚かない                       |
| 母国語の名前           | 国をまたぐ読み手を失う             | 業務の語と翻訳無しに対応する         |

**費用は書き手が払い、利益は読み手が受ける。** これが Shidzuku の受け入れの難しさの芯である。
言語を選ぶのは主に書き手であり(Meyerovich & Rabkin)、利益を受ける読み手は選ぶ場に居ない事が多い。

### 5.2 読み手に書かせない

振る舞い駆動開発は、非技術者が筋書きを書く事を前提にして、負担と受け取られた。書く役は開発者と試験者に寄った。
Shidzuku の肯定(第4節(肯定))は、いずれも読み手が**読む**事で得られ、書く事を求めていない。この線は守る方がよい。
言い換えると、Shidzuku の記述をプログラマ以外が読める形で届ける道具——図(可視化(Phase 3))と、名前と区分の一覧——が、肯定を実際に届ける唯一の経路になる。
その経路は今、最も後のフェーズにある(論点2(読み手を誰と定めるか))。

### 5.3 組織の判断として届ける

モデル駆動工学の成否は組織の要因で決まった(Hutchinson ほか)。Shidzuku の利益が読み手(監査・運用・業務・後任)の側にある以上、
導入を決めるのは個々のプログラマの好みではなく、読み手の利益を数える組織の判断になる。肯定の強い所——科学技術・計測・金融、規制のある分野——が、最初に届く先の候補である。

### 5.4 反証の強い所

強い反証は三つで、いずれも言語の設計の誤りではなく、**未完成と生態系**の問題である。

- 言語の外の物(第3節 3.5) — shidzuku-lint(ADR 0026)とトランスパイルが既に向いている
- 外部世界が書けない(第3節 3.8) — 外部世界との境界(U12)が Phase 1 の前に決める課題に入っている
- 逃げ道の無さ(第3節 3.3) — 警告の抑止は第3章 3.5(未定事項)にある

設計そのものに向かう反証(書く量・慣れた操作・設計を書く層)は中に留まり、いずれも意図して逆を選んだ所である(ADR 0008(省略の禁止)・ADR 0013(文字列型の廃止、text 型の導入、および層モデル)・ADR 0024(APoSD と結合バランスの考え方の取り込み))。
思考実験 28(シンプリシティとの比較)の「規則か、判断か」と同じ所に立っている。

## 6. 論点

### 論点1: 書く量を道具で減らす時期

ADR 0008(省略の禁止)の将来想定は、記述量の不満を雛形生成で解くとした。これを最小の言語実装(Phase 1)の成果物に含めるか。
省略の禁止は書かれた物の規則であり、書く手間の規則ではない。雛形が `none` を書いて渡す事は省略の禁止と矛盾しない。

### 論点2: 読み手を誰と定めるか

第4節(肯定)の各項はいずれも読み手に届いて初めて成り立つ。システムの段(Context)だけの図を可視化(Phase 3)より前に出すか、
名前と直和の区分の一覧を書き出す道具を置くか。思考実験 30(開発の流れと用語辞書)の、辞書を書き出して関係者のレビューに使う形と同じ方向である。

### 論点3: 外部世界との境界(U12)の優先

反証のうち、今のプログラマに見せられる記述例を最も狭めているのは外部世界である。Phase 1 の前に決める課題の中で、順を前に出すか。

### 論点4: 警告の抑止

第3章 3.5(未定事項)と思考実験 26(shidzuku-lint)の論点3(警告を黙らせる書き方が無い)にある。抑止と理由を組で書かせる形にすれば、ADR 0003(検証不能な意図の記述形式)の `rejected` と揃い、逃げ道の無さを和らげる。

### 論点5: 意図の置き場と規制の追跡

DO-178C の改訂が追跡の情報を運用コードに埋める事を退けた理由と範囲を原典で確かめ、Shidzuku の意図(コードの隣の宣言)がそれに当たるかを調べるか。
当たるなら、規制のある分野へは、意図を記述から書き出した物を追跡の記録として渡す形になる。

### 論点6: 名前の言語と肯定の関係

業務の専門家(第4節 4.1)と母国語で学ぶ人(第4節 4.6)の肯定は、母国語の名前に依る。思考実験 29(用語辞書による名前の規則)の論点7(名前を英語に限る事)を決める時の材料として渡す。
英語に限るなら、この二つの肯定はローカライズが引き受ける事になる。

### 論点7: 反証を測る

反証の多くは推論か、他の言語からの類推である。最小の言語実装(Phase 1)の成果物の題材で、書く量(宣言の行数・`none` の数)と、
プログラマ以外が記述を読んで誤りを指せるかを測る試験を置くか。

## 7. まとめ

- **反証の芯は、費用を書き手が払い、利益を読み手が受ける非対称である。** 言語を選ぶのは書き手であり、言語の普及は機能よりもライブラリ・既存のコード・慣れで決まる。
- 強い反証は、**言語の外の物**(生態系)・**外部世界が書けない事**・**逃げ道の無さ**の三つで、いずれも未完成の部分である。設計そのものへの反証(書く量・慣れた操作・設計を書く層)は、意図して逆を選んだ所に当たる。
- **肯定が最も強いのは、科学技術・計測・金融の担当者**である。単位と暗黙の変換による失敗は、事故と論文の実例がある。次いで業務の専門家・監査・後任に、業務の語と判断の跡が届く。
- 肯定はいずれも**読む事**で得られる。読み手に書かせない線を守り、読める形で届ける道具(図・名前と区分の一覧)を早く持つ事が、肯定を実際に届ける条件になる。
- 外部の知見は要旨と二次資料に拠る。引用の前に原典を確かめる。

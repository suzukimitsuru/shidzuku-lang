## 2. 書き下ろし

### 2.1 量と単位・暦の宣言

```plaintext
量 長さ 基準 メートル
単位 ミリメートル : 長さ = メートル × 1/1000

量 温度 基準 なし                       # 換算比を持たない量(℃↔℉ はオフセットを伴う)
単位 摂氏 : 温度
単位 華氏 : 温度

量 通貨 基準 なし
単位 円   : 通貨
単位 ドル : 通貨

暦 和暦 : グレゴリオ暦 の紀年法 {
  紀元 明治 : 1873-01-01 から 6 年
  紀元 大正 : 1912-07-30 から 1 年
  紀元 昭和 : 1926-12-25 から 1 年
  紀元 平成 : 1989-01-08 から 1 年
  紀元 令和 : 2019-05-01 から 1 年
}
```

`量 時間` は言語が最初から持つため宣言しない(6.3)。

### 2.3 実験 01 — 注文管理

```plaintext
data 注文     { 品目: 品目ID, 数量: 整数 単位なし }
data 受注結果 = 受注(受注番号) | 受注不可(理由)
data 理由     = 在庫不足(不足数: 整数 単位なし) | 取扱終了 | 与信超過
```

- 数量が `整数 単位なし` になった。桁の宣言が消え、上限を設計時に決めさせられない(6.3)。
- 「受注できたか」は真偽ではなく直和で書かれている(E0019-1 に触れない)。

### 2.4 実験 02 — センサー収集

```plaintext
data 変位計測 { センサー: センサーID, 起きた: 時点, 生値: 実数 ミリメートル | 欠損 }
data 温度計測 { センサー: センサーID, 起きた: 時点, 生値: 実数 華氏       | 欠損 }
data 正規化済み変位 { センサー: センサーID, 起きた: 時点, 値: 実数 メートル }
data 正規化済み温度 { センサー: センサーID, 起きた: 時点, 値: 実数 摂氏   }
data 集約区間 { 始まり: 時点, 終わり: 時点 }
data 集約値   { センサー: センサーID, 区間: 集約区間,
                平均: 実数 メートル, 最大: 実数 メートル, 最小: 実数 メートル }
```

- 計測値は `実数`(6.3 の指針「測って得た」)。桁も丸めも書かない。
- 単位が型に載り、`実数 華氏` を `実数 摂氏` の欄へ渡すと E0010-2 で落ちる。℉→℃ は Normalizer の body で `単位を外す`・`単位を付ける` を通る。
- `期間` は基本型ではないため直積で書いた(6.2 の一覧に無い)。

### 2.5 実験 03 — 画像変換

```plaintext
data 変換依頼 { 受付: 受付ID, 原画: バイト列, 指定: 変換指定 }
data 変換指定 { 幅: 整数 単位なし, 高さ: 整数 単位なし, 形式: PNG | JPEG | WebP }
data 変換結果 = 成功(受付ID, バイト列) | 失敗(受付ID, 理由)
```

- 画素数は数えた値なので `整数 単位なし`。バイト列は不透明な値のまま通る(6.2)。

### 2.6 実験 04 — 分散 KV ストア

```plaintext
data 値       { 中身: バイト列 }
data 書込記録 { キー: キー, 値: 値, 版: 整数 単位なし }
data 照会結果 = 見つかった(値) | なし
```

- 版は `整数 単位なし`。比較と +1 しかせず、桁の宣言に意味が無い(6.3)。
- **因果の順序が要る所で `時点` を使っていない。** 6.4 の「順序比較は起きた順ではない」がそのまま効いている。

### 2.7 実験 06 — 金額と税

```plaintext
data 明細 { 品目: 品目ID, 単価: 十進数(7.2) 円, 数量: 整数 単位なし }
data 請求 { 小計: 十進数(9.2) 円, 消費税: 十進数(9.2) 円, 合計: 十進数(9.2) 円 }
```

- 金額は `十進数`(6.3 の指針「刻みを人が十進で決めた」)。数量は `整数`。
- `単価 × 数量` は**型が混ざる**——`十進数 × 整数` は E0019-3 で落ちる。**書き手は `収める(数量, 十進数(5.0))` を挟む**(→ 論点1)。
- 消費税の端数処理は `割る(…, 十進数(9.2), 丸め 切り捨て)` のように丸めを宣言する(E0010-3)。

### 2.8 実験 08 — 多言語カタログ

```plaintext
data ロケール     = ja_JP | en_US | zh_CN
data 検索語       { 語: テキスト }
data 商品の見出し { 商品: 商品コード, 表示名: テキスト, 説明: テキスト }
data 検索結果     = 見つかった(list<商品の見出し>) | 検索不可(理由)
```

- ロケールは区分(直和)。テキストは不透明な値として通り、キーにはできない(E0013-1)。

### 2.9 実験 10 — 多地域シフト勤怠

```plaintext
data 打刻   { 従業員: 従業員ID, 起きた: 時点, 端末地: 時間帯, 向き: 出勤 | 退勤 }
data シフト { 拠点: 拠点ID, 勤務日: 日付 グレゴリオ暦, 開始: 時刻, 長さ: 整数 分 }
data 締め期間 { 始まり: 日付 グレゴリオ暦, 終わり: 日付 グレゴリオ暦 }
data 実績   { 従業員: 従業員ID, 勤務日: 日付 グレゴリオ暦, 実働: 整数 分,
              超過: 所定内 | 残業(整数 分) }
data 支給   { 従業員: 従業員ID, 基本: 十進数(9.2) 円, 割増: 十進数(9.2) 円 }
```

- 時間の3層が型で分かれている(6.4)。`シフト` は暦の値、`打刻` は時間軸の値である。
- `時刻` を持つ `シフト` は同じ直積に `拠点` を持つ(6.4 の指針)。

### 2.10 実験 11 — 和暦の届出

```plaintext
data 届出 { 受理日: 日付 和暦, 内容: テキスト }

# 受理日をグレゴリオ暦へ移す(boundary または format の層で)
換算(受理日, グレゴリオ暦)                     # 日付 グレゴリオ暦。全域
換算(ある日 グレゴリオ暦, 和暦)                # 日付 和暦 | 暦の外(E0020-2)
```

## 3. 検証結果

### 3.1 書けた事

- **11 実験の全データが、第6章だけを読んで書けた。** ADR を参照する必要は無かった。
- **真偽は一度も要らなかった。** 「受注できたか」「見つかったか」「残業したか」は全て名前の付いた直和になった(E0019-1 に触れない)。
- **`期間`・`時間量` を外した事で困らなかった。** 集約区間は直積、シフトの長さは `整数 分` で書けた。
- **数値型の使い分けが、書きながら決まった。** 数えた値は `整数`、測った値は `実数`、金額は `十進数` と、6.3 の指針の3列がそのまま当たった。
- **暦の欄が公開面の語彙になった。** `日付 和暦` と `日付 グレゴリオ暦` が別の型である事が読んで分かる。

### 3.2 書けなかった事 — 仕様に戻す論点

#### 論点1: `十進数 × 整数` が書けない — スカラー倍の穴

`単価 十進数(7.2) 円 × 数量 整数 単位なし` は、3つの数値型が混ざるため E0019-3 で落ちる。
書くには `収める(数量, 十進数(5.0))` を挟む事になるが、**これは全ての明細行に現れる**。

- ADR 0010 は「`単位なし` の値との乗除算(スカラー倍)は単位を変えない」と書いており、**単位の側は既に答えを持っている**。
- 足りないのは**型の側**である。`単位なし` の `整数` を、数値型を跨ぐスカラーとして許すかどうかが決まっていない。
- 危険は少ない。`整数` から `十進数` への変換は原理的に丸めが起きない(6.3 の変換表)。
- → **`単位なし` の `整数` によるスカラー倍だけを、明示の変換なしに許す**のが候補である。
  ただし「暗黙の変換を置かない」(6.3)の例外になるため、決定が要る。

#### 論点2: 直和の区分名がプログラム全体で衝突する

`理由` は実験 01(在庫不足・取扱終了・与信超過)と実験 03(失敗の理由)の両方に現れた。
別の `data` の区分だが、**名前空間の範囲が「1プログラム内」である**(第5章 5.5)ため、
2つの `data 理由` は E0014-3 以前に**同じ名前の宣言が2つある**事になる。

- 第6章 6.6 は名前空間を U14 に送っているが、**区分名がどの名前空間に属するか**は U14 の論点として挙がっていない。
- 直和の区分名(`受注`・`なし`・`欠損`・`所定内`)は `data` の中に閉じるのか、トップレベルに出るのか。
  `なし` は実験 04 と実験 08 の両方に現れ、**同じ意味である**。閉じるなら別物、出すなら共有語彙になる。
- → U14 に**区分名の可視範囲**を論点として足す。

#### 論点3: `list` の要素型に何が書けるか決まっていない

`list<商品の見出し>` は書けたが、`list<論理>` は書けるのか。6.2 は論理を「`data` の欄・公開面・`flow` の内容・`state`」で禁じているが、
**列の要素型は列挙されていない**。`list<論理>` を `data` の欄に置けば間接的に論理がデータに入る。

- 同じ穴が直和の区分の引数にもある。`data 結果 = 成否(論理)` は E0019-1 に当たるのか。
- → **E0019-1 の対象を「型の中に論理が現れる事」に読み替える**必要がある。仕様書の文面は場所を列挙しており、入れ子を拾えていない。

#### 論点4: 単位を持つ量の宣言が、どの段に属するか書かれていない

`量 長さ 基準 メートル` と `暦 和暦 : …` は、`data` と同じくトップレベルの宣言である。
しかし第6章はこれらを「宣言する」とだけ書いており、**`data` と同じトップレベルなのか、別の場所なのか**を定めていない。

- 第2章 2.1 は「コンポーネントはちょうど1つのシステムの `contains` に属する」と定めるが、`data`・`量`・`単位`・`暦` は `contains` に現れない。
- システムの入れ子(ADR 0018)を許した今、**内側のシステムだけが使う量や暦を、どこに書くか**が決まっていない。
- → U14(プログラムの宣言)の論点である。第6章 6.6 の「`data` 宣言の置き場所」に `量`・`単位`・`暦` を含めて書く。

#### 論点5: `暦の外` と `なし` と `欠損` が同じ形で、区別の指針が無い

実験を跨いで、データとして正常な不在が3つの名前で現れた——`なし`(実験 04)・`欠損`(実験 02)・`暦の外`(実験 11)。
いずれも直和の区分であり、6.1 の「『無い』は直和で明示する」に従っている。

- しかし**同じ意味の不在に別の名前が付く**事は、公開面の語彙が揃わない事を意味する。
- 言語が `なし` を1つ持つ案は ADR 0009 が退けている(不在の意味は文脈で違う)。
- → 指針の候補: **不在の区分名は、何が無いのかを言う**(`欠損` = 計測が取れなかった、`暦の外` = その暦では呼べない)。
  現状はそうなっているが、仕様書に書かれていない。

# 思考実験 08: 多言語商品カタログ検索(ADR 0013・0015 の新題材での検証)

- 状態: Draft
- 日付: 2026-08-28
- 目的: 採用した ADR 0013(テキストと層の役割)・ADR 0015(system 宣言)・ADR 0005(内部階層)を、**新しい題材で一から**記述して検証する
- 進め方: 既存の思考実験への後付けではなく、まだ書いた事のない系を選ぶ。ADR 0013 が求めた「テキストが主役の系」と、ADR 0015 が求めた「外部システムを複数持ち、システム境界の判断が難しい系」を一つの題材に載せた。書けない事があれば仕様に戻す

## 1. 対象システム

多言語の商品カタログを、人が入力した語で検索する系。テキストが公開面の主役になる初めての題材である。

- 買い物客が語を入力し、商品の候補を自分の言語で見る
- 商品の原簿(名前・説明・改廃)は社内の別系が持ち、こちらへ流してくる
- 訳文は外部の翻訳事業者から取り寄せ、こちらで保管する

コンポーネントは4つ。

| コンポーネント   | 隠す知識                                 | 公開面           |
| ---------------- | ---------------------------------------- | ---------------- |
| SearchGate       | HTTP・外部表現(JSON)・要求ロケールの取得 | 検索の受付       |
| ProductIndex     | 語の揺れと照合の強度                     | 候補の絞り込み   |
| TranslationStore | 訳文の保管と、訳が無い言語への代替の選択 | 見出しの取得     |
| CatalogSync      | 原簿の取り込み方式と差分の判定           | 原簿の受け入れ口 |

この題材を選んだ理由は、**文字列型を廃した言語で書けるかが最も疑わしい系**だからである。
検索語も商品名も自然言語であり、従来なら全て文字列で書かれる。ADR 0013 の主張(公開面に文字列は要らない)への
反証を探す位置づけを兼ねる(思考実験 07 と同じ向き)。

## 2. Shidzuku による記述

構文は第1〜4章に従う。基本型のうちテキストは ADR 0013 の決定1(仕様書への反映は ADR 0009 の採否待ち)を先取りして使う。

### 2.1 system — Context 段

``` plaintext
system 商品カタログ検索 {
  intent {
    why      "買い物客の言葉から商品を見つけ、その人の言語で見せるところまでを一つの境界に収める。
              商品の原簿そのものと、訳文を作る仕事は外に置き、この系は「見つける」と「見せる」だけを知る"
    rejected option "商品原簿を内側に持つ"
             reason "原簿は仕入・価格改定・改廃など検索以外の系からも動く。内側に入れると、この系が商品の真実の持ち主になってしまう"
    rejected option "訳文を内側で機械翻訳して作る"
             reason "訳の品質は事業の判断であり、検索の設計とは変更の理由が違う。作る仕事は外に置き、この系は受け取って選ぶだけにする"
    change   "取扱言語の追加を想定。外部システムは増えず、TranslationStore の内側の代替規則で吸収する"
  }
  constraint {
    actor    買い物客 "語を入力し、商品の候補を自分の言語で見る"
    actor    カタログ運用者 "取込の失敗と訳の欠落を見る"
    external 商品原簿 "社内の別系。商品の追加・改廃を流してくる"
    external 翻訳サービス "外部事業者。訳文を返す"
    depends  翻訳サービス
    expose   検索(検索語, ロケール) -> 列<商品の見出し> | 検索不可   担当 SearchGate
    expose   原簿の受け入れ(原簿の断片) の受け口                     担当 CatalogSync
    contains SearchGate, ProductIndex, TranslationStore, CatalogSync
  }
}
```

### 2.2 SearchGate — 検索の受付

``` plaintext
component SearchGate {
  intent {
    why      "HTTP・外部表現(JSON)・要求のロケールの取得をこのコンポーネントに閉じ込める。内側は検索語とロケールというデータだけを扱う"
    rejected option "ロケールを各コンポーネントが自分で決める"
             reason "同じ要求の中で層ごとに違うロケールが選ばれ、並び順と訳文が食い違うため"
    change   "gRPC の追加を想定。内側への公開面(検索語とロケール)は変えない"
  }
  constraint {
    depends  ProductIndex, TranslationStore
    expose   検索(検索語, ロケール) -> 列<商品の見出し> | 検索不可
    照合器   なし
    state    なし
    layers {
      受信   { io   境界 }   # HTTP のバイト列と Accept-Language の授受
      復号   { pure 解析 }   # バイト列 -> 検索語(テキスト)・ロケール
      受付   { io   領域 }   # 絞り込みと見出しの取得の依頼
      符号化 { pure 整形 }   # 見出しの列 -> JSON のバイト列
    }
  }
  body { ... }
}
```

### 2.3 ProductIndex — 候補の絞り込み

``` plaintext
component ProductIndex {
  intent {
    why      "人が入力した語から商品の候補を絞り込む知識(照合の強度と語の揺れ)をこのコンポーネントに閉じ込める"
    rejected option "呼び手が名前の完全一致で引く"
             reason "全角半角・異体字・正規化の差で一致せず、一致しない事が呼び手に見えないため"
    change   "対象ロケールと照合の強度の追加を想定。公開面(候補の列)は変えない"
  }
  constraint {
    depends  なし
    expose   絞り込み(検索語, ロケール) -> 列<商品コード>
    expose   原簿更新(商品の見出し) の受け口
    照合器   名前順(ロケール ja-JP, 強度 二次)
    state    索引 recoverable(商品原簿の再生)
    layers {
      照合 { pure 領域 }
      表   { io   領域 }
    }
  }
  body { ... }
}
```

### 2.4 TranslationStore — 見出しの取得

``` plaintext
component TranslationStore {
  intent {
    why      "訳文の保管と、訳が無い言語への代替の選び方をこのコンポーネントに閉じ込める"
    rejected option "呼び手が言語ごとに別の公開面を持つ"
             reason "言語が増えるたびに公開面が増え、代替の規則が呼び手の側に散るため"
    change   "機械翻訳による自動補完を想定。公開面(見出しの取得)は変えない"
  }
  constraint {
    depends  なし
    expose   見出し(商品コード, ロケール) -> 商品の見出し | 訳なし
    expose   訳の取り寄せ(商品コード) -> 済 | 訳なし
    照合器   なし
    state    訳文 recoverable(商品原簿と翻訳サービスからの再取得)
    layers {
      選択 { pure 領域 }   # 訳が無い言語への代替の選択
      保管 { io   領域 }   # 訳文の読み書き
      要求 { pure 整形 }   # 翻訳サービスへの要求の組み立て
      通信 { io   境界 }   # 翻訳サービスとのバイト列の授受
      受領 { pure 解析 }   # 応答のバイト列 -> 訳文
    }
  }
  body { ... }
}
```

### 2.5 CatalogSync — 原簿の受け入れ

``` plaintext
component CatalogSync {
  intent {
    why      "商品原簿の取り込み方式と、既に取り込んだ物との差分の判定をこのコンポーネントに閉じ込める"
    rejected option "ProductIndex が原簿を直接受ける"
             reason "取込方式(全量・差分・再送)の変更が、照合の知識を持つコンポーネントに波及するため"
    change   "全量再取込への切り替えを想定。内側の差分の層で吸収し、公開面は変えない"
  }
  constraint {
    depends  ProductIndex, TranslationStore
    expose   原簿の受け入れ(原簿の断片) の受け口
    照合器   なし
    state    取込位置 recoverable(商品原簿の再生)
    layers {
      受信 { io   境界 }   # 原簿の断片のバイト列の授受
      復号 { pure 解析 }   # バイト列 -> 商品の見出し
      差分 { pure 領域 }   # 既知との差分の判定
      配布 { io   領域 }   # 索引と訳文への配布の依頼
    }
  }
  body { ... }
}
```

### 2.6 フロー

``` plaintext
flow 検索 {
  intent {
    why      "候補の絞り込みを先に行い、見出しの訳はその候補にだけ引く"
    rejected option "先に訳文を引いてから語で絞る"
             reason "訳の取得が候補数ではなく全件に比例し、応答時間が語の一般性に依存するため"
    change   "候補数の上限の導入を想定。順序は変えない"
  }
  SearchGate -> ProductIndex     : ask 絞り込み(検索語, ロケール) 期限 200ms -> 列<商品コード>
  SearchGate -> TranslationStore : ask 見出し(商品コード, ロケール) 期限 300ms -> 商品の見出し | 訳なし
  on failure SearchGate       : 再起動(受付中の要求は失われる。state なし)
  on failure ProductIndex     : SearchGate は検索不可を返す(伝播しない)
  on failure TranslationStore : SearchGate は検索不可を返す(伝播しない)
}

flow 原簿取込 {
  intent {
    why      "原簿の断片を先に索引へ載せ、訳の取り寄せは索引に載った商品にだけ後から行う"
    rejected option "訳が揃ってから索引に載せる"
             reason "訳の遅れが検索可能になる時期を決めてしまい、原語では見つかる商品が見つからなくなるため"
    change   "訳の取り寄せの一括化を想定。索引への配布が先である順序は変えない"
  }
  CatalogSync -> ProductIndex     : flow 商品の見出し pressure block(期限 1s) durable
  CatalogSync -> TranslationStore : ask 訳の取り寄せ(商品コード) 期限 10s -> 済 | 訳なし
  on failure CatalogSync      : 再起動(取込位置から再開。state recoverable)
  on failure ProductIndex     : CatalogSync は取込位置を進めず、再送に任せる(伝播しない)
  on failure TranslationStore : CatalogSync は訳なしとして取込位置を進める(代替応答)
}
```

## 3. 検証結果

### 3.1 書けた事

- **公開面に文字列型が要らなかった**。検索語と商品の見出しはテキスト、商品コードは識別子型、ロケールは区分(直和)で書けた。
  ADR 0013 の主張は、テキストが主役の系でも保った。これは既存4実験の裏返し(文字列が現れなかった)より強い裏付けである。
- **照合器の宣言が意図の場所を作った**。ProductIndex の `照合器 名前順(ロケール ja-JP, 強度 二次)` は、
  従来なら body の奥に埋まっていた「どの強度で一致とみなすか」を制約層へ引き上げた。
  戻り値が `列<商品コード>`(単一の値ではない)である事も宣言から読め、曖昧一致である事が呼び手に見える。
- **役割の宣言が層の数を増やしたが、コンポーネントは割れなかった**。4コンポーネントで計15層になった。
  TranslationStore は5層と最も多いが、これは元から body の中にあった区別(訳の選択・保管・外部との授受)に名前が付いただけであり、
  隠す知識(訳の保管と代替の選択)は1つのままである。ADR 0013 決定5 の予測どおりだった。
- **system 宣言を一から書けた**。既存実験への後付けではなく、境界の判断(原簿を外に置く・訳を作る仕事を外に置く)を
  `rejected` に2件書けた。ADR 0015 が「新しい題材での検証」を残していた点は、この形で消化できた。
- **actor が2種に分かれた**。買い物客と運用者は見る物が違う。ADR 0015 の机上検証では actor が1種の系ばかりだったが、
  複数の actor も自然に並んだ。

### 3.2 書きにくかった事 — 仕様に戻す論点

#### 論点1: 「境界」の役割が指す外部と、システムの `external` が別物

役割の表(ADR 0013 決定6)は境界を「**外部システム**とのバイト列の授受」と定義する。
一方、第1章 1.4 の `external` は「独立に設計され、独立に壊れる相手」だけを指し、RDB のような永続化方式は含まない。

本実験では両方が現れた。

| 層                         | 相手          | 第1章 1.4 の判定  |
| -------------------------- | ------------- | ----------------- |
| TranslationStore の `通信` | 翻訳サービス  | external          |
| ProductIndex の `表`       | 索引の保存先  | external ではない |
| SearchGate の `受信`       | HTTP の呼び手 | actor(人)         |

同じ「境界」の役割が、external・外部の技術・人への窓口の三つを指している。
ADR 0013 の「外部システム」は ADR 0015 の `external` より広い意味で使われており、**同じ語が二つの段で別の物を指す**。
ADR 0015 決定2 は「段が変われば指す先が変わるが意味は同じ」を `depends` / `expose` について明示したが、
「外部」については何も言っていない。→ 第2章 2.4 と第1章 1.4 の語の突き合わせが要る。

#### 論点2: 役割の向きは、コンポーネント間の通信に適用されるのか

ADR 0013 決定5 は「データの向きは 境界 → 解析 → 領域 → 整形 → 境界 の一方向」とし、逆流を E20 とした。
しかし SearchGate の `受付 { io 領域 }` は ProductIndex へ ask を出し、応答を受け取る。これは領域層の中で
「送る」と「受け取る」が両方起きるが、バイト列化は動作環境の仕事であり(ADR 0012 の接合面)、
コンポーネントの記述には現れない。

つまり役割の向きは**コンポーネントと外の世界のあいだの話**であって、コンポーネント間の通信には適用されないはずである。
ところが仕様にも ADR 0013 にもその限定が書かれていない。文字どおり読むと、領域層が ask を出す事が
「領域でのバイト列化」に当たるのか判断できない。→ E20 の適用範囲の明示が要る。

#### 論点3: 外部を呼ぶのはコンポーネントなのに、コンポーネントの `depends` に書けない

翻訳サービスを実際に呼ぶのは TranslationStore である。しかし

- コンポーネントの `depends` は「通信してよい**コンポーネント**の列挙」(第3章 3.2)であり、外部システムは書けない。
  結果 `depends なし` となる。
- システムの `depends` は「このシステムが呼ぶ**外部システム**」であり、担当を書く欄が無い。

したがって「どのコンポーネントが翻訳サービスを呼ぶか」は、`external 翻訳サービス "…"` の説明文という
**検証されない散文**にしか書けない。ADR 0015 の机上検証(思考実験 02)でも `external 通知基盤 "…Alerter が使う"` と
散文で書かれており、同じ穴である。

`expose` は `担当 <コンポーネント名>` を持ち E13 で検証されるのに、`depends` は持たない。**非対称である**。
`depends なし` と書いたコンポーネントが実際には外部を呼ぶのは、省略の禁止(ADR 0008)の理念からも苦しい。

#### 論点4: 全文検索の索引が、照合キーの永続化の禁止に当たる

ADR 0013 決定9 は、照合キーの永続化・受け渡し・ハッシュを E19 として禁じた。理由は Unicode の版を跨ぐと
一致しなくなるためである。

ところが ProductIndex の `state 索引 recoverable(商品原簿の再生)` は、まさに照合の結果を保存した構造である。
語の揺れを吸収した索引は、照合器のロケールと強度と Unicode の版に依存する。**決定9 を文字どおり適用すると
全文検索の索引は書けない**。

ADR 0013 は「全文検索の索引ユニットの形」を将来の変更想定に送っていたが、本実験はそれが
**将来ではなく今ぶつかる**事を示した。逃げ道は三つあり、いずれも決めていない。

1. 索引を external の全文検索基盤に出す(論点5 に当たる)
2. 索引を「照合キー」ではなく再構築可能な派生状態として扱い、E19 の対象外と定める
3. 索引が依存する Unicode の版を宣言させ、版が変わったら `recoverable` の復元元から作り直させる

3 は ADR 0014 が E23 の判定で同じ論点(版の永続化)に触れており、系全体で一貫した答えが要る。

#### 論点5: 外部システムの判定基準が割れる

第1章 1.4 の判定は「その相手が**独立に設計され、独立に壊れるか**」である。
自社で運用する全文検索基盤(別プロセス・別ノード)を当てはめると、

- 独立に壊れる → **はい**(ノードごと落ちる)
- 独立に設計される → **いいえ**(スキーマも運用も自分たちが決める)

二つの条件の答えが割れる。連言(両方満たす時だけ external)か選言(どちらかで external)かが書かれていないため、
判定できない。RDB が external でないのは「両方を満たさない」からではなく、たまたま両方の直感が一致していただけだった。

本実験では連言と読んで external に入れなかったが、これは記述者の解釈である。→ 判定基準の明示が要る。

#### 論点6: 実行時に決まるロケールで、定型の文言を作る手段が無い

ADR 0013 決定10 は、テキストのリテラルにロケールの明示を要求する。

``` plaintext
テキスト("在庫がありません", ロケール ja-JP)   # 整形の層でのみ
```

しかし本実験で必要なのは「**要求のロケール**での文言」である。ロケールは実行時に外部から入る(決定2)ため、
リテラルに書けるのは `ja-JP` のような固定値だけであり、実行時の値を与える形が無い。

`訳なし` の商品をどう見せるか、`検索不可` に何と書くかは、すべてこの形を要する。
表示文言のカタログを整形の層に置く事は決まっているが、**カタログを要求ロケールで引く記法が未定**である。

#### 論点7: フローの端点に外部システムを書けるか

`商品原簿 -> CatalogSync : flow 原簿の断片 …` と書きたいが、第4章 4.2 は接続の両端を
コンポーネントの `depends` / `expose` と突き合わせる(E4・E5)。外部システムは `contains` の外にあり、
突き合わせる先が無い。

本実験ではこの接続をフローから外し、CatalogSync の受け口だけを system の `expose` に載せた。
結果、**原簿が届く経路がフロー図に現れない**。`on failure` も「フローに参加する全コンポーネント」が対象であり(E9)、
外部システムの障害時に何をするかを書く場所が無い。durable な受け口なのに、送り手の障害の記述が落ちる。

#### 論点8: 値のロケールと照合器のロケールが食い違うとき

ProductIndex の照合器は `ロケール ja-JP` を宣言している。しかし検索語のロケールは実行時に決まり、
`en-US` の語で日本語の商品名を引く事は普通に起きる。テキストの値は (ロケール, 正規化形, 内容) の三つ組であり(決定2)、
**値のロケールと照合器のロケールの関係**が定義されていない。

照合器を複数宣言してロケールで選ぶのか、要求のロケールを照合器に渡すのか、そもそも一致を要求するのか。
ADR 0013 は「対象ロケールの追加」を将来の変更想定に挙げているが、多言語が前提の系では最初から必要になる。

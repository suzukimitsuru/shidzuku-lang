# 思考実験 17: 主要言語の数値型の比較 — ビット幅と範囲

- 状態: Draft
- 日付: 2026-09-15
- 目的: 幅の違う整数型を複数持つ言語が、何をどう分けているかを一覧にする。
  ADR 0021 の決定9(境界の幅付き整数)が持つべき幅と符号、および `実数` を binary64 の1つに絞った判断の裏付けを取る
- 進め方: まず「なぜ幅で分けるのか」を4つの理由に整理する。次にビット幅ごとの範囲を表にし、主要言語を7つの軸で並べる。最後に ADR 0021 への入力をまとめる

## 1. なぜ幅の違う整数型があるのか

理由は4つあり、**それぞれ別の層の都合**である。

| #  | 理由               | 中身                                                                                           | 誰の都合 |
| -- | ------------------ | ---------------------------------------------------------------------------------------------- | -------- |
| 1  | 記憶域             | 100 万件の列で 1 バイトか 8 バイトかは 8 倍の差になる。組込みでは RAM が数十キロバイトしかない | 内側     |
| 2  | 実行時間の上界     | 固定幅なら1命令で終わる。任意精度は桁数に比例し、上界が値に依存する(思考実験 16 の 4.1)        | 内側     |
| 3  | 外部形式との一致   | プロトコル・ファイル形式・DB の列・機器のレジスタは、**幅で定義されている**                    | 境界     |
| 4  | ハードウェアの語長 | レジスタ・アドレス・添字は機械の語長に合わせるのが自然                                         | 実装     |

**ADR 0021 は 3 だけを言語の語彙に残し、1・2 を実装と将来の値域の宣言に、4 を実装に委ねた。**
「幅を持つ型が8種も要る」のではなく、「**幅が意味を持つのは外部と接する瞬間だけ**」という切り分けである。

## 2. ビット幅ごとの範囲

| ビット | バイト | 符号付きの最小                                       | 符号付きの最大                                      | 符号なしの最大                                      | 十進の桁数 |
| ------ | ------ | ---------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------- | ---------- |
| 8      | 1      | -128                                                 | 127                                                 | 255                                                 | 3          |
| 16     | 2      | -32,768                                              | 32,767                                              | 65,535                                              | 5          |
| 32     | 4      | -2,147,483,648                                       | 2,147,483,647                                       | 4,294,967,295                                       | 10         |
| 64     | 8      | -9,223,372,036,854,775,808                           | 9,223,372,036,854,775,807                           | 18,446,744,073,709,551,615                          | 19〜20     |
| 128    | 16     | -170,141,183,460,469,231,731,687,303,715,884,105,728 | 170,141,183,460,469,231,731,687,303,715,884,105,727 | 340,282,366,920,938,463,463,374,607,431,768,211,455 | 39         |

符号付きは2の補数であり、**最小の絶対値が最大より 1 大きい**(`-128` はあるが `128` は無い)。
`-最小値` が表せないため、絶対値を取る演算はここで桁溢れする——固定幅を使う限り避けられない非対称である。

## 3. 浮動小数点(IEEE 754)の範囲

| 形式                 | ビット | 符号/指数/仮数 | 有効桁(十進) | 最大                    | 最小(正規)               | 最小(非正規)            | 整数を厳密に表せる上限       |
| -------------------- | ------ | -------------- | ------------ | ----------------------- | ------------------------ | ----------------------- | ---------------------------- |
| binary16(半精度)     | 16     | 1/5/10         | 約 3.3       | 65,504                  | 6.104e-5                 | 5.96e-8                 | 2^11 = 2,048                 |
| binary32(単精度)     | 32     | 1/8/23         | 約 7.2       | 3.4028234663852886e38   | 1.1754943508222875e-38   | 1.401298464324817e-45   | 2^24 = 16,777,216            |
| **binary64(倍精度)** | 64     | 1/11/52        | 約 15.95     | 1.7976931348623157e308  | 2.2250738585072014e-308  | 4.9406564584124654e-324 | 2^53 = 9,007,199,254,740,992 |
| binary128(四倍精度)  | 128    | 1/15/112       | 約 34.0      | 1.1897314953572318e4932 | 3.3621031431120935e-4932 | 6.48e-4966              | 2^113                        |

- **「整数を厳密に表せる上限」が重要である。** binary64 は 2^53 を超えると 1 刻みを表せなくなる。
  JavaScript の `Number.MAX_SAFE_INTEGER`(9,007,199,254,740,991)はこの値から来ている。
- ADR 0019 が `整数` を置いた背景「`実数` は 19 桁の値(ナノ秒の時点・64 ビットの識別子)を壊す」は、この行が根拠である。

## 4. 言語ごとの数値型

| 言語           | 整数の幅                            | 符号なし | 既定の整数      | 桁溢れの扱い                               | 数値型の暗黙変換              | 浮動小数点                       | 10進型              | 任意精度整数        |
| -------------- | ----------------------------------- | -------- | --------------- | ------------------------------------------ | ----------------------------- | -------------------------------- | ------------------- | ------------------- |
| **Rust**       | 8/16/32/64/128 + `isize`/`usize`    | あり     | `i32`           | debug はパニック、release はラップ         | **無し**                      | `f32`・`f64`                     | 無し(外部 crate)    | 無し(`num-bigint`)  |
| **TypeScript** | 無し(`number` のみ)                 | —        | `number`(64)    | 2^53 超は精度が落ちる(黙って)              | 無し(`bigint` と混ぜられない) | `number`(binary64)               | 無し(外部)          | `bigint`(標準)      |
| **Go**         | 8/16/32/64 + `int`/`uint`/`uintptr` | あり     | `int`(通常 64)  | ラップ                                     | **無し**(定数は別)            | `float32`・`float64`             | 無し(`math/big`)    | `math/big.Int`      |
| **Java**       | 8/16/32/64(`char` は 16 の符号なし) | ほぼ無し | `int`           | ラップ(`Math.addExact` は例外)             | あり(widening)                | `float`・`double`                | `BigDecimal`        | `BigInteger`        |
| **C#**         | 8/16/32/64/128 + `nint`/`nuint`     | あり     | `int`           | 既定はラップ、`checked` で例外             | あり(安全な向き)              | `float`・`double`                | **`decimal`**(組込) | `BigInteger`        |
| **Python**     | 無し(`int` のみ)                    | —        | `int`(任意精度) | **起きない**                               | `int`↔`float` は暗黙          | `float`(binary64)                | `decimal`(標準)     | `int` そのもの      |
| **Swift**      | 8/16/32/64 + `Int`/`UInt`           | あり     | `Int`(64)       | **既定でトラップ**(`&+` でラップ)          | **無し**                      | `Float`・`Double`・`Float80`     | `Decimal`(標準)     | 無し                |
| **C / C++**    | 8/16/32/64(`int8_t` 等)+ `size_t`   | あり     | `int`(通常 32)  | 符号付きは**未定義動作**、符号なしはラップ | あり(暗黙の格上げ)            | `float`・`double`・`long double` | 無し                | 無し                |
| **Zig**        | **任意ビット幅**(`i3`・`u7` 等)     | あり     | `comptime_int`  | 検査つき(安全ビルドで捕捉)                 | 無し                          | `f16`〜`f128`                    | 無し                | `comptime_int` のみ |
| **Haskell**    | `Int`(≧64)・`Int8`〜`Int64`・`Word` | あり     | `Integer`       | `Int` はラップ、`Integer` は起きない       | **無し**                      | `Float`・`Double`                | `Data.Fixed`        | `Integer`(標準)     |
| **Erlang**     | 無し                                | —        | 整数(任意精度)  | **起きない**                               | 一部あり                      | `float`(binary64)                | 無し                | 標準                |

### 4.1 Rust

- 幅と符号を全て型に出す(`i8`〜`i128`・`u8`〜`u128`)。`isize`/`usize` はポインタ幅で、**添字と長さは `usize`** と決まっている。
- 桁溢れは**ビルド設定で挙動が変わる**(debug はパニック、release はラップ)。曖昧さを嫌う場面のために `checked_add`(直和で返す)・`wrapping_add`・`saturating_add`・`overflowing_add` が揃っている。
- 数値型どうしの暗黙変換は**一切無い**。`as` か `TryFrom` を書く。思考実験 14 が分類した「完全分離」の側である。
- 10進型は言語に無く、`rust_decimal`(96 ビット)・`bigdecimal`(任意精度)・`fpdec`(位取りを型の定数に持つ)が使われる。

### 4.2 TypeScript(JavaScript)

- **数値型は `number` だけ**で、実体は binary64 である。整数型は無く、2^53 を超えると 1 刻みが表せなくなる。
- ビット演算(`&`・`|`・`<<`)は、いったん **32 ビット整数に丸めてから**行う。`>>>` だけが符号なし 32 ビットとして扱う。
- ES2020 で `bigint`(任意精度整数)が入った。`number` と `bigint` は**混ぜると実行時エラー**になる(`TypeError`)——
  **型を1つに絞った言語が、後から幅と精度の概念を取り戻した実例**である。
- TypeScript の型注釈は実行時には消える。`number` に「32 ビット整数」を表す型は無い。

### 4.3 Go

- 幅つきの型(`int8`〜`int64`・`uint8`〜`uint64`)と、実装が決める `int`/`uint`(通常 64 ビット)を持つ。`byte` は `uint8`、`rune` は `int32` の別名である。
- **定数だけが特別で、任意精度で保持される**。仕様は「整数の定数は最低 256 ビット」を実装に要求し、**定数は桁溢れしない**。
  型が付くのは変数に代入する瞬間であり、そこで初めて溢れ得る。
- 変数どうしの暗黙変換は無い。`int32` と `int64` を足すには明示の変換が要る。

### 4.4 Java と C# — 符号なしの有無と decimal

- Java は**符号なし整数を持たない**(`char` だけが 16 ビットの符号なし)。配列の長さと添字は `int`(最大 21 億)であり、これが大きな配列の壁として知られている。
- C# は符号あり/なしを揃え、`Int128`/`UInt128`(.NET 7 以降)も持つ。**`decimal` を言語の組込み型として持つ**点が他と違う。
  128 ビット・有効桁 28〜29・範囲 ±1.0e-28 〜 ±7.9228162514264337593543950335e28 で、内部は 96 ビットの仮数と 0〜28 の位取りである。
- どちらも「安全な向き」の暗黙変換を持つ(`int` → `long`、`int` → `double` など)。思考実験 14 が「非対称の橋」と呼んだ設計である。

### 4.5 Python・Erlang — 幅を持たない側

- Python の `int` は**任意精度のみ**で、桁溢れが存在しない。添字も長さも同じ型である。
- 代わりに **CPython は小さい整数を最適化する**(-5〜256 を事前に確保して使い回す)。言語の型ではなく実装の工夫で速度を保つ形であり、思考実験 16 の 4.6 に書いた通りである。
- Erlang も整数は任意精度で、小さい値は即値(fixnum)として1ワードに収める。

### 4.6 Zig — 幅を型の引数にした極端

- `i3`・`u7`・`u65535` のように**任意のビット幅**を型に書ける。プロトコルのビットフィールドをそのまま型にできる。
- 「幅は外部表現の性質である」という ADR 0021 の見方を、**型の側で徹底した反対の実例**として置いておく価値がある。

## 5. 軸ごとの比較

### 5.1 最も分かれるのは「桁溢れをどうするか」

| 扱い                   | 言語                                                            | 何が起きるか                                     |
| ---------------------- | --------------------------------------------------------------- | ------------------------------------------------ |
| ラップ(2の補数)        | Java・Go・C#(既定)・Rust(release)・C の符号なし                 | 最大値 + 1 が最小値になる。**静かに壊れる**      |
| トラップ(実行時に停止) | Swift(既定)・Rust(debug)・C#(`checked`)・Ada                    | 落ちるが、気づける                               |
| 未定義動作             | C・C++ の符号付き                                               | 最適化器が「起きない」と仮定して分岐ごと消し得る |
| 起きない(任意精度)     | Python・Erlang・Haskell の `Integer`・JS の `bigint`・Go の定数 | 代わりに**記憶域と実行時間が値に依存する**       |

Shidzuku の `十進数` は最後の行にいる。**ADR 0021 が引き受けた代償は、この行に固有のもの**である(思考実験 16 の 4.1・7.3)。

### 5.2 「幅を選ぶ」言語と「1つに決める」言語

- 幅を選ぶ: Rust・C/C++・Go・Swift・Zig(組込み・システム寄り)
- 1つに決める: JavaScript(binary64)・Python(任意精度)・Erlang(任意精度)
- **1つに決めた言語は、後から取り戻している。** JavaScript は `bigint` を足し、Python は `array`・`numpy` で幅つきの器を別に持つ。
  「幅は要らない」と言い切れた言語は無く、**どこに置くか**だけが違う。

### 5.3 10進型を言語に持つのは少数

| 持ち方         | 言語                                                    |
| -------------- | ------------------------------------------------------- |
| 言語の組込み型 | C#(`decimal`)・SQL(`NUMERIC`)                           |
| 標準ライブラリ | Java(`BigDecimal`)・Python(`decimal`)・Swift(`Decimal`) |
| 外部ライブラリ | Rust・Go・JavaScript                                    |

金額を扱う言語が `decimal` を持つのは共通するが、**位取りを型に持つ**のは SQL の `NUMERIC(p,s)` と Haskell の `Data.Fixed` だけである(思考実験なし・ADR 0021 の「この形式の名前」)。

### 5.4 添字と長さの型

| 言語       | 添字・長さの型 | 実質の上限                |
| ---------- | -------------- | ------------------------- |
| Rust       | `usize`        | ポインタ幅(64)            |
| C/C++      | `size_t`       | ポインタ幅                |
| Go         | `int`          | 通常 64 ビット            |
| Swift      | `Int`          | 64 ビット                 |
| **Java**   | `int`          | **約 21 億**              |
| JavaScript | `number`       | 2^53 - 1(配列は 2^32 - 1) |
| Python     | `int`          | 無し(任意精度)            |

**Java の配列長が 32 ビットである事は、幅を決め打った設計が後から効いてくる典型例**である。
逆に Python は上限を持たないが、実装が小さい整数を最適化している。思考実験 16 の 4.2(添字の上界を型が言うか)はこの対比そのものである。

## 6. ADR 0021 への入力

- **幅は 8/16/32/64 の4種で足りる。** 128 ビット整数を持つのは Rust・C#・Zig 程度で、外部形式(プロトコル・DB・機器)で 128 ビット整数が現れる事は稀である。
- **符号あり/なしの両方が要る。** `u8` はバイト、`u16`/`u32` は長さ・識別子、`i32`/`i64` は座標・時刻という使い分けが、どの言語でも共通して現れる。
- **バイト順の宣言も要る。** 言語の型には現れないが、外部形式では必ず決まっている(Zig・Erlang のビット構文はそこまで型に載せている)。
- **`実数` を binary64 に絞った判断は多数派と一致する。** JavaScript の `number`、Go の浮動小数点リテラルの既定、Python の `float` はいずれも binary64 である。
  binary32 が要るのは組込み・GPU・機械学習であり、ADR 0021 が保留にした範囲と重なる。
- **`number` と `bigint` を混ぜると失敗する JavaScript の規則**は、ADR 0021 の E0019-3(`実数` と `十進数` を混ぜない)と同じ形の先例である。
  ただし JavaScript は実行時エラー、Shidzuku はコンパイル時エラーである。
- **Go の定数(任意精度で保持し、代入時に型が決まり、そこで初めて溢れる)**は、リテラルの扱いの先例として参考になる。
  ADR 0021 のリテラルは「書かれた通りの十進の値」であり、Go の定数と同じ立場に近い。

## 7. 未解決課題への入力

- **U12(外部世界との境界)**: 幅・符号・バイト順の3つを宣言する形は、Zig のビット幅型・Erlang のビット構文・Ada の表現節が先例になる。名前付きの外部形式を設計する際の参考にする。
- **U15(数値の型と単位)**: binary32 を追加するかどうかは、組込み・GPU を対象に含める判断と一体である(思考実験 14 の論点4)。
- **U13(失敗の体系)**: 桁溢れの扱いは4通りある(5.1)。Shidzuku は「起きない(任意精度)」と「境界で失敗」の組み合わせであり、**ラップとトラップのどちらも採らない**事を記録しておく。

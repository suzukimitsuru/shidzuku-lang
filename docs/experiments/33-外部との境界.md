## 2. 外の相手の棚卸し

本書で書き下ろす範囲(思考実験 02 の5つ、受注の一生の5つ、思考実験 08 の4つ、計14のコンポーネント)で、外の形式で何かと授受するコンポーネントを数えた。

| 題材               | コンポーネント   | 外の相手           | 向き                         | 外の形式         | `external` に書いてあるか  |
| ------------------ | ---------------- | ------------------ | ---------------------------- | ---------------- | -------------------------- |
| センサー収集       | SensorIntake     | センサー機器群     | 外から内(送ってくる)         | MQTT             | 書いてある                 |
| センサー収集       | MetricStore      | 時系列データベース | 内から外(書く・読む)         | データベースの行 | 書いていない(外部の技術)   |
| センサー収集       | Alerter          | 通知基盤           | 内から外(呼ぶ)               | 通知基盤の要求   | 書いてある                 |
| 受注の一生         | Frontdesk        | 買い物客の HTTP    | 外から内(要求と応答)         | HTTP             | 書いていない(actor の窓口) |
| 受注の一生         | OrderStore       | 受注台帳の保存先   | 内から外(書く・読む)         | データベースの行 | 書いていない(外部の技術)   |
| 受注の一生         | PaymentBridge    | 決済代行           | 往復(依頼を送り、結果が来る) | HTTP             | 書いてある                 |
| 多言語商品カタログ | SearchGate       | 買い物客の HTTP    | 外から内(要求と応答)         | HTTP             | 書いていない(actor の窓口) |
| 多言語商品カタログ | ProductIndex     | 索引の保存先       | 内から外(書く・読む)         | データベースの行 | 書いていない(外部の技術)   |
| 多言語商品カタログ | TranslationStore | 翻訳サービス       | 内から外(呼ぶ)               | HTTP             | 書いてある                 |
| 多言語商品カタログ | CatalogSync      | 商品原簿           | 外から内(流してくる)         | 社内の別系の形式 | 書いてある                 |

- **14 のうち 10 が、外の形式で何かと授受する。** 外の相手を持たないのは Normalizer・Aggregator・OrderIntake・Inventory の4つだけである。
  外部依存の書き方は、例外ではなく大半のコンポーネントに掛かる。
- **10 のうち `external` に書いてあるのは 5 である。** 残りは外部の技術(データベース)3 と、actor の窓口(HTTP)2 である。
- **向きは三つある。** 呼ぶ(Alerter)、送ってくる(SensorIntake)、往復する(PaymentBridge)。第1章 1.4 の `external`(存在)と `depends`(呼ぶ)の区別は、前の二つを分けるために置かれた。往復は両方に当たる。

### 2.1 「外部」は二つの軸の語である

棚卸しの10行は、二つの問いで分けると重ならずに並ぶ。

- **記述の外か**: `external` に書いたか(ADR 0018 の決定10)。誰が相手かの問いである。
- **誰が運ぶか**: 動作環境が正準形で運ぶか、コンポーネントの境界の層が外の形式で運ぶか(ADR 0012)。何の形で授受するかの問いである。

| 相手の置き場                          | 動作環境が正準形で運ぶ                                         | 境界の層が外の形式で運ぶ                            |
| ------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------- |
| 記述の中(兄弟・親の兄弟)              | `ask`・`flow`。フローに書ける                                  | 無い(コンポーネント間の通信は `ask` と `flow` だけ) |
| 記述の外(`external` に書いた)         | 別に設計した Shidzuku の系(商品原簿が社内の Shidzuku の系なら) | センサー機器群・通知基盤・決済代行・翻訳サービス    |
| どちらでもない(`external` に書かない) | 無い                                                           | データベース・HTTP の呼び手・機器に繋いだ素子       |

- 第1章 1.4 の `external` は**行**の問い、第2章 2.4 の役割「境界」は**列**の問いに答えている。思考実験 08 の論点1(同じ語が二つの段で別の物を指す)は、二つの軸を一つの語で呼んでいた事から起きている。
- **右上の欄は規則で空いている**(ADR 0004)。左下の欄も空く——`external` に書かない相手と、動作環境が正準形で話す事は無い。
- **左中の欄(動作環境で話す外部)を、今の仕様は右中の欄と区別しない。** 商品原簿が社内の Shidzuku の系なら、CatalogSync の受け口は動作環境が運ぶ普通の `flow` で足り、境界の層は要らない。
  外の形式の系なら、CatalogSync の境界の層が受ける。同じ `external 商品原簿` が、二つの違う授受を指す。
- 思考実験 27 の 7.1(境界の位置が配置で一段内側へ動く)は、右中の欄から右下の欄への移動として読める。SensorIntake を機器に載せると、相手はセンサー機器群(`external`)から素子(`external` に書かない)に替わり、運ぶのは同じく境界の層である。

### 2.2 システムの `expose` は、どちらの列で届くのか

センサー収集の `expose 計測値の受け入れ(計測値) flow in by SensorIntake` は、型の付いた `flow` の受け口として書かれている。
ところがセンサー機器群は MQTT で送ってくる(思考実験 02)。SensorIntake の境界の層が MQTT のバイト列を受け、解析の層が `計測値` に読む。

- この `expose` を文字どおり読むと、センサー機器群が動作環境に正準形の `計測値` を流す事になる。実際には、そうなっていない。
- 多言語商品カタログの `expose 検索(検索語, ロケール) -> 列<商品の見出し> | 検索不可 by SearchGate` も同じで、実際の入口は SearchGate の境界の層が受ける HTTP である。
- **システムの `expose` が、動作環境の受け口なのか、境界の層が外の形式で受ける入口の要約なのかが、仕様に書かれていない。** 第1章 1.4 は担い手との一致(E0015-3)だけを見る。
  二つの軸の表(第2.1節)の左中と右中の区別が、`expose` の側にも要る事になる。

## 3. 案

### 3.1 外部依存の書き場所 — 三案

第1章 1.8 の穴(外部を呼ぶコンポーネントが `depends none` と書く)を塞ぐ形を三つ置く。

| 案                                     | 書く所                                                                                      | 一行の例                            |
| -------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------- |
| `depends` を広げる案                   | コンポーネントの `depends` に、親の `external` の名前を書けるようにする                     | `depends OrderStore, 決済代行`      |
| システムの `depends` に担い手を書く案  | システムの `depends` に `by` を足す。`expose ... by` と対にする                             | `depends 決済代行 by PaymentBridge` |
| コンポーネントにも `external` を置く案 | コンポーネントの constraint に `external` を足し、授受する外部を書く(必須。無ければ `none`) | `external 決済代行`                 |

- 三案とも、`external` の名前が親(システム)の `external` にある事を求める。外部は段を上がっても外部である(E0018-5 と同じ向き)。
- 三案とも、`external` に書かない相手(データベース・HTTP の呼び手)には何も足さない。そちらは今どおりコンポーネントの intent の `why` と、境界の層に現れる。

### 3.2 フローの端点 — 二案

| 案                 | 形                                                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 端点に書かない案   | 外部はフローに現れない。外部の前に立つコンポーネント(PaymentBridge など。以下「前に立つコンポーネント」)が端点になり、外部との授受は body と境界の層が行う |
| 外部を端点に書く案 | `PaymentBridge -> 決済代行 : ask ...` のように、外部をフローの端点に書く。ADR 0031 の決定6 の範囲を外部との接続へ広げ、`on failure` の対象に外部を入れる   |

- 今の仕様は端点に書かない案の形である。ADR 0031 の机上検証1 も、決済代行をフローに書かず PaymentBridge を端点にしている。
- **二つの問いは独立ではない。** `depends` を広げる案を採ると、ADR 0031 の決定6 の E0031-4(`depends` の相手との接続がどのフローにも無い)が、決済代行との接続をフローに求める。
  端点に書かない案と組むには、E0031-4 から外部を除く一文が要る。

## 4. 書き下ろす

### 4.1 今の仕様で書く — センサー収集

第1章 1.7 の記述例に、コンポーネントの constraint を添える。intent と body は略す(本書の問いに関わらない)。

```plaintext
system センサー収集 {
  intent { ... }
  constraint {
    actor    運用者 "閾値超過の通知を受け取る"
    external センサー機器群 "多数の機器。計測値を送ってくる"
    external 通知基盤 "外部の通知手段。Alerter が使う"
    depends  通知基盤
    expose   計測値の受け入れ(計測値) flow in   by SensorIntake
    contains SensorIntake, Normalizer, Aggregator, MetricStore, Alerter
  }
}

component SensorIntake {
  constraint {
    depends  Normalizer
    expose   計測値の受け入れ(計測値) flow in
    expose   計測値(計測値) flow out
    state    none
    collator none
    layers {
      受信 { io   boundary }   # MQTT の授受
      読取 { pure parse    }   # バイト列 -> 計測値
      送出 { io   domain   }   # Normalizer への流れ
    }
  }
}

component MetricStore {
  constraint {
    depends    none
    expose     保存(集約値) flow in
    idempotent 保存
    state      none
    collator   none
    layers {
      保管 { io   domain   }
      書式 { pure format   }   # 集約値 -> 時系列データベースの行
      書込 { io   boundary }   # 時系列データベースとの授受
    }
  }
}

component Alerter {
  constraint {
    depends  none                # 通知基盤を呼ぶが、書けない
    expose   集約値(集約値) flow in
    state    none
    collator none
    layers {
      判定 { pure domain   }
      文面 { pure format   }   # 通知の文面
      送信 { io   boundary }   # 通知基盤との授受
    }
  }
}
```

- **Alerter は `depends none` と書く。** 通知基盤を呼ぶ事は、システムの `external` の説明文「Alerter が使う」にしか無い(思考実験 08 の論点3(外部を呼ぶコンポーネントの depends)と同じ穴)。
- **SensorIntake が受ける相手も書けない。** `expose 計測値の受け入れ` は、誰から届くかを言わない。センサー機器群から届く事は、システムの `external` の説明文にしか無い。
- MetricStore の時系列データベースは `external` に書いていないため、外部ではない(第1章 1.7)。境界の層 `書込` だけが、外の相手の存在を語る。
- **システムの `depends 通知基盤` は、W0018-1 に当たり得る。** W0018-1 は「`depends` に宣言した相手を、`contains` のどのメンバも呼んでいない」である。
  メンバの `depends` で判定するなら、メンバは外部を `depends` に書けないので、外部への `depends` は全て W0018-1 になる。第1章 1.7 の記述例そのものが警告を受ける(第6節)。

### 4.2 今の仕様で書く — 決済代行と PaymentBridge

ADR 0031 の机上検証1 はシステムを書いていない。本書では受注の一生の5つのコンポーネントを、一つのシステム「注文管理」に入れる(第1章 1.5 の例では、決済代行は通販の `external` にある)。

```plaintext
system 注文管理 {
  intent { ... }
  constraint {
    actor    買い物客 "注文を送り、受注の状態を受け取る"
    external 決済代行 "外部の事業者。PaymentBridge が依頼を送り、結果を通知してくる"
    depends  決済代行
    expose   受注(注文) -> 受注番号 | 受注不可   by Frontdesk
    contains Frontdesk, OrderIntake, Inventory, OrderStore, PaymentBridge
  }
}

component PaymentBridge {
  intent {
    why      "決済代行の要求の形式・認証・結果の通知の受け方を、このコンポーネントに閉じ込める。
              内側は決済の依頼と決済の結果というデータだけを扱う"
    rejected option "OrderStore が決済代行を直接呼ぶ"
             reason "決済代行の差し替えが、受注台帳の永続化を持つコンポーネントに波及するため"
    change   "決済代行の追加を想定。公開面(決済の依頼と決済の結果)は変えない"
  }
  constraint {
    depends    OrderStore
    expose     決済の依頼(決済の依頼) flow in
    expose     決済の結果(決済の結果) flow out
    idempotent 決済の依頼
    state      none
    collator   none
    layers {
      中継 { io   domain   }   # OrderStore との流れの受け渡し
      要求 { pure format   }   # 決済の依頼 -> 決済代行の要求のバイト列
      通信 { io   boundary }   # 決済代行との授受(要求の送信と、結果の通知の受信)
      読取 { pure parse    }   # 結果の通知のバイト列 -> 決済の結果
    }
  }
  body { ... }
}
```

```plaintext
# PaymentBridge の body(擬似)
決済の依頼(依頼) を受けたら:
  要求 = 決済代行の要求に組む(依頼)              # format の層
  応答 = 待つ 決済代行へ 要求 を送る              # boundary の層。期限はどこにも宣言されていない
  応答が 受付済み なら 何もしない                  # 結果は後から通知で来る
  応答が 拒否(理由) なら 決済の結果 を流す : 決済不成立(受注番号, 理由)
決済代行から 通知 を受けたら:                     # boundary の層
  結果 = 決済の結果に読む(通知)                    # parse の層
  決済の結果 を流す : 結果
```

- **決済代行への要求には、期限がどこにも無い。** `ask` なら `deadline` が必須(ADR 0008)だが、外部への要求は `ask` ではない。
  思考実験 26 の論点5(外への要求の期限)は、ここに当たる。既存の言語の lint の方が先に「外への要求に期限が無い」を拒める。
- **決済代行が要求に答えない時、何が起きるかを書く場所が無い。** ADR 0031 の決定1(四つの置き場)を当てる。

| 置き場           | 決済代行への要求の失敗が入るか                                                                      |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| データの区分     | 入れられる。記述者が `決済の結果` に `決済代行に届かなかった` の区分を足せば、OrderStore まで流せる |
| 演算と解析の失敗 | 入らない。言語の操作の失敗ではない。応答のバイト列を読めなかった時だけ、解析の失敗になる            |
| 接続の失敗       | 入らない。動作環境が運ぶ接続ではなく、`flow` 宣言にも無い                                           |
| 待ちの期限切れ   | 結果として入る。誰も何もしなければ、OrderStore の `within 30 分` が `on expiry 決済の結果` で拾う   |

- **今の仕様では、記述者は三つの書き方のどれでも書ける。** データの区分にして流す、body で障害にして `restart` に任せる、黙って捨てて期限切れに任せる。
  言語はどれも求めず、どれも拒まない。決済代行の沈黙は待ちの期限切れが受ける(ADR 0031 の机上検証2)が、それは最後の網であり、30 分かかる。
- **障害にすると、再送が呼び直しになる。** `決済の依頼` は durable で受け口は idempotent なので、PaymentBridge が再起動すると動作環境が同じ依頼を再送し、body はもう一度決済代行を呼ぶ。
  ADR 0031 の決定8 は「再試行は接続の属性として足し、既定値を置かない」としたが、この形では再試行が言語の外で、回数も間隔も書かれずに起きる。
  決済代行が要求の重複を許さない相手なら、二重の決済になり得る。PaymentBridge の `idempotent` は「PaymentBridge が二度受けても効果が一度」の約束であり、決済代行の側の重複を守らない。
- **決済代行は往復する相手である。** システムの `depends 決済代行` は依頼を送る向きを言うが、結果の通知が決済代行から PaymentBridge へ来る向きは、どこにも書かれない。
  センサー機器群(送ってくるだけ)と通知基盤(呼ぶだけ)の両方の性質を持つ。

### 4.3 外部依存の三案で書く

#### `depends` を広げる案

```plaintext
component Alerter       { constraint { depends 通知基盤 ... } }
component PaymentBridge { constraint { depends OrderStore, 決済代行 ... } }
component SensorIntake  { constraint { depends Normalizer ... } }     # センサー機器群は呼ばないので書かない
```

- Alerter と PaymentBridge の穴は塞がる。E0018-3(`depends` の相手が兄弟・親の兄弟・`external` のどれでもない)を、コンポーネントにも親の `external` を許す形に広げればよい。
- **SensorIntake の相手は書けないままである。** `depends` は「呼ぶ」の宣言であり、送ってくるだけの相手は載らない。システムの段で `external` と `depends` を分けた理由(第1章 1.4)が、そのまま効く。
- **E0031-4 が決済代行との接続をフローに求める**(フローの端点の二案、第3.2節)。この案は、外部を端点に書く案と組むか、E0031-4 から外部を除くかのどちらかを伴う。
- `depends` に、動作環境が運ぶ相手(兄弟)と境界の層が運ぶ相手(外部)が混ざる。E0000-2(`depends` 宣言外の相手への通信)を見る時、二つは検査の仕方が違う。

#### システムの `depends` に担い手を書く案

```plaintext
system センサー収集 {
  constraint {
    depends  通知基盤 by Alerter
    expose   計測値の受け入れ(計測値) flow in   by SensorIntake
    ...
  }
}
system 注文管理 {
  constraint {
    depends  決済代行 by PaymentBridge
    ...
  }
}
```

- **`expose ... by`(入る側の担い手)と `depends ... by`(出る側の担い手)が対になる。** ADR 0015 が `expose` に担い手を置いた理由(システムの境界は担い手の公開面として実在する)と同じ形である。
- SensorIntake は `expose ... by` に既に現れている。送ってくる相手の受け手は、入口の担い手として書ける。ただしその入口が**誰から**届くかは、まだ言わない。
- **コンポーネントだけを読むと、外部を呼ぶ事が分からない。** Alerter は `depends none` のままであり、第0章 0.5(各段の記述はそれ自体で読める)に擦れる。
  親の `by` を見て初めて分かる。`expose` の側は、担い手の側にも同じ受け口がある(E0015-3)ので擦れない。
- 担い手の検査は、`by` に書いたコンポーネントに境界の役割の層がある事くらいしか見られない。入れ子が深ければ、`by` を段ごとに書き継ぐ(公開面の転記と同じ代価)。

#### コンポーネントにも `external` を置く案

```plaintext
component SensorIntake  { constraint { external センサー機器群  depends Normalizer ... } }
component Normalizer    { constraint { external none            depends Aggregator ... } }
component Aggregator    { constraint { external none            depends MetricStore, Alerter ... } }
component MetricStore   { constraint { external none            depends none ... } }
component Alerter       { constraint { external 通知基盤        depends none ... } }
component PaymentBridge { constraint { external 決済代行        depends OrderStore ... } }
```

- **向きを問わずに書ける。** 送ってくる相手(センサー機器群)も、呼ぶ相手(通知基盤)も、往復する相手(決済代行)も同じ語で書ける。システムの段の `external` と同じく、存在(授受する)の宣言だからである。
  向き(誰が呼ぶか)は、外部を端点に書く案ならフローが、端点に書かない案なら body が持つ。
- **`depends` は記述の中の相手だけのままである。** E0031-4 は変わらない。動作環境が運ぶ相手(`depends`)と境界の層が運ぶ相手(`external`)が、語で分かれる(二つの軸の表(第2.1節)の二つの列)。
- **省略の禁止で、全てのコンポーネントに一行増える。** 14 のコンポーネントのうち、`external` に名前を書くのは5つ、`external none` が9つである。
- 検査が二つ立つ。コンポーネントの `external` が親の `external` に無ければエラー(E0018-5 を下へ延ばす)。親の `external` を、どのメンバの `external` も挙げていなければ、使わない外部である(第6節)。
- コンポーネントの `external` に名前を書いたのに、境界の役割の層が無ければ、授受する層が無い。逆(境界の層があり `external none`)は、MetricStore のように外部の技術を隠すコンポーネントであり、正しい。

| 見る事                          | `depends` を広げる案               | システムの `depends` に担い手を書く案 | コンポーネントにも `external` を置く案 |
| ------------------------------- | ---------------------------------- | ------------------------------------- | -------------------------------------- |
| Alerter・PaymentBridge が呼ぶ事 | 書ける(コンポーネントに)           | 書ける(システムに)                    | 書ける(コンポーネントに)               |
| SensorIntake が受ける事         | 書けない                           | 入口の担い手としてだけ書ける          | 書ける                                 |
| 決済代行の往復                  | 依頼の向きだけ                     | 依頼の向きだけ                        | 向きを問わない                         |
| コンポーネントだけで読めるか    | 読める                             | 読めない                              | 読める                                 |
| E0031-4 への影響                | 外部をフローに求める               | 無い                                  | 無い                                   |
| 増える宣言                      | 外部を呼ぶコンポーネントの名前だけ | システムの `by` だけ                  | 全てのコンポーネントに一行             |

### 4.4 フローの端点の二案で書く — 受注の一生

#### 端点に書かない案

ADR 0031 の机上検証1 の `flow 受注の一生` が、そのままこの案である。決済代行は現れない。

```plaintext
  OrderStore    -> PaymentBridge : flow 決済の依頼 pressure block(deadline 1 秒) (durable)
  PaymentBridge -> OrderStore    : flow 決済の結果 pressure block(deadline 1 秒) (durable)
  correlate 受注番号 : 受注 -> 保存 -> 決済の依頼 -> 決済の結果 within 30 分 -> 受注の状態
  on expiry 決済の結果 { ... }
```

- 決済代行の沈黙は、OrderStore の `within 30 分` が受ける。**前に立つコンポーネントが居れば、待ちの期限切れの仕組みはそのまま効く。** 時計は OrderStore の動作環境にあり、決済代行の時計は要らない。
- 決済代行への要求の期限と、その失敗の置き場は、決済代行と PaymentBridge の書き下ろし(第4.2節)のとおり body に沈む。
- 外部が図(Phase 3)のフローに現れない。思考実験 08 の論点7(原簿が届く経路がフロー図に現れない)は残る。

#### 外部を端点に書く案

```plaintext
  OrderStore    -> PaymentBridge : flow 決済の依頼 pressure block(deadline 1 秒) (durable)
  PaymentBridge -> 決済代行      : ask 決済(決済の要求) deadline 10 秒 -> 受付済み | 拒否
  決済代行      -> PaymentBridge : flow 決済の通知 pressure ? (?)
  PaymentBridge -> OrderStore    : flow 決済の結果 pressure block(deadline 1 秒) (durable)
  correlate 受注番号 : 受注 -> 保存 -> 決済の依頼 -> 決済 -> 決済の通知 within 30 分 -> 決済の結果 -> 受注の状態
  on failure 決済代行 at 決済 {
    PaymentBridge -> OrderStore : 決済の結果      # 決済不成立(受注番号, 決済代行に届かなかった) を流す
    restart ?                                     # 外部は再起動できない
  }
```

書いてみると、五つの所で今の規則が立たない。

1. **外部の公開面が無い。** 接続の両端は `depends`・`expose` と突き合わせる(E0000-2・E0000-3)。決済代行には `expose` が無く、`決済(決済の要求) -> 受付済み | 拒否` を突き合わせる先が無い。
   外部の公開面を宣言する所(例えばシステムの `external` に公開面を添える)が要る。その型は、境界の層と解析の層が外の形式から読んだ**後の**型である。
2. **運ぶのが動作環境ではない。** `ask` の期限は動作環境が測る(第4章 4.2)。決済代行への要求は HTTP であり、動作環境は話せない(動作環境はコンポーネントの値を解釈しない。ADR 0012)。
   この行は、PaymentBridge の境界の層が行う授受を、フローの上に宣言したものになる。期限を誰が測るか——境界の層が自分で測るか、動作環境に計時だけを頼む呼び出しを接合面に足すか——が新しく問われる。
3. **外部から来る流れに、`pressure` と配達保証の意味が立たない。** `pressure block` は上流を待たせるが、決済代行を待たせる手段は HTTP の応答を遅らせる事しか無い。
   `durable` は動作環境が永続化と再送を担う意味だが、決済代行の通知の再送は決済代行の方針であり、こちらの動作環境のものではない。
4. **`on failure 決済代行` に `restart` を書けない。** 第4章 4.5 は `restart` を必須とする(E0008-1)。外部は再起動できないので、外部については `restart` を求めない一文が要る。
   残る中身(接続の行と `respond`)は前に立つコンポーネントが行うので、今の形のまま書ける。
5. **鍵が外部を通るとは限らない。** `correlate 受注番号` で `決済 -> 決済の通知` を結ぶには、決済代行の通知に受注番号が載っていなければならない。
   決済代行は自分の取引番号で通知する事が多く、加盟店の参照番号を返すかは相手次第である。**鍵の型が届く物に現れるかは、外部の仕様が決める**(E0023-2 は型の入れ子を辿るだけである)。

- 得る物もある。外部の失敗が接続の失敗になり、`on failure` に置き場ができる。ADR 0031 の決定6 を外部へ広げれば、外部との授受がどのフローにも無い事を見つけられる。外部が図に現れる。
- **得る物の多くは、外部の公開面の宣言(1)と、期限の測り手(2)を決めて初めて手に入る。** 端点に書くかどうかより、その二つの方が重い。

## 5. 外部の時刻表現を分ける

第6章 6.6 の未定事項(外部の時刻表現を `時点` と `時間帯` に分解する規則)を、題材に現れる時刻で見る。
ISO 8601 は日時の表記の国際規格であり、Unix 秒は 1970-01-01T00:00:00Z からの秒数である。tzdata は IANA(Internet Assigned Numbers Authority)の時間帯の規則の表である。

| 外の表現         | 例                                | 出どころ                                | `時点` になるか                                                   | `時間帯` は分かるか                                           |
| ---------------- | --------------------------------- | --------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------- |
| 時差付きの日時   | `2026-11-05T10:15:00+09:00`       | 決済代行の決済日時(ISO 8601)            | なる(時差を引けば決まる)                                          | 分からない。`+09:00` は Asia/Tokyo とも Asia/Seoul とも読める |
| 地帯名付きの日時 | `2026-11-05T10:15:00[Asia/Tokyo]` | 外部の予約系など                        | なる(地帯名で `時点にする`)                                       | 分かる。ただし地帯名を解決できない事がある                    |
| 時差の無い日時   | `2026-11-05 10:15:00`             | 時系列データベースの時間帯の無い型      | 時間帯を与えれば `時点にする`。存在しない・二度ある時刻があり得る | 記述の外の約束(データベースの設定)にある                      |
| Unix 秒          | `1793841300`                      | 時刻を同期したセンサー機器              | なる                                                              | 要らない                                                      |
| 起動からの経過   | 起動から 3600 秒                  | 時刻を同期していない ESP32(思考実験 27) | ならない                                                          | 要らない                                                      |

- **時差付きの日時は、`時点` と時差に分かれる。`時間帯` には分かれない。** 第6章 6.4 のとおり、時差は `量 時間` の値であり、他の時間帯へ読み替えられない。
  決済日時を記録するだけなら `時点` で足りる。客に決済した地の暦で見せたいなら、時間帯は外の表現からは得られず、別の欄(店の所在地など)から引く事になる。
- **入りの道で `時点にする` を書ける層が無い。** 第6章 6.4 は `暦で読む`・`時点にする` を `boundary` と `format` の層に限る(E0019-5)。
  時差の無い日時を読むには、まず解析の層がテキストから(`日付`, `時刻`)を作り、それから `時点にする` を書く。ところが解析の層では書けず、
  役割の向き(boundary → parse → domain → format → boundary)で解析の層の後に来る `boundary`・`format` は、出る側の層である。文字どおり読むと、入ってきた時計の読みは `時点` にできない。
- **時差を引いて `時点` を作る事が、`時点にする` に当たるかが書かれていない。** 暦(グレゴリオ暦)で日数を数えるので暦の変換とも読めるし、時間帯を使わないので当たらないとも読める。当たるなら、上と同じく解析の層では書けない。
- **地帯名を解決できない時の扱いは、形の失敗ではない。** 送り手の tzdata が新しく、こちらの表に無い地帯名が届いた時、同じバイト列が表の更新の後には読める。
  ADR 0031 の決定7 の解析の失敗「形が合わない」に入れると、表の版の食い違いが形の誤りに見える。地帯の改名(Asia/Calcutta から Asia/Kolkata)は表が別名を持つので読めるが、廃止は読めない。
- **起動からの経過は、言語の型に無い。** 経過時間計は言語の型にしない(第6章 6.4)ため、時刻を同期していない機器は `時点` を送れない。
  SensorIntake が受けた時点を付ける事になり、`計測値` の `時刻` の欄は「測った時点」から「受けた時点」へ意味が変わる。型は同じ `時点` であり、違いは欄の名前にしか現れない。
- **tzdata を誰が持つか。** 第6章 6.6 は動作環境が tzdata を供給する形を未定としている。ESP32 の最小の動作環境が tzdata を持たなければ、`時点にする`・`暦で読む` を使うコンポーネントは
  能力(ADR 0029)で拒む対象になる。`collator` と同じ扱いである(思考実験 27 の第6節)。

## 6. 使わない依存 — W0018-1 の扱い

第1章 1.8 と ADR 0018 は、W0018-1 を警告に留めた理由を「同じ問いがコンポーネントの `depends` にも立つのに、そちらに検査が無いため」とした。
その後、ADR 0031 の決定6 が入り、事情が変わっている。

| 宣言                                 | 「宣言したが使わない」を見る検査                   | 強さ   |
| ------------------------------------ | -------------------------------------------------- | ------ |
| システムの `depends`(兄弟・親の兄弟) | W0018-1(どのメンバも呼んでいない)                  | 警告   |
| システムの `depends`(外部)           | W0018-1。ただしメンバは外部を `depends` に書けない | 警告   |
| コンポーネントの `depends`           | E0031-4(その相手との接続がどのフローにも無い)      | エラー |
| システムの `external`                | 無い                                               | —      |

- **非対称は逆向きになった。** ADR 0018 の時点では、コンポーネントの側に検査が無かった。今はコンポーネントの側が E0031-4 でエラーになり、システムの側が警告である。
  ADR 0018 が挙げた「片方だけをエラーにできない」理由は、記述の中の相手については、もう立たない。
- **外部への `depends` は、今の判定では必ず W0018-1 になる**(センサー収集の書き下ろし、第4.1節)。メンバの `depends` で判定する限り、外部を呼ぶメンバを書く場所が無いからである。
  W0018-1 の扱いは、外部依存の書き場所(第3.1節)が決まらないと決められない。
  - `depends` を広げる案なら、メンバの `depends` を見ればよく、W0018-1 は E0031-4 と同じ強さに揃えられる。
  - システムの `depends` に担い手を書く案なら、`by` が必須になり、「誰も呼ばない」は `by` の欠落として E0008-1(必須宣言の欠落)で見つかる。
  - コンポーネントにも `external` を置く案なら、システムの `external` のうち、どのメンバも挙げていない物が見える。`depends` ではなく `external` の側の検査になる。
- **センサー機器群のように `external` にだけ載る相手は、今はどの検査も見ない。** どのメンバも受けていない外部を宣言しても、何も言われない。

## 7. actor の使い道

actor は検証されない宣言である(第1章 1.4)。題材の actor が、記述のどこで外と繋がるかを見た。

| actor          | システム           | 届く所                                                                   |
| -------------- | ------------------ | ------------------------------------------------------------------------ |
| 買い物客       | 注文管理           | `expose 受注 by Frontdesk`(Frontdesk の境界の層が HTTP で受ける)         |
| 運用者         | センサー収集       | どの `expose` でもない。外部の通知基盤を経て通知を受け取る               |
| 買い物客       | 多言語商品カタログ | `expose 検索 by SearchGate`                                              |
| カタログ運用者 | 多言語商品カタログ | どの `expose` でもない。取込の失敗と訳の欠落を見る(手段は書かれていない) |

- **actor が届く所は、入口(`expose`)と、外部を経た出口の二つに分かれた。** 運用者は、こちらの入口を使わず、通知基盤という外部の向こうに居る。
  actor を `expose` に結ぶ形(どの入口を誰が使うか)を置くと、運用者は書けない。actor を外部に結ぶ形も要る。
- **権限に使う形は重い。** actor で入口を分けて権限を確かめるには、誰が要求したかがデータとして届かなければならない。
  HTTP の呼び手を認証するのは Frontdesk の境界の層であり、動作環境はコンポーネントの値を解釈しない(ADR 0012)。言語が権限を見るには、認証の結果を型として運ぶ形が要る。
- **図と意図のためだけに残す案も、検査を一つ持てる。** `expose` の担い手(E0015-3)と同じく、actor が入口か外部のどちらかに結ばれている事だけを見る形である。
  結ぶ先の書き方は、外部依存の書き場所(第3.1節)と同じ所で決まる。

## 8. 役割の向きと通信 — 役割の向きと通信の関係(U20)

### 8.1 「外部」の語義(思考実験 08 の論点1)

二つの軸の表(第2.1節)で、二つの語は別の軸に答えていると分かった。

- `external` は**誰が相手か**(記述の外にある系)を言う。
- 役割「境界」の「外部とのバイト列の授受」は、**何の形で授受するか**(外の形式)を言う。相手が `external` かどうかは問わない。データベースも HTTP の呼び手も素子も入る。
- 語を揃える形は二つある。役割の表の「外部」を「外の形式」に言い換えて `external` と切り離す形と、`external` の側を「記述の外の系」と言い換えて役割と切り離す形である。
  どちらも、二つの軸の表(第2.1節)の左中の欄(動作環境で話す外部)を持つかで差が出る。動作環境で話す外部には、境界の層が要らない。

### 8.2 役割の向きはコンポーネント間の通信に及ぶか(思考実験 08 の論点2)

- `ask` と `flow` は動作環境が正準形で運ぶ。コンポーネントの層はバイト列を見ない(接合面を流れるのは正準形のバイト列と型の指紋だけで、骨組みはバックエンドが生成する。ADR 0012)。
  したがって、領域の層が `ask` を出す事は「領域でのバイト列化」に当たらない。PaymentBridge の `中継 { io domain }` が OrderStore へ流す事も同じである。
- **役割の向きは外の形式の授受にだけ掛かる**と書けば、思考実験 08 の論点2(役割の向きと通信)は閉じる。二つの軸の表(第2.1節)の右の列にだけ掛かり、左の列には掛からない。
- **ただし、外部を端点に書く案と擦れる。** 外部を端点に書くと、境界の層が運ぶ授受がフローの接続にもなる(フローの端点の書き下ろし(第4.4節)の二つ目、運ぶのが動作環境ではない)。そのフローの行の型(`決済の要求`)は、境界の層と書式・解析の層を通った後の型である。
  役割の向きの範囲(右の列)と、フローの範囲(左の列)が、外部との接続でだけ重なる。外部世界との境界(U12)と役割の向きと通信の関係(U20)を同じ段で決める理由は、この重なりにある。
- 思考実験 32 の第10節(再入を選ぶ単位の数え上げ)が出した「待つ所の範囲(`io` の層の外部への入出力を含むか)」も、同じ右の列の話である。PaymentBridge の `待つ 決済代行へ 要求 を送る` は、境界の層の中の待つ所である。

### 案の素描(ADR へ渡す)

- **論点1(外部依存の書き場所)・論点7(W0018-1)**: コンポーネントにも `external` を置く案が、向き(送ってくる・呼ぶ・往復)を問わずに書け、`depends` を記述の中の相手(動作環境が運ぶ相手)に保てる。
  増える一行は、省略の禁止(ADR 0008)の代価として `collator none` と同じ種類である。この案なら W0018-1 は、`external` の側の検査(どのメンバも挙げない外部)と、
  `depends` の側の検査(どのメンバも `depends` に書かない兄弟・親の兄弟。E0031-4 と揃えてエラーにできる)に分けられる。
- **論点2(フローの端点)・論点3(外部への要求の期限と失敗の置き場)**: 外部の公開面と期限を、コンポーネントの `external` の行に添える形が考えられる(仮の形 `external 決済代行 { 決済(決済の要求) -> 受付済み | 拒否 deadline 10 秒 }`)。
  外部をフローの端点に書くかは、その後に決められる——公開面と期限が宣言されていれば、端点に書く時に突き合わせる先と測る値がある。
  期限を測るのは境界の層ではなく動作環境とし、接合面に計時の呼び出しを足す形が、ADR 0031 の決定11(待ちを動作環境に預ける)と同じ向きである。
- **論点3(外部への要求の期限と失敗の置き場)**: 外部への要求の失敗を、言語が持つ型(演算と解析の失敗と同じく、ADR 0031 の決定7 の形)で境界の層に返す案。前に立つコンポーネントの body が、データの区分へ翻訳するか障害にするかを書く。
  障害にした時の再送が呼び直しになる事は、W0031-1(durable な受け口で演算の失敗を障害にする)と同じ形の警告で拾える。
- **論点4(「外部」の二つの軸)・論点9(役割の向きの範囲)**: 役割の表の「外部」を「外の形式」に言い換え、`external` と切り離す案。役割の向き(E0013-4)の範囲は外の形式の授受に限ると書く。
- **論点5(システムの `expose` の届き方)**: システムの `expose` は、動作環境の受け口とする案。外の形式で受ける入口は、担い手のコンポーネントの `external`(論点1(外部依存の書き場所))が語る。
- **論点6(外部の時刻表現)**: 入りの道の `時点にする` を、境界の層の直後の解析の層にも許す案。tzdata の版は表示にしか効かない(第6章 6.4)という理由は、入りの道では成り立たない——読んだ `時点` は状態に入る。
  ここは型と単位の領域の判断であり、本書は渡すだけにする。

## 10. 所見

- **八つの問いは、「外部」が二つの軸の語である事に集まった。** `external`(誰が相手か)と、境界の層(何の形で授受するか)である。
  外部依存の書き場所・フローの端点・役割の向き・システムの `expose` の届き方は、どれも二つの軸を一つの語で呼んだ所から擦れていた。外部世界との境界(U12)と役割の向きと通信の関係(U20)を同じ段で決めるとした計画書の判断は、書き下ろしても正しかった。
- **外部依存は例外ではない。** 14 のコンポーネントのうち 10 が外の形式で授受していた。`external` の相手は 5 である。
- **端点に書くかどうかより、外部の公開面と期限の方が重い。** 端点に書かなくても、前に立つコンポーネントと待ちの期限切れで、外部の沈黙は受けられた。
  受けられないのは、外部への一回の要求の期限と、その失敗の置き場である。
- **ADR 0031 の決定6 が、ADR 0018 の残した非対称を逆向きにしていた。** W0018-1 を警告に留めた理由は、記述の中の相手については既に無い。

## 11. 未解決課題への入力

外部との境界の領域の外へ渡す物。各領域の作業で取り込む。

- **型と単位の領域(ADR 0019・第6章 6.4)**: 入りの道で `時点にする` を書ける層が無い(論点6)。時差から `時点` を作る事が `時点にする` に当たるか。解決できない地帯名の失敗の区分。
- **通信と失敗の領域(ADR 0031)**: 外部への要求の失敗が四つの置き場のどれにも決まって入らない事(論点3)。外部について `on failure` の `restart` を求めない一文(論点2)。
  durable の再送が外部への呼び直しになる事と、W0031-1 に倣う警告(論点3)。
- **実行モデルの領域(コンポーネントの実行モデル(U10))**: 境界の層の中の待つ所(PaymentBridge が決済代行を待つ所)。思考実験 32 の第10節(再入を選ぶ単位の数え上げ)の「待つ所の範囲」と同じ問いである。
- **プログラムの宣言の領域(プログラムの宣言(U14))**: W0018-1 の扱い(論点7)。ADR 0018 は W0018-1 をエラーへ上げるかをプログラムの宣言(U14)で扱うとした。外部依存の書き場所が決まった後に揃える。
- **動作環境の領域**: 外部への要求の期限を動作環境が測るなら、接合面に計時の呼び出しが要る(論点2)。ESP32 の最小の動作環境が tzdata を持つか、持たないなら能力で拒むか(論点6)。

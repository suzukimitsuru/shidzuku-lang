## 1. 問いの置き直し

### 1.1 Shidzuku の名前の種類

問いに挙がった名前の種類は、オブジェクト指向の言語の語である。Shidzuku にはクラスもメソッドも無いため、先に写す。

| 問いの語         | Shidzuku で当たる物                                                                   | 定める所            |
| ---------------- | ------------------------------------------------------------------------------------- | ------------------- |
| コンポーネント名 | `system`・`component`・`actor`・`external` の名前                                     | 第1章・第2章        |
| クラス名         | `record`・`choice`・`id` の名前、量・単位・暦の名前                                   | 第6章               |
| メンバー名       | `record` の欄名、`choice` の区分名、`state` の名前、内部階層(`layers`)の名前          | 第2章・第3章・第6章 |
| メソッド名       | 公開面(`expose`)の名前、`flow` 宣言の名前                                             | 第3章・第4章        |
| 変数名           | 公開面の引数名、body の中の関数名・変数名(body の記法(U26)が決まっていないため未確定) | 第3章・第5章 5.4    |

いずれも「記述者が定める名前」(第5章 5.1、ADR 0014)である。現在の仕様では UTF-8 で書け、日本語の名前は正規の記述である。
言語が名前に課している規則は、文字集合(UAX #31(Unicode 標準附属書 第31号、識別子の構文))・正準形(NFC(正規化形 C))・見分けのつかない名前の禁止(E0014-3)の三つだけで、**語の選び方には何も言っていない**。

### 1.2 なぜ名前の規則が Shidzuku の問題になるか

Shidzuku は名前に多くを負わせている。

- **名前的型付け**: 構造が同じでも名前が違えば別型である(第6章 6.1)。`受注番号` と `受付ID` の区別は名前だけが担う。
- **型の名前が値の出どころを告げる**(第6章 6.6)。論理型を公開面に書けず、名前の付いた直和を書かせるのも(論理型の置き場の検査、E0019-1)、名前に語らせるためである。
- **図はコードからの投影である**(第0章 0.7)。図の節に載るのは名前であり、名前が揃っていなければ図も揃わない。

名前の語が揃っていない事は、型の検査では見つからない。`受注番号` と `注文番号` が同じ物を指すつもりで書かれても、名前的型付けは二つを別型として**正しく**拒む。
拒まれた記述者は変換を書くか、片方に寄せるかを迫られるが、どちらに寄せるべきかを言語は知らない。

### 1.3 呼び名 — 用語辞典と用語辞書

suzukimitsuru の指示により、「用語辞典」を「用語辞書」に変えても結論が同じかを確かめた。**結論は同じである。**

- 第4節の規則は、記述者が宣言した文字列と宣言の種類を比べるだけで、仕組みの呼び名には依らない。呼び名を変えても、判定は一つも動かない。
- 呼び名としては「辞書」の方が合う。母国語と英語の対応表を兼ねる(前提)ので、英和辞書のように**語を引いて訳と意味を得る**物になるためである。
  先行例も「辞書」と呼ぶ。Deissenboeck と Pizka の識別子の辞書(identifier dictionary)、cspell の辞書(dictionary)、codic の「ネーミング辞書」である(第7節)。
- 仕様の中で「辞書」は他の物を指していない(ADR 0015(C4 モデルの命名の取り込み)の「辞書データの配布元」は業務の例であり、言語の語ではない)。
- キーと値の対応の型(第6章 6.6 の未定事項)は対応表(map)と呼び、辞書とは呼ばない(suzukimitsuru の判断、2026-10-15)。「辞書」は用語辞書のように語を引く物に限って使う。

### 1.4 呼び名 — 「用語」と「語彙」と、他の候補

辞書は見出し語を引いて中身を得る物であり、「〇〇辞書」の〇〇は**見出し語が何か**を言う語になる。用語辞書なら、見出し語は用語で、中身は役・母国語の語・定義である。その上で、suzukimitsuru の指示により、「用語」を「語彙」に替えた「語彙辞書」が「用語辞書」より的確になるかを調べた。
**「語彙辞書」は「用語辞書」より的確にならない。** 理由は三つある。suzukimitsuru の判断により「用語辞書」のままとした。

1. **語彙は語の集まりを指し、一つ一つの語を指さない。** 見出し語は一つの語であり、「語彙を見出し語に持つ辞書」とは言えない。
   辞書は元々ある言語や分野の語彙を収めた物であり(言語学では辞書を「ある目的のために語彙の一部を表した物」と見る)、「語彙辞書」は重ね言葉に近い。
2. **Shidzuku の仕様では「語彙」は主に言語が定める語を指す。** 第5章 5.1・5.3 の「言語が定める語彙」、「語彙を ASCII に揃えた」「丸めの語彙」「通信の語彙」のように、キーワードと型の名前に使ってきた。
   記述者が定める物は「名前」と呼び分けている(第5章 5.1)。「語彙辞書」は言語のキーワードの辞書と読まれる。
3. 逆に、辞書の**中身の総体**を「業務の語彙」「共有語彙」と呼ぶのは合っている。辞書が収める物の総体は語彙であり、見出しの一つ一つは用語である。

他の候補も同じ物差しで比べた。

| 呼び名       | 見出し語                   | 合う所                                                                                                              | 合わない所                                                                   |
| ------------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 用語辞書     | 用語(分野で意味を定めた語) | 定義を持つ事と合う。日本語の論理名と英語の物理名を相互に変換する道具も「用語集」を元にする(富士通の Naming Utility) | 添える語(`done`)のような一般の語も載る                                       |
| 語彙辞書     | (語の集まり)               | 辞書の中身の総体が業務の語彙である事は言える                                                                        | 見出し語を指さない。言語の語彙と紛れる                                       |
| 単語辞書     | 単語                       | 名前を単語の並びとして組む事(語の閉包)と合う。形態素解析の辞書や、データ項目名の標準化の単語辞書と同じ呼び方        | 分野で意味を定めた語である事が言えず、定義の欄が脇役に見える                 |
| 命名辞書     | (名前を作る語)             | 目的(名前を付ける)をそのまま言う。codic の「ネーミング辞書」                                                        | 見出しは名前ではなく語である。図・ログで母国語の名前を引く用途と定義が外れる |
| 対訳辞書     | 母国語と英語の組           | 母国語と英語の対応表である事を言う                                                                                  | 役と定義が入らない                                                           |
| ドメイン辞書 | 業務の語                   | ドメイン駆動設計の言い方と合う                                                                                      | `domain` は層の役割の語(第2章 2.4)であり紛れる                               |

**「用語辞書」のままが最も的確である。** 次点は「単語辞書」で、名前を単語の並びとして組む規則を前に出したい時の候補になる。

言語の語彙の綴りは仮に `glossary` のままとする。英語の glossary は特定の分野の用語に説明を添えた一覧であり、「用語」と同じ所を指す。
`lexicon`(語彙目録)は「語彙辞書」に当たり、上の1・2 と同じ理由で外す。`dictionary` は多くの言語でキーと値の対応の型を指すため(C# の `Dictionary`、Python の `dict`)、宣言の語には使わない。

## 2. 既存の名前の棚卸し

思考実験 01〜28 に現れた名前から、同じ物か近い物を指すのに語が揃っていない所を拾った。題材ごとに書かれた時期が違うため揺れは当然であり、責める物ではない。**用語辞書があれば何が見えたか**を見るための材料である。

| 揺れ                   | 現れた名前                                                                                                                                       | 出どころ                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| 識別子を表す語         | `品目ID`・`受付ID`・`従業員ID`・`拠点ID`・`センサーID` / `受注番号`・`引当番号`・`打刻番号` / `商品コード` / `キー`                              | 思考実験 05・08・10・12・21 |
| 公開面の名前の形       | `受注`・`引当`・`照会`(名詞の形) / `請求する`・`按分する`(動詞の形)                                                                              | 思考実験 01・06             |
| 「の」の有無           | `受注の照会` / `実績照会`、`引当の結果`・`決済の結果` / `受注結果`・`検索結果`                                                                   | 思考実験 05・10・12・20・21 |
| 送り仮名               | `引当済` / `引当済み`・`正規化済み` / `済`                                                                                                       | 思考実験 01・02・08・21     |
| 同じ事態の別の語       | `在庫不足` / `在庫なし` / `在庫切れ`                                                                                                             | 思考実験 01・20・21         |
| 字種                   | `OrderIntake`・`Frontdesk`・`PaymentBridge` と `注文管理` が同じ `contains` に並ぶ。`在庫同期` は日本語                                          | 思考実験 18・20             |
| 一つの語が二つの役     | `受注` が公開面の名前(`expose 受注(注文)`)と、直和の区分名(`choice 受注結果 = 受注(受注番号) \| …`)の両方                                        | 思考実験 01・05・12         |
| コンポーネント名の品詞 | 担い手(`Frontdesk`・`SearchGate`・`PaymentBridge`)/ 物(`Inventory`・`ShiftPlan`・`ProductIndex`)/ 働き(`OrderIntake`・`CatalogSync`・`在庫同期`) | 思考実験 01・08・10・18・20 |

棚卸しから分かった事は三つある。

1. **揺れの多くは「同じ概念に二つの語」である。** 識別子を表す語(`ID`・`番号`・`コード`・`キー`)と、在庫が足りない事態(`不足`・`なし`・`切れ`)がその例である。
   別の概念として使い分けているのか、同じ物を別の語で書いただけなのかは、名前からは分からない。
2. **語の並びは同じで、繋ぎだけが違う物がある。** `受注の照会` と `実績照会` は「何を照会するか」の書き方が二通りある。`引当の結果` と `受注結果` も同じである。
3. **名詞と動詞の境目が日本語では曖昧である。** `受注`・`引当`・`照会` はサ変名詞(「する」を付けて動詞になる名詞)で、物(受けた注文)も働き(注文を受ける事)も指す。
   `受注` が公開面の名前と区分名の両方に現れたのは、この曖昧さによる。

前提(コードは英語)の下では、これらの揺れは**母国語の語と英語の語の対応の揺れ**として現れる。
識別子を表す語なら `Id`・`Number`・`Code`・`Key` のどれに対応させるか、送り仮名の揺れは母国語の欄の中の揺れになる。
字種の混在はコードからは消えるが、`OrderIntake` と `注文管理` は「`注文管理` を英語で何と書くか」という対応の問題に変わる。

## 3. 用語辞書の形(試案)

規則を当てるために、用語辞書を仮に置く。言語の語彙(`glossary`・`term`・`native` など)は全て仮であり、ADR 0014 の決定2(言語の語彙は ASCII)に従う。

```plaintext
glossary commerce {
  native ja
  term order    thing    ja "注文"     "客が品目と数量を示して出す依頼"
  term accept   action   ja "受注"     "店が注文を受け、受注番号を振る事"
  term accepted modifier ja "受注済み" "受注が成った状態"
  term inquire  action   ja "照会"     "記録を変えずに読む事"
  term number   thing    ja "番号"     "店が振る連番。外部の符号は code と書く"
  term code     thing    ja "コード"   "外部の事業者が振った符号。店は振らない"
  term desk     agent    ja "窓口"     "外からの依頼を受け、内側の言葉に直して渡す役"
  term refusal  thing    ja "不可"     "業務の規則により受け付けない事"
  rejected term id       use number, code reason "店が振るか外部が振るかを語で分けるため"
  rejected ja   "オーダー" use order     reason "母国語の欄も 注文 に揃える"
}
```

辞書を引く側のコードは ASCII だけで書く(辞書の語は一部だけを示した)。

```plaintext
id     OrderNumber
record Order { item: ItemCode, quantity: uint32(0) piece }
choice AcceptResult = Accepted(OrderNumber) | AcceptRefusal(RefusalReason)

component OrderDesk {
  constraint {
    expose accept(Order) -> OrderNumber | AcceptRefusal
    expose inquire(OrderNumber) -> OrderState | InquireRefusal
    ...
  }
}
```

- `term` は英語の語と、その**役**と、母国語の語と、定義を持つ。定義は機械が検証しない文であり、意図の層(第0章 0.5)と同じ扱いになる。
  定義と母国語の語はテキストであって名前ではないため、前提の下でも母国語で書ける。
- `native` は母国語の欄の言語を宣言する。欄を増やせば(`ja`・`fr`)、一つの辞書が複数の母国語の対応表になる。
- **役は品詞ではなく、Shidzuku の宣言の種類に結び付ける。** 名詞・動詞という文法の区別は自然言語ごとに違うが(第2節の三つ目)、宣言の種類は言語が定めている。

| 役         | 意味             | 名前の中心に据えてよい宣言                                                      |
| ---------- | ---------------- | ------------------------------------------------------------------------------- |
| `agent`    | 担い手           | `system`・`component`・`actor`・`external`                                      |
| `thing`    | 物               | `record`・`choice`・`id`・`state`・`record` の欄・`choice` の区分・量・単位・暦 |
| `action`   | 働き             | `expose`(公開面の名前)・`flow` 宣言                                             |
| `modifier` | 他の語に添える語 | 単独では名前の中心にならない                                                    |

- **語の切れ目は言語が定める。** ASCII の名前は、`_`、小文字から大文字への変わり目、数字の前後で語に分かれる(`OrderNumber` は `Order` と `Number`)。
  これは文字の性質であって自然言語の文法ではない。母国語で書く場合に要った繋ぎ(「の」)の宣言は要らなくなる。
- 図・ログ・診断に母国語の名前を出す時は、語ごとに辞書を引いて並べる(`OrderNumber` は `注文` と `番号` で `注文番号`)。
  語順が母国語と同じとは限らない事と、既存の名前(`受注番号`)と並べた結果が一致しない事は、論点3(母国語の名前の組み立て)に残す。
- `rejected term` は**退けた語**と、代わりに使う語と、理由を持つ。意図の層の `rejected`(ADR 0003(検証不能な意図の記述形式))と同じ形である。
  母国語の欄の語も退けられる(`rejected ja`)。何を退けたかが残らなければ、後から来た記述者が同じ揺れを持ち込む。

## 4. 規則の候補と判定

規則の候補を一つずつ、第2節の揺れに当てる。判定は次の四つである。

| 判定                       | 意味                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| 言語が強制できる           | 宣言された文字列と宣言の種類だけを比べて判定できる。自然言語の文法に踏み込まない           |
| 英語を仮定すれば強制できる | 英語の語順(複合語の末尾が中心)を言語が仮定すれば判定できる。前提を置いた事で新しく生じた段 |
| 自然言語の性質の宣言が要る | 語順や活用など、自然言語ごとに違う性質を記述者が宣言すれば判定できる。宣言が方言になる     |
| 強制できない               | 意味の正しさに踏み込む。意図の層と同じく、書かせる事はできても検証はできない               |

### 4.1 語の閉包 — 名前は辞書の語だけで組む

名前を語の切れ目で分けた時、全ての語が辞書にある事を求める。無い語を含む名前はエラーとする。

- 判定: **言語が強制できる**。前提の下では語の切れ目が文字で決まるため、分け方は一通りしか無い。
  母国語で書く場合は、分かち書きの無い日本語を辞書の語で分ける必要があり、二通りに分けられる名前(`検索語` を一語とも `検索` と `語` の二語とも読める)の扱いが要った。前提はこの問題を消す。
- 第2節で捕まる物: `ID` と `番号` の混在(`Id` を退けるか、`Number` と別の定義で宣言するかを迫られる)、`請求する` と `受注` の形の混在(英語では `bill` と `billing` が別の語になり、どちらを辞書に置くかを決める)。
- 新しい語を使うには辞書に足すしかなく、**語の追加が差分に現れる**。語彙の変化がレビューの対象になる事が、この規則の一番の効果である。

### 4.2 退けた語 — 退けた語を名前に使わない

`rejected term` に挙げた英語の語を名前に含めない。母国語の欄では、`rejected ja` に挙げた語を辞書の母国語の欄に書かない。

- 判定: **言語が強制できる**。ただし退けたと宣言された語だけが対象である。
- 宣言されていない同義語(ある記述者が `shortage`、別の記述者が `stockout` と書く)は、語の閉包で辞書に足される時に初めて人の目に触れる。
  **同義である事を機械は判定できない**。語の閉包と合わせて、同義語が辞書に入る瞬間をレビューで捕まえる形になる。
  ただし前提の下では、二つの英語の語の母国語の欄が同じ(`在庫不足`)なら、同義の疑いとして機械が示せる(4.7)。

### 4.3 語の並びの衝突と大文字小文字の形

同じ名前空間に、語の並びが一致する別の名前が二つ以上あるとき、エラーとする(`order_inquiry` と `OrderInquiry`)。
併せて、宣言の種類ごとに大文字小文字の形を一つに決める(型と担い手は `UpperCamelCase`、公開面と欄は `lowerCamelCase` など)。

- 判定: **言語が強制できる**。E0014-3(見分けのつかない名前)の、語の段での対応物である。大文字小文字は ASCII の文字の性質であり、自然言語の文法ではない。
- 母国語で書く場合は「の」の有無(`受注の照会` と `実績照会`)を揃えられなかった。英語の繋ぎ(`of`・`by`)も残るが、
  複合語を語の並びで書く(`OrderInquiry`)のが英語の識別子の通例であり、`of` を辞書に置かなければ繋ぎ自体が書けない。

### 4.4 役の一致 — 宣言の種類に合う役の語を名前の中心に置く

`component` の名前の中心は `agent` の語、公開面の名前の中心は `action` の語、という規則である。

- 判定: **英語を仮定すれば強制できる**。「名前の中心」がどの語かは語順で決まる。英語の複合語は末尾が中心(`OrderNumber` の中心は `Number`)であり、
  言語が英語を仮定してよいなら「末尾の語の役」を見れば足りる。英語の句(`NumberOfOrders`)は先頭が中心だが、`of` を辞書に置かなければ書けない(4.3)。
- 母国語で書く場合は、二つの理由で崩れていた。
  - **述語を含む名前**: `受注不可` の末尾 `不可` は添える語であり、名前全体は物(`choice` の名前)である。英語では `AcceptRefusal` のように名詞の形(`refusal`)を選べるため、末尾を物にできる。
  - **サ変名詞**: `受注` は物と働きを兼ねる。英語では `accept`(働き)と `accepted`・`acceptance`(状態・物)が別の語になり、辞書で別の役を持てる。
    母国語の欄では同じ `受注` が二つの英語の語に対応するが、それは辞書の中に閉じる(論点2(一つの語の二つの役))。
- 英語を仮定する事は、ADR 0003 が拒否語リストを退けた理由「言語仕様が特定の自然言語を仮定する」に当たる(第5節 5.1)。

### 4.5 表現語と型 — 名前の末尾の語が型の形を告げる

`id` の名前は識別子を表す語(`Number`・`Code`)で終わる、量の欄の名前は量を表す語で終わる、という規則である。
データ項目の命名の規格である ISO/IEC 11179-5(国際標準化機構と国際電気標準会議の規格。メタデータ登録簿の命名と識別の原則)の表現語(representation term。名前の末尾に置き、値の形を指す語。`Amount`・`Code`・`Identifier` 等)に当たる。

- 判定: **英語を仮定すれば強制できる**。末尾という位置を使うため、4.4 と同じく英語の語順に依る。
- Shidzuku の名前的型付けとの相性は良い。`id OrderNumber` の `Number` は、型の名前が値の出どころを告げる(第6章 6.6)事をそのまま語の段で支える。
  ISO/IEC 11179-5 の名前の例も、英語で「対象の語・性質の語・表現語」の順に並ぶ(`EmployeeAddressText`)。前提の下ではそのまま借りられる。

### 4.6 欄名と型名 — 欄の名前と、その型の名前の語を揃える

`record Order { item: ItemCode, … }` の欄名 `item` は、型名 `ItemCode` の語の一部である。これを規則にする案である。

- 判定: **強制できない**。型名をそのまま欄名にする書き方(`refusalReason: RefusalReason`)と、役割だけを書く書き方(`reason: RefusalReason`)のどちらも正しい。
  同じ型の欄が二つある時(`origin: Address`・`destination: Address`)は、欄名が型名と違う事が要点になる。指針には書けるが、規則にはならない。

### 4.7 対応の一意と、宣言されていない同義語

- **対応の一意**: 同じ役の中で、英語の語と母国語の語が一対一に対応する事を求める。二つの英語の語が同じ母国語の語を持てば同義の疑い、一つの英語の語に二つの母国語の語を書けば訳の揺れである。
  判定は **言語が強制できる**。図・ログに母国語の名前を出すには、この一意が要る。
- **定義の質**: 定義の文が正しいか、定義と使い方が合っているかは**強制できない**。意図の層と同じで、書かせる事はできても検証はできない(ADR 0003)。
- **英語である事**: 言語が強制できるのは ASCII である事までで、語が英語かどうかは判定できない(`hikiate` のようなローマ字も ASCII である)。
  `引当`・`締め`・`按分` のように英語に一語で当たらない業務の語は、近い英語(`allocation`)を当てて定義で意味を縛るか、ローマ字で書くかを辞書で決める事になる。

### 4.8 判定の集計

| 規則                   | 母国語で書く場合           | 英語(ASCII)で書く場合      | 第2節で捕まる揺れ                          |
| ---------------------- | -------------------------- | -------------------------- | ------------------------------------------ |
| 語の閉包               | 言語が強制できる           | 言語が強制できる           | 識別子を表す語・公開面の名前の形・送り仮名 |
| 退けた語               | 言語が強制できる           | 言語が強制できる           | 一度退けた後の、同じ揺れの再発             |
| 語の並びの衝突         | 言語が強制できる           | 言語が強制できる           | 同じ名前空間での繋ぎの違い                 |
| 大文字小文字の形       | —                          | 言語が強制できる           | —(母国語には無い)                          |
| 対応の一意             | —                          | 言語が強制できる           | 同じ事態の別の語(母国語の欄が重なる時)     |
| 役の一致               | 自然言語の性質の宣言が要る | 英語を仮定すれば強制できる | コンポーネント名の品詞・一つの語が二つの役 |
| 表現語と型             | 自然言語の性質の宣言が要る | 英語を仮定すれば強制できる | 識別子を表す語                             |
| 欄名と型名             | 強制できない               | 強制できない               | —                                          |
| 定義の質・英語である事 | 強制できない               | 強制できない               | —                                          |

**問いへの答えは「一部は出来る」で、前提を置くと出来る所が広がる。**

- 名前を辞書の語だけで組ませる事、退けた語を使わせない事、語の並びが同じ名前を並べさせない事は、母国語でも英語でも、自然言語に踏み込まずに強制できる。
- 前提(コードは英語)を置くと、語の切れ目が文字で決まり、分け方の曖昧さが消える。大文字小文字の形と対応の一意も強制できる。
- 名詞と動詞という文法の規則(役の一致・表現語と型)は、母国語では崩れるが、英語を仮定すれば強制できる。その代わり、言語が英語を仮定する事になる。

## 5. 既存の決定との突き合わせ

### 5.1 自然言語を仮定しない(ADR 0003・0006・0014)

ADR 0003 は拒否語リストと最小文字数を、ADR 0006(コンポーネントの粒度の指針)は指針の機械検証を、いずれも「言語仕様が特定の自然言語を仮定する」として退けた。
ADR 0014 は同じ理由で、言語の語彙を ASCII にした。

- 語の閉包・退けた語・語の並びの衝突・大文字小文字の形・対応の一意は、**記述者が宣言した文字列と照らすか、文字の性質を見るだけ**である。言語は英語の文法を知らないまま判定できる。
  拒否語リストとの違いは、語を決めるのが言語ではなく記述者である所にある。ADR 0003 の退けた理由には当たらない。
- 「名前は ASCII」も、それだけでは自然言語を仮定しない。ASCII のローマ字も書けるからである。
- 役の一致と表現語と型は、英語の語順を仮定する。**ここで初めて ADR 0003 の線を越える**(論点8(英語の文法を仮定するか))。

### 5.2 名前を英語に限る事(ADR 0014 の決定3)

ADR 0014 は決定3 で記述者の名前を UTF-8 とし、「識別子も ASCII に限る」案を次の理由で退けた。
ドメインの語彙に翻訳が1段入り、`受注番号` と `受付ID` の区別が翻訳者の語彙力に左右される。名前だけが別の言語で書かれる事になる。

用語辞書はこの理由の一部に答える。

| ADR 0014 の退けた理由        | 用語辞書の下での事情                                                                      |
| ---------------------------- | ----------------------------------------------------------------------------------------- |
| 翻訳が1段入る                | 入る。ただし翻訳は辞書に一度だけ、定義と共に宣言され、レビューを受ける                    |
| 区別が翻訳者の語彙力に依る   | 依る。ただし対応の一意(4.7)が、二つの概念に同じ訳を当てる事と、一つの概念の訳の揺れを拒む |
| 名前だけが別の言語で書かれる | 書かれる。図・ログ・診断には辞書を引いて母国語の名前を出せる(第0章 0.7 の投影)            |

一方で、**ソースを読む人は英語を読む事になる**。これは辞書では消えない費用である。

前提を採ると、他の所も変わる。

- 第5章 5.6 の**可逆な符号化**は要らなくなる。ソースの名前がそのまま出力先(Rust・TypeScript)の識別子になり、Rust の非 ASCII 識別子の lint にも当たらない。
  符号化の対応表の代わりに、用語辞書が母国語への対応表になる。向きが逆になる。
- 名前の NFC の検査(E0014-2)は、ASCII では常に満たされる。見分けのつかない名前の検査(E0014-3)は、`l` と `I` のような ASCII の中の紛れに縮む。
  名前に双方向制御文字が入る余地も無くなる(テキストとコメントには残る)。
- 思考実験 01〜28 の名前は日本語で書かれている。採るなら、移行点検(M4)で題材を書き下ろす時に英語の名前と辞書で書き直す事になる。

前提を言語の規則にするには、ADR 0014 の決定3 を改める新しい ADR と、第5章 5.4・5.5・5.6 の改訂が要る(論点7(名前を英語に限る事))。

### 5.3 方言の問題(ADR 0014 の捨てた選択肢)

ADR 0014 は「識別子の文字集合をプロジェクトごとに宣言させる」案を、言語が方言を持つ事になり、コンポーネントの再利用が現場の宣言に依存するとして退けた。

用語辞書も現場ごとに違う。しかし事情が一つ違う。**コンポーネントの公開面は既にデータ宣言に依存している**(`expose accept(Order)` の `Order` はトップレベルの `record`)。
語彙の共有は名前的型付けを採った時から始まっており、用語辞書はそれを型の名前から全ての名前へ広げる物である。
コンポーネントを別のシステムへ持って行く時に辞書の語が足りなければ、それは「語彙が違う所へ持って行った」事が見えたのであって、方言の害とは言い切れない。
ドメイン駆動設計(Domain-Driven Design)の言葉で言えば、ユビキタス言語(関係者が共有する一つの語彙)は境界づけられたコンテキストごとに違ってよく、境界を跨ぐ所では訳が要る。

### 5.4 省略の禁止(ADR 0008)

用語辞書を言語に入れるなら、辞書を書かない事は省略時の既定(検査しない)になる。ADR 0008(省略の禁止)に従えば、辞書は必須とし、使わない事も `glossary none` と書く事になる。
一方で ADR 0008 は「約束の欠如」(`idempotent` を書かない事は冪等を約束しない事)を既定と区別しており、辞書を書かない事を「語を揃える約束をしない」と読む余地もある。
前提(コードは英語)を採るなら、母国語の名前を出す元が辞書しか無いため、辞書は実質的に必須になる。

### 5.5 名前空間(プログラムの宣言(U14))

辞書がどの範囲に掛かるかは、名前空間の範囲と同じ問いである。システムの入れ子(ADR 0018(システムの入れ子))を許した今、境界づけられたコンテキストはシステムに当たるのが素直で、
内側のシステムは親の辞書を受け継いで語を足すか、別の辞書を持つかを選ぶ形になる。プログラムの宣言(U14)の論点4(名前空間の分け方)と同時に決まる。
プログラムの宣言(U14)の論点2(直和の区分名)も関わる。`Found`・`None` が複数の `choice` に現れるのは、同じ語を辞書に一度宣言し、多くの名前で使う形として自然に読める。

### 5.6 図とログ(第0章 0.7、ログ規約(U4))

辞書そのものが、コードから抽出できる用語集になる。図の凡例・ログの読み方・運用の手引きに、定義の文をそのまま載せられる。
前提の下では、図とログは英語の名前と母国語の名前のどちらでも出せる。投影の原則(第0章 0.7)の範囲を、構造から語彙へ広げる事になる。

### 5.7 body の記法(U26)

body の中の変数名は、body の記法(U26)が決まるまで規則を当てられない。body は原則自由(第0章 0.5)であり、辞書を body の中にまで掛けるかどうか自体が論点になる(論点5(範囲))。

## 6. 置き場の三案の比較

suzukimitsuru の指摘の通り、言語の外に置き lint で見る案は、Shidzuku 以外の言語にも当てられる汎用性がある。三案を同じ物差しで比べる。

| 案                           | 中身                                                                                                                    |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 言語の宣言にする案           | `glossary` をトップレベルの宣言にし、Shidzuku のコンパイラが第4節の規則をエラーとして検査する                           |
| 言語の外に置き lint で見る案 | 辞書は言語に依らない別のファイルとし、shidzuku-lint(ADR 0026)が Shidzuku と既存の言語(Rust・TypeScript)の両方を検査する |
| 新しい宣言を足さない案       | データ宣言(`record`・`choice`・`id`)の名前を辞書とみなし、他の名前がそれらの語で組まれている事だけを見る                |

| 物差し                       | 言語の宣言にする案                               | 言語の外に置き lint で見る案                                       | 新しい宣言を足さない案                   |
| ---------------------------- | ------------------------------------------------ | ------------------------------------------------------------------ | ---------------------------------------- |
| 強制の強さ                   | エラー。破れば動かない                           | 警告。抑止できる(ADR 0008・0013 が lint を退けた理由)              | エラーにできるが、見る範囲が狭い         |
| 他の言語への適用             | できない。Shidzuku の構文の中に辞書がある        | できる。辞書のファイルを Rust・TypeScript・Hike のコードにも当てる | できない。Shidzuku のデータ宣言に依る    |
| 母国語と英語の対応表         | 持てる                                           | 持てる                                                             | 持てない。データ宣言は名前しか持たない   |
| 働き・担い手の語             | 持てる                                           | 持てる                                                             | 持てない。データ宣言は物の語しか持たない |
| 退けた語                     | 書ける                                           | 書ける                                                             | 書く所が無い                             |
| 図・ログ・診断への投影       | コンパイラが辞書を知っているので、そのまま使える | 図とログを作る道具が辞書のファイルを別に読む必要がある             | 母国語の名前が無いため、投影できない     |
| 書く量                       | 宣言が一つ増える                                 | ファイルが一つ増える                                               | 増えない                                 |
| それ自体で読める事(ADR 0008) | 保てる。辞書もソースの一部である                 | 崩れる。名前の意味がソースの外のファイルに依る                     | 保てる                                   |
| 方言(5.3)                    | 言語が方言を持つ                                 | 言語は方言を持たない。方言は lint の設定に留まる                   | 方言は増えない                           |
| 辞書の版と記述の版(U16)      | 同じ版で動く                                     | 辞書とソースの版がずれ得る                                         | 同じ版で動く                             |
| 始められる時期               | Phase 1 の言語実装の後                           | shidzuku-lint の着手と同時(Phase 1)。既存のコードに先に届く        | Phase 1 の言語実装の後                   |

### 6.1 言語の宣言にする案

- 利点: 強制になる。辞書をコンパイラが知るため、図・ログ・診断に母国語の名前を出せる。辞書もソースの一部として、それ自体で読める記述(ADR 0008)を保つ。
- 欠点: Shidzuku の中でしか働かない。辞書の書式を Shidzuku の構文に縛ると、同じ現場の Rust や TypeScript のコードと辞書を共有できない。言語が方言を持つ。

### 6.2 言語の外に置き lint で見る案

- 利点: 汎用性がある。一つの辞書のファイルを、Shidzuku のソースと、出力先や既存の言語のコードの両方に当てられる。
  Shidzuku を採る前の現場にも先に届き、ADR 0026 の「考え方を既存の言語へ先に届ける」(第0章 0.8)に沿う。言語の仕様を増やさない。
- 欠点: 警告であり、抑止できる。名前の意味がソースの外のファイルに依り、ADR 0008 の「それ自体で読める」が崩れる。辞書とソースの版がずれ得る。
  図とログに母国語の名前を出すには、それぞれの道具が辞書のファイルを読む必要がある。

### 6.3 新しい宣言を足さない案

- 利点: 宣言が増えない。名前的型付けの延長で済み、型の名前が既に担っている語彙をそのまま使える。
- 欠点: 母国語と英語の対応表を持てないため、**前提(コードは英語)とは両立しない**。働きと担い手の語、退けた語も書けない。第4節の規則のうち、語の閉包の一部しか当てられない。

### 6.4 組み合わせの余地

言語の宣言にする案と、言語の外に置き lint で見る案は、排他ではない。辞書の書式を**言語に依らないファイル**として定め、
Shidzuku のコンパイラはそれを読んでエラーとし、shidzuku-lint は同じファイルを読んで既存の言語に警告として当てる形が採れる。
汎用性と強制を両立できる代わりに、辞書がソースの外に出るため、ADR 0008 の「それ自体で読める」をファイルの単位でなくプログラムの単位で満たすと読み替える必要がある。
これはプログラムの宣言(U14)の論点7(ファイルとの関係)と同じ所で決まる。

## 7. 同じ目的の lint

名前を辞書に照らして揃える既存の道具を調べた。**調べた範囲では、辞書による語の閉包・語の役・母国語との対応表を一つで持つ lint は見つからなかった。**
部分ごとに近い物は多い。

| 区分                       | 道具                                                                                                                                                                                                 | 第4節の規則との対応                                                                   |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 綴りの検査と辞書           | cspell(識別子を `camelCase`・`snake_case` で語に分けて辞書と照らす。`flagWords` で禁じる語を書ける)                                                                                                  | 語の閉包(未知の語を知らせる)と退けた語に近い。役・定義・母国語の対応は無い            |
| 綴りの検査と辞書           | typos(crate-ci)・codespell                                                                                                                                                                           | よくある綴りの誤りの表で直す。語の選択は揃えない                                      |
| 名前の形の検査             | typescript-eslint `naming-convention`(宣言の種類ごとに大文字小文字の形・接頭辞を決める。真偽の変数に `is` 等を求められる)                                                                            | 大文字小文字の形と、役の一致の英語の一部(真偽は表明の形)                              |
| 名前の形の検査             | ESLint `id-match`・`id-denylist`、rustc `non_snake_case`・`non_camel_case_types`、clippy `disallowed_names`・`enum_variant_names`、Checkstyle の名前の検査、Pylint `invalid-name`・`disallowed-name` | 正規表現と禁じる名前の一覧。語の段ではなく名前の段で見る                              |
| 名前と中身の食い違い       | PMD `LinguisticNaming`(Java。6.7.0 から)                                                                                                                                                             | `isX` が真偽を返さない、`getX` が何も返さない等を見る。役の一致を型と照らす英語の規則 |
| 名前と中身の食い違い       | IDEAL(Peruma・Arnaoudova・Newman、2021。Java と C#)                                                                                                                                                  | Arnaoudova らの言語的なアンチパターンを検出する。プロジェクトごとの設定を持つ         |
| 用語集を見せる道具         | Contextive(定義のファイルをリポジトリに置き、補完と hover で定義を見せる)                                                                                                                            | 用語辞書の定義の欄に当たる。誤用の警告は計画中であり、検査はしない                    |
| 母国語から英語の名前を引く | codic(日本語から英語の変数名・メソッド名を提案する「ネーミング辞書」のサービス)                                                                                                                      | 母国語と英語の対応表に当たる。提案であって検査ではなく、辞書は現場ごとに持たない      |
| 研究                       | Deissenboeck と Pizka の識別子の辞書(2006)                                                                                                                                                           | 概念と名前の一対一の対応を保つ辞書を、開発と共に作り続ける道具。対応の一意に当たる    |

分かった事は三つある。

1. **語の閉包と退けた語は、cspell の仕組みでほぼ書ける。** 識別子を語に分け、現場の辞書と照らし、禁じる語を知らせる。足りないのは、語の役と、母国語の欄と、代わりに使う語の指定である。
2. **役の一致の英語版は、既に lint になっている。** typescript-eslint の `naming-convention` と PMD の `LinguisticNaming` は、英語の文法(真偽は `is` で始まる、`get` は値を返す)を前提にしている。
   既存の lint は英語を仮定する事をためらっていない。Shidzuku が言語として仮定しない(5.1)のと対照的である。
3. **母国語との対応表は、検査の道具ではなく提案と表示の道具として在る。** codic は名前を提案し、Contextive は定義を見せる。
   対応表を**検査に使う**(母国語の欄の重なりで同義を疑う、退けた母国語の語を拒む)物は見つからなかった。ここが shidzuku-lint で新しく作る所になる。

## 8. Swift の API 設計の指針の要約

Swift の API 設計の指針(API Design Guidelines、swift.org)は、名前の付け方を英語の文法に結び付けた指針の代表である。要点を短くまとめる。

| 区分         | 要点                                                                                                                                                                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基本         | 使う所での明快さを最優先にする。宣言でなく呼び出しの形で評価する。短さより明快さ。全ての宣言に文書のコメントを書く                                                                                                                                                     |
| 明快な使い方 | 曖昧さを避ける語は入れる(`remove(at: x)`)。型を繰り返すだけの語は省く(`removeElement` ではなく `remove`)。変数は型ではなく役で名付ける(`string` ではなく `greeting`)                                                                                                   |
| 流れる使い方 | 呼び出しが英語の句として読めるようにする(`x.insert(y, at: z)`)。生成は `make` で始める。副作用の無い物は名詞句(`distance(to:)`)、有る物は命令形の動詞句(`sort()`)。対は `sort()` と `sorted()` のように揃える。真偽は表明として読める(`isEmpty`)。型・性質・変数は名詞 |
| 用語の使い方 | 難しい語より普通の語。専門用語は確立した意味でだけ使う。略語は避ける。先例に従う(`List` ではなく `Array`)                                                                                                                                                              |
| 規約         | 型は `UpperCamelCase`、それ以外は `lowerCamelCase`。略語の大文字小文字は揃える(`utf8Bytes`)。同じ働きの物だけが同じ基本の名前を持つ                                                                                                                                    |
| 引数のラベル | 区別できない引数はラベルを省く(`min(a, b)`)。前置詞句を作る引数はラベルを付ける。基本の名前と文を作る最初の引数はラベルを省く                                                                                                                                          |

本実験との関わりは二つある。

- **副作用で品詞を分ける規則**は、品詞を宣言の性質に結び付ける先例である。本実験は品詞の代わりに、役を Shidzuku の宣言の種類に結び付けた(第3節)。
- 指針の大半(流れる使い方・引数のラベル)は**英語の文法そのもの**を前提にしている。前提(コードは英語)を採っても、Shidzuku がここまで言語の規則にするかは論点8(英語の文法を仮定するか)の答えに依る。
  略語を避ける事は、本リポジトリの省略表現の規則(計画書 第7節 7.18)とも同じ向きである。

## 9. 論点

### 論点1: 置き場 — 用語辞書をどこに置くか

第6節で比べた。前提(コードは英語)を採るなら、新しい宣言を足さない案は対応表を持てないため外れ、言語の宣言にする案と言語の外に置き lint で見る案の二つになる。
汎用性を取るなら、辞書の書式を言語に依らないファイルとし、Shidzuku のコンパイラと shidzuku-lint の両方が読む組み合わせが有力である。

### 論点2: 一つの語の二つの役

前提の下では、英語の語形(`accept` と `acceptance`)が役を分けるため、コードの側ではサ変名詞の曖昧さが消える。
残るのは、母国語の欄で同じ `受注` が二つの英語の語に対応する事を、対応の一意(4.7)の例外として許すかである。役が違えば許す、が素直である。

### 論点3: 母国語の名前の組み立て

図・ログに母国語の名前を出す時、語ごとに辞書を引いて並べると、`OrderNumber` は `注文番号` になり、既存の名前 `受注番号` とは一致しない。
語順も母国語と同じとは限らない。名前ごとの母国語の訳を辞書に書けるようにする(`name OrderNumber ja "受注番号"`)か、語の並べ方の規則を母国語ごとに持つか、並べた結果を受け入れるかを決める。

### 論点4: 繋ぎ

英語の識別子では繋ぎ(`of`・`by`)を使わず語の並びで書くのが通例である。`of` を辞書に置けるようにするか、繋ぎの語は辞書に置けない事にするかを決める。

### 論点5: 範囲 — どの名前に辞書を掛けるか

公開面に現れる名前(システム・コンポーネント・公開面・データ宣言・欄・区分)だけに掛けるか、内部階層の名前・`state` の名前・body の中の名前まで掛けるか。
コンポーネントの内側は原則自由(第0章 0.5)であり、情報隠蔽の内側の語は外の語彙に縛られないとも読める。一方で、ログ規約(U4)のログと図に出る名前は内側の物も含む。

### 論点6: 外部の語彙

`external` の公開面は外部の事業者の語彙で書かれる(`決済代行` の API(Application Programming Interface)の名前)。
外部の語を自分の辞書に入れると、退けた語(4.2)が外部との境界で使えなくなる。外部世界との境界(U12)で、外部の語彙を別の辞書として持つか、訳の置き場とするかを決める事になる。
プログラムの宣言(U14)の論点8(外部システムの語彙)と同じ所で決まる。

### 論点7: 名前を英語に限る事

前提(コードの名前は英語(ASCII)だけ)は、ADR 0014 の決定3(記述者の名前は UTF-8)を改める事になる(第5節 5.2)。
用語辞書は ADR 0014 が ASCII を退けた理由の一部に答えるが、ソースを読む人が英語を読む費用は残る。言語の規則にするなら、新しい ADR で決定3 を改め、第5章 5.4・5.5・5.6 を改訂する。
思考実験 01〜28 の名前の書き直しは移行点検(M4)の作業になる。

### 論点8: 英語の文法を仮定するか

役の一致と表現語と型は、英語の語順を仮定すれば強制できる(4.4・4.5)。仮定すれば ADR 0003・0006 が守ってきた「言語仕様が特定の自然言語を仮定しない」線を越える。
仮定しないなら、二つは指針に留め、shidzuku-lint の警告として持つ道がある(既存の lint は英語を仮定している。第7節)。
Swift の指針のどこまでを取り込むか(第8節)も、この答えに依る。

### 論点9: 課題として登録するか

本実験は課題(U)を足していない。用語辞書を進めるなら、「名前の規則」を新しい課題として登録し、
プログラムの宣言(U14)・外部世界との境界(U12)・body の記法(U26)の後ろか並びに置く事になる。名前空間と外部の語彙の答えに依るためである。
論点7(名前を英語に限る事)は記述の表記(U17)の決定を改めるため、別の課題として切り出す事もできる。
Phase 1 へ移る条件(計画書 第4節 4.5)には含めず、Phase 1 の中で shidzuku-lint と共に試す道もある。

## 11. まとめ

- **呼び名**: 「用語辞典」を「用語辞書」に変えても結論は同じである。用語辞書は辞書(キーと値の対応)の一種であり、キーは用語である。
  「語彙辞書」は、語彙が語の集まりを指してキーを言わない事と、仕様の「言語が定める語彙」と紛れる事から、用語辞書より的確にならない。次点は「単語辞書」である。
- **出来る事**: 名前を辞書の語だけで組ませる事(語の閉包)、退けた語を使わせない事、語の並びが同じ名前を並べさせない事は、自然言語に踏み込まずに強制できる。
  前提(コードは英語(ASCII)、母国語は辞書にだけ書く)を置くと、語の切れ目が文字で決まって分け方の曖昧さが消え、大文字小文字の形と対応の一意も強制できる。
- **英語を仮定すれば出来る事**: 名前の中心の語の役と、表現語と型。母国語では崩れていた所(サ変名詞、述語を含む名前)が、英語の語形で分けられる。
  その代わり、言語が英語を仮定し、ADR 0003 の線を越える。
- **出来ない事**: 欄名と型名を揃える事、定義の正しさ、語が英語である事。
- **置き場**: 言語の外に置き lint で見る案は汎用性が高い。強制と投影を取るなら言語の宣言にする案が強く、二つは辞書の書式を言語に依らないファイルにすれば組み合わせられる。
  新しい宣言を足さない案は、母国語との対応表を持てないため前提と両立しない。
- **既存の lint**: 辞書による語の閉包・語の役・母国語との対応表を一つで持つ物は見つからなかった。cspell・typescript-eslint・PMD・codic・Contextive がそれぞれ一部を持つ。
- **決める事**: 置き場(論点1)、母国語の名前の組み立て(論点3)、範囲(論点5)、外部の語彙(論点6)、名前を英語に限る事(論点7。ADR 0014 を改める)、
  英語の文法を仮定するか(論点8)、課題として登録するか(論点9)。

# 思考実験 03: 画像変換サービス(同期 API+非同期処理の混在系)

- 状態: Draft
- 日付: 2026-08-19
- 目的: ADR 0004(ask/flow・バックプレッシャ・フローの intent)、ADR 0005(内部階層)、ADR 0006(粒度)の提案を、両方式が混在する系に適用して検証する
- 進め方: 計画書の検証方法に従い、既存の小さなシステムを Shidzuku で記述してみる。書けない事があれば仕様に戻す。思考実験 01 は ask 中心、02 は flow 中心だったため、本実験は **ask と flow の境目**を持つ系を選ぶ

## 1. 対象システム

よくある画像変換サービスの最小構成。

- 利用者が HTTP API で画像の変換を依頼し、すぐに受付 ID を受け取る
- 変換は時間がかかる(数十秒)ため、非同期で処理する
- 変換結果を保存し、完了を利用者に通知する

単位は4つ。

| 単位        | 隠す知識                   | 公開面           |
| ----------- | -------------------------- | ---------------- |
| UploadGate  | HTTP・外部表現(JSON)       | 変換依頼の受付   |
| Converter   | 画像変換の方式(コーデック) | 変換結果の流れ   |
| ResultStore | 依頼と結果の永続化方式     | 登録・保存・照会 |
| Notifier    | 完了通知の手段             | 完了の通知       |

当初「JobQueue(ジョブの待ち行列)」を5つ目の単位として置こうとしたが、why に書ける「隠す知識」がなかった(待ち行列は接続の pressure が担う)。
ADR 0006 の「小さすぎのシグナル」が統合(不要化)の判定として機能した実例。

## 2. Shidzuku による記述(仮構文)

### 2.1 UploadGate — 依頼の受付

```plaintext
unit UploadGate {
  intent {
    why      "HTTP と外部表現(JSON)の知識をこの単位に閉じ込める。内側は変換依頼というデータだけを扱う。"
    rejected option "各単位が自分の HTTP エンドポイントを持つ"
             reason "プロトコルの変更が全単位に波及するため。"
    change   "アップロード方式の追加(分割アップロード等)を想定。内側への公開面は変えない。"
  }
  constraint {
    depends  Converter, ResultStore
    expose   受付(変換依頼) -> 受付ID | 受付不可
    isolate  failure
  }
  body { ... }
}
```

### 2.2 Converter — 画像の変換

```plaintext
unit Converter {
  intent {
    why      "画像変換の方式(コーデック・パラメータ調整)の知識をこの単位に閉じ込める。"
    rejected option "UploadGate が受付処理の中で変換まで行う"
             reason "変換は数十秒かかり、受付の応答期限(HTTP)と変換の都合が互いを壊すため。"
    change   "対応形式の追加を想定。追加はこの単位の内側で閉じ、公開面は変えない。"
  }
  constraint {
    depends    ResultStore, Notifier
    expose     変換結果(受付ID, 結果) の流れ
    idempotent 変換                 # 同じジョブの再実行は同じ結果になり、二重保存しない
    layers {
      planning { pure }             # 変換パラメータの決定は純粋
      codec    { io }               # コーデック実行・ファイル IO
    }
  }
  body { ... }
}
```

### 2.3 ResultStore — 依頼と結果の永続化

```plaintext
unit ResultStore {
  intent {
    why      "依頼と結果の永続化方式(現在は RDB+オブジェクトストレージ)の知識をこの単位に閉じ込める。"
    rejected option "各単位が直接ストレージに書く"
             reason "保存方式の変更が全単位に波及するため。"
    change   "結果の保存先をオブジェクトストレージ単独へ移行する可能性。公開面は変えない。"
  }
  constraint {
    depends    なし
    expose     受付登録(変換依頼) -> 受付ID
    expose     保存(受付ID, 結果)
    expose     照会(受付ID) -> 状態・結果
    idempotent 保存
  }
  body { ... }
}
```

### 2.4 Notifier — 完了の通知

```plaintext
unit Notifier {
  intent {
    why      "通知手段(現在はチャット通知)の知識をこの単位に閉じ込める。"
    rejected option "Converter が変換のついでに通知する"
             reason "通知先の障害や遅延を変換に持ち込みたくないため。"
    change   "通知手段の追加(メール)を想定。公開面は変えない。"
  }
  constraint {
    depends  なし
    expose   (外部への通知のみ。内側への公開面なし)
    isolate  failure
  }
  body { ... }
}
```

### 2.5 フロー — 変換依頼の処理

ADR 0004 に従い、フローにも intent を必須で書く。

```plaintext
flow 画像変換 {
  intent {
    why      "受付には応答期限があるため ask、変換は時間がかかるため flow で切り離す。受付時に返すのは受付IDのみとし、完了は通知で知らせる。"
    rejected option "変換完了まで ask で待たせる"
             reason "変換は数十秒かかり、HTTP の応答期限にも利用者の待ち時間にも収まらないため。"
    change   "優先度付きの処理を想定。接続の宣言の変更で吸収し、単位の公開面は変えない。"
  }
  UploadGate -> ResultStore : ask 受付登録(変換依頼) -> 受付ID
  UploadGate -> Converter   : flow 変換ジョブ pressure block   # ← 論点1: 期限なしの block では書けない
  Converter  -> ResultStore : ask 保存(受付ID, 結果)
  Converter  -> Notifier    : flow 完了イベント pressure block
  on failure Converter   : 再起動する。処理中のジョブは失ってはならない   # ← 論点2: 「失わない」を書く手段がない
  on failure ResultStore : UploadGate は受付不可を返す(伝播しない)
  on failure Notifier    : 再起動する。通知の欠落は許容し、障害イベントを記録する
}
```

## 3. 検証結果

### 3.1 書けた事 — ADR 0004〜0006 は概ね機能した

- **ask と flow の混在(ADR 0004)**: 「応答期限がある受付は ask、時間のかかる変換は flow」という切り分けがそのまま書けた。方式の選択自体が設計判断として記述に現れる。
- **フローの intent(ADR 0004)**: ask/flow の切り替えを**どこで**行うかという、この系で最も重要な判断を書く場所がフローの intent だった。必須化の妥当性を裏付ける。
- **粒度の指針(ADR 0006)**: 「JobQueue 単位は不要(隠す知識がない)」を小さすぎのシグナルで判定できた。大きすぎ(01・02)に続き、統合側のシグナルも機能した。
- **内部階層(ADR 0005)**: Converter を planning(純粋)/codec(IO)で宣言できた。名前が自由である事で、単位の文脈に合った層名(domain/driver 以外)を選べた。

### 3.2 書きにくかった事 — 仕様に戻す論点

1. **ask の世界と flow の世界の境目で、期限なしの block が破綻する**。
  UploadGate → Converter は欠損不可なので pressure block(既定)だが、変換が詰まると UploadGate の受付処理が**無期限に待ち**、HTTP の応答期限を破る。
  latest / drop はジョブの黙殺なので論外。必要なのは「**期限付き block**」: 期限内に受け付けられなければ投入が失敗として上流に返り、UploadGate は受付不可を応答できる。
  → ADR 0004 の pressure に期限の宣言を追加する提案。
2. **「失ってはならない」を書く手段がない**。
  受付 ID を返した後に Converter が再起動してジョブが消えるのは、利用者にとって最大の驚きになる。
  思考実験 02 で「失ってよい状態」の宣言を提案したが、本実験ではその対偶「**失ってはならない**」の宣言と、それを実行系が守る手段(配達保証)が必要になった。
  flow の配達保証(単位の障害を跨いでメッセージが残るか)が未定である。
  → ADR 0004 に配達保証(接続の属性)を追加する提案。既定は軽量(障害時は失われ得る)とし、失えない接続だけ durable を宣言、受け口に idempotent を要求する形が候補。
  durable の実現手段(永続化・再送・Raft)は U6(Phase 2)に接続する。

### 3.3 未解決課題への入力

- **U2(ADR 0004 の修正)**: pressure block への期限の宣言。flow の配達保証(既定は軽量、durable は明示宣言+idempotent 受け口)。
- **U3(ADR 0005 の裏付け)**: 強度2種で3実験連続で足りた。層名の自由が機能した(planning/codec)。
- **U7(ADR 0006 の裏付け)**: 大きすぎ(02)・小さすぎ(03)の両シグナルが実地で機能した。
- **U6 への先行入力(Phase 2 で決定)**: durable な flow の実現手段(永続化・再送・Raft の適用範囲)。

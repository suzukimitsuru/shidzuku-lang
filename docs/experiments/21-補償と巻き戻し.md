# 思考実験 21: 補償と巻き戻し — 引き当てた在庫を、どこで解放するか

- 状態: Draft
- 日付: 2026-09-25
- 目的: 思考実験 20 の論点6(仕事の途中で失敗した時の巻き戻しが `on failure` で書けない)を、補償が要る系で測る。
  サーガの語彙(補償を言語が持つ形)に踏み込む必要があるかを判断する
- 経緯: 思考実験 20 は、`ask` の応答と後から届く `flow` が一つの仕事である形を書き、7つの論点を出した。
  相関(論点1・2)は D-2(`flow` 宣言に鍵を書く)で解ける見込みが立ったが、論点3・4・6 はどの案でも残った。
  そのうち**巻き戻し**を、もう一段の題材で確かめる
- 進め方: 引当 → 決済 → 確定という、巻き戻しが必要な系を現在の語彙だけで書く。
  補償が**どこに書かれるか**を数え、検査の網に載っているかを見る

## 1. 題材 — 引き当ててから確定するまで

```plaintext
 ①ask 受注      ②ask 引当     ③ask 保存(受注番号を返す)
Frontdesk ─▶ OrderIntake ─▶ Inventory
                   └────────▶ OrderStore ─┐
                                          │ ④決済(記述の外)
                            PaymentBridge ─▶ 決済代行(external)
                                 │
                                 │ ⑤flow 決済の結果
                                 ▼
                            OrderStore ─▶ Inventory   ⑥ask 引当の解放(不成立のとき)
                                 └──────▶ Frontdesk   ⑦flow 受注の状態
```

巻き戻し(引当の解放)が必要になる道は二つある。**この二つが別の形で書かれる事が、本実験の発見である。**

- **業務上の取消**: 決済が不成立だった。取消は正常な結果であり、障害ではない。
- **障害**: 引当の後、保存で `OrderStore` が落ちた。受注は成立していない。

## 2. 現在の語彙で書き下ろす

### 2.1 データ

```plaintext
量  個数 計数 基準 個

data 品目ID   (id)
data 受注番号 (id)
data 引当番号 (id)
data 注文         { 品目: 品目ID, 数量: uint32(0) 個 }
data 引当の結果   = 引当済み(引当番号) | 在庫なし
data 保存の結果   = 保存済み(受注番号) | 保存不可
data 解放の結果   = 解放済み(引当番号) | 引当番号が無い
data 決済の結果   = 決済成立(受注番号) | 決済不成立(受注番号, 不成立の理由)
data 不成立の理由 = 残高不足 | 与信否決 | 応答なし
data 受注の状態   = 確定(受注番号) | 取消(受注番号, 取消の理由)
data 取消の理由   = 在庫切れ | 決済できなかった | 客の取消
```

### 2.2 公開面

```plaintext
component Inventory {
  intent { ... }
  constraint {
    depends    none
    expose     引当(品目ID, uint32(0) 個) -> 引当の結果
    expose     引当の解放(引当番号) -> 解放の結果
    idempotent 引当の解放                       # 二度解放しても効果は一度
    state      引当台帳 recoverable(在庫の台帳の照会)
    collator   none
    layers {
      引当 { pure domain }
      台帳 { io   domain }
    }
  }
  body { ... }
}

component PaymentBridge {
  intent { ... }
  constraint {
    depends    none                             # 決済代行(external)は書けない(U12)
    expose     決済の依頼(受注番号) flow in
    expose     決済の結果(決済の結果) flow out
    idempotent 決済の依頼
    state      依頼中 recoverable(受注台帳の照会)
    collator   none
    layers {
      要求 { pure format }
      通信 { io   boundary }
      受領 { pure parse }
    }
  }
  body { ... }
}
```

`PaymentBridge` の `depends none` が、思考実験 08 の論点3(外部を呼ぶコンポーネントを書けない)の姿である。
**巻き戻しの引き金を引くのは外部の応答なのに、その相手が `depends` に現れない。**

### 2.3 フロー — 受付

```plaintext
flow 受注の受付 {
  intent {
    why      "引当と保存を同じ仕事として並べ、保存に失敗したら引当を戻す。
              在庫を押さえたまま受注が成立しない状態を残さないため"
    rejected option "保存してから引き当てる"
             reason "在庫が無い注文に受注番号を発行してしまう"
    change   "配送枠の引当が増える事を想定。接続が1本増える形で吸収する"
  }
  OrderIntake -> Inventory  : ask 引当(品目ID, 数量) deadline 100 ミリ秒 -> 引当の結果
  OrderIntake -> OrderStore : ask 保存(注文, 引当番号) deadline 200 ミリ秒 -> 保存の結果
  on failure Inventory   : OrderIntake は受注不可を返す(伝播しない)
  on failure OrderStore  : OrderIntake は引当を解放し、受注不可を返す(伝播しない)
  on failure OrderIntake : 再起動する。引当は残り得る
}
```

### 2.4 フロー — 確定と取消

```plaintext
flow 受注の確定と取消 {
  intent {
    why      "決済の結果を受けて、確定か取消を決める。取消なら引当を解放してから客へ知らせる"
    rejected option "解放を客への通知より後に回す"
             reason "通知が失敗すると在庫が戻らない。在庫の回復を通知の成否に依存させない"
    change   "部分取消(明細単位)を想定。解放の引数が増える形で吸収する"
  }
  PaymentBridge -> OrderStore : flow 決済の結果 pressure block(deadline 1 秒) (durable)
  OrderStore    -> Inventory  : ask 引当の解放(引当番号) deadline 100 ミリ秒 -> 解放の結果
  OrderStore    -> Frontdesk  : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  on failure PaymentBridge : 再起動する。決済の結果は durable なので再送される
  on failure OrderStore    : 再起動し、受注台帳から途中の受注を復元する
  on failure Inventory     : OrderStore は解放を再試行する(引当の解放は idempotent)
  on failure Frontdesk     : 再起動する。客は受注の照会で引き直す
}
```

## 3. 書けた事

| 書けた事                             | 担った語彙                                |
| ------------------------------------ | ----------------------------------------- |
| 業務上の取消に伴う補償(解放)         | 普通の接続(`ask 引当の解放`)              |
| 補償が二度走ってよい事               | `idempotent 引当の解放`                   |
| 解放を通知より先に行う事と、その理由 | `flow` 宣言の接続の順序と intent の `why` |
| 途中で落ちた受注を復元できる事       | `state 受注台帳 recoverable(...)`         |
| 決済の結果を落とさない事             | 接続の `durable`                          |

**業務上の巻き戻しは、新しい語彙なしで書けた。** 補償は「普通の通信」であり、順序は `flow` 宣言の並びが、
理由は intent が引き受ける。ここまでは思考実験 20 の論点6 が心配したほどの穴ではない。

## 4. 書けなかった事

### 論点1: 同じ補償が、二つの形で書かれる

`引当の解放` は本実験に二度現れる。**同じ操作が、片方は検査される接続、片方は自然言語である。**

| 現れる場所                            | 形                                            | 言語が見るもの                   |
| ------------------------------------- | --------------------------------------------- | -------------------------------- |
| 業務上の取消(`flow 受注の確定と取消`) | `OrderStore -> Inventory : ask 引当の解放(…)` | 両端の宣言・型・期限(E0000-2 他) |
| 障害時(`on failure OrderStore`)       | 「OrderIntake は引当を解放し、…」(散文)       | 何も見ない                       |

障害の埋め合わせに補償を書く事は第4章 4.5 が明記している(「補償(引当の解放等)」)。
しかしその欄は**文**であり、接続ではない。同じ設計判断が、記述の中で二つの精度を持つ。

### 論点2: `on failure` に書いた通信は、省略の禁止の網に載らない

「OrderIntake は引当を解放し」と書いた時、次のどれも検査されない。

- `OrderIntake` の `depends` に `Inventory` があるか(平常時の接続には E0000-2 が効くのに、ここには効かない)。
- 解放の公開面が相手に在るか、引数と応答の型が合うか(E0000-3・E0009-1)。
- その解放の期限はいくつか。`ask` なら `deadline` が必須(ADR 0008)なのに、散文には無い。
- **補償自身が失敗したらどうするか。** `Inventory` も落ちていれば解放は届かない。その先を書く欄が無い。

本実験では `OrderIntake` が `Inventory` を呼ぶ接続が平常時にも在るため、たまたま `depends` は揃っている。
**「たまたま揃っている」事を言語が確かめていない**のが問題である。

### 論点3: 巻き戻しの引き金が、記述に現れない

取消を起こすのは決済代行(`external`)の応答である。しかし `external` はフローの端点に書けない(第1章 1.8、思考実験 08 論点7)。
そのため `flow 受注の確定と取消` は `PaymentBridge` から始まり、**なぜその流れが起きたのかが記述の外にある**。

`on failure PaymentBridge` に書けるのは `PaymentBridge` の障害であって、**決済代行の否決でも沈黙でもない**。

### 論点4: 途中まで進んだ仕事の残骸を、誰が片付けるか

`on failure OrderIntake : 再起動する。引当は残り得る` と書いた。これは正直な記述だが、その後が無い。

- `Inventory` の `引当台帳` には、どの受注にも結び付かない引当が残る(**孤児の引当**)。
- 誰かが期限で掃除しなければ、在庫は戻らない。掃除の主体も期限も、記述のどこにも無い。

これは思考実験 20 の論点5(仕事全体の期限)と**同じ穴**である。あちらは「確定がいつまでも来ない」、
こちらは「引当がいつまでも残る」であり、どちらも**仕事に期限が無い**事から出ている。
論点5 は U13(失敗の体系)へ送った。**本実験はその判断を裏付ける**——期限が無い事の害は、相関の書き方とは独立に現れる。

### 論点5: 補償を結ぶ鍵は、元の仕事の鍵と違う

思考実験 20 の D-2 は `correlate 受注番号` のように**仕事に一つの鍵**を書く形だった。しかし本実験では鍵が二つ要る。

| 結ぶ相手                                     | 鍵         |
| -------------------------------------------- | ---------- |
| `ask 受注` の応答と、後から届く `受注の状態` | `受注番号` |
| `ask 引当` の応答と、後から走る `引当の解放` | `引当番号` |

しかも `引当番号` は**客にも窓口にも見えない**。`受注番号` は公開面に出るが、`引当番号` は `注文管理` の内側で閉じている。
**鍵は仕事に一つではなく、接続の対ごとにある。** D-2 の設計はここで直さなければならない。

### 論点6(小): 同じ通信を、二つの倍率で書ける

`OrderStore -> Frontdesk : flow 受注の状態` と書いたが、これは `注文管理 -> Frontdesk` とも書ける(第4章 4.1)。
どちらも正しいが、**どちらで書くかの指針が無い**。
段を跨ぐ仕事では、フローの端点の倍率が揃っていないと図(Phase 3)の抽出も揺れる。

## 5. 案

### S-a: `on failure` に接続を書けるようにする

散文の代わりに、平常時と同じ形の接続を書く。

```plaintext
  on failure OrderStore : OrderIntake -> Inventory : ask 引当の解放(引当番号) deadline 100 ミリ秒 -> 解放の結果
                          OrderIntake は受注不可を返す(伝播しない)
```

- 補償が**平常時と同じ検査**(`depends`・`expose`・型・期限)を受ける。論点1・2 が閉じる。
- 新しい段も新しい単位も作らない。`on failure` の欄が「接続 + 文」を取るようになるだけである。
- 補償自身の失敗は、その接続の `on failure` として書ける(入れ子になる)。深さの上限は置かない。
- 論点3・4・6 は閉じない。

### S-b: サーガの単位を新設する

「一つの仕事」を宣言し、その中に手順と補償を並べる(`saga` に当たる語)。

- 手順と補償の対応が構文に出る。論点1・2・5 が一度に閉じる。
- しかし `flow` 宣言と**役割が重なる**。`flow` は既に「接続と障害時の振る舞い」を持つ単位であり、
  仕事の単位をもう一つ置くと、どちらに書くかという外部知識が増える(ADR 0015 が段を増やさなかったのと同じ理由)。
- 分散トランザクションの語彙(補償の自動実行・実行順序の巻き戻し)を実行系が担う事になり、Phase 2 の負担が跳ね上がる。

### S-c: 現状維持

- 補償は散文のままとし、レビューが担保する。
- ADR 0003 の立場(検証不能な物は intent に置く)に沿うように見えるが、**補償は検証可能である**——
  接続として書けば型も相手も期限も機械が見られる。検証できる物を散文に落とす理由が無い。

### 比較

| 観点              | S-a               | S-b                   | S-c      |
| ----------------- | ----------------- | --------------------- | -------- |
| 論点1(補償が二形) | 閉じる            | 閉じる                | 残る     |
| 論点2(検査の網)   | 閉じる            | 閉じる                | 残る     |
| 論点5(鍵の粒度)   | 接続ごとに書ける  | 仕事の中で対応が付く  | 残る     |
| 改訂する決定      | 第4章 4.5(欄の形) | ADR 0004・第4章の構造 | なし     |
| 実行系への要求    | 増えない          | 大きく増える          | 増えない |
| 読み手が覚える語  | 増えない          | 1単位(+その中の語彙)  | 増えない |

## 6. 示唆

- **S-a を採る値打ちがある。** 補償は検証可能な記述であり、散文に落ちているのは欄の形の都合にすぎない。
  第4章 4.5 の `on failure` が「補償・代替応答・再起動」の三つを挙げている以上、**補償だけを接続の形に上げる**のは自然である。
- **S-b(サーガの単位)は採らない。** `flow` 宣言と役割が重なり、実行系に分散トランザクションを要求する。
  補償の順序は `flow` の並びで書けており、足りないのは**検査**であって単位ではない。
- **D-2(思考実験 20)は鍵の粒度を直す必要がある。** 鍵は仕事に一つではなく、結ぶ対ごとにある(論点5)。
  `correlate` を書く位置は、`flow` 宣言の全体ではなく**接続の対**である。
- 論点3(引き金が記述の外)は U12 のまま、論点4(孤児と期限)は U13 のままである。
  **本実験は、どちらも相関の語彙では閉じない事を確かめた。**

## 7. 未解決課題への入力

- **U25(対になる通信)**: 鍵は仕事に一つではなく、結ぶ対ごとに要る(論点5)。D-2 の形を直して起案する。
- **U13(失敗の体系)**: 孤児の引当(論点4)は、思考実験 20 の論点5(仕事の期限)と同じ穴である。
  期限を過ぎた仕事をどう扱うか——失敗と呼ぶか、掃除の主体を言語が持つか。
- **U12(外部世界との境界)**: 巻き戻しの引き金が `external` の応答であり、それがフローに書けない(論点3)。
- **U2・第4章 4.5(`on failure` の欄の形)**: 補償を接続として書けるようにするか(S-a)。ADR 0004・0008 の延長にある。
- **U4(ログ規約)**: 補償が走った事・補償が失敗した事を、運用がどう知るか。
- **U8(図と実装の一致)**: 同じ通信を二つの倍率で書ける事(論点6)が、抽出する図の端点を揺らす。

## 8. 次の行動

- U25 の ADR を起案する。相関の鍵は**接続の対ごと**に書く形とし、仕事の期限は U13 に委ねる
- `on failure` に接続を書けるようにする案(S-a)を、U13 の検討と併せて判断する。
  補償の失敗が入れ子になる事(補償の `on failure`)の深さをどう扱うかが論点になる
- 論点6(倍率の指針)は、Phase 3 の図の抽出を検討する時に U8 と併せて決める

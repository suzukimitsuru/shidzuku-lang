# 思考実験 20: 対になる通信 — ask の後から届く flow をどう結ぶか

- 状態: Draft
- 日付: 2026-09-25
- 目的: 第4章 4.6 の未定事項「対になる通信の相関」を、実際の系で書き下ろして論点を出す
- 経緯: ADR 0018 の採用(2026-09-25)の過程で、逆向きの通信を「元の `ask` への後からの戻り(コールバック)」で説明する案を捨てた。
  捨てた理由は `ask` の定義(期限内に必ず返る。ADR 0004)を壊すからであり、**二本の通信が一つの仕事である事をどう書くか**は未決のまま第4章 4.6 に残った
- 進め方: 確定が後から決まる系を、現在の語彙だけで書き下ろす。書けた所と書けない所を分け、その上で案を3つ当てる

## 1. 題材 — 確定が後から決まる受注

客が注文すると、窓口は**受注番号を即座に返す**。しかし受注が確定するかどうかは、決済代行の応答を待たないと決まらない。
確定または取消は、後から客へ届ける。

```plaintext
            ask 受注(注文)                    ask 決済(受注番号, 金額)
 買い物客 ─▶ Frontdesk ──────────▶ 注文管理 ─────────────────▶ 決済代行(external)
                ▲                    │
                └────────────────────┘
              flow 受注の状態(確定 | 取消)
```

この題材を選んだのは、次の三つが同時に現れるからである。

- `ask` の応答(受注番号)と、後から届く `flow`(確定・取消)が**一つの仕事**である。
- 窓口は同じ相手に**別の `ask`** も出す(取消・照会)。戻りがどれへの戻りかが問題になる。
- 確定を待つ相手が `external` である。**相手が沈黙する**という、障害ではない待ちが起きる。

## 2. 現在の語彙で書き下ろす

### 2.1 データ

```plaintext
量  個数 計数 基準 個

data 品目ID (id)
data 受注番号 (id)
data 注文       { 品目: 品目ID, 数量: uint32(0) 個 }
data 受注不可   = 在庫なし | 受付停止中
data 受注の状態 = 確定(受注番号) | 取消(受注番号, 取消の理由)
data 取消の理由 = 在庫切れ | 決済不成立 | 客の取消
data 取消の結果 = 取消受付(受注番号) | 出荷済みのため取消不可
data 照会不可   = 受注番号が無い
```

`受注の状態` が `受注番号` を持つのは、**どの受注の話かを受け取った側が知るため**である。
これは言語の機構ではなく、書き手が型に置いた欄である。ここが本実験の焦点になる。

### 2.2 システムとコンポーネント

ADR 0018 の混在(コンポーネントとシステムが一つの `contains` に並ぶ)をそのまま使う。

```plaintext
system 通販 {
  intent { ... }
  constraint {
    actor    買い物客 "注文し、確定の知らせを受け取る"
    external 決済代行 "外部の事業者。注文管理が呼ぶ"
    depends  none
    expose   注文受付(注文) -> 受注番号 | 受注不可          by Frontdesk
    expose   受注の照会(受注番号) -> 受注の状態 | 照会不可  by Frontdesk
    contains Frontdesk, 注文管理
  }
}

component Frontdesk {
  intent {
    why      "客との接続と外部表現(HTTP・JSON)の授受を、このコンポーネントに閉じ込める。
              受注番号を即座に返し、確定は後から客へ中継する"
    rejected option "確定まで ask の中で待つ"
             reason "決済代行の応答は数分に及び得る。ask の期限に収めると、収まらない時に受注そのものが失敗になる"
    change   "確定の通知手段(SSE・ポーリング)の入れ替えを想定。内側への公開面は変えない"
  }
  constraint {
    depends    注文管理
    expose     注文受付(注文) -> 受注番号 | 受注不可
    expose     受注の照会(受注番号) -> 受注の状態 | 照会不可
    expose     受注の通知(受注の状態) flow in
    idempotent 受注の通知
    state      待ちの対応 volatile
    collator   none
    layers {
      受信   { io   boundary }
      復号   { pure parse }
      受付   { io   domain }
      符号化 { pure format }
    }
  }
  body { ... }
}

system 注文管理 {
  intent { ... }
  constraint {
    actor    none
    external 決済代行 "外部の事業者。PaymentBridge が呼ぶ"
    depends  決済代行
    expose   受注(注文) -> 受注番号 | 受注不可              by OrderIntake
    expose   取消(受注番号) -> 取消の結果                   by OrderIntake
    expose   受注の照会(受注番号) -> 受注の状態 | 照会不可  by OrderStore
    expose   受注の通知(受注の状態) flow out                by OrderStore
    contains OrderIntake, Inventory, OrderStore, PaymentBridge
  }
}
```

### 2.3 フロー

第4章 4.2 の `flow` 宣言は接続を複数行持てる(思考実験 04 の `flow 格納` が ask と durable な flow を混ぜている)。
二本を一つの宣言に並べてみる。

```plaintext
flow 受注の受付と確定 {
  intent {
    why      "受注番号は期限内に返し、確定は後から流す。決済代行の応答時間を客の待ち時間にしないため"
    rejected option "確定まで ask の中で待つ"
             reason "決済代行の応答は数分に及び得る。ask の deadline に収まらない"
    change   "確定の前に配送手配を挟む事を想定。接続が1本増える形で吸収する"
  }
  Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
  注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  on failure 注文管理  : Frontdesk は受注不可を返す(伝播しない)
  on failure Frontdesk : 再起動する。待ちの対応は失われ、客は受注の照会で引き直す
}
```

## 3. 書けた事

| 書けた事                     | 何が担ったか                                      |
| ---------------------------- | ------------------------------------------------- |
| 二本が一つの仕事である事     | `flow` 宣言の単位(2本を1つの宣言に並べた)         |
| なぜ二段なのか               | `flow` の intent の `why` と `rejected`           |
| 両端の障害時の埋め合わせ     | `on failure`(参加する全員について必須)            |
| 確定を失わない事             | 接続の `durable` と受け口の `idempotent`(E0004-1) |
| 再起動で客との対応が消える事 | `state 待ちの対応 volatile`                       |
| 消えた後に客が引き直す道     | `expose 受注の照会`                               |

**再起動の扱いは、宣言から設計が読める好例になった。** `volatile` と書いた時点で「客との対応は失われる」と宣言している。
ならば客が受注番号で引き直す公開面が要る——この要求は散文ではなく `state` の宣言から出ている(省略の禁止が働いた形)。

## 4. 書けなかった事

### 論点1: 二本を結ぶ鍵が、言語から見えない

`受注の状態` が `受注番号` を持つ事も、その `受注番号` が `ask 受注` の応答と同じ値である事も、**どこにも宣言されていない**。
言語が見るのは接続の両端の型の一致(E0009-1)だけである。

```plaintext
Frontdesk -> 注文管理  : ask 受注(注文) ... -> 受注番号 | 受注不可
注文管理  -> Frontdesk : flow 受注の状態 ...        # 受注の状態 の中に 受注番号 が居る
```

二本が同じ `flow` 宣言に並んでいる事だけが手掛かりであり、**その並びに意味を与える規則が無い**。
同じ宣言に無関係な二本を並べても言語は何も言わない。

### 論点2: どの ask への戻りかが決まらない

`注文管理` は `受注`・`取消`・`受注の照会` の三つの `ask` を受ける。`受注の状態` は、このうちどれの続きなのか。

- 受注の確定 → `ask 受注` の続きである。
- 客が取り消した結果の `取消(受注番号, 客の取消)` → `ask 取消` の続きでもある。

**同じ型の戻りが、二つの `ask` の続きになっている。** 記述の上では区別が無い。
受け取った `Frontdesk` は、`受注番号` を手掛かりに自分の待ち表を引くしかなく、その照合は body の中に沈む。

### 論点3: 同じ事実が二経路で届く

客の取消は、`ask 取消` の応答(`取消受付`)でも、後から届く `flow 受注の状態` の `取消(..., 客の取消)` でも分かる。
`idempotent` は**同じ受け口への同一要求の重複**を実行系が監視する宣言であり(第4章 4.4)、**経路をまたいだ重複**は対象外である。

二経路のどちらが先に届くかも書かれていない。順序保証は U11 の課題だが、そこで扱うのは**一本の flow の中の順序**であり、
`ask` の応答と `flow` の到着のあいだには、そもそも順序の語彙が無い。

### 論点4: durable で届いた物を捨てる事が、記述に出ない

`Frontdesk` が再起動すると `待ちの対応` は消える(`volatile`)。しかし接続は `durable` なので、確定の通知は**再送されて届く**。
届いた先には宛先の客が居ないため、body は受け取って捨てる。

- 捨てる事は `pressure latest` / `drop` のような**宣言された廃棄**ではない。接続は `block` のままである。
- `on failure` は障害時の埋め合わせであり、**平常時に届いた物を捨てる**事は書く場所が無い。

「黙ってデータが消えるのは運用の驚きである」(第4章 4.3)という立場からは、ここに穴がある。

### 論点5: 仕事全体の期限を書く場所が無い

- `ask` の `deadline` は 200 ミリ秒。**受注番号を返すまで**の期限である。
- `flow` の `pressure block(deadline 1 秒)` は、**投入が受け付けられるまで**の期限である。
- どちらも「**確定が何分以内に決まるか**」を語っていない。

決済代行が生きたまま沈黙すれば、確定は永久に来ない。これは接続の障害ではないため `on failure` に当たらず、
客から見れば「受注番号は貰ったが、いつまでも確定しない」状態になる。**仕事の期限は、二本のどちらの属性でもない。**

これは相関の問題より重いかもしれない。相関は body の照合で凌げるが、期限は**どこにも書けない**。

### 論点6: `on failure` の埋め合わせが、二本に跨ると効かない

`on failure 注文管理 : Frontdesk は受注不可を返す` と書いたが、これが使えるのは `ask` がまだ返っていない間だけである。
受注番号を返した後に `注文管理` が落ちた場合、返すべき応答はもう無い。埋め合わせは「客に取消を届ける」事になるが、
それは**同じ落ちた相手から届く通知**であり、書けない。

`on failure` は接続ごとの埋め合わせを書く欄であり、**仕事の途中で失敗した時の巻き戻し**を書く欄ではない。

### 論点7(小): 期限の綴りが揃っていない

第4章 4.2 は `deadline` を「`量 時間` を持つ数値」と定め(`deadline 200 ミリ秒`)、4.3 は `pressure block(deadline 1s)` と書いている。
`1s` は言語の単位の綴り(ナノ秒・ミリ秒・秒・分・時・日。第6章 6.3)に無い。**仕様書の文面の修正で閉じる。**

## 5. 三つの案を当てる

### D-1: 何も足さない

相関は `受注番号` というデータで表し、二本が対である事は `flow` 宣言の並びと intent に委ねる。

- 言語は変わらない。書ける形は §2 のままである。
- 論点1・2・3 は body とレビューが引き受ける。論点5(期限)は残る。

### D-2: `flow` 宣言に相関の鍵を書く

接続の属性として、二本を結ぶ鍵を宣言する。

```plaintext
flow 受注の受付と確定 {
  intent { ... }
  Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
  注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  correlate 受注番号                                 # 仮の語。二本を結ぶ鍵
  within    30 分                                    # 仮の語。仕事の期限(論点5)
  on failure 注文管理  : ...
  on failure Frontdesk : ...
}
```

検査できるようになるもの。

| 検査                                                   | 論点 |
| ------------------------------------------------------ | ---- |
| 鍵の型が、`ask` の応答と `flow` の内容の両方に現れる   | 1    |
| 同じ相手への別の `ask` と、鍵の型が衝突していない      | 2    |
| 仕事の期限を過ぎた事を実行系が検出し、失敗として扱える | 5    |

- `ask`・`flow` の語彙は変わらない。ADR 0004 を改訂せずに済む。
- 増えるのは `flow` 宣言の欄であり、**省略の禁止に沿う**(書かないなら `correlate none` を書く事になる)。
- 論点3(二経路の重複)・論点4(捨てた通知)・論点6(巻き戻し)は、これでも残る。

### D-3: 公開面で対を宣言する

担い手の側に「後から返る物」を書く。

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可 then 受注の状態    # 仮の構文
```

- ADR 0004 の決定(通信は ask と flow の2方式)を改訂する規模になる。
- 「必ず期限内に返る」という `ask` の保証が、同じ宣言の中で成り立つ部分と成り立たない部分に割れる。
- 再送の宛先は呼び出しではなくコンポーネントであるため(1コンポーネント = 1プロセス。ADR 0012)、
  受け取り口は結局 `expose ... flow in` になる。**消えるのは `depends` と `flow` 宣言の記述だけである。**

### 比較

| 観点                | D-1             | D-2                        | D-3                       |
| ------------------- | --------------- | -------------------------- | ------------------------- |
| 改訂する決定        | なし            | 第4章 4.2(欄が増える)      | ADR 0004(方式が増える)    |
| 相関(論点1・2)      | body とレビュー | 宣言と検査                 | 宣言(構文そのもの)        |
| 仕事の期限(論点5)   | 書けない        | 書ける(`within`)           | `ask` の期限と混ざる      |
| 二経路の重複(論点3) | 残る            | 残る                       | 残る                      |
| 捨てた通知(論点4)   | 残る            | 残る                       | 残る                      |
| 巻き戻し(論点6)     | 残る            | 残る                       | 残る                      |
| 読み手が覚える語    | 増えない        | 2語(`correlate`・`within`) | 1語(`then`)+ 例外的な意味 |

## 6. 示唆

- **D-3 は採らない。** ADR 0018 の採用時に捨てた理由(§ 経緯)に加え、本実験の論点5・6 を1つも解かない。
- **D-2 が最も費用対効果が高い。** `ask`・`flow` の2方式を保ったまま、論点1・2 を宣言と検査へ移せる。
- **`within`(仕事の期限)は `correlate`(相関の鍵)とは別の問いである。**
  **書き手の判断(2026-09-25): 論点5 は U13(失敗の体系)へ送る。** 「相手は生きているが、いつまでも確定しない」は、
  何を失敗と呼ぶかの問いであり、二本の通信を結ぶ書き方の問いではない。U25 が引き受けるのは相関(論点1・2)だけとする。
  期限を書く欄(`within` に当たるもの)の形は、U13 が失敗の体系を決めた後に、その語彙の上で決める。
- 論点3・4・6 はどの案でも残る。これらは「**一つの仕事が複数の通信に跨る**」事そのものの帰結であり、
  相関の語彙だけでは閉じない。トランザクションや補償の語彙(サーガ)に踏み込むかどうかの判断が要る。

## 7. 未解決課題への入力

- **U25(対になる通信)**: 相関の鍵(論点1・2)。案は D-1〜D-3。**仕事の期限(論点5)は U25 から外した**(§6)。
- **U13(失敗の体系)**: 仕事の期限(論点5)を引き取る。「相手は生きているが、いつまでも確定しない」を失敗として扱うか。
  ドメインの失敗(在庫なし)とも、系の失敗(期限超過・障害)とも違う三つ目に見える。
  期限を測る主体(実行系か、書き手が置くコンポーネントか)も、失敗の体系と同じ所で決まる。
- **U11(メッセージの順序保証)**: `ask` の応答と `flow` の到着のあいだに順序の語彙が無い(論点3)。
- **U12(外部世界との境界)**: 沈黙する `external` の扱い。`depends` に書けても、待ち続ける事は書けない。
- **U4(ログ規約)**: 宛先を失って捨てた通知を、運用がどう知るか(論点4)。
- **第4章 4.3**: `pressure block(deadline 1s)` の綴りを単位の語彙に揃える(論点7)。仕様書の文面の修正で閉じる。

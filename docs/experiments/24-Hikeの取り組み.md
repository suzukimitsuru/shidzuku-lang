## 1. 層の違い — 比べられる所と比べられない所

Hike と Shidzuku は、同じ「言語」でも受け持つ範囲が重ならない。

| 観点         | Hike                                             | Shidzuku                                                             |
| ------------ | ------------------------------------------------ | -------------------------------------------------------------------- |
| 記述する物   | 一つのプロセスの中の計算                         | プロセスの間の構造(システム・コンポーネント・接続)と、その内側の実装 |
| 出力先       | LLVM IR(ネイティブ・wasm32)と WAT                | Rust と TypeScript(ADR 0012)                                         |
| 実行時の支援 | 使った機能の分だけ生成する。常駐する物は無い     | 動作環境(Rust の1実装)が常駐し、監督・期限・流量制御を担う           |
| 並行の単位   | OS のスレッドプール上のタスク(`Async`)           | コンポーネント(1つ1プロセス。ADR 0012 決定5)                         |
| 共有の仕方   | モジュール変数の宣言(`threadable`・`concurrent`) | 共有しない。コンポーネントを跨ぐ共有メモリは存在しない(第4章 4.1)    |
| 障害の単位   | 定めない(プロセス全体)                           | コンポーネント(第0章 0.4)                                            |
| 書き手の手間 | Go に倣い、既定値や推論で短くする                | 省略の禁止。既定値を持たない(ADR 0008)                               |

**Hike はプロセスの内側を、Shidzuku はプロセスの間を管轄する。** したがって Hike の取り組みが直接当たる先は、
Shidzuku のうちプロセスの内側を語る所——コンポーネントの内側の実行モデル(U10)と、body の出力(Phase 1)——に限られる。
コンポーネントの間(接続・障害境界・配置)には、Hike は比べる物を持たない。

## 2. 取り組みの一覧と判定

| #    | Hike の取り組み                                                   | Shidzuku で対応する所                                          | 判定                   |
| ---- | ----------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------- |

## 3. 取り込む候補

### 3.1 H-1 — 共有の仕方を宣言の側で言う

Hike はモジュール変数を二つの宣言に分ける。

``` plaintext
var threadable(64) { requestCount int }   // スレッドごとに別の実体。他のスレッドから見えない
var concurrent(64) { completed int }      // 全スレッドが同じ実体。読み書きは言語が同期する
```

要点は、**共有するかどうかを使う側ではなく宣言の側で言う**事である。呼び手がそれぞれ同期の仕組みを組む必要が無く、
宣言を読めば、その変数が並行の下でどう振る舞うかが分かる。Hike の文書は「二つは別の所有の規則であり、取り替えの効く記憶域の種類ではない」と書く。

Shidzuku の `state` は、状態の**再起動時の扱い**(`volatile`・`recoverable`)を宣言させる。
これは「状態の性質を宣言の側で言う」という同じ形であり、Hike は同じ形の**もう一つの軸**——並行時の扱い——を持っている。

- U10 が**コンポーネントの内側を逐次(actor)にする**なら、この軸は要らない。内側で同時に走る物が無いからである。
- U10 が**内側の並行を許す**なら、`state` に並行時の扱いを書く欄が要る。省略の禁止(ADR 0008)により、並行の無い状態も `none` の類を書く事になる。

したがって H-1 は、U10 の選択肢それぞれの**費用を見積もる材料**になる。並行を許すと、全ての `state` 宣言に欄が一つ増える。
これは Erlang/OTP の系譜(第0章 0.9。プロセスの中は逐次)が逐次を選んだ理由の一つを、宣言の数として見せている。

### 3.2 H-2 — 送り出しと待ちを分ける

Hike の `Async(f)` は、関数をスレッドプールへ送り出し、**型付きの一度きりの通り道**(タスクの把手)をすぐ返す。
`<-task` はそれを待って、戻り値を複数でもそのまま受け取る。`<-Async(f)` と続けて書けば、送り出してすぐ待つ。

``` plaintext
chA := eventloop.InvokeCh[int](...)    // 送り出すだけ
chB := eventloop.InvokeCh[string](...) // 続けて送り出す
valA := <-chA                          // ここで初めて待つ
valB := <-chB
```

Hike はこれで**関数の色**(`async` を付けた関数は、呼ぶ側も全て `async` になる問題)を避けている。
関数そのものは同期のままで、待つ所だけが `<-` として記述に現れる。

Shidzuku の `ask` は、第4章で「構文上は要求-応答だが、実行系では非同期メッセージ+応答」と定められている。
一方、**body の中で `ask` をどう書くか**は決まっていない。ここに二つの問いがある。

- **複数の `ask` を先に送り出してから待てるか。** 思考実験 01 の `OrderIntake` は `引当` と `保存` を順に `ask` する。
  互いに依存しない `ask` を並べて送れれば、仕事の所要時間は期限の和ではなく最大に近づく。Hike の `InvokeCh` と `Invoke` の分離はこの形である。
- **待つ所が記述に現れるか。** U10 の「応答待ち中の再入」は、待つ所で他の要求を受けてよいかという問いである。
  待つ所が `<-` のような印として body に現れていれば、**再入が起き得る所が記述から読める**。印が無いと、どの呼び出しで待つのかは出力言語の都合に埋もれる。

関数の色について、Shidzuku は既に半分を解いている。制約強度 `pure` の層は IO を持てない(第2章 2.4)ため、
`ask` を書けるのは `io` の層だけであり、色は io の層に閉じ込められる。
TypeScript に出力すれば io の層は `async` になるが、pure の層は色を持たない。**Hike が構文で避けた物を、Shidzuku は層で囲っている。**
残るのは io の層の中で、送り出しと待ちを分けて書けるかどうかである。

### 3.3 H-3 — デッドロックを構文で起こせなくする

Hike の `lock` ブロックには三つの制限がある。

1. `lock` の中に `lock` を書けない
2. `lock` の中で関数を呼べない
3. `concurrent` の変数以外を守れない

2 が効いている。呼び出しを禁じる事で、**呼んだ先で間接にロックを取る**経路が消え、デッドロックは実行時に検出する物ではなく、書けない物になる。

Shidzuku の第3章 3.5 には「依存の循環の扱い。`ask` の循環はデッドロックの温床だが、`flow` の循環(フィードバック)には用途があり得る」が未定のまま残っている。
Hike の制限は、この未定事項に一つの形を与える。

- **`ask` の閉路を検証器で禁じる。** `depends` は宣言されているため(第3章 3.2)、`ask` だけを辺にしたグラフの閉路はコンパイル時に見つかる。
  A が B へ `ask` し、B が応答前に A へ `ask` する形は、U10 が再入を禁じれば必ず期限切れになり、許せば A の状態が応答待ちの途中で書き換わる。
- **`flow` の辺は数えない。** 応答を待たないため、閉路があっても待ちは生じない。Hike が `concurrent` の変数だけを対象にしたのと同じく、対象を待ちの生じる物に絞る。

ただし Shidzuku の `ask` は期限の中で必ず返る(ADR 0004)。したがって閉路は**永久に止まる**のではなく、**毎回期限切れになる**。
害は Hike のデッドロックより静かで、そのぶん気付きにくい。検出をエラーにするか警告にするかは、U10 の再入の決定と組にして決める。

### 3.4 H-4 — 出力から元の記述へ戻る対応表

Hike は `-g` 一つで、ネイティブ出力には DWARF を、WebAssembly 出力には DWARF のカスタムセクションと source map を付ける。
どちらでも、生成した LLVM IR や WAT ではなく**元の `.hike` の行**で止まり、局所変数と戻り値が見える。
Hike はこのために、LLVM を経ない WAT の出力(WABT の経路)を別に持っている。**元の記述への対応を自分の手で保つため**である。

Shidzuku はトランスパイル先が2つある(ADR 0012)。書き手が body の誤りを追う時、今のままでは生成された Rust か TypeScript の上で追う事になる。
これは第0章 0.2 の一つ目の問題——設計と実装の乖離——を、**デバッガの上で**再び起こす。

- ADR 0012 決定8 のバックエンドの責務 G1〜G6 には、元の記述への対応表が無い。**G7 として足すか**が問いになる。
- TypeScript は source map という標準の形がある(第0章 0.8 が倣う TypeScript の前例そのものが、これを持っている)。
- Rust には元の位置を指す標準の指令が無い。生成コードに記述の位置を注記する所から始め、デバッガへの対応は後に回す事になる。
- **ログ(U4)には要らない。** ログは接合面を通る物から動作環境が出す(ADR 0012 決定2)ため、コンポーネント名と公開面は動作環境が既に知っている。
  対応表が要るのは、body の中を人が追う時だけである。

### 3.5 H-5 — 出力先ごとの差し替えには対を揃えさせる

Hike はファイル名の接尾辞(`_linux`・`_amd64`)と `//hike:build` の条件で、出力先ごとにファイルを選ぶ。
さらに、特定の CPU の命令を書いたインラインアセンブリは条件で守らなければならず、wasm32 のような出力先には**持ち運べる実装を別に用意する**よう求める。
守られていない命令を別の出力先へ出すと、コンパイル時に落ちる。

Shidzuku には今、body を出力言語で直に書く逃げ道(Hike の `__asm__` や C の関数の宣言に当たる物)が無い。
しかし外部との境界(U12)で既存のライブラリを使う時、あるいは性能のために Rust で直に書きたい時に、逃げ道を求められる事は想像できる。
その時に効くのが ADR 0012 決定9 である——**同一バージョンの Rust 出力と TypeScript 出力は相互に置換可能でなければならない**。

- 逃げ道を置くなら、**全てのトランスパイル先の対が揃って初めて通る**事を条件にする。Rust だけの逃げ道は、そのコンポーネントを TypeScript に出せなくし、混在の適合試験(Phase 1 の成果物)を壊す。
- 逃げ道は io の層に限るか、役割 `boundary` に限るのが自然である(外部の技術との授受は boundary の責務。第2章 2.4)。

逃げ道を置くかどうか自体は、本書の範囲ではない。**置くなら対を必須にする**という条件だけを、U12 と Phase 1 への入力として残す。

## 4. 既に持っている物

Hike の取り組みのうち、Shidzuku が既に同じ判断をしている物。**独立に同じ所へ着いた事は、その判断の裏付けになる。**

- **H-6 テキストとバイト列。** Hike は `string` を「正しい UTF-8 のバイト列」に限り、C との授受は `cstring` で、
  UTF-8 でない符号(Shift_JIS 等)は**決して `string` に直接入れず**、専用の復号器を通す。これは ADR 0013 のテキストとバイト列の分離、役割 `parse` による生成と同じ線引きである。
  Shidzuku の方が一歩進んでいる。Hike の `string` はバイト単位の添字と切り出しを許し(文書で「強く非推奨」とするに留まる)、
  Shidzuku はテキストを不透明な値にして、添字と長さを `parse` の層に閉じ込めた(第2章 2.4)。Hike の非推奨は、Shidzuku が構文で禁じた物である。
  なお Hike の復号器は `(string, error, 消費したバイト数)` を返す。消費量を返す形は、`parse` の層がバイト列を少しずつ読む時(流れの受け口)に参考になる。
- **H-7 共有の相手を宣言の外から触らせない。** Hike の `threadable`・`concurrent` の変数は、宣言したモジュールの外から触れない。
  「モジュール間の通信は公開の関数を通す。所有と同期の境界を、記憶域の内部への偶然の接触に頼らず、プログラムに現す」と書く。
  Shidzuku ではコンポーネントを跨ぐ共有メモリそのものが無く、内側への侵入は書けない(E0018-4)。同じ考えを、Shidzuku はプロセスの境界で構造的に保証している(ADR 0012 決定5)。
- **H-8 接着コードを書かせない。** Hike は輸出した関数から C のヘッダを、WebAssembly の出力から `runtime.js` を生成し、境界の両側を一つの記述から作る。
  Shidzuku でも公開面の受け口・出口の骨組みと接合面の呼び出しはバックエンドが生成する(ADR 0012 決定8 の G3・G4)。
  記述の外にある相手(U12)へ向けた骨組み(相手側の型定義など)まで生成するかは、U12 で改めて問える。
- **H-9 型に値の引数を取る。** Hike の `Matrix[int, 8, 8]` は、型の引数にコンパイル時の値を取る。Shidzuku の `int64(2)`・`dec(18.2)`・単位の欄も、型に値を載せている(ADR 0021・0022)。
  書き手の `data` に値の引数を許すかは U14 以降の話であり、今は要らない。
- **H-10 識別子の目録。** Hike は道具(VS Code の拡張)のために、識別子の目録を JSON で出す。Shidzuku のコンポーネント記述子(ADR 0012 決定9)は、
  省略の禁止で必須化された宣言の全てを載せる、より強い目録である。図(U8)を記述子と同じ物から出せば、C4 の「一つのモデルから図を投影する」原則(ADR 0007)も満たす。

## 5. 取り込まない物

- **H-11 既定の引数。** Hike は具体の実装の引数に既定値を付ける事を勧める(`Decode(src, length int = -1)`)。
  Shidzuku は既定値を持たない(ADR 0008)。ADR 0024 決定2 の通り、既定値は読み手に記述の外の知識を求める。
- **H-12 綴りで決まる可視性。** Hike は Go に倣い、大文字で始まる名前を公開とし、`threadable`・`concurrent` の変数には小文字を強制して、うっかり公開されるのを防いでいる。
  **綴りが可視性を運ぶ事自体が、省略された宣言である。** Shidzuku は可視性をキーワードで言う方向を取っている(計画書 7.2)。
  また書き手の名前は UTF-8 であり(ADR 0014)、大文字と小文字の区別を持たない文字(漢字・仮名)で名前を書けるため、綴りに意味を載せられない。
- **H-13 常駐する物を持たない。** Hike は、使った機能の分だけ実行時の支援を生成し、使わない物は最終的な出力から消える。
  Shidzuku は逆に、動作環境を常駐させて期限・流量制御・監督・ログを引き受けさせた(ADR 0012 決定1・2)。
  **目的が違う。** Hike の目的は余計な物を持たない事、Shidzuku の目的は障害を伝播させない事であり、後者は常駐する監督なしには成り立たない。
- **H-14 寿命の模型。** `area` ブロックは、ブロックの中で作った値をブロックの終わりにまとめて捨てる。外へ持ち出すには `deepcopy` を明示し、
  浅い持ち出しはコンパイル時エラーになる。他に関数単位の region、参照計数と写し書きの文字列がある。
  これらはメモリの管理であり、ADR 0012 決定8 の分担では**出力言語の仕事**である(Rust は所有権で、TypeScript は GC で持つ)。
  Shidzuku の body に寿命の宣言を足すと、出力言語ごとに意味を写す負担が増え、TypeScript には写す先が無い。
  ただし「寿命の境界を越えるのは明示の操作だけ」という形は、ADR 0023 決定2(内側の鍵は外へ出ない)や E0013-3(照合キーを永続化しない)と同じ形をしている。
  Shidzuku は同じ形を、メモリではなく**データの届く範囲**に使っている。
- **H-15 インラインアセンブリと C の関数の直接の宣言。** 今のトランスパイル先(Rust・TypeScript)には要らない。
  ADR 0012 決定7 が C を4番目の言語に置いており(組込みの機器にコンポーネントを置けるか)、その時に H-5 の条件と併せて再考する。
- **H-16 主スレッドへの固定。** GUI や GPU の文脈は特定のスレッドでしか触れない。Hike の `eventloop` は、作業スレッドから主スレッドへ関数を送って結果を受け取る。
  Shidzuku で対応するのは「特定の機器が繋がった節点でしか動けないコンポーネント」であり、スレッドではなく**配置**の問題である。
  配置の記述は Phase 2 の動作環境の設計で扱う。今は取り込まない。
- **H-17 流れを繰り返しで受ける。** Hike は `for v := range <-stream` で流れを引き出し、途中で `break` できる。これは受け手が引く(pull)形である。
  Shidzuku の `flow` は、動作環境が受け口へ配り(接合面 H5)、流量制御は接続の属性として動作環境が適用する(第4章 4.3)。
  受け手が引く形にすると、流量制御が body の書き方に依存し、接続の宣言から読めなくなる。受け口は配られる形のまま置く。

## 6. 論点 — 課題への入力

本書が見つけた問いを、受け取る課題ごとに並べる。いずれも本書では決めない。

| # | 問い                                                                                    | 受け取る課題               | 出どころ |
| - | --------------------------------------------------------------------------------------- | -------------------------- | -------- |
| 1 | 内側の並行を許すなら、`state` に並行時の扱いの欄を足すか。逐次ならこの欄は要らない      | U10                        | H-1      |
| 2 | body の中で、互いに依存しない `ask` を先に送り出し、後で待てるか                        | U10(関連 U13 の仕事の期限) | H-2      |
| 3 | 応答を待つ所を body に印として現し、再入が起き得る所を記述から読めるようにするか        | U10                        | H-2      |
| 4 | `ask` の閉路を検証器で見つけるか。見つけたらエラーか警告か。`flow` の辺は数えない       | 第3章 3.5・U10             | H-3      |
| 5 | バックエンドの責務に「元の記述への対応表」(G7)を足すか                                  | Phase 1(ADR 0012 決定8)    | H-4      |
| 6 | body を出力言語で直に書く逃げ道を置くか。置くなら全てのトランスパイル先の対を必須にする | U12・Phase 1               | H-5      |
| 7 | 記述の外の相手へ向けた骨組み(相手側の型定義など)を生成するか                            | U12                        | H-8      |

- 論点1〜3 は U10 の三つの面であり、**U10 と U11 を同時に決める時(計画書 4.3 の順2)の比較の材料**として使う。
  特に論点1 は、U10 の選択肢(逐次か並行か)の費用を宣言の数で見せるため、選択肢の表に載せる。
- 論点4 は U10 の再入の決定に従う。再入を禁じれば閉路は必ず期限切れになり、許せば状態が応答待ちの途中で書き換わる。どちらでも閉路は害であり、残る問いは重さ(エラーか警告か)だけである。
- 論点5・6 は Phase 1 の実装に入ってから決めても、仕様を書き直さない。接合面 H1〜H8 に触れないためである。

## 7. 所見

- **Hike から取り込める物は、コンポーネントの内側に集まった。** 一覧の17件のうち、取り込む候補は5件で、全て U10(内側の実行モデル)と Phase 1(body の出力)に当たる。
  コンポーネントの間(接続・障害境界・配置)には、Hike は比べる物を持たない。Hike はプロセスの内側の言語だからである(第1節)。
- **Hike が構文で解いた問題のいくつかを、Shidzuku は構造で解いている。** 関数の色は制約強度の層が囲い(3.2)、共有状態への侵入はプロセスの境界が塞ぎ(H-7)、
  テキストの添字は役割が閉じ込める(H-6)。Hike は一つのプロセスの中で同じ問題に当たり、宣言と構文の制限で答えた。
- **取り込まない物の多くは、ADR 0008(省略の禁止)と ADR 0012(分担)で切れた。** 既定の引数と綴りの可視性は前者で、寿命の模型と常駐しない実行時は後者で切れる。
  新しい理由を要した物は無い。
- **第0章 0.9 の系譜には、今は足さない。** 取り込む候補は全て入力の段階であり、U10 や Phase 1 の ADR が採った時に、何を取り込んだかと併せて系譜に足すのが順序である
  (ADR 0024 の背景:「取り込みの範囲が書かれていないと、後の ADR が同じ名前を根拠に挙げても、何を根拠にしたのかが読み手に分からない」)。

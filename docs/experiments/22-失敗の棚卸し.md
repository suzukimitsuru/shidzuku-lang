# 思考実験 22: 失敗の棚卸し — 何を失敗と呼び、どこに書くか

- 状態: Draft
- 日付: 2026-09-26
- 目的: U13(失敗の体系)の材料を集める。仕様書と ADR に散らばった「うまくいかない事」を全て並べ、区別の軸を探す
- 経緯: ADR 0023(対になる通信の相関)を採用し、U25 は閉じた。第4章 4.6 に残ったのは
  **仕事全体の期限**(思考実験 20 の論点5)と **`on failure` の欄の形**(思考実験 21 の論点1・2)であり、
  どちらも「何を失敗と呼ぶか」に依る。第6章 6.1 は「データとして正常な不在と系の失敗は別の語彙とする。後者は U13 で定める」と宣言したまま、語彙を持っていない
- 進め方: 棚卸し → 軸の抽出 → 一つの系に全部出して書き下ろし → 論点

## 2. 分かった事 — 「失敗」は一語で三つの物を指している

| 呼び方                 | 実体                                 | 群   | 受け取る側                                                   |
| ---------------------- | ------------------------------------ | ---- | ------------------------------------------------------------ |
| 直和の区分としての失敗 | 正常な結果の一つ。型に名前がある     | A・B | 呼び手が分岐する                                             |
| 戻る値としての失敗     | 演算・解析の結果。**型に名前が無い** | C・D | 書かないとコンパイルが通らない(はずだが、何を書くのかが未定) |
| 接続の失敗             | 期限超過・相手障害・投入不能         | E    | 呼び手と `on failure`                                        |

**F 群(待ち)はどれでもない。** 何も返らず、何も起きない。時間が経つだけである。

## 3. 軸を当てる

棚卸しを四つの軸で並べ直した。

| 軸                     | 値                                      | 分かれ目                          |
| ---------------------- | --------------------------------------- | --------------------------------- |
| 軸1 誰が決めたか       | 業務の規則 / 系の事情                   | A・B が業務、C〜F が系            |
| 軸2 型に名前があるか   | ある / 無い                             | A・B はある、C〜F は無い          |
| 軸3 再試行で変わるか   | 変わらない(決定的) / 変わり得る(一過性) | C・D は決定的、E・F は一過性      |
| 軸4 誰が埋め合わせるか | 呼び手 / 実行系 / 運用                  | A〜D は呼び手、E は両方、F は運用 |

**軸1 と軸2 はほぼ一致する**——業務が決めた失敗には名前があり、系の事情による失敗には無い。
第6章 6.1 が「別の語彙とする」と言ったのはこの境目である。

**しかし軸3 は境目が違う。** C・D(演算と解析)は何度やっても同じ結果になるが、E(通信)は再試行で変わり得る。
呼び手にとっての意味はまるで違う——前者は記述の誤りに近く、後者は運が悪かっただけである。
**「系の失敗」を一つの語彙にまとめると、この違いが消える。**

## 4. 一つの系に全部出す

思考実験 21 の受注の系に、A〜F の全ての失敗を出した。

```plaintext
data 受注番号 (id)
data 引当番号 (id)
data 注文       { 品目: 品目ID, 数量: uint32(0) 個, 合計: int64(2) 円 }
data 受注不可   = 在庫なし | 受付停止中                      # B
data 引当の結果 = 引当済み(引当番号) | 在庫なし              # B
data 受注の状態 = 確定(受注番号) | 取消(受注番号, 取消の理由) # A・B

component OrderIntake {
  constraint {
    depends  Inventory, OrderStore
    expose   受注(注文) -> 受注番号 | 受注不可              # B は書ける
    ...
  }
  body {
    # C: 合計 = 単価 × 数量 が int64(2) 円 の幅を出たら?
    # D: Frontdesk から来たバイト列が JSON として読めなかったら?(境界と解析の役割)
    # E: Inventory への ask が期限超過したら?
  }
}
```

書けた物と書けなかった物が、はっきり分かれた。

| 群 | 書けたか     | どこに書いたか                                        |
| -- | ------------ | ----------------------------------------------------- |
| A  | 書けた       | `data` の直和(第6章 6.1)                              |
| B  | 書けた       | 公開面の直和(`-> 受注番号 \| 受注不可`)               |
| C  | **書けない** | 失敗の型が無い。`body` の中で分岐する形も宣言できない |
| D  | **書けない** | 同上。parse の役割は決まっているが、失敗の形が無い    |
| E  | 半分         | `on failure` に散文で書く。呼び手の受け口には現れない |
| F  | **書けない** | 何も起きないため、書く場所そのものが無い              |

## 5. 論点

### 論点1: 公開面の宣言に、系の失敗が現れない

```plaintext
expose 受注(注文) -> 受注番号 | 受注不可
```

この宣言を読むと、返ってくるのは**受注番号か受注不可の二つだけ**に見える。
しかし第4章 4.1 は「相手の障害・期限超過時は失敗応答が返る」と定めている。**三つ目が型に現れていない。**

- 呼び手は、宣言に無い物を受け取る事になる。**省略の禁止(第0章 0.5)の網に穴がある。**
- 書けば `-> 受注番号 | 受注不可 | 期限超過 | 相手障害` となり、**全ての公開面に同じ二語が並ぶ**。
- これは U13 の中心の問いである。

### 論点2: C 群(数値の失敗)の型が無い

第3章 3.3 は「例外ではなく**失敗として戻る値**であり、受け取りを書かなければコンパイルが通らない」と定めている。
しかし**戻る値の型が宣言されていない**。`加える(a, b)` の結果は `int64(2) 円` なのか、`int64(2) 円 | 幅を出た` なのか。

- 後者なら、**全ての算術に分岐が付く**。第0章 0.5 の「静けさ」と正面から擦れる。
- 前者なら、失敗はどこへ行くのか。
- `body` の中は自由(第2章 2.4)だが、**自由なのは型の選択であって、失敗の有無ではない**。

### 論点3: 軸3(再試行で変わるか)が、語彙に現れていない

`0 除算` と `期限超過` を同じ「系の失敗」と呼ぶと、呼び手は同じ扱いをする事になる。

- `0 除算` は何度やっても起きる。再試行は無意味であり、記述の誤りに近い。
- `期限超過` は次は通るかもしれない。再試行が意味を持つ(再試行の規定は第4章 4.6 の未定事項)。

**この二つを型の上で分けるかどうか**が、U13 の二つ目の問いである。

### 論点4: F 群(待ち)は、失敗が起きない事が問題である

確定が来ない・引当が残る・通知が捨てられる。いずれも**何も返らない**ため、受け取って分岐する形では書けない。

- 誰かが時間を測らなければ、失敗は永久に起きない。
- 測る主体は、実行系(期限を持たせる)か、書き手が置くコンポーネント(掃除をする)かのどちらかである。
- **仕事の期限(第4章 4.6)は、この問いの一部である。**

### 論点5: `on failure` が受け持つのは E 群だけである

`on failure <コンポーネント>` はコンポーネントの障害に対する埋め合わせを書く欄であり、
B 群(業務の拒否)も C 群(演算の失敗)も対象外である。

- 業務の拒否は普通の応答であり、フローの接続として書ける。
- **C 群が落ちる場所が無い。** `合計` の桁が溢れた時、それはコンポーネントの障害なのか、応答なのか。
- 思考実験 21 の論点1・2(補償が散文になる)も、この欄の形の問題である。

### 論点6: 「障害は伝播しない」と「失敗は値として戻る」の関係

第0章 0.4 は障害の非伝播を全コンポーネントの不変条件とする。一方、失敗は値として呼び手へ戻る。

- **戻った失敗を呼び手が無視したら、それは伝播したのと同じではないか。**
- 現在は「受け取りを書かなければコンパイルが通らない」(第3章 3.3)で塞いでいるが、
  その検査の番号も、受け取りの形も決まっていない。

## 6. 案の素描(U13 の ADR へ渡す)

### 論点1 への案

- **F-1: 系の失敗を公開面に書かない。** 全ての `ask` に暗黙で付く。記述は軽いが、**既定表という外部知識**が生まれる(ADR 0008 と擦れる)。
- **F-2: 公開面に書かせる。** `-> 受注番号 | 受注不可 | 期限超過`。省略の禁止に沿うが、同じ語が全公開面に並ぶ。
- **F-3: 器を分ける。** 応答の型とは別に、系の失敗だけを受ける欄を公開面に持つ(`-> 受注番号 | 受注不可 fails 期限超過 | 相手障害` のような形)。
  業務の失敗と系の失敗が**型の上で混ざらない**。語が1つ増える。

### 論点2 への案

- **G-1: 演算の結果を直和にする。** 全ての算術に分岐が付く。
- **G-2: 失敗を伝播させる形を持つ**(`?` に当たる記法)。書く量は減るが、記法が1つ増える。
- **G-3: 境界で受ける。** 演算は幅を宣言した型の上でのみ許し、幅を出る可能性がある計算は
  `収める`・`丸める` のような明示の操作に閉じ込める(ADR 0021 の既存の形を広げる)。

### 論点4 への案

- **H-1: 仕事に期限を書く**(`flow` 宣言の欄。思考実験 20 の `within`)。
- **H-2: 状態に期限を書く**(`state 引当中 volatile within 30 分` のような形)。孤児の掃除はこちらが自然である。
- **H-3: 言語は持たず、運用に委ねる。** ADR 0008 の立場からは弱い。

## 7. 未解決課題への入力

- **U13(失敗の体系)**: 本実験が材料である。決めるべきは四つ——
  (a) 系の失敗を公開面にどう書くか(論点1)、(b) 数値と解析の失敗の型(論点2)、
  (c) 再試行で変わる失敗と変わらない失敗を分けるか(論点3)、(d) 待ちに期限を与える場所(論点4)。
- **U2・第4章 4.5(`on failure` の欄の形)**: C 群の落ちる場所が無い(論点5)。思考実験 21 の S-a と同じ所で決まる。
- **U4(ログ規約)**: 捨てられた通知・走った補償・期限で掃除した引当を、運用がどう知るか。
- **U11(順序保証)**: 再試行が意味を持つ失敗(論点3)は、再送の順序と絡む。
- **U12(外部世界との境界)**: 外部が返す失敗は、この体系のどこに入るか。
- **U16(版の混在)**: 失敗の語彙が版を跨ぐ(古い版が知らない失敗を受け取る)。

## 8. 次の行動

- U13 の ADR を起案する前に、**論点1 の三案(F-1〜F-3)を一つの系で書き比べる**。
  公開面が何行になるか、呼び手の分岐がどう変わるかを測る
- 論点2 は数値の章(第6章 6.3)の既存の操作と地続きであるため、ADR 0021 の決定を読み直した上で判断する
- 論点4 は、思考実験 20・21 が出した二つの穴(確定が来ない・孤児の引当)を同じ形で塞げるかを確かめる

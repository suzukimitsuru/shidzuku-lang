## 2. 仮構文による記述

型の構文は未定のため仮。直積(レコード)・直和(選択)・識別子型・列で書いてみる。

```plaintext
data 品目ID     (識別子)
data 受注番号   (識別子)
data 受付ID     (識別子)
data センサーID (識別子)

data 注文       { 品目: 品目ID, 数量: 数値 }
data 受注結果   = 受注(受注番号) | 受注不可(理由)

data 計測値     { センサー: センサーID, 時刻: 時刻, 生値: 数値 | 欠損 }
data 集約値     { センサー: センサーID, 期間: 期間, 平均: 数値, 最大: 数値, 最小: 数値 }

data 書込記録   { キー: キー, 値: 値, 版: 版 }
data 照会結果   = 見つかった(値) | なし
```

## 3. 検証結果

### 3.1 書けた事

- **直積+直和+識別子型+列で、4実験の全データが書けた**。それ以上の語彙(継承・型引数等)は一度も必要にならなかった。
- **ask の応答は直和そのもの**。`受注番号 | 受注不可` はデータの直和と同じ語彙で書け、応答の形とデータの形が一つの体系に揃う。
- **欠損は直和で明示できる**(`数値 | 欠損`)。null が要らない。「値が無い」事も型に書かれる——省略の禁止(ADR 0008)の型への自然な延長。
- **識別子型の名前的な区別が効く**。受注番号・受付ID・センサーID は中身が同じ文字列でも別型になり、取り違え(受付ID を受注番号として渡す)が型検査で落ちる。静かさ(驚きの排除)に直結する。

### 3.2 書きにくかった事 — 仕様に戻す論点

1. **宣言の置き場所が無い**。`注文` は OrderIntake と OrderStore の両方の公開面に現れる**共有語彙**であり、どちらのユニットの内側にも置けない。
  片方に置くと、語彙を参照するためだけに depends が発生し、依存の意味(通信相手)が濁る。→ ユニット・フローと並ぶトップレベルの宣言が要る。
  これはユニット・フロー・データを束ねる器、すなわち **U14(プログラムの宣言)の必要性の2件目の裏付け**になる(1件目はユニット名の一意性の範囲)。
2. **内部表現との切り分け**。OrderStore の DB スキーマや KVCore のメモリ表は `data 注文` とは別物であり、隠されたままで良い。
  data は「公開面の語彙」だけを対象とし、body 内部の型は自由(内側の原則)——この切り分けは自然に書けた。
3. **「無い」と「失敗」は別物**。照会の `なし`(データとして正常な不在)と、ask の期限超過(系の失敗)を同じ「失敗」に混ぜると語彙が濁る。
  → U13(失敗の体系)への入力。データの直和は前者を、ask の失敗応答は後者を担う、という切り分けの候補。
4. **時間の型が要る**。時刻(計測値)・期間(集約値)・時間量(期限 1s)の3つは言語組み込みの基本型が必要。構文の細部は Phase 1。
5. **計測の単位(℃/℉)は型に載せるか**。Normalizer の変換の本質は単位系の変換だが、単位付き数値型は複雑さが大きい。
  今回は「数値」で書けたため、論点として記録するに留める。

### 3.3 未解決課題への入力

- **U9**: 直積・直和・識別子型・列で全データが書けた。名前的型付けが取り違え検出に有効。宣言はトップレベル。→ ADR 0009 を起案。
- **U14(プログラムの宣言)**: data 宣言の置き場所がトップレベルの器を要求する(本実験 3.2-1)。検討時の入力とする。
- **U13(失敗の体系)**: 「データとして正常な不在」と「系の失敗」の区別が型の語彙に現れた(本実験 3.2-3)。

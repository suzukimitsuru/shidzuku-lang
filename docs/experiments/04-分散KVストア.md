# 思考実験 04: 分散 KV ストア(Phase 2 の目標システムの先取り)

- 状態: Draft
- 日付: 2026-08-19
- 目的: 第1〜3章(Draft)の語彙を通しで検証する。特に第2章の新形式(flow の受け口の expose、state の宣言)と、durable+idempotent の型。併せて Phase 2 の成果物(小さな分散 KV ストア)を先取りし、仕様の穴を探す
- 進め方: 計画書の検証方法に従う。まず単一ノードの永続 KV を書き、次に3ノード複製へ拡張を試みる。書けない事があれば仕様に戻す

## 1. 対象システム

- クライアントが get / put する KV ストア
- 書き込みは追記ログで永続化し、再起動後も失われない
- (拡張)3ノードに複製し、ノード障害でも応答を続ける

単位は3つ。

| 単位       | 隠す知識                           | 公開面           |
| ---------- | ---------------------------------- | ---------------- |
| ClientGate | クライアントプロトコル・外部表現   | get / put の受付 |
| KVCore     | キー空間の整合性(版・上書きの規則) | 取得・格納       |
| Persister  | 永続化方式(現在は追記ログ)         | 書込記録の受付   |

## 2. Shidzuku による記述(第1〜3章の構文)

### 2.1 ClientGate — 受付

```plaintext
unit ClientGate {
  intent {
    why      "クライアントプロトコルと外部表現の知識をこの単位に閉じ込める。内側はキーと値だけを扱う。"
    rejected option "各単位が自分のプロトコル実装を持つ"
             reason "プロトコルの変更が全単位に波及するため。"
    change   "プロトコルの追加(HTTP 管理 API 等)を想定。内側への公開面は変えない。"
  }
  constraint {
    depends  KVCore
    expose   受付(要求) -> 結果 | 失敗
    isolate  failure
  }
  body { ... }
}
```

### 2.2 KVCore — キー空間の整合性

```plaintext
unit KVCore {
  intent {
    why      "キー空間の整合性(版の管理・上書きの規則)の知識をこの単位に閉じ込める。"
    rejected option "ClientGate が直接 Persister を読み書きする"
             reason "整合性の規則(版の比較・同時書込の解決)が受付と永続化に散らばるため。"
    change   "版の規則の変更(単調増加 → ベクタクロック)を想定。公開面は変えない。"
  }
  constraint {
    depends    Persister
    expose     取得(キー) -> 値 | なし
    expose     格納(キー, 値) -> 完了 | 失敗
    expose     書込記録(キー, 値, 版) の流れ
    state      KV表 volatile          # ← 論点1: volatile では言い切れない(復元できる事が本質)
    layers {
      rules { pure }                  # 版の比較・上書き判定は純粋
      store { io }                    # メモリ表の保持・復元
    }
  }
  body { ... }
}
```

### 2.3 Persister — 書込記録の永続化

```plaintext
unit Persister {
  intent {
    why      "永続化方式(現在は追記ログ)の知識をこの単位に閉じ込める。"
    rejected option "KVCore がメモリ表と永続化を一緒に持つ"
             reason "整合性の規則と保存方式は変更の理由が異なるため。"
    change   "スナップショット+ログ圧縮の導入を想定。公開面(書込記録の受付・再生)は変えない。"
  }
  constraint {
    depends    なし
    expose     書込記録(キー, 値, 版) の受け口   # 第2章の新形式。自然に書けた
    expose     再生() -> 書込記録の列
    idempotent 書込記録                          # durable 接続の受け口の必須条件(E7)
  }
  body { ... }
}
```

### 2.4 フロー — 格納と復元

```plaintext
flow 格納 {
  intent {
    why      "応答期限のある get/put は ask、永続化は durable な flow で切り離す。格納の完了応答は永続化の完了を待って返し、受け付けた書込を失わない。"
    rejected option "put の応答を永続化を待たずに返す"
             reason "完了と応答した書込がノード障害で消え、利用者にとって最大の驚きになるため。"
    change   "応答を早く返す緩い書込モードの追加を想定。接続の宣言(durable の有無)の違いとして表す。"
  }
  ClientGate -> KVCore    : ask 格納(キー, 値) -> 完了 | 失敗
  KVCore     -> Persister : flow 書込記録  pressure block(期限 1s)  durable
  on failure Persister : KVCore は格納に失敗を返す(伝播しない)
  on failure KVCore    : 再起動し、Persister の再生() から KV表 を復元する
}
```

## 3. 検証結果

### 3.1 書けた事 — 第1〜3章の語彙は単一ノードでは通った

- **単一ノードの永続 KV は全て書けた**。ask(get/put)、durable+idempotent の型(E7)、期限付き block、on failure の埋め合わせ、pure/io の階層、粒度の指針(3単位とも why 1文)。
- **flow の受け口の expose(第2章の新形式)**: Persister の `書込記録(…) の受け口` が自然に書け、公開面の完全性(E5)が接続の検査と噛み合う。
- **「durable な入力と冪等な再処理で復元」の型**(第2章 2.2)が、KVCore の復元(`再生()` からの再構成)としてそのまま現れた。

### 3.2 書きにくかった事 — 仕様に戻す論点

1. **state volatile では KVCore を言い切れない**。KV表 は論理的には「失ってはならない」が、メモリ上の写しは再起動で消えてよい(durable な書込記録から復元できるから)。
  volatile(失ってよい)の一語では「消えるが復元できる」と「消えたら失われる」を区別できず、E8(矛盾検査)も判定できない。
  → 第2章の state に **recoverable(復元元の指定付き)** を追加する提案。`state KV表 recoverable(Persister.再生)` のように復元元を指せば、E8 は「復元元が durable か」まで機械検査できる。
2. **複製を書く場所が仕様にない**。3ノード複製へ拡張しようとすると、KVCore という**1つの設計単位**を**3つの配置単位**として動かす事になるが、
  unit 宣言にも flow 宣言にも「いくつ動くか・どこで動くか・レプリカ間で何を合意するか」を書く場所がない。
  第0章 0.3 の「設計=処理=障害=配置が同一」は、複製された単位では**設計単位1つ:配置単位N個**となり緊張する。
  Replicator のような単位を立てても、それは全ノードに跨る存在であり、単位=配置単位の原則と噛み合わない。
  → 配置・複製・合意対象の記述は U6(Raft の適用範囲)そのものであり、Phase 2 の決定事項。
  ただし「言語仕様に配置の章(第4章)が要るか、実行系の設定に置くか」は Phase 0 の骨格に関わるため、**ユーザーの判断が必要**。

### 3.3 未解決課題への入力

- **第2章の修正(本実験で実施)**: state の語彙に recoverable を追加。E8 の判定を「復元元の durable 検査」まで具体化。
- **U6(Phase 2)**: 複製の記述場所、合意対象の宣言(どの接続・どの状態を Raft に載せるか)、設計単位と配置単位の 1:N 関係の整理。本実験の 3.2-2 が最初の具体例。
- **U4(Phase 2)**: 復元中の単位の扱い(受付を止めるか・遅らせるか)は運用イベントとしてログ規約の対象。

## 4. 次の行動

- 第2章の state を volatile | recoverable の2種に改訂する(本実験の結論。実施済み)
- 「配置の記述を言語仕様に含めるか」をユーザーに諮る(Phase 0 の骨格判断)
- U6 の検討開始時に本実験の 3.2-2 を最初の入力とする

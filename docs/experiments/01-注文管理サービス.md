# 思考実験 01: 注文管理サービス(Web API+DB)

- 状態: Draft
- 日付: 2026-08-19
- 目的: U1(ADR 0003 の意図テンプレート)の実地検証。副次的に U2(通信)・U3(内部階層)・U7(粒度)への入力収集
- 進め方: 計画書の検証方法に従い、既存の小さなシステムを Shidzuku で記述してみる。書けない事があれば仕様に戻す

## 1. 対象システム

よくある注文管理の最小構成。

- 顧客が HTTP API で注文を送る
- 在庫を引き当てる(在庫不足なら受注を断る)
- 注文を DB に保存し、受注番号を返す

単位は3つ。

| 単位        | 隠す知識                 | 公開面           |
| ----------- | ------------------------ | ---------------- |
| OrderIntake | HTTP・外部表現(JSON)     | 注文の受付       |
| Inventory   | 在庫の整合性(引当・解放) | 引当の可否       |
| OrderStore  | 永続化方式(RDB)          | 注文の保存・照会 |

## 2. Shidzuku による記述(仮構文)

単位・制約・フローの構文は第1〜3章が未定のため仮。意図(intent)のみ ADR 0003 に従って書く。

### 2.1 OrderIntake — 受注の受付

```plaintext
unit OrderIntake {
  intent {
    why      "HTTP と外部表現(JSON)の知識をこの単位に閉じ込める。内側の単位はプロトコルを知らず、注文というデータだけを扱う。"
    rejected option "各単位が自分の HTTP エンドポイントを持つ"
             reason "プロトコルの変更(REST から gRPC 等)が全単位に波及するため。"
    change   "モバイル向けに gRPC を追加する可能性。追加しても内側への公開面(注文データ)は変えない。"
  }
  constraint {                      # 仮: 第2章で定義予定
    depends  Inventory, OrderStore  # 依存はこの2つのみ
    expose   受注(注文) -> 受注番号 | 受注不可
    isolate  failure                # 内部の障害を外へ伝播させない
  }
  body { ... }
}
```

### 2.2 Inventory — 在庫の引当

```plaintext
unit Inventory {
  intent {
    why      "在庫の整合性を保つ知識(引当・解放・二重引当の防止)をこの単位に閉じ込める。"
    rejected option "OrderStore が注文と在庫を一緒に管理する"
             reason "注文の永続化と在庫の整合性は変更の理由が異なり、一方の変更が他方を壊すため。"
    change   "複数倉庫への分割を想定。倉庫が増えても公開面(引当の可否)は変えない。"
    refs     "docs/decisions/0003-検証不能な意図の記述形式.md"   # 任意項目の使用例
  }
  constraint {
    depends    なし
    expose     引当(品目, 数量) -> 引当済 | 在庫不足
    expose     解放(引当)
    idempotent 引当                 # 同じ注文の再引当は二重にならない
  }
  body { ... }
}
```

### 2.3 OrderStore — 注文の永続化

```plaintext
unit OrderStore {
  intent {
    why      "注文の永続化方式(現在は RDB)の知識をこの単位に閉じ込める。"
    rejected option "各単位が直接 SQL を書く"
             reason "スキーマ変更が全単位に波及するため。"
    change   "注文履歴の増加でイベントソーシングへ移行する可能性。移行しても公開面は変えない。"
  }
  constraint {
    depends  なし
    expose   保存(注文) -> 受注番号
    layers {                        # 仮: U3 内部階層の宣言
      domain { pure }               # 注文の組み立ては純粋
      driver { io }                 # SQL ドライバ層のみ IO 可
    }
  }
  body { ... }
}
```

### 2.4 フロー — 受注処理

```plaintext
flow 受注処理 {
  OrderIntake -> Inventory  : ask 引当(品目, 数量)   # 同期: 応答に引当可否が要る
  OrderIntake -> OrderStore : ask 保存(注文)         # 同期: 受注番号を返すため
  on failure Inventory  : OrderIntake は受注不可を返す(伝播しない)
  on failure OrderStore : OrderIntake は引当を解放し、受注不可を返す(伝播しない)
}
```

## 3. 検証結果

### 3.1 書けた事 — テンプレートは機能した

- **理由(why)**: 3単位とも「何の知識を隠すか」に実質的な答えを書けた。「必要だったから」のような動機文にならず、設計判断そのものが残る。
- **棄却(rejected)**: (選択肢, 理由)の構造が「本当に代替案を検討したか」を自問させる。E2(1件以上)は3単位とも自然に満たせ、`rejected none` は不要だった。
- **変化(change)**: 公開面の安定性の宣言として機能し、W2(陳腐化検出)の判定対象が明確になる。
- **参考資料(refs)**: 任意項目として1箇所のみ使用。無理なく省略できた。

### 3.2 書きにくかった事 — 仕様に戻す論点

1. **棄却のスコープが混在する**。Inventory の棄却は「単位の分割」への棄却、OrderStore の棄却は「実装方式」への棄却だった。
  テンプレートがどちらを求めるのかは ADR 0003 に明記されていない。
  → ADR 0003 に「棄却の対象は、この単位の境界を決めた判断(分割・実装方式のどちらも可)」等の追記を提案。
2. **フロー(接続)に意図が書けない**。「なぜ引当を保存より先にするか」(過剰販売を防ぐため。受けてから引く案を捨てた)という設計判断は、どの単位の intent にも属さない。
  現仕様では意図は単位の三層記述にのみ存在する。
  → フローにも intent(少なくとも理由と棄却)が必要ではないか。第3章(通信モデル)・U2 の論点として追加を提案。
3. **入口単位の why は定型化しやすい**。OrderIntake の「隠す知識」はプロトコルであり、この種の変換(adapter)単位では答えがほぼ定型になる。
  W1(コピペ検出)は完全一致のみ検出するため誤検出はしないが、形骸化の初期兆候として経過観察。

### 3.3 未解決課題への入力

- **U2(通信モデル)**: 受注 API の応答には引当可否と受注番号が要るため、request-reply(同期相当)が2箇所必要だった。
  非同期メッセージのみのモデルでは応答経路を手で組む事になり、この種のシステムでは記述が捻れる。「非同期のみ」案への反証材料。
- **U2(補償)**: 保存の失敗時に引当を解放する補償の流れが必要だった。
  障害境界の記述は「伝播させない」だけでなく「何で埋め合わせるか」を含む必要がある。
- **U3(内部階層)**: OrderStore で domain(純粋)/driver(IO 可)の2階層を宣言する形は自然に書けた。固定階層で足りる感触。
- **U7(粒度)**: 「隠す設計判断が1つ = 1単位」という基準で3単位とも why が1文で書けた。粒度指針の候補として有望。

# 思考実験 14: 数値型の再検討 — 他言語のアプローチの比較

- 状態: Draft
- 日付: 2026-09-03
- 目的: 思考実験 13(数える単位)で見つかった9つの問題を受け、数値型の体系(ADR 0010・0017、および ADR 0019 決定2・決定7)を**白紙から**検討し直す。金融機関・科学技術計算それぞれで実際に使われている型のアプローチを他言語で調べ、比較する
- 経緯: ADR 0010・0017 は本実験の検証を受けて破棄した(採用の記録を参照)。ADR 0019 のうち決定2(整数)・決定7(3つの数値型の変換規則)は再検討の対象として凍結し、決定1・3・4・5・6(論理・時点・日付・時刻・時間帯・暦)は影響を受けない
- 進め方: 「型をいくつ持つか」「変換をどこまで暗黙に許すか」という2つの軸で言語を分類し、Shidzuku がどこに立っていたか、他にどんな立ち位置があるかを比較する。結論は出さず、論点として次の ADR に渡す

## 1. これまでの決定が抱えていた問題(要約)

思考実験 13 で「`単位なし` の値とのスカラー倍は単位も型も変えない」という案を検証したところ、9つの組み合わせのうち4つで**宣言のない丸め**が起きる事が分かった。

とくに `十進数 円 × 実数 単位なし` は、**金額が黙って近似になる経路**である。ADR 0017 が「主に使う型は `実数`」と決めたため、`単位なし` の値が `実数` で書かれる事は起きやすく、既存の警告(W0017-1)はこの経路を検出しない。

根本には、Shidzuku が **3つの数値型を最初から分離し、変換を常に明示させる**という設計を選んだ事がある(ADR 0017 の「2つの型は暗黙に混ざらない」、ADR 0019 の「3つの数値型は暗黙に混ざらない」)。
この設計そのものを、他言語のアプローチと比較しながら再検討する。

## 2. 分類の軸

言語の数値型の設計は、大きく2つの軸で整理できる。

- **軸A: 型をいくつ持つか。** 1つの汎用型に寄せるか、少数の型に分けるか、多数の専用型を持つか。
- **軸B: 変換をどこまで暗黙に許すか。** 全く許さない(常に明示)か、安全な方向だけ許す(非対称)か、全方向を暗黙に許す(数値の塔)か。

この2軸で、調べた言語を配置する。

| 言語 / 体系                   | 軸A(型の数)                                                    | 軸B(暗黙変換)                                                       |
| ----------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------- |
| Shidzuku(現行・破棄対象)      | 3つ(整数・実数・十進数)                                        | 無し。常に明示                                                      |
| Swift                         | 多数(Int8〜Int64・Float・Double 等)                            | 無し。常に明示(`Int(x)` 等の構築子)                                 |
| Haskell                       | 多数(`Integer`・`Int`・`Double`・`Rational` 等)                | **無し。型クラスは能力の共有であって暗黙変換ではない**              |
| C#                            | 少数(`int`・`long`・`float`・`double`・`decimal`)              | **非対称。整数 → `decimal` のみ暗黙、浮動小数点とは明示**           |
| Ada                           | 多数(範囲付き整数・順序固定小数点・十進固定小数点・浮動小数点) | 無し。型ごとに演算子が別で、暗黙の変換が無い                        |
| Fortran                       | 少数(`KIND` で選ぶ `INTEGER`・`REAL`)                          | 一部あり(整数 → 実数の代入)。KIND を跨ぐ演算は警告の対象になり得る  |
| Scheme / Common Lisp / Racket | 1つの塔(整数 → 有理数 → 実数 → 複素数)                         | **全方向。ただし「不正確さは伝染する」という片方向規則を持つ**      |
| Julia                         | 1つの塔に近い(`promote_type` による多重ディスパッチ)           | 全方向。ただし変換の規則を型ごとに1つずつ宣言する                   |
| Python                        | `int`(任意精度)・`float`・`Decimal`・`Fraction`                | `int`↔`float` は暗黙。`Decimal` は分離(Shidzuku と同じ問題を抱える) |

## 3. 型を分けない立場 — 数値の塔(numeric tower)

Scheme・Common Lisp・Julia などの動的型付き言語の多くは、**数値を1つの塔として持つ**。整数は有理数の特殊形であり、有理数は実数の特殊形である、という包含関係を型そのものに埋め込む。

### 3.1 Scheme/Racket の「伝染」規則

Scheme の数値の塔は「正確(exact)」と「不正確(inexact)」の区別を持つ。整数と有理数は正確、浮動小数点は不正確である。
演算に片方でも不正確な値が混じると、**結果は必ず不正確になる**——これを「伝染(contagion)」と呼ぶ。

> Inexactness is a contagious property of numbers, and any numerical operation involving both exact and inexact values must yield inexact return values of at least the same precision as the most precise inexact number appearing in the expression.

これは Shidzuku の言葉で言えば、「**厳密 → 近似の向きだけ、変換を暗黙に許す**」という規則である。近似 → 厳密の向きは常に丸めを要するため、暗黙にはしない。
ADR 0019 の「整数 → 十進数 は原理的に丸めが起きない」という観察と、方向は違うが**構造は同じ**——安全な向きだけ暗黙にする、という考え方である。

### 3.2 Julia の `promote_type` — 明示的に書く暗黙変換

Julia は動的だが型付けは静的に近い。`+` のような演算子は、両辺の型から結果の型を決める`promote_rule` を型ごとに1つずつ宣言する。

```julia
promote_rule(::Type{Rational{T}}, ::Type{S}) where {T<:Integer,S<:Integer} = Rational{promote_type(T,S)}
promote_rule(::Type{Rational{T}}, ::Type{S}) where {T<:Integer,S<:AbstractFloat} = promote_type(T,S)
```

有理数と整数を混ぜると有理数のまま、有理数と浮動小数点を混ぜると浮動小数点になる——**混ぜた結果がどちらの型になるかを、型ごとに1つの規則として書く**。
これは「暗黙変換を許さない」のではなく「**暗黙変換の規則を、言語ではなくライブラリの著者が明示的に定義する**」という第三の道である。ADR 0010・0017・0019 が「言語が3つの型を持ち、変換は書き手が呼び出しごとに書く」としていたのに対し、
Julia は「型ごとに変換の規則を1回だけ書けば、以降は暗黙で効く」という設計である。

### 3.3 Haskell — 塔に見えるが、暗黙変換は無い

Haskell の `Num`・`Real`・`Integral`・`Fractional` は**型クラス**(できる演算の集合)であり、数値の塔のような**包含関係**ではない。

> These conversion functions exist precisely because Haskell does not provide implicit numeric type conversions. For example, when dividing by an `Int` value in a context requiring `Fractional`, you get a type error and must explicitly use `fromIntegral` to convert.

`Int` を `Double` の文脈で使うには `fromIntegral` を必ず書く。**Haskell は「型がいくつあるように見えても、変換は Shidzuku と同じくらい明示的である」**という反例になる。
数値の塔という言葉から連想される「自動でよろしくやってくれる」印象は、Haskell には当てはまらない。

## 4. 型を分けるが、一方向だけ橋を架ける立場 — C# の decimal

C# は `int`・`long`・`float`・`double`・`decimal` を分けて持つ。**`decimal` だけが特別**で、整数型からの暗黙の変換を持つ。

> The decimal type is appropriate when the required degree of precision is determined by the number of digits to the right of the decimal point... commonly used in financial applications.

`decimal` は 128 ビットの十進固定小数点で、`sbyte`・`byte`・`short`・`int`・`long` 等の整数型から**暗黙に**変換できる。
一方で `float`・`double` との間には暗黙の変換が無く、明示のキャストを要する——**整数 → decimal だけを安全な橋として空け、浮動小数点とは橋を架けない**。

これは Shidzuku の `十進数`・`実数`・`整数` にそのまま当てはまる構造である。

| C#                         | Shidzuku に当てはめると                                                 |
| -------------------------- | ----------------------------------------------------------------------- |
| `int` → `decimal`(暗黙)    | `整数` → `十進数`(暗黙にできる候補)                                     |
| `int` → `double`(暗黙)     | `整数` → `実数`(2^53 を超えると丸まる。暗黙にすると W0019-1 相当が必要) |
| `double` → `decimal`(明示) | `実数` → `十進数`(暗黙にしない)                                         |
| `decimal` → `double`(明示) | `十進数` → `実数`(暗黙にしない)                                         |

C# の実例は、思考実験 13 が推した「整数 → 十進数 だけ安全」という判断を裏付ける先行例である。ただし C# は `int` → `double` も暗黙にしており、**Shidzuku がそこまで踏み込むかどうかは別の判断**である(2^53 の桁溢れが static に見えない)。

## 5. 型を分け、変換も一切許さない立場 — Swift・Ada

### 5.1 Swift

Swift は整数だけで `Int8`〜`Int64`・`UInt8`〜`UInt64` の8種、浮動小数点で `Float`・`Double`・`Float80` を持つ。**型どうしの暗黙変換は一切無い。**

> Types that conform to Numeric are also ExpressibleByIntegerLiteral but not expressible by float literals. Integers can be converted to floats in a straightforward manner, but you need to consider rounding when going from float to integer.

`Int` から `Double` へも、`let x: Double = someInt` とは書けず、`Double(someInt)` という構築子を必ず呼ぶ。**Shidzuku の現行の E0019-3(3つの数値型は暗黙に混ざらない)は、Swift と同じ厳格さである。**

### 5.2 Ada

Ada は整数(範囲付き)・順序固定小数点・十進固定小数点・浮動小数点をそれぞれ独立した型として持ち、**型ごとに演算子が別**である。異なる型どうしの演算は書けず、明示の型変換関数を呼ぶ。
ADR 0010 が Ada を「ほぼ同型」として参照していたのは、この厳格さ込みでの類似である。

## 6. 金融機関の実態

### 6.1 COBOL の圧縮10進数(COMP-3)は、いまも現役である

COBOL の `PICTURE` 句と `COMP-3`(圧縮10進数、1バイトに2桁を詰める)は、銀行の基幹系で**いまも高頻度取引を処理し続けている**。10進の桁をそのまま持ち、2進化10進(BCD)の一種である点は ADR 0010 が検討して退けた形と同じだが、
「なぜ退けたか」(1桁4ビットで約17%が無駄、桁補正が要る)は表現効率の問題であり、**型を分ける・分けないの設計とは別の軸**である。

### 6.2 Java の BigDecimal — 丸めは常に明示

新しい金融システムの多くは Java の `BigDecimal` を使う。`BigDecimal` は任意精度の十進数で、加減乗算は厳密、除算だけ `MathContext`(精度と丸め方式)を要求する。

> Never use double for prices, taxes, or currency; always use BigDecimal with String constructors; prefer .compareTo() over == or .equals(); use rounding modes explicitly for division.

構造は ADR 0010 の `十進数` にきわめて近い——**除算だけ丸めを明示させ、他は厳密**という規則が一致する。相違点は、`BigDecimal` が**桁を型に持たない**(任意精度)事である。
ADR 0010 が桁を型に持たせた理由(値域と刻みが型を読めば分かる、記憶域が実行前に決まる)は、`BigDecimal` の設計では捨てられている。

### 6.3 C# の decimal — 言語組み込みで、範囲は有限

C# は `decimal` を言語の基本型として持ち、128 ビット固定・有効桁 28〜29 桁・範囲 ±7.9×10²⁸ という**固定の器**を用意する(BigDecimal のような任意精度ではない)。
実務上は「28桁もあれば十分」という判断であり、Shidzuku の `十進数(i.f)` のように**呼び出しごとに桁を書く**設計とは違う——**器を1つ決めて、そこに収まらない場合だけ別の対応をする**という設計である。

## 7. 科学技術計算の実態

### 7.1 Fortran の KIND — 「どの精度で計算するか」を型で選ぶ

Fortran は `REAL` に `KIND` パラメータを持たせ、`SELECTED_REAL_KIND(P, R)` で「少なくとも P 桁の精度、R の指数範囲」を要求すると、処理系がそれを満たす表現(単精度・倍精度・四倍精度)を選ぶ。

> To solve the portability crisis, Fortran 90 introduced the KIND parameter. Instead of requesting a specific number of bytes, the developer requests a specific "kind" of real number.

これは ADR 0010 の静的指数(桁の窓の位置を型に書く)と発想が近い——**「どれだけの精度が要るか」を型に書き、表現をそこから決める**。
ただし Fortran は基数を2に固定しており(binary32/64/128)、Shidzuku の `実数` と同じ立場である。`十進数` に相当する型は Fortran には無い。

### 7.2 単精度(float32)が主役の領域がある

機械学習・GPU計算・組込みの領域では、**64 ビットではなく 32 ビットの浮動小数点が主に使われる**。ADR 0017 が「主に使う型は binary64」としたのは、
業務システム・計測・分散制御を想定してのものであり、**この領域には binary64 の想定が当てはまらない**。ADR 0017 の「将来の変更想定」が binary32 の追加を検討事項として残しているのは、この余地を認めたものである。

### 7.3 区間演算(interval arithmetic)— Shidzuku に無い領域

数値解析の一部では、誤差の上下限を値そのものに持たせる**区間演算**(下限・上限の対を1つの数として扱う)が使われる。
Shidzuku の `実数`・`十進数` のどちらにも区間演算に相当する型は無い。往復不能な誤差を持つ計算(反復解法・条件数の悪い問題)の扱いは、ADR 0010・0017 双方が「将来の変更想定」に送ったまま解決していない。

## 8. 名前空間の研究との接点 — 単位付き数値

F# の Units of Measure は、ADR 0010 の量と単位の宣言と**ほぼ同じ設計**である。

> Units of measure are used for compile-time unit checking but are not persisted in the run-time environment, and therefore do not affect performance.

コンパイル時にのみ検査し、実行時の値には現れない——ADR 0010 の「単位は型情報のみであり、実行時コストはゼロ」と一致する。
量と単位の設計はここでは再検討の対象にしない(思考実験 13 でも単位の軸と数値型の軸は独立していると確認済み)。

## 9. 比較の総括

| 観点           | Shidzuku 現行(破棄対象) | 数値の塔(Scheme・Julia)      | 非対称の橋(C#)     | 完全分離(Swift・Ada・Haskell) |
| -------------- | ----------------------- | ---------------------------- | ------------------ | ----------------------------- |
| 型の数         | 3                       | 概念上1つ(実装は複数)        | 少数(用途別)       | 多数(精度・符号別)            |
| 変換の暗黙度   | 無し                    | 全方向(伝染規則あり)         | **安全な向きだけ** | 無し                          |
| 金融の実例     | (無し)                  | 無し                         | **言語の標準機能** | Swift は `Decimal` を別途持つ |
| 科学技術の実例 | (無し)                  | Julia は科学技術計算の主戦場 | 無し               | Fortran の KIND が近い        |
| 宣言の重さ     | 桁・丸めを毎回書く      | 書かない(塔が吸収する)       | 型を選ぶだけ       | 変換を毎回書く                |
| 静的検査       | 強い(型で保証)          | 弱い(動的型付けが主)         | 中間               | 強い                          |

**最も近い先行例は C# の `decimal` である。** 型を分け、変換を明示させるという Shidzuku の根本方針は Swift・Ada・Haskell と同じ立場であり、その方針自体を疑う根拠はここまでの調査からは出ていない。
一方で、**どこか1本だけ橋を架ける**(整数 → 十進数)という C# の判断は、Shidzuku がまだ採っていない選択肢であり、思考実験 13 の推奨と一致する。

## 10. 論点 — 次の ADR に渡す問い

1. **数値型は3つのままか。** 分離を維持するなら、C# の実例が「整数 → 十進数 の非対称な暗黙変換」を後押しする。塔にするなら Julia の `promote_type` 方式(型ごとに規則を1つ書く)が候補になる。
2. **整数 → 実数 の暗黙変換を認めるか。** C# は認めるが、2^53 の桁溢れが静的に見えない。Swift・Ada は認めない。
3. **丸めの宣言をどこまで型シグネチャに残すか。** `BigDecimal` は任意精度で桁を型から外している。ADR 0010 の「桁を読めば値域が分かる」という利点とは背反する。
4. **binary32(単精度)を追加するか。** 機械学習・GPU・組込みの領域を Shidzuku の対象に含めるかどうかに懸かる。
5. **区間演算・任意精度整数を持つか。** 現状は「将来の変更想定」に送られたままである。
6. **序数(U24)と数値型の関係。** `版`・`連番` に掛け算を許さない設計は、どの数値型アーキテクチャを選んでも別途決める必要がある。
7. **量と単位(ADR 0010 の該当部分)は維持してよいか。** F# の実例が設計を裏付けているため、本実験では維持を前提とした。

## 11. 次の行動

- 論点1〜7 について、ユーザーとの相談を経て方向を定める
- 方向が決まり次第、新しい ADR(数値型の体系、暫定 ADR 0021)を起案する。ADR 0010・0017 の本文は履歴として残す(ADR 0016 決定4 と同じ扱い)
- ADR 0019 決定2・決定7 は、新しい ADR が確定するまで凍結する

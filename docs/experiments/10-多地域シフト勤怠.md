# 思考実験 10: 多地域シフト勤怠(ADR 0019 の反証試験)

- 状態: Draft
- 日付: 2026-08-29
- 目的: ADR 0019(提案)が定めた基本型で、**時間の3つの層——時間軸(`時点`)・暦(`日付`・`時刻`)・時間帯——が全部出てくる系**を書き下ろし、書けない事を探す
- 進め方: 思考実験 07 と同じく**反証を探す**。ADR 0019 は棚卸し(思考実験 09)から導いた決定であり、系を書いた裏付けを持たない。書けない事が見つかったら、原理的な限界か設計で救えるかを分ける

## 1. 対象システム — なぜこの題材か

多地域でシフト勤務する従業員の、**シフト計画・打刻・給与締め**の系を選んだ。この題材は ADR 0019 の決定を全て通る。

| 出てくる値                 | ADR 0019 の型       | 試される決定                  |
| -------------------------- | ------------------- | ----------------------------- |
| 打刻                       | `時点`              | 決定4(壁時計・巻き戻り)       |
| 拠点の時計                 | `時間帯`            | 決定5(読み替え・夏時間)       |
| シフトの開始「毎日 09:00」 | `時刻`              | 決定5(日を持たない時計の読み) |
| 勤務日・締め日             | `日付 グレゴリオ暦` | 決定5(暦の欄)                 |
| 労働時間・所定時間         | `量 時間` の値      | 決定6(時間量を量へ寄せる)     |
| 時給・給与                 | `十進数(9.2) 円`    | ADR 0010(厳密さが要る値)      |
| 勤務回数・連番             | `整数 単位なし`     | 決定2(数えた値)               |
| 残業したか                 | 名前の付いた直和    | 決定3(論理は公開面に書けない) |

夏時間のある地域を含むため、**存在しない時刻・二度ある時刻・23時間の日・25時間の日**が実際に現れる。

コンポーネントは4つ。

| コンポーネント | 隠す知識                             | 公開面                   |
| -------------- | ------------------------------------ | ------------------------ |
| ClockGate      | 打刻端末のプロトコルと外部表現       | 打刻の受付               |
| ShiftPlan      | シフトの型と拠点の時計(暦の側の知識) | 予定の照会               |
| WorkLedger     | 実績の突合の規則(勤務日の決め方)     | 実績の受け口・実績の照会 |
| PayrollClose   | 締めの規則と給与の計算               | 締めの実行               |

## 2. Shidzuku による記述

構文は第1〜5章に従う。基本型は ADR 0019(提案)を先取りして使う。

### 2.1 system — Context 段

```plaintext
system シフト勤怠 {
  intent {
    why      "働いた事実(いつ働いたか)と、働く約束(いつ働く予定か)を一つの境界に収める。
              前者は時間軸の値、後者は暦の値であり、両者を突き合わせる規則がこの系の設計判断である"
    rejected option "拠点ごとに別の系を置き、各拠点の現地時刻だけで完結させる"
             reason "拠点をまたぐ応援勤務と、全社の締めが書けなくなる。現地時刻は表示の都合であり、事実は時間軸の上にある"
    rejected option "打刻を現地の日時(年月日時分)として受ける"
             reason "夏時間の日に、存在しない打刻と二度ある打刻が生まれる。受けた時点で曖昧さが確定できない"
    change   "拠点の追加と就業規則の改定を想定。打刻の受付と実績の照会は変えない"
  }
  constraint {
    actor    従業員 "出退勤を打刻する"
    actor    労務担当 "シフトを組み、締めを実行し、乖離を見る"
    external 人事マスタ "社内の別系。従業員と拠点(拠点の時計を含む)を流してくる"
    external 給与支払 "外部事業者。確定した支給額を受け取る"
    depends  給与支払
    expose   打刻(従業員ID, 時点) -> 受理(打刻番号) | 受理不可(理由)   by ClockGate
    expose   実績照会(従業員ID, 締め期間) -> 実績                      by WorkLedger
    expose   締め実行(締め期間) -> 確定(支給の列) | 締め不可(理由)     by PayrollClose
    contains ClockGate, ShiftPlan, WorkLedger, PayrollClose
  }
}
```

### 2.2 data 宣言 — 型が3つの層に分かれる

```plaintext
data 従業員ID (id)
data 拠点ID   (id)
data 打刻番号 (id)

# --- 時間軸の側 ---
data 打刻 {
  従業員: 従業員ID,
  起きた: 時点,                       # いつ押されたか。時間帯に依らない
  端末地: 時間帯,                     # どこの時計の前で押されたか
  向き:   出勤 | 退勤
}

# --- 暦の側 ---
data シフト {
  拠点:   拠点ID,
  勤務日: 日付 グレゴリオ暦,          # 暦の欄は省略できない
  開始:   時刻,                       # 09:00。日も暦も時間帯も持たない
  長さ:   整数 分                      # 480 分。量 時間 の値
}

data 締め期間 { 始まり: 日付 グレゴリオ暦, 終わり: 日付 グレゴリオ暦 }

# --- 突き合わせた結果 ---
data 実績 {
  従業員:   従業員ID,
  勤務日:   日付 グレゴリオ暦,        # 業務規則で決めた日(下記 論点4)
  実働:     整数 分,
  超過:     所定内 | 残業(整数 分)    # 論理を使わない(決定3)
}

data 支給 { 従業員: 従業員ID, 基本: 十進数(9.2) 円, 割増: 十進数(9.2) 円 }
```

### 2.3 ClockGate — 打刻の受付

```plaintext
component ClockGate {
  intent {
    why      "打刻端末のプロトコルと外部表現をこのコンポーネントに閉じ込める。
              内側へ渡すのは時間軸の一点(時点)と、押された場所の時計(時間帯)だけにする"
    rejected option "端末が送ってきた現地日時の文字列をそのまま内側へ渡す"
             reason "夏時間の日に曖昧さが残る。境界で時点に確定させれば、内側は暦を知らずに済む"
    change   "端末の種類の追加を想定。内側への公開面(時点と時間帯)は変えない"
  }
  constraint {
    depends    WorkLedger
    expose     打刻(従業員ID, 時点) -> 受理(打刻番号) | 受理不可(理由)
    expose     打刻記録(打刻) flow out
    idempotent none
    state      none
    collator   none
    layers {
      受信 { io   boundary }   # 端末とのバイト列の授受
      復号 { pure parse    }   # バイト列 -> 時点・時間帯・向き
      受付 { io   domain   }   # 打刻番号の採番と送出
    }
  }
  body { ... }
}
```

### 2.4 ShiftPlan — 暦の側の知識

```plaintext
component ShiftPlan {
  intent {
    why      "シフトが暦の値である事(その拠点の時計で 09:00 から 8 時間)と、
              それを時間軸へ移す時に現れる夏時間の曖昧さの扱いを、このコンポーネントに閉じ込める"
    rejected option "シフトを時点の対(開始時点・終了時点)で持つ"
             reason "「毎日 09:00 開始」が書けなくなる。夏時間の日に開始時刻が動いてしまい、就業規則と食い違う"
    change   "変形労働時間制の導入を想定。予定の照会(時点の区間を返す)は変えない"
  }
  constraint {
    depends    none
    expose     予定(従業員ID, 日付 グレゴリオ暦) -> 予定区間 | 予定なし | 時刻が無い日
    state      シフト表 recoverable(人事マスタ)
    collator   none
    layers {
      保持 { io   domain }   # シフト表の保持と復元
      展開 { pure domain }   # 暦の値 -> 時間軸の区間(拠点の時間帯を注入して計算)
    }
  }
  body { ... }
}
```

### 2.5 WorkLedger — 実績の突合

```plaintext
component WorkLedger {
  intent {
    why      "打刻の対から実働を作る規則——どの打刻とどの打刻を組にするか、
              日を跨ぐ夜勤をどの勤務日に付けるか——をこのコンポーネントに閉じ込める"
    rejected option "打刻の時点をその拠点の暦で読み、その日付を勤務日とする"
             reason "夜勤が日付をまたぎ、1回の勤務が2日に割れる。勤務日はシフトの開始日とするのが就業規則である"
    change   "労働時間の丸め単位(15 分)の変更を想定。実績の形は変えない"
  }
  constraint {
    depends    ShiftPlan
    expose     打刻記録(打刻) flow in
    expose     実績照会(従業員ID, 締め期間) -> 実績の列
    idempotent 打刻記録
    state      実績台帳 recoverable(打刻記録)
    collator   none
    layers {
      受領 { io   domain }   # 打刻の受け取りと台帳の保持
      突合 { pure domain }   # 打刻の対 -> 実働。勤務日の決定
    }
  }
  body { ... }
}
```

### 2.6 PayrollClose — 締めと給与

```plaintext
component PayrollClose {
  intent {
    why      "締めの規則(どの勤務日までを一回の締めに入れるか)と、
              時間から金額を作る計算をこのコンポーネントに閉じ込める"
    rejected option "実働の分を実数で受け、時給を掛けて丸める"
             reason "金額は帳簿に載り、外部の支払と突き合わせる。刻みは人が十進で決めた値である(ADR 0017 の指針)"
    change   "割増率の改定を想定。締め実行の公開面は変えない"
  }
  constraint {
    depends    WorkLedger, 給与支払
    expose     締め実行(締め期間) -> 確定(支給の列) | 締め不可(理由)
    idempotent 締め実行
    state      締め記録 durable
    collator   none
    layers {
      集計 { pure domain }   # 実績の列 -> 実働の合計
      算定 { pure domain }   # 実働 -> 金額(十進数・丸めの宣言つき)
      送出 { io   boundary } # 給与支払への授受
    }
  }
  body { ... }
}
```

### 2.7 接続

```plaintext
flow 勤怠 {
  intent {
    why      "打刻は失ってはならない事実であるため durable。締めは応答を待つため ask とする"
    rejected option "打刻も ask にする"
             reason "端末が待たされると打刻が押せなくなる。事実の記録は非同期で受け、受理だけを即答する"
    change   "打刻の再送(端末の再接続)を想定。受け口の冪等は変えない"
  }
  ClockGate    -> WorkLedger   : flow 打刻 pressure block(deadline 1 秒) durable
  WorkLedger   -> ShiftPlan    : ask 予定(従業員ID, 日付 グレゴリオ暦) deadline 200 ミリ秒 -> 予定区間 | 予定なし | 時刻が無い日
  PayrollClose -> WorkLedger   : ask 実績照会(従業員ID, 締め期間) deadline 5 秒 -> 実績の列
  on failure ClockGate    : 受理不可を返す。端末は再送する
  on failure ShiftPlan    : 予定なしとして扱い、実働をそのまま記録して乖離に上げる
  on failure WorkLedger   : 締めを中止し、締め不可(理由)を返す
  on failure PayrollClose : 締め記録を巻き戻し、労務担当へ通知する
}
```

## 3. 検証結果

### 3.1 書けた事 — ADR 0019 の決定が効いた所

- **打刻を `時点` で受ける形が、境界の設計をそのまま決めた。** 端末が送ってくる現地日時の文字列は境界の層で `時点` に確定し、
  内側は暦も時間帯も知らない。「夏時間の日に打刻が曖昧になる」問題が、**内側へ入る前に消える**。
- **「毎日 09:00 開始」が `時刻` で書けた。** 日も暦も時間帯も持たない値として書けるため、シフト表が拠点の日ごとに膨らまない。
- **夏時間の曖昧さが公開面に出た。** `予定(…) -> 予定区間 | 予定なし | 時刻が無い日` の3番目は、
  `時点にする` が返す `存在しない` をそのまま公開面へ持ち上げたものである。**呼び手が必ず扱う。**
- **`論理` を使わずに書けた。** 「残業したか」は `所定内 | 残業(整数 分)` になり、超過分が同じ区分に入った。真偽なら別の欄が要る。
- **金額と時間で数値型が分かれた。** 実働は `整数 分`、金額は `十進数(9.2) 円`。混ぜるとコンパイル時に落ちる(E0019-3)。
- **暦の欄が公開面の語彙になった。** `予定(従業員ID, 日付 グレゴリオ暦)` は、どの暦で日を渡すかが呼び手に見える。

### 3.2 書けなかった事 — 仕様に戻す論点

#### 論点1: `時刻` に長さを足せないため、シフトの終了時刻が書けない

シフトは「09:00 から 480 分」である。就業規則は「17:00 まで」と書かれ、勤怠表にもそう出る。
しかし ADR 0019 決定5 は `時刻` の演算を**比較と等価だけ**と定めており、`09:00 + 480 分` が書けない。

`時刻` を2つ(開始・終了)持たせる案は、**時計の読みの差が実労働時間ではない**という問題を生む。
夏時間の日には `09:00` から `17:00` までが 7 時間または 9 時間になる。差を取れる型にすると、その 8 時間が正しいと読めてしまう。

- 原理的な限界ではない。**時計の文字盤の上の加算**は曖昧さを持たない演算であり、日が繰り上がるかどうかも計算できる。
- 危ないのは、その結果を**時間軸の加算だと読む**事である。
- → **繰り上がりを返す加算**を置けば両立する。`時計を進める(23:00, 3 時) -> (02:00, 1 日)`。
  ADR 0010 が桁溢れを直和で受けさせた形と同じで、**黙って巻き戻らない**。

#### 論点2: 曜日が無い

締め日は「月末」または「毎週日曜」であり、休日判定にも曜日が要る。ADR 0019 の `日付` の演算は
`日を足す`・比較・`日数`・`換算` の4つで、**曜日が取れない**。

- 曜日は**暦に依らない**。日番号を 7 で割った余りで決まり、グレゴリオ暦の改暦(1582-10-04 の翌日が 1582-10-15)でも曜日の並びは途切れていない。
- したがって `曜日(日付) -> 月 | 火 | 水 | 木 | 金 | 土 | 日` は、暦の欄と無関係に置ける。
- 月末は `日を足す` では書けない(月の長さが暦に依る)。ADR 0019 が「月の加算を持たない」と決めた事の裏返しであり、
  **締め日の指定は日付そのもの(`締め期間`)を渡す形にすれば回避できた**。本実験ではそう書いた。

#### 論点3: `整数` の単位換算の規則が無い

`隔たり(出勤, 退勤)` は `整数 ナノ秒` を返し、給与計算は分単位で丸める(15 分単位の切り捨て)。
つまり `整数 ナノ秒 -> 整数 分` の換算が要る。

ADR 0010 の換算規則は `十進数` の桁を前提に書かれており、**`整数` の換算は誰も定めていない**。

| 換算の向き            | 起きる事                                  | 要る宣言                   |
| --------------------- | ----------------------------------------- | -------------------------- |
| 細かい単位 → 粗い単位 | 情報が落ちる(ナノ秒 → 分)                 | 丸めの宣言                 |
| 粗い単位 → 細かい単位 | 値が大きくなる(分 → ナノ秒)。範囲を出得る | 直和で受ける(桁溢れと同じ) |

- → `換算(値, <単位>, 丸め <方式>)` と `換算(値, <単位>)`(粗→細。結果は `整数 <単位> | 桁溢れ`)を定める。
- 比が 10 のべきかどうかは関係ない。**整数の刻みは常に 1 であり、1 より粗い単位へ移せば必ず丸めが起きる**。
  `十進数` の「10 のべきの換算は無損失」という規則は、小数部の桁があるから成り立っていた。整数には無い。

#### 論点4: 「勤務日」は変換の結果ではなく、業務規則が決めた値である

夜勤は日を跨ぐ。打刻の `時点` を拠点の暦で読むと、出勤は 2026-08-29、退勤は 2026-08-30 になる。
しかし就業規則は「勤務日はシフトの開始日とする」と定めており、**勤務日は打刻から機械的には決まらない**。

ADR 0019 の W0019-3 は「時間帯を用いて得た暦の読みを `state`・`data` に持つと警告」である。
`実績 { 勤務日: 日付 グレゴリオ暦, … }` はこれに当たるように見えるが、**性質が違う**。

| 種類                       | 例                           | tzdata の版が変わると |
| -------------------------- | ---------------------------- | --------------------- |
| 時間帯で変換しただけの読み | 「打刻を東京の暦で読んだ日」 | 変わり得る            |
| 業務規則が決めた暦の値     | 「就業規則が定める勤務日」   | 変わらない            |

後者は**業務上の事実であり、決まった時点で確定する**。締め日・営業日・売上計上日も同じである。
→ W0019-3 の対象を「変換の結果をそのまま持つ場合」に限り、業務規則が決めた暦の値は対象外と書き分ける必要がある。

#### 論点5: `時刻` だけでは、どこの 09:00 か分からない

`シフト { 拠点, 勤務日, 開始: 時刻, 長さ }` の `09:00` は、拠点の時計での 09:00 である。
しかし `時刻` は時間帯を持たないため、**その事は型に現れない**。同じ行の `拠点` が持っている知識である。

- これは ADR 0010 の `単位なし` と同じ形である。単位を持たない数値も正規の値であり、意味は文脈が持つ。
- 型に時間帯を載せる案(`時刻 <時間帯>`)は、ADR 0019 が退けた「時間帯を欄にする案」と同じ問題(行ごとに違う)に当たる。
- → **指針で扱う**。時計の読みを持つ `data` は、同じ直積の中にその時計の持ち主(拠点・時間帯)を持つ。

#### 論点6: `隔たり` の結果の単位が固定されている

`隔たり(始め, 終わり)` は `整数 ナノ秒 | 逆行` を返す。勤怠が欲しいのは分であり、必ず論点3 の換算を経る。
ナノ秒で受ける事に害は無いが、**19 桁に近い値が中間に現れる**(1 年 ≒ 3.15×10^16 ナノ秒 = 17 桁)。
100 年を超える隔たりは `整数` の範囲(19 桁)を出る。`時点` の範囲が ±292 年であるため、**最大の隔たりは 584 年 ≒ 1.84×10^19 ナノ秒で桁溢れする**。

- → `隔たり` の失敗に「範囲外」を加えるか、結果の単位を選ばせる(`隔たり(始め, 終わり, <単位>, 丸め <方式>)`)。
  後者の方が ADR 0010 の形(結果の桁と丸めを宣言する)に揃う。

#### 論点7: 拠点の時間帯が解決できなくなる事の扱い

拠点の時計は人事マスタから `Asia/Kolkata` のような地帯名で来る。ADR 0019 は地帯名の廃止・改名を欠点に挙げているが、
**解決できない地帯名を受け取った時にどうなるか**を定めていない。

- `時間帯` の値を作る操作は失敗し得る。→ 外部から値を作る所は直和で受ける(U12)。
- `state シフト表 recoverable(人事マスタ)` は地帯名を保持するため、**復元時に解決できない事がある**。
  これは ADR 0013 が照合キーで見つけた問題と同じ形(版に依存する知識の永続化)である。

#### 論点8: 夏時間の「二度ある時刻」が公開面に出ていない

`予定(…) -> 予定区間 | 予定なし | 時刻が無い日` は `存在しない` だけを扱っている。
`二度ある(時点, 時点)` の方は、シフト計画では「先の方を採る」と決めれば公開面に出さずに済んだ。

- **これは ADR 0019 の穴ではなく、直和が働いた証拠である。** 書き手はどちらを採るか決めさせられ、その判断が body の中に残る。
- ただし決め方は業務判断であり、**intent に書く場所が無い**(body の中の分岐に意図が宿るが、intent は公開面の設計判断を書く場所である)。
  → ADR 0003 の intent テンプレートが body 内の判断をどこまで拾うかは、U14・粒度(ADR 0006)の話題に近い。本実験では ShiftPlan の change 欄に書いた。

#### 論点9: `state 締め記録 durable` — 締めの冪等と暦

`締め実行(締め期間)` は `idempotent` である。同じ締め期間で二度実行しても支給は二重にならない。
これは締め期間が**暦の値(日付の対)**であり、tzdata にも時間帯にも依らないためである。

- もし締め期間を `時点` の対で持つと、拠点ごとに境界がずれ、同じ「8 月分」が拠点によって違う区間になる。
- **暦の値を鍵にした事で冪等が成り立った。** これは ADR 0019 が暦と時間軸を分けた事の、予期していなかった利点である。

## 4. 未解決課題への入力

- **U22(基本型の体系)**: 論点1(`時計を進める`)・論点2(`曜日`)・論点3(整数の換算)・論点6(`隔たり` の単位)は ADR 0019 の改訂で埋まる。
  論点4 は W0019-3 の書き分け、論点5 は指針として本文に加える。
- **U13(失敗の体系)**: 論点6 の隔たりの桁溢れ、論点7 の地帯名の解決失敗を失敗の語彙に含める。
- **U12(外部世界との境界)**: 論点7。外部から `時間帯` の値を作る所は直和で受ける。tzdata の版と `state` の復元の関係も同じ節で扱う。
- **U3・U1(intent の範囲)**: 論点8。body 内の業務判断(二度ある時刻でどちらを採るか)を intent のどこに書くか。
- **U16(版の移行)**: 論点7 の地帯名の改名は、永続化済みデータの移行の一例である。

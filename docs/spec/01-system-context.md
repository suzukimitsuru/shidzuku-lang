# Shidzuku 言語仕様書 — 第1章 システムコンテキスト

- 状態: Draft
- 日付: 2026-08-26(改訂 2026-08-29: ADR 0014 の採用に伴い語彙を ASCII に揃え、ADR 0018(提案)のシステムの入れ子を先行反映した)
- 依拠: 第0章 0.3〜0.5、第5章、ADR 0003・0008・0014・0015・0016(いずれも採用)、ADR 0012・0018(提案)。未採用 ADR の採否により本章も改訂される

## 1.1 システムとは

システム(system)は Shidzuku の最も外側の段であり、C4 モデルの System Context に対応する(第0章 0.3、ADR 0015)。
システムが記述するのは**境界**である——何を内側に入れ、何を外に置き、誰が使うのか。

- 内側にあるのはコンポーネント(第2章)と、**別のシステム**である(1.5)。システム自身は実装を持たない。
- 外側にあるのは**人**(actor)と**外部システム**(external)である。
- システムは入れ子にできる。最も外側の1つを**ルート**と呼び、プログラムの外周を表す(1.5、ADR 0018)。

コンポーネントの境界の決定を intent が記録するのと同じく、システムの境界の決定も検証不能な判断であり、記録を強制する。
「在庫台帳を内側に持たない」「決済は外に置く」は、後から見て理由の分からなくなる典型的な判断である。

## 1.2 システムの宣言

システムは**二層**で記述する(第0章 0.5)。body は無い。システムの実装は、その内側のコンポーネントそのものである。

``` plaintext
system <システム名> {
  intent     { ... }   # 第一層: 意図(1.3)
  constraint { ... }   # 第二層: 制約(1.4)
}
```

- 二層はいずれも省略できない。欠落はコンパイル時エラーとする(E0015-1)。
- システム名はプログラム内で一意とする。名前空間を system 単位に狭めるかは U14 で決める(第5章 5.5)。
- プログラム内の全てのコンポーネントとシステムは、**ルートを除き**、ちょうど1つの `contains` に属する(E0015-2)。
- ルートも普通のシステムであり、二層で書き、五つの制約を全て書く。特別扱いの構文は無い。

## 1.3 第一層: 意図(intent)

形式はコンポーネントと同じ(ADR 0003、第2章 2.2)。書く対象がコンポーネントの境界ではなく**システムの境界**である点だけが違う。

``` plaintext
intent {
  why      "<なぜこの範囲で系を切るか。このシステムは何を引き受け、何を引き受けないか>"
  rejected option "<検討して捨てた選択肢。内側に入れる事を検討して外に置いた物>"
           reason "<なぜ捨てたか>"
  change   "<将来どんな変化を想定するか。境界はそれをどう吸収するか>"
  refs     "<システム横断の決定を記録した ADR 等>"     # 任意
}
```

- why・rejected・change は必須、refs は任意。検証(E0003-1・E0003-2・W0003-1・W0003-2)はコンポーネントの intent と同じに適用する。
- `rejected` に書くのは**境界の判断**である。「外部システムを内側に取り込む案」「一つの系を二つに割る案」など。
- システム横断の決定(プロトコル選定・トランスパイル先など)は `docs/decisions/` の ADR に置き、`refs` で指す(ADR 0007)。

## 1.4 第二層: 制約(constraint)

``` plaintext
constraint {
  actor    <人・役割> "<何をする人か>" ...        # 必須(無ければ none)
  external <外部システム名> "<何であるか>" ...    # 必須(無ければ none)
  depends  <呼ぶ相手の列挙 | none>                # 外部システムと兄弟システム。必須
  expose   <公開面の宣言> by <担い手の名前>       # 必須(無ければ none)
  contains <コンポーネント名・システム名の列挙>   # 必須
}
```

| 語彙     | 意味                                                                   | 検証時期                   |
| -------- | ---------------------------------------------------------------------- | -------------------------- |
| actor    | このシステムを使う人・役割の列挙。必須(無ければ `none`)                | 検証しない(図と意図のため) |
| external | 外部システムの列挙とその説明。必須(無ければ `none`)                    | コンパイル時(名前の解決)   |
| depends  | このシステムが呼ぶ相手(external と兄弟システム)。必須(無ければ `none`) | コンパイル時               |
| expose   | システムが外へ見せる面と、それを担うコンポーネント・システム。必須     | コンパイル時               |
| contains | 内側のコンポーネントとシステムの列挙。必須                             | コンパイル時               |

**省略の禁止**(第0章 0.5、ADR 0008)は段を跨いで適用する。外部が無い事も `external none` と明示する(E0008-1)。

### depends と expose — 段を跨いで同じ語

`depends` と `expose` はコンポーネントの constraint(第3章 3.2)と同じ語である。
段が変われば指す先が変わるが、「依存の向き」と「公開面」という意味は同じである。
C4 のズームレベルと同じく、同じ物が違う倍率で現れる。

- `external` は**存在**の宣言、`depends` は**呼ぶ**という宣言である。両者は一致しない。
  センサー機器のように「送ってくるだけで、こちらからは呼ばない」相手は external に載り depends には載らない。
- `depends` に書けるのは次の二つだけであり、どちらでもない名前は E0018-3 とする。

| 相手                 | 意味                                                 | 通信の記述            |
| -------------------- | ---------------------------------------------------- | --------------------- |
| `external` の名前    | 記述の外にある系。自分の `external` に宣言済みである | 方式は未定(U12)       |
| 同じ親を持つシステム | 記述の中にある系。相手の `expose` を通る             | フロー(第4章)に書ける |

### expose — 担い手

システムの公開面は、必ずどれか1つの**コンポーネントまたは内側のシステム**が担う。

``` plaintext
expose 受注(注文) -> 受注番号 | 受注不可      by OrderIntake     # 担い手はコンポーネント
expose 計測値の受け入れ(計測値) flow in       by SensorIntake    # 同上
expose 注文受付(注文) -> 受注番号 | 受注不可  by 注文管理        # 担い手はシステム
```

- 公開面の形は第3章 3.2(ask の受け口 / flow の出口 / flow の受け口)と同じである。
- `by` に書いた担い手が、自分の expose に同じ受け口を持たない場合はコンパイル時エラー(E0015-3)。
  **システムの境界は、必ず担い手の公開面として実在する**。図の上の箱だけの境界は作れない。
- 突き合わせは**1段ずつ**行う。担い手がシステムなら、その expose はさらにその担い手の expose と突き合わせる。
  C4 のズームと同じく、一度に見るのは1段である。

### 外部システムと「外部の技術」の区別

外にある物が全て `external` になる訳ではない。判定は二段構えである(ADR 0018)。

1. **その系を Shidzuku で記述しているか**。しているなら external ではなく、内側のシステムとして `contains` に書く(1.5)。
   この問いは記述から決まるため、機械検証できる。
2. していないなら、**その相手が独立に設計され、独立に壊れるか**で判定する。

| 例                              | 扱い              | 理由                                                               |
| ------------------------------- | ----------------- | ------------------------------------------------------------------ |
| 注文を保存する RDB              | external ではない | 永続化方式の選択であり、それを隠す事がコンポーネントの仕事         |
| 社内の別系(Shidzuku で書く)     | external ではない | 内側のシステムとして `contains` に書く(判定 1)                     |
| 社内の別系(Shidzuku で書かない) | external          | 別の系として設計され、別に壊れ、こちらの都合で変えられない(判定 2) |
| 通知基盤(外部の事業者)          | external          | 同上                                                               |
| 集約値を書く時系列 DB           | external ではない | 同じく永続化方式の選択                                             |

- external でない外部の技術は、それを隠すコンポーネントの intent の `why`(何の知識を隠すか)に現れる。
- **判定は機械検証しない**。担保はレビューと思考実験に置く(粒度の指針と同じ扱い。第2章 2.5)。
- **2 の判定基準は未完成である**。「独立に設計され」と「独立に壊れる」の二つが連言なのか選言なのかが決まっていない。
  自社で運用する全文検索基盤は「独立に壊れる」が「独立に設計されない」ため、答えが割れる(思考実験 08 論点5)。
  U12 で機械検証可能な形に落とせるかと併せて決める。
  ただし 1 が先に立つため、**その系を Shidzuku で書いているなら割れは起きない**。割れが効く範囲は狭くなった。

### 「外部」という語の範囲

第2章 2.4 の層の役割「境界」も外部との授受を担うが、そこでの「外部」は本節の `external` より広い。
external ではない外部の技術(RDB・索引の保存先)や、人への窓口(HTTP)も境界の層が受け持つ。
**同じ語が二つの段で別の物を指している**。突き合わせは U20 で行う(思考実験 08 論点1)。

## 1.5 システムの入れ子 — System Landscape

システムは `contains` に**別のシステム**を書ける(ADR 0018)。C4 の System Landscape に当たる形である。

``` plaintext
system 通販 {                                    # ルート
  intent     { ... }
  constraint {
    actor    買い物客 "商品を探し、注文する"
    external 決済代行 "外部の事業者。注文管理が呼ぶ"
    depends  none
    expose   注文受付(注文) -> 受注番号 | 受注不可    by 注文管理
    expose   商品検索(検索語) -> 商品の列 | 該当なし  by 商品カタログ検索
    contains 注文管理, 商品カタログ検索
  }
}

system 注文管理 {                                # 通販の内側にある
  intent     { ... }
  constraint {
    ...
    contains OrderIntake, Inventory, OrderStore
  }
}
```

### 段は増えない

入れ子は**新しい段ではない**。Context 段を一段引いて見た図であり、第0章 0.3 の四段は変わらない。
図(Phase 3)は、ルートから `contains` を1段掘るごとに Context 図を1枚出す。最上段の1枚が Landscape 図に当たる。
**図の枚数が段の数ではない。**

### 規則

- **ルートはちょうど1つ**。`contains` のどこにも現れないシステムをルートと呼ぶ。0個または2個以上は E0018-2 とする。
  プログラムの外周が一意に決まらないと、`contains` の網羅性も名前の一意性も図の起点も定義できない。
  「どこまでが自分たちの範囲か」も境界の判断であり、ルートの intent がそれを記録する。
- **深さに上限は無い**。深すぎる木は粒度の問題であり(第2章 2.5)、レビューが受け持つ。
- **循環は禁じる**。システムが直接・間接に自分自身を含む記述は E0018-1 とする。
- 一つの `contains` にコンポーネントとシステムが混在してよい。
- 内側のシステムも**二層**である。body は無い(1.2)。

### 段を飛ばせない

`depends` と `expose ... by` が指せるのは、**自分の `contains` に直接ある**相手だけである。
内側のシステムの中のコンポーネントを外から直接指す記述は E0018-4 とする。

情報隠蔽はコンポーネントだけの性質ではない。システムも内側を隠して境界で繋がる物であり、
段を飛ばせるなら、システムの境界は図の上の線でしかなくなる。
その代わり、深い木では同じ公開面が段ごとに転記される。これは情報隠蔽の代価である。

### 外部は段を上がっても外部である

内側のシステムが `external` を宣言したら、その名前は**親の `external` にも現れなければならない**(E0018-5)。

``` plaintext
system 通販 {
  constraint {
    external 翻訳サービス "外部の機械翻訳。商品カタログ検索が呼ぶ"   # 繰り上がる
    ...
  }
}

system 商品カタログ検索 {
  constraint {
    external 翻訳サービス "外部の機械翻訳。TranslationStore が呼ぶ"
    depends  翻訳サービス
    ...
  }
}
```

- 現れなければ、上段の図だけを見た読者は「この範囲は外に何も頼っていない」と読む。
- `external` を親から継承させる形は採らない。各段の記述はそれ自体で読めなければならない(第0章 0.5)。
  重複はその代価である。
- **actor は繰り上げを要求しない**。内側の `actor none` は「このシステムを直接使う人は居ない」の意味であり、
  親の actor が内側の公開面に届く事と矛盾しない。actor は検証しない宣言である(1.4)。

### コンポーネントから兄弟システムを呼ぶ

コンポーネントの `depends`(第3章 3.2)にも、**親の兄弟システム**を書ける。

- コンポーネント `c` が兄弟システム `B` を呼ぶとき、`c` の `depends` に `B` を書く。
- `c` の親システム `A` の `depends` にも `B` を書く。書かれていなければ E0018-3 とする。
- `A` の `depends` に宣言した相手を `contains` の誰も呼んでいなければ W0018-1(警告)とする。

これは「外部を呼ぶのはコンポーネントなのに、コンポーネントの `depends` に書けない」という穴(思考実験 08 論点3)の
**半分**を塞ぐ。相手が記述の中にあるときだけ塞がり、真に外にある `external` は U12 のままである(1.8)。

## 1.6 動作環境(Container)は言語の記述対象外

C4 の Container 段に当たるのは Shidzuku の**動作環境**である(第0章 0.3、ADR 0015)。
この段には言語の宣言が無い。

- 動作環境はノードに常駐し、期限を測り、durable な流れを届け切り、コンポーネントを監督する実行系である(ADR 0012)。
- どのノードの動作環境に、どのコンポーネントを、いくつ載せるかは**配置の設定**であり、言語ではなく実行系が受け取る。
  設計を変えていないのに配置が変わるたびにコードが変わる事を避けるためである(ADR 0015)。
- コンポーネントと動作環境の境目は、ADR 0012 の接合面 H1〜H8 である。
- 配置の設定の形式、複製数、監督の範囲は Phase 2 で定める。Container 図はその設定から抽出する。

四位一体(第0章 0.4)は動作環境によって動かない。**配置単位はコンポーネントのままである**。
1つの動作環境に複数のコンポーネントが載るのは配置の事実であって、設計・処理・障害の単位を割る事ではない。

## 1.7 記述例

思考実験 02(センサー収集パイプライン)にシステム層を被せた形。

``` plaintext
system センサー収集 {
  intent {
    why      "機器から届く計測値を、正規化・集約して保存し、閾値超過を知らせるところまでを一つの境界に収める。
              機器そのものと通知の手段は外に置き、この系は「計測値の一生」だけを知る"
    rejected option "通知手段(メール・チャット)を内側に持つ"
             reason "通知手段は運用の都合で入れ替わる。内側に入れると、その入れ替えが系の設計変更になる"
    change   "機種の追加を想定。Normalizer の内側で吸収し、システムの境界は変えない"
  }
  constraint {
    actor    運用者 "閾値超過の通知を受け取る"
    external センサー機器群 "多数の機器。計測値を送ってくる"
    external 通知基盤 "外部の通知手段。Alerter が使う"
    depends  通知基盤
    expose   計測値の受け入れ(計測値) flow in   by SensorIntake
    contains SensorIntake, Normalizer, Aggregator, MetricStore, Alerter
  }
}
```

- センサー機器群は `external` に載るが `depends` には載らない(送ってくるだけで、こちらからは呼ばない)。
- 時系列 DB は MetricStore が隠す永続化方式であり、`external` ではない(1.4 の判定)。

## 1.8 未定事項(Phase 1 以降で決める)

- **外部との通信そのものの記述**(U12)。外部システムとどの方式で繋がるか、その障害時に何をするか、
  省略の禁止をどこまで適用するか。本章は「誰が外にいるか」「境界のどこを通るか」までを引き受ける。
- **どのコンポーネントが外部を呼ぶか**(U12)。`expose` は `by <担い手の名前>` を持ち E0015-3 で検証されるが、
  `depends` には `by` に当たる欄が無い。外部を呼ぶのは実際にはコンポーネントであり、それを書ける場所が
  `external` の説明文という検証されない散文しかない。コンポーネントの `depends` に書けるのは
  兄弟コンポーネントと兄弟システムまでであり(第3章 3.2)、真に外にある `external` は書けないため、
  外部を呼ぶコンポーネントが `depends none` と宣言する事になる。
  **省略の禁止の網に穴が開いている**(思考実験 08 論点3)。ADR 0018 は、この穴のうち
  「相手が記述の中にあるとき」だけを塞いだ。
- **外部システムの判定基準**(U12)。1.4 の通り、連言か選言かが未定(思考実験 08 論点5)。
- **フローの端点に外部システムを書けるか**(U12)。外部から流れてくる durable な受け口があっても、
  送り手が `contains` の外にあるためフローに書けず、`on failure` の対象にもならない(思考実験 08 論点7)。
- **名前空間**(U14)。システムの入れ子は入ったが(1.5)、名前は依然としてプログラム内で一意である(1.2)。
  修飾名の構文・名前の解決規則・E0014-3(混同可能な識別子)の範囲を、まとめて U14 で決める。
  system 単位が第一候補である(ADR 0018 決定9)。
- **W0018-1 の扱い**(U12・U14)。「宣言したが誰も呼ばない `depends`」は現在は警告である。
  同じ問いがコンポーネントの `depends` にも立つのに、そちらに検査が無いため、両方まとめて扱いを決める。
- **actor の使い道**。現在は検証されず、図(Phase 3)と意図のためだけに存在する。
  権限・入口の区別に使うかは U12 と併せて決める。

## 3.1 制約とは

制約(constraint)は**検証可能な意図**である。コンパイラ・実行系が違反を拒否する(Eiffel Design by Contract の系譜)。
検証できない理由は意図層(intent)に、検証できる約束は制約層に書く。この区別が三層記述の背骨である。

制約は段を跨いで現れる。システムの制約(第1章 1.4)はシステム境界を、コンポーネントの制約(本章)は
コンポーネント境界を検証する。本章が扱うのはコンポーネントの制約であり、システムの語彙は第1章に置く。

## 3.2 制約の語彙

| 制約       | 意味                                                                | 検証時期            |
| ---------- | ------------------------------------------------------------------- | ------------------- |
| depends    | 通信してよい相手の列挙。必須(無ければ `none`)                       | コンパイル時        |
| expose     | 公開面の宣言。必須(無ければ `none`)。宣言外の受け口・出口は無い     | コンパイル時        |
| idempotent | 同一要求の再実行が二重の効果を持たない(約束。該当時のみ)            | コンパイル時+実行時 |
| state      | 状態の再起動時の扱い(volatile / recoverable)。必須(無ければ `none`) | コンパイル時(整合)  |
| collator   | テキストの比較・整列・検索に使う照合器の宣言。必須(無ければ `none`) | コンパイル時        |
| layers     | 内部階層の名前・制約強度・役割の宣言。必須(第2章 2.4)               | コンパイル時        |

**省略の禁止**(第0章 0.5、ADR 0008): 選択のある宣言に省略時の既定は無く、該当が無い事も `none` と明示する(E0008-1)。
なお障害の非伝播は宣言ではなく全コンポーネントの不変条件である(第0章 0.4)。実行系が保証し、埋め合わせの記述はフローの `on failure`(第4章)が担う。

### depends — 通信してよい相手

コンポーネントの `depends` に書けるのは次の二つである。どちらでもない名前は E0018-3 とする。

| 相手               | 意味                                              |
| ------------------ | ------------------------------------------------- |
| 兄弟コンポーネント | 同じシステムの `contains` にあるコンポーネント    |
| 親の兄弟システム   | 親システムの `depends` にも書かれている必要がある |

- 相手がシステムのとき、届く先はそのシステムの `expose` である。内側のコンポーネントは指せない(第1章 1.5、E0018-4)。
- 記述の外にある `external` は、コンポーネントの `depends` には書けない。書ける場所は U12 で決める(第1章 1.8)。

### expose — 公開面の形式

公開面は3種の形で宣言する(通信方式は第4章)。

``` plaintext
expose <名前>(<引数>) -> <応答> | <失敗>   # ask の受け口
expose <名前>(<内容>) flow out             # flow の出口
expose <名前>(<内容>) flow in              # flow の受け口
```

思考実験 01〜03 では flow の受け口の宣言を省略していたが、「宣言外の受け口は存在しない」という公開面の完全性を保つため、受け口も expose に含める。
この形は思考実験 04 で検証する。

システムの公開面(第1章 1.4)も同じ3種の形を使い、`by <担い手の名前>` を伴う。
担い手(コンポーネントまたは内側のシステム)の expose に同じ受け口が無ければ E0015-3 とする。

### idempotent — 冪等性

- durable な flow 接続の受け口には idempotent の宣言を必須とする(ADR 0004。欠落はコンパイル時エラー)。
- 性質そのものの完全な機械検証は不能である。実行系は同一要求 ID の重複検出(効果が一度である事の監視)を行い、逸脱を障害イベントとして報告する。
  それ以上の担保は意図層とレビューに委ねる。

### state — 状態の再起動時の扱い

コンポーネントが持つ状態は、再起動時の扱いを2種から宣言する。

``` plaintext
state <状態名> volatile                  # 再起動で失われてよい
state <状態名> recoverable(<復元元>)     # 再起動で消えるが、復元元から再構成できる
state none                               # 再起動を跨ぐ状態を持たない(明示。省略の禁止)
```

- **volatile**: 失われてよい状態(集約途中のウィンドウ等)。失ってよい事自体が設計判断であり、宣言によって明示する。
- **recoverable**: メモリ上の写しは消えてよいが、論理的には失われない状態(KV 表等)。復元元(durable な入力の再生、永続ストアの照会)を指定する。
  復元元が durable でない場合はコンパイル時エラー(E0000-4)。「失ってよい」と「消えるが復元できる」の区別は思考実験 04 で必要になった。
- 障害時の記述(第4章 `on failure`)が「失ってはならない」とする状態を volatile と宣言する事はできない(E0000-4)。
- 復元によらず再起動を跨いで守る手段(複製・合意)の語彙は未定であり、U6(Raft の適用範囲)として Phase 2 で定める。

### collator — テキストの比較の宣言

テキストは素の等値比較とハッシュを持たない(ADR 0013)。順序づけ・曖昧一致が要る場合は、照合器(collator)を宣言して使う。

``` plaintext
collator 名前順(locale ja-JP, strength secondary)   # 使う場合
collator none                                       # 使わない場合(明示。省略の禁止)
```

- 宣言は必須である(E0008-1)。使わないコンポーネントは `collator none` と書く。
- collator は boundary を除く全ての役割(parse・domain・format)で使える。名前での整列・絞り込みは業務ロジックそのものであり、
  domain から追い出せないためである(ADR 0013 決定8)。boundary で使えないのは、その層にまだテキストが存在しないためである。
- **照合の結果は保存できない**。照合キーの永続化・受け渡し・ハッシュは E0013-3 とする。
  照合キーは locale・strength に加えて Unicode の版に依存し、版が変われば一致しなくなる。
  collator の結果は「その場限りの判定」であり、保存できる同一性ではない(ADR 0013 決定9)。
- 同一性が要る所には識別子型を使う。テキストはそこへ立ち入らない。
- `strength` の語彙(`primary`・`secondary`・`tertiary`…)は ICU に倣うが、語の選定は Phase 1 で定める。
- **表記**: 照合器と役割の語彙は ADR 0014 の採用により英字へ揃えた(`collator`・`locale`・`strength`、`boundary`・`parse`・`domain`・`format`)。
  語彙は ASCII、書き手の名前(`名前順` など)は UTF-8 という線引きは第5章に置く。ADR 0013 決定8 が保留していた論点である。

## 3.3 検証の一覧 — エラーと警告の2段階

深刻度は ADR 0003 の原則に従い2段階とする。エラーは深刻な違反でコンパイル不能、警告は誤検出があり得る検出でコンパイルは通る。

### 番号の読み方

識別子は `E<出自>-<連番>`(警告は `W<出自>-<連番>`)である(ADR 0016)。

- **出自**は、その検査を定めた ADR の番号(4桁)である。`E0013-3` なら ADR 0013 を読めばよい。
- **連番**はその出自の中での出現順であり、1 から始まる。エラーと警告で別に数える。
- 出自 `0000` は、ADR を持たず**仕様書が直接定めた検査**を表す。
- **番号は順序を表さない**。識別のためだけにあり、一度与えた番号は変えない。廃止した検査は欠番とする。

出自ごとに採番するため、ADR どうしで番号が衝突する事はない。表は出自の順に並べてある。

### 実行時に戻る失敗(数値。ADR 0021)

数値の失敗は、コンパイル時に拒否できない7つに限る。いずれも例外ではなく**失敗として戻る値**であり、受け取りを書かなければ
コンパイルが通らない(第6章 6.3、U13)。

| 失敗                                         | 起きる所                         |
| -------------------------------------------- | -------------------------------- |
| 加減乗の結果が幅を出る                       | 演算ごと(`int`・`uint`)          |
| 位取りを揃える所で幅を出る                   | 加減算・`丸める`・`換算`         |
| `変換` の結果が幅を出る                      | 幅・符号を跨ぐ変換               |
| `分ける(a, 0)`・`割る(a, 0, …)`(0 除算)      | 除算                             |
| `float` が特殊値を生む(0 除算・負数の平方根) | 名前を得る所での例外フラグの検査 |
| `復号` のバイト列の長さが幅と合わない        | `境界` の役割での詰め替え        |
| `dec` が名前を得る所で宣言した桁を超える     | `dec` の受け渡しと `収める`      |

量の種別(ADR 0022)は失敗を増やさない。位置 ± 差 が幅を出る事(空の列の末尾を求める等)は、1行目の「加減乗の結果が幅を出る」に含む。

2026-08-28 以前は通し番号(E1・E2 …)で採番していた。ADR と思考実験は書かれた時点の番号のまま残すため(ADR 0016 決定4)、

ADR の本文が使っている番号も、その ADR の中での連番として読み替える——

## 3.4 検証時期の原則

- **コンパイル時**: 宣言の構造と整合(3.3 のエラー全件)。記述から静的に決まるものはすべてここで拒否する。
- **実行時**: 振る舞いの保証と監視。障害の非伝播(全コンポーネントの不変条件)、冪等性の重複検出、バックプレッシャ・配達保証(第4章)。
  逸脱は障害イベントとしてログ規約(U4、Phase 2)に従い報告する。
- **検証不能**: 内容の意味的な正しさ・誠実さ。意図層の管轄であり、レビューと可視化(U8)に委ねる。
  何を `external` に書くか(第1章 1.4)と粒度の指針(第2章 2.5)もここに入る。前者は指針すら持たない。

## 3.5 未定事項(Phase 1 以降で決める)

- 依存の循環の扱い。ask の循環はデッドロックの温床だが、flow の循環(フィードバック)には用途があり得る。Phase 1 の検証器設計で決める。
- W0003-2(陳腐化)の判定基準。何をもって「公開面・制約の変更」とみなすか(ADR 0003 の将来想定)。
- pure の検証範囲。**純粋性の検査は Shidzuku 側で完結させ、トランスパイル先の言語には要求しない**(ADR 0012 決定8)。
  検査をトランスパイル先の型システムに預けると、動的型の言語を足せなくなるためである。役割の一方向性(E0013-4)も同じく Shidzuku 側で検査する。
  残るのは、何を副作用とみなすかの具体であり、Phase 1 の検証器で決める。
- 外部システムとの通信の検証(U12)。第1章の `external` / `depends` を実際の接続に結び付ける検査。
- **E0014-3 の「同一の名前空間」の範囲**(U14)。現在は1プログラム内である(第5章 5.5)。
  システムの入れ子(第1章 1.5)が入ったため、system 単位に狭める案が第一候補になった。
- **W0018-1 をエラーへ上げるか**(U12・U14)。同じ問い(宣言したが誰も呼ばない `depends`)が
  コンポーネントの `depends` にも立つのに、そちらに検査が無い。片方だけをエラーにはできない。
- **E0013-4 の適用範囲**(U20)。役割の向きがコンポーネント間の通信にも及ぶのか、外の世界との授受に限るのか(思考実験 08 論点2)。
- **E0013-3 と全文検索の索引の衝突**(U21)。照合の結果を保存した索引は照合キーの永続化に当たり、文字どおり適用すると
  全文検索が書けない。索引を派生状態として例外にするか、Unicode の版を宣言させるかを決める(思考実験 08 論点4)。
- 型そのものの未定事項は第6章 6.6 に置く(名前空間・失敗の体系・外部世界との境界・書けない暦・月の加算・対応表・中間結果の幅)。
- 出自 `0000` の4件(E0000-1〜E0000-4)に決定の記録が無い事(ADR 0016 の将来想定)。ADR を起こすかを決める。

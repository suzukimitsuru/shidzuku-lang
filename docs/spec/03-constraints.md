## 3.1 制約とは

制約(constraint)は**検証可能な意図**である。コンパイラ・実行系が違反を拒否する(Eiffel Design by Contract の系譜)。
検証できない理由は意図層(intent)に、検証できる約束は制約層に書く。この区別が三層記述の背骨である。

制約は段を跨いで現れる。システムの制約(第1章 1.4)はシステム境界を、コンポーネントの制約(本章)は
コンポーネント境界を検証する。本章が扱うのはコンポーネントの制約であり、システムの語彙は第1章に置く。

## 3.2 制約の語彙

| 制約       | 意味                                                                | 検証時期            |
| ---------- | ------------------------------------------------------------------- | ------------------- |
| depends    | 通信してよいコンポーネントの列挙。必須(無ければ `なし`)             | コンパイル時        |
| expose     | 公開面の宣言。必須(無ければ `なし`)。宣言外の受け口・出口は無い     | コンパイル時        |
| idempotent | 同一要求の再実行が二重の効果を持たない(約束。該当時のみ)            | コンパイル時+実行時 |
| state      | 状態の再起動時の扱い(volatile / recoverable)。必須(無ければ `なし`) | コンパイル時(整合)  |
| layers     | 内部階層と制約強度(pure / io)の宣言。必須(第2章 2.4)                | コンパイル時        |

**省略の禁止**(第0章 0.5、ADR 0008): 選択のある宣言に省略時の既定は無く、該当が無い事も `なし` と明示する(E9)。
なお障害の非伝播は宣言ではなく全コンポーネントの不変条件である(第0章 0.4)。実行系が保証し、埋め合わせの記述はフローの `on failure`(第4章)が担う。

### expose — 公開面の形式

公開面は3種の形で宣言する(通信方式は第4章)。

``` plaintext
expose <名前>(<引数>) -> <応答> | <失敗>   # ask の受け口
expose <名前>(<内容>) の流れ               # flow の出口
expose <名前>(<内容>) の受け口             # flow の受け口
```

思考実験 01〜03 では flow の受け口の宣言を省略していたが、「宣言外の受け口は存在しない」という公開面の完全性を保つため、受け口も expose に含める。
この形は思考実験 04 で検証する。

システムの公開面(第1章 1.4)も同じ3種の形を使い、`担当 <コンポーネント名>` を伴う。
担当コンポーネントの expose に同じ受け口が無ければ E13 とする。

### idempotent — 冪等性

- durable な flow 接続の受け口には idempotent の宣言を必須とする(ADR 0004。欠落はコンパイル時エラー)。
- 性質そのものの完全な機械検証は不能である。実行系は同一要求 ID の重複検出(効果が一度である事の監視)を行い、逸脱を障害イベントとして報告する。
  それ以上の担保は意図層とレビューに委ねる。

### state — 状態の再起動時の扱い

コンポーネントが持つ状態は、再起動時の扱いを2種から宣言する。

``` plaintext
state <状態名> volatile                  # 再起動で失われてよい
state <状態名> recoverable(<復元元>)     # 再起動で消えるが、復元元から再構成できる
state なし                               # 再起動を跨ぐ状態を持たない(明示。省略の禁止)
```

- **volatile**: 失われてよい状態(集約途中のウィンドウ等)。失ってよい事自体が設計判断であり、宣言によって明示する。
- **recoverable**: メモリ上の写しは消えてよいが、論理的には失われない状態(KV 表等)。復元元(durable な入力の再生、永続ストアの照会)を指定する。
  復元元が durable でない場合はコンパイル時エラー(E8)。「失ってよい」と「消えるが復元できる」の区別は思考実験 04 で必要になった。
- 障害時の記述(第4章 `on failure`)が「失ってはならない」とする状態を volatile と宣言する事はできない(E8)。
- 復元によらず再起動を跨いで守る手段(複製・合意)の語彙は未定であり、U6(Raft の適用範囲)として Phase 2 で定める。

## 3.3 検証の一覧 — エラーと警告の2段階

深刻度は ADR 0003 の原則に従い2段階とする。エラーは深刻な違反でコンパイル不能、警告は誤検出があり得る検出でコンパイルは通る。

**エラー(コンパイル不能)**:

| #   | 検査                                                                                                            | 段        | 由来      |
| --- | --------------------------------------------------------------------------------------------------------------- | --------- | --------- |
| E1  | intent 必須項目の欠落・空欄                                                                                     | 両段      | ADR 0003  |
| E2  | rejected の構造違反((選択肢, 理由)の組が0件)                                                                    | 両段      | ADR 0003  |
| E3  | 三層記述の欠落                                                                                                  | Component | 第0章 0.5 |
| E4  | depends 宣言外のコンポーネントへの通信                                                                          | Component | 本章      |
| E5  | expose 宣言外の受け口・出口の使用                                                                               | Component | 本章      |
| E6  | pure 層での IO・pure 層から io 層への依存                                                                       | Code      | ADR 0005  |
| E7  | durable 接続の受け口に idempotent 宣言がない                                                                    | Component | ADR 0004  |
| E8  | 状態の宣言と障害時の記述の矛盾(「失ってはならない」状態の volatile 宣言、recoverable の復元元が durable でない) | Component | 本章      |
| E9  | 必須宣言の欠落(depends・expose・state・layers、接続の pressure・配達保証・期限、on failure、システムの5宣言)    | 両段      | ADR 0008  |
| E10 | state 宣言に無い状態の保持(`state なし` のコンポーネントが再起動を跨ぐ状態を持つ場合を含む)                     | Component | ADR 0008  |
| E11 | system 宣言の欠落、または intent / constraint の欠落                                                            | Context   | ADR 0015  |
| E12 | contains の網羅性違反(どのシステムにも属さないコンポーネント、二つ以上のシステムへの所属)                       | Context   | ADR 0015  |
| E13 | システムの expose と、担当コンポーネントの expose の不一致                                                      | Context   | ADR 0015  |

**警告(コンパイルは通る)**:

| #   | 検査                                                       | 由来     |
| --- | ---------------------------------------------------------- | -------- |
| W1  | 他のコンポーネント・フローと intent 本文が完全一致(コピペ) | ADR 0003 |
| W2  | 公開面・制約の変更に intent が未追従(陳腐化)               | ADR 0003 |

「両段」はシステムとコンポーネントの双方に適用する検査である。W1・W2 もシステムの intent に同じく適用する。

## 3.4 検証時期の原則

- **コンパイル時**: 宣言の構造と整合(E1〜E13)。記述から静的に決まるものはすべてここで拒否する。
- **実行時**: 振る舞いの保証と監視。障害の非伝播(全コンポーネントの不変条件)、冪等性の重複検出、バックプレッシャ・配達保証(第4章)。
  逸脱は障害イベントとしてログ規約(U4、Phase 2)に従い報告する。
- **検証不能**: 内容の意味的な正しさ・誠実さ。意図層の管轄であり、レビューと可視化(U8)に委ねる。
  外部システムの判定(第1章 1.4)と粒度の指針(第2章 2.5)もここに入る。

## 3.5 未定事項(Phase 1 以降で決める)

- 依存の循環の扱い。ask の循環はデッドロックの温床だが、flow の循環(フィードバック)には用途があり得る。Phase 1 の検証器設計で決める。
- W2(陳腐化)の判定基準。何をもって「公開面・制約の変更」とみなすか(ADR 0003 の将来想定)。
- pure の検証範囲。トランスパイル先言語(U5)でどこまで純粋性を機械検証できるか。
- 外部システムとの通信の検証(U12)。第1章の `external` / `depends` を実際の接続に結び付ける検査。

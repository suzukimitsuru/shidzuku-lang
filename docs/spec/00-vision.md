# Shizuku 言語仕様書 — 第0章 ビジョン

- 状態: Draft
- 日付: 2026-08-18

## 0.1 理念

**綺麗なコード、静かなシステム。**

設計意図から制約、構造、実装までを一本の記述で貫く。図面は別に描くものではなく、コードからの投影として常に実装と一致する。実行時の静けさ——障害が伝播しない、ログが騒がしくない、運用で驚きがない——は偶然ではなく、構造から生まれる。

## 0.2 解決したい問題

1. **設計と実装の乖離** — 設計文書・図面は実装の変更に追従できず、嘘になる。
2. **設計意図の喪失** — 「なぜこの分割にしたか」「何を捨てたか」が残らず、将来の変更が設計を壊す。
3. **実行時の騒がしさ** — 障害の伝播経路が設計時に見えず、運用が驚きの連続になる。

## 0.3 基本単位

Shizuku の基本単位は、次の四つが**同一のもの**である。

| 観点 | 単位の意味                                         |
| ---- | -------------------------------------------------- |
| 設計 | モジュール(狭い公開面+豊かな実装 = 深いモジュール) |
| 処理 | フローの節(データを受け、変換し、流す)             |
| 障害 | 障害境界(この内側で壊れてよい)                     |
| 配置 | 配置単位(どのプロセス・ノードで動くか)             |

設計単位・実行単位・運用単位が一致するため、図の一つの節が、そのまま検証・配置・障害対応の単位になる。(Erlang/OTP の「プロセス=障害境界=分散単位」の系譜)

## 0.4 単位の三層記述

各単位は三層で記述され、いずれも省略できない。

1. **意図(Intent)** — 検証不能な理由の記録。「なぜこの分割か」「何を捨てたか」「将来どう変わると想定するか」。機械は検証できないが、言語が**記述を強制**する。
2. **制約(Constraint)** — 検証可能な意図。依存の方向、公開面の狭さ、冪等性、障害の非伝播など。コンパイラ・実行系が**違反を拒否**する。(Eiffel Design by Contract の系譜)
3. **実装(Body)** — 単位の内側は原則自由(ミュータブル・例外可)。外側との通信のみが言語の管轄。ただし内部に階層(例: アプリケーション層/ドライバ層)を設け、階層ごとに制約強度を宣言できる。

## 0.5 静かさの構造化

- **障害境界=基本単位**であるため、障害の伝播経路はフロー図の上に現れる。どこで壊れてよいかは設計時に決まる。
- 分散合意には Raft を用い、障害の解消を実行系が担う。
- ログは規約から**自動生成**する。単位の入出力・状態遷移・障害イベントが規約に従って出力され、手書きのログ散布を不要にする。

## 0.6 可視化

構造図・データフロー図・障害境界図は、すべてコードからの**抽出**である。描いた図が古びるのではなく、コードが変われば図が変わる。可視化は言語の基礎が固まった後に実装する。

## 0.7 実現戦略

完全な言語を目指すが、段階を踏む。

1. 第一段階は既存言語への**トランスパイル**(TypeScript が型の層を既存エコシステムに被せて成功した前例に倣う)。
2. 着手は「言語仕様の記述+最小の言語実装+最小の分散動作環境」の三点セット。

## 0.8 参照する系譜

- John Ousterhout, *A Philosophy of Software Design* — 深いモジュール
- D. L. Parnas (1972), *On the Criteria to be Used in Decomposing Systems into Modules* — 情報隠蔽
- Eiffel — Design by Contract(検証可能な意図)
- Erlang/OTP — プロセス=障害境界=分散単位、Let it crash
- TypeScript — 既存エコシステムへの漸進的導入
- Raft — 分散合意

## 0.9 名前について

**雫(Shizuku)** — 流れの最小単位。雫が集まって川になるように、単位が繋がってシステムになる。そして、静かである。

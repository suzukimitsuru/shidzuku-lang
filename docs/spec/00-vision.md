# Shidzuku 言語仕様書 — 第0章 ビジョン

- 状態: Draft
- 日付: 2026-08-18(改訂 2026-08-26: C4 の命名を取り込み、四つの段を 0.3 に置いた。ADR 0015 提案)

## 0.1 理念

**綺麗なコード、静かなシステム。**

設計意図から制約、構造、実装までを一本の記述で貫く。図面は別に描くものではなく、コードからの投影として常に実装と一致する。実行時の静けさ——障害が伝播しない、ログが騒がしくない、運用で驚きがない——は偶然ではなく、構造から生まれる。

## 0.2 解決したい問題

1. **設計と実装の乖離** — 設計文書・図面は実装の変更に追従できず、嘘になる。
2. **設計意図の喪失** — 「なぜこの分割にしたか」「何を捨てたか」が残らず、将来の変更が設計を壊す。
3. **実行時の騒がしさ** — 障害の伝播経路が設計時に見えず、運用が驚きの連続になる。

## 0.3 四つの段

Shidzuku の記述は、C4 モデル(Simon Brown)の四つのズームレベルと同じ名前・同じ順序を持つ(ADR 0007・0015)。
読者によって必要な高度が違う——利用者・運用者・設計者・実装者——という C4 の知見をそのまま使う。

| 段        | Shidzuku での名前       | 記述する物                               | 仕様書での位置            |
| --------- | ----------------------- | ---------------------------------------- | ------------------------- |
| Context   | システム                | システム境界・外部の人と外部システム     | 第1章                     |
| Container | 動作環境                | コンポーネントを載せ、監督する実行系     | 言語の記述対象外(Phase 2) |
| Component | コンポーネント          | 情報隠蔽・フローの節・障害境界・配置単位 | 第2章・第3章              |
| Code      | コード(body と内部階層) | 名前付きの層(pure / io)と、その中の実装  | 第2章 2.4                 |

**動作環境(Container)だけは書き手が書かない**。コンポーネントを載せて監督する器であり、Shidzuku が実行系として提供する(ADR 0012)。
1つの動作環境に複数のコンポーネントが載るが、これは配置の事実であって、設計・処理・障害の単位を動かさない。

## 0.4 コンポーネント — 四位一体

Shidzuku のコンポーネント(component)は、次の四つが**同一のもの**である。

| 観点 | コンポーネントの意味                               |
| ---- | -------------------------------------------------- |
| 設計 | モジュール(狭い公開面+豊かな実装 = 深いモジュール) |
| 処理 | フローの節(データを受け、変換し、流す)             |
| 障害 | 障害境界(この内側で壊れてよい)                     |
| 配置 | 配置単位(どの動作環境・どのノードで動くか)         |

設計単位・実行単位・運用単位が一致するため、図の一つの節が、そのまま検証・配置・障害対応の単位になる。(Erlang/OTP の「プロセス=障害境界=分散単位」の系譜)

## 0.5 三層記述

各コンポーネントは三層で記述され、いずれも省略できない。

1. **意図(Intent)** — 検証不能な理由の記録。「なぜこの分割か」「何を捨てたか」「将来どう変わると想定するか」。機械は検証できないが、言語が**記述を強制**する。
2. **制約(Constraint)** — 検証可能な意図。依存の方向、公開面の狭さ、冪等性、障害の非伝播など。コンパイラ・実行系が**違反を拒否**する。(Eiffel Design by Contract の系譜)
3. **実装(Body)** — コンポーネントの内側は原則自由(ミュータブル・例外可)。外側との通信のみが言語の管轄。ただし実装の全ては名前付きの内部階層(例: アプリケーション層/ドライバ層)に属し、階層ごとに制約強度(純粋/IO 可)を**必ず宣言する**。宣言のない実装は存在しない。

システム(第1章)は意図と制約の**二層**で記述する。システムの実装は、その内側のコンポーネントそのものだからである。

三層に限らず、Shidzuku の記述に**省略時の既定は存在しない**。選択のある宣言——依存・公開面・状態・内部階層、接続の方式・流量制御・配達保証・期限・障害時の埋め合わせ——は必ず明示し、該当が無い事も「なし」と書く。書かれなかった事を既定の表で補う事はなく、システム・コンポーネント・フローは、言語の既定規則という外部知識なしに、それ自体で読める。

## 0.6 静かさの構造化

- **障害境界=コンポーネント**であるため、障害の伝播経路はフロー図の上に現れる。どこで壊れてよいかは設計時に決まる。
- 分散合意には Raft を用い、障害の解消を実行系が担う。
- ログは規約から**自動生成**する。コンポーネントの入出力・状態遷移・障害イベントが規約に従って出力され、手書きのログ散布を不要にする。

## 0.7 可視化

構造図・データフロー図・障害境界図は、すべてコードからの**抽出**である。描いた図が古びるのではなく、コードが変われば図が変わる。
四つの段(0.3)がそのまま図の段になる。可視化は言語の基礎が固まった後に実装する。

## 0.8 実現戦略

完全な言語を目指すが、段階を踏む。

1. 第一段階は既存言語への**トランスパイル**(TypeScript が型の層を既存エコシステムに被せて成功した前例に倣う)。
2. 着手は「言語仕様の記述+最小の言語実装+最小の分散動作環境」の三点セット。

## 0.9 参照する系譜

- John Ousterhout, *A Philosophy of Software Design* — 深いモジュール
- D. L. Parnas (1972), *On the Criteria to be Used in Decomposing Systems into Modules* — 情報隠蔽
- Eiffel — Design by Contract(検証可能な意図)
- Erlang/OTP — プロセス=障害境界=分散単位、Let it crash
- TypeScript — 既存エコシステムへの漸進的導入
- Raft — 分散合意
- Zenoh — エッジからクラウドまでを一つで覆う分散データ通信(ADR 0001 で採用)
- ADR(Michael Nygard) — Architecture Decision Record / アーキテクチャ決定記録。決定を背景・捨てた選択肢・理由とともに1決定=1文書で記録し、上書きせず「破棄」として履歴を残す様式。意図層と開発プロセスの範(ADR 0007)
- C4 モデル(Simon Brown)/ Structurizr — Context / Container / Component / Code の4段のズームレベルと「1つのモデルから図を投影する」原則。原則を ADR 0007 で、段の命名を ADR 0015 で取り込んだ(0.3)
- Reactive Streams — バックプレッシャ(需要に応じた流量制御)
- Saga — 障害時の補償による整合性の回復

## 0.10 名前について

**雫(Shidzuku)** — 流れの最小単位。雫が集まって川になるように、コンポーネントが繋がってシステムになる。そして、静かである。

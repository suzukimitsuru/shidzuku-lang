# Shidzuku 言語仕様書 — 第3章 通信モデル

- 状態: Draft
- 日付: 2026-08-19
- 依拠: 第0章 0.3・0.5、ADR 0004(提案)。ADR の採否により本章も改訂される

## 3.1 二つの通信方式

単位間の通信は ask と flow の2方式のみである(ADR 0004)。

| 方式 | 意味                 | 応答                                         | 用途の例                   |
| ---- | -------------------- | -------------------------------------------- | -------------------------- |
| ask  | 要求-応答            | 必ず返る(成功応答、または失敗・タイムアウト) | 引当の可否、受付 ID の発行 |
| flow | 非同期の一方向の流れ | なし                                         | 計測値ストリーム、イベント |

- ask は構文上は要求-応答だが、実行系では非同期メッセージ+応答として実装する。単位を跨ぐ直接呼び出し・共有メモリは存在しない。
- ask の応答は必ず返る。相手の障害・期限超過時は失敗応答が返り、呼び出し側が待ち続ける事はない。

## 3.2 フローの宣言

フロー(flow 宣言)は単位間の接続と障害時の振る舞いを記述する。フローも意図を持つ(必須)。

```plaintext
flow <フロー名> {
  intent { ... }                                  # 単位と同じテンプレート(ADR 0003)。必須
  <送り手> -> <受け手> : ask <公開面>(<引数>) -> <応答>
  <送り手> -> <受け手> : flow <内容> [pressure <ポリシー>] [transient | durable]
  on failure <単位> : <補償・代替応答・再起動の記述>
}
```

- 接続の両端は、受け手・送り手の constraint(depends / expose)と整合しなければならない(E4・E5)。
- 処理の順序、ポリシーの選択、補償の設計といった判断は接続に宿るため、フローの intent は必須である。
  検証(E1・E2・W1・W2)も単位の intent と同じに適用する。

## 3.3 バックプレッシャ — 接続の属性

flow の接続ごとに pressure を宣言する。

| ポリシー | 意味                                     | 既定 |
| -------- | ---------------------------------------- | ---- |
| block    | 下流が詰まったら上流を待たせる(欠損なし) | ✓    |
| latest   | 最新値のみ保持し、途中の値を捨てる       |      |
| drop     | あふれた分を捨てる                       |      |

- 既定は block。黙ってデータが消えるのは「運用の驚き」であり、捨てる事は明示の宣言によってのみ起きる。
- block は期限を任意で宣言できる(`pressure block(期限 1s)` 等)。期限内に受け付けられない投入は失敗として上流に返る。
  応答期限を持つ ask の世界と flow の境目で必要になる(思考実験 03)。
- ファンアウト(1出力を複数の受け手へ)の各接続は互いに独立である。片方の詰まりは他方に波及しない。
- latest / drop で捨てた事実、block の期限超過は、ログ規約(U4、Phase 2)の対象イベントとする。

## 3.4 配達保証 — 接続の属性

| 保証      | 意味                                                                                         | 既定 |
| --------- | -------------------------------------------------------------------------------------------- | ---- |
| transient | 平常時は届くが、単位の障害・再起動を跨ぐと失われ得る                                         | ✓    |
| durable   | 単位の障害・再起動を跨いで失われない。実行系が永続化・再送し、受け口に idempotent を要求する |      |

- 既定は transient。durable は失えない接続(受付 ID を返した後のジョブ等)だけが明示的に負う。
- durable 接続の受け口には idempotent 宣言が必須(E7)。
- transient の消失は黙った消失にならない。何が失われ得るかは `on failure` と状態の宣言(第2章 state)に現れる。
- durable の実現手段(永続化・再送・Raft の適用)は U6 として Phase 2 で定める。

## 3.5 障害時の記述

フローは `on failure <単位>` で、障害を伝播させない事に加えて**何で埋め合わせるか**を記す。

- 埋め合わせの種類: 補償(引当の解放等)、代替応答(受付不可を返す等)、再起動(Let it crash)。
- 再起動で失われる状態は、当該単位の state 宣言(第2章: volatile / recoverable)と整合しなければならない(E8)。
- 「伝播させない」だけの宣言は不完全である(思考実験 01・02)。埋め合わせの記述を伴って初めて障害境界の記述になる。

## 3.6 未定事項(Phase 1 以降で決める)

- ask の期限の既定値と再試行の規定(U4 のログ規約と合わせて)。
- pressure の語彙の拡張(バッファ上限付き block 等)。実装で必要が確認されてから。
- ADR 0001(Zenoh)へのマッピング(flow=Pub/Sub、ask=Query)。Phase 2 で検証。

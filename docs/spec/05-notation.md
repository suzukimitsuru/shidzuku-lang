# Shidzuku 言語仕様書 — 第5章 記述の表記

- 状態: Draft
- 日付: 2026-08-29(ADR 0014 の採用に伴い新設。同日 ADR 0009・0010・0017・0019・0020 の採用で型の語彙を 5.3 に加えた)
- 依拠: 第0章 0.5、第6章、ADR 0008・0009・0010・0014・0015・0016・0017・0019・0020(いずれも採用)、ADR 0012(提案)。未採用 ADR の採否により本章も改訂される

## 5.1 二つの語 — 言語が定める語と、書き手が定める名前

Shidzuku の記述に現れる語は二種類しかない(ADR 0014)。

| 出自               | 誰が決めるか       | 文字集合 | 例                                    |
| ------------------ | ------------------ | -------- | ------------------------------------- |
| 言語が定める語彙   | 言語(変更できない) | ASCII    | `component` `depends` `pure` `none`   |
| 書き手が定める名前 | 書き手             | UTF-8    | `受注受付` `受注番号` `名前順` `索引` |

この線引きが本章の全てである。「日本語か英語か」ではなく、**どちらの語かで文字集合が決まる**。

- 言語の語彙を特定の自然言語に寄せない理由は、ADR 0003(拒否語リストの棄却)・ADR 0006(指針の機械検証の棄却)と同じ
  「言語仕様が特定の自然言語を仮定しない」である。語彙は言語の実装・トランスパイル先(ADR 0012)・
  動作環境のキー空間と共有される最小の集合であり、ここが母語に依存すると外部との接合が全て翻訳を伴う。
- 名前に母語を許す理由は、名前がドメインの語彙そのものだからである。`受注番号` と `受付ID` の区別は業務の区別であり、
  綴り直せば設計意図から実装までを一本の記述で貫く(第0章 0.1)道筋に翻訳が1段入る。

本章は段に属さない。ソースの符号化も識別子の規則も、Context から Code まで同じに掛かる(第0章 0.3)。

## 5.2 ソースファイル

- 符号化は **UTF-8** に固定する。他の符号化は受け付けない。
- BOM は付けない。あれば読み飛ばすが、書き出しでは付けない。
- 改行は **LF** とする。行末の CR は E0014-1 とする。
- 符号化の宣言(`# -*- coding: -*-` の類)は持たない。**選べない事は宣言する事が無い事**であり、
  省略の禁止(第0章 0.5、ADR 0008)は選択のある宣言に掛かる規則である。

## 5.3 言語が定める語彙 — ASCII

キーワード・基本型の名前・属性の値・演算子・区切り・組み込みの操作名は、US-ASCII の図形文字(U+0020〜U+007E)だけで綴る。
別名は与えない。`depends` を別の綴りで書く事はできず、`none` を `なし` と書く事もできない。

現在の語彙は次の通りである(型の語彙は第6章が定める)。

| 区分                 | 語                                                                                                                     | 定める所             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------- |
| 段の宣言             | `system` `component` `flow`                                                                                            | 第1・2・4章          |
| 三層                 | `intent` `constraint` `body`                                                                                           | 第1章 1.2・第2章 2.1 |
| 意図                 | `why` `rejected` `option` `reason` `change` `refs`                                                                     | 第2章 2.2            |
| システムの制約       | `actor` `external` `depends` `expose` `contains` `by`                                                                  | 第1章 1.4            |
| コンポーネントの制約 | `depends` `expose` `idempotent` `state` `collator` `layers`                                                            | 第3章 3.2            |
| 公開面の形           | `->` `\|` `flow out` `flow in`                                                                                         | 第3章 3.2            |
| 状態                 | `volatile` `recoverable`                                                                                               | 第3章 3.2            |
| 層の制約強度         | `pure` `io`                                                                                                            | 第2章 2.4            |

| データの宣言         | `data` `id` `list`                                                                                                     | 第6章 6.1            |
| 基本型               | `bool` `int` `real` `decimal` `text` `bytes` `instant` `date` `clock` `zone`                                           | 第6章 6.2            |
| 論理                 | `true` `false` `and` `or` `not`                                                                                        | 第6章 6.2            |
| 数値の量と単位       | `quantity` `unit` `unitless` `base` `exp` `convert`                                                                    | 第6章 6.3            |

| 暦                   | `calendar` `gregorian` `julian` `eras` `era` `from` `outside_eras`                                                     | 第6章 6.4            |
| 共通                 | `none`                                                                                                                 | 全章                 |

- `none` は「該当なし」を表す唯一の語である。`depends none`・`state none`・`external none`・`collator none`・
  `deadline none` はいずれも同じ語であり、省略の禁止(第0章 0.5)が要求する明示の形はこの一語に揃う。
- `flow` は二つの位置に現れる。接続の宣言(第4章 4.2)と、公開面の形(`flow out` / `flow in`)である。
  同じ物——非同期の一方向の流れ——を、関係の側と公開面の側から見ている。
- 綴りの最終決定は Phase 1 のパーサ実装で行う。本節は基準であり、語ごとの再検討はそこで行う(ADR 0014)。

## 5.4 書き手が定める名前 — UTF-8

書き手が名付ける対象は、5.5 の規則の範囲で UTF-8 の任意の文字を使える。
**日本語の名前は正規の記述であり、例外的な許容ではない。**

| 種別                     | 例                                       |
| ------------------------ | ---------------------------------------- |
| システム名               | `system センサー収集`                    |
| コンポーネント名         | `component 受注受付`                     |
| フロー名                 | `flow 注文の流れ`                        |
| 公開面の名前・引数名     | `expose 受注(注文) -> 受注番号`          |
| 外部システム名・actor 名 | `external 通知基盤` `actor 運用者`       |
| 状態名                   | `state 索引 recoverable(商品原簿の再生)` |
| 内部階層の名前           | `layers { 照合 { pure domain } }`        |
| 照合器の名前             | `collator 名前順(locale ja-JP, …)`       |
| body 内の関数名・変数名  | 実装の記述に現れる名前すべて             |

内部階層の名前は書き手のものだが、その**制約強度と役割**は言語が定める語であり 5.3 に従う。
`照合 { pure domain }` の1行に、書き手の名前と言語の語が並ぶ。出自が違うものが字種で見分けられる。

データ名・フィールド名・量と単位の名前も同じ扱いになるが、宣言の形はデータ型の決定(U9・U15)を待つ。

## 5.5 識別子の規則

### 使える文字 — UAX #31

- 開始文字は `XID_Start` または `_`、継続文字は `XID_Continue` とする(Unicode Standard Annex #31)。
- 制御文字・双方向制御文字(U+202A〜U+202E, U+2066〜U+2069)・書式文字・私用領域・未割り当てのコードポイントは使えない。
- `Pattern_Syntax` と `Pattern_White_Space` の文字は構文のために予約する。
- 全角空白(U+3000)は空白として扱わず、識別子にも使えない。空白は ASCII の空白と改行だけである。
- 違反は E0014-1 とする。

双方向制御文字を禁じるのは、**見た目の並びと構文解析の結果が食い違うソース**を書けなくするためである
(Trojan Source, CVE-2021-42574)。これは実行時ではなく読解時の驚きであり、静けさ(第0章 0.1)の対象に含める。

### 正準形 — NFC

- 識別子は NFC(正規化形 C)で書く。NFC でない識別子は E0014-2 とする。
- 同一性の判定は、NFC のコードポイント列の一致とする。
- **正規化して受け入れる事はしない**。書き手の綴りをコンパイラが書き換えると、書いた通りに読めなくなる。
  拒否して書き手に直させる。

テキストは正準形を持たないため素の等値比較とハッシュを持たない(第3章 3.2、ADR 0013)。
識別子はその逆で、**正準形を一つに限る事で同一性を持てる**側に置く。

### 見分けのつかない名前

同一の名前空間に、UAX #39 の skeleton(混同可能性の骨格)が一致する別の識別子が二つ以上あるとき、E0014-3 とする。

``` plaintext
data 注文 { … }
data 注 文 { … }        # E0014-1: 識別子に空白は使えない
data ＩＤ { … }
data ID  { … }          # E0014-3: 全角と半角が同じ名前空間で見分けられない
```

- **別の名前として拒む**のであって、NFKC で正規化して同じ名前に畳むのではない。
- 名前空間の範囲は U14(プログラムの宣言)が決める。それまでは1プログラム内を範囲とする。
  現在の仕様は、システム名・コンポーネント名をプログラム内で一意としており(第1章 1.2、第2章 2.1)、これと一致する。
- 混同の判定表は Unicode の版に依存する。検査はコンパイル時のみとし、**判定結果を永続化しない**。
  照合キーを永続化しない(E0013-3)のと同じ理由である。

## 5.6 言語の外への写像

名前は言語の外へ出る。出た先で綴りが失われると、コードからの投影という原則(第0章 0.7)が破れる。

- **コンポーネント記述子**(ADR 0012 の H1)は言語中立であり、名前は NFC の UTF-8 のまま持つ。
  Zenoh のキー空間に載る名前と版も同じとする。
- **トランスパイル先の識別子**は出力言語の規則に従う。TypeScript と Rust はいずれも非 ASCII 識別子を受けるが、
  Rust は非 ASCII の識別子に lint を持ち、出力先によっては ASCII しか使えない。
  したがってトランスパイラは、出力言語が受けない名前を**可逆な符号化**で綴り直し、元の名前との対応表を出力に添える。
- 可逆である事を要求するのは、ログ(U4)・図(Phase 3)・診断が元の名前で読めなければならないためである。
- 符号化の具体的な規則は、Phase 1 の接合面(H1〜H8)の凍結と併せて決める。

## 5.7 対象外 — 診断と文書の自然言語

本章が定めるのは**ソースの綴り**である。次は対象外とする。

- コンパイラの診断メッセージ。診断は `E<出自>-<連番>` で識別されるため(第3章 3.3)、本文の自然言語は実装の選択に委ねる。
- ログの本文(U4)。
- 仕様書・ADR・思考実験の記述言語。

## 5.8 未定事項(Phase 1 以降で決める)

- **語ごとの綴りの確定**。5.3 は基準であり、パーサ実装で語ごとに再検討する。決まっているのは「ASCII である事」と、
  衝突を避ける判断の基準である(ADR 0014)。
- **名前空間の範囲**(U14)。5.5 の「同一の名前空間」がプログラム全体なのか system 単位なのか。
  システムの入れ子(第1章 1.5、ADR 0018)を許すなら system 単位が第一候補になる。
- **Unicode の版**。E0014-3 の判定は版に依存する。判定結果を永続化しない事で版の更新が過去の成果物を壊さないようにしてあるが、
  検査に使う版をプログラムの宣言に含める必要が出るかもしれない。全文検索の索引(U21)と一貫した答えを取る。
- **型の語彙の綴りの確定**。5.3 に区分を8つ足したが(データの宣言・基本型・論理・量と単位・数値の操作・丸め・時間の操作・暦)、
  語ごとの綴りは Phase 1 のパーサ実装で再検討する。`unit` は度量衡の単位を指し、コンポーネントの旧称とは衝突しない(ADR 0015)。
- **正規化の要求の緩和**。NFD で書きたい環境が現れた場合、5.5 を「入力時に NFC へ正規化して保存する道具の仕事」として
  整理し直す余地がある。言語の側は NFC のみを受ける立場を動かさない。

## 5.9 参照する規格と先行例

| 規格・文献                                                   | 使っている所                     |
| ------------------------------------------------------------ | -------------------------------- |
| Unicode Standard Annex #31 *Identifier and Pattern Syntax*   | 5.5 の文字集合、構文用文字の予約 |
| Unicode Standard Annex #15 *Unicode Normalization Forms*     | 5.5 の NFC                       |
| Unicode Technical Standard #39 *Unicode Security Mechanisms* | 5.5 の skeleton による混同検出   |
| Boucher & Anderson (2021) *Trojan Source*(CVE-2021-42574)    | 5.5 の双方向制御文字の禁止       |

主要な言語(Rust・Python・Java・C#・Go・Swift)は「語彙は ASCII、識別子は Unicode」でほぼ一致している。
Shidzuku はこの線引きを踏襲し、Rust が lint(警告)に置いた正規化と混同の規則を**エラーに上げる**点だけが異なる。
破っても動く検出を採らないのは、設計と実装が一体であるという原則による(ADR 0013・0014)。

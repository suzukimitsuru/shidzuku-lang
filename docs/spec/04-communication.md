## 4.1 二つの通信方式

コンポーネント間の通信は ask と flow の2方式のみである(ADR 0004)。

| 方式 | 意味                 | 応答                                         | 用途の例                   |
| ---- | -------------------- | -------------------------------------------- | -------------------------- |
| ask  | 要求-応答            | 必ず返る(成功応答、または失敗・タイムアウト) | 引当の可否、受付 ID の発行 |
| flow | 非同期の一方向の流れ | なし                                         | 計測値ストリーム、イベント |

- ask は構文上は要求-応答だが、実行系では非同期メッセージ+応答として実装する。コンポーネントを跨ぐ直接呼び出し・共有メモリは存在しない。
- ask の応答は必ず返る。相手の障害・期限超過時は**接続の失敗**が返り、呼び出し側が待ち続ける事はない。
  接続の失敗は公開面の応答には現れない。呼び手へ何を返すかは、フローの `on failure` が業務の区分で書く(4.5、ADR 0031 の決定2(接続の失敗は公開面に書かない))。
- ask は期限(`deadline`)を必ず宣言する(有限値。ADR 0008)。期限は「必ず返る」の保証を実行系が果たすための上限であり、既定値は無い。

通信は C4 の「関係(relationship)」に当たり、特定の段に属さず段を跨いで現れる(第0章 0.3、ADR 0015)。
本章が定めるのはコンポーネント間の接続と、**記述の中にあるシステムとの接続**である。
システムを端点に書くとき、届く先はそのシステムの `expose` であり、内側のコンポーネントを直接指す事はできない(第1章 1.5、E0018-4)。
記述の外にある `external` との接続の方式は U12 で決める。

## 4.2 フローの宣言

フロー(flow 宣言)はコンポーネント間の接続と障害時の振る舞いを記述する。フローも意図を持つ(必須)。

``` plaintext
flow <フロー名> {
  intent { ... }                                  # コンポーネントと同じテンプレート(ADR 0003)。必須
  <送り手> -> <受け手> : ask <公開面>(<引数>) deadline <量 時間 を持つ数値> -> <応答>
  <送り手> -> <受け手> : flow <内容> pressure <ポリシー> (transient | durable)
  correlate <鍵の型> : <接続> -> <接続> [within <量 時間 を持つ数値>] -> ...   # 二本以上を結ぶ鍵。接続が2本以上なら必須
  on failure <コンポーネント> [at <接続>, ...] { <埋め合わせの行> ... }       # フローに参加する全コンポーネントについて必須(4.5)
  on expiry <接続> { <埋め合わせの行> ... }                                   # 有限の within を付けた区間ごとに必須
}
```

- 接続の両端は、受け手・送り手の constraint(depends / expose)と整合しなければならない(E0000-2・E0000-3)。型の一致は E0009-1 が見る(第6章 6.1)。
- **`deadline` の欄は `量 時間` を持つ数値を受ける**(`deadline 200 ミリ秒`)。`時間量` という基本型は無い(第6章 6.3)。
  期限に `時点` を書く事はできない——システム時刻は巻き戻るため、経過時間の測定には使えない(E0019-2、第6章 6.4)。
- 接続の属性(ask の `deadline`、flow の pressure・配達保証)と、参加する全コンポーネントの `on failure` は省略できない(省略の禁止。第0章 0.5、ADR 0008、E0008-1)。
  既定で補われる箇所は無く、フローは既定表という外部知識なしに読める。
- 処理の順序、ポリシーの選択、補償の設計といった判断は接続に宿るため、フローの intent は必須である。
- **記述の中の接続は、全てどれかの `flow` 宣言に現れる**(ADR 0031 の決定6)。`depends` に書いた相手(兄弟と親の兄弟)との接続がどの `flow` 宣言にも無ければ E0031-4、
  body が行う通信がどの `flow` 宣言の接続(`on failure`・`on expiry` の中の行を含む)にも当たらなければ E0031-5 とする。
  接続の失敗を翻訳する場所(`on failure`)は `flow` 宣言にしか無いためである。記述の外にある `external` との接続は、外部世界との境界(U12)が端点を決める時に範囲へ入れる。
  検証(E0003-1・E0003-2・W0003-1・W0003-2)もコンポーネントの intent と同じに適用する。

### correlate — 二本以上を結ぶ鍵

一つの仕事が複数の通信に分かれる事がある——`ask 受注(注文) -> 受注番号` を期限内に返し、
確定は後から `flow 受注の状態` で届ける形である。この二本が**一つの仕事である事**を、鍵の型で宣言する(ADR 0023)。

``` plaintext
flow 受注の受付と確定 {
  intent { ... }
  Frontdesk -> 注文管理  : ask 受注(注文) deadline 200 ミリ秒 -> 受注番号 | 受注不可
  注文管理  -> Frontdesk : flow 受注の状態 pressure block(deadline 1 秒) (durable)
  correlate 受注番号 : 受注 -> 受注の状態
  on failure 注文管理  { ... }
  on failure Frontdesk { ... }
}
```

- 読み方は「**受注番号 で結ぶ: 受注 の後に 受注の状態**」である。並びは**時間の順**であり、接続の並びと前後してはならない(E0023-4)。
- **接続の指し方**は、その行に書かれている名前を使う。`ask` は公開面名(`受注`)、`flow` は内容の型(`受注の状態`)である。
  指した接続がこの宣言に無ければ E0023-1、同名の接続が二本あって一意に決まらなければ E0023-3 とする。
- **鍵は型で指す**。`受注の状態` が `確定(受注番号) | 取消(受注番号, 取消の理由)` のように区分ごとに違う形でも、
  型で指せば「どの区分を通っても鍵は同じ型である」と一度で言える。欄の経路(`受注の状態.受注番号`)は書かない。
  鍵の型が指した接続のいずれかに現れなければ E0023-2 とする。検査は型の入れ子(直積の欄・直和の区分の引数・`list` の要素)を辿る。
- **一つの鍵で三本以上を結べる**(`correlate 受注番号 : 受注 -> 決済の結果 -> 受注の状態`)。
  連なる仕事は対ではなく道であり、対に割ると同じ鍵が何度も書かれて道が読めなくなる。
- **接続が2本以上ある `flow` 宣言では必須**である。結ぶ対が無ければ `correlate none` と書く(欠落は E0008-1)。
  接続が1本の宣言には要求しない。結ぶ相手が存在し得ないためである。
- `correlate` が指せるのは**その `flow` 宣言の中にある接続だけ**である。宣言を跨いで結ぶ事はできない。
  `flow` 宣言は一つの仕事の単位であり、鍵で結ばれる通信は同じ仕事だからである。
  **この規則は、フローの切り方に影響する**——引当と解放を別の宣言に分けると、在庫を戻す道が記述の上で切れる。
- `correlate none` と書いた宣言に、同じ相手との `ask` と後から届く `flow` が両方あるときは W0023-1(警告)とする。
  結ばない事が正しい場合(同じ相手と無関係な二つの仕事をする)があるため、エラーにはしない。

### within と on expiry — 待ちの期限

`correlate` の道の区間(二つの接続の間)に `within` で期限を書く。期限を過ぎた時の埋め合わせは `on expiry` に書く(ADR 0031 の決定9)。

``` plaintext
  correlate 受注番号 : 受注 -> 保存 -> 決済の依頼 -> 決済の結果 within 30 分 -> 受注の状態
  on expiry 決済の結果 {
    OrderStore -> Inventory : 引当の解放
    OrderStore -> Frontdesk : 受注の状態
  }
```

- 読み方は「**決済の依頼 の後、決済の結果 が 30 分以内に届く**」である。`within` は直前の矢印(区間)に付く。
- **待つ側**は、区間の前の接続の端点であり、かつ後ろの接続の受け手であるコンポーネントである。後ろの接続の送り手が待つ側自身なら、それは待ちではない。
  待つ側が決まらない区間に `within` を書けば E0031-8 とする。
- **待つ側がある区間には `within` が必須である**(欠落は E0008-1)。無期限は `within none` と書く。
  有限の `within` には、後ろの接続を名指す `on expiry` が必須である。指した接続の直前の区間に有限の `within` が無ければ E0031-9 とする。
- `on expiry` の中身は 4.5 の接続の行と `respond` で書き、**待つ側が行う**。`restart` は書かない(誰も落ちていない)。
  待つ側が通信せずに自分の中だけで片付ける時は `on expiry <接続> none` と書く。
- **期限を測るのは、待つ側の動作環境である。** ノードを跨いだ時計は要らない。期限は `量 時間` を持つ数値であり、`時点` は書けない(E0019-2)。
  動作環境は経過時間計で測り、コードには出さない。待ちは鍵の正準形のまま動作環境に預ける(ADR 0012 の接合面の9つ目の呼び出し、ADR 0031 の決定11(接合面への写し))。
- **待ちは、後ろの接続が届いた時か、待つ側が同じ鍵を持つ同じ `flow` 宣言の接続を受けた時に解ける。** 取消が先に届けば、決済の結果を待ち続けない。
- **期限の後に届いた物や、鍵の合わない到着は失敗と呼ばない**(ADR 0031 の決定10)。普通のデータとして待つ側に届き、body が分岐して扱う。
  遅れて届いた `決済成立` を捨てるか返金の流れを起こすかは業務の判断であり、言語は既定の扱いを置かない。

## 4.3 バックプレッシャ — 接続の属性

flow の接続ごとに pressure を宣言する(必須。既定は無い)。

| ポリシー | 意味                                     |
| -------- | ---------------------------------------- |
| block    | 下流が詰まったら上流を待たせる(欠損なし) |
| latest   | 最新値のみ保持し、途中の値を捨てる       |
| drop     | あふれた分を捨てる                       |

- どのポリシーも明示の選択である。黙ってデータが消えるのは「運用の驚き」であり、捨てる事(latest / drop)は宣言によってのみ起きる。
- block は期限を必ず宣言する(`pressure block(deadline 1 秒)`、無期限なら `pressure block(deadline none)`)。期限は `量 時間` を持つ数値であり、4.2 の `deadline` と同じ形である。期限内に受け付けられない投入は失敗として上流に返る。
  応答期限を持つ ask の世界と flow の境目で必要になる(思考実験 03)。
- ファンアウト(1出力を複数の受け手へ)の各接続は互いに独立である。片方の詰まりは他方に波及しない。
- latest / drop で捨てた事実、block の `deadline` 超過は、ログ規約(U4、Phase 2)の対象イベントとする。

## 4.4 配達保証 — 接続の属性

flow の接続ごとに配達保証を宣言する(必須。既定は無い)。

| 保証      | 意味                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------ |
| transient | 平常時は届くが、コンポーネントの障害・再起動を跨ぐと失われ得る                                         |
| durable   | コンポーネントの障害・再起動を跨いで失われない。実行系が永続化・再送し、受け口に idempotent を要求する |

- durable はコスト(永続化・再送)を伴うため、失えない接続(受付 ID を返した後のジョブ等)が明示的に負う。transient を選ぶ事も明示の判断である。
- durable 接続の受け口には idempotent 宣言が必須(E0004-1)。
- transient の消失は黙った消失にならない。何が失われ得るかは `on failure` と状態の宣言(第3章 3.2 の state)に現れる。
- durable の実現手段(永続化・再送・Raft の適用)は U6 として Phase 2 で定める。

## 4.5 障害時の記述

うまくいかない事は、どこで受けるかで四つの置き場に分かれる(ADR 0031 の決定1(四つの置き場))。

| 置き場           | 含む物                                                    | 受ける所                         |
| ---------------- | --------------------------------------------------------- | -------------------------------- |
| データの区分     | データとして正常な不在・業務の拒否                        | 呼び手の body(第6章 6.1)         |
| 演算と解析の失敗 | 桁溢れ・0 除算・範囲外・テキストを読めない等              | その操作を書いた body(第6章 6.3) |
| 接続の失敗       | `ask` の期限超過・相手の障害・`pressure block` の期限超過 | `flow` 宣言の `on failure`(本節) |
| 待ちの期限切れ   | 相手が生きたまま届かない物                                | `flow` 宣言の `on expiry`(4.2)   |

- `transient` の流れが再起動を跨いで消える事は送った側に返らず、接続の失敗に含めない(4.4)。`latest`・`drop` で捨てた事は宣言された廃棄であり、失敗ではない(4.3)。

フローは `on failure <コンポーネント>` で、そのコンポーネントの障害(接続の失敗)を**何で埋め合わせるか**を記す。中身は次の三種の行の並びである(ADR 0031 の決定3)。

``` plaintext
on failure Inventory at 引当 {
  OrderIntake respond 受注 : 受け付けられなかった    # 代わりの応答
  restart                                           # 障害を起こした側の扱い
}
on failure OrderStore at 保存 {
  OrderIntake -> Inventory : ask 引当の解放(引当番号) deadline 100 ミリ秒 -> 解放の結果   # 補償の接続
  OrderIntake respond 受注 : 受け付けられなかった
  restart
}
```

| 行        | 意味                                                                    | 検査                                                            |
| --------- | ----------------------------------------------------------------------- | --------------------------------------------------------------- |
| 接続の行  | 生き残った側が、補償・後始末に使う接続                                  | 平常時の接続と同じ(E0000-2・E0000-3・E0009-1・E0008-1)          |
| `respond` | 生き残った側が、待たせている `ask` に業務の区分で答える                 | E0031-1(区分が応答に無い)・E0031-2(答えられない `ask`)          |
| `restart` | 障害を起こしたコンポーネントを再起動する。`restart none` で再起動しない | 必須(E0008-1)。再起動で失われる状態と state 宣言の整合(E0000-4) |

- **接続の失敗は公開面に書かず、`respond` で業務の区分へ翻訳する。** 返すべき区分が無ければ、記述者が公開面の直和に区分を足す(`受け付けられなかった`)。
  言語が接続の失敗の種類を足しても公開面は変わらず、コンポーネントの版は上がらない。
- **接続の行は平常時と同じ検査を受ける。** 同じ `flow` 宣言の本文に同じ送り手・受け手・名前の接続があれば、名前だけで指せる(`OrderStore -> Inventory : 引当の解放`)。
  属性は本文の行から読む。本文に無い接続は全ての属性を書く。
- **`respond` は、まだ答えていない `ask` にだけ書ける。** 名指す公開面の `ask` は同じ `flow` 宣言にあって `at` の接続より前に並び、
  答える者はその `ask` の受け手であり、かつ `at` の接続の送り手でなければならない。
- **`at` で接続を絞れる。** 一つのコンポーネントについて、`at` の無い `on failure` を1つ書くか、`at` を付けた `on failure` で端点になる全ての接続をちょうど一度ずつ覆う(E0031-3)。
  「残り全部」を受ける書き方は置かない。`respond` は `at` で絞った `on failure` の中でだけ書ける。
- **補償の失敗は入れ子にしない。** 補償が届かずに残った物は、それを待つ側の期限切れ(`on expiry`)が引き受ける。待つ側が居なければ、記述者が待つ側を置く(ADR 0031 の決定5)。
- **接続の失敗を受けた body は、`on failure` に書かれた手順だけを行う。** 同じ接続を呼び直す事は書けない(E0031-5 の範囲)。再試行は 4.6 の未定事項である。
- `on failure` はフローに参加する全コンポーネントについて書く(E0008-1)。端点がシステムのときは、そのシステムについて書く。書かれないコンポーネントの障害時挙動という暗黙を残さない(ADR 0008 の机上検証で、4フロー全てに入口の記述漏れが見つかった)。
- 「伝播しない」の一句は書かない。障害の非伝播は全コンポーネントの不変条件である(第0章 0.4)。
- 演算と解析の失敗を body が「障害にする」で受けた時は、そのコンポーネントの障害となり、`on failure` が引き受ける(第6章 6.3)。
- 語の綴り(`at`・`respond`・`restart`・`within`・`on expiry`)は第5章 5.3 に置き、パーサの実装中に語ごとに再検討する(ADR 0014)。

## 4.6 未定事項(Phase 1 以降で決める)

- ask の再試行の規定(U4 のログ規約と合わせて)。`deadline` は既定値を置かず必須とした(ADR 0008)。
  今は接続の失敗を受けた body は呼び直せない(4.5)。再試行は接続の属性として足し、足す時も既定値を置かず全ての `ask` に書かせる(ADR 0031 の決定8)。
- **監督の詳細**。`restart` の回数・間隔・諦めた後の扱い。今は再起動するかしないかだけを書く(4.5)。最小の分散動作環境(Phase 2)の監督と併せて決める。
- **期限の和**。外側の `ask` の期限が、その中で順に走る内側の期限の和より短い記述を警告にするか(ADR 0031 の机上検証1)。U10・U11 の後に決める。
- pressure の語彙の拡張(バッファ上限付き block 等)。実装で必要が確認されてから。
  ただし **block の上限そのもの**は、ADR 0012 の机上検証(思考実験 04 の `pressure block(期限 1s)`)で必要が確認されている。
  キューを作るのは動作環境であり、作る時に上限が要るためである。残るのは上限の書き方であり、実装を待たずに決める。
- ADR 0001(Zenoh)へのマッピング(flow=Pub/Sub、ask=Query)。Phase 2 で検証。
- 外部システムとの接続の方式・属性・障害時の記述(U12)。第1章 1.8 の未定事項と同じ課題である。
  記述の中にある兄弟システムとの接続は書けるようになった(第1章 1.5)ため、残るのは記述の外にある相手である。
- **フローの端点に外部システムを書けるか**(U12)。現在の接続は両端を depends / expose と突き合わせる(E0000-2・E0000-3)ため、
  記述の外にある `external` を端点に書けない。結果、外部から届く経路がフローに現れず、
  `on failure` の対象(フローに参加する全コンポーネント)にも外部が入らない。durable な受け口でも送り手の障害の記述が書けないまま残る(思考実験 08 論点7)。
- **役割の向きと通信の関係**(U20)。層の役割の一方向性(第2章 2.4、E0013-4)が ask / flow にも及ぶのかが未定である(思考実験 08 論点2)。

## 4.7 思考実験による裏付け

表の「ユニット」は改名前の呼称であり、コンポーネントと読み替える(ADR 0015)。
思考実験の語彙(`期限` など)は日本語のままである。英字への読み替えは ADR 0014 決定7 と第5章 5.3 による。

| 構成要素                 | 裏付け                                                     |
| ------------------------ | ---------------------------------------------------------- |
| ask / flow の2方式       | 思考実験 01(ask が必須)・02(flow のみで完結)・03・04(混在) |
| バックプレッシャ         | 思考実験 02(接続ごとに block / latest)・03(期限付き block) |
| 配達保証                 | 思考実験 02(transient で足りる)・03・04(durable が必要)    |
| フローの intent(必須)    | 思考実験 01〜04(順序・切替・補償の判断が接続に宿った)      |

| 外部が端点になる接続     | 思考実験 08(書けない事を発見。論点7)                       |
| 失敗の置き場・待ちの期限 | 思考実験 20〜22・25、ADR 0031 の机上検証                   |

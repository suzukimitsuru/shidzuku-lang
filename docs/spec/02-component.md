# Shidzuku 言語仕様書 — 第2章 コンポーネントの定義

- 状態: Draft
- 日付: 2026-08-19(改訂 2026-08-26: ユニットをコンポーネントに改名し、body を Code 段として位置づけた。ADR 0015 提案)
- 依拠: 第0章 0.3〜0.5、ADR 0003(採用)・0005(提案)・0006(提案)・0008(採用)・0015(提案)。未採用 ADR の採否により本章も改訂される

## 2.1 コンポーネントの宣言

コンポーネント(component)は Shidzuku の唯一の構成要素である。設計単位・処理単位・障害境界・配置単位は同一である(第0章 0.4)。
C4 モデルの Component 段に対応し、その内側(body と内部階層)が Code 段である(第0章 0.3、ADR 0015)。

``` plaintext
component <コンポーネント名> {
  intent     { ... }   # 第一層: 意図(2.2)
  constraint { ... }   # 第二層: 制約(2.3、語彙は第3章)
  body       { ... }   # 第三層: 実装(2.4)= Code 段
}
```

- 三層はいずれも省略できない(第0章 0.5)。欠落はコンパイル時エラーとする。
- コンポーネント名はプログラム内で一意とする。
- コンポーネントは、ちょうど1つのシステムの `contains` に属する(第1章 1.2、E12)。
- コンポーネントの外との相互作用は、constraint に宣言された公開面を通る通信のみである(通信は第4章)。
  コンポーネントを跨ぐ直接呼び出し・共有メモリは存在しない。

## 2.2 第一層: 意図(intent)

検証不能な理由の記録。形式は ADR 0003 に従う。

``` plaintext
intent {
  why      "<なぜこの境界で切るか。このコンポーネントは何の知識を隠すか>"
  rejected option "<検討して捨てた選択肢>"
           reason "<なぜ捨てたか>"
  change   "<将来どんな変化を想定するか。このコンポーネントはそれをどう吸収するか>"
  refs     "<意図の理解を助ける外部資料>"     # 任意
}
```

- why・rejected・change は必須、refs は任意。
- rejected は(選択肢, 理由)の組を1件以上書く。棄却の対象は、このコンポーネントの境界を決めた判断の全て(分割方法・実装方式のどちらも可)。
  検討の結果、捨てた選択肢が存在しなかった場合のみ `rejected none "<選択肢がなかった理由>"` と明示できる。
- 記述の検証(エラー E1〜E2・警告 W1〜W2)は第3章 3.3 に一覧する。内容の意味的な正しさは機械検証しない。
- システムの intent(第1章 1.3)と形式は同じであり、書く対象が「コンポーネントの境界」か「システムの境界」かだけが違う。

## 2.3 第二層: 制約(constraint)

検証可能な意図。コンパイラ・実行系が違反を拒否する。語彙と検証時期の一覧は第3章に置く。

``` plaintext
constraint {
  depends    <コンポーネント名の列挙 | なし>       # 通信してよい相手。必須
  expose     <公開面の宣言 | なし>       # ask の受け口 / flow の出入り(第3章 3.2)。必須
  idempotent <公開面名>                  # 再実行が二重の効果を持たない(約束。該当時のみ)
  state      <状態名> volatile | recoverable(<復元元>)   # 状態の再起動時の扱い。必須(持たなければ state なし)
  layers     { <階層名> { pure | io } ... }   # 内部階層(2.4)。必須
}
```

**省略の禁止**(第0章 0.5、ADR 0008): 選択のある宣言に省略時の既定は無い。該当が無い事も `なし` と明示する(E9)。
約束(idempotent)を書かない事は既定ではなく「保証しない」という約束の不存在である。
障害の非伝播は全コンポーネントの不変条件(第0章 0.4)であり、宣言の語彙には無い。埋め合わせはフローの `on failure` に書く(第4章)。

`depends` と `expose` は、システムの constraint(第1章 1.4)と同じ語である。段が変われば指す先が変わる。

## 2.4 第三層: 実装(body)と内部階層 — Code 段

コンポーネントの内側は原則自由である(ミュータブル・例外可)。言語が管轄するのは外側との通信のみ。
body とその内部階層が C4 の Code 段に当たる(第0章 0.3、ADR 0015)。

内部階層は ADR 0005・0008 に従う。

- **階層の宣言は必須である**。body の全てのコードはいずれかの名前付き階層に属し、宣言のない実装は存在しない(E9)。
  コンポーネントは、言語の既定規則という外部知識なしに、それ自体で読める(第0章 0.5)。
- 階層の名前と数は自由(domain / driver、planning / codec など、コンポーネントの文脈に合った名前を付ける)。
- 制約強度は固定の2種から選ぶ。

| 強度 | 意味                                                     |
| ---- | -------------------------------------------------------- |
| pure | 純粋。IO 不可・外部状態への依存不可。決定的な計算のみ    |
| io   | 自由。IO・可変状態を許す(コンポーネントの内側の原則通り) |

- pure 層は io 層に依存できない。環境依存値(現在時刻・乱数・設定)は io 層が取得し、値として pure 層へ注入する。

**階層は Component 段ではなく Code 段に属する**(ADR 0015)。階層は外から見える面ではないからである。
コンポーネントの外との相互作用は expose を通る通信だけであり、どの層が何を持つかは外から観測できない。

C4 の Code 段は「必要な時だけ描く、実装から読み取る最下段」だが、Shidzuku の Code 段は宣言によって常に構造を持つ。
階層の名前・制約強度(pure / io)が必須である事が、抽出できる Code 図の条件である。

## 2.5 粒度の指針

**1コンポーネント = 隠す設計判断が1つ**(ADR 0006)。判定には intent の why を使う。

- why が1文で書けない(「〜し、かつ〜する」)→ 分割を検討する。
- why が隠す知識を挙げられない(公開面が素通しの委譲だけ、親コンポーネントの why の言い換え)→ 統合を検討する。

この指針は機械検証しない。担保はレビューと思考実験に置く。
システムの境界(第1章 1.4 の外部システムの判定)も同じ扱いであり、段が上がっても機械検証の届かない判断は残る。

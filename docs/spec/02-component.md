# Shidzuku 言語仕様書 — 第2章 コンポーネントの定義

- 状態: Draft
- 日付: 2026-08-19(改訂 2026-08-29: ADR 0014 の採用に伴い、語彙を ASCII に揃えた)
- 依拠: 第0章 0.3〜0.5、第5章、ADR 0003・0005・0008・0013・0014・0015・0016(いずれも採用)、ADR 0006・0018(提案)。未採用 ADR の採否により本章も改訂される

## 2.1 コンポーネントの宣言

コンポーネント(component)は Shidzuku の唯一の構成要素である。設計単位・処理単位・障害境界・配置単位は同一である(第0章 0.4)。
C4 モデルの Component 段に対応し、その内側(body と内部階層)が Code 段である(第0章 0.3、ADR 0015)。

``` plaintext
component <コンポーネント名> {
  intent     { ... }   # 第一層: 意図(2.2)
  constraint { ... }   # 第二層: 制約(2.3、語彙は第3章)
  body       { ... }   # 第三層: 実装(2.4)= Code 段
}
```

- 三層はいずれも省略できない(第0章 0.5)。欠落はコンパイル時エラーとする。
- コンポーネント名はプログラム内で一意とする。
- コンポーネントは、ちょうど1つのシステムの `contains` に属する(第1章 1.2、E0015-2)。
- コンポーネントの外との相互作用は、constraint に宣言された公開面を通る通信のみである(通信は第4章)。
  コンポーネントを跨ぐ直接呼び出し・共有メモリは存在しない。

## 2.2 第一層: 意図(intent)

検証不能な理由の記録。形式は ADR 0003 に従う。

``` plaintext
intent {
  why      "<なぜこの境界で切るか。このコンポーネントは何の知識を隠すか>"
  rejected option "<検討して捨てた選択肢>"
           reason "<なぜ捨てたか>"
  change   "<将来どんな変化を想定するか。このコンポーネントはそれをどう吸収するか>"
  refs     "<意図の理解を助ける外部資料>"     # 任意
}
```

- why・rejected・change は必須、refs は任意。
- rejected は(選択肢, 理由)の組を1件以上書く。棄却の対象は、このコンポーネントの境界を決めた判断の全て(分割方法・実装方式のどちらも可)。
  検討の結果、捨てた選択肢が存在しなかった場合のみ `rejected none "<選択肢がなかった理由>"` と明示できる。
- 記述の検証(エラー E0003-1・E0003-2・警告 W0003-1〜W0003-2)は第3章 3.3 に一覧する。内容の意味的な正しさは機械検証しない。
- システムの intent(第1章 1.3)と形式は同じであり、書く対象が「コンポーネントの境界」か「システムの境界」かだけが違う。

## 2.3 第二層: 制約(constraint)

検証可能な意図。コンパイラ・実行系が違反を拒否する。語彙と検証時期の一覧は第3章に置く。

``` plaintext
constraint {
  depends    <コンポーネント名の列挙 | none>      # 通信してよい相手。必須
  expose     <公開面の宣言 | none>       # ask の受け口 / flow の出入り(第3章 3.2)。必須
  idempotent <公開面名>                  # 再実行が二重の効果を持たない(約束。該当時のみ)
  state      <状態名> volatile | recoverable(<復元元>)   # 状態の再起動時の扱い。必須(持たなければ state none)
  collator   <照合器名>(locale <ロケール>, strength <強度>) | none   # 必須(使わなければ none)
  layers     { <階層名> { <制約強度> <役割> } ... }   # 内部階層(2.4)。必須
}
```

**省略の禁止**(第0章 0.5、ADR 0008): 選択のある宣言に省略時の既定は無い。該当が無い事も `none` と明示する(E0008-1)。
約束(idempotent)を書かない事は既定ではなく「保証しない」という約束の不存在である。
障害の非伝播は全コンポーネントの不変条件(第0章 0.4)であり、宣言の語彙には無い。埋め合わせはフローの `on failure` に書く(第4章)。

`depends` と `expose` は、システムの constraint(第1章 1.4)と同じ語である。段が変われば指す先が変わる。
`depends` に書けるのは兄弟コンポーネントと、**親の兄弟システム**である(第1章 1.5、第3章 3.2)。

## 2.4 第三層: 実装(body)と内部階層 — Code 段

コンポーネントの内側は原則自由である(ミュータブル・例外可)。言語が管轄するのは外側との通信のみ。
body とその内部階層が C4 の Code 段に当たる(第0章 0.3、ADR 0015)。

内部階層は ADR 0005・0008・0013 に従う。階層は**名前・制約強度・役割**の三つを持つ。

``` plaintext
layers {
  <階層名> { <制約強度> <役割> }
  ...
}
```

- **階層の宣言は必須である**。body の全てのコードはいずれかの名前付き階層に属し、宣言のない実装は存在しない(E0008-1)。
  コンポーネントは、言語の既定規則という外部知識なしに、それ自体で読める(第0章 0.5)。
- 階層の名前と数は自由(`受付` / `照合`、`計画` / `符号化` など、コンポーネントの文脈に合った名前を付ける)。名前は書き手のものであり UTF-8 を使える(第5章 5.4)。
- **制約強度と役割はいずれも必須**であり、欠落は E0008-1 とする。二つの軸は直交する——
  強度は「何をしてよいか(IO と決定性)」を、役割は「何を扱ってよいか(外部表現とテキスト)」を語る。

### 制約強度 — pure / io

制約強度は固定の2種から選ぶ(ADR 0005)。

| 強度 | 意味                                                     |
| ---- | -------------------------------------------------------- |
| pure | 純粋。IO 不可・外部状態への依存不可。決定的な計算のみ    |
| io   | 自由。IO・可変状態を許す(コンポーネントの内側の原則通り) |

- pure 層は io 層に依存できない。環境依存値(現在時刻・乱数・設定)は io 層が取得し、値として pure 層へ注入する。
- 違反は E0005-1 とする。

### 役割 — boundary / parse / domain / format

役割は固定の4種から選ぶ(ADR 0013)。テキストと外部表現(バイト列)に対する権能を決める。

| 役割     | 語義 | 責務                                                                   |
| -------- | ---- | ---------------------------------------------------------------------- |
| boundary | 境界 | 外部とのバイト列の授受。テキストも領域の型も現れない                   |
| parse    | 解析 | バイト列またはテキストから領域の型を作る。部分取得が許される唯一の役割 |
| domain   | 領域 | 業務。テキストは不透明な値として通過するだけ                           |
| format   | 整形 | 領域の型とテキストから、表示と出力用のバイト列を組み立てる             |

**データの向きは boundary → parse → domain → format → boundary の一方向**である。逆流(domain でバイト列を作る、format の結果を domain へ戻す)は E0013-4 とする。
入りと出りを別の役割にはしない。向きはデータの流れから決まり、受付のコンポーネントは必ず両方向を持つ。

○ = 可、× = 不可。

| 機能                                                       | boundary | parse | domain | format           |
| ---------------------------------------------------------- | -------- | ----- | ------ | ---------------- |
| バイト列の入出力(外部との授受)                             | ○        | ×     | ×      | ×                |
| バイト列・テキストからの解析(部分取得・分割・パターン照合) | ×        | ○     | ×      | ×                |
| 領域の型への変換                                           | ×        | ○     | ×      | ×                |
| テキストの生成                                             | ×        | ○     | ×      | ○                |
| テキストの保持・受け渡し                                   | ×        | ○     | ○      | ○                |
| 素の等値比較・ハッシュ・キー利用                           | ×        | ×     | ×      | ×                |
| collator による比較・整列・検索                            | ×        | ○     | ○      | ○                |
| 照合キーの永続化・受け渡し                                 | ×        | ×     | ×      | ×                |
| テキストの内容による分岐                                   | ×        | ○     | ×      | ×                |
| 連結                                                       | ×        | ×     | ×      | テンプレートのみ |
| 長さ・添字                                                 | ×        | ○     | ×      | 表示幅のみ       |
| 出力用のバイト列化                                         | ×        | ×     | ×      | ○                |

boundary に collator が無いのは、その層にまだテキストが存在しないためである。

### 役割と制約強度の組合せ

役割は選べる強度を狭める。矛盾する組合せ(io の parse 層など)は E0013-2 とする。

| 役割     | pure | io  | 理由                                                                             |
| -------- | ---- | --- | -------------------------------------------------------------------------------- |
| boundary | ×    | ○   | 外部との授受そのものが IO である                                                 |
| parse    | ○    | ×   | 解析の途中で外部を引くと変換規則が記述から読めない。対応表は boundary が注入する |
| domain   | ○    | ○   | 純粋な計算の層と、状態を持つ層の双方がある                                       |
| format   | ○    | ×   | 組み立ては決定的である。出力は boundary が行う                                   |

### 段としての位置づけ

**階層は Component 段ではなく Code 段に属する**(ADR 0015)。階層は外から見える面ではないからである。
コンポーネントの外との相互作用は expose を通る通信だけであり、どの層が何を持つかは外から観測できない。

C4 の Code 段は「必要な時だけ描く、実装から読み取る最下段」だが、Shidzuku の Code 段は宣言によって常に構造を持つ。
階層の名前・制約強度・役割が必須である事が、抽出できる Code 図の条件である。

### 未定事項

- **「外部」の語義**。役割の表で boundary が受け持つ「外部」は、システムの `external`(第1章 1.4)より広く、
  外部の技術(RDB 等)と人への窓口(HTTP)を含む。同じ語が二つの段で別の物を指しており、突き合わせが要る(U20、思考実験 08 論点1)。
- **E0013-4 の適用範囲**。役割の向きはコンポーネントと外の世界のあいだの話であり、コンポーネント間の通信(ask / flow)には
  適用されないはずだが、その限定が書かれていない(U20、思考実験 08 論点2)。
- **テキスト・バイト列の型そのもの**は、データ型の決定(U9・ADR 0009)を待って本仕様書に入る。
  現時点では役割の表が語る権能の対象として存在し、型の定義を持つ章がまだ無い。

## 2.5 粒度の指針

**1コンポーネント = 隠す設計判断が1つ**(ADR 0006)。判定には intent の why を使う。

- why が1文で書けない(「〜し、かつ〜する」)→ 分割を検討する。
- why が隠す知識を挙げられない(公開面が素通しの委譲だけ、親コンポーネントの why の言い換え)→ 統合を検討する。

この指針は機械検証しない。担保はレビューと思考実験に置く。
システムの境界——何を `external` に書き、何を `contains` に入れるか——も同じ扱いである。
そちらは指針すら持たない。言語は規則を置かず、判断は intent に残る(第1章 1.4)。

# 雫 (Shidzuku)

**綺麗なコード、静かなシステム。**

Shidzuku は、設計意図から制約・構造・実装までを一本の記述で貫く事を目指す言語プロジェクトです。
図面は別に描くものではなく、コードからの投影として常に実装と一致します。

## 中核となる考え

- コンポーネント: **モジュール = フローの節 = 障害境界 = 配置単位**
- 各コンポーネントは三層で記述する: **意図**(検証不能な理由の記録)/ **制約**(機械検証)/ **実装**(名前付きの層に強度と役割を宣言。ADR 0005・0013)
- 記述の段は C4 モデルに揃える: **システム** / **動作環境** / **コンポーネント** / **コード**(ADR 0015)。システムは入れ子にできる(ADR 0018)
- 記述の表記は「言語が定める語彙は ASCII、書き手が定める名前は UTF-8」(ADR 0014)
- データの型は11 の基本型と4つの構成子。**型の名前が値の出どころを告げる**(ADR 0009・0019・0020・0021・0022)。数値は幅と位取りを型に書き、単位は量の種別(比率・計数・計量・位置)に属する(下記)
- 実行時の静けさ(障害が伝播しない・ログが騒がしくない・運用で驚きがない)を構造から生む

詳細は [docs/spec/00-vision.md](docs/spec/00-vision.md) を参照。

## 状態

Phase 0(言語仕様)を進行中。

課題(U1〜U25)は [docs/PLAN.md](docs/PLAN.md) 第2節に、
それに対する決定(ADR 0001〜0025、0011 は欠番)の状態は同じく第3節にまとめてあります。
ADR 0005・0013・0015・0016 は 2026-08-28 に、ADR 0014・0009・0019・0020 は 2026-08-29 に採用しました。
**型の体系(束 B)の大半が確定し、第6章「データと型」を新設しました。**
**2026-09-03、数値型の設計(ADR 0010・0017)を白紙から再検討する事にしました。** 金融機関・科学技術計算での他言語の実例を
思考実験 14 で比較し、7つの論点にまとめた上で(詳細は [docs/PLAN.md](docs/PLAN.md) 第7節)、
**2026-09-10 に ADR 0021(数値型の体系)として起案し直し**、思考実験 16〜18 で整数型の要否・他言語の数値型・書き下ろしを検証した上で、
**2026-09-16 に採用して数値型を確定しました** — `int8/16/32/64/128/256(s)`・`uint8/16/32/64/128/256(s)`・`float32/64` と、
内部計算用の `dec(整数部.小数部)` の4種です。
**幅(`dec` は宣言した桁)が上限を、位取り(小数点以下の桁数)が刻みを決めます**。単位の欄は必須で、単位なしは `unitless` です。
`dec` は格納が値による可変長ですが上界は宣言が言い、データフロー・外部インターフェイス・状態には書けません。
暗黙の変換は1本も置かず、型に序列も置きません(ADR 0017 の「主に使う型」は引き継ぎません)。
`float128` はハードウェアと出力先の事情から置きません(ADR 0021)。
これで**型の体系(束 B)は数値まで含めて確定し**、ADR 0019 の凍結していた決定2・決定7 も解けました。
併せて U14(プログラムの宣言)の名前空間案(逆ドメイン名)は撤回し、思考実験 15 で再検討しています。
2026-09-17 には ADR 0012(動作環境の言語とトランスパイル先の言語)を採用し、**動作環境は Rust の1実装、トランスパイル先は Rust と TypeScript** に確定しました。
**2026-09-17 には ADR 0022(単位の種別)を採用しました** — 量を比率・計数・計量・位置の4種別に分けて宣言し、
数える量(`個`)は掛けると単位が消え(`円 × 個 = 円`)、版や添字のような位置の量は差とだけ足せます(序数と基数の区別、U24)。
2026-09-18 には ADR 0006(コンポーネントの粒度の指針)を後続の ADR に追従させて採用し、**1コンポーネント = 隠す設計判断が1つ、内部階層の数では割らない** と確定しました(U7 の検証は続けます)。
2026-09-25 には ADR 0018(システムの入れ子)を採用しました — `contains` にシステムを書け、ルートはちょうど1つです。
採用に先立ち、コンポーネントとシステムが混在した `contains` の中で互いを呼べない穴を塞ぎ、
`depends` の相手を**兄弟(同じ `contains`)と親の兄弟、そして `external`** に揃えました。
2026-09-25 の思考実験 20(対になる通信)と思考実験 21(補償と巻き戻し)を経て、2026-09-26 に
**ADR 0023(対になる通信の相関)を起案しました** — `ask` の応答と後から届く `flow` が一つの仕事である時、
二本を結ぶ鍵を `flow` 宣言に書きます(`correlate 受注番号 : 受注 -> 受注の状態`)。鍵は仕事に一つではなく、結ぶ対ごとに書きます。
**同日に採用し、第4章 4.2 に `correlate` を置きました。** 接続が2本以上あるフローでは必須で、結ぶ対が無ければ `correlate none` と書きます。
同日、思考実験 23(結合の釣り合い)で既存の記述を Khononov の結合バランス(強度・距離・変動性)で読み直し、
**ADR 0024(APoSD と結合バランスの考え方の取り込み)と ADR 0025(粒度の指針に結合の釣り合いを加える)を提案として起案しました。**
仕様は結合の釣り合いを名前を挙げずに使っていましたが、`data` の共有(モデル結合)の距離だけは測っていませんでした。これは U14 の入力にしています。
判断待ちの ADR はこの2本です。その後は U13(失敗の体系)で、仕事の期限と `on failure` の欄の形を扱います(計画書 第4節 4.3)。

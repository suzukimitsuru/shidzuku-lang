## 締めの確かめ

計画書 第4節の締めの確かめは「記述から生成した Rust が動き、試験の口から流した計測値が正規化されて受け口に届く。`pressure` を書かない記述を検証器が拒む」である。
`cargo test -p shidzuku-example-thin-vertical-slice` で次の4つが通る。

| 試験                                                       | 見る事                                                                       |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 試験の口から流した計測値が正規化されて受け口に届く         | 機種A と機種B の計測値10件が、全てヘクトパスカルに揃い、送った順に届く       |
| 受け口が詰まると上流は待たされ、受け口が受けると流れが戻る | 受け口が受けないと上流は 192 件で止まり、受け始めると 300 件が送った順に届く |
| pressure を書かない記述を検証器が拒む                      | 74行目の接続を E0008-1(必須宣言の欠落)で拒む。他の診断は出ない               |
| 元の記述は検証を通る                                       | 拒まれる記述と元の記述の違いが `pressure` だけである事の裏                   |

192 件は、上限 64 の待ち行列が3本(試験の入口、SensorIntake から Normalizer、試験の受け口)並んだ和である。
上限が仕掛かりの物も数える(ADR 0032(実行モデルと順序保証)の決定6(上限を `bound` で書く))ため、ちょうど3本分で止まる。

コンパイラ側の検証番号ごとの確かめ(元の記述を一か所ずつ崩す)は [compiler/tests/check.rs](../../compiler/tests/check.rs) にある。

## 試作の中で仮に決めた事

計画書 第4節「仮置き」に従った物と、着手の時に確認を取って仮に決めた物である。仕様書には書かない。

| 事                    | 仮の決め方                                                                                                            |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 外部との境界          | 外部は書かない。ルートの system の `expose`(`flow in`・`flow out`)を、試験から値を流し込む口と、値を受け取る口にする  |
| 試験の口の `pressure` | 書く場所が無いので、動作環境が `block`(期限は無期限、上限 64)に決め打つ                                               |
| body の記法           | `body { }` と書き、パーサは中を読み飛ばす。Rust の body は `src/body/` に置く                                         |
| データの型            | 計測値を読むのに要る型の機能だけ(`id`・`quantity`・`record`、`instant`・`float64`・整数)。`id` の中身は64ビットの整数 |
| 実行モデル            | コンポーネントの中は逐次、接続の中は FIFO(先入れ先出し)。待つ所で次の仕事を受ける再入はしない                         |
| 正準形                | 欄の順に、数を大きい桁から並べる。型の指紋は型の綴りの FNV-1a(Fowler–Noll–Vo のハッシュ関数)の 64 ビット              |
| プログラムの宣言      | 1ファイルに1つのルートの system。名前はファイルの中で一意                                                             |
| ファイルの拡張子      | `.shidzuku`(略号を作らないため)                                                                                       |

## 試作で分かった事

担当する領域ごとに並べる。各領域の README の経緯から、ここを指す。

### 実行モデル

- `flow` だけの流れは、コンポーネントの中は逐次・接続の中は FIFO だけで動いた。3本の接続を跨いでも、300 件が送った順に届いた
- `bound` が仕掛かりを数える定め(ADR 0032 の決定6(上限を `bound` で書く))は、上流が止まる件数を宣言から計算できる形で効いた(64 × 3 = 192)
- 待つ所は body の中の出口の呼び出し(`.await`)にそのまま現れた(ADR 0032 の決定2(待つ所の範囲)の `pressure block` の受付)
- 確かめたのは ADR 0032 の決定1(コンポーネントの中は逐次)・決定6(上限を `bound` で書く)・決定8(接続の中は FIFO)である。再入(決定2)・重ならない仕事の組(決定3)・時計の仕事(決定4)・`ask`(決定7・決定11)・durable の再送(決定9)は通っていない

### 外部との境界

- ルートの system の `expose` を試験の口にする形は、新しい構文無しで書けた
- システムの公開面には `pressure` と配達保証を書く場所が無い。そのため試験の口の振る舞いを動作環境が決め打った。外部を書く時、境界の端の流量と配達保証をどこに書くかが要る(思考実験 33 の論点2(フローの端点)と同じ問い)
- 外部を書かないと、SensorIntake は計測値を素通しに流すだけになる。粒度の指針の「公開面が素通しの委譲だけなら統合を検討する」(第2章 2.5)に当たる形であり、外部を書かない仮置きが作った物である

### プログラムの宣言

- 1ファイルに1つのルートの system と、ファイルの中で一意の名前で足りた。データ宣言は `contains` に現れないが、ファイルの中で引けば困らなかった

### bodyの記法

- 出力言語で直に書く形は、生成器がコンポーネントごとに `<名前>の本体` の trait(`flow in` ごとに一つの非同期の関数)と `<名前>の出口`(`flow out` ごとに一つの関数)を出す形で書けた
- 内部階層(`換算 { pure domain }`・`送り出し { io domain }`)は Rust の側では注記でしか表せず、`pure` の層で入出力をしても誰も止めない。仮置きの通り検査していない
- body が返す障害でコンポーネントの仕事は止まる。`on failure` の `restart` は記述から読んでいるが、まだ動作環境が行わない(再起動と版の入れ替えの試作で行う)

### 動作環境

- 意味の核(待ち行列と `pressure`・期限の判定・記述子の照合と能力)は、標準ライブラリに依らないクレートとして RISC-V の素の目標(`riscv32imac-unknown-none-elf`。ESP32-C6 と同じ系)でも組めた
- 接合面のうち、結合(1つ目)・流す(4つ目)・流れを受ける(5つ目)を Rust の同居の形で通した。器は正準形のバイト列と型の指紋だけを見て、値を解釈しない
- 能力に無い `durable` を要る記述子は、結合の時に拒んだ(ADR 0029(最小の動作環境)の決定3(能力と配置の設定))
- 正準形の形式と型の指紋の作り方は仮である。混在の試作の前に決める(計画書 第4節「Phase 1 の中で決める物」)

### 記述と構造

- `flow` 宣言に `intent` が無い時の検証番号が、仕様書 第3章 3.3 に無い。試作では E0003-1(intent の必須項目の欠落)で拒んだ
- 記述者の名前(日本語)は、Rust の識別子にそのまま写せた。綴り直しの対応表(第5章 5.6)はまだ要らない。Rust の側では命名の警告(`non_snake_case`・`mixed_script_confusables`)を外す必要がある

### 型と単位

- 量の宣言を ASCII の語彙で `quantity 気圧 amount base ヘクトパスカル` と綴った。第6章 6.3 の例は日本語の語(`量`・`計量`・`基準`)のままである
- `id` の中身の表現は仕様書に無い。試作では64ビットの整数とした。正準形の形式と併せて決める
- 単位は Rust の型には残らない(第6章 6.3 の「単位は型情報のみ」の通り)。単位の検査は Shidzuku の側で行う必要がある
